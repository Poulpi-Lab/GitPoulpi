# GitPoulpi

Lightweight, cross-platform Rust TUI Git client - with no Electron footprint. Full commit-tree UI with mouse support (right-click, drag & drop, double-click), a keyboard-first shortcut system with a fuzzy command palette, hosting/issue integrations (code hosts: GitHub, GitLab incl. self-managed, Gitea and Forgejo incl. Codeberg, Azure DevOps, Bitbucket, Gerrit; issue trackers: Jira, Trello, Linear, YouTrack, Redmine, and local Markdown notes; personal tokens, no accounts), and equally-capable CLI and MCP interfaces so AI agents can drive it just like a human.

**Starting cold?** Read `docs/developer/where-we-are.md` first: snapshot with the module map, what is open, hand checks, and "Conventions that bit us" (Log row arithmetic, `row_to_index`'s `top_offset`, emoji presentation, falsifying buffer tests, never blocking the render thread...). Read that section before any TUI change.

Then as needed: `docs/architecture/overview.md` (architecture), `docs/architecture/session-and-state.md` (per-feature decisions and traps), `docs/developer/testing.md`, `docs/developer/visual-verification.md` (screenshotting the TUI without capturing the wrong window), `docs/developer/i18n.md`, `docs/developer/perf-budgets.md`, `docs/developer/contributing.md`.

## Workspace layout

| Crate | Responsibility |
|---|---|
| `gitpoulpi-core` | Domain model + `GitBackend` trait + undo journal vocabulary. No TUI/CLI/MCP/IO-framework dependencies - everything else is an adapter around this. |
| `gitpoulpi-git2-backend` | `GitBackend` over libgit2 (`git2` crate), decorating `gitpoulpi-cli-backend` for operations git2 doesn't support well. |
| `gitpoulpi-cli-backend` | `GitBackend` driving an installed system `git` (machine-readable output only). Also the standalone "system git" backend choice. |
| `gitpoulpi-config` | Config schema, TOML load/save, OS-correct paths, themes (presets chosen at build time by `GITPOULPI_THEMES`). |
| `gitpoulpi-log` | Application log: a `tracing` sink with a live level, daily files, retention, size rotation and secret redaction. The TUI's Activity Log reads it; a standalone daemon writes to it too. |
| `gitpoulpi-secrets` | Credential-helper adapter (tokens use the OS credential helper, else stay in memory for the session). SSH stays on the system ssh-agent. |
| `gitpoulpi-session` | Named-session (tabs/layout) and per-repo state (ref filters, pending auto-stash) persistence. |
| `gitpoulpi-hosting` | Hosting/issue API clients (GitHub, GitLab, Gitea/Forgejo, Azure DevOps, Bitbucket, Gerrit, Jira, Trello, Linear, YouTrack, Redmine, local Markdown issues), issue/PR references, clone helpers, `HttpTransport` (tests never open a socket). |
| `gitpoulpi-ai` | AI (off by default, never needs an account): completion clients (OpenAI-compatible, Anthropic, local agent CLI such as `claude -p` as a subprocess), prompt builders, answer parsers, `assist::Job` shared by TUI and CLI. HTTP via `gitpoulpi-hosting`'s transport. |
| `gitpoulpi-i18n` | Compiled-in UI catalogs (`locales/*.toml`, 17 languages), typed accessors generated by `build.rs`. CLI/MCP output stays English. |
| `gitpoulpi-ipc` | Client↔daemon protocol shared by TUI/CLI/MCP: requests + a live event-subscription stream. |
| `gitpoulpi-daemon` | Background per-session server owning all state, so mutations from any frontend show up live in the others. |
| `gitpoulpi-tui` | ratatui/crossterm UI - an IPC client. A library used by `gitpoulpi`; its own bin exists only for tests and `cargo run`. |
| `gitpoulpi-commands` | Shared command layer: the `gitpoulpi` clap `Cli` tree, the IPC `Session` client, and `execute` - one mapping per subcommand, run by both `gitpoulpi-cli` and `gitpoulpi-mcp` so their surfaces can't drift apart. |
| `gitpoulpi-updater` | `gitpoulpi-updater`: the separate program that stops every GitPoulpi process of an install, updates it by its install channel (file swap, or the package manager), verifies, rolls back on failure and relaunches. Only its Program Files copy runs elevated. |
| `gitpoulpi-cli` | `gitpoulpi`, the one real program: the scriptable CLI, the terminal UI when run without a subcommand, `mcp serve`, `daemon`, `launch`. An IPC client, auto-starts its session's daemon. |
| `gitpoulpi-mcp` | MCP server: one tool per `Cli` leaf (via `rmcp`), gated by `config.toml`'s `[mcp]` table - an IPC client. A library used by `gitpoulpi mcp serve`; its own bin exists only for tests and `cargo run`. |
| `gitpoulpi-shim` | Std-only relay (about 0.3 MiB), copied into the archive as `gitpoulpi-tui` and `gitpoulpi-mcp`: it starts the `gitpoulpi` next to it as that program. |
| `gitpoulpi-testkit` | Fixture-repo builder + backend contract-test suite + spawn budgets. |
| `xtask` | Dev/release tasks (`cargo run -p xtask -- <task>`): `tui` (PTY driver behind the `pty_*` tests), `perf`, `dist`, `build-custom`, `features`, `merge-fixture`, `desktop-lock`, `emit`. |

## Architecture principles

1. **`gitpoulpi-core` has no I/O-framework dependencies.** Never `git2`, `ratatui`, `tokio`'s runtime, or any frontend crate.
2. **`GitBackend` is the seam.** Every mutation and every read goes through it. `Git2Backend` and `SystemGitBackend` must behave identically - enforced by the contract suite in `gitpoulpi-testkit`.
3. **One daemon per named session owns all state.** TUI, CLI and MCP never touch `GitBackend` directly; they are IPC clients, so they never disagree and changes show up live in the others.
4. **Cross-platform is a constraint on every component.** Windows is the primary daily driver; Linux (incl. Wayland/Hyprland) and macOS (best-effort, untested) must keep working. Mitigations per component: `docs/architecture/overview.md`.
5. **Every mouse interaction has a keyboard equivalent**, and the command palette reaches 100% of functionality.

## Build / run / test

```
cargo build --workspace
cargo test --workspace            # everything (Linux CI runs this)
cargo run -p xtask -- test        # fast tier: all but the pty_* tests; --tier pty | full
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
```

- **Profiles:** `release` is the everyday build, tuned for rebuild time (incremental, 16 codegen units, no LTO; `./build.sh` / `build.cmd` → `scripts/build.*`). `dist` is packaging (thin LTO, 16 codegen units; `./build-opti.sh` / `build-opti.cmd` → `scripts/build-opti.*`). `custom` = `cargo run -p xtask -- build-custom` (or `./build-custom.sh` / `build-custom.cmd`, interactive) builds chosen languages/integrations/features/themes into `target/custom/` (`docs/user/custom-builds.md`).
- **Test tiers:** `fast` (default) = everything except the PTY end-to-end targets (`pty_*`), `pty` = only those, `full` = both (`xtask test --tier ...`, selection derived from `cargo metadata`; `docs/developer/testing.md`). `scripts/check.ps1` = fmt + clippy + fast, `-Pty` adds the PTY tier, `-Full` = all, `-Quick` = fmt + clippy; it prints which tiers ran and which were skipped.
- **Feature-matrix gate:** `cargo run -p xtask -- features [--quick]` (clippy with each feature off, twice: bins only as a custom build compiles them, then `--all-targets`; `scripts/check.ps1 -Features` runs `--quick`).
- **sccache (local, optional):** a gitignored `.cargo/config.toml` sets `rustc-wrapper = "scripts/sccache-deps-only.sh"` (inherited by the worktrees under `.claude/worktrees/`, resolved against the main checkout) so they share compiled third-party dependencies. The script sends only registry/git crates (`CARGO_MANIFEST_DIR` under `CARGO_HOME`) through sccache and runs workspace crates (`crates/*`, `xtask`) plain, so a cache hit can never replay another tree's sources or diagnostics. Never point `rustc-wrapper` at bare `sccache`. Delete the file to turn it off; if a build shows errors from code your tree does not have, rerun with `RUSTC_WRAPPER=` and `cargo clean -p <crate>`.
- **CI is disabled** (`gh workflow disable CI`, 2026-09-29: kept failing; re-enable with `gh workflow enable CI`). When enabled, `.github/workflows/ci.yml` runs Ubuntu (fmt, clippy, full tests) on push to `main`; Windows (fmt + clippy only, its test compile exceeds the job timeout) and macOS (fast tier) weekly / on demand (`gh workflow run CI`), because Windows/macOS minutes cost ~2×/~10×. **Releases:** `.github/workflows/release.yml` runs only on a pushed `releases/v*` tag (tags are prefixed by purpose, see `CONTRIBUTING.md` "Tags"): `xtask dist` on Linux x86_64, Windows x86_64 and macOS arm64/x86_64, then one GitHub release with every archive and its `.sha256` (notes from the tag's `CHANGELOG.md` section, else generated; a `-` in the tag makes a pre-release). **Windows tests are local:** `pwsh scripts/check.ps1` (fmt + clippy + fast tier) before pushing, `pwsh scripts/check.ps1 -Full` (adds the PTY tier) before a release tag; `scripts/install-hooks.ps1` installs a pre-push hook running `-Quick` (fmt + clippy). Batch pushes: one per coherent set of commits.

## TDD expectations

- New `GitBackend` operation: contract test in `gitpoulpi-testkit` first (red), then `Git2Backend`, then `SystemGitBackend`, then the TUI/CLI/MCP surface. Prefer extending the contract suite over backend-specific tests.
- TUI: every fix gets a PTY test (`crates/gitpoulpi-tui/tests/pty_*.rs`, driven by `xtask::pty`), falsified (break the fix, see it red, restore). Buffer/`insta` tests via `ratatui::TestBackend` for rendering.
- CLI: `assert_cmd` tests asserting on deserialized JSON, never string matches.
- Every new mutation decides its undo story (journaled, or explicitly not undoable) and tests it.

## Conventions

- Conventional-commit-style messages (`feat:`, `fix:`, `docs:`, ...).
- Every change passes fmt, clippy `-D warnings` and `cargo test --workspace` on Linux and Windows.
- Tests use temp config dirs and fixture repos; never your real config.
- Code is the source of truth: docs record decisions, reasons and traps, not what the code already says.

## Pointer for AI agents

For git work in this repo you may use the `gitpoulpi` CLI/MCP (see `skills/gitpoulpi/SKILL.md`); plain `cargo`/`git` is fine too.
