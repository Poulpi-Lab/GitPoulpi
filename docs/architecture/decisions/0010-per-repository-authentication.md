# 0010 - Per-repository authentication

## Status
Accepted (2026-11-09). Extends ADR 0004 (credential strategy) and ADR 0008 (per-profile SSH keys). Implemented in slices; this record states the whole design, and `docs/architecture/session-and-state.md` ("Per-repository authentication") says which slice has landed.

## Context
Until now a repository could authenticate in only two ways that GitPoulpi controls, both global: `credentials.https_mode` and `ssh.private_key_path`. Both are process-wide statics that the daemon sets before each network operation. One daemon serves many repositories (ADR 0006), so a per-repository value kept in the same place would race between two concurrent fetches, and the one existing per-repository choice, the SSH pin of ADR 0008, writes `core.sshCommand` into `.git/config`, a file the repository's own tooling can also write.

Two real cases drive this: a repository that carries its own `credential.helper` pointing at a script that does not exist on this machine (git then sends no credentials and the remote's refusal hides the real cause), and a person with a work and a personal account who must never push to one with the other's identity.

## Decision
1. **Per-invocation authentication at the git boundary.** `gitpoulpi_core::domain::NetworkAuth` describes what one repository's network git processes get: a credential helper list, a username, "never prompt", a reset of `http.extraHeader`, an ssh command and a few non-secret environment variables. `GitBackend::set_network_auth(&RepoRef, Option<NetworkAuth>)` sets it. It lives in memory only, is never persisted by the backend, and is not a repository mutation (not journaled, not undoable, like settings).
2. **One place applies it.** `apply_network_auth` in the system-git backend's process layer builds the credential and ssh part of every network command: the async ones (`git_async`: fetch, pull, push, clone, LFS, tag push) and the synchronous one (`run_network`: submodule update). With an entry for the repository it applies **instead of** the process-wide credential mode and ssh key; without one nothing changes. `Git2Backend` forwards the call to its system-git fallback, which already does all its networking (ADR 0001), so both backends behave identically by construction. The registry is keyed by the canonical repository root and is process-wide because the network operations are free functions that only receive a root.
3. **The helper reset is what makes a repository's own helpers harmless.** With `credential_helpers = Some(list)` the command line gets `-c credential.helper=` and then one `-c credential.helper=<entry>` per entry. Command-line configuration comes after every file, so the reset clears the helpers of `.git/config`, of files it includes and of `credential.<url>.helper` entries. `http.extraHeader` is reset the same way, `core.askPass` is emptied and `GIT_ASKPASS` / `SSH_ASKPASS` are removed when the entry says no prompt.
4. **ssh precedence.** An explicit choice for a repository ranks first: the entry's `ssh_command` is set as `GIT_SSH_COMMAND` on the child, which git ranks above `core.sshCommand` and which replaces a `GIT_SSH_COMMAND` the user exported. Then, as before: the environment, `core.sshCommand`, the global key, ssh defaults.
5. **No secret on a command line or in an environment.** `NetworkAuth` holds helper commands, never a credential. A later slice supplies tokens through a helper that asks the daemon for a short-lived, host-bound grant; this record only fixes the seam it plugs into.
6. **A connection test (planned in the same wave).** `GitBackend::remote_access_check` runs `ls-remote --heads` against a remote's fetch (or push) URL through the same code path, so the entry applies, and reports which identity answered. It is the basis of the "Test connection" action. It is a network read: it never changes the repository.
7. **Quoting.** `gitpoulpi_core::repo_config::sh_quote_path` is the one quoting of a path for the `sh` git runs a command through (double quotes, `"`, `$` and the backtick escaped, backslashes turned into `/`). `ssh_command_for_key` and the future credential helper command both use it.
8. **Hardening that must not move.** The transport allowlist (`protocol.allow=never`, `ext::` stays off) and the cleared environment (`GIT_DIR` and friends) are applied to every command, entry or not, and keep their tests. The entry's `-c` arguments sit after the allowlist and before the command's own arguments.

Not decided here and added by later slices: where a profile is stored (a private file, never the repository, `RepoState` or git config), how the daemon resolves it into a `NetworkAuth` before each transfer, the credential broker and its grants, the IPC, CLI/MCP and TUI surfaces. The rule for them is already fixed: a profile that cannot be used refuses the transfer, it never falls back to the machine's own identity.

## Consequences
- Two repositories with different authentication can transfer at the same time without crossing identities (contract check `check_two_repositories_with_different_auth_do_not_cross`).
- The behaviour without an entry is byte for byte the previous one, including the global credential mode and key.
- The registry is process-wide: two backend values in one process share entries for the same repository root. The daemon has one backend, so this is not observable there; tests use separate temporary repositories.
- A repository's helper that a user wants to keep must be listed in the entry on purpose: the reset removes it.
- Tests need no network: a loopback HTTP server that asks for credentials and records what arrives, and a stub `ssh` that runs the remote command locally (`gitpoulpi-testkit`, `AuthHttpRemote` and `StubSsh`; the latter is Unix only because it is a `sh` script).
