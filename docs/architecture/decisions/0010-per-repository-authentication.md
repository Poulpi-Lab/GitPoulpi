# 0010 - Per-repository authentication

## Status
Accepted (2026-11-09). Extends ADR 0004 (credential strategy) and ADR 0008 (per-profile SSH keys). Implemented in slices; this record states the whole design, and `docs/architecture/session-and-state.md` ("Per-repository authentication") says which slice has landed.

## Context
Until now a repository could authenticate in only two ways that GitPoulpi controls, both global: `credentials.https_mode` and `ssh.private_key_path`. Both are process-wide statics that the daemon sets before each network operation. One daemon serves many repositories (ADR 0006), so a per-repository value kept in the same place would race between two concurrent fetches, and the one existing per-repository choice, the SSH pin of ADR 0008, writes `core.sshCommand` into `.git/config`, a file the repository's own tooling can also write.

Two real cases drive this: a repository that carries its own `credential.helper` pointing at a script that does not exist on this machine (git then sends no credentials and the remote's refusal hides the real cause), and a person with a work and a personal account who must never push to one with the other's identity.

## Decision
1. **Per-invocation authentication at the git boundary.** `gitpoulpi_core::domain::NetworkAuth` describes what one repository's network git processes get: a credential helper list, a username, "never prompt", a reset of `http.extraHeader`, an ssh command and a few non-secret environment variables. `GitBackend::set_network_auth(&RepoRef, Option<NetworkAuth>)` sets it. It lives in memory only, is never persisted by the backend, and is not a repository mutation (not journaled, not undoable, like settings).
2. **One place applies it.** `apply_network_auth` in the system-git backend's process layer builds the credential and ssh part of every network command: the async ones (`git_async`: fetch, pull, push, clone, LFS, tag push) and the synchronous one (`run_network`: submodule update). With an entry for the repository it applies **instead of** the process-wide credential mode and ssh key; without one nothing changes. `Git2Backend` forwards the call to its system-git fallback, which already does all its networking (ADR 0001), so both backends behave identically by construction. The registry is keyed by the canonical repository root and is process-wide because the network operations are free functions that only receive a root.
3. **The helper reset is what makes a repository's own helpers harmless.** With `credential_helpers = Some(list)` the command line gets `-c credential.helper=` and then one `-c credential.helper=<entry>` per entry. Command-line configuration comes after every file, so the reset clears the helpers of `.git/config`, of files it includes and of `credential.<url>.helper` entries. `http.extraHeader` is reset the same way, `core.askPass` is emptied and `GIT_ASKPASS` / `SSH_ASKPASS` are removed when the entry says no prompt.
4. **ssh precedence.** An explicit choice for a repository ranks first: the entry's `ssh_command` is set as `GIT_SSH_COMMAND` on the child, which git ranks above `core.sshCommand` and which replaces a `GIT_SSH_COMMAND` the user exported. Then, as before: the environment, `core.sshCommand`, the global key, ssh defaults.
5. **No secret on a command line or in an environment.** `NetworkAuth` holds helper commands, never a credential. Tokens reach git through a helper that asks the daemon for a short-lived, host-bound grant (12 and 13 below); `NetworkAuth` only fixes the seam it plugs into.
6. **A connection test.** `GitBackend::remote_access_check` runs `ls-remote --heads` against a remote's fetch (or push) URL through the same code path, so the entry applies, and reports which identity answered. It is the basis of the "Test connection" action. It is a network read: it never changes the repository.
7. **Quoting.** `gitpoulpi_core::repo_config::sh_quote_path` is the one quoting of a path for the `sh` git runs a command through (double quotes, `"`, `$` and the backtick escaped, backslashes turned into `/`). `ssh_command_for_key` and the future credential helper command both use it.
8. **Hardening that must not move.** The transport allowlist (`protocol.allow=never`, `ext::` stays off) and the cleared environment (`GIT_DIR` and friends) are applied to every command, entry or not, and keep their tests. The entry's `-c` arguments sit after the allowlist and before the command's own arguments.

9. **The profile is a private file, resolved by the daemon before each transfer.** `<private>/repo-auth.toml` (0600 / user-only DACL, keyed by the repository's data-folder name, never in the repository, `RepoState` or git config) holds one profile per repository: an HTTPS source (system, integration, helper, token command) and an SSH source (system, key file, integration key). The daemon reads it live, resolves it into a `NetworkAuth` and calls `set_network_auth` before every transfer (`credentials::apply_for`). A profile that cannot be used (unreadable file, missing account or key, a source not built yet) **refuses the transfer** with the typed `RepoAuthUnavailable { reason }`: it never falls back to the machine's own identity. Choosing a profile is a setting: not journaled, not undoable.
10. **`ignore_repo_helpers` is a scope filter.** The System source can keep only the credential helpers of system and global scope (`git config --show-scope`; an included file has the scope of the file including it, so includes of `.git/config` are dropped too); URL-scoped ones it keeps are re-added with their URL (`NetworkAuth::credential_url_helpers`) so they do not widen to every host.
11. **SSH key file.** The ssh program is the first word of the effective global `core.sshCommand`, else `ssh`; the key is offered with `IdentitiesOnly`, and the profile may add `UserKnownHostsFile` and `StrictHostKeyChecking=yes`.

12. **The credential broker: an account's token reaches git through a grant, never through an argument or an environment variable.** For the integration HTTPS source the daemon resolves the account (its record in the trust store, its git user name, its token), issues a **grant** and gives git's child only a credential helper plus two non-secret variables. The helper is `!"<current executable>" --gitpoulpi-git-credential`: every binary that can host a daemon (`gitpoulpi`, `gitpoulpi-tui`, `gitpoulpi-mcp`) calls `gitpoulpi_ipc::git_credential::run_if_requested()` first thing in `main`, and when started that way it reads git's request on stdin, asks the session's daemon over the token-authenticated IPC (`OperationKind::CredentialGrant`, a daemon-control request like `Hello`) and prints `username=` and `password=` for `get`. It holds no secret, prints nothing on any failure and exits 0, so git ends with its own "no credential" failure.
13. **A grant is bound to a host and to one operation.** It answers `get` only when the protocol is the account's recorded scheme and `host[:port]` equals the account's **trust-store origin** character for character (lowercased), never the config's URL: an edited account address refuses the transfer (`RepoAuthUnavailable`, from the trust gate) instead of moving the token. Anything else gets an empty answer and the daemon remembers the refused host; if the transfer then fails, the error is replaced by `GrantRefused { host, expected }` ("GitPoulpi did not send the account's token to evil.example: it is not github.example"). This is what keeps a repository's own `url.<x>.insteadOf` from sending the token to another server. The grant lives exactly as long as the operation (a drop guard: success, failure and cancel all revoke it). A fetch and a push of one repository share the transfer lock and each process reads the repository's current auth when it starts, so grants for the same repository and the same credential are shared and counted, and revoked when the last holder lets go. `store` (git reports the credential accepted) is what a connection test reads to name the identity (`RemoteAccessReport.accepted_identity`); `erase` (a 401 or 403) marks the token refused.
14. **The session a helper reaches is the daemon's own.** The helper learns the session name from `GITPOULPI_CREDENTIAL_SESSION`; the daemon stamps its own session name on every request in the server loop (a client-written name is untrusted), and that is the value `credentials::apply_for(backend, repo, session)` puts in the variable.
15. **Which user name goes with a token** is a pure table, `gitpoulpi_hosting::git_username(kind, account, login)`: GitHub `x-access-token`, GitLab `oauth2`, Bitbucket Cloud the account (or `x-token-auth` for an access token, empty account), Azure any non-empty name, Gitea/Forgejo the login, Gerrit the account; a profile's own `username` overrides it. A kind that is not a code host (an issue tracker) is refused as a source.
16. **Exact-value redaction.** The shape rules of `gitpoulpi_core::redact` cannot see a token with no known prefix, so the daemon registers every token it resolves with `redact_register_secret` and `redact` (hence the Activity Log, the log files and every `ErrorDetail`) masks that exact value from then on.
17. **The daemon's `hosting` feature** (default on; the tui and commands `hosting` features forward it) gates the daemon's dependency on `gitpoulpi-hosting` (without its HTTP clients: `default-features = false`, no socket) and `gitpoulpi-secrets`. Without it the System and key sources remain and an account source refuses ("this build has no GitPoulpi accounts"); `xtask features --quick` builds that combination.
18. **Helper and token-command sources run a command only a person confirmed.** A command lives only in the private store, so a repository can never cause one to run. `RepoAuthSet` stores a helper or a token command only with `confirm: true`; a request without it gets the typed refusal `NeedsConfirmation`; the daemon computes (never believes a client's) `confirmed_sha256` (SHA-256 hex of the helper string, or of the argv joined by NUL) over the helper string or the argv, and `script_sha256` over every file the command names that lies inside the work tree (path relative to the root plus content). Whether the requester is a person is decided by the surface, as for hook and history-rewrite script trust: the CLI sends `confirm` only when `Session::may_trust()`, the TUI after its dialog, MCP never; the daemon socket is not a boundary against local malware. Before every use the daemon re-checks both hashes: a different command is `RepoAuthUnavailable`, a changed in-tree file (a pull can rewrite a tracked script) is `RepoAuthCommandChanged { path }`, and the transfer is refused until the command is confirmed again. A request without `confirm` is stored only when its command is the very one already confirmed with unchanged files (editing hosts or the cache time keeps the confirmation).
19. **Helper source**: `credential_helpers = Some([helper])` (or, when the profile lists `hosts`, URL-scoped `credential.https://<host>.helper` entries after the reset) and no prompt; git runs the helper as the person wrote it.
20. **Token command source**: the GitPoulpi helper plus a grant whose `get` runs the argv itself (`gitpoulpi_cli_backend::run_command`): no shell, cwd = the repository root, stdin closed, 30 s, the whole process tree killed on timeout or cancel. The first non-empty stdout line is the token, or `username=` / `password=` lines; the profile's `username` wins over the command's, else `x-access-token`. The token is cached in memory per (root, argv) for `cache_minutes` (default 50; 0 = never) until git reports it refused (`erase`: 401/403), until the profile is set or cleared, or the daemon ends. Commands run one at a time (git can ask twice in one transfer). The grant is host-bound to the profile's `hosts` (default: the host of `origin`, https only; plain http only when every host is loopback). stderr goes to the Activity Log through `redact`, the token is registered with `redact_register_secret`, and a failure is `TokenCommandFailed { exit, stderr_tail }` (redacted; `exit` is `None` for a timeout or a command that cannot start), which replaces git's "terminal prompts disabled".

21. **A helper reaches the daemon that issued its grant, published or not.** An embedded daemon of a short-lived CLI run publishes nothing (`Session::connect(.., publish: false)`), so a helper that rediscovered the daemon through `sessions/<session>.port` found no file, or a stale one, printed nothing and git failed with "terminal prompts disabled" (the bug: a token-command or integration profile never worked from a standalone `gitpoulpi` run unless a TUI of that session was open). The grant exists only in the daemon that issued it, so the helper must go to that daemon. While a grant lives, the daemon writes a user-only file (`secure_fs` 0600 / user-only DACL) `sessions/<session>.grant-<id>.cred` holding its port and IPC token, and the child gets its **path** in `GITPOULPI_CREDENTIAL_ENDPOINT` next to the grant id and the session. The file is removed when the grant's last holder lets go (a day-old leftover of a crash is swept the next time one is written). The helper reads that file first and only then falls back to the session's port file (a grant from a daemon that registered no endpoint). The file wins over a published daemon of the same session: that one does not know the grant.
22. **Why a file path and not the token.** The IPC token is what makes the daemon refuse any process that cannot read the user's config folder: a same-user process can already read the published token file, so a published daemon loses nothing. An environment is readable by more than the helper: git, every hook and credential helper it runs, and (same user) `/proc/<pid>/environ` or the process list of the OS; and it is inherited by anything those start. Putting the token value there would make an unpublished daemon's secret as widely readable as that. A path gives a reader nothing unless it can read a user-only file, which also exposes the token only while the operation runs, and the file is deleted with the grant. Argv is excluded for the same reason as before. A hook that runs during the operation can read the file, as it can already call `git credential fill` (decision 13): no new power. The alternative of a per-grant random capability token carried in the environment was rejected: the helper would still need the endpoint, and a second secret in an environment is the exposure this decision avoids.
23. **A helper that could not reach the daemon is a typed error.** A grant records whether any `CredentialGrant` request for it ever arrived. When the transfer failed with git's "could not read Username/Password ... terminal prompts disabled" and the grant was never asked about, `GrantGuard::explain` / `reads_as` turns it into `Error::CredentialHelperUnreachable` (wire `TypedError::CredentialHelperUnreachable`, "GitPoulpi's credential helper could not reach the daemon") instead of `AuthFailed`; the TUI reading leads to the SSH & credentials page. A connection test, whose per-remote failure is an `ErrorDetail` and not an `Error`, gets the same sentence as the first line of the report's stderr.

Not decided here and added by later slices: the CLI/MCP and TUI surfaces.

## Consequences
- Two repositories with different authentication can transfer at the same time without crossing identities (contract check `check_two_repositories_with_different_auth_do_not_cross`).
- The behaviour without an entry is byte for byte the previous one, including the global credential mode and key.
- The registry is process-wide: two backend values in one process share entries for the same repository root. The daemon has one backend, so this is not observable there; tests use separate temporary repositories.
- A repository's helper that a user wants to keep must be listed in the entry on purpose: the reset removes it.
- Tests need no network: a loopback HTTP server that asks for credentials and records what arrives, and a stub `ssh` that runs the remote command locally (`gitpoulpi-testkit`, `AuthHttpRemote` and `StubSsh`; the latter is Unix only because it is a `sh` script).
