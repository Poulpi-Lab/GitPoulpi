# i18n contributor guide

This page is the working reference. Crate: `crates/gitpoulpi-i18n`
(std only, so the TUI and the CLI use it alike).

## Languages

Shipped: `en`, `fr`, `es`, `pt-BR`, `pt-PT` (two separate languages), `it`, `de`,
`zh-CN` (简体中文), `ja` (日本語), `ko` (한국어), `ru` (русский), `uk` (українська), `pl` (polski), `cs` (čeština), `nl` (Nederlands), `sv` (Svenska), `tr` (Türkçe), plus the pseudo-locale `qps`.
To add another, see "Adding a language". `Lang` has one variant each; `Lang::parse`
accepts `fr`, `fr_CA.UTF-8`, `pt`/`pt_BR` (Brazilian), `pt-PT`/`pt_AO` (European),
`zh`/`zh_CN`/`zh-Hans` (simplified only: `zh-Hant`, `zh_TW`, `zh_HK`, `zh_MO` give
`None`, so `auto` falls back to English), `ja_JP`, `ko_KR`, `ru_RU`, `uk_UA`,
`pl_PL`, `cs_CZ`, `sv_SE`, `tr_TR`, `nl_NL`/`nl_BE`, `qps`.
`SHIPPED` (generated by `build.rs`) lists the complete ones that are built into
the binary (see "Custom builds" below). A language without a file, or
a key missing from its file, shows English (`MISSING` records it; the catalog test
fails for shipped languages).

## The API

```rust
use gitpoulpi_i18n::{msg, M, Lang};
msg::toolbar::PULL.get()              // &'static str, no allocation
msg::status::branch_deleted(&name)    // String; one fn per message with {args}
msg::status::files_staged(n)          // plural: n: u64 first, then other args
```

- Plain message: `const M` (a `Copy` id). Static tables of labels stay `const`.
  `M::get()` current language, `get_in(lang)`, `english()` (bilingual search).
- `{name}` placeholders become typed fn parameters (`impl Display`), in order of
  first appearance in English; a translation may reorder them. `{{` / `}}` are
  literal braces. A plural's first parameter is `n: u64`.
- `epoch()` changes on every language, vocabulary or host switch: key caches of
  resolved text (palette haystacks, wrapped help, measured widths) on it.
- Production state: `set(Lang)`, `set_translate_git_terms(bool)`,
  `set_merge_terms(bool)` (PR/MR host). Tests: `with_lang`, `override_lang`,
  `override_git_terms`, `override_merge_terms`: per-thread, restored on drop. A
  test that sets nothing gets English.
- `month_name(1..=12)`, `month_abbr(..)` and `msg::reltime::*` carry dates.

### Cost model

Plain `get()`: one thread-local read, one atomic load, a few indexes; `&'static str`.
Message with arguments: one `String::with_capacity` plus pushes over segments
split at build time; call it where state changes, not per frame. Switching
language or vocabulary: a few atomic stores. Nothing is parsed at run time.
Storage: all text in one deduplicated blob addressed by integer tables (not one
`&str` per message: that cost 6.5 MB of relocations, `binary-size.md`); only
messages with term tokens carry variants. `tests/lookup_snapshot.rs` compares
every lookup against a reference.

## Call-site rules

- Draw code passes `M::get()` straight into a `Span`; no `.to_string()`.
- Messages with arguments are built where state changes, as `format!` is today.
- Never store a resolved string in long-lived state: store the `M`.
- Never concatenate sentence pieces; one message with several placeholders.
- Never derive a display label from a config value (`as_str`): map to an `M`.
- Glyphs (the AI star, VS15 glyphs) stay in code, outside messages.

## Adding a key

1. Add it to the right `[section]` of `locales/en.toml` (sections are named after
   the TUI area; key names are lowercase snake_case, not a Rust keyword). Write the
   English by `l10n/en.md` (capitalization per kind of text, voice, ellipsis, terms).
2. Add it to every other `locales/*.toml` in the same section (a shipped language missing a key fails the catalog test).
3. Ambiguous words get a `# context:` comment above the key; it is copied into
   the generated doc comment and the translator sees it.
4. Use `msg::section::NAME` (plain) or `msg::section::name(..)`.

Build errors (they name file and key): key not in `en.toml`; placeholder set
differs from English (a plural's `one` may drop `{n}`); plural in one language
and not another; `other` without `{n}`; unbalanced braces; unknown `{$term}`;
missing `_meta.language_name`. Run `cargo test -p gitpoulpi-i18n` afterwards.

## Message shapes

```toml
key = "Staged {n} files"
key = { one = "Staged {n} file", other = "Staged {n} files" }     # plural
key = { git = "Undo {$commit}", local = "Undo {$commit}" }        # per vocabulary
key = { one = { git = "..", local = ".." }, other = { git = "..", local = ".." } }
```

Plural rules (CLDR, integers; `Lang::plural_form`): en, es, it, de, pt-PT, nl, sv,
tr: `one` iff n = 1. fr and pt-BR: `one` iff n is 0 or 1. zh-CN, ja, ko: always
`other`. ru, uk: `one` (n % 10 = 1 and n % 100 != 11), `few` (n % 10 in 2..4 and
n % 100 not in 12..14), `many` otherwise. pl: `one` iff n = 1, `few` as ru, `many`
otherwise. cs: `one` iff n = 1, `few` for 2..4, `other` otherwise. A plural table
always has `one` and `other` (both with `{n}` but `one` may drop it); a language
whose rule has `few` / `many` adds them (`few = ".."`, `many = ".."`; each must
contain `{n}`; a missing one falls back to `other`). For ru/uk/pl `other` is only
for fractions, so write it as `many`.

## Git terms and the "Translate git terms" setting

Maintainer rule: git words stay English everywhere by default; a Settings checkbox
(off by default, below the language selector) switches to the translated
vocabulary (fr "remiser", "étiquette", "valider"). So every language holds both.

- `[term]` in every language file: `name = { git = X, local = X }`. `git` is the
  English vocabulary, `local` the translated one. English has both, identical.
- A message writes `{$commit}` (as is), `{$Commit}` (capitalised) or
  `{$COMMIT}` (upper case). The build expands it into static variants, so
  `get()` is still `&'static str`.
- `{$^pr}` capitalises every word ("Pull Request", English Title Case labels such as
  "My {$^prs}"); other languages use `{$pr}` / `{$Pr}`.
- Host-dependent terms (`pr`, `prs`, `pr_abbr`) are `{ pull = .., merge = .. }`
  in both vocabularies; the host (GitHub or GitLab) selects pull or merge.
- When grammar changes with the term (fr "le commit" / "la validation"), write
  the message as `{ git = "..", local = ".." }` instead of relying on the token.
- A term is a noun or a verb form; use separate terms where a language needs both
  (`commit` / `commits`). Terms missing from a language fall back to English.
- Variant bits: see "English git words" below (`(english << 2) | (translate << 1) | merge`); only messages that vary carry variants.

### Noun forms of the git actions

`push`, `pull`, `fetch`, `merge`, `rebase` are the English words in git mode and the language's
*verb* in local mode (fr "pousser", es "enviar", it "invia"), which is what a button or a "{$push}
the branch" sentence needs. A sentence that names the operation ("LFS push: 2/5 files", "from
before the pull") needs the *noun* ("l'envoi", "el envío"), so the same five words exist as
`push_noun`, `pull_noun`, `fetch_noun`, `merge_noun`, `rebase_noun` in every `[term]` table:
`git` = the English word (the verb term's `git` value), `local` = the noun. English has them
identical to the verbs. Use them where the sentence is a noun phrase: `autostash.reason_*`
(`the {$pull_noun}`), `lfs_ui.verb_*` (`LFS {verb}: ...`), `log_pane_commit_9/11` ("only
{$rebase_noun}"). Grammar still decides per language: when the article or a case ending
changes with the vocabulary write a `{ git, local }` pair around the token (es `{ git = "del
{$pull_noun}", local = "de la {$pull_noun}" }`; it "al" / "allo"); when the language declines
the noun (pl, cs genitive / instrumental) write the inflected words in the pair instead of the
token. Imperative hints and buttons (`footer_hint.push`) stay on the verb terms.

### Counted phrases

A message holds one count at most (`{ one, other }` plus `few` / `many`). Never write "file(s)"
or "{n} lines" with a fixed noun: one plural message per number, and a plain message that joins
them, so each language inflects each noun and may reorder or re-punctuate the parts:

```toml
changes_tooltip = "{files}, {insertions}, {deletions}"          # the joiner
changes_files = { one = "{n} file changed", other = "{n} files changed" }
changes_insertions = { one = "{n} insertion", other = "{n} insertions" }
```

The call composes them (`event_loop/draw/overlay_menus.rs::changes_tooltip`); `retention_unit_days` (and weeks, months, years), `unit_minutes` (and milliseconds, seconds, hours) and
`help_title_filtered` are plurals of their own count. `tests/catalog.rs` fails if a shipped
language still renders "(s)" or "(es)".

### Stash verbs and pane names

`pop`, `apply` and `stash_drop` are terms (git: the English verb; local: the language's verb), used
by the toolbar button and the stash menu rows (`{$Pop}`, `{$Apply}`, `{$Stash_drop}`). `drop` is
the rebase action, a different word in several languages. `staged_files` / `unstaged_files` are
the titles of the two file panes (`status_pane.staged_title` is just `{$staged_files}`); messages
that name a pane use the same tokens so they cannot drift from the title.

### Stage terms and the vocabulary lint

`stage`, `unstage`, `staged`, `unstaged` are terms like `commit` (git = local = English in
en.toml). Capitals: `{$Stage}`. Where grammar inflects (fr "indexé/indexés") write a
per-message `{ git = "..", local = ".." }`; fr git mode reads "{n} fichiers staged". Local
forms are in each catalog's `[term]` table.

`crates/gitpoulpi-i18n/tests/git_vocabulary.rs` lints the catalogs. Git mode (every non-en
language, "Translate git terms" off): if the English text of a message holds a git word
(commit, push, pull, fetch, stash, tag, merge, rebase, cherry-pick, diff, stage family), the
localized text must keep the same stem. Local mode (secondary): where a language's local term
differs from the git one, the text must not use the English word. The local-mode check matches
whole English words (`tag`, `tags`, `tagged`, `unstaged`...), not stems, so a local word that only
shares a stem (sv "tagg", es "rebasar") passes. `agent_reason.*` is English only (see below).

Known violations are baselined per language in `tests/git_vocabulary/<code>.toml`
(`git_mode` and `local_mode` key lists). The test fails on a new violation and on a stale
entry (now clean), so baselines only shrink: when you fix a message, delete its key from your
language's baseline. Reseed with
`GIT_VOCAB_SEED=1 cargo test -p gitpoulpi-i18n --test git_vocabulary -- --ignored --nocapture print_violations`
(only to regenerate after a deliberate catalog change; never to hide a new violation).

### English git words (ja, ko, zh-CN)

`ui.git_terms_english` (Settings checkbox under "Translate git terms", shown only for
ja, ko and zh-CN, disabled while terms are translated; default off). Maintainer rule:
transliterations (ja ステージ, ko 스테이징) are fine in git mode, translated words (zh 暂存,
ko 병합) are not. In those three catalogs every git word is a `{$term}` token, never
inline text, so variant bit 2 (`override_english_git_terms`, `set_english_git_terms`) can
swap the term for the English term's git form. zh-CN's git forms are English already.
The lint accepts transliterations in git mode (`translits` in `git_vocabulary.rs`) and
asserts the English-forced rendering holds the English stems (no baseline). The variant is
`(english << 2) | (translate << 1) | merge`: tables hold 8 slots per varying message.

## Adding a language

All 17 languages are wired and shipped; a new one is data plus registrations:

1. `Lang` variant, `Lang::ALL`, `code()`, `parse`, plural rule in `src/lib.rs` (before `Qps`); file stem and endonym in `LANGS` of `build.rs` (same order); `SHIPPED_ORDER` in `build.rs`.
2. `UiLanguage` and its `endonym` in `gitpoulpi-config` (`schema/ui.rs`); the English language name in `answer_language_name` (`gitpoulpi-tui/src/ai_ui.rs`, for AI prompts); locale cases in `detect.rs` tests.
3. `locales/<code>.toml`: copy `en.toml`, keep every key and the key order, translate everything incl. `[_meta] language_name` and both `[term]` vocabularies. A missing file just shows English.
4. CLI help: `crates/gitpoulpi-commands/locales/help/<code>.toml` (copy `en.reference.toml`, keep backticked code, flags and headings) and the code in `HELP_LANGS` (`crates/gitpoulpi-commands/build.rs`). Update the `--lang` doc comment (`cli/mod.rs`), the `en.reference.toml` entry and every help catalog's `--lang` line (a drift test compares them), and the language lists of `docs/user/cli-reference.md` and `config-reference.md`.
5. A `lang-<code>` feature (and in `all-langs`) in `gitpoulpi-i18n`, `-cli`, `-tui`, `-mcp` (`xtask/tests/feature_contract.rs` fails otherwise).
6. Gate: `cargo build -p gitpoulpi-i18n` (reports missing entries; fails naming file and key on placeholder/plural mistakes), `cargo test -p gitpoulpi-i18n`, `cargo test -p gitpoulpi-commands --test help_catalog`, `cargo test -p gitpoulpi-tui i18n_layout` (shorten any label over budget), the toolbar/Settings label-budget tests, `cargo test -p gitpoulpi-cli --test help_lang` (add the code to its list).

## Display width (CJK)

zh-CN, ja and ko characters are two terminal cells wide. Every layout width in the
TUI uses `ui_kit::display_width` / `take_width` / `truncate_with_ellipsis`
(`unicode-width`), never `chars().count()` or `len()`: toolbar and dialog
buttons, the confirm dialog, tab labels (a repo name may be CJK too) and their hit
rects, palette rows, popups. Text content (editor, diff, commit message) already
measured cells. Budgets such as "labels <= 9 cells" are cells: four CJK characters.
The palette search handles the full-width colon after a category.

## The layout test

`crates/gitpoulpi-tui/src/i18n_layout_tests.rs` draws the key screens with
`TestBackend` at 100 and 160 columns in every shipped language (`SHIPPED`: the
real ones, and the padded pseudo-locale `qps`), with git terms off and on:
toolbar, Settings (General, Appearance, Keyboard & mouse), the command palette
(`event_loop/draw/palette_overlay.rs`, extracted for it), the help overlay, the
merge editor wide and narrow, ref and commit context menus anchored at the left
and at the right edge, the commit composer, Home, the Log's column headers and
the sidebar section titles. It asserts: nothing wide in the last column, no
garbled box border (a corner whose side is overwritten, an unbalanced box), the
toolbar's labels within budget with disjoint hits, menu rows whole and closed by
the border, headers whole or cut with an ellipsis, and the section-title budget
(18 cells, both PR/MR hosts). `qps` keeps the structural rules; the per-label
budgets are asserted for the real languages. A self-test proves the border check
fails on a garbled box.



## Glossary and checklist

Glossary: the English git vocabulary under `git`, git's own translations under `local`.
Checklist: register (fr infinitive for buttons, "vous" in
sentences; de "Sie"; es/it "tu"; pt "voce"), identical glossary terms everywhere,
placeholders natural where moved, fr/pt-BR treat 0 as singular, typographic marks
(fr non-breaking space before `: ; ? !` and guillemets, the plain `'` apostrophe in every
language and never `’` (maintainer, 2026-10-09; guarded by a `catalog.rs` test), de low quotes, es inverted
marks, the real `…`), width budgets, no emoji, keys stay `Ctrl`/`Shift`/`Alt`/`Enter`/`Esc`.

## Pseudo-locale `qps`

`GITPOULPI_LANG=qps` (never in the picker): every message is accented, wrapped in
`⟦…⟧` and padded by about 35 %. Plain English left on screen is a literal the lint
missed; overflow shows layout problems.

## The setting, detection and the live switch

- `ui.language` (`auto|en|fr|es|pt-BR|pt-PT|it|de|zh-CN|ja|ko|ru|uk|pl|cs|nl|sv|tr`) and `ui.translate_git_terms`
  (default off, right below it in Settings > General) live in
  `gitpoulpi-config`. Resolution (`gitpoulpi_i18n::resolve`, `src/detect.rs`):
  `GITPOULPI_LANG` (any `Lang::parse` value, `qps` included; empty or unknown is
  ignored), then `ui.language`, then for `auto` the OS locale through
  `sys-locale` (cached, `C`/`POSIX`/unsupported give `en`).
- `live_settings::install_language(&UiConfig)` publishes both settings
  (`gitpoulpi_i18n::set`, `set_translate_git_terms`, which bump `epoch()`). It runs
  at start-up, in `apply_live_settings` (config reload) and when Settings writes
  either key. Labels resolve at draw time, so the next frame is the new language.
  A switch comes from an input event or a reload, so the redraw is already due
  (P2 rules in `event_loop/window/idle.rs`); nothing in i18n animates.
- The PTY harness (`xtask/src/pty/mod.rs`) and `xtask perf` pin
  `GITPOULPI_LANG=en`; a test about languages overrides it (`.env("GITPOULPI_LANG", ..)`,
  empty to let the config decide). Unit tests get English from the per-thread
  default; use `override_lang` / `override_git_terms`.

## The source lint (strict)

`src/source_scan.rs` (test-only) scans production sources for string literals that
read as prose. `no_new_hard_coded_ui_strings` fails on ANY flagged literal: the
baseline file is gone, there is no ratchet to lower. A flagged literal is either
user text or not:

- **User text** goes into `locales/*.toml` (every shipped language's file) and is read through
  `gitpoulpi_i18n::msg::..`.
- **Not user text** stays in code and is marked, the marker on the literal's own
  line (a literal that spans lines is marked on its first line; for a block that
  cannot carry a trailing comment use the fence):
  `// i18n-english` (text for an agent or a model, developer diagnostics such as
  the exit log, the panic report, `--help` of the dev entrypoint, protocol strings
  like HTTP headers and URLs), `// i18n-core-frame` (English frames the core writes,
  matched and never shown), `// i18n-scan: off` ... `// i18n-scan: on` (a block that
  only matches English identifiers, such as `terminology::tr`). Whole test-only
  files (`keymap/drift.rs`) are excluded in `production_source_files`.
  Use the fences sparingly and never around UI text.
- Brand names (`GitHub`, `VS Code`, ...) are in `ALLOWED`.

Rules each extraction area left behind:

- **Config values:** a combobox stores the raw schema word and `choice_labels.rs` maps it to display text, so a language switch never rewrites `config.toml`. Searches (Settings, keymap page, help filter) match the translated *and* the English text.
- **Errors:** the daemon, CLI and MCP keep English `Error` `Display`; the TUI translates only at its display edge (`daemon_link::error_text::error_text` maps typed errors to `[typed_error]`; untyped `Backend`/`Io`/git stderr is shown as it came). A host's own error `detail` stays as the host wrote it. The git-lfs error keeps its install URL (the window matches on it).
- **Always English:** what an agent or a model reads (`agent_reason`, resolved with `agent_view::en`, so it lives in `en.toml` only and the other catalogs and the build skip it; text a human reads, such as the `ui_intent.agent_shown_but` status line, belongs in another section; `ui show settings` errors; AI chip sentences read with `english()`; a new AI profile is stored as "New profile"); stable action ids, config table names, key names; identity sentinels such as `tabs::NO_REPOSITORY`, `tab_dir::QUIT_CD_HOW`; the keymap and palette tables of `docs/user/keybindings.md` are generated in every guide's own language: `UPDATE_KEYMAP_DOCS=1 cargo test -p gitpoulpi-tui docs` rewrites `docs/user/<lang>/keybindings.md` (the labels come from that language's catalog, the header row stays as the guide has it) and the freshness tests (`keymap::drift::docs_table_is_current`, `palette::tests::docs`) check every shipped language, so a catalog edit that changes a label fails until the tables are regenerated. A guide needs the markers `<!-- keymap:begin -->` ... `<!-- keymap:end -->` and `<!-- palette:begin -->` ... `<!-- palette:end -->` around the two tables (`docs_tables.rs`).
- **Key names** in hints come from the chord printer (`dialog_kit::key_name` / `ctrl_key` / `alt_key`), never from a message. Keymap keys inside a help message are written `{{ctx.action}}` (`{{*ctx.action}}` for every binding) and resolved at draw time, so rebinding still shows.
- **Help overlay** (`chrome/help_text.rs`): a table of whole sentences; nothing is wrapped by hand (`help_lines` wraps to the overlay width).
- **Widths:** buttons size on the widest translated label (rebase actions, composer AI button), never fixed columns; labels <= 9 cells in toolbar and Settings, unit-tested in every language and both vocabularies; a Settings row label too long for its value is `fit` and repeated in full when focused.
- **PR/MR word:** `terminology::install` / `set_host` mirror the host term into `gitpoulpi_i18n::set_merge_terms` (per-thread under `cfg(test)`). `terminology::tr` (the old English rewriting) still serves context-menu rows and footer messages not extracted yet; delete it with the last one.

## Custom builds (`lang-*` features)

English is always built. Every other language is a cargo feature (`lang-fr`,
`lang-pt-br`, ..., `lang-qps` for the pseudo-locale; `all-langs` is all of them
and what `full` / the default turn on). The binaries (`gitpoulpi-cli`,
`gitpoulpi-tui`, `gitpoulpi-mcp`) forward each one to `gitpoulpi-i18n`.

- `build.rs` loads and emits only built catalogs. `LANG_ROW[lang]` maps a
  language to its table row; an unbuilt language shares row 0 (English).
  `Lang::is_built()` tells which; `SHIPPED` = complete catalogs that are built.
- `Lang` stays complete, so `ui.language = "de"` and `-l de` still parse in a
  build without German. `detect::resolve` falls back to English; Settings shows
  the configured language as "Deutsch (not built into this binary)".
- CLI help catalogs: `gitpoulpi-commands/build.rs` reads
  `DEP_GITPOULPI_I18N_LANGS` and generates the `include_str!` match; the `--lang`
  error lists `SHIPPED`.
- `tests/catalog.rs`, `tests/git_vocabulary.rs` and `tests/lookup_snapshot.rs`
  need every language and are `#![cfg(feature = "all-langs")]`.
- Example: `cargo build -p gitpoulpi-cli -p gitpoulpi-tui -p gitpoulpi-mcp
  --no-default-features --features gitpoulpi-cli/lang-fr,gitpoulpi-tui/lang-fr,gitpoulpi-mcp/lang-fr`.
