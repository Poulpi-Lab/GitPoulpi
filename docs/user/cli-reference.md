# CLI reference

`gitpoulpi` with no subcommand opens the window; with one, it is a scriptable git
client. Every command goes through the same background daemon as the window, so
a change made from a script shows up live in an open GitPoulpi. The MCP tools an
agent gets are generated from these same commands ([MCP and
agents](mcp-and-agents.md)). `gitpoulpi <command> --help` has every flag.

## Global flags

| Flag | Effect |
|---|---|
| `--json` | Print the result as JSON. Errors are JSON too: `{"error": "..."}` on stdout, exit code 1. A failed git operation adds `"detail": {"operation", "command", "exit_code", "stderr"}` (the git command that ran, redacted, its exit code and the tail of its stderr; for the built-in git library `"git2": {"class", "code", "message"}`); the MCP tools return the same object. Without `--json` the lines go to stderr. |
| `--repo <path>` | The repository to act on (default: the one around the current directory, like git). |
| `-s, --session <name>` | The session (daemon) to talk to. Default: derived from the repository root, so everything opened inside one repository shares one daemon and two repositories get two. |
| `--backend git2\|system` | Backend for a daemon this command starts (a running one keeps its own). |
| `--cwd-file <file>` | Where the window writes the active tab's folder when it quits (used by `shell-init`). |
| `-a, --add [path]`, `--no-raise` | Open a folder as a new tab of the GitPoulpi that is already running instead of starting another one; see [Add a folder to the open window](#add-a-folder-to-the-open-window). Takes no subcommand. |
| `-l, --lang <lang>` | Language of the `--help` text only: `en`, `fr`, `es`, `pt-BR`, `pt-PT`, `it`, `de`, `zh-CN`, `ja`, `ko`, `ru`, `uk`, `pl`, `cs`, `nl`, `sv`, `tr`. See [Translated help](#translated-help). |

### Add a folder to the open window

`gitpoulpi --add [path]` (`-a`; `gp -a` and the `gpa` command alias run the same
code) opens `path` (default: the current directory, resolved to its enclosing
repository) as a new tab of a GitPoulpi that is already running, so a folder
you `cd` into in a terminal does not start a second window.

- A *running session* is one whose daemon answers and that has a GitPoulpi window attached. Windows whose
  user turned off **Allow AI agents to drive the view** do not announce themselves and are not found (the same
  limit `gitpoulpi launch` has).
- One running session: it gets the tab (or shows the tab if that repository is already open), its window
  comes forward when the desktop allows it (Windows, WezTerm, Hyprland; `--no-raise` skips it), and a
  line says which session got it.
- Several: they are listed, numbered, with their tab count and repository names; type the number and Enter
  (an empty line or Esc then Enter cancels, exit code 130). Without a terminal on stdin the command fails and
  says to pass `--session NAME`. `-s NAME` skips the question.
- None (or `-s NAME` names a session that is not running): GitPoulpi starts normally in this terminal on that
  folder, exactly like `gp [path]`.
- The window applies it at once, as your own choice (no confirmation chip, no agent mark), unless you are
  typing in a form there: then the window offers the tab on its status line chip and the exit code is 3. A folder
  that is not inside a repository is refused (exit 1).

`--json` prints one object: `{"action": "joined", "session", "repo", "already_open", "raised", "outcome": {...}}`
(`outcome` is the window's answer, as for `ui show`) or `{"action": "cancelled"}`; errors are `{"error": "..."}`.
Exit codes: 0 the tab is open, 3 offered on the chip, 1 refused or failed, 130 canceled. There is no MCP tool
for it: an agent that wants to show a repository to the user uses `ui show tab`.

### Translated help

`gitpoulpi --help` is in English. Add `-l` to read the explanations in another
language: `gitpoulpi -l fr --help`, `gitpoulpi -l de commit --help`. Only the
explanations and the section headings are translated. Command names, flags,
value names and possible values do not change, so scripts and agents see the
same interface. The help language is not read from the environment: the output
changes only when you give `-l`. The MCP tool descriptions are always in
English.

Revisions accept anything git does (`HEAD~2`, a branch, a tag, a short sha).
Hunks and lines are numbered as `gitpoulpi --json diff` numbers them.

Re-signing uses the repository's own setup (`gpg.format` openpgp, ssh or x509, `user.signingkey`, `gpg.*.program`) and happens in the preview (a signed commit's id includes its signature): the plan's `counts.resigned` and `counts.signing_millis` say how many and how long. A setup that does not sign is refused first as `signing_failed` (or `tool_missing`), before anything is read. `rewrite check-signing` runs that test alone (signs and verifies a dummy payload once) and prints `{format, tool, millis}`, the time of one signature, to estimate a run (exit 2 with the reason when it fails; it may open a passphrase prompt). `--remove-signatures` adds the rule that strips the signature of every commit in scope even where nothing else changes; those commits need no `--signatures` answer. `--fix-message-encoding` adds the rule that re-encodes messages to UTF-8: a commit with an `encoding` header (ISO-8859-1, Shift_JIS...) is decoded and the header goes, and UTF-8 that was once read as Latin-1 or Windows-1252 (`RÃ©Ã©criture`) is repaired only when the round trip is exact; what cannot be decided stays as it is and is counted in `counts.encoding_left`. The names of a commit whose header goes are decoded with it, and `--fix-name-encoding` also repairs mangled names elsewhere. `preview` plans without changing anything and prints the plan `{run, digest, counts, refs, warnings, per_rule, rows, rows_total}` (the first `--limit` changed commits, default 50, or `--all`) and keeps it in the session's daemon and on disk in the repository's git dir (`gitpoulpi/rewrite/<run>/`): `apply --run ID --digest D` works from a later command, after a daemon restart or from another frontend, with no `daemon start`; a stored plan that no longer matches its digest is `stale`. Only `rows` needs the daemon that previewed (a running one, e.g. the TUI's or `daemon start`), so use `preview --all` to see every row in one command. Identity and anonymise rules rewrite the tagger of re-created annotated tags only when the recipe sets `include_taggers`. `rows` pages the run `{run, filter, offset, total, rows}` (at most 200 per page). `apply` runs the plan you reviewed (its `run` and `digest`) as ONE undo entry and prints `{run, moved, commits_changed}`; `undo` puts everything back. It never pushes: a pushed ref needs your force push afterwards. `run` previews and applies in one command (no daemon needed) and prints `{plan, outcome}`. `discard` drops a run (twice is fine). Trailer rules (`--trailer-add KEY=VALUE`, `--trailer-remove KEY`, `--trailer-map KEY:OLD=NEW`, repeatable, in that order after `--replace-message`) edit the `Key: value` lines of the last paragraph of each message with the grammar of `git interpret-trailers`: `--trailer-add` skips a message that already has exactly that trailer, `--trailer-remove` takes every trailer of the key, `--trailer-map` replaces literal text in the values of the key; the rest of the message is untouched (a recipe can also set `if_exists` `replace` or `skip`, a `find` pattern on `remove`, and `regex` patterns). `--map-trailers` (needs the identity flags) makes the identity rule also set the `Name <email>` trailers it matches. `--update-message-hashes` replaces abbreviated commit ids (7+ hex characters) in messages by the new ids of the same length when exactly one rewritten commit matches; the plan's `counts.message_hashes_updated` and `counts.message_hashes_left` (ambiguous, unknown, or created later) say what happened. Content rules (the recipe's `remove_paths`, `remove_blobs_over` and `content_replace`, or the flags `--remove-path`, `--remove-blobs-over`, `--replace-content`) rewrite the files of every commit: each unique file is read once, binary files are skipped and counted (`counts.blobs_skipped_binary`), a commit a rule leaves empty is dropped (`counts.commits_dropped`, rows with `new: null`; `--prune-empty never` keeps it) and its children move onto its parent, and the checked-out files follow the new tree. Refused with `dirty_paths_touched` when a file with local changes is one the rewrite would change, `checked_out_elsewhere` when a rewritten branch is checked out in another worktree, `partial_clone` in a partial clone. Path rules (`--move-path FROM=TO`, repeatable; `--into-subdir DIR`; `--extract DIR`, or the recipe's `move_paths`) rename a file or folder, move the whole repository into a subdirectory, or keep only a subdirectory as the new root; they act on trees, so every file keeps its id, and they run after the content rules. A rename never overwrites: where the new path exists in some commit the preview is refused as `path_collision` (exit 2) with the short commit ids and the paths in `refused.detail`. `--extract` is **asked each time**: without `--extract-mode` (`clone`, `in-place` or `submodule`) nothing is previewed and the answer is `{"needs_choice":{choice:"extract_mode", options, prompt}}` with exit code 3. `in-place` rewrites this repository like any rule (one undo entry; branches and tags that have nothing of the folder are deleted, rows with `refs[].new: null`; the checked-out branch must have the folder, else `empty_scope`). `clone` and `submodule` preview the history the new repository will hold over every local branch and tag, nothing is pushed or protected there, and are applied with the folder of the new repository: `--target PATH` on `run`, or on `apply` (`rewrite apply` of such a plan without `--target` is refused as `invalid_rule`; the folder must not exist or be empty and not be inside the repository). `clone` makes `git clone --no-local` of this repository there, rewrites it with the recipe, removes the remote, expires the reflogs and prunes the old objects, so it holds only the extracted history; this repository is not touched and nothing is journaled (`outcome.moved` is empty). `submodule` does the same, then adds one commit on the current branch that replaces the folder by a submodule of the new repository (the URL in `.gitmodules` is its local path), initialises it, and journals it (`outcome.moved` has the branch; `undo` moves it back and releases the submodule); the history is not rewritten, so the old commits keep the folder. Edited or untracked files in the folder, or a detached HEAD, refuse it. Order when combined: the content rules (`--replace-content`, `--remove-blobs-over`, `--lfs-import`, `--lfs-export`) and `--remove-path` run first on the original paths, then the path rules; an LFS pattern and a removal glob therefore name the original paths, and the `.gitattributes` lines of an import are added at the original root and then move with the files. **LFS rules** (the recipe's `lfs_import { patterns, min_size }` and `lfs_export { patterns }`, or `--lfs-import PATTERN...` with `--lfs-min-size BYTES`, and `--lfs-export PATTERN...`) need `git-lfs` (`tool_missing` otherwise): an import turns matching files into spec v1 pointers in every commit, writes the content to the local LFS store at apply (atomically, once per content) and adds `<pattern> filter=lfs diff=lfs merge=lfs -text` to the root `.gitattributes` of every rewritten commit that holds a pointer (the rest of the file is untouched); an export turns matching pointers back into the files and removes those lines, and is refused as `lfs_objects_missing` (`detail`: one `<oid> <path>` per line) when the objects are not in the local store (`lfs fetch` first). The plan's `counts.lfs_blobs`, `lfs_bytes`, `lfs_objects`, `lfs_restored` and `lfs_run` say what happens, rows list `lfs_imported` / `lfs_exported` paths, and the checked-out files stay the real content (apply installs the repository's LFS filters when missing). Send the objects afterwards with `lfs push --all`. **Text rules** (the recipe's `line_endings`, `strip_exec` and `reencode`, or `--eol`, `--strip-exec`, `--reencode`): `--eol lf\|crlf\|cr --eol-paths GLOB...` gives every text file the globs name that line ending (mixed endings become uniform; `--eol-exclude` leaves files alone; `--eol-follow-attributes` reads each commit's root `.gitattributes`: `-text`/`binary` files are skipped and `eol=` files keep their own ending); `--strip-exec GLOB...` turns mode 100755 into 100644 on the matching files (at least one glob, `--strip-exec-exclude` to spare some); `--reencode utf-8\|utf-8-bom\|utf-16le\|utf-16be\|windows-1252\|iso-8859-1 --encoding-paths GLOB...` converts the text files to that encoding, from `--from SOURCE` or, by default, detected per file (byte order mark, valid UTF-8, else `--encoding-fallback`, default `windows-1252`). They run in the content stage with the other content rules, in the order of the recipe. Binary files are skipped and counted (`counts.blobs_skipped_binary`); files the source encoding cannot read or the target cannot hold stay as they are and are counted in `counts.blobs_skipped_undecodable`; `counts.blobs_changed` is the number of new file versions, and rows list the changed paths as `modified`. `diff` shows what the rules did to one file of one commit of a previewed run (`{kind, binary, redacted, old_size, new_size, hunks}`); the lines a secret rule removes are hidden. Lua scripts (`--script FILE`, repeatable, run in order after the other rules; the file is embedded in the recipe) call `rewrite_commit(c, ctx)` on every commit and may return new `author` / `committer` (`name`, `email`, `time`, `offset_minutes`) and `message`, plus the `state` carried to the next call; the script's `--!` header declares its parameters, window and needs. The sandbox has no files, clock, process or modules and limits instructions (10 million per call), memory (64 MiB) and time (5 s per call). `script check` prints `{header, functions, problems}` (exit 2 when `problems` is not empty); `script test` runs a script on some commits without writing anything and prints `{rows: [{commit, fields, log}]}`. A failing script is refused as `script_failed` with `refused.script = {commit, reason}`. **External scripts** (language `shell`, `python` or `lua-external`: `--script-language` / `--language`, by default the file's extension `.sh`, `.bash`, `.ps1`, `.py`, `.lua`, else the embedded Lua) run as a process of their own with your rights, not sandboxed: one JSON request per line on stdin, one JSON answer per line on stdout, the same fields as above, `"error": "text"` to give up, diagnostics on stderr (they come back as the commit's `log`). The environment is cleared (only `PATH`, `HOME`/`USERPROFILE`, `SYSTEMROOT`, `TEMP`/`TMP` and `LANG` are passed), the working directory is a fresh temporary one, `rewrite.script_timeout_ms` (5000) bounds each answer and `rewrite.script_total_timeout_s` (3600) the pass; on a timeout, a crash or a cancel the whole process tree is killed and the rewrite is refused as `script_failed` (the commit and the reason), with nothing moved. Which languages exist is the `rewrite.external_scripts` setting (default `["shell"]`; add `"python"` or `"lua"` yourself): a language that is off is refused as `scripts_disabled`, a missing interpreter as `tool_missing` (`rewrite tools` lists them). **Trust**: an external script runs only when a person trusted its exact text: `rewrite script trust FILE` (or `--trust` on `preview`, `run`, `script check` and `script test`, which does it in the same command) remembers the file's SHA-256 for this repository, and a changed script asks again. An untrusted script is refused as `script_not_trusted` with `refused.script = {hash}`, and is never started, not even by `script check`, which reports `{trust: "untrusted", hash}` with exit code 2; for a trusted one `script check` starts it once with a made-up commit (`"dry_run": true`) to check its answer and also prints `interpreter`. The MCP server cannot trust: it has no `rewrite script trust` tool and no `trust` argument, so an agent can run only a script a person trusted before. `scan-secrets` reads the history of the scope (the current branch, `--all-local`, or `--ref`) once and prints `{findings: [{id, rule, path, more_paths, first_commit, last_commit, commits, blobs, preview}], commits, blobs_scanned, blobs_skipped_binary, blobs_skipped_large}`: the rule that matched (token prefixes, private keys, JWTs, passwords in URLs, `password = value` lines that look random), a redacted `preview` such as `ghp_****abcd` and never the value; it is not exhaustive and it reads only. `analyze` is the size analysis (like `filter-repo --analyze`): one pass over the scope's history that prints `{blobs, folders, deleted, top, commits, blobs_total, bytes_total, disk_total, bytes_in_head, bytes_history_only, deleted_paths, blobs_cut, folders_cut, deleted_cut}`. `blobs` are the `--top` (default 50, at most 5000) largest unique blobs, largest first, each `{path, more_paths, blob, size, disk_size, first_commit, last_commit, state}` (`state` is `in_head`, `replaced` for an old version of a file that is still in HEAD, or `deleted`; `last_commit` is the commit that removed it, else the one that added it; `disk_size` is the object database size, a packed delta counts as the delta); `folders` are `{path, size, blobs, in_head}` (unique blob bytes ever stored below it); `deleted` are paths that left HEAD but that the history still holds, `{path, versions, size, first_commit, last_commit}`. `bytes_history_only` is what removing everything that only the history holds would free, about, and only after a purge of the old objects and a gc; it reads only and never changes a ref. Turn a row into a rule with `--remove-path PATH` (or the folder) or `--remove-blobs-over BYTES`. `--remove-finding ID` (repeatable, or `all`) adds a rule that removes those findings from every commit: the daemon scans the same scope again and resolves the ids itself, so the value never reaches the command line, a recipe or a log. A secret that was pushed is leaked: rotate it first. Secrets never go in the command line or a saved recipe: `--secrets-file F` (one per line) fills the recipe's `content_replace` secrets rules and is never echoed. ### Workspaces and search

A **workspace** is a named group of repositories, optionally with a default commit
profile. It lives in `workspaces.toml` beside `config.toml`, shared by every
session and by the window, so `workspace` commands start no daemon (only `add`
and `create --add` ask one for each repository's `origin` URL). A repository can
be in several workspaces. Paths are compared like favorites and the recent list.

| Command | What it does |
|---|---|
| `workspace list`, `workspace show <id>` | `{workspaces: [...]}` / `{workspace}`: `id` (a slug, stable when renamed), `name`, `color`, `description`, `profile`, `profile_exists`, and `repos: [{path, exists, remote}]` (`remote` is the `origin` URL recorded when the repository was added, credentials stripped). |
| `workspace create <name> [--add PATH]... [--profile ID] [--color C] [--description T]` | Creates a workspace and prints it; two workspaces cannot share a name. `--add` is repeatable and is not `--repo`, which picks the repository a command runs in. |
| `workspace rename <id> <name>`, `workspace delete <id>` | Rename keeps the id. Delete never touches the repositories. |
| `workspace add <id> <path>...`, `workspace remove <id> <path>...` | `add` records each repository's root and `origin` URL (a path that does not exist, or is not inside a repository, is refused with a message and nothing is saved: only a repository that vanishes later stays listed, marked missing); `remove` also takes the path of a repository that is gone from disk. |

| `search <query> [--workspace ID] [--kind K]... [--limit N]` | Fuzzy search over branches (local and remote), tags, worktrees, stashes, commit messages and the pull/merge requests and issues of the hosting caches, of the current repository or of every repository of the workspace (`GITPOULPI_WORKSPACE` stands in for the flag). `search` answers `{query, workspace, hits, partial, repos}`. Each hit is
`{kind, label, detail, target, score, positions, repo}`: `kind` is `branch`,
`tag`, `commit`, `stash`, `worktree`, `repo`, `pull_request` or `issue`; `positions` are the matched
characters of `label` to highlight; `target` says where to go
(`{type: "ref", name}` with the full ref name, `{type: "commit", id}`,
`{type: "stash", index, id}`, `{type: "worktree", path}`,
`{type: "repo", path}`, `{type: "pull_request", number}`, `{type: "issue", number}`); hits are merged across repositories by `score`, best
first. Matching is the command palette's: the query verbatim, then verbatim
anywhere, then its characters in order (earlier and shorter win). A commit's body
is searched only when its subject does not match and the query has three
characters or more. A prefix narrows the search and is not part of the text:
`b:` branches, `t:` tags, `c:` commits, `s:` stashes, `w:` worktrees, `r:`
repositories (workspace only), `pr:` (or `mr:`) pull/merge requests, `i:` issues, `#`
both of those; `--kind` (repeatable, same names) filters too.
`partial` is true when a repository's commits were cut at
[`search.commit_limit`](config-reference.md#search-the-workspace-search); `repos`
says for each repository whether it was searched (`reason` when not: a path
gone from disk is reported, never fatal). A one-shot command builds each
repository's index first; with a window open on the same session the daemon
already has it warm. Pull/merge requests and issues are read from each repository's
hosting cache (the file the window keeps in `.gitpoulpi/hosting-cache.json`) and never
from a host: a repository whose window never loaded them has none to find, and a
missing or half-written cache is simply no hits.

**Showing things in the open window** (`ui`; every command also takes
`--viewer <id>` and `--launch`)

| Command | What it does |
|---|---|
| `ui viewers [--all-sessions]`, `ui state [--text]` | The open windows; what one shows. |
| `ui show commit <rev> [--also R] [--files] [--focus refs\|log\|status]`, `ui show ref <name>`, `ui show pr <n>`, `ui show issue <n>`, `ui show wip [path] [--staged] [--composer]` | Select something. |
| `ui show diff <path> [--rev R \| --unstaged \| --staged] [--line N] [--side old\|new] [--split \| --inline] [--whole-file \| --hunks] [--highlight A-B]` | Open a diff at a line. |
| `ui show file <path> [--rev R \| --worktree \| --index] [--blame \| --history] [--line N] [--column C] [--highlight A-B]` | Open a file, its blame or history. |
| `ui show tab [path]`, `ui show home [--filter F]`, `ui show search <query>`, `ui show palette [query]`, `ui show keys [topic]`, `ui show settings [page] [--setting KEY]` | Move to a tab, Home, the find bar, the palette, the help, a Settings page. `gitpoulpi ui show settings --help` lists the page names. |
| `ui highlight <A[:C]-B[:C]> [--no-scroll]`, `ui notify <message>`, `ui back` | Tint lines; a toast; undo the last view change. |
| `ui show conflict <path> [--conflict N]` | Open the merge editor on a conflicted file, at conflict N (nothing is picked or saved). |
| `ui propose reword <rev> -m M`, `ui propose commit-message <summary> [--body B]`, `ui propose branch <name> [--start-point R]`, `ui propose tag <name> [--target R] [-m M]` | Open a pre-filled dialog you confirm (needs `[mcp] allow_ui_propose = true`). |
| `ui propose split <rev> --plan <file\|->` | Open the split editor over a commit, filled with a plan (the `split-commit --plan` JSON) for you to review, edit and apply; nothing is split until you do. Same gate as the other proposals. |
| `ui propose rewrite --recipe <file\|->` | Open the history rewrite workbench with a recipe (TOML or JSON, as `rewrite preview --recipe`) already in it, for you to preview and apply; nothing is rewritten, purged or pushed until you do. A proposal carries at most 50 rules, no script (a script would run when previewed) and no secret value. Same gate as the other proposals. |
| `ui propose resolution <path> (--pick 1=a,2=ba,... [--default a\|b] \| --content-file F)` | Open the merge editor with a resolution already picked (or the whole file as text) for you to review; your Save & mark resolved is the only confirm. Same gate as the other proposals. |

Exit codes: 0 applied, 3 deferred to the user, 1 otherwise. Details and the
rules the window follows: [MCP and agents](mcp-and-agents.md#showing-things-to-the-user).

## Notes

- **Sessions.** `gitpoulpi session list` shows each session with `live` / `stale`
  (decided by connecting to its port). The derived name is
  `<folder>-<hash of the path>`.
- **No interactive prompts.** Nothing asks a question: risky operations either
  need a flag (`--yes`, `--force-with-lease`) or are refused with a reason.
- **Not in the CLI**: `checkout --file` (restore one file) is in the window only.
