# CLI-Referenz

`gitpoulpi` ohne Unterbefehl öffnet das Fenster; mit einem ist es ein skriptbarer
Git-Client. Jeder Befehl läuft über denselben Hintergrund-Daemon wie das Fenster, sodass
eine Änderung aus einem Skript live in einem geöffneten GitPoulpi erscheint. Die MCP-Tools,
die ein Agent erhält, werden aus denselben Befehlen erzeugt ([MCP und
Agenten](mcp-and-agents.md)). `gitpoulpi <Befehl> --help` nennt jede Option.

## Globale Optionen

| Option | Wirkung |
|---|---|
| `--json` | Gibt das Ergebnis als JSON aus. Auch Fehler sind JSON: `{"error": "..."}` auf stdout, Exit-Code 1. Eine fehlgeschlagene Git-Operation fügt `"detail": {"operation", "command", "exit_code", "stderr"}` hinzu (der ausgeführte Git-Befehl mit maskierten Geheimnissen, sein Exit-Code und das Ende seiner stderr-Ausgabe; bei der eingebauten Git-Bibliothek `"git2": {"class", "code", "message"}`), und ein Fehler, den der Daemon benennen konnte, fügt `"context": {"operation", "label", "args", "repo", "frontend", "request", "job"}` hinzu (der Vorgang, ein menschenlesbarer Name dafür, seine wichtigsten Argumente mit maskierten Geheimnissen, das Repository, wer ihn angefordert hat, die ID der Anfrage und, bei Fetch oder Push, seine Job-Nummer); die MCP-Werkzeuge liefern dasselbe Objekt. Ohne `--json` gehen die Zeilen nach stderr. |
| `--repo <path>` | Das Repository, auf dem gearbeitet wird (Standard: das um das aktuelle Verzeichnis, wie bei git). |
| `-s, --session <name>` | Die Sitzung (der Daemon), mit der gesprochen wird. Standard: aus der Repository-Wurzel abgeleitet, sodass alles, was in einem Repository geöffnet wird, einen Daemon teilt und zwei Repositories zwei bekommen. |
| `--backend git2\|system` | Backend für einen Daemon, den dieser Befehl startet (ein laufender behält seines). |
| `--cwd-file <file>` | Wohin das Fenster beim Beenden den Ordner des aktiven Tabs schreibt (genutzt von `shell-init`). |
| `-a, --add [path]`, `--no-raise` | Öffnet einen Ordner als neuen Tab des bereits laufenden GitPoulpi, statt ein weiteres zu starten; siehe [Einen Ordner zum offenen Fenster hinzufügen](#einen-ordner-zum-offenen-fenster-hinzufügen). Nimmt keinen Unterbefehl. |
| `-l, --lang <lang>` | Sprache nur des `--help`-Textes: `en`, `fr`, `es`, `pt-BR`, `pt-PT`, `it`, `de`, `zh-CN`, `ja`, `ko`, `ru`, `uk`, `pl`, `cs`, `nl`, `sv`, `tr`. Siehe [Übersetzte Hilfe](#übersetzte-hilfe). |

### Einen Ordner zum offenen Fenster hinzufügen

`gitpoulpi --add [path]` (`-a`; `gp -a` und der Befehlsalias `gpa` führen denselben
Code aus) öffnet `path` (Standard: das aktuelle Verzeichnis, aufgelöst zum umgebenden
Repository) als neuen Tab eines bereits laufenden GitPoulpi, sodass ein Ordner, in den
Sie in einem Terminal wechseln, kein zweites Fenster startet.

- Eine *laufende Sitzung* ist eine, deren Daemon antwortet und an die ein GitPoulpi-Fenster angebunden ist. Fenster,
  in denen **KI-Agenten die Ansicht steuern lassen** ausgeschaltet ist, melden sich nicht an und werden nicht
  gefunden (dieselbe Grenze wie bei `gitpoulpi launch`).
- Eine laufende Sitzung: Sie erhält den Tab (oder zeigt ihn, wenn dieses Repository schon offen ist), ihr Fenster
  kommt in den Vordergrund, wenn die Desktop-Umgebung es erlaubt (Windows, WezTerm, Hyprland; `--no-raise` lässt
  das aus), und eine Zeile nennt die Sitzung, die ihn erhalten hat.
- Mehrere: Sie werden nummeriert aufgelistet, mit ihrer Tab-Anzahl und den Repository-Namen; geben Sie die Nummer
  und Enter ein (eine leere Zeile oder Esc und dann Enter bricht ab, Exitcode 130). Ohne Terminal an stdin schlägt
  der Befehl fehl und verlangt `--session NAME`. `-s NAME` überspringt die Frage.
- Keine (oder `-s NAME` nennt eine Sitzung, die nicht läuft): GitPoulpi startet normal in diesem Terminal auf diesem
  Ordner, genau wie `gp [path]`.
- Das Fenster wendet es sofort an, als Ihre eigene Wahl (kein Bestätigungs-Chip, keine Agentenmarkierung), außer Sie
  tippen dort gerade in ein Formular: Dann bietet das Fenster den Tab im Chip der Statuszeile an und der Exitcode ist 3.
  Ein Ordner, der in keinem Repository liegt, wird abgelehnt (Exitcode 1).

`--json` gibt ein Objekt aus: `{"action": "joined", "session", "repo", "already_open", "raised", "outcome": {...}}`
(`outcome` ist die Antwort des Fensters, wie bei `ui show`) oder `{"action": "cancelled"}`; Fehler sind `{"error": "..."}`.
Exitcodes: 0 der Tab ist offen, 3 im Chip angeboten, 1 abgelehnt oder fehlgeschlagen, 130 abgebrochen. Es gibt kein
MCP-Tool dafür: Ein Agent, der dem Benutzer ein Repository zeigen will, nutzt `ui show tab`.

### Übersetzte Hilfe

`gitpoulpi --help` ist auf Englisch. Fügen Sie `-l` hinzu, um die Erklärungen in einer
anderen Sprache zu lesen: `gitpoulpi -l fr --help`, `gitpoulpi -l de commit --help`. Nur
die Erklärungen und die Abschnittsüberschriften werden übersetzt. Befehlsnamen,
Optionen, Wertnamen und mögliche Werte ändern sich nicht, sodass Skripte und Agenten
dieselbe Schnittstelle sehen. Die Hilfesprache wird nicht aus der Umgebung gelesen: Die
Ausgabe ändert sich nur, wenn Sie `-l` angeben. Die Beschreibungen der MCP-Tools sind
immer auf Englisch.

Revisionen akzeptieren alles, was git akzeptiert (`HEAD~2`, einen Branch, einen Tag, einen
kurzen sha). Hunks und Zeilen werden so nummeriert, wie `gitpoulpi --json diff` sie
nummeriert.

Nur `rows` braucht den Daemon, der die Vorschau erstellt hat (einen laufenden, z. B. den der TUI oder `daemon start`); für alle Zeilen in einem Befehl also `preview --all` verwenden. Identitäts- und Anonymisierungsregeln schreiben den Tagger neu erzeugter annotierter Tags nur um, wenn das Rezept `include_taggers` setzt. `rows` blättert durch den Lauf `{run, filter, offset, total, rows}` (höchstens 200 pro Seite). `apply` führt den geprüften Plan (sein `run` und `digest`) als EINEN Undo-Eintrag aus und gibt `{run, moved, commits_changed}` aus; `undo` stellt alles wieder her. Es pusht nie: Eine gepushte Ref braucht danach Ihren Force-Push. `run` macht Vorschau und Anwenden in einem Befehl (kein Daemon nötig) und gibt `{plan, outcome}` aus. `discard` verwirft einen Lauf (zweimal ist unproblematisch). Trailer-Regeln (`--trailer-add KEY=VALUE`, `--trailer-remove KEY`, `--trailer-map KEY:OLD=NEW`, wiederholbar, in dieser Reihenfolge nach `--replace-message`) bearbeiten die Zeilen `Key: value` des letzten Absatzes jeder Nachricht nach der Grammatik von `git interpret-trailers`: `--trailer-add` überspringt eine Nachricht, die genau diesen Trailer schon hat, `--trailer-remove` nimmt jeden Trailer des Schlüssels, `--trailer-map` ersetzt wörtlichen Text in den Werten des Schlüssels; der Rest der Nachricht bleibt unberührt (ein Rezept kann außerdem `if_exists` `replace` oder `skip`, ein `find`-Muster bei `remove` und `regex`-Muster setzen). `--map-trailers` (braucht die Identitäts-Flags) lässt die Identitätsregel auch die `Name <email>`-Trailer setzen, auf die sie passt. `--update-message-hashes` ersetzt abgekürzte Commit-IDs (7+ Hex-Zeichen) in Nachrichten durch die neuen IDs gleicher Länge, wenn genau ein umgeschriebener Commit passt; `counts.message_hashes_updated` und `counts.message_hashes_left` des Plans (mehrdeutig, unbekannt oder später erzeugt) sagen, was geschehen ist. Inhaltsregeln (`remove_paths`, `remove_blobs_over` und `content_replace` des Rezepts, oder die Optionen `--remove-path`, `--remove-blobs-over`, `--replace-content`) schreiben die Dateien jedes Commits um: Jede eindeutige Datei wird einmal gelesen, Binärdateien werden übersprungen und mitgezählt (`counts.blobs_skipped_binary`), ein Commit, den eine Regel leer lässt, wird verworfen (`counts.commits_dropped`, Zeilen mit `new: null`; `--prune-empty never` behält ihn) und seine Kinder rücken auf seinen Elternteil, und die ausgecheckten Dateien folgen dem neuen Tree. Abgelehnt wird mit `dirty_paths_touched`, wenn eine Datei mit lokalen Änderungen eine ist, die das Umschreiben ändern würde, mit `checked_out_elsewhere`, wenn ein umgeschriebener Branch in einem anderen Worktree ausgecheckt ist, und mit `partial_clone` in einem partiellen Klon. Pfadregeln (`--move-path FROM=TO`, wiederholbar; `--into-subdir DIR`; `--extract DIR`, oder `move_paths` des Rezepts) benennen eine Datei oder einen Ordner um, verschieben das ganze Repository in ein Unterverzeichnis oder behalten nur ein Unterverzeichnis als neue Wurzel; sie wirken auf Trees, jede Datei behält also ihre ID, und sie laufen nach den Inhaltsregeln. Ein Umbenennen überschreibt nie: Existiert der neue Pfad in einem Commit, wird die Vorschau als `path_collision` (Exit-Code 2) abgelehnt, mit den kurzen Commit-IDs und den Pfaden in `refused.detail`. `--extract` wird **jedes Mal gefragt**: Ohne `--extract-mode` (`clone`, `in-place` oder `submodule`) wird nichts in der Vorschau gezeigt, und die Antwort ist `{"needs_choice":{choice:"extract_mode", options, prompt}}` mit Exit-Code 3. `in-place` schreibt dieses Repository wie jede Regel um (ein Undo-Eintrag; Branches und Tags, die nichts von dem Ordner haben, werden gelöscht, Zeilen mit `refs[].new: null`; der ausgecheckte Branch muss den Ordner haben, sonst `empty_scope`). `clone` und `submodule` zeigen in der Vorschau den Verlauf, den das neue Repository über jeden lokalen Branch und Tag halten wird, nichts wird dort gepusht oder geschützt, und werden mit dem Ordner des neuen Repositorys angewendet: `--target PATH` bei `run` oder bei `apply` (`rewrite apply` eines solchen Plans ohne `--target` wird als `invalid_rule` abgelehnt; der Ordner darf nicht existieren oder muss leer sein und nicht im Repository liegen). `clone` führt dort `git clone --no-local` dieses Repositorys aus, schreibt es mit dem Rezept um, entfernt das Remote, lässt die Reflogs ablaufen und bereinigt die alten Objekte, sodass es nur den herausgelösten Verlauf enthält; dieses Repository bleibt unberührt, und nichts wird im Journal festgehalten (`outcome.moved` ist leer). `submodule` tut dasselbe und fügt dann einen Commit auf dem aktuellen Branch hinzu, der den Ordner durch ein Submodul des neuen Repositorys ersetzt (die URL in `.gitmodules` ist sein lokaler Pfad), initialisiert es und hält es im Journal fest (`outcome.moved` hat den Branch; `undo` setzt ihn zurück und gibt das Submodul frei); der Verlauf wird nicht umgeschrieben, die alten Commits behalten den Ordner also. Bearbeitete oder unversionierte Dateien im Ordner oder ein losgelöster HEAD lehnen es ab. Reihenfolge bei Kombination: Die Inhaltsregeln (`--replace-content`, `--remove-blobs-over`, `--lfs-import`, `--lfs-export`) und `--remove-path` laufen zuerst auf den ursprünglichen Pfaden, dann die Pfadregeln; ein LFS-Muster und ein Glob zum Entfernen nennen daher die ursprünglichen Pfade, und die `.gitattributes`-Zeilen eines Imports werden an der ursprünglichen Wurzel hinzugefügt und wandern dann mit den Dateien. **LFS-Regeln** (`lfs_import { patterns, min_size }` und `lfs_export { patterns }` des Rezepts, oder `--lfs-import PATTERN...` mit `--lfs-min-size BYTES` und `--lfs-export PATTERN...`) brauchen `git-lfs` (sonst `tool_missing`): Ein Import macht passende Dateien in jedem Commit zu Zeigern nach Spezifikation v1, schreibt den Inhalt beim Anwenden in den lokalen LFS-Speicher (atomar, einmal pro Inhalt) und fügt `<Muster> filter=lfs diff=lfs merge=lfs -text` zur `.gitattributes` an der Wurzel jedes umgeschriebenen Commits hinzu, der einen Zeiger enthält (der Rest der Datei bleibt unberührt); ein Export macht passende Zeiger wieder zu den Dateien und entfernt diese Zeilen und wird als `lfs_objects_missing` abgelehnt (`detail`: ein `<oid> <path>` pro Zeile), wenn die Objekte nicht im lokalen Speicher liegen (zuerst `lfs fetch`). `counts.lfs_blobs`, `lfs_bytes`, `lfs_objects`, `lfs_restored` und `lfs_run` des Plans sagen, was geschieht, Zeilen listen die Pfade `lfs_imported` / `lfs_exported`, und die ausgecheckten Dateien bleiben der echte Inhalt (das Anwenden installiert die LFS-Filter des Repositorys, wenn sie fehlen). Die Objekte danach mit `lfs push --all` senden. **Textregeln** (`line_endings`, `strip_exec` und `reencode` des Rezepts, oder `--eol`, `--strip-exec`, `--reencode`): `--eol lf\|crlf\|cr --eol-paths GLOB...` gibt jeder Textdatei, die die Globs nennen, dieses Zeilenende (gemischte Zeilenenden werden einheitlich; `--eol-exclude` lässt Dateien in Ruhe; `--eol-follow-attributes` liest die `.gitattributes` an der Wurzel jedes Commits: `-text`- und `binary`-Dateien werden übersprungen, und `eol=`-Dateien behalten ihr eigenes Zeilenende); `--strip-exec GLOB...` macht auf den passenden Dateien aus Modus 100755 100644 (mindestens ein Glob, `--strip-exec-exclude`, um einige auszunehmen); `--reencode utf-8\|utf-8-bom\|utf-16le\|utf-16be\|windows-1252\|iso-8859-1 --encoding-paths GLOB...` wandelt die Textdateien in diese Kodierung um, aus `--from SOURCE` oder standardmäßig pro Datei erkannt (Byte-Order-Mark, gültiges UTF-8, sonst `--encoding-fallback`, Standard `windows-1252`). Sie laufen in der Inhaltsstufe mit den übrigen Inhaltsregeln, in der Reihenfolge des Rezepts. Binärdateien werden übersprungen und gezählt (`counts.blobs_skipped_binary`); Dateien, die die Quellkodierung nicht lesen oder das Ziel nicht halten kann, bleiben, wie sie sind, und werden in `counts.blobs_skipped_undecodable` gezählt; `counts.blobs_changed` ist die Zahl der neuen Dateiversionen, und Zeilen listen die geänderten Pfade als `modified`. `diff` zeigt, was die Regeln an einer Datei eines Commits eines geprüften Laufs getan haben (`{kind, binary, redacted, old_size, new_size, hunks}`); die Zeilen, die eine Geheimnisregel entfernt, bleiben verborgen. Lua-Skripte (`--script FILE`, wiederholbar, der Reihe nach nach den übrigen Regeln; die Datei wird ins Rezept eingebettet) rufen `rewrite_commit(c, ctx)` für jeden Commit auf und dürfen neue `author` / `committer` (`name`, `email`, `time`, `offset_minutes`) und `message` zurückgeben, dazu den `state`, der an den nächsten Aufruf weitergegeben wird; der `--!`-Header des Skripts deklariert seine Parameter, sein Zeitfenster und seine Anforderungen. Die Sandbox hat keine Dateien, keine Uhr, keine Prozesse und keine Module und begrenzt Anweisungen (10 Millionen pro Aufruf), Speicher (64 MiB) und Zeit (5 s pro Aufruf). `script check` gibt `{header, functions, problems}` aus (Exit-Code 2, wenn `problems` nicht leer ist); `script test` führt ein Skript auf einigen Commits aus, ohne etwas zu schreiben, und gibt `{rows: [{commit, fields, log}]}` aus. Ein fehlschlagendes Skript wird als `script_failed` mit `refused.script = {commit, reason}` abgelehnt. **Externe Skripte** (Sprache `shell`, `python` oder `lua-external`: `--script-language` / `--language`, standardmäßig nach der Dateiendung `.sh`, `.bash`, `.ps1`, `.py`, `.lua`, sonst das eingebaute Lua) laufen als eigener Prozess mit Ihren Rechten, ohne Sandbox: eine JSON-Anfrage pro Zeile auf stdin, eine JSON-Antwort pro Zeile auf stdout, dieselben Felder wie oben, `"error": "text"` zum Aufgeben, Diagnosen auf stderr (sie kommen als `log` des Commits zurück). Die Umgebung wird geleert (nur `PATH`, `HOME`/`USERPROFILE`, `SYSTEMROOT`, `TEMP`/`TMP` und `LANG` werden durchgereicht), das Arbeitsverzeichnis ist ein frisches temporäres, `rewrite.script_timeout_ms` (5000) begrenzt jede Antwort und `rewrite.script_total_timeout_s` (3600) den Durchlauf; bei einer Zeitüberschreitung, einem Absturz oder einem Abbruch wird der ganze Prozessbaum beendet und das Umschreiben als `script_failed` (Commit und Grund) abgelehnt, ohne dass sich etwas bewegt hat. Welche Sprachen es gibt, bestimmt die Einstellung `rewrite.external_scripts` (Standard `["shell"]`; `"python"` oder `"lua"` selbst ergänzen): Eine ausgeschaltete Sprache wird als `scripts_disabled` abgelehnt, ein fehlender Interpreter als `tool_missing` (`rewrite tools` listet sie). **Vertrauen**: Ein externes Skript läuft nur, wenn ein Mensch seinem genauen Text vertraut hat: `rewrite script trust FILE` (oder `--trust` bei `preview`, `run`, `script check` und `script test`, was es im selben Befehl erledigt) merkt sich den SHA-256 der Datei für dieses Repository, und ein geändertes Skript fragt erneut. Ein Skript ohne Vertrauen wird als `script_not_trusted` mit `refused.script = {hash}` abgelehnt und nie gestartet, auch nicht von `script check`, das `{trust: "untrusted", hash}` mit Exit-Code 2 meldet; bei einem vertrauten startet `script check` es einmal mit einem erfundenen Commit (`"dry_run": true`), um seine Antwort zu prüfen, und gibt außerdem `interpreter` aus. Der MCP-Server kann nicht vertrauen: Er hat kein Werkzeug `rewrite script trust` und kein Argument `trust`, ein Agent kann also nur ein Skript ausführen, dem ein Mensch vorher vertraut hat. `scan-secrets` liest den Verlauf des Bereichs (aktueller Branch, `--all-local` oder `--ref`) einmal und gibt `{findings: [{id, rule, path, more_paths, first_commit, last_commit, commits, blobs, preview}], commits, blobs_scanned, blobs_skipped_binary, blobs_skipped_large}` aus: die Regel, die gepasst hat (Token-Präfixe, private Schlüssel, JWTs, Passwörter in URLs, zufällig aussehende Zeilen der Art `password = value`), eine geschwärzte `preview` wie `ghp_****abcd` und nie den Wert; es ist nicht vollständig und liest nur. `analyze` ist die Größenanalyse (wie `filter-repo --analyze`): ein Durchlauf über den Verlauf des Bereichs, der `{blobs, folders, deleted, top, commits, blobs_total, bytes_total, disk_total, bytes_in_head, bytes_history_only, deleted_paths, blobs_cut, folders_cut, deleted_cut}` ausgibt. `blobs` sind die `--top` (Standard 50, höchstens 5000) größten eindeutigen Blobs, die größten zuerst, jeweils `{path, more_paths, blob, size, disk_size, first_commit, last_commit, state}` (`state` ist `in_head`, `replaced` für eine alte Version einer Datei, die noch in HEAD ist, oder `deleted`; `last_commit` ist der Commit, der sie entfernt hat, sonst der, der sie hinzugefügt hat; `disk_size` ist die Größe in der Objektdatenbank, ein gepacktes Delta zählt als Delta); `folders` sind `{path, size, blobs, in_head}` (die Bytes eindeutiger Blobs, die je darunter gespeichert wurden); `deleted` sind Pfade, die HEAD verlassen haben, die der Verlauf aber noch hält, `{path, versions, size, first_commit, last_commit}`. `bytes_history_only` ist, was das Entfernen von allem, das nur der Verlauf hält, ungefähr freigäbe, und erst nach einer Bereinigung der alten Objekte und einem gc; es liest nur und ändert nie eine Ref. Aus einer Zeile wird mit `--remove-path PATH` (oder dem Ordner) oder `--remove-blobs-over BYTES` eine Regel. `--remove-finding ID` (wiederholbar, oder `all`) fügt eine Regel hinzu, die diese Treffer aus jedem Commit entfernt: Der Daemon durchsucht denselben Bereich erneut und löst die IDs selbst auf, der Wert gelangt also nie in die Befehlszeile, ein Rezept oder ein Log. Ein gepushtes Geheimnis gilt als offengelegt: zuerst rotieren. Geheimnisse gehören nie in die Befehlszeile oder ein gespeichertes Rezept: `--secrets-file F` (eines pro Zeile) füllt die Geheimnisregeln `content_replace` des Rezepts und wird nie ausgegeben. Exit-Codes: 0 erledigt; 1 Fehler (unlesbares Rezept, falsche Optionen); 2 abgelehnt, ausgegeben als `{"refused":{reason, message, detail}}` mit dem Grund `stale` (falscher Digest, unbekannter Lauf, eine Ref hat sich seit der Vorschau bewegt), `no_rule`, `invalid_rule`, `empty_scope`, `shallow`, `signature_choice_needed`, ...; 3 der Plan verschiebt Refs, die bereits auf einem Remote liegen, und `--yes` fehlt, ausgegeben als `{"needs_confirmation":{prompt}}`, nichts geändert (`run` verwirft dabei auch seine Vorschau). |

Eine `IDENTITY` ist `Name <email>` (oder `<email>`). `list` gibt `{identities: [{name, email, as_author, as_committer, mapped_to}], commits, has_mailmap}` aus: jeden Namen und jede E-Mail-Adresse des Bereichs (aktueller Branch, `--all-local` oder `--ref`) mit ihren Commits als Autor und als Committer, die meisten zuerst, und mit der Identität, auf die die `.mailmap` sie schon abbildet (`mapped_to`, fehlt, wenn keine); `--mapped` / `--unmapped` filtern. `check` gibt `{identities: [{identity, shown_as, mapped}]}` aus: wie jede Identität durch die `.mailmap` (und `mailmap.file`) erscheint, die Antwort von `git check-mailmap`. `add` hängt pro `--from` eine Zeile an die `.mailmap` an (`Canonical Name <canonical@email> Old Name <old@email>`; wird bei Bedarf angelegt; eine bereits vorhandene Zeile wird nicht wiederholt) und gibt `{mailmap: {added, file}}` aus. Es bearbeitet die Datei und committet nichts: selbst committen. Ein rückgängig machbarer Eintrag (`undo` stellt die vorherige Datei wieder her). Solange `log.use_mailmap` an ist (Standard), zeigen `log`, `blame` und `file-history` die kanonischen Identitäten sofort, die gespeicherten Commits bleiben unverändert, und nichts braucht einen Force-Push. Um die Commits selbst umzuschreiben, `rewrite preview --mailmap` verwenden (eine `mailmap`-Regel: Autoren und Committer werden zu dem, was `git log --use-mailmap` zeigt; `--who` wählt welche; `--mailmap-file F` wendet eine andere Datei an). |
| `undo-restore <id> [--name N] [--dry-run]` (auch `undo restore <id>`) | „Nur diese wiederherstellen“: bringt zurück, was ein früherer Eintrag entfernt hat (gelöschter Branch oder Tag, verworfener Stash, verworfene oder gelöschte Datei, entferntes Remote, Ignorier-Zeile), ohne die Einträge danach rückgängig zu machen. Überschreibt nie: Eine geänderte Datei bekommt `<name>.restored` daneben; ein Reset, Amend oder Rebase kommt als neuer Branch an der alten Spitze zurück. Ein neuer Journal-Eintrag, also nimmt `undo` es zurück. Exit 2 abgelehnt (Name vergeben, nichts wiederherzustellen...). |
| `reflog [<ref>] [--skip N] [--limit N]` | Eine Seite des Reflogs von `HEAD` (Standard) oder eines Branches, die neueste zuerst, mit dem Grund von git: zeigt auch Verschiebungen aus einer Shell. Ein gelöschter Branch hat keins. |
| `reflog-restore <ref> <oid> [--mode keep\|soft\|mixed\|hard] [--dry-run]` (auch `reflog restore ...`) | Einen Branch oder `HEAD` auf eine Reflog-Position bewegen. Ein ausgecheckter Branch mit nicht committeten Änderungen braucht `--mode`. Ein Journal-Eintrag: `undo` nimmt es zurück. Exit 2 abgelehnt. |
| `lost-commits [--skip N] [--limit N] [--no-deep] [--budget-ms MS]` | Commits, die kein Branch, Tag, Remote oder Stash erreicht (Commits eines gelöschten Branches, alte Rückgängig-Sicherungen, unreferenzierte Objekte), die neueste zuerst. Der Scan endet an seinem Zeitbudget und meldet `partial`. |

| `checkout <target> [--autostash]` | Den Branch wechseln oder sich an einem Commit lösen. |

Ohne Flag entscheidet die Fast-Forward-Einstellung (die eigene Wahl des Repositorys, sonst `git.merge_fast_forward`, Standard `never`: ein Merge-Commit, auch wenn ein Fast-Forward möglich wäre). `--ff` spult per Fast-Forward vor, wenn möglich (Gits Standard), `--no-ff` erzeugt immer einen Merge-Commit, `--ff-only` spult vor oder schlägt mit *cannot fast-forward* fehl und ändert nichts; die Flags schließen einander aus. Das JSON sagt, was geschah: `{"FastForwarded": oid}`, `{"Merged": oid}` (ein Merge-Commit), `"UpToDate"` oder `{"Conflicted": [paths]}`. `--squash` stagt die Änderungen des Branches und erstellt keinen Commit (`merge --squash`); danach folgt ein `commit`. | `rebase [onto] [--autostash]` | Rebase; `--continue`, `--skip`, `--abort`, `--status` während eines laufenden. |
| `rebase <upstream> --interactive --plan <file\|->` | Nicht interaktiver „interaktiver“ Rebase aus einem JSON-Plan (`[{"commit", "action", "message"}]`, Aktionen `pick`, `reword`, `squash`, `fixup`, `drop`, `edit` oder ihre Ein-Buchstaben-Formen `p`, `r`, `s`, `f`, `d`, `e`; Groß-/Kleinschreibung egal, wie in einer Rebase-Todo-Liste); `--root`, `--onto-commit`, `--autosquash`. Bauen Sie ihn aus `rebase-plan`. |
| `cherry-pick <commits>...` oder `cherry-pick --plan <file\|->` | Commits der Reihe nach anwenden (Plan: Schritte `pick` / `drop`). |
| `revert <commit> [-m <parent>]` | Einen Commit rückgängig machen (Revert). Ein Merge-Commit braucht `--mainline <parent>` (`-m`), die Nummer (ab 1) des Elternteils, der bleibt: `1` ist der Branch, auf dem der Merge erstellt wurde. |
| `reset <target> --mode soft\|mixed\|hard` | Den Branch bewegen. |
| `tag list [--unpushed]`, `tag create <name> [at] [-m M]`, `tag annotate <name> -m M` | Tags. `tag list` gibt jeden Tag mit seinem Aufenthaltsort aus, gelernt aus dem letzten Fetch oder Tag-Push (nie aus dem Netzwerk): `local` (er existiert hier), `remote` (die Remotes, die ihn haben), `differs_on` (Remotes, die ihn an einem anderen Commit halten) und `where`: `local`, `remote` (ein Remote hat ihn, dieses Repository nicht), `both` oder `differs`. |
| `tag delete <name> [--local \| --remote R \| --both [--remote R]]` | Löscht einen Tag: lokal (Standard), nur auf einem Remote (`git push R --delete`; nach außen wirksam und nicht rückgängig zu machen) oder hier und auf dem Remote, das ihn hat. Die Antwort trägt `scope` (`local`, `remote`, `both`) und, beim nur lokalen Löschen eines Tags, den ein Remote noch hat, `still_on` (der nächste `fetch` bringt ihn zurück). Ein kombiniertes Löschen entfernt zuerst das Remote; `undo` stellt dann nur den lokalen Tag wieder her, und `tag push` legt ihn wieder an. |
| `tag fetch <name> [--remote R]` | Fetcht einen Tag von einem Remote (standardmäßig dem, das ihn hat), z. B. einen Tag mit `where: remote`. Überschreibt nie einen lokalen Tag an einem anderen Commit. |
| `tag push [names...] [--remote R]`, `tag delete-remote <name> [--remote R]` | Tags auf einem Remote (ohne Namen: jeder Tag, den kein Remote hat). Das Löschen eines Tags auf einem Remote ist rückgängig zu machen (`undo --yes`). |
| `worktree list`, `worktree add <path> <start> [-b BRANCH]` | Verknüpfte Worktrees. |
| `submodule list`, `submodule init [paths]`, `submodule update [paths] [--init] [--recursive]` | Submodule ([Submodule](submodules.md)). |

`--autostash` stasht lokale Änderungen, die die Operation blockieren, führt sie aus und
poppt den Stash, unabhängig von `general.auto_stash` ([Auto-Stash](log-and-history.md#auto-stash)).

| Befehl | Was er tut |
|---|---|
| `autostash start-over [--dry-run] [--yes]` | Bei ausstehendem Auto-Stash: die Änderungen an den Dateien des Stashs verwerfen (eine Kopie bleibt unter `refs/gitpoulpi-backup/`), die Operation rückgängig machen, die den Auto-Stash erstellt hat, den Stash auf dem ursprünglichen Commit poppen. Hält mit intaktem Stash an, wenn ein Schritt fehlschlägt. Exit-Code 3 ohne `--yes`; eine Ablehnung ist ein Fehler (Exit 1) mit dem Grund. |

| `desktop shortcut remove [--where ...]` | Entfernt die Verknüpfungen, die GitPoulpi angelegt hat (Standard: alle); eine Datei, die nicht von GitPoulpi stammt, wird nie angerührt. |
| `desktop folder-menu status`, `desktop folder-menu install`, `desktop folder-menu remove` | Der Eintrag **In GitPoulpi öffnen** im Rechtsklickmenü des Dateimanagers (Einstellungen > Starter > Menü des Dateimanagers): Datei-Explorer unter Windows, GNOME Dateien, Dolphin, Nemo, Thunar, Caja und PCManFM unter Linux, Finder unter macOS. `status` gibt JSON `{os, entries:[{manager, detected, state}], unavailable, error}` aus (`state`: `not_installed`, `installed`, `outdated`, `foreign`; `unavailable`: der Start-Helfer fehlt neben GitPoulpi). `install` schreibt den Eintrag für jeden gefundenen Dateimanager (nie über eine Datei, die nicht von GitPoulpi stammt); `remove` nimmt genau heraus, was `install` geschrieben hat. Kein Daemon; kein MCP-Werkzeug. |
| `alias status`, `alias create <name> [--add]`, `alias remove [name]` | Der Befehlsalias (`gp` oder ein beliebiger Name) und, mit `--add`, die Variante zum Hinzufügen (`gpa`, die `gitpoulpi --add` ausführt: ein markiertes `/bin/sh`-Skript unter Linux und macOS, eine `.cmd` unter Windows): JSON mit dem Zustand und der `kind` (`open` oder `add`) jedes von GitPoulpi angelegten Alias (`installed`, `outdated`, `foreign`), dem bin-Ordner und dem Ziel. `create` meldet außerdem Warnungen (der Name führt im PATH schon etwas aus, der eigene Alias von PowerShell) und ob der bin-Ordner im PATH liegt; eine Datei, die nicht von GitPoulpi stammt, wird abgelehnt. `remove` ohne Namen entfernt jeden von GitPoulpi angelegten Alias. Kein Daemon; die Installationsprogramme rufen diese Befehle auf. |
| `path status`, `path add`, `path remove` | GitPoulpi im Benutzer-PATH, für neue Terminals: ein markierter Block in den Shell-Startdateien (Linux, macOS) oder `HKCU\Environment` (Windows). `status` ist `not_added`, `added`, `outdated` oder `on_path` (schon vorhanden, aber nicht durch GitPoulpi). `remove` nimmt nur heraus, was `add` hineingeschrieben hat. |
| `uninstall [--keep-files]` | Entfernt die von GitPoulpi angelegten Befehlsaliasse, PATH-Einträge und Verknüpfungen und, bei einer Release-Installation, die Programmdateien (das führen `install.sh --uninstall` und das Windows-Deinstallationsprogramm aus). Lehnt ein Build ohne die Markierung `.gitpoulpi-dist` ab (ein cargo-Build). Für MCP-Agenten nicht verfügbar. |
| `launch [--new-window] [-- COMMAND...]`, `launch [--new-window] --folder DIR` | Was die GitPoulpi-Verknüpfungen ausführen: zeigt das Fenster eines bereits geöffneten GitPoulpi (`ui.reuse_window`), sonst startet es COMMAND (den Terminal-Befehl). JSON: `{"action":"raised"}` oder `{"action":"started","reason":...}`. Startet nie einen Daemon; kein MCP-Tool. `--new-window` startet immer COMMAND (Grund `new_window`); unter Windows bewirkt dasselbe, die Umschalttaste (Shift) beim Klick auf die Verknüpfung oder das Taskleistensymbol gedrückt zu halten. `--folder DIR` ist das, was der Eintrag **In GitPoulpi öffnen** des Dateimanagers ausführt: Ist `ui.reuse_window` an und ein Fenster offen, wird das Repository, das DIR enthält, zu einem Tab des zuletzt fokussierten Fensters (`{"action":"joined",...}`), sonst startet das Terminal aus `ui.launch_terminal` GitPoulpi in DIR. |
| `mcp serve --stdio \| --http [ADDR] [--allow-remote] [--ui-control auto\|ask\|off]` | Der MCP-Server ([MCP und Agenten](mcp-and-agents.md)). Ohne `ADDR` nutzt `--http` `[mcp] bind` (Standard `127.0.0.1:8808`). `--http` braucht das Bearer-Token, außer `[mcp] http_auth` ist aus; `--allow-remote` wird abgelehnt, außer die Authentifizierung ist an und der Datenverkehr ist verschlüsselt (`[mcp] tls` oder `behind_proxy`). |
| `mcp token [--show] [--copy] [--rotate]` | Das Bearer-Token des MCP-HTTP-Endpunkts, als JSON `{token_hint, path, rotated}` (das Token wird bei der ersten Nutzung erzeugt). `--show` fügt das vollständige `token` hinzu, zum Einfügen in den `Authorization: Bearer`-Header eines Clients; `--copy` legt es über das Terminal (OSC 52) in die Zwischenablage, ohne es auszugeben; `--rotate` ersetzt es, und das alte funktioniert sofort nicht mehr. Kein MCP-Tool: Ein Agent kann den Schlüssel nicht lesen oder ersetzen, der seinen eigenen Server schützt. Siehe [MCP und Agenten](mcp-and-agents.md#den-endpunkt-von-einem-anderen-rechner-erreichen). |
| `completions bash\|zsh\|fish\|powershell\|elvish` | Ein Shell-Vervollständigungsskript auf stdout. |
| `shell-init bash\|zsh\|fish\|pwsh [--name gp]` | Eine Wrapper-Funktion (`gp`), die in den Ordner des aktiven Tabs wechselt (`cd`), wenn Sie mit *Beenden & cd hierher* beenden: `eval "$(gitpoulpi shell-init bash)"`. Siehe [Dem Ordner des Tabs folgen](following-the-tab-folder.md). |

### Workspaces und Suche

Ein **Workspace** ist eine benannte Gruppe von Repositories, optional mit einem
Standard-Commit-Profil. Er liegt in `workspaces.toml` neben `config.toml`, wird von
jeder Sitzung und vom Fenster gemeinsam genutzt, daher starten `workspace`-Befehle
keinen Daemon (nur `add` und `create --add` fragen einen nach der `origin`-URL jedes
Repositorys). Ein Repository kann in mehreren Workspaces sein. Pfade werden wie bei
Favoriten und der Liste der zuletzt verwendeten verglichen.

| Befehl | Was er tut |
|---|---|
| `workspace list`, `workspace show <id>` | `{workspaces: [...]}` / `{workspace}`: `id` (ein Slug, beim Umbenennen stabil), `name`, `color`, `description`, `profile`, `profile_exists` und `repos: [{path, exists, remote}]` (`remote` ist die `origin`-URL, die beim Hinzufügen des Repositorys gespeichert wurde, ohne Zugangsdaten). |
| `workspace create <name> [--add PATH]... [--profile ID] [--color C] [--description T]` | Legt einen Workspace an und gibt ihn aus; zwei Workspaces können nicht denselben Namen haben. `--add` ist wiederholbar und nicht `--repo`, das das Repository wählt, in dem ein Befehl läuft. |
| `workspace rename <id> <name>`, `workspace delete <id>` | Umbenennen behält die ID. Löschen berührt die Repositories nie. |
| `workspace add <id> <path>...`, `workspace remove <id> <path>...` | `add` speichert Wurzel und `origin`-URL jedes Repositorys (ein Pfad, der nicht existiert oder nicht in einem Repository liegt, wird mit einer Meldung abgelehnt und nichts gespeichert: nur ein Repository, das später verschwindet, bleibt aufgelistet, als fehlend markiert); `remove` nimmt auch den Pfad eines Repositorys, das vom Datenträger verschwunden ist. |
| `workspace set-profile <id> <profile>` / `--none` | Die `[[profiles]]`-ID, unter der in den Repositories des Workspace committet wird. Eine ID, die kein Profil nennt, wird gespeichert (`profile_exists: false`) und wirkt nicht. |
| `workspace set-ai-instructions <id> [--action <a>] [--mode append\|replace] (--text T \| --clear)` | Die KI-Anweisungen des Workspace, für jede Aktion oder für eine (`commit_message`, `code_review`, ...). `append` fügt sie nach den globalen an, `replace` verwendet sie stattdessen. Sie gelten für jedes Repository des Workspace, vor den eigenen des Repositorys. `workspace show` gibt sie als `ai_instructions` aus. |
| `commit -m M [--workspace ID]` | Committet als Profil des Workspace, wenn das Repository im Workspace ist und das Profil existiert; sonst `general.active_profile`; sonst die eigene Identität des Repositorys. Ohne `--workspace` (oder `GITPOULPI_WORKSPACE`) ändert sich nichts: Ein Commit rät nie einen Workspace aus der Mitgliedschaft, da ein Repository in mehreren sein kann. Eine unbekannte ID ist ein Fehler. |
| `search <query> [--workspace ID] [--kind K]... [--limit N]` | Fuzzy-Suche über Branches (lokal und Remote), Tags, Worktrees, Stashes, Commit-Nachrichten und die Pull/Merge Requests und Issues der Hosting-Caches, im aktuellen Repository oder in jedem Repository des Workspace (`GITPOULPI_WORKSPACE` ersetzt die Option). Die Fensterversion ist die [Suche](search.md). |

`search` antwortet mit `{query, workspace, hits, partial, repos}`. Jeder Treffer ist
`{kind, label, detail, target, score, positions, repo}`: `kind` ist `branch`, `tag`,
`commit`, `stash`, `worktree`, `repo`, `pull_request` oder `issue`; `positions` sind die
passenden Zeichen von `label`, die hervorzuheben sind; `target` sagt, wohin zu gehen ist
(`{type: "ref", name}` mit dem vollständigen Ref-Namen, `{type: "commit", id}`,
`{type: "stash", index, id}`, `{type: "worktree", path}`, `{type: "repo", path}`,
`{type: "pull_request", number}`, `{type: "issue", number}`); Treffer werden über
Repositories hinweg nach `score` gemischt, der beste zuerst. Gefunden wird wie in der
Befehlspalette: die Anfrage wörtlich, dann wörtlich irgendwo, dann ihre Zeichen in der
Reihenfolge (früher und kürzer gewinnt). Der Text eines Commits wird nur durchsucht,
wenn sein Betreff nicht passt und die Anfrage drei oder mehr Zeichen hat. Ein Präfix
schränkt die Suche ein und gehört nicht zum Text: `b:` Branches, `t:` Tags, `c:`
Commits, `s:` Stashes, `w:` Worktrees, `r:` Repositories (nur Workspace), `pr:` (oder
`mr:`) Pull/Merge Requests, `i:` Issues, `#` beide davon; `--kind` (wiederholbar,
dieselben Namen) filtert ebenfalls. `partial` ist wahr, wenn die Commits eines
Repositorys bei [`search.commit_limit`](config-reference.md#search-die-suche-im-workspace)
abgeschnitten wurden; `repos` sagt für jedes Repository, ob es durchsucht wurde
(`reason`, wenn nicht: ein vom Datenträger verschwundener Pfad wird gemeldet, nie
fatal). Ein einmaliger Befehl baut zuerst den Index jedes Repositorys; bei einem
offenen Fenster derselben Sitzung hat ihn der Daemon schon warm. Pull/Merge Requests
und Issues werden aus dem Hosting-Cache jedes Repositorys gelesen (die Datei, die das
Fenster in `.gitpoulpi/hosting-cache.json` führt) und nie von einem Host: Ein
Repository, dessen Fenster sie nie geladen hat, hat keine zu finden, und ein fehlender
oder halb geschriebener Cache ergibt einfach keine Treffer.

**Dinge im geöffneten Fenster zeigen** (`ui`; jeder Befehl akzeptiert auch `--viewer <id>`
und `--launch`)

| Befehl | Was er tut |
|---|---|
| `ui viewers [--all-sessions]`, `ui state [--text]` | Die geöffneten Fenster; was eines zeigt. |
| `ui show commit <rev> [--also R] [--files] [--focus refs\|log\|status]`, `ui show ref <name>`, `ui show pr <n>`, `ui show issue <n>`, `ui show wip [path] [--staged] [--composer]` | Etwas auswählen. |
| `ui show diff <path> [--rev R \| --unstaged \| --staged] [--line N] [--side old\|new] [--split \| --inline] [--whole-file \| --hunks] [--highlight A-B]` | Einen Diff an einer Zeile öffnen. |
| `ui show file <path> [--rev R \| --worktree \| --index] [--blame \| --history] [--line N] [--column C] [--highlight A-B]` | Eine Datei, ihr Blame oder ihren Verlauf öffnen. |
| `ui show tab [path]`, `ui show home [--filter F]`, `ui show search <query>`, `ui show palette [query]`, `ui show keys [topic]`, `ui show settings [page] [--setting KEY]` | Zu einem Tab, Home, der Suchleiste, der Palette, der Hilfe, einer Einstellungsseite wechseln. `gitpoulpi ui show settings --help` listet die Seitennamen. |
| `ui highlight <A[:C]-B[:C]> [--no-scroll]`, `ui notify <message>`, `ui back` | Zeilen hervorheben; eine Benachrichtigung; die letzte Ansichtsänderung rückgängig machen. |
| `ui show conflict <path> [--conflict N]` | Den Merge-Editor auf einer Datei im Konflikt öffnen, bei Konflikt N (nichts wird gewählt oder gespeichert). |
| `ui propose reword <rev> -m M`, `ui propose commit-message <summary> [--body B]`, `ui propose branch <name> [--start-point R]`, `ui propose tag <name> [--target R] [-m M]` | Einen vorausgefüllten Dialog öffnen, den Sie bestätigen (braucht `[mcp] allow_ui_propose = true`). |
| `ui propose split <rev> --plan <file\|->` | Öffnet den Aufteilungseditor über einem Commit, gefüllt mit einem Plan (dem JSON von `split-commit --plan`), den Sie prüfen, ändern und anwenden; aufgeteilt wird erst, wenn Sie es tun. Dieselbe Sperre wie bei den anderen Vorschlägen. |
| `ui propose rewrite --recipe <file\|->` | Öffnet die Werkbank zum Umschreiben mit einem bereits eingetragenen Rezept (TOML oder JSON, wie `rewrite preview --recipe`), damit Sie es in der Vorschau prüfen und anwenden; nichts wird umgeschrieben, bereinigt oder gepusht, bis Sie es tun. Ein Vorschlag trägt höchstens 50 Regeln, kein Skript (es liefe bei der Vorschau) und keinen geheimen Wert. Dasselbe Tor wie die anderen Vorschläge. |
| `ui propose resolution <path> (--pick 1=a,2=ba,... [--default a\|b] \| --content-file F)` | Den Merge-Editor mit einer bereits gewählten Lösung (oder der ganzen Datei als Text) zur Prüfung öffnen; Ihr Speichern & als gelöst markieren ist die einzige Bestätigung. Dieselbe Sperre wie bei den anderen Vorschlägen. |

Exit-Codes: 0 angewandt, 3 an den Benutzer zurückgegeben, sonst 1. Einzelheiten und die
Regeln, denen das Fenster folgt: [MCP und Agenten](mcp-and-agents.md#dem-benutzer-dinge-zeigen).

## Hinweise

- **Sitzungen.** `gitpoulpi session list` zeigt jede Sitzung mit `live` / `stale`
  (entschieden durch Verbinden mit ihrem Port). Der abgeleitete Name ist
  `<Ordner>-<Hash des Pfades>`.
- **Keine interaktiven Rückfragen.** Nichts stellt eine Frage: Riskante Operationen
  brauchen entweder eine Option (`--yes`, `--force-with-lease`) oder werden mit einem
  Grund abgelehnt.
- **Nicht in der CLI**: `checkout --file` (eine Datei wiederherstellen) gibt es nur im
  Fenster.
