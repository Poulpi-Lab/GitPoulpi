# Referencia de la CLI

`gitpoulpi` sin subcomando abre la ventana; con uno, es un cliente de git
programable. Todos los comandos pasan por el mismo daemon en segundo plano que la ventana, de modo que
un cambio hecho desde un script aparece al instante en un GitPoulpi abierto. Las herramientas MCP que
recibe un agente se generan a partir de estos mismos comandos ([MCP y
agentes](mcp-and-agents.md)). `gitpoulpi <command> --help` muestra todas las opciones.

## Opciones globales

| Opción | Efecto |
|---|---|
| `--json` | Imprime el resultado como JSON. Los errores también son JSON: `{"error": "..."}` en stdout, código de salida 1. Una operación de git que falla añade `"detail": {"operation", "command", "exit_code", "stderr"}` (el comando de git que se ejecutó, con los secretos ocultos, su código de salida y el final de su stderr; para la biblioteca de git integrada `"git2": {"class", "code", "message"}`), y un fallo que el daemon pudo identificar añade `"context": {"operation", "label", "args", "repo", "frontend", "request", "job"}` (la operación, un nombre legible para ella, sus argumentos principales con los secretos ocultos, el repositorio, quién la pidió, el id de la petición y, en un fetch o un push, el número de su tarea); las herramientas MCP devuelven el mismo objeto. Sin `--json` las líneas van a stderr. |
| `--repo <path>` | El repositorio sobre el que actuar (por defecto: el que rodea el directorio actual, como git). |
| `-s, --session <name>` | La sesión (daemon) con la que hablar. Por defecto: derivada de la raíz del repositorio, de modo que todo lo que se abre dentro de un repositorio comparte un daemon y dos repositorios tienen dos. |
| `--backend git2\|system` | Backend para un daemon que inicie este comando (uno en marcha conserva el suyo). |
| `--cwd-file <file>` | Dónde escribe la ventana la carpeta de la pestaña activa al salir (lo usa `shell-init`). |
| `-a, --add [path]`, `--no-raise` | Abre una carpeta en una pestaña nueva del GitPoulpi que ya está en marcha, en lugar de iniciar otro; ver [Añadir una carpeta a la ventana abierta](#añadir-una-carpeta-a-la-ventana-abierta). No admite subcomando. |
| `-l, --lang <lang>` | Idioma del texto de `--help` únicamente: `en`, `fr`, `es`, `pt-BR`, `pt-PT`, `it`, `de`, `zh-CN`, `ja`, `ko`, `ru`, `uk`, `pl`, `cs`, `nl`, `sv`, `tr`. Ver [Ayuda traducida](#ayuda-traducida). |

### Añadir una carpeta a la ventana abierta

`gitpoulpi --add [path]` (`-a`; `gp -a` y el alias de comando `gpa` ejecutan el mismo
código) abre `path` (por defecto: el directorio actual, resuelto al repositorio que lo
contiene) en una pestaña nueva de un GitPoulpi que ya está en marcha, de modo que una carpeta
a la que haces `cd` en un terminal no inicia una segunda ventana.

- Una *sesión en marcha* es aquella cuyo daemon responde y que tiene una ventana de GitPoulpi conectada. Las ventanas
  cuyo usuario desactivó **Permitir que los agentes de IA controlen la vista** no se anuncian y no se encuentran (el mismo
  límite que tiene `gitpoulpi launch`).
- Una sesión en marcha: recibe la pestaña (o muestra la pestaña si ese repositorio ya está abierto), su ventana
  pasa al frente si el escritorio lo permite (Windows, WezTerm, Hyprland; `--no-raise` lo omite) y una
  línea indica qué sesión la recibió.
- Varias: se listan, numeradas, con su número de pestañas y los nombres de los repositorios; escribe el número y Enter
  (una línea vacía o Esc y luego Enter cancela, código de salida 130). Sin un terminal en stdin el comando falla y
  indica que pases `--session NOMBRE`. `-s NOMBRE` se salta la pregunta.
- Ninguna (o `-s NOMBRE` nombra una sesión que no está en marcha): GitPoulpi se inicia con normalidad en este terminal sobre esa
  carpeta, exactamente como `gp [path]`.
- La ventana lo aplica al instante, como una elección tuya (sin chip de confirmación ni marca de agente), salvo que estés
  escribiendo en un formulario de ella: entonces la ventana ofrece la pestaña en el chip de su barra de estado y el código de salida es 3. Una carpeta
  que no está dentro de un repositorio se rechaza (código de salida 1).

`--json` imprime un objeto: `{"action": "joined", "session", "repo", "already_open", "raised", "outcome": {...}}`
(`outcome` es la respuesta de la ventana, como en `ui show`) o `{"action": "cancelled"}`; los errores son `{"error": "..."}`.
Códigos de salida: 0 la pestaña está abierta, 3 ofrecida en el chip, 1 rechazada o fallida, 130 cancelada. No hay herramienta MCP
para esto: un agente que quiere mostrar un repositorio al usuario usa `ui show tab`.

### Ayuda traducida

`gitpoulpi --help` está en inglés. Añade `-l` para leer las explicaciones en otro
idioma: `gitpoulpi -l fr --help`, `gitpoulpi -l de commit --help`. Solo se traducen las
explicaciones y los encabezados de sección. Los nombres de comandos, las opciones, los
nombres de valores y los valores posibles no cambian, de modo que los scripts y los agentes ven la
misma interfaz. El idioma de la ayuda no se lee del entorno: la salida
cambia solo cuando das `-l`. Las descripciones de las herramientas MCP siempre están en
inglés.

Las revisiones aceptan cualquier cosa que acepte git (`HEAD~2`, una rama, una etiqueta, un sha corto).
Los hunks y las líneas se numeran como los numera `gitpoulpi --json diff`.

**Consultar**

| `conflicts resolve <path> --side ours\|theirs\|base` | Resuelve un archivo con un lado (`--ours` / `--theirs` son atajos). |

| `conflicts resolve <path> --pick 1=a,2=ba [--default a\|b]` | Una elección por conflicto: `a` ours, `b` theirs, `ab`, `ba`, `none`. Se rechaza con `pick_incomplete` salvo que cada conflicto tenga una o se dé `--default`. |
| `conflicts resolve <path> --content-file F\|- [--encoding L]` | Escribe el texto final dado (UTF-8, o codificado como `L`). |

| `conflicts resolve ... [--no-stage] [--expect base,ours,theirs]` | `--no-stage` guarda sin marcar como resuelto; `--expect` es la protección contra datos obsoletos (oids de stage, `-` para ninguno). |
| `conflicts unresolve <path>` | Devuelve a conflicto un archivo resuelto durante esta operación. |
| `conflicts check` | ¿Daría conflictos hacer merge de HEAD en la rama de la que partió? `{"status": "conflicts"\|"clean"\|"no-base"\|"disabled", "head", "base_ref", "base", "base_source": "globs"\|"pull-request", "files": [...]}`. | `conflicts am-skip` | Omite el parche en el que se detuvo el `git am`. |

| `job list` | Los trabajos en segundo plano del daemon, del más antiguo al más reciente: cada fetch, push, pull, clon y transferencia LFS es uno desde el momento en que se recibe (en cola, en curso o terminado en los últimos 30 s). JSON: id, kind, state, phase, progress, `not_cancellable`, `error`. |
| `job cancel <id>` | Detiene un trabajo. Se rechaza (código de salida 1, no cambia nada) pasado el punto en que detenerlo es seguro. Ctrl+C en un comando que inició un trabajo cancela ese trabajo. |

| `index-lock remove` | Elimina un `index.lock` obsoleto. Se rechaza si tiene menos de 10 s o si no existe. |
| `rebase-plan [<upstream>] [--root]` | Los commits que reproduciría un rebase interactivo, del más antiguo al más reciente. |

[--param NAME=VALUE...] [--language L] [--trust]`, `rewrite script trust FILE` (y `--script FILE --script-param NAME=VALUE [--script-language L] [--trust]` en `preview`/`run`) | Reescritura del historial a partir de una receta (el TOML que guarda el editor de la TUI, o JSON; los flags añaden reglas después de las de la receta y sustituyen su alcance y sus opciones). `tools` lista las herramientas externas que necesitan volver a firmar y los scripts (`{tools: [...]}`). **Firmas**: cuando se reescriben commits firmados, `--signatures` es obligatorio (`strip` los quita, `resign-signed` vuelve a firmar solo los que estaban firmados, `resign-all` firma todos los commits reescritos); si no, la vista previa se rechaza como `signature_choice_needed`; los commits que quedan como están conservan su firma. Volver a firmar usa la configuración del propio repositorio (`gpg.format` openpgp, ssh o x509, `user.signingkey`, `gpg.*.program`) y ocurre en la vista previa (el id de un commit firmado incluye su firma): `counts.resigned` y `counts.signing_millis` del plan dicen cuántos y cuánto tardó. Una configuración que no firma se rechaza primero como `signing_failed` (o `tool_missing`), antes de leer nada. `rewrite check-signing` ejecuta solo esa prueba (firma y verifica una vez un contenido de prueba) e imprime `{format, tool, millis}`, lo que tarda una firma, para estimar una ejecución (código de salida 2 con el motivo si falla; puede abrir una petición de contraseña). `--remove-signatures` añade la regla que quita la firma de cada commit del alcance aunque no cambie nada más; esos commits no necesitan respuesta de `--signatures`. `--fix-message-encoding` añade la regla que recodifica los mensajes a UTF-8: un commit con cabecera `encoding` (ISO-8859-1, Shift_JIS...) se decodifica y la cabecera se quita, y el UTF-8 que antes se leyó como Latin-1 o Windows-1252 (`RÃ©Ã©criture`) solo se repara cuando la conversión de ida y vuelta es exacta; lo que no se puede decidir se deja como está y se cuenta en `counts.encoding_left`. Los nombres de un commit cuya cabecera se quita se decodifican con ella, y `--fix-name-encoding` repara también los nombres estropeados en otros sitios. `preview` planifica sin cambiar nada e imprime el plan `{run, digest, counts, refs, warnings, per_rule, rows, rows_total}` (los primeros `--limit` commits modificados, 50 por defecto, o `--all`) y lo guarda en el daemon de la sesión y en disco, en el directorio git del repositorio (`gitpoulpi/rewrite/<run>/`): `apply --run ID --digest D` funciona desde un comando posterior, tras reiniciar el daemon o desde otro frontend, sin `daemon start`; un plan guardado que ya no coincide con su digest es `stale`. Solo `rows` necesita el daemon que generó la vista previa (uno en marcha, por ejemplo el de la TUI o `daemon start`), así que usa `preview --all` para ver todas las filas en un solo comando. Las reglas de identidad y de anonimizado reescriben el tagger de los tags anotados recreados solo cuando la receta activa `include_taggers`. `rows` pagina la ejecución `{run, filter, offset, total, rows}` (como máximo 200 por página). `apply` ejecuta el plan que revisaste (su `run` y su `digest`) como UNA sola entrada de deshacer e imprime `{run, moved, commits_changed}`; `undo` lo deja todo como estaba. Nunca hace push: una ref ya publicada necesita después tu force push. `run` hace la vista previa y la aplicación en un solo comando (sin daemon) e imprime `{plan, outcome}`. `discard` descarta una ejecución (hacerlo dos veces no da problemas). Las reglas de trailers (`--trailer-add KEY=VALUE`, `--trailer-remove KEY`, `--trailer-map KEY:OLD=NEW`, repetibles, en ese orden después de `--replace-message`) editan las líneas `Clave: valor` del último párrafo de cada mensaje con la gramática de `git interpret-trailers`: `--trailer-add` omite un mensaje que ya tiene exactamente ese trailer, `--trailer-remove` quita todos los trailers de la clave y `--trailer-map` reemplaza texto literal en los valores de la clave; el resto del mensaje no se toca (una receta también puede poner `if_exists` en `replace` o `skip`, un patrón `find` en `remove` y patrones `regex`). `--map-trailers` (necesita los flags de identidad) hace que la regla de identidad cambie también los trailers `Nombre <correo>` que coinciden. `--update-message-hashes` reemplaza en los mensajes los ids abreviados de commit (7 o más caracteres hexadecimales) por los ids nuevos de la misma longitud cuando coincide exactamente un commit reescrito; `counts.message_hashes_updated` y `counts.message_hashes_left` (ambiguos, desconocidos o creados después) del plan dicen qué pasó. Las reglas de contenido (`remove_paths`, `remove_blobs_over` y `content_replace` de la receta, o los flags `--remove-path`, `--remove-blobs-over`, `--replace-content`) reescriben los archivos de cada commit: cada archivo único se lee una sola vez, los archivos binarios se omiten y se cuentan (`counts.blobs_skipped_binary`), un commit que una regla deja vacío se elimina (`counts.commits_dropped`, filas con `new: null`; `--prune-empty never` lo conserva) y sus hijos pasan a su padre, y los archivos del directorio de trabajo siguen al árbol nuevo. Se rechaza con `dirty_paths_touched` cuando un archivo con cambios locales es uno de los que la reescritura cambiaría, con `checked_out_elsewhere` cuando una rama reescrita está activa en otro worktree y con `partial_clone` en un clon parcial. Las reglas de rutas (`--move-path FROM=TO`, repetible; `--into-subdir DIR`; `--extract DIR`, o los `move_paths` de la receta) renombran un archivo o carpeta, mueven todo el repositorio a un subdirectorio o conservan solo un subdirectorio como raíz nueva; actúan sobre árboles, así que cada archivo conserva su id, y se ejecutan después de las reglas de contenido. Un renombrado nunca sobrescribe: si la ruta nueva existe en algún commit, la vista previa se rechaza como `path_collision` (código de salida 2) con los ids cortos de los commits y las rutas en `refused.detail`. `--extract` se **pregunta cada vez**: sin `--extract-mode` (`clone`, `in-place` o `submodule`) no se previsualiza nada y la respuesta es `{"needs_choice":{choice:"extract_mode", options, prompt}}` con código de salida 3. `in-place` reescribe este repositorio como cualquier regla (una entrada de deshacer; las ramas y tags que no tienen nada de la carpeta se eliminan, filas con `refs[].new: null`; la rama activa debe tener la carpeta, si no, `empty_scope`). `clone` y `submodule` previsualizan el historial que tendrá el repositorio nuevo sobre todas las ramas y tags locales, no se hace push de nada ni se protege nada allí, y se aplican con la carpeta del repositorio nuevo: `--target PATH` en `run` o en `apply` (`rewrite apply` de un plan así sin `--target` se rechaza como `invalid_rule`; la carpeta no debe existir o debe estar vacía, y no puede estar dentro del repositorio). `clone` hace allí un `git clone --no-local` de este repositorio, lo reescribe con la receta, quita el remoto, hace expirar los reflogs y poda los objetos antiguos, así que contiene solo el historial extraído; este repositorio no se toca y no se registra nada para deshacer (`outcome.moved` está vacío). `submodule` hace lo mismo y después añade un commit en la rama actual que reemplaza la carpeta por un submódulo del repositorio nuevo (la URL de `.gitmodules` es su ruta local), lo inicializa y lo registra para deshacer (`outcome.moved` contiene la rama; `undo` la devuelve y libera el submódulo); el historial no se reescribe, así que los commits antiguos conservan la carpeta. Archivos editados o sin seguimiento en la carpeta, o un HEAD desacoplado, lo rechazan. Orden al combinar: las reglas de contenido (`--replace-content`, `--remove-blobs-over`, `--lfs-import`, `--lfs-export`) y `--remove-path` se ejecutan primero sobre las rutas originales, y después las reglas de rutas; por tanto, un patrón LFS y un glob de eliminación nombran las rutas originales, y las líneas de `.gitattributes` de una importación se añaden en la raíz original y luego se mueven con los archivos. **Reglas de LFS** (`lfs_import { patterns, min_size }` y `lfs_export { patterns }` de la receta, o `--lfs-import PATTERN...` con `--lfs-min-size BYTES`, y `--lfs-export PATTERN...`) necesitan `git-lfs` (si no, `tool_missing`): una importación convierte los archivos que coinciden en punteros de la especificación v1 en cada commit, escribe el contenido en el almacén LFS local al aplicar (de forma atómica, una vez por contenido) y añade `<patrón> filter=lfs diff=lfs merge=lfs -text` al `.gitattributes` de la raíz de cada commit reescrito que contiene un puntero (el resto del archivo no se toca); una exportación convierte de nuevo los punteros que coinciden en los archivos y quita esas líneas, y se rechaza como `lfs_objects_missing` (`detail`: un `<oid> <ruta>` por línea) cuando los objetos no están en el almacén local (antes, `lfs fetch`). `counts.lfs_blobs`, `lfs_bytes`, `lfs_objects`, `lfs_restored` y `lfs_run` del plan dicen qué ocurre, las filas listan las rutas `lfs_imported` / `lfs_exported`, y los archivos del directorio de trabajo siguen siendo el contenido real (`apply` instala los filtros LFS del repositorio si faltan). Después, envía los objetos con `lfs push --all`. **Reglas de texto** (`line_endings`, `strip_exec` y `reencode` de la receta, o `--eol`, `--strip-exec`, `--reencode`): `--eol lf\|crlf\|cr --eol-paths GLOB...` da ese fin de línea a todos los archivos de texto que nombran los globs (los fines mezclados quedan uniformes; `--eol-exclude` deja archivos como están; `--eol-follow-attributes` lee el `.gitattributes` de la raíz de cada commit: los archivos `-text`/`binary` se omiten y los de `eol=` conservan su propio fin de línea); `--strip-exec GLOB...` pasa el modo 100755 a 100644 en los archivos que coinciden (al menos un glob; `--strip-exec-exclude` para librar a algunos); `--reencode utf-8\|utf-8-bom\|utf-16le\|utf-16be\|windows-1252\|iso-8859-1 --encoding-paths GLOB...` convierte los archivos de texto a esa codificación, desde `--from SOURCE` o, por defecto, detectada por archivo (marca de orden de bytes, UTF-8 válido o, si no, `--encoding-fallback`, por defecto `windows-1252`). Se ejecutan en la etapa de contenido con las demás reglas de contenido, en el orden de la receta. Los archivos binarios se omiten y se cuentan (`counts.blobs_skipped_binary`); los archivos que la codificación de origen no puede leer o que el destino no puede representar se dejan como están y se cuentan en `counts.blobs_skipped_undecodable`; `counts.blobs_changed` es el número de versiones nuevas de archivo, y las filas listan las rutas cambiadas como `modified`. `diff` muestra lo que hicieron las reglas a un archivo de un commit de una ejecución con vista previa (`{kind, binary, redacted, old_size, new_size, hunks}`); las líneas que elimina una regla de secretos se ocultan. Los scripts Lua (`--script FILE`, repetible, se ejecutan en orden después de las demás reglas; el archivo se incrusta en la receta) llaman a `rewrite_commit(c, ctx)` en cada commit y pueden devolver un nuevo `author` / `committer` (`name`, `email`, `time`, `offset_minutes`) y `message`, además del `state` que pasa a la llamada siguiente; la cabecera `--!` del script declara sus parámetros, su ventana y lo que necesita. El sandbox no tiene archivos, reloj, procesos ni módulos, y limita las instrucciones (10 millones por llamada), la memoria (64 MiB) y el tiempo (5 s por llamada). `script check` imprime `{header, functions, problems}` (código de salida 2 si `problems` no está vacío); `script test` ejecuta un script en unos commits sin escribir nada e imprime `{rows: [{commit, fields, log}]}`. Un script que falla se rechaza como `script_failed` con `refused.script = {commit, reason}`. **Scripts externos** (lenguaje `shell`, `python` o `lua-external`: `--script-language` / `--language`; por defecto, según la extensión del archivo, `.sh`, `.bash`, `.ps1`, `.py`, `.lua`, y si no, el Lua integrado) se ejecutan como un proceso aparte con tus permisos, sin aislar: una petición JSON por línea en stdin, una respuesta JSON por línea en stdout, con los mismos campos de arriba, `"error": "texto"` para rendirse, y los diagnósticos en stderr (vuelven como el `log` del commit). El entorno se vacía (solo se pasan `PATH`, `HOME`/`USERPROFILE`, `SYSTEMROOT`, `TEMP`/`TMP` y `LANG`), el directorio de trabajo es uno temporal nuevo, `rewrite.script_timeout_ms` (5000) acota cada respuesta y `rewrite.script_total_timeout_s` (3600) la pasada; ante un tiempo agotado, un fallo o una cancelación se mata todo el árbol de procesos y la reescritura se rechaza como `script_failed` (el commit y el motivo), sin mover nada. Qué lenguajes existen lo decide el ajuste `rewrite.external_scripts` (por defecto `["shell"]`; añade tú `"python"` o `"lua"`): un lenguaje desactivado se rechaza como `scripts_disabled`, y un intérprete que falta como `tool_missing` (`rewrite tools` los lista). **Confianza**: un script externo solo se ejecuta cuando una persona confió en su texto exacto: `rewrite script trust FILE` (o `--trust` en `preview`, `run`, `script check` y `script test`, que lo hace en el mismo comando) recuerda el SHA-256 del archivo para este repositorio, y un script modificado vuelve a preguntar. Un script sin confianza se rechaza como `script_not_trusted` con `refused.script = {hash}` y nunca se arranca, ni siquiera con `script check`, que informa `{trust: "untrusted", hash}` con código de salida 2; para uno de confianza, `script check` lo arranca una vez con un commit inventado (`"dry_run": true`) para comprobar su respuesta e imprime también `interpreter`. El servidor MCP no puede dar confianza: no tiene la herramienta `rewrite script trust` ni el argumento `trust`, así que un agente solo puede ejecutar un script en el que una persona ya confió. `scan-secrets` lee una vez el historial del alcance (la rama actual, `--all-local` o `--ref`) e imprime `{findings: [{id, rule, path, more_paths, first_commit, last_commit, commits, blobs, preview}], commits, blobs_scanned, blobs_skipped_binary, blobs_skipped_large}`: la regla que coincidió (prefijos de token, claves privadas, JWT, contraseñas en URL, líneas `password = value` que parecen aleatorias), una vista censurada `preview` como `ghp_****abcd` y nunca el valor; no es exhaustivo y solo lee. `analyze` es el análisis de tamaño (como `filter-repo --analyze`): una pasada por el historial del alcance que imprime `{blobs, folders, deleted, top, commits, blobs_total, bytes_total, disk_total, bytes_in_head, bytes_history_only, deleted_paths, blobs_cut, folders_cut, deleted_cut}`. `blobs` son los `--top` blobs únicos más grandes (50 por defecto, 5000 como máximo), el mayor primero, cada uno `{path, more_paths, blob, size, disk_size, first_commit, last_commit, state}` (`state` es `in_head`, `replaced` para una versión antigua de un archivo que sigue en HEAD, o `deleted`; `last_commit` es el commit que lo quitó, o si no, el que lo añadió; `disk_size` es el tamaño en la base de objetos, y un delta empaquetado cuenta como el delta); `folders` son `{path, size, blobs, in_head}` (los bytes de blobs únicos guardados alguna vez bajo ella); `deleted` son las rutas que salieron de HEAD pero que el historial aún conserva, `{path, versions, size, first_commit, last_commit}`. `bytes_history_only` es lo que liberaría, aproximadamente, quitar todo lo que solo conserva el historial, y solo tras una purga de los objetos antiguos y un gc; solo lee y nunca cambia una ref. Convierte una fila en una regla con `--remove-path RUTA` (o la carpeta) o `--remove-blobs-over BYTES`. `--remove-finding ID` (repetible, o `all`) añade una regla que quita esos hallazgos de todos los commits: el daemon vuelve a analizar el mismo alcance y resuelve los ids él mismo, así que el valor nunca llega a la línea de comandos, a una receta ni a un registro. Un secreto que ya se publicó se considera filtrado: rótalo primero. Los secretos nunca van en la línea de comandos ni en una receta guardada: `--secrets-file F` (uno por línea) rellena las reglas de secretos `content_replace` de la receta y nunca se repite en la salida. Códigos de salida: 0 hecho; 1 error (receta ilegible, flags incorrectos); 2 rechazado, impreso como `{"refused":{reason, message, detail}}` con el motivo `stale` (digest incorrecto, ejecución desconocida, una ref se movió desde la vista previa), `no_rule`, `invalid_rule`, `empty_scope`, `shallow`, `signature_choice_needed`, ...; 3 el plan mueve refs que ya están en un remoto y falta `--yes`, impreso como `{"needs_confirmation":{prompt}}`, no cambia nada (`run` también descarta su vista previa). |

### Espacios de trabajo y búsqueda

Un **espacio de trabajo** es un grupo con nombre de repositorios, con un perfil de
commit predeterminado opcional. Vive en `workspaces.toml`, junto a `config.toml`,
y lo comparten todas las sesiones y la ventana, así que los comandos `workspace`
no arrancan ningún daemon (solo `add` y `create --add` le piden uno la URL de
`origin` de cada repositorio). Un repositorio puede estar en varios espacios de
trabajo. Las rutas se comparan como los favoritos y la lista de recientes.

| Comando | Qué hace |
|---|---|
| `workspace list`, `workspace show <id>` | `{workspaces: [...]}` / `{workspace}`: `id` (un slug, estable al renombrar), `name`, `color`, `description`, `profile`, `profile_exists` y `repos: [{path, exists, remote}]` (`remote` es la URL de `origin` registrada al añadir el repositorio, sin credenciales). |
| `workspace create <name> [--add PATH]... [--profile ID] [--color C] [--description T]` | Crea un espacio de trabajo y lo imprime; dos espacios de trabajo no pueden compartir nombre. `--add` es repetible y no es `--repo`, que elige el repositorio donde se ejecuta un comando. |
| `workspace rename <id> <name>`, `workspace delete <id>` | Renombrar mantiene el id. Eliminar nunca toca los repositorios. |
| `workspace add <id> <path>...`, `workspace remove <id> <path>...` | `add` registra la raíz y la URL de `origin` de cada repositorio (una ruta que no existe, o que no está dentro de un repositorio, se rechaza con un mensaje y no se guarda nada: solo un repositorio que desaparece más tarde sigue en la lista, marcado como ausente); `remove` acepta también la ruta de un repositorio que ya no está en el disco. |
| `workspace set-profile <id> <profile>` / `--none` | El id de `[[profiles]]` con el que se hacen los commits en los repositorios del espacio de trabajo. Un id que no corresponde a ningún perfil se guarda (`profile_exists: false`) y no se aplica. |
| `workspace set-ai-instructions <id> [--action <a>] [--mode append\|replace] (--text T \| --clear)` | Las instrucciones de IA del espacio de trabajo, para todas las acciones o para una (`commit_message`, `code_review`, ...). `append` las añade después de las globales, `replace` las usa en su lugar. Se aplican a todos los repositorios del espacio de trabajo, antes de las propias del repositorio. `workspace show` las imprime como `ai_instructions`. |
| `commit -m M [--workspace ID]` | Hace el commit con el perfil del espacio de trabajo cuando el repositorio está en él y el perfil existe; si no, `general.active_profile`; si no, la identidad del propio repositorio. Sin `--workspace` (o `GITPOULPI_WORKSPACE`) nada cambia: un commit nunca adivina un espacio de trabajo por pertenencia, porque un repositorio puede estar en varios. Un id desconocido es un error. |
| `search <query> [--workspace ID] [--kind K]... [--limit N]` | Búsqueda aproximada en ramas (locales y remotas), tags, worktrees, stashes, mensajes de commit y las pull/merge requests e issues de las cachés de alojamiento, del repositorio actual o de todos los repositorios del espacio de trabajo (`GITPOULPI_WORKSPACE` sustituye a la opción). La versión de la ventana es [Búsqueda](search.md). |

`search` responde `{query, workspace, hits, partial, repos}`. Cada resultado es
`{kind, label, detail, target, score, positions, repo}`: `kind` es `branch`,
`tag`, `commit`, `stash`, `worktree`, `repo`, `pull_request` o `issue`;
`positions` son los caracteres de `label` que coinciden, para resaltarlos;
`target` dice adónde ir (`{type: "ref", name}` con el nombre completo de la ref,
`{type: "commit", id}`, `{type: "stash", index, id}`, `{type: "worktree", path}`,
`{type: "repo", path}`, `{type: "pull_request", number}`,
`{type: "issue", number}`); los resultados se mezclan entre repositorios por
`score`, el mejor primero. La coincidencia es la de la paleta de comandos: la
consulta literal, luego literal en cualquier posición, luego sus caracteres en
orden (gana lo más temprano y más corto). El cuerpo de un commit solo se busca
cuando su asunto no coincide y la consulta tiene tres caracteres o más. Un
prefijo acota la búsqueda y no forma parte del texto: `b:` ramas, `t:` tags, `c:`
commits, `s:` stashes, `w:` worktrees, `r:` repositorios (solo en un espacio de
trabajo), `pr:` (o `mr:`) pull/merge requests, `i:` issues, `#` ambos; `--kind`
(repetible, mismos nombres) también filtra. `partial` es true cuando los commits
de un repositorio se cortaron en
[`search.commit_limit`](config-reference.md#search-la-búsqueda-en-el-espacio-de-trabajo);
`repos` dice por cada repositorio si se buscó en él (con `reason` cuando no: una
ruta que ya no está en el disco se informa, nunca es fatal). Un comando puntual
construye primero el índice de cada repositorio; con una ventana abierta en la
misma sesión, el daemon ya lo tiene en caliente. Las pull/merge requests y los
issues se leen de la caché de alojamiento de cada repositorio (el archivo que la
ventana mantiene en `.gitpoulpi/hosting-cache.json`) y nunca de un host: un
repositorio cuya ventana nunca los cargó no tiene nada que encontrar, y una caché
ausente o a medio escribir simplemente no da resultados.

**Mostrar cosas en la ventana abierta** (`ui`; todos los comandos aceptan además
`--viewer <id>` y `--launch`)

| Comando | Qué hace |
|---|---|
| `ui viewers [--all-sessions]`, `ui state [--text]` | Las ventanas abiertas; lo que muestra una. |
| `ui show commit <rev> [--also R] [--files] [--focus refs\|log\|status]`, `ui show ref <name>`, `ui show pr <n>`, `ui show issue <n>`, `ui show wip [path] [--staged] [--composer]` | Selecciona algo. |
| `ui show diff <path> [--rev R \| --unstaged \| --staged] [--line N] [--side old\|new] [--split \| --inline] [--whole-file \| --hunks] [--highlight A-B]` | Abre un diff en una línea. |
| `ui show file <path> [--rev R \| --worktree \| --index] [--blame \| --history] [--line N] [--column C] [--highlight A-B]` | Abre un archivo, su blame o su historial. |
| `ui show tab [path]`, `ui show home [--filter F]`, `ui show search <query>`, `ui show palette [query]`, `ui show keys [topic]`, `ui show settings [page] [--setting KEY]` | Va a una pestaña, a Inicio, a la barra de búsqueda, a la paleta, a la ayuda, a una página de Ajustes. `gitpoulpi ui show settings --help` lista los nombres de página. |
| `ui highlight <A[:C]-B[:C]> [--no-scroll]`, `ui notify <message>`, `ui back` | Tiñe líneas; un toast; deshace el último cambio de vista. |
| `ui show conflict <path> [--conflict N]` | Abre el editor de merge sobre un archivo en conflicto, en el conflicto N (no se elige ni se guarda nada). |
| `ui propose reword <rev> -m M`, `ui propose commit-message <summary> [--body B]`, `ui propose branch <name> [--start-point R]`, `ui propose tag <name> [--target R] [-m M]` | Abre un diálogo rellenado de antemano que confirmas tú (necesita `[mcp] allow_ui_propose = true`). |
| `ui propose split <rev> --plan <file\|->` | Abre el editor de división sobre un commit, rellenado con un plan (el JSON de `split-commit --plan`) para que lo revises, edites y apliques; no se divide nada hasta que lo hagas. Misma puerta que las demás propuestas. |
| `ui propose rewrite --recipe <file\|->` | Abre el editor de reescritura del historial con una receta (TOML o JSON, como la acepta `rewrite preview --recipe`) ya puesta, para que la revises con la vista previa y la apliques; no se reescribe, purga ni envía nada hasta que lo hagas tú. Una propuesta lleva como máximo 50 reglas, ningún script (un script se ejecutaría al previsualizar) y ningún valor secreto. La misma compuerta que las demás propuestas. |
| `ui propose resolution <path> (--pick 1=a,2=ba,... [--default a\|b] \| --content-file F)` | Abre el editor de merge con una resolución ya elegida (o el archivo entero como texto) para que la revises; tu Guardar y marcar resuelto es la única confirmación. Misma puerta que las demás propuestas. |

Códigos de salida: 0 aplicado, 3 diferido al usuario, 1 en los demás casos. Detalles y reglas
que sigue la ventana: [MCP y agentes](mcp-and-agents.md#mostrar-cosas-al-usuario).

## Notas

- **Sesiones.** `gitpoulpi session list` muestra cada sesión con `live` / `stale`
  (se decide conectando a su puerto). El nombre derivado es
  `<carpeta>-<hash de la ruta>`.
- **Sin preguntas interactivas.** Nada hace una pregunta: las operaciones arriesgadas o
  necesitan una opción (`--yes`, `--force-with-lease`) o se rechazan con un motivo.
- **No está en la CLI**: `checkout --file` (restaurar un archivo) solo está en la ventana.
