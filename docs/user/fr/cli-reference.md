# Référence CLI

`gitpoulpi` sans sous-commande ouvre la fenêtre ; avec une sous-commande, c'est un
client git scriptable. Chaque commande passe par le même démon d'arrière-plan que
la fenêtre, si bien qu'un changement fait depuis un script apparaît en direct dans
un GitPoulpi ouvert. Les outils MCP qu'obtient un agent sont générés à partir de ces
mêmes commandes ([MCP et agents](mcp-and-agents.md)). `gitpoulpi <commande> --help`
donne chaque option.

## Options globales

| Option | Effet |
|---|---|
| `--json` | Affiche le résultat en JSON. Les erreurs aussi sont en JSON : `{"error": "..."}` sur stdout, code de sortie 1. Une opération git qui échoue ajoute `"detail": {"operation", "command", "exit_code", "stderr"}` (la commande git exécutée, secrets masqués, son code de sortie et la fin de son stderr ; pour la bibliothèque git intégrée `"git2": {"class", "code", "message"}`) ; les outils MCP renvoient le même objet. Sans `--json`, les lignes vont sur stderr. |
| `--repo <path>` | Le dépôt sur lequel agir (par défaut : celui qui entoure le dossier courant, comme git). |
| `-s, --session <name>` | La session (le démon) avec laquelle parler. Par défaut : déduite de la racine du dépôt, si bien que tout ce qui est ouvert dans un dépôt partage un démon et que deux dépôts en ont deux. |
| `--backend git2\|system` | Moteur d'un démon que cette commande démarre (un démon déjà lancé garde le sien). |
| `--cwd-file <file>` | Où la fenêtre écrit le dossier de l'onglet actif quand elle quitte (utilisé par `shell-init`). |
| `-a, --add [path]`, `--no-raise` | Ouvre un dossier dans un nouvel onglet du GitPoulpi déjà lancé au lieu d'en démarrer un autre ; voir [Ajouter un dossier à la fenêtre ouverte](#ajouter-un-dossier-à-la-fenêtre-ouverte). N'accepte aucune sous-commande. |
| `-l, --lang <lang>` | Langue du texte de `--help` seulement : `en`, `fr`, `es`, `pt-BR`, `pt-PT`, `it`, `de`, `zh-CN`, `ja`, `ko`, `ru`, `uk`, `pl`, `cs`, `nl`, `sv`, `tr`. Voir [Aide traduite](#aide-traduite). |

### Ajouter un dossier à la fenêtre ouverte

`gitpoulpi --add [path]` (`-a` ; `gp -a` et l'alias de commande `gpa` exécutent le même
code) ouvre `path` (par défaut : le dossier courant, résolu en son dépôt englobant) dans un nouvel onglet d'un GitPoulpi
déjà lancé, si bien qu'un dossier dans lequel vous faites `cd` dans un terminal ne démarre pas une seconde fenêtre.

- Une *session lancée* est une session dont le démon répond et à laquelle une fenêtre GitPoulpi est rattachée. Les fenêtres dont
  l'utilisateur a désactivé **Laisser les agents IA piloter la vue** ne s'annoncent pas et ne sont pas trouvées (la même
  limite que pour `gitpoulpi launch`).
- Une seule session lancée : elle reçoit l'onglet (ou affiche l'onglet si ce dépôt est déjà ouvert), sa fenêtre
  passe au premier plan si le bureau le permet (Windows, WezTerm, Hyprland ; `--no-raise` l'évite), et une
  ligne indique quelle session l'a reçu.
- Plusieurs : elles sont listées, numérotées, avec leur nombre d'onglets et les noms de leurs dépôts ; tapez le numéro puis Enter
  (une ligne vide ou Esc puis Enter annule, code de sortie 130). Sans terminal sur l'entrée standard, la commande échoue et
  demande de passer `--session NAME`. `-s NAME` évite la question.
- Aucune (ou `-s NAME` désigne une session qui n'est pas lancée) : GitPoulpi démarre normalement dans ce terminal sur ce
  dossier, exactement comme `gp [path]`.
- La fenêtre l'applique aussitôt, comme un choix de votre part (ni pastille de confirmation, ni marque d'agent), sauf si vous
  saisissez du texte dans un formulaire : la fenêtre propose alors l'onglet dans la pastille de sa ligne d'état et le code de sortie est 3. Un dossier
  qui n'est pas dans un dépôt est refusé (code de sortie 1).

`--json` affiche un objet : `{"action": "joined", "session", "repo", "already_open", "raised", "outcome": {...}}`
(`outcome` est la réponse de la fenêtre, comme pour `ui show`) ou `{"action": "cancelled"}` ; les erreurs sont `{"error": "..."}`.
Codes de sortie : 0 l'onglet est ouvert, 3 proposé dans la pastille, 1 refusé ou échec, 130 annulé. Il n'existe pas d'outil MCP
pour cela : un agent qui veut montrer un dépôt à l'utilisateur utilise `ui show tab`.

### Aide traduite

`gitpoulpi --help` est en anglais. Ajoutez `-l` pour lire les explications dans une
autre langue : `gitpoulpi -l fr --help`, `gitpoulpi -l de commit --help`. Seuls les
explications et les titres de section sont traduits. Les noms de commandes, les
options, les noms de valeurs et les valeurs possibles ne changent pas, si bien que
les scripts et les agents voient la même interface. La langue de l'aide n'est pas lue
dans l'environnement : la sortie ne change que si vous donnez `-l`. Les descriptions
des outils MCP sont toujours en anglais.

Les révisions acceptent tout ce que git accepte (`HEAD~2`, une branche, un tag, un
sha court). Les hunks et les lignes sont numérotés comme les numérote
`gitpoulpi --json diff`.

La re-signature utilise la configuration du dépôt (`gpg.format` openpgp, ssh ou x509, `user.signingkey`, `gpg.*.program`) et se fait pendant l'aperçu (l'identifiant d'un commit signé inclut sa signature) : `counts.resigned` et `counts.signing_millis` du plan indiquent combien et en combien de temps. Une configuration qui ne signe pas est refusée d'emblée sous la forme `signing_failed` (ou `tool_missing`), avant toute lecture. `rewrite check-signing` lance ce seul test (signe et vérifie une fois une charge factice) et affiche `{format, tool, millis}`, la durée d'une signature, pour estimer une exécution (code de sortie 2 avec la raison en cas d'échec ; une demande de phrase secrète peut s'ouvrir). `--remove-signatures` ajoute la règle qui retire la signature de chaque commit du périmètre, même quand rien d'autre ne change ; ces commits n'ont pas besoin de réponse à `--signatures`. `--fix-message-encoding` ajoute la règle qui réencode les messages en UTF-8 : un commit avec un en-tête `encoding` (ISO-8859-1, Shift_JIS...) est décodé et l'en-tête disparaît, et de l'UTF-8 qui a été lu comme du Latin-1 ou du Windows-1252 (`RÃ©Ã©criture`) n'est réparé que si l'aller-retour est exact ; ce qui ne peut pas être décidé reste tel quel et est compté dans `counts.encoding_left`. Les noms d'un commit dont l'en-tête disparaît sont décodés avec lui, et `--fix-name-encoding` répare aussi les noms abîmés ailleurs. `preview` établit le plan sans rien modifier et affiche `{run, digest, counts, refs, warnings, per_rule, rows, rows_total}` (les `--limit` premiers commits modifiés, 50 par défaut, ou `--all`) ; il le garde dans le démon de la session et sur disque, dans le dossier git du dépôt (`gitpoulpi/rewrite/<run>/`) : `apply --run ID --digest D` fonctionne depuis une commande ultérieure, après un redémarrage du démon ou depuis une autre interface, sans `daemon start` ; un plan stocké qui ne correspond plus à son empreinte est `stale`. Seul `rows` a besoin du démon qui a fait l'aperçu (un démon en cours d'exécution, par exemple celui du TUI ou `daemon start`) : utilisez `preview --all` pour voir toutes les lignes en une commande. Les règles d'identité et d'anonymisation ne réécrivent le tagger des tags annotés recréés que si la recette définit `include_taggers`. `rows` pagine l'exécution `{run, filter, offset, total, rows}` (200 par page au plus). `apply` exécute le plan que vous avez relu (son `run` et son `digest`) en UNE seule entrée d'annulation et affiche `{run, moved, commits_changed}` ; `undo` remet tout en place. Il ne pousse jamais : une ref déjà poussée demande ensuite votre push forcé. `run` fait l'aperçu et l'application en une commande (sans démon requis) et affiche `{plan, outcome}`. `discard` abandonne une exécution (deux fois est sans danger). Les règles de trailers (`--trailer-add KEY=VALUE`, `--trailer-remove KEY`, `--trailer-map KEY:OLD=NEW`, répétables, dans cet ordre après `--replace-message`) modifient les lignes `Clé: valeur` du dernier paragraphe de chaque message avec la grammaire de `git interpret-trailers` : `--trailer-add` laisse de côté un message qui a déjà exactement ce trailer, `--trailer-remove` retire tous les trailers de la clé, `--trailer-map` remplace du texte littéral dans les valeurs de la clé ; le reste du message n'est pas touché (une recette peut aussi définir `if_exists` à `replace` ou `skip`, un motif `find` sur `remove`, et des motifs `regex`). `--map-trailers` (nécessite les options d'identité) fait que la règle d'identité réécrit aussi les trailers `Nom <e-mail>` qu'elle reconnaît. `--update-message-hashes` remplace les identifiants de commit abrégés (7 caractères hexadécimaux ou plus) des messages par les nouveaux identifiants de même longueur quand un seul commit réécrit correspond ; `counts.message_hashes_updated` et `counts.message_hashes_left` (ambigus, inconnus ou créés plus tard) du plan disent ce qui s'est passé. Les règles de contenu (`remove_paths`, `remove_blobs_over` et `content_replace` de la recette, ou les options `--remove-path`, `--remove-blobs-over`, `--replace-content`) réécrivent les fichiers de chaque commit : chaque fichier distinct est lu une seule fois, les fichiers binaires sont ignorés et comptés (`counts.blobs_skipped_binary`), un commit qu'une règle laisse vide est supprimé (`counts.commits_dropped`, lignes avec `new: null` ; `--prune-empty never` le conserve) et ses enfants passent sur son parent, et les fichiers extraits suivent le nouvel arbre. Refus `dirty_paths_touched` quand un fichier avec des modifications locales est de ceux que la réécriture changerait, `checked_out_elsewhere` quand une branche réécrite est extraite dans un autre worktree, `partial_clone` dans un clone partiel. Les règles de chemin (`--move-path FROM=TO`, répétable ; `--into-subdir DIR` ; `--extract DIR`, ou `move_paths` de la recette) renomment un fichier ou un dossier, déplacent tout le dépôt dans un sous-dossier, ou ne gardent qu'un sous-dossier comme nouvelle racine ; elles agissent sur les arbres, donc chaque fichier garde son identifiant, et s'exécutent après les règles de contenu. Un renommage n'écrase jamais rien : là où le nouveau chemin existe dans un commit, l'aperçu est refusé sous la forme `path_collision` (code de sortie 2), avec les identifiants courts des commits et les chemins dans `refused.detail`. `--extract` est **demandé à chaque fois** : sans `--extract-mode` (`clone`, `in-place` ou `submodule`), rien n'est prévisualisé et la réponse est `{"needs_choice":{choice:"extract_mode", options, prompt}}` avec le code de sortie 3. `in-place` réécrit ce dépôt comme n'importe quelle règle (une entrée d'annulation ; les branches et les tags qui ne contiennent rien du dossier sont supprimés, lignes avec `refs[].new: null` ; la branche extraite doit avoir le dossier, sinon `empty_scope`). `clone` et `submodule` prévisualisent l'historique que contiendra le nouveau dépôt sur chaque branche et chaque tag locaux, rien n'y est poussé ni protégé, et s'appliquent avec le dossier du nouveau dépôt : `--target PATH` sur `run`, ou sur `apply` (`rewrite apply` d'un tel plan sans `--target` est refusé sous la forme `invalid_rule` ; le dossier ne doit pas exister, ou doit être vide, et ne pas se trouver dans le dépôt). `clone` y fait un `git clone --no-local` de ce dépôt, le réécrit avec la recette, retire le distant, fait expirer les reflogs et élague les anciens objets : il ne contient donc que l'historique extrait ; ce dépôt-ci n'est pas touché et rien n'est journalisé (`outcome.moved` est vide). `submodule` fait pareil, puis ajoute un commit sur la branche courante qui remplace le dossier par un sous-module du nouveau dépôt (l'URL de `.gitmodules` est son chemin local), l'initialise et le journalise (`outcome.moved` contient la branche ; `undo` la remet en place et libère le sous-module) ; l'historique n'est pas réécrit, donc les anciens commits gardent le dossier. Des fichiers modifiés ou non suivis dans le dossier, ou un HEAD détaché, le refusent. Ordre en cas de combinaison : les règles de contenu (`--replace-content`, `--remove-blobs-over`, `--lfs-import`, `--lfs-export`) et `--remove-path` s'exécutent d'abord sur les chemins d'origine, puis les règles de chemin ; un motif LFS et un glob de suppression désignent donc les chemins d'origine, et les lignes `.gitattributes` d'un import sont ajoutées à la racine d'origine puis suivent les fichiers. **Règles LFS** (`lfs_import { patterns, min_size }` et `lfs_export { patterns }` de la recette, ou `--lfs-import PATTERN...` avec `--lfs-min-size BYTES`, et `--lfs-export PATTERN...`) nécessitent `git-lfs` (sinon `tool_missing`) : un import transforme les fichiers correspondants en pointeurs spec v1 dans chaque commit, écrit leur contenu dans le stockage LFS local à l'application (de façon atomique, une fois par contenu) et ajoute `<motif> filter=lfs diff=lfs merge=lfs -text` au `.gitattributes` racine de chaque commit réécrit qui contient un pointeur (le reste du fichier n'est pas touché) ; un export retransforme les pointeurs correspondants en fichiers et retire ces lignes, et il est refusé sous la forme `lfs_objects_missing` (`detail` : un `<oid> <chemin>` par ligne) quand les objets ne sont pas dans le stockage local (faites d'abord `lfs fetch`). `counts.lfs_blobs`, `lfs_bytes`, `lfs_objects`, `lfs_restored` et `lfs_run` du plan disent ce qui se passe, les lignes listent les chemins `lfs_imported` / `lfs_exported`, et les fichiers extraits gardent leur vrai contenu (l'application installe les filtres LFS du dépôt s'ils manquent). Envoyez ensuite les objets avec `lfs push --all`. **Règles sur le texte** (`line_endings`, `strip_exec` et `reencode` de la recette, ou `--eol`, `--strip-exec`, `--reencode`) : `--eol lf\|crlf\|cr --eol-paths GLOB...` donne cette fin de ligne à chaque fichier texte que les globs désignent (les fins de ligne mélangées deviennent uniformes ; `--eol-exclude` laisse des fichiers tels quels ; `--eol-follow-attributes` lit le `.gitattributes` racine de chaque commit : les fichiers `-text`/`binary` sont ignorés et ceux en `eol=` gardent leur propre fin de ligne) ; `--strip-exec GLOB...` fait passer le mode 100755 à 100644 sur les fichiers correspondants (au moins un glob, `--strip-exec-exclude` pour en épargner) ; `--reencode utf-8\|utf-8-bom\|utf-16le\|utf-16be\|windows-1252\|iso-8859-1 --encoding-paths GLOB...` convertit les fichiers texte dans cet encodage, depuis `--from SOURCE` ou, par défaut, l'encodage détecté fichier par fichier (marque d'ordre des octets, UTF-8 valide, sinon `--encoding-fallback`, `windows-1252` par défaut). Elles s'exécutent à l'étape du contenu avec les autres règles de contenu, dans l'ordre de la recette. Les fichiers binaires sont ignorés et comptés (`counts.blobs_skipped_binary`) ; les fichiers que l'encodage source ne sait pas lire ou que la cible ne peut pas contenir restent tels quels et sont comptés dans `counts.blobs_skipped_undecodable` ; `counts.blobs_changed` est le nombre de nouvelles versions de fichier, et les lignes listent les chemins modifiés comme `modified`. `diff` montre ce que les règles ont fait à un fichier d'un commit d'une exécution prévisualisée (`{kind, binary, redacted, old_size, new_size, hunks}`) ; les lignes qu'une règle de secrets retire sont masquées. Les scripts Lua (`--script FILE`, répétable, exécutés dans l'ordre après les autres règles ; le fichier est intégré à la recette) appellent `rewrite_commit(c, ctx)` sur chaque commit et peuvent renvoyer de nouveaux `author` / `committer` (`name`, `email`, `time`, `offset_minutes`) et `message`, ainsi que le `state` transmis à l'appel suivant ; l'en-tête `--!` du script déclare ses paramètres, sa plage et ses besoins. Le bac à sable n'a ni fichiers, ni horloge, ni processus, ni modules, et limite les instructions (10 millions par appel), la mémoire (64 MiB) et le temps (5 s par appel). `script check` affiche `{header, functions, problems}` (code de sortie 2 si `problems` n'est pas vide) ; `script test` exécute un script sur quelques commits sans rien écrire et affiche `{rows: [{commit, fields, log}]}`. Un script qui échoue est refusé sous la forme `script_failed` avec `refused.script = {commit, reason}`. **Scripts externes** (langage `shell`, `python` ou `lua-external` : `--script-language` / `--language`, par défaut selon l'extension du fichier `.sh`, `.bash`, `.ps1`, `.py`, `.lua`, sinon le Lua intégré) s'exécutent comme un processus à part avec vos droits, sans isolation : une requête JSON par ligne sur l'entrée standard, une réponse JSON par ligne sur la sortie standard, avec les mêmes champs que ci-dessus, `"error": "texte"` pour abandonner, les diagnostics sur la sortie d'erreur (ils reviennent dans le `log` du commit). L'environnement est vidé (seuls `PATH`, `HOME`/`USERPROFILE`, `SYSTEMROOT`, `TEMP`/`TMP` et `LANG` sont transmis), le dossier de travail est un dossier temporaire neuf, `rewrite.script_timeout_ms` (5000) borne chaque réponse et `rewrite.script_total_timeout_s` (3600) l'ensemble de la passe ; en cas de dépassement, de plantage ou d'annulation, tout l'arbre de processus est tué et la réécriture est refusée sous la forme `script_failed` (le commit et la raison), sans que rien ne bouge. Les langages disponibles sont ceux du réglage `rewrite.external_scripts` (par défaut `["shell"]` ; ajoutez vous-même `"python"` ou `"lua"`) : un langage désactivé est refusé sous la forme `scripts_disabled`, un interpréteur absent sous la forme `tool_missing` (`rewrite tools` les liste). **Confiance** : un script externe ne s'exécute que si une personne a approuvé son texte exact : `rewrite script trust FILE` (ou `--trust` sur `preview`, `run`, `script check` et `script test`, qui le fait dans la même commande) mémorise le SHA-256 du fichier pour ce dépôt, et un script modifié redemande. Un script non approuvé est refusé sous la forme `script_not_trusted` avec `refused.script = {hash}` et n'est jamais lancé, pas même par `script check`, qui affiche `{trust: "untrusted", hash}` avec le code de sortie 2 ; pour un script approuvé, `script check` le lance une fois avec un commit fictif (`"dry_run": true`) pour vérifier sa réponse et affiche aussi `interpreter`. Transformez une ligne en règle avec `--remove-path CHEMIN` (ou le dossier) ou `--remove-blobs-over OCTETS`. `--remove-finding ID` (répétable, ou `all`) ajoute une règle qui retire ces résultats de chaque commit : le démon relance l'analyse sur le même périmètre et résout lui-même les identifiants, donc la valeur n'atteint jamais la ligne de commande, une recette ni un journal. Un secret qui a été poussé est compromis : renouvelez-le d'abord. Les secrets ne passent jamais par la ligne de commande ni par une recette enregistrée : `--secrets-file F` (un par ligne) alimente les règles de secrets `content_replace` de la recette et n'est jamais répété. ### Espaces de travail et recherche

Un **espace de travail** est un groupe nommé de dépôts, avec éventuellement un
profil de commit par défaut. Il vit dans `workspaces.toml` à côté de
`config.toml`, partagé par toutes les sessions et par la fenêtre ; les commandes
`workspace` ne démarrent donc aucun démon (seuls `add` et `create --add` en
interrogent un pour l'URL `origin` de chaque dépôt). Un dépôt peut être dans
plusieurs espaces de travail. Les chemins sont comparés comme pour les favoris et
la liste des récents.

| Commande | Ce qu'elle fait |
|---|---|
| `workspace list`, `workspace show <id>` | `{workspaces: [...]}` / `{workspace}` : `id` (un slug, stable quand on renomme), `name`, `color`, `description`, `profile`, `profile_exists`, et `repos: [{path, exists, remote}]` (`remote` est l'URL `origin` enregistrée à l'ajout du dépôt, identifiants retirés). |
| `workspace create <nom> [--add CHEMIN]... [--profile ID] [--color C] [--description T]` | Crée un espace de travail et l'affiche ; deux espaces de travail ne peuvent pas porter le même nom. `--add` est répétable et n'est pas `--repo`, qui choisit le dépôt dans lequel une commande s'exécute. |
| `workspace rename <id> <nom>`, `workspace delete <id>` | Renommer garde l'id. Supprimer ne touche jamais aux dépôts. |
| `workspace add <id> <chemin>...`, `workspace remove <id> <chemin>...` | `add` enregistre la racine et l'URL `origin` de chaque dépôt (un chemin qui n'existe pas, ou qui n'est pas dans un dépôt, est refusé avec un message et rien n'est enregistré : seul un dépôt qui disparaît plus tard reste listé, marqué absent) ; `remove` accepte aussi le chemin d'un dépôt disparu du disque. |
| `workspace set-profile <id> <profil>` / `--none` | L'id de `[[profiles]]` avec lequel les commits sont faits dans les dépôts de l'espace de travail. Un id qui ne désigne aucun profil est enregistré (`profile_exists: false`) et ne s'applique pas. |
| `workspace set-ai-instructions <id> [--action <a>] [--mode append\|replace] (--text T \| --clear)` | Les instructions IA de l'espace de travail, pour toutes les actions ou pour une seule (`commit_message`, `code_review`, ...). `append` les ajoute après les globales, `replace` les utilise à leur place. | `commit -m M [--workspace ID]` | Commite avec le profil de l'espace de travail quand le dépôt y est et que le profil existe ; sinon `general.active_profile` ; sinon l'identité propre du dépôt. | `search <requête> [--workspace ID] [--kind K]... [--limit N]` | Recherche approximative dans les branches (locales et distantes), tags, worktrees, stashes, messages de commit et les pull/merge requests et tickets des caches de l'hébergeur, du dépôt courant ou de tous les dépôts de l'espace de travail (`GITPOULPI_WORKSPACE` remplace l'option). La version de la fenêtre est la [Recherche](search.md). |

`search` répond `{query, workspace, hits, partial, repos}`. Chaque résultat est
`{kind, label, detail, target, score, positions, repo}` : `kind` vaut `branch`,
`tag`, `commit`, `stash`, `worktree`, `repo`, `pull_request` ou `issue` ;
`positions` sont les caractères de `label` qui ont correspondu, à mettre en
surbrillance ; `target` dit où aller (`{type: "ref", name}` avec le nom complet
de la ref, `{type: "commit", id}`, `{type: "stash", index, id}`,
`{type: "worktree", path}`, `{type: "repo", path}`,
`{type: "pull_request", number}`, `{type: "issue", number}`) ; les résultats sont
fusionnés entre dépôts par `score`, le meilleur en premier. La correspondance est
celle de la palette : la requête telle quelle, puis telle quelle n'importe où,
puis ses caractères dans l'ordre (plus tôt et plus court gagnent). Le corps d'un
commit n'est cherché que lorsque son sujet ne correspond pas et que la requête
compte trois caractères ou plus. Un préfixe restreint la recherche et ne fait pas
partie du texte : `b:` branches, `t:` tags, `c:` commits, `s:` stashes, `w:`
worktrees, `r:` dépôts (espace de travail seulement), `pr:` (ou `mr:`)
pull/merge requests, `i:` tickets, `#` ces deux derniers ; `--kind` (répétable,
mêmes noms) filtre aussi.
`partial` vaut vrai quand les commits d'un dépôt ont été coupés à
[`search.commit_limit`](config-reference.md#search-la-recherche-dans-lespace-de-travail) ;
`repos` dit pour chaque dépôt s'il a été cherché (`reason` sinon : un chemin
disparu du disque est signalé, jamais fatal). Une commande ponctuelle construit
d'abord l'index de chaque dépôt ; avec une fenêtre ouverte sur la même session, le
démon l'a déjà au chaud. Les pull/merge requests et les tickets sont lus dans le
cache d'hébergement de chaque dépôt (le fichier que la fenêtre garde dans
`.gitpoulpi/hosting-cache.json`) et jamais depuis un hébergeur : un dépôt dont la
fenêtre ne les a jamais chargés n'en a aucun à trouver, et un cache absent ou à
moitié écrit donne simplement zéro résultat.

**Montrer des choses dans la fenêtre ouverte** (`ui` ; chaque commande accepte aussi
`--viewer <id>` et `--launch`)

| Commande | Ce qu'elle fait |
|---|---|
| `ui viewers [--all-sessions]`, `ui state [--text]` | Les fenêtres ouvertes ; ce que l'une montre. |
| `ui show commit <rev> [--also R] [--files] [--focus refs\|log\|status]`, `ui show ref <name>`, `ui show pr <n>`, `ui show issue <n>`, `ui show wip [path] [--staged] [--composer]` | Sélectionner quelque chose. |
| `ui show diff <path> [--rev R \| --unstaged \| --staged] [--line N] [--side old\|new] [--split \| --inline] [--whole-file \| --hunks] [--highlight A-B]` | Ouvrir un diff à une ligne. |
| `ui show file <path> [--rev R \| --worktree \| --index] [--blame \| --history] [--line N] [--column C] [--highlight A-B]` | Ouvrir un fichier, son blame ou son historique. |
| `ui show tab [path]`, `ui show home [--filter F]`, `ui show search <query>`, `ui show palette [query]`, `ui show keys [topic]`, `ui show settings [page] [--setting KEY]` | Aller à un onglet, à l'Accueil, à la barre de recherche, à la palette, à l'aide, à une page des Paramètres. `gitpoulpi ui show settings --help` liste les noms de pages. |
| `ui highlight <A[:C]-B[:C]> [--no-scroll]`, `ui notify <message>`, `ui back` | Teinter des lignes ; une notification ; annuler le dernier changement de vue. |

| `ui propose reword <rev> -m M`, `ui propose commit-message <summary> [--body B]`, `ui propose branch <name> [--start-point R]`, `ui propose tag <name> [--target R] [-m M]` | Ouvrir une boîte préremplie que vous confirmez (demande `[mcp] allow_ui_propose = true`). |
| `ui propose split <rev> --plan <file\|->` | Ouvre l'éditeur de scission sur un commit, rempli avec un plan (le JSON de `split-commit --plan`) que vous relisez, modifiez et appliquez ; rien n'est scindé avant. Même condition que les autres propositions. |
| `ui propose rewrite --recipe <file\|->` | Ouvre l'atelier de réécriture d'historique avec une recette (TOML ou JSON, comme `rewrite preview --recipe`) déjà remplie, que vous prévisualisez et appliquez ; rien n'est réécrit, purgé ni poussé avant. Une proposition contient au plus 50 règles, aucun script (il s'exécuterait à l'aperçu) et aucune valeur secrète. Même condition que les autres propositions. |
| `ui propose resolution <path> (--pick 1=a,2=ba,... [--default a\|b] \| --content-file F)` | Ouvrir l'éditeur de merge avec une résolution déjà choisie (ou tout le fichier comme texte) à relire ; votre Enregistrer et marquer résolu est la seule confirmation. que suit la fenêtre : [MCP et agents](mcp-and-agents.md#montrer-des-choses-à-lutilisateur).

## Notes

- **Sessions.** `gitpoulpi session list` montre chaque session avec `live` / `stale`
  (décidé en se connectant à son port). Le nom déduit est
  `<dossier>-<hash du chemin>`.
- **Aucune question interactive.** Rien ne pose de question : les opérations risquées
  demandent soit une option (`--yes`, `--force-with-lease`), soit sont refusées avec une
  raison.
- **Pas dans la CLI** : `checkout --file` (restaurer un fichier) n'existe que dans la
  fenêtre.
