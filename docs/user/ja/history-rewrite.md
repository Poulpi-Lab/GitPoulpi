# 履歴の書き換え

履歴の書き換えは、すでにある commit を変更します。誰がいつ書いたか、メッセージ、含まれるファイル、署名などです。GitPoulpi は **レシピ**（対象範囲と、順番のあるルールの一覧）と 3 つの手順で行います。途中の手順は省略できません。

1. **プレビュー**は、何も変更せずに新しい履歴を計算します。件数、各ルールが行ったこと、動くブランチと tag、変更される commit ごとの 1 行が分かります。
2. **適用**は、ローカルのブランチと tag を新しい履歴へ動かします。[元に戻す履歴](undo-redo.md)の 1 件になり、**元に戻す**で動かしたすべての ref（とチェックアウト中のファイル）が元の位置に戻ります。
3. **push**（リース付きの強制 push）と**消去**は、元に戻せないため、意図して行う別の手順です。[結果を push する](#結果を-push-する)と[古い履歴を削除する](#古い履歴を削除する消去)を参照してください。

ワークベンチ、パレット、`gitpoulpi rewrite` コマンド、MCP ツールは同じエンジンを使うため、どれかで作ったプレビューを、別のものから適用できます。フラグの一覧は[コマンドラインから](#コマンドラインから)に、[AI でルールを作成する](#ai-でルールを作成する)は説明からワークベンチを埋め、エージェントにできること・できないことは [AI エージェントからの提案](#ai-エージェントからの提案)にあります。

**変更内容別のルール**

| グループ | ルール | 節 |
|---|---|---|
| 作成者 | 作成者を置き換え、作成者を匿名化、.mailmap を適用 | [作成者と .mailmap](#作成者と-mailmap) |
| 日付 | 日付をずらす、タイムゾーンを変更、時間帯内に収める、コミッターの日付を作成者に合わせる | [日付](#日付) |
| メッセージ | メッセージ内を検索して置換、メッセージの行を削除、トレーラーを追加/削除、メッセージのエンコーディングを修正 | [メッセージ](#メッセージ) |
| ファイルの内容とパス | ファイル内を検索して置換、履歴からファイルを削除、大きなファイルを削除、パスを移動/名前変更、改行コードを変換、実行ビットを削除、ファイルのエンコーディングを変換 | [ファイルとパス](#ファイルとパス) |
| LFS | ファイルを LFS に移行、LFS からファイルを戻す | [Git LFS への移行と復帰](#git-lfs-への移行と復帰) |
| 署名 | 署名を削除（適用時の再署名を含む） | [署名](#署名) |
| スクリプト | Lua、シェル、Python | [スクリプトルール](#スクリプトルール) |

**始める前に**

- プレビューは何も変更しません。適用が変更するのはローカルの ref だけで、push はしません。
- 書き換えられた commit には新しい ID が付きます。古い履歴を持っている全員に知らせる必要があります。[結果を push する](#結果を-push-する)がそのためのメモを作ります。
- push 済みのシークレットは漏えいしています。**先にローテーション**（無効化して再発行）してから、書き換え、強制 push、消去を行ってください。
- 変更されない commit は、ID も署名もそのままです。

## ワークベンチ

`Ctrl+G Shift+H`（またはパレットの **書き換え: 履歴ワークベンチ**）で、Log の上に書き換えワークベンチが開きます。ツールバーのボタンはありません。高度な操作は、パレット（`書き換え: ...` の各行は、そのルールを追加済みの状態でワークベンチを開きます）、commit メニューの **履歴を書き換え** サブメニュー（*この commit から HEAD まで...*、複数選択時は *選択した commits...*、*ワークベンチを開く...*）、そしてこのキーの組み合わせから使います。

`Ctrl+N` を押すとワークベンチの各コントロール（対象範囲、ルール、欄、タブ、ボタン）にバッジが表示されます。バッジを押すとそのコントロールをクリックしたのと同じ動作をし、`Esc` でバッジが消えます（[バッジ](keybindings.md#バッジ)を参照）。

![履歴書き換えワークベンチ：対象範囲バー、「作成者を置き換え」ルール 2 件の一覧と選択中のルールの項目、変更されるコミット数を示すプレビューの概要](../images/history-rewrite.png)

- **対象範囲バー：** どの ref を動かすか（現在のブランチ、すべてのローカルブランチ、選んだブランチと tag、選択した commit）、*Tags* のチェックボックス、そして *この commit から HEAD まで...* の後は、その commit の親より後から始めるためのチェックボックス。
- **ルール：** 番号付きの一覧で、上から順に適用されます。チェックボックスでルールのオン/オフを切り替え、矢印で移動し、×で削除します（*削除したルールを復元* か `Ctrl+Z` で戻せます）。*ルールを追加* には種類がグループ別に並びます。持っていないプログラムが必要なルールは、理由付きでグレー表示のままになります。
- **ルールの設定：** テキスト欄はクリックして編集します。複数の値がある欄はクリックすると一覧が開き、チェックボックスは切り替わります。
- **プレビュー**（`F5`）は、何も変更せずに新しい履歴を計算し、進行状況バーを表示します。タブは次のとおりです。**概要**（件数、各ルールが行ったこと、警告）、**Commits**（変更された commit を 1 行ずつ、デーモンからページ単位で表示。フィルターで変更あり、削除、push 済みを絞り込み）、**ブランチと tags**（動くもの、およびすでに push 済みの保護ブランチ。それぞれにチェックボックス付き）、**影響**（push 済みの履歴を書き換える意味：リース付きの強制 push、共同作業者、署名）、**シークレット**、**名義**、**サイズ**（いずれも下記）。
- **commit のファイル：** Commits の行で `Enter`（またはダブルクリック）すると、内容ルールで変更されたファイルの一覧と、その横に選択したファイルの diff が開きます。×、`Esc`、または外側のクリックで閉じます。シークレットルールが削除した行は非表示です。
- **適用**（`Ctrl+S` または `Ctrl+Enter`）は、プレビューがルールと一致している間だけ使えます。既定値のない質問は毎回尋ねられます。署名付き commit の署名をどうするか、フォルダーをどう取り出すか、です。結果パネルの **元に戻す** で、動かしたすべての ref が元の位置に戻ります。
- **保存 / 読み込み**は、レシピをリポジトリ（共有）または自分用に保存します。シークレット値は保存されません。

すべてのボタンにキーがあります。一覧は 設定 > キーボードとマウス（コンテキスト *書き換え*）と、ガイド `keybindings.md` にあります。

### 作成者と .mailmap

- **作成者を置き換え**は、名前やメールアドレス（文字列そのもの、または正規表現）で作成者またはコミッターを探し、新しい名前やメールアドレスに設定します。*適用先* で作成者、コミッター、両方を選びます。*tags の作成者も含める* をオンにすると、作り直される注釈付き tag も追従します。元のコミッターは、実行で *自分、今* を選ばない限り保たれます。
- **作成者を匿名化**は、すべての名義を番号付きの仮名に置き換えます（`Contributor 1`、`contributor-1@anonymous.invalid`。どちらのパターンも変更でき、番号は `{n}` で入れます）。1 回の実行では、同じ人には必ず同じ番号が付きます。*変更しない対象* に挙げた名義はそのままです。
- **名義タブ**（パレットの **書き換え: 名義を merge（.mailmap）...** でも開けます）は、複数の名前とメールアドレスで commit した人を、**何も書き換えずに**直すための場所です。対象範囲バーの範囲にあるすべての名前とメールアドレスを、作成者として書いた commit の数とコミッターとしての数とともに一覧にし、リポジトリの `.mailmap` がすでに対応付けているもの（`mapped to Name <email>` と同様の表示）も示します。同一人物の名義にチェックを入れ（`Space` またはクリック。*すべて選択* / *すべて解除*）、**名義を merge...**（`m`）を押すと、どれを残すかをダイアログで尋ね（commit の多いものが先頭）、**ほかの名義ごとに 1 行を `.mailmap` に追加します**（`Name <email> Old Name <old@email>`。すでにある行は繰り返さず、ファイルがなければ作成します）。commit はされないので、共有するには `.mailmap` を自分で commit してください。Log、blame、ファイル履歴には、正規の名前がすぐに表示されます（設定 `log.use_mailmap`、既定でオン）。保存済みの commit は変わらないため、強制 push は不要です。ステータスバーに書き込んだ内容が表示され、**元に戻す**（`u`）で以前の `.mailmap` に戻せます（ほかの操作と同じく、元に戻す履歴の 1 件です）。`r` で一覧を読み直します。
- **書き換えの代わりに `.mailmap`：** 作成者ルールがすでにリモートにある commit を変更する場合、概要に「書き換えなくても、.mailmap なら表示だけを直せます。代わりに .mailmap を使いますか？」と表示され、**.mailmap を使う** ボタン（概要で `m`）が出ます。押すと名義タブが開き、そのルールに一致する名義がチェック済みになります。ルールが設定しようとしていた名義は、まだどの commit にもなくても、残す候補として提示されます。
- **`.mailmap` ルール**（*書き換え: 履歴に .mailmap を適用...*、または `rewrite preview --mailmap`）は実際に書き換えます。作成者とコミッター（選択可）が、作業ツリーの `.mailmap` が指定する名前になり、結果は `git log --use-mailmap` の表示と同じです。公開する前など、履歴そのものに正規の名前を持たせたいときに使います。ほかのルールと同じ書き換えです（プレビュー、適用、強制 push）。
- **作成者のルールとトレーラー：** 作成者のルールは、トレーラーに書かれた人も変更できます。**トレーラーにも適用**（`--map-trailers`）をオンにしてください。値がちょうど `Name <email>` で、ルールの *メールアドレスが* / *名前が* に一致するトレーラーはすべて、作成者とコミッターへの処理にかかわらず、新しい名前とメールアドレスに設定されます。既定ではオフです。`Signed-off-by` は誰が署名したかの記録なので、変えるかどうかは別に判断する必要があるからです。

### 日付

4 つの日付ルールは、作成者の日付、コミッターの日付、または両方に作用します（ルールのペインの *日付*）。

- **日付をずらす**は、すべての日付を一定の量だけ動かします（`+2h`、`-1d`、`90m`、`1d 2h`）。各 commit が書かれたタイムゾーンは保たれます。
- **タイムゾーンを変更**は、日付を別の UTC オフセットで書き直します。*維持する対象* で何を保つかを選びます。**時点**（同じ瞬間で、時計の表示が変わる）か、**時計の表示**（同じ現地時刻で、時点が変わる）です。
- **時間帯内に収める**は、許可された時間帯（たとえば `Mon-Fri 18:00-23:30; Sat,Sun 10:00-20:00`）の外にある commit を、最も近い許可された時刻へ、または前だけ、後ろだけへ動かします（*移動方向*）。*親より前にしない* は履歴の順序を保ちます。*シード* は小さなランダムのばらつきを再現可能にします。同じ履歴に同じシードなら、同じ日付になります。
- **コミッターの日付を作成者に合わせる**は、コミッター（名前、メールアドレス、日付）を作成者のものに設定します。`git commit --amend` やリベースで元に戻ってしまったものを直します。

日付も、ほかのルールと同じです。プレビューし、**Commits** タブで確認し（各行に古い日付と新しい日付が表示されます）、適用します。commit の ID は日付に依存するため、日付ルールは、最初に変更される commit より後のすべての commit を変更します。

### メッセージ

- **メッセージ内を検索して置換**と**メッセージの行を削除**は、文字列そのもの、または正規表現（*正規表現*、*大文字小文字を区別*）を受け付けます。置換後が空なら削除になります。有効な UTF-8 でないメッセージには、これらのルールは何もしません。編集したい場合は、先に**メッセージのエンコーディングを修正**を実行してください。
- **トレーラー：** *トレーラーを追加/削除*（パレットの *書き換え: トレーラーを追加/削除...*、または `--trailer-add`、`--trailer-remove`、`--trailer-map`）は、メッセージの末尾にある `Key: value` の行、つまり `git interpret-trailers` が認識するもの（`Signed-off-by`、`Co-authored-by`、`Reviewed-by` など）を編集します。**操作** のドロップダウンで、*追加*（**トレーラー** のキー、その **値**、**すでにある場合**：*追加（同じものがなければ）*、*既存のものを置き換え*、*その commit は変更しない*）、*削除*（そのキーのトレーラーすべて、または **値に含まれる文字列** を値に持つものだけ）、*値を変更*（**値の検索** が **置換後** になります。たとえば `Signed-off-by` の古いメールアドレスを新しいものに）を選びます。キーは大文字小文字を区別せずに照合します。変わるのはトレーラーの行だけで、メッセージのそれ以外の部分はそのままです。トレーラーのまだないメッセージには、空行と、独立したブロックが追加されます。Commits タブには、各変更が `+Signed-off-by: ...` / `-Co-authored-by: ...` として表示されます。メッセージの最後の段落がトレーラーのブロックです（タイトルは含みません）。そのため、本文にある `Note: see the ticket` のような行は、最後の段落にほかのトレーラーと並んでいない限り、トレーラーではありません。
- **メッセージ内の commit ID：** **commit ID を更新**（`--update-message-hashes`。既定でオフ。メッセージを編集するルールのペインの末尾にあります）をオンにすると、メッセージに書かれた ID も書き換えに追従します。書き換え後の履歴でちょうど 1 つの commit を指す、16 進で 7 文字以上の短縮 ID（`This reverts commit 1a2b3c4`、`see 1a2b3c4d5e`）は、その commit の新しい ID に、同じ長さに切り詰めて置き換えられます。複数の commit に一致するもの、どれにも一致しないもの、書き換えの後で作られる commit を指すものは、そのままです。概要には、置き換えた数とそのままにした数が表示されます。
- **メッセージのエンコーディングを修正**（*書き換え: メッセージのエンコーディングを修正...*、または `--fix-message-encoding [--fix-name-encoding]`）は、メッセージを UTF-8 に変換し直します。対象は 2 つの場合です。
  - `encoding` ヘッダーのある commit（`ISO-8859-1`、`Windows-1252`、`Shift_JIS` など、git とエンコーディング表が知っているもの）は、デコードして UTF-8 で書き直し、ヘッダーは削除します。テキストはどこでも同じように読め、変換は不要になります。その commit の作成者とコミッターの名前も同じエンコーディングだったため、一緒にデコードされ、半端に変換された commit が残ることはありません。
  - **文字化け**、つまり UTF-8 がかつて Latin-1 や Windows-1252 として読まれたもの（`Réécriture` が `RÃ©Ã©criture` になるなど）は、**往復変換が厳密に一致する場合にだけ**修復します。テキストをエンコードし直すと有効な UTF-8 のバイト列になり、結果を同じ方法で文字化けさせると元に戻る必要があります。本物の文字の隣に `Ã©` があるだけのメッセージや、古い文字セットにない文字を含むメッセージは条件を満たさず、そのままです。

  *名前も修正*（`--fix-name-encoding`）は、文字化けした作成者名とコミッター名も同じ方法で修復します。判定できないもの（未知のエンコーディング名、宣言されたエンコーディングでは無効なバイト列、何も宣言していない UTF-8 でないメッセージ、文字化けに見えるが証明できないテキスト）は、**そのままにして件数を表示します**。概要には *n 件のメッセージは、エンコーディングを判定できないためそのままです* と表示され、`counts.encoding_left` に数が入ります。Commits タブには、各修正が古いメッセージと新しいメッセージ、そして *エンコーディング* の行（`ISO-8859-1` が `UTF-8` になる）として表示されます。

### ファイルとパス

- **ファイルの内容のルール**（*ファイル内を検索して置換*、*履歴からファイルを削除*、*大きなファイルを削除*）：入力するたびに値が検証され、理由が欄の下に表示されます（コンパイルできないパターン、不正なパスのパターン、1 バイト未満のサイズなど）。サイズには単位が使えます（`500 KiB`、`5 MiB`、`1 GiB`）。スラッシュのないパスのパターンは、どの階層にも一致します。*シークレット値* はマスクされた欄に入力し、その実行にのみ使われ、保存されません。プレビューでは、それを含んでいた行が非表示になります。*空の commits* は、ルールの結果が空になった commit を削除する（既定）か残すかを決めます。バイナリファイルとサイズ上限を超えるファイルはそのままにされ、概要に数が表示されます。
- **パスの移動：** *パスを移動/名前変更*（パレットの *書き換え: パスを移動/名前変更...*）には 3 種類あり、**操作** のドロップダウンで選びます。
  - *パスの名前を変更*（**移動元**、**移動先**。`--move-path FROM=TO`）：古いパスを持っていたすべての commit で、同じファイルとフォルダーが新しいパスに現れます。ほかは変わらず、すべてのファイルが ID を保ちます。新しいパスがすでに存在する commit は上書きされません。プレビューは拒否され、衝突する commit とパスが一覧されます（空いている名前を選ぶか、既存のものを先に移動してください）。指定できるのは正確なパスだけで、ワイルドカードは使えません。
  - *すべてをフォルダーに移す*（**フォルダー**。`--into-subdir DIR`）：すべての commit のすべてのパスに、接頭辞が付きます。名前の衝突なしにリポジトリを統合するのに便利です。
  - *フォルダーをルートとして取り出す*（**フォルダー**。`--extract DIR`）：そのフォルダーがルートになります。それに触れない commit は削除され（フォルダーを作った commit は親を持たなくなります）、何も結合しなくなったマージは単純化され、そのフォルダーのファイルがまったくないブランチと tag は削除されます。どう終えるかは**毎回**尋ねられます。
    - *新しいクローンへ（新しいタブで開く）*（`--extract-mode clone`）：選んだフォルダーにこのリポジトリのコピーを作り（新しいリポジトリは、その中に、取り出したフォルダーの名前のフォルダーとして作られます）、そこで書き換えて、新しい履歴だけが残るように整理します。そのフォルダーを持つすべてのローカルブランチと tag が含まれます。このリポジトリには触れません。新しいリポジトリにリモートはありません（元のリポジトリはアップストリームではありません）。
    - *その場で：このリポジトリの履歴を書き換える*（`--extract-mode in-place`）：通常の書き換えで、プレビュー、適用、元に戻すが使えます。そのフォルダーを持たないブランチは削除されます（元に戻すと戻ります）。チェックアウト中のブランチには、そのフォルダーがある必要があります。
    - *このリポジトリのサブモジュールとして*（`--extract-mode submodule`）：新しいリポジトリをクローンの場合と同じように作り、続いて現在のブランチに **新しい commit を 1 件** 追加して、フォルダーをそのサブモジュールに置き換えます（`.gitmodules` とリンク）。フォルダーは、チェックアウトされたサブモジュールとして残ります。このリポジトリの履歴は書き換え**ません**。古い commit にはフォルダーのファイルが残るため、それを指すもの（tag、ほかのクローン）は壊れません。`.gitmodules` の URL は新しいリポジトリのローカルパスです。ホストに置いたら変更してください（`git config -f .gitmodules submodule.<folder>.url`）。フォルダー内に編集済みまたは未追跡のファイルがあると拒否されます。元に戻すと、通常のフォルダーに戻ります。

    概要には、プレビューが新しいリポジトリの履歴を表していること、そしてその作成先のフォルダーが表示されます。取り出しの後に来るルール（名前変更や削除）は、取り出されたツリーに適用されます。クローンやサブモジュールの場合、取り出しは最初のパスルールでなければなりません。パスルールは内容ルールの後に実行されるため、削除のグロブは、変更前のパスで指定します。

#### 改行コード、実行ビット、ファイルのエンコーディング

追加メニューの**内容**グループにある 3 つのルールです（パレットの *書き換え: 改行コードを変換...*、*書き換え: 実行ビットを削除...*、*書き換え: ファイルのエンコーディングを変換...* でも開けます）。どれも **ファイル**（グロブ。スラッシュのないパターンはどの階層にも一致し、空ならすべてのファイル）と **除外するファイル** を受け付けます。変わるのは、グロブで指定したものだけで、対象範囲のすべての commit が対象です。バイナリファイル（先頭 8 KiB に NUL バイトがあるもの）は変更されません。概要には *そのままにした* ものとして数えられます。

- **改行コードを変換**（`--eol lf|crlf|cr --eol-paths GLOB... [--eol-exclude GLOB...]`）。*変換後*：LF（Linux、macOS）、CRLF（Windows）、CR（旧 Mac）。一致するテキストファイルのすべての改行が選んだものに揃うため、改行が混在していたファイルも統一されます。すでに正しいファイルは、そのまま変わりません。*.gitattributes に従う*（既定でオフ、`--eol-follow-attributes`）をオンにすると、各 commit のルートの `.gitattributes` を読み、`-text` や `binary` のファイルはスキップし、`eol=lf` や `eol=crlf` のファイルは、選んだものではなく、その改行を保ちます。
- **実行ビットを削除**（`--strip-exec GLOB... [--strip-exec-exclude GLOB...]`）。一致するファイルは、モード 100755 から 100644 になります。内容は変更しません。ファイルのパターンが 1 つ以上必要です。すべての実行ファイルから外すと、スクリプトが動かなくなるためです。
- **ファイルのエンコーディングを変換**（`--reencode TARGET [--from SOURCE] [--encoding-fallback ENC] --encoding-paths GLOB... [--encoding-exclude GLOB...]`）。*変換後*：UTF-8（既定）、BOM 付き UTF-8、UTF-16 LE または BE（バイトオーダーマーク付きで書き込み）、Windows-1252、ISO-8859-1。*ファイルのエンコーディング*：既定ではファイルごとに自動検出します（バイトオーダーマーク、次に有効な UTF-8、それ以外は *UTF-8 でない場合の指定*。変更しなければ Windows-1252）。エンコーディングを指定すると強制できますが、誤った指定は誤ったテキストになります（UTF-8 を Latin-1 として読むと、すべてのアクセント付き文字が二重になります）。変換元のエンコーディングで読めないファイル、または変換先で保存できない文字（ISO-8859-1 でのユーロ記号など）を含むファイルは、そのまま残され、概要に数が表示されます。

ルールは一覧の順に、同じファイルに対して実行されます。ファイルを UTF-16 に変換してから改行コードを指定しても、何も起きません（そのファイルはもうプレーンテキストではないためです）。適用は、ほかの書き換えと同じく、元に戻す一覧の 1 件になります。

### シークレットを探す

- **シークレットを探す：** `gitpoulpi rewrite scan-secrets`（および MCP ツール `rewrite_scan_secrets`）は履歴を一度読み取り、トークンの接頭辞（GitHub、GitLab、Slack、AWS、Stripe、npm、Google、OpenAI、Anthropic）、秘密鍵、JWT、URL 内のパスワード、ランダムに見える `password = value` の行を、ファイル、最初と最後の commit、`ghp_****abcd` のようなマスクしたプレビューとともに一覧にします。網羅的ではなく、値そのものは表示も記録も保存もされません。`--remove-finding ID` を付けると、その検出結果をすべての commit から削除するルールになります。push 済みのシークレットは漏えいしています。先にローテーション（無効化して再発行）し、そのあとで書き換え、強制 push、消去を行ってください。
- **シークレットタブ**は、同じことをワークベンチで、対象範囲バーの範囲に対して行います。**シークレットをスキャン**（`s`）はスキャンをジョブとして実行します（進行状況バーには *スキャン中* と表示され、**キャンセル**または `Esc` で止まります）。検出結果は 1 行ずつ、種類、マスクしたプレビュー、ファイル、同じものを含むほかのファイルの数で表示されます。一覧の下には、最初と最後に見つかった commit と、含まれる commit とファイルバージョンの数が出ます。読み取らなかったバイナリファイルとサイズ超過のファイルの数、およびスキャンが網羅的でないことも表示されます。検出結果は最初はすべてチェック済みです。**履歴から削除**（`r`）は、チェックした項目を、値ではなく ID で指定する 1 つのルールにします。ほかのルールと同じようにプレビューして適用します。書き換えや対象範囲の変更のあとで検出結果は古くなります。その場合はタブに表示されるので、もう一度スキャンしてください。ワークベンチはシークレットの値を保持しないため、表示することもできません。

### 容量を使っているものを探す

- **容量を使っているものを探す：** `gitpoulpi rewrite analyze [--top N]`（および MCP ツール `rewrite_analyze`）は `filter-repo --analyze` のようなサイズ分析です。最大のファイル（パス、サイズ、最初と最後の commit、まだ HEAD にあるかどうか）、最大のフォルダー、HEAD からは削除済みでも履歴が保持しているファイル、そして合計を表示します。読み取るのはサイズとパスだけで、ファイルの内容は読まず、何も変更しません。
- **サイズタブ**は、同じことをワークベンチで行います（`F7`、またはパレットの *履歴のサイズを分析* で、開いて実行します）。**サイズを分析**（`s`）はジョブです（*分析中*、**キャンセル**または `Esc` で止まります）。**表示**（`v`）で一覧を選びます。*ファイル*（固有のファイルバージョンを大きい順に。*HEAD 内*、まだ残っているファイルの *古い版*、*削除済み* の印が付きます）、*フォルダー*（それぞれの下に過去に保存されたすべて）、*削除済み*（HEAD からは消えたが履歴が保持しているパス）です。**並べ替え**（`o`）は、サイズ順、パス順、削除済みを先頭に、から選びます。行にチェックを入れる（`Space`。すべて / なしは `Alt+A` / `Alt+U`）と、それらが占める容量がタブに「最大約」として表示されます。容量が戻るのは、書き換え、古いオブジェクトの消去、`gc` を行った後だからです。**履歴から削除**（`r`）は、チェックしたパスをパスルールにします（特殊文字はエスケープされ、すでにルールにあるパスは重複して追加されません）。**... を超えるファイルをすべて削除**（`b`、ファイル一覧）は、チェックしたファイルのうち最小のものよりわずかに小さい値でサイズルールを作ります。どちらもほかのルールと同じようにプレビューして適用します。一覧に表示するのは大きい順に 200 行で、CLI は残りの数を示し、`--top` で表示できます。書き換えや対象範囲の変更のあとで行は古くなります。その場合はもう一度分析してください。

### 署名

- **署名：** 書き換えられた commit は署名を保てません（署名は古いバイト列に対するものだからです）。そのため、署名付きの commit を書き換えるときは、毎回次の選択を尋ねられます。*署名を外す*（先に件数が表示されます）、*署名済みだった commit だけ再署名*、*書き換えたすべての commit を再署名*。既定はありません。変更されない commit は署名を保ちます。再署名には、署名付き commit を作るときと同じ、あなた自身の設定が使われます。`gpg.format`（`openpgp`、`ssh`、`x509`）、`user.signingkey`、`gpg.program` / `gpg.ssh.program` / `gpg.x509.program` です。質問の 4 行目の **署名を確認**（`4`）は、ダミーのデータに 1 回署名して検証します。1 件の署名にかかる時間と、質問の対象になっている commit の数に応じた実行時間の見積もり、または動作しない理由（鍵がない、エージェントがロックされている、プログラムが未インストール。インストール方法つき）が分かります。プレビューも、履歴を読む前に同じ確認を行い、動作しなければその理由で拒否するため、設定が壊れたまま、署名が中途半端な書き換えが残ることはありません。commit の署名は**プレビュー中に**行われる（commit の ID に署名が含まれるため）ので、再署名するプレビューは署名の時間がかかり、概要には *再署名した commits：n 件、所要時間 12.5 s* と表示されます。そのときにパスフレーズの入力画面が開くことがあるため、先にエージェントのロックを解除してください（署名を確認がまさにそれを行います）。**キャンセル**は 2 件の署名の間で止まり、何も残しません。再作成されるのは commit の署名だけで、署名付き tag は署名を失ったままです。
- **署名を削除ルール**（追加メニューの *署名* グループ、パレットの *書き換え: 署名を削除...*、`--remove-signatures`）は、ほかに変更がなくても、対象範囲のすべての commit の署名を外し、再署名については何も尋ねません。CLI からは `rewrite check-signing` と `--signatures strip|resign-signed|resign-all` です。

### 書き換えを元に戻す

**元に戻す**（結果パネルのボタン、Log でツールバーの *元に戻す* または `Ctrl+Z`、`gitpoulpi undo`）は、書き換えが保持している古い commit から、動かしたすべてのブランチ、tag、note を、チェックアウト中のファイルとともに元に戻します。書き換えたブランチがすでにアップストリームにある場合（ローカルで元に戻しても push は取り消されません）や、未 commit の変更がある場合は、先に確認します。未 commit の変更は保たれ、古い履歴が上書きしてしまう、変更したファイルがあるときは、元に戻す操作自体が止まります（ファイルは `reset --keep` と同じように動きます）。その書き換えの古い履歴を[消去](#古い履歴を削除する消去)すると、元に戻すことはできなくなり、履歴の一覧には *消去済み* と表示されます。

## Git LFS への移行と復帰

追加メニューの *LFS* グループにある 2 つのルールは、大きなファイルを最初から [Git LFS](lfs.md) に置くように（または LFS から出すように）履歴を書き換えます。`git-lfs` プログラムが必要です。ない場合、ルールはインストール方法つきでグレー表示になり、プレビューは拒否されます。これは `git lfs migrate` ではなく GitPoulpi 独自のエンジンなので、ほかのルールと同じプレビュー、対象範囲、元に戻す、push の保護が使えます。

- **ファイルを LFS に移行**（*書き換え: ファイルを LFS に移行...*、または `--lfs-import PATTERN` と `--lfs-min-size BYTES`）。パターン（`*.psd`、`assets/**`。スラッシュのないパターンはどの階層にも一致）に一致し、*次以上のファイルのみ* のサイズ以上（空なら一致するすべて）のファイルは、それを含むすべての commit で LFS ポインターになります。内容は、適用するときにローカルの LFS ストア（`.git/lfs/objects`。内容ごとに 1 回）に入ります。ポインターを含む、書き換えられた各 commit のルートの `.gitattributes` には、`<pattern> filter=lfs diff=lfs merge=lfs -text` が追加されます（なければ作成し、ほかの行には触れず、重複もしません）。すでにポインターであるファイルは変更しません。概要には *3 件のファイル（12 MiB）が LFS に移ります。書き込む LFS オブジェクト：3。* と表示され、Commits タブには commit ごとに *big.psd を LFS に移動* と表示されます。
- **LFS からファイルを戻す**（*書き換え: LFS からファイルを戻す...*、または `--lfs-export PATTERN`）。一致するポインターは実際のファイルに戻り、それらのパターンの `.gitattributes` の行は削除されます。オブジェクトはローカルの LFS ストアにある必要があります。足りないものがあるとプレビューは拒否され、一覧と、`origin` から取得する **LFS オブジェクトをダウンロード** ボタンが表示されます。そのあと、もう一度プレビューしてください。同じパターンで移行してから戻すと、まったく同じ commit に戻ります。

適用の後、チェックアウト中のファイルは（ポインターではなく）実際の内容になり、**元に戻す**で古い履歴に戻ります。結果パネルには **LFS オブジェクトを送信**（`l`）があり、`LFS: すべてのオブジェクトを push` と同じ働きをします。これにより、新しい履歴を push したときに、あとの push がオブジェクト不足で止まることがありません（書き換えたブランチを普通に push しても、適用時にインストールされる pre-push フックを通してオブジェクトもアップロードされます）。共同作業者向けのメモには、git-lfs と `git lfs pull` が必要だと書かれます。

知っておくとよいこと：適用は、リポジトリの LFS フィルターがなければ（`git lfs install --local`）インストールします。実際のファイルとポインターを比べるのに git が必要とするためです。書き込まれるのはルートの `.gitattributes` だけで、ネストしたものには書き込みません。パターンに一致しても、最小サイズ*未満*のファイルは通常のファイルのままですが、git は次の add でポインターにしようとするため、commit するまで `git status` には変更ありと表示されます。移行は大きなファイルをストリーム処理し、戻す処理は一度に 1 つのファイルだけをメモリに保持します。

## 結果を push する

書き換えを適用しても、push は行われません。リモートにあった書き換え済みのブランチと tag には強制 push が必要ですが、見境なく強制することはありません。各 ref は、プレビュー時にリモートが持っていた ID（現在の追跡ブランチが指す ID ではありません）に対するリース付きで送られるため、その間に同僚が push していた場合は、上書きされずにその ref が拒否されます。サーバーが対応していれば、ref は全部成功か全部失敗かの 1 回の push（`--atomic`）で送られます。CLI からは次のとおりです。

```
gitpoulpi rewrite push --dry-run        # リモートに問い合わせるだけで、何も送らない
gitpoulpi rewrite push --yes            # 送信する
gitpoulpi rewrite note                  # ほかの人が実行すべきこと
gitpoulpi rewrite maps --out ./maps     # commit-map と ref-map
```

保護ブランチ（設定 `rewrite.protected_branches`。既定は `main`、`master`、`develop`、`release/*`）は、書き換えのときと push のときの両方で対象外になります。`--include-protected main` のように名前を指定するか、すべてを含めた場合は別です。強制 push を受け付けるかどうかは、ホスト側のブランチ保護が決め、拒否された場合は ref ごとに表示されます。

ワークベンチでは、適用後の結果パネルでこれらをすべて行えます。

- **書き換えた ref をリモートへ送信**には、書き換えで動いた ref のうちリモートにあるものが、チェックボックス（`Space`）付きで並びます。保護ブランチは最初はチェックなしで、横に *保護* と表示されます。1 つずつチェックするか、*すべて選択* / *すべて解除*（`Alt+A` / `Alt+U`）を使います。**書き換えたブランチを push**（`p`）はチェックしたものを送り、結果は ref ごとに 1 行です（*push 済み*、*すでに最新*、*拒否：プレビューの後でリモートが更新されました*、*拒否：ホストにより保護されています*、*スキップ：保護ブランチ*、*未 push*）。拒否された行には **fetch して確認**（`f`）があり、押すとワークベンチが閉じてリモートを fetch するので、ほかの人が push した内容が Log に表示されます。何も上書きされません。リースがその人たちの作業を守っています。やり直す前に、もう一度プレビューしてください。
- **メモをコピー**（`c`）は、共同作業者向けのメモをクリップボードにコピーします。git コマンドは翻訳せず、そのほかの部分はインターフェースの言語になります。
- **commit マップを開く**（`m`）は、commit マップと ref マップの場所を表示します。パスをクリックする（または `1` / `2`）とコピーされます。

push は元に戻せません。あとで書き換えを `undo` しても変わるのは手元のリポジトリだけで、undo はその旨を、実行する前に伝えます。古い履歴を持っている全員にメモを送ってください。メモには、各ブランチと tag の古い先端と新しい先端、そして実行するコマンド（`git fetch` のあと、`git reset --hard origin/<branch>` または `git rebase --onto`）が書かれています。2 つのマップは実行とともに 24 時間保持されます。GitLab のリポジトリクリーンアップやスクリプトで必要なら、コピーしておいてください。

## ホストがブランチを保護しているとき

ホストが独自にブランチを保護し（GitHub のブランチ保護とルールセット、GitLab の保護ブランチ、Azure DevOps のブランチポリシー、Bitbucket のブランチ制限）、書き換えに必要な強制 push を拒否することがあります。リポジトリがホストに**連携**されている場合（サイドバーのプルリクエストのセクション。[ホスト連携](hosting-integration.md)を参照）、ワークベンチはあなた自身のトークンを使って、ホストがどのブランチを保護しているかを問い合わせます。

- それらのブランチは、`rewrite.protected_branches` やワークフローの保護ブランチと同じく、**既定では書き換えの対象外**になります。Refs タブには、それぞれにチェックボックスと *すべて選択* / *すべて解除* ボタンが並び、*GitHub で保護されています* のように理由も表示されます。
- トークンが保護設定を読み取れない場合（スコープが足りない、管理者ではない）、ワークベンチは *ホストの保護設定は不明です* と表示し、ホストの言い分に基づいて保護されているものとは扱いません。そのために書き換えが妨げられることはありません。連携されていないリポジトリには問い合わせません。

保護されたブランチが障害になったとき（すべてのブランチが保護されているためプレビューが拒否された、またはホストが push を拒否した：*拒否：ホストにより保護されています*）は、**対処方法**ボタン（`Alt+H`）が、3 つの対処をお使いのプロバイダーとリポジトリの正確な設定ページとともに説明します（リンクを選んで `c` でコピー、`o` で開けます）。GitPoulpi がそれらを代わりに行うことはありません。

1. ホストの設定で、**保護を一時的に解除**し、push してから、元に戻す。
2. **書き換えを新しいブランチ名で push** し、そのブランチを既定のブランチにして（または名前を変更して）、誰も使わなくなったら古いブランチを削除する。
3. **最後の手段として、リモートリポジトリを削除して作り直し**、すべてを push する。これにより、プルリクエスト / マージリクエストとそのレビュー、Issue、フォークと古い履歴のつながり、スターとウォッチャー、CI の設定、シークレット、変数、Webhook とデプロイキーが失われます。

CLI では、同じ内容が `rewrite preview` / `rewrite run` の JSON（ホストが対象範囲のブランチを保護しているとき）、拒否された `rewrite push`、`rewrite note` の `protected_by_host` として返ります。`provider`、`branches`、`ways`（それぞれに `steps` と `links`）、`recreate_loses`、そして説明全体の `text` が含まれます。

## 古い履歴を削除する（消去）

書き換えのあとも、古い commit はリポジトリに残っています。書き換えの undo がそれを保持していますし（だから元に戻せるのです）、reflog も保持しています。シークレットを消すために書き換えたのなら、そのシークレットはまだ `.git` フォルダーの中にあります。消去は、古い履歴を完全に削除します。

```
gitpoulpi rewrite purge                 # 確認だけ：削除されるものと失われるものを表示（終了コード 3）
gitpoulpi rewrite purge --yes           # 実行する
```

書き換えの undo ピンを外し、古い commit を指す reflog の項目を期限切れにし、`git gc --prune=now` を実行して、古い commit とファイルバージョンがすべて本当に消えたことを確認します。確認の画面では、何を失うかが事前に示されます。その書き換え（および、undo に同じ古い commit を必要とする以前の操作）は**元に戻せなくなり**、履歴の一覧には消去済みとして残ります。消去は、始まると中断できず、元に戻すこともできません。リモートには触れません。

古い履歴をまだ保持しているものがあると、消去は実行できず、何も変更されません。一覧には、該当するものと対処が 1 つずつ示されます。書き換えの対象外だったブランチや tag、古い履歴上の stash（破棄するか、残して古い履歴が残ることを受け入れる）、HEAD が古い履歴上にある別の worktree、古い履歴をまだ指しているリモート追跡ブランチ（書き換えたブランチを push してから fetch する）です。stash の一覧と、ほかのブランチの reflog には触れません。

push 済みのシークレットは漏えいしています。**先にローテーションしてください。** 消去のあとの応答には、リモートごとにホスト側で必要な手順が示されます。GitHub はキャッシュされたビューやプルリクエストの ref 経由で古い commit に到達できる状態を保ちます（GitHub Support に連絡するか、リポジトリを削除して作り直します）。GitLab には `commit-map`（`gitpoulpi rewrite maps --out DIR`）を受け取るリポジトリクリーンアップとハウスキーピングがあります。Azure DevOps と Bitbucket はサポートへの依頼か新しいリポジトリが必要です。そして、クローンやフォークを持っている人には、古い履歴が残っています。

### 消去画面

ワークベンチでは、書き換えの結果パネルに **古い履歴を消去...** ボタン（キー `e`）があり、パレットには **書き換え: 古い履歴を消去...** があります（まだ消去されていない最新の書き換えが対象で、ワークベンチを閉じたあとでも使えます）。画面には、消去で削除されるものと失われるもの（undo が一緒に失われる操作。*元に戻す履歴も失われます* と付くものは、書き換えではありませんが古い commit を必要としていた操作です）が表示され、続いて、古い履歴をまだ保持しているものが 1 行ずつ並びます。

- リモート追跡ブランチ：**fetch** でリモートから更新します。
- stash：**破棄** は、stash が commit していない作業内容であるため、先に確認を求めます。
- ブランチ、tag、worktree、そのほかの ref：**名前をコピー** してから、それがある場所で対処します（ブランチを書き換えるか削除する、worktree で書き換えたブランチをチェックアウトする）。

確認は修正のたびに再実行され、**再確認**（`r`）で好きなときに実行することもできます。**消去**（`p`）は、何も残っていないときだけ使えます。最後に、番号付きで既定のない質問が出され（`1` は完全に消去、`2` はそのままにする）、そのあと実行されます。画面には現在のステップが表示され、中断できないことが示されます。結果には、古い履歴がこのクローンから消えたこと、または古いオブジェクトがまだ何個残っているかが示されます。その下に、各リモートで行う手順が表示されます（リンクはコピーできます）。×、`Esc`、外側のクリックで画面を閉じられます。消去の実行中は閉じられません。

MCP では、`config.toml` の `[mcp]` テーブルに `allow_history_purge = true` を設定しない限り、消去ツールは存在しません。

## スクリプトルール

*ルールを追加 > スクリプト*（またはパレットの **書き換え: スクリプトを実行...**）は、Lua スクリプトのルールを追加してそのエディターをワークベンチの上に開きます。ルールの *スクリプト* の行で `Enter` を押すと、もう一度開けます。エディターには小さなテンプレートが最初から入っています。

- **言語**（ルールのペインの 1 行）：*Lua（内蔵）*、*シェルスクリプト*、*Python*、*Lua（インストール済み）* から選びます。内蔵の Lua 以外は[外部スクリプト](#外部スクリプトシェルpythonlua)で、サンドボックスの外で動きます。設定でオフの言語や、インタープリターが見つからない言語は、一覧ではグレー表示で、理由が横に出ます（選ぶと、何をすればよいかが示されます）。まだ何も書いていないスクリプトの言語を変えると、テンプレートが入れ替わります。
- **スクリプト**は、行番号付きのテキストエディターです。入力した内容がそのままルールになり、確定操作は要りません。
- その下の**検査**の行には、`OK: rewrite_commit found` と表示されるか、問題が行番号付き（`script:3: ...`。余白の行番号が赤くなります）で並びます。入力をやめてからしばらくして実行され、キーを押している間は実行されません。
- **パラメーター**には、スクリプトのヘッダーの `--! param` 行ごとに 1 行あり、ラベルが欄の横に表示されます。テキスト、数値、真偽のチェックボックスのいずれかです。消した値はヘッダーの既定値に戻ります。既定値のないテキストパラメーターは、プレビューの前に入力が必要です。
- **ファイル**（リポジトリ内のパス。最初は `.gitpoulpi/rewrite/script.lua`）には、**ファイルから読み込み...**（テキストを置き換えます）と **ファイルに保存...** があります。
- **選択範囲でテスト**は、Log で選択した commit に対してスクリプトを実行します。何も選択していなければ最新の 20 件が対象で、何も書き込みません。表の各行は commit（短い ID）、変更されるすべてのフィールドを `old -> new` で並べたもの、そしてスクリプトの `log(...)` の出力です。**キャンセル**で待つのをやめます。スクリプトが失敗すると、その commit と理由が表示されます。
- ×、エディターの外側のクリック、`Esc` で閉じます。`Tab` と `Shift+Tab` でエディター、パラメーター、ファイル、ボタン、結果の間を移動し、`F5` でテストします。

コンパイルできないスクリプトは、プレビューが拒否します。プレビューのペインに *スクリプトが失敗しました* と、その行（commit での失敗なら、短い ID と理由）が表示されます。スクリプト機能を含まないビルドでは、この種類は追加メニューにグレー表示で残ります。

## AI でスクリプトを作成する

AI をオンにしていると（[AI アシスタント](ai.md)）、スクリプトエディターに `✦ AI で作成...` ボタンが表示され、パレットには `✦ 書き換え: AI でスクリプトを作成...` が追加されます。後者は、新しいスクリプトルールの上でワークベンチを開き、ダイアログも開きます。**送信**を押すまで、何も送られません。ダイアログには、入力に合わせて、実際に送られる文面がそのまま表示されます。

- **スクリプトにどんな処理をさせますか？** 自分の言葉で書きます。*夜間に作成されたすべての commit を翌朝に移す*、*古いメールアドレスを新しいものに置き換える（2024 年より前のみ）* など。
- **N 件の commit のサンプル（作成者、日付、件名）を送る**（オフ）：チェックすると、「選択範囲でテスト」が使うはずの commit（Log の選択、なければ最新の 20 件）の作成者、日付、件名が追加され、モデルがデータの様子を把握できます。ファイルの内容や commit の本文は送りません。チェックしていなければ、commit のデータはこのマシンの外に出ません。
- **送信される内容**には、モデルへの指示（固定のスクリプト仕様と、あなたの AI 指示）、あなたの指示、そして送信先のプロファイルが表示されます。`Tab` で移動でき、矢印キーでスクロールします。
- **送信**（`Tab` で移動して `Enter`）。モデルが処理している間、ダイアログは待機し、`Esc` でリクエストをキャンセルします。失敗した場合は、理由とともにダイアログが残るので、やり直せます。

返ってきた答えは、自分で入力したスクリプトと同じデーモンの検査にかけられ、コンパイルエラーがあれば一度だけモデルに返されます。そのあと、スクリプトは**エディターのテキストを置き換えます**（エディターにテンプレート以外の内容があるときは、ダイアログがそう伝えます）。テキストを変更するまで、エディターのタイトルには *✦ AI が作成：プレビューの前に内容を確認してください* と表示されます。テスト、プレビュー、適用が自動で行われることはありません。内容を読み、**選択範囲でテスト**を押してから、ほかのスクリプトと同じようにプレビューしてください。スクリプトは、自分で書いたものと同じサンドボックス（ファイルなし、時計なし、ネットワークなし）で動きます。

コマンドラインからは、`gitpoulpi ai rewrite-script "<instruction>" [--sample N]` がスクリプトと、それに対する `rewrite script check` の結果を JSON で出力し、何も実行しません（まだコンパイルできない場合の終了コードは 2）。設定 > AI の *履歴書き換えスクリプト* のプロファイルが使われます。

## AI でルールを作成する

AI をオンにしていると（[AI アシスタント](ai.md)）、ワークベンチの保存と読み込みの横に `✦ AI でルールを作成...` ボタンが表示され、キー `Alt+I`（設定 > キーボードとマウスの *AI で書き換えルールを作成*、コンテキスト *書き換え*）が使え、パレットには `✦ 書き換え: AI でルールを作成...` が追加されます。AI がオフのとき、または AI を含まないビルドでは、ボタンもパレットの行もありません。履歴をどう書き換えたいかを自分の言葉で説明すると（*古いメールアドレス a@b.org を c@d.org に置き換える*、*secrets.txt を全履歴から削除する*、*日付を 2 時間ずらす* など）、モデルがルールと設定を提案し、それが**ワークベンチに入ります**。**送信**を押すまで、何も送られません。ダイアログには、入力に合わせて、実際に送られる文面がそのまま表示されます。

- **履歴をどのように書き換えますか？** 複数行の欄です。`Enter` で改行、`Ctrl+Enter` または `Ctrl+S` で送信、`Esc` と × でキャンセルします。
- **対象範囲、ブランチと tag の名前、履歴の作成者を送信する**（オフ）：チェックすると、対象範囲バーの範囲、ブランチと tag の名前、そして Log に表示されている最新の commit（最大 20 件）の作成者（名前とメールアドレス、重複なし）が追加され、モデルがあなたのメールアドレスを正確に書けるようになります（コマンドラインの `ai rewrite-rules --context` は、代わりに最新 200 件の commit を読み取ります）。ファイルの内容や commit メッセージは送りません。チェックしていなければ、マシンの外に出るのはあなたの説明と固定の指示だけです。
- **現在のルールを置き換える**（ワークベンチにすでにルールがあるときだけ表示。オフ）：既定では、新しいルールは今あるルールの後ろに追加されます。チェックすると置き換えます（答えが指定した対象範囲と設定は、どちらの場合も適用されます）。
- **送信される内容**には、指示（ルールの語彙、続いてあなたの AI 指示）、あなたの依頼、そして送信先のプロファイルが表示されます。`Tab` で移動でき、矢印キーでスクロールします。

モデルは、このページのすべての種類のルールを使えます。ただし**スクリプト**（コードは *AI でスクリプトを作成する* で、確認用にスクリプトを表示します）と、*ファイル内を検索して置換* のシークレット値の形式（シークレット値がモデルに渡ることはありません。シークレットタブを使ってください）は除きます。対象範囲は、現在のブランチ、すべてのローカルブランチと tag、または存在する名前のブランチと tag に設定でき、オプションの *Tags*、*コミッター*、*空の commit*、*メッセージ内の短縮 ID* も設定できます。ワークベンチで表せないもの（*3 月以降* のような日付の制限、commit の範囲）は推測せず、モデルがその旨を注記します。署名をどうするかはモデルが決めることはなく、適用のときにあなたに確認されます。

**AI が準備するのはルールと設定だけです。** プレビュー、適用、実行は一切行いません。答えは読み込んだレシピと同じようにワークベンチにコピーされ、画面のプレビューは古くなります。プレビューと適用（とその質問や確認）は、いつもどおりあなたが行います。各ルールは、エディターとエンジンが使うのと同じ検査で個別に解析・確認され、通らないルールは除外されます。除外されたものがあるとき、またはモデルが注記したときは、ルールが入った後に一覧が表示されます（*除外されたもの（有効なルールは残してあります）*、それぞれに位置、名前、理由）。`Enter` または `Esc` で閉じます。ルールを読み、編集してから、プレビューしてください。

コマンドラインからは、`gitpoulpi ai rewrite-rules "<description>" [--context]` が提案を JSON（`rewrite preview --recipe-json` が読む `recipe`、`problems`、`notes`、`applied: false`）で出力し、何も実行しません（除外されたものがある場合の終了コードは 2）。MCP ツールは `ai_rewrite_rules` です。設定 > AI の *履歴書き換えルール* のプロファイルが使われます。

## Lua スクリプト

スクリプトルールは、すべての commit に対してあなたの関数を実行します。サンドボックス内の標準的な Lua 5.4 で、ファイル、時計、プロセス、モジュール、`pcall` はありません。同じ履歴に同じスクリプトを使えば結果は常に同じで、1,000 万命令、64 MiB、5 秒を超えた呼び出しは、その commit を示すエラーで停止します。

```lua
--! name: Replace an email
--! param old_email: text "Email to replace"
--! param new_email: text "New email"
function rewrite_commit(c, ctx)
  if c.author.email == ctx.params.old_email then
    return { author = { email = ctx.params.new_email } }
  end
end
```

`c` には `id`、`parents`、`tree`、`author` と `committer`（`name`、`email`、`time`、`offset_minutes`）、`message`、`signed` が入っています。`ctx` には `index`、`total`、`params`、`state`（`state = {...}` を返すと次の commit にデータを引き継げます）、`window.before` / `window.after`（`--! window: N` で設定）が入っています。返すのは変更したいものだけです（`author`、`committer`、`message`）。ヘルパーは `regex_replace`、`regex_match`、`stable_hash`、`rand`、`weekday`、`hour`、`log` と、メッセージ用の `trailers(message)`（`{key, value}` のリスト）、`set_trailer(message, key, value)`（そのキーのトレーラーを置き換えます。4 番目の引数に `"add"` または `"skip"` を渡すと動作が変わります）、`remove_trailer(message, key)`、そして `at("2024-03-05 18:30", offset_minutes)`（オフセット付きの日付を Unix 時間で返します）です。

コマンドラインからは、`gitpoulpi rewrite script check my.lua` でコンパイルを確認し、`gitpoulpi rewrite script test my.lua --commit HEAD --param old_email=a@b` で何も書き込まずに変更内容を確認し、`gitpoulpi rewrite preview --script my.lua --script-param old_email=a@b` で書き換え全体を計画できます。

## 外部スクリプト（シェル、Python、Lua）

Lua スクリプトと同じ仕様で、あなたのマシン上のプログラムが実行します。*シェルスクリプト*（bash または sh。Windows では PowerShell、または任意の `.ps1`）、*Python*、*Lua（インストール済み）*（内蔵ではなく、お使いの `lua`。JSON ライブラリがないため、テンプレートはパターンで行を読み取ります）が使えます。**サンドボックスはありません。外部スクリプトはあなたの権限で動作し**、あなたが読み書きできるものを何でも読み取り・変更できます。ルールのペインとエディターのタイトルにも、そう表示されます。

やり取りの方法：GitPoulpi は実行ごとにスクリプトを一度起動し、標準入力に 1 行に 1 つの JSON リクエストを送ります（commit のフィールド、`params`、直前の応答が返した `state`）。スクリプトは標準出力に 1 行の JSON で答えます。フィールドは Lua スクリプトが返すものと同じ（`author`、`committer`、`message`、`state`、`log`）で、あきらめるときは `{"error": "text"}` を返します。診断メッセージは標準エラー出力に書くと、その commit の `log` の行として表示されます。ヘッダー行は、シェルと Python では `#!` で始め（`#! name: ...`、`#! param old: text "Old"`。shebang 行は shebang のままです）、Lua では `--!` で始めます。

```sh
#!/bin/sh
#! name: Uppercase author names
while IFS= read -r line; do
  name=$(printf '%s' "$line" | sed -n 's/.*"author":{[^}]*"name":"\([^"]*\)".*/\1/p' | tr 'a-z' 'A-Z')
  printf '{"author":{"name":"%s"}}\n' "$name"
done
```

**スクリプトに渡されるもの：** `PATH`、`HOME` / `USERPROFILE`、`SYSTEMROOT`、`TEMP` / `TMP`、`LANG` 以外は空の環境、作業フォルダーとして新しい一時フォルダー（スクリプト自身のコピーが入っています）です。リポジトリのパスは渡されません。**時間制限：** 1 回の応答ごとに `rewrite.script_timeout_ms`（5000）、全体で `rewrite.script_total_timeout_s`（3600）です。超過したとき、クラッシュしたとき、JSON ではないものを出力したとき、ジョブがキャンセルされたときは、GitPoulpi がスクリプトと、それが起動したものをすべて終了させ、書き換えは commit と理由を示して停止します。何も動いていません。

**使える言語：** `config.toml` の `rewrite.external_scripts` に列挙します。既定は `["shell"]` で、`"python"` と `"lua"` は自分で `config.toml` に追加します（`[rewrite]`、`external_scripts = ["shell", "python"]`。リストは `gitpoulpi config set` では設定できません）。列挙されていない言語は、ワークベンチではグレー表示、CLI と MCP では拒否されます（`scripts_disabled`）。列挙されていてもインタープリターが見つからない言語は、インストールのヒント付きでグレー表示になります（`tool_missing`）。

**信頼：** 言語がオンでも、スクリプトが実行されるのは、その内容そのものを信頼したあとだけです。ワークベンチで自分で入力したスクリプトは自分のものなので、すぐに実行されます。共有レシピやリポジトリのファイルから来たスクリプトは別で、プレビューと *選択範囲でテスト* は止まって *このスクリプトを信頼しますか？* と尋ねます。答えは番号付きの 2 つで、どちらも選択済みにはなりません（`1` は信頼して続行、`2` は信頼しない、`Esc` はそのままにする）。信頼すると、このリポジトリについてテキストの SHA-256 が記憶されるため、変更されたスクリプトは再度確認を求め、クローンしたリポジトリが勝手にあなたのマシンでコードを実行することはありません。コマンドラインからは、ファイルを読んでから `gitpoulpi rewrite script trust FILE` を実行します（`preview`、`run`、`script check`、`script test` の `--trust` は、信頼して続行します）。MCP 経由のエージェントは何も信頼できず、実行できるのは、あなたがあらかじめ信頼したスクリプトだけです。

**検査：** エディターの下の検査行は、信頼されていないスクリプトには *まだ信頼されていません* と表示します（何も起動していません）。信頼済みのスクリプトは、GitPoulpi が架空の commit（`"dry_run": true`）で一度起動し、応答が仕様に沿っているかを確認します。`gitpoulpi rewrite script check FILE` も同じことを行い、`trust`、`hash`、`interpreter` を報告します。

## コマンドラインから

`gitpoulpi rewrite`（と、同名の MCP ツール）は、スクリプトやエージェント向けに同じエンジンを実行します。**レシピ**は、ワークベンチが保存するのと同じ TOML または JSON のファイルで（`--recipe FILE`、標準入力なら `-`）、フラグでレシピ自身のルールの後ろにルールを追加できます。

```
gitpoulpi rewrite preview --recipe fix.toml --all     # 計画を立てる。何も変更しない
gitpoulpi rewrite apply --run ID --digest D           # 確認した計画を実行する
gitpoulpi rewrite run --fix-message-encoding --signatures strip --yes
gitpoulpi undo                                        # すべて元に戻す
```

- フラグで指定するルール：`--set-name` / `--set-email` と `--match-email`（名義）、`--mailmap`、`--shift-dates`、`--replace-message FIND=WITH`、`--trailer-add`、`--trailer-remove`、`--trailer-map`、`--fix-message-encoding`（`--fix-name-encoding`）、`--remove-path`、`--remove-blobs-over`、`--replace-content`、`--eol`（`--eol-paths`）、`--strip-exec`、`--reencode`（`--encoding-paths`）、`--move-path`、`--into-subdir`、`--extract`、`--lfs-import`、`--lfs-export`、`--script`、`--remove-signatures`、`--remove-finding`。対象範囲は、現在のブランチ、`--all-local`、または `--ref R`（複数指定可）で、`--since REV` から始められます。
- **既定のない質問**はフラグになっています。署名付き commit が変わるときの `--signatures strip|resign-signed|resign-all`、フォルダーの取り出しでの `--extract-mode` です。指定しないと、答えは拒否か `needs_choice`（終了コード 3）になり、推測で進むことはありません。
- **終了コード：** 0 は完了、1 はエラー（読めないレシピ、不正なフラグ）、2 は理由つきの拒否（`stale`、`signature_choice_needed`、`dirty_paths_touched`、`empty_scope` など）、3 は答える必要のある質問、または `--yes` が必要な push 済みの ref です。
- `preview` は計画をリポジトリに保存するため、`apply` は後のコマンド、デーモンの再起動後、別のフロントエンドからでも実行できます。ダイジェストが一致しなくなった計画は `stale` になります。

すべてのフラグは [CLI リファレンス](cli-reference.md)に、エージェントが使えるツールは [MCP とエージェント](mcp-and-agents.md)にあります（消去ツールは有効にしない限り存在せず、エージェントはスクリプトを信頼できません）。

## AI エージェントからの提案

エージェントは書き換えを**提案**できますが、実行はできません。`gitpoulpi ui propose rewrite --recipe FILE|-`（MCP ツール `ui_propose_rewrite`。`[mcp]` の `allow_ui_propose = true` にするまでオフ）は、実行中のウィンドウでワークベンチを開き、レシピのルールを一覧に入れた状態で、紫のバナー *✦ <agent> からの提案：履歴の書き換え（3 件のルール）· Ctrl+Enter で承認 · Esc で却下* を表示します。

- **何も実行されません。** プレビュー、適用、push、消去のどれも行われず、提案はルールを入れるだけです。ルールを読み、必要なら編集し、**プレビュー**して、ご自身のキーで適用します。ワークベンチを閉じると、提案は却下されます。
- **エージェントが含められないもの：** スクリプト（プレビューで実行されてしまうため）、50 件を超えるルール、シークレット値（送信前にレシピから取り除かれます）。そのような提案は、理由つきで拒否されます。
- エージェントは `ui state` で結果を読めます（ルールを提案どおりに適用したら `accepted`、先に変更したら `accepted_edited`、閉じたら `rejected`）。同時に扱える提案は 1 件で、ほかのダイアログが開いている間は拒否されます。

## ツール

履歴の書き換えの大半は Git 以外を必要としません。作成者とコミッターの変更、`.mailmap` の適用、匿名化、日付のずらしや時間帯の指定、メッセージとトレーラーの書き換え、内容の置換、パスや大きなファイルの削除、パスの移動は、すべて GitPoulpi の中で完結します。

**Lua スクリプトは内蔵されています。** インタープリターが GitPoulpi に組み込まれているため、Lua スクリプトに追加のツールや設定は不要です。シェル、Python、インストール済みの Lua のスクリプトはそれぞれのインタープリターが必要で（下の表を参照）、[外部スクリプト](#外部スクリプトシェルpythonlua)で説明します。

一部の機能は外部プログラムを使います。GitPoulpi はそれを探します（プログラムは `PATH` から、Windows では `PATHEXT` と Git for Windows 自身の `usr/bin` も通して見つかり、2 秒以内に `--version` に応答する必要があります）。結果は 1 分間キャッシュされ、「再確認」で改めて調べます。プログラムが見つからないルールは、理由とインストール方法を添えてグレー表示のまま一覧に残り、プレビューは何かが実行される前に拒否されます。

| 機能 | ツール | 備考 |
|---|---|---|
| commit の再署名 | `gpg`（OpenPGP）、`ssh-keygen`（`gpg.format = ssh`）、`gpgsm`（`gpg.format = x509`） | SSH と X.509 の署名には `user.signingkey` も必要です。`gpg.program`、`gpg.ssh.program`、`gpg.x509.program` が尊重されます。 |
| LFS への移行 | `git-lfs` 3.0 以降 | LFS ペインと同じ確認です。 |
| Python スクリプト | `python` 3.8 以降（Windows では `py -3`） | 既定でオフです。`rewrite.external_scripts` に `"python"` を追加してください。 |
| Lua（インストール済み）スクリプト | `lua5.4`、`lua54`、`lua`、`luajit` | 既定でオフです。`rewrite.external_scripts` に `"lua"` を追加してください。 |
| シェルスクリプト | `bash`、`pwsh`（PowerShell）、`sh` | 既定でオン（`"shell"`）です。PowerShell スクリプト（`.ps1` ファイル、`pwsh` の shebang、または Windows 上のシェルスクリプト）には `pwsh` または `powershell` が、POSIX のスクリプトには `bash` または `sh` が必要です（Windows では Git for Windows が提供します）。 |

インストールのヒント（Windows を先に）：

- Windows：Git for Windows に `gpg`、`ssh-keygen`、`bash`、`sh`、Git LFS が同梱されています。そうでない場合は `winget install GnuPG.GnuPG`、設定 > オプション機能 > OpenSSH クライアント、`winget install GitHub.GitLFS`、`winget install Python.Python.3.12`、`winget install DEVCOM.Lua`、`winget install Microsoft.PowerShell`。
- Linux：ディストリビューションのパッケージ（`gnupg`、`openssh`、`git-lfs`、`python3`、`lua5.4`、`bash`、`powershell`）。
- macOS：`brew install gnupg git-lfs python lua powershell`。`ssh-keygen` と `sh` は標準で付属しています。
