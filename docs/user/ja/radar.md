# Radar

Radar はホームのすぐ右にある専用のタブで、**複数のリポジトリ**にまたがって、ユーザーを待っているものを 1 つにまとめた一覧です。
自分が書いた pull request（または merge request）、レビューを依頼されているもの、自分に割り当てられた Issue や自分が作成した Issue、
そして作業中の変更を残したままのリポジトリが並びます。ホームのウィンドウの上に Radar のビューを重ねたものなので、
下にあるものがクリックやキーを奪うことはありません。

コードホストのプロファイル（[ホスティングと Issue トラッカーの連携](hosting-integration.md)を参照。1 つのリポジトリの一覧は [pull request と Issue](pull-requests-and-issues.md) に、行の議論は[会話](conversations.md)として開きます）と、
それにリンクされたリポジトリ、またはアカウント全体の一覧をオンにしたプロファイル（下の「対象を超えて」を参照）が必要です。
リンクされていないリポジトリには問い合わせず、代わりに**連携...**の行が表示されます
（下の「伝えたいことがあるリポジトリ」を参照）。

![2 つのリポジトリにまたがる Radar：固定された 1 件のリクエスト、続いて自分のレビュー待ち、自分の pull request、自分に割り当て、Issue、作業中が並んでいる](../images/radar.png)

pull request / merge request の行の**レビュー...**（または `e`）は、そのリポジトリを開き、リクエストのアプリ内レビューを開きます（[pull request / merge request のレビュー](review.md)）。

## 開く

- **`Alt+R`**（再割り当て可能：`global.radar`）。どこからでも使えます。
- パレット：`Radar: 開く`。
- タブバーのホームのすぐ右にある **Radar** タブ。
- **`+`** メニューの **Radar** 行（タブを閉じている間）。

リポジトリのタブからは、Radar を開いた状態のホームウィンドウに移動します。`Esc` または**戻る**でリポジトリの一覧に戻り、
`⌂` でも同じです。

## タブを閉じる、または Radar をオフにする

タブはリポジトリのタブと同じように閉じられます。**x**、中クリック、表示中の `Ctrl+W`、またはパレットの `Radar: タブを閉じる` を使います。閉じられないのはホームだけです。閉じたタブは、そのセッションでは再起動後も閉じたままで、Radar をもう一度開く（`Alt+R`、`Radar: 開く`、または `+` メニュー）と、ホームのすぐ右に戻ります。閉じても設定は変わりません。

使わない場合は、**設定 > 一般 > Radar を有効化**（`general.radar_enabled`。[設定リファレンス](config-reference.md)を参照）でオフにします。オフにすると、タブ、そのパレットコマンド、`Alt+R` がなくなり、GitPoulpi はそのための取得を一切行いません。再起動なしで、すぐに反映されます。

## 対象とする範囲：対象

**対象**のコンボボックスで、どのリポジトリに問い合わせるかを選びます。

- **ワークスペース**（名前で選びます）。そのリポジトリが対象で、タブが開いていないものも含みます。
- **開いているタブ**：このセッションのタブとして開いているリポジトリ。
- **既定のクローン先フォルダー**と**既定の参照フォルダー**：[設定](config-reference.md)で指定したフォルダー（`repos.clone_root`、`repos.browse_root`）にあるすべてのリポジトリ。タブが開いているかどうかは問いません。

ここで最後に選んだ対象（`radar.toml` に保存）がまだ存在していればそれで開きます。最初に選ぶ前、またはそのワークスペースが削除された場合は、セッションで有効なワークスペース、なければ開いているタブで開きます。この選択はこのビューだけに有効で、ウィンドウの有効なワークスペースは変わりません。
2 つのリポジトリのフォルダー名が同じときは、見分けられるよう、チップに親フォルダーが付きます。

### 2 つのフォルダー対象

フォルダー対象は、**2 階層の深さ**までリポジトリを探します。フォルダー直下のフォルダーと、その中にあって自身はリポジトリではないフォルダー（`~/src/work/app`）です。隠しフォルダーはスキップされ、リポジトリの中には入らず、一覧に出るのは最大 200 件です。検索はバックグラウンドで行われ、描画するスレッドでは行われません。結果は更新するまで保持されます。更新ボタン、`r`、`F5`（ウィンドウの更新キー。割り当て変更可）、`Radar: 更新` はフォルダーをもう一度検索します（その後にクローンしたリポジトリも表示されます）。

ホスティングは、リポジトリごとに有効にする方式のままです。フォルダー内の、ホストに**連携されていない**リポジトリには問い合わせません。作業中の行だけが表示され、リポジトリの下に `未連携` の行と **連携...** が出ます（そのリポジトリのプルリクエストのセクションが開き、プロバイダーとプロジェクトを選べます）。ステータスバーにも件数が出ます（`3 件が未連携（作業中の変更のみ）`）。

指定されていないフォルダーは、一覧でグレー表示になります（`既定の参照フォルダー（設定で指定してください）`）。選ぶと、その設定の行（設定 > 全般）が開き、対象は変わりません。クローン先フォルダーは、OS ごとの既定値（クローンダイアログが開く最初のフォルダー）があり、そのフォルダーが存在する限り、指定済みとして扱われます。参照フォルダーには既定値がありません。対象の一覧は、開くたびに設定から読み直されるため、設定の変更はすぐに反映されます。

## 一覧

| グループ | 内容 |
|---|---|
| 固定 | 固定したものすべて。種類を問わず、固定した順 |
| 自分のレビュー待ち | ユーザーにレビューを依頼しているリクエスト（自分が書いたものを除く） |
| 自分のリクエスト | 自分が書いたリクエスト。ドラフトにはチップで `ドラフト` と表示されます |
| 自分に割り当て | 自分に割り当てられたリクエスト |
| 自分への言及 | ユーザーに言及していて、上のグループにまだ入っていない open なリクエストと Issue（自分に割り当てられておらず自分が作成してもいない Issue は、ユーザーに言及している場合のみここに出ます） |
| その他のリクエスト | 残りの open なリクエスト |
| 自分に割り当てられた Issue | 自分に割り当てられた open な Issue |
| 自分が作成した Issue | 自分が作成した open な Issue |
| 作業中 | 対象のリポジトリのうち、未 commit の変更または未 push の commit があるもの |
| 保留中 | しばらく非表示にした項目。開くまでは折りたたまれています |
| リポジトリ | 伝えたいことがあるリポジトリ（オフライン、トークンの更新が必要、未連携） |

「pull request」と「merge request」の表記は、通常の用語の設定とホストに従います。

各行には、項目の種類（`⇄` リクエスト、`●` Issue、`✎` 作業中）、リポジトリのチップ（ワークスペースの色）、番号、タイトル、作成者、経過時間、
余裕があればラベルが表示されます。作業中の行には、ブランチと、そこで待っているものが表示されます：`✎` 変更したファイル、`+` 新しいファイル、
`↑` push する commit、`↓` pull する commit。

件数は各見出しにあります。グループの中では、最近更新されたものが先頭に来ます。

フィルターの下のステータスバーには、ホストの応答に少し時間がかかるとスピナーが表示されます。キャッシュされた一覧（サイドバーと同じキャッシュ）はすぐに表示され、
応答が届くたびに置き換えられます。

### 列

リポジトリのチップ、`#`（番号とチェックの印）、作成者、経過は、**サイズを変えられる列**です。自動のままだと、リポジトリ列は画面上で最も長い名前の幅になり（最大 40 セル、かつウィンドウの 3 分の 1 まで）、通常のターミナルでは `owner/name` やアカウント一覧の `group/sub/project` が切れません。タイトルは残りを使います。収まらない名前は省略記号で終わり（`group/sub...`）、次のことができます。

- 切れたリポジトリ、タイトル、作成者、ラベル一覧に**ポインタを置く**と、ツールチップに全文が表示されます。行を選択すると、フィルターの下のステータスバーにも完全なプロジェクト名とタイトルが表示されるので、キーボードでも同じ内容を確認できます。
- **区切りをドラッグ**する（リポジトリ名の直後のセル、`#` の後、または作成者か経過の直前）と列のサイズを変えられ、**ダブルクリック**すると列を再び内容に合わせます。一覧には**ヘッダー行**（リポジトリ、`#`、タイトル、作成者、経過）があり、区切りは Log と同じく `ui.column_resize` に従います。`line`（既定）では、ヘッダー行の区切りに薄い `│` が置かれ、ポインターが区切りにある間（ヘッダー上でも一覧のどの行でも）、キーで列を選んでいる間、またはドラッグ中は、アクセント色の細い線が一覧の全高にわたって描かれ、線上のどこからでもドラッグしてサイズを変えられます。手を離すと、ポインターがまだ区切りの上にある場合を除いて線は消え（その場合はポインターと一緒に消えます）、マウスのドラッグで列が選ばれたままになることはありません。`header` では目印も線もなく、ヘッダー行で区切りの次のセルが光り、そこだけがドラッグの起点です。対応するターミナルでは、区切りの上でポインターがサイズ変更用の形になります。状態のチップは固定幅で、経過も同じです（サイズを変えるまでは表示される最も広い経過に合わせます。狭い列で切れた経過は、ツールチップに完全な日付が表示されます）。そのため、作成者はどの行でも同じセルから始まります。
- またはキーを使います。**`C`** で列を選び（もう一度押すか `Tab` で次の列）、**`]`** で 2 セル広げ、**`[`** で狭め、**`0`** ですべての列を自動に戻し、`Esc` で終了します。パレットにも同じ操作があります：`Radar: 列を選択`、`Radar: 列を広げる`、`Radar: 列を狭める`、`Radar: 列の幅をリセット`。

幅は `radar.toml`（`[columns]`、`repo`、`number`、`author`、`age`、セル単位）に保存され、再起動後も保たれます。Log の列と同じサイズ変更の操作です。

### チェックと競合

リクエストの行には、ホストが何かを伝えている場合、番号の後ろに 2 つの小さな印が付きます。

| 印 | 意味 |
|---|---|
| `✓` | head の commit のチェックに合格した |
| `✗` | チェックが失敗した |
| `●` | チェックが待機中または実行中 |
| `!`（その隣） | リクエストがターゲットブランチと競合している |

印にポインターを置くとツールチップが言葉で伝えます（「チェックに失敗」、「main と競合」）。行を選ぶと、フィルターの下のステータスバーも同じことを伝えるので、キーボードでも分かります。印のないリクエストは、ホストが何も伝えていないもの（CI が設定されていない、または問い合わせていない）です。

- **GitLab** は、パイプラインの状態と競合のフラグを merge request の一覧と一緒に送るため、すべての行に印が付きます。
- **GitHub** は送らないため、一覧にはどちらもありません。GitPoulpi はリクエストごとに問い合わせます（マージの状態はリクエスト自体、head の commit の統合ステータスとチェックランの合計 3 回の呼び出し）。対象は、リポジトリごとに最大 **15 件の open なリクエスト**で、自分のものが先です。そのうち 1 つの呼び出しを GitHub が拒否した場合（レート制限）、残りは次の更新まで印が付きません。応答はホストのキャッシュと一緒に保存されます。

- **Gitea と Forgejo** は GitHub と同じように読み取られます：一覧には競合のフラグ（`mergeable`）が含まれ、commit のステータスはリクエストごとに問い合わせ（リポジトリごとに最大 15 件、自分のものが先）、Issue のグループも同じです。メンションにはサーバーの検索（`mentioned_by`）を使います。

### メンション

**自分への言及**と**表示：自分への言及**のフィルターは、ホストがメンションについて知っていることを使います。GitHub では検索（`mentions:`）、GitLab では ToDo リストを通して問い合わせます。そこで**保留中**のメンションだけが数えられるため、完了にした ToDo はグループから外れます。

クローズされた、または merge 済みのリクエストと、クローズされた Issue は一覧に出ません。

## ビューと絞り込み

3 つのコンボボックスとテキストフィールドで、一覧を絞り込みます。どの選択もドロップダウンで、クリックするかキーで操作します。

- **表示**（`v`）：すべて、リクエスト、Issue、WIP（作業中）、保留中。
- **絞り込み**（`f`）：全員、自分が作成（自分が書いたリクエスト、自分が作成した Issue）、自分に割り当て、レビュー依頼、自分への言及。
- **対象**（`w`）：上を参照してください。
- **絞り込みのテキスト**（`/` または `Ctrl+F`）：リポジトリ、番号、タイトル、作成者、ブランチ、ラベルであいまい一致します。
  `Enter` でキーを一覧に戻し（テキストは残ります）、`Esc` でクリアします。

`Ctrl+N` を押すと、フィルター、各コンボボックス、更新と戻るのボタン、画面上の各セクション見出しにバッジが表示されます。バッジの文字を押すと、フィルターにキーボードが移り、コンボボックスが開き、ボタンが実行され、見出しが選択されます（続けて `Enter` または `Space` で折りたたみます）。`Esc` でキャンセルします。[バッジ](keybindings.md#バッジ)を参照してください。

## 操作

行を選び、そのメニュー（右クリック、行末の `⋮`、`.`、`Menu`）、キー、またはパレット（`Radar: ...`）を使います。
マウスでできる操作には、必ずキーとパレットの対応があります。

| 操作 | キー | パレット |
|---|---|---|
| リポジトリを開く（そのタブが開く、または切り替わる） | `Enter` / ダブルクリック | `Radar: リポジトリを開く` |
| レビュー...（リクエスト。クローンしていないリクエストでは方法を尋ねる） | `e` | `Radar: リクエストをレビュー...` |
| ホストの API 経由でリクエストをレビュー（クローンなし） | 質問の中で `a` | `Radar: API 経由でレビュー` |
| リポジトリをクローンしてからリクエストをレビュー | 質問の中で `c` | `Radar: クローンしてレビュー...` |
| ブラウザーで開く | `o` | `Radar: ブラウザーで開く` |
| ブランチをチェックアウト（リクエスト） | `c` | `Radar: ブランチをチェックアウト` |
| worktree を作成...（リクエスト） | `t` | `Radar: worktree を作成...` |
| リポジトリで表示（その一覧で） | `s` | `Radar: リポジトリで表示` |
| この Issue の作業を開始...（Issue） | `n` | `Radar: Issue の作業を開始...` |
| 先頭に固定、または固定を解除 | `p` / `★` をクリック | `Radar: 固定／固定解除` |
| 担当者を編集... / レビュアーを編集... / ラベルを編集...、マイルストーンを設定...（GitHub、GitLab） | 行メニュー | `Radar: 担当者を編集...`、`Radar: レビュアーを編集...`、`Radar: ラベルを編集...`、`Radar: マイルストーンを設定...` |
| 保留... | `z` | `Radar: 保留...` |
| 保留を解除 | `u` | |
| クローンしていないリポジトリのリクエストを表示または非表示 | `a` | `Radar: 未クローンのリクエストを表示` |
| アカウント全体の行のドラフトを表示または非表示 | `d` | `Radar: ドラフトを表示` |
| ホストのアカウント全体のレビュー依頼を有効にする | `T` / そのヒント行で `Enter` / **有効にする** | `Radar: アカウント全体のレビュー依頼を有効にする...` |
| 更新 | `r`、`F5` | `Radar: 更新` |
| 行メニュー | `.` | `Radar: 行メニュー...` |
| ホームに戻る | `Esc` | `Radar: ホームに戻る` |

リポジトリ自身のウィンドウが必要な操作（チェックアウト、worktree、表示、作業の開始、連携、メタデータのピッカー）は、先にそのタブに切り替え、
読み込みが終わってからそこで実行されます。

- **チェックアウト**は、サイドバー自身のチェックアウトを使います。ブランチがローカルで分かっていればそのブランチを、
  そうでなければ（たとえばフォークの場合）リクエストの head を fetch してローカルブランチにします。
- **worktree を作成...**は、リクエストのブランチで「worktree を作成」ダイアログを開きます。
- **リポジトリで表示**は、PULL REQUESTS または ISSUES の一覧でその項目を選択します。
- **Issue の作業を開始**は、Issue から作った名前（`12-fix-the-thing`）で、新しいブランチのプロンプトを開きます。

### 固定と保留

**固定**は、項目を先頭に置いたままにします。**保留**は、**1 時間**、**4 時間**、**明日まで**（翌朝 8:00、ローカル時刻。今がまだ 8:00 前でも翌朝です）、
または**変更があるまで**（ホストがその項目の更新を報告するまで。作業中の行では、そのカウンターが動くまで）非表示にします。
どちらも、設定フォルダーの `radar.toml` に、ホスト、リポジトリ、種類、番号をキーとして保存され、このマシンのすべてのセッションで共有されます。

### 伝えたいことがあるリポジトリ

問題のあるリポジトリは、一覧の最後に独自の行が付き、キャッシュされた項目は画面に残ります。

- **オフライン（データの古さ：5分）**：ホストに接続できませんでした。
- **再接続**：トークンがないか、拒否されました。このボタンで設定 > 連携が開きます。
- **今回は一時停止中**：ホストから速度を落とすよう求められた（またはトークンを拒否された）ため、GitPoulpi はこのラウンドの
  ほかのリポジトリには再度問い合わせませんでした。
- **未連携、GitHub を提案**：リポジトリのリモートがプロファイルに一致していますが、ホスティングはリポジトリごとのオプトインなので、
  リンクするまで何も問い合わせられません。**連携...**で、そのリポジトリの PULL REQUESTS セクションに移動し、プロバイダーとプロジェクトを選びます。

同時に問い合わせるリポジトリは最大 4 つで、画面を描画するスレッドでは決して行いません。

## 対象を超えて：アカウント全体の行

対象がカバーするのは、クローンしたリポジトリです。一度もクローンしていないリポジトリであなたのレビューを待っている
リクエストは、そこには表示されません。**アカウント全体の行**はプロファイルごとに1回ホストそのものに問い合わせ、
対象に関係なく一覧に加わります。これらはフォルダーではなく、あなたに関するものだからです。

これらは**既定でオフ**です（ホストの検索は API の割り当てを消費します）。接続済みのコードホストにオンの一覧がない間は、
一覧の先頭にそのホストの行が表示されます。

`GitHub: クローンしていないリポジトリも含め、自分のレビュー待ちのリクエストを一覧表示  [有効にする]`

**有効にする**をクリックするか、その行で `Enter` を押すか、`T` を押すか、`Radar: アカウント全体のレビュー依頼を有効にする...`
を実行すると、そのプロファイルの `integrations.radar.review_requests = true` が `config.toml` に書き込まれ、すぐにホストに
問い合わせます。そのほかの一覧（自分の名前空間の未完了のリクエストすべて、自分に割り当てられた Issue、ドラフト、名前空間）は
`gitpoulpi hosting integrations radar` またはプロファイルの設定で指定します。[設定リファレンス](config-reference.md)と
[CLI リファレンス](cli-reference.md)を参照してください。GitHub、GitLab、Gitea、Forgejo、Azure DevOps、Bitbucket Data Center、
Gerrit が対応しています。Bitbucket Cloud にはアカウント全体のエンドポイントがないため、そのリクエストは対象のリンク済み
リポジトリの分だけが表示されます。

プロファイルの**名前空間**は、そのすべての一覧を一部のリポジトリに絞り込みます（設定 > 連携 > Radar：1 行に 1 項目のテキスト領域と、**正規表現**のチェックボックス）。行は、リポジトリの完全なパスと等しいか、`/` で終わるパスのプレフィックスのときに一致します：`ptm` は `ptm/produits/x` を残し、`ptmx/y` と `formation/y` は除きます。チェックボックスをオンにすると、各行はパス全体に対して（表示どおりの形で）実行される正規表現になります（`^ptm/(produits|infra)/`）。無効な行はフィールドの下に表示されて保存されません。空なら制限なしです。

行の配置は次のとおりです。

- 対象がすでに一覧にしている行（同じホスト、プロジェクト、種類、番号）は1回だけ表示されます：**対象の行が優先**されます。
- プロジェクトをどこかでクローンしている行（最近のリポジトリ、ワークスペース、フォルダー対象が見つけたフォルダー。リモート URL で照合）は、
  そのクローンを持ちます：**Enter**、チェックアウト、worktree などは、通常の行と同じようにそのクローンを開きます。
- それ以外の行は**クローンされていません**：リポジトリのチップが暗くなってプロジェクト（`acme/app`）を表示し、選択するとステータスバーに
  `未クローン` と表示されます。**ブラウザーで開く**は使えます。**レビュー**は方法を尋ね（下を参照）、チェックアウト、worktree、
  リポジトリで表示、作業の開始は `先にリポジトリをクローンしてください` と表示します。

### リクエストのレビュー

対象自身のリポジトリのリクエストでは、**レビュー**（`e`）はそのリポジトリのタブをレビュー付きで開きます。アカウント全体の行の
リクエストでは、クローンが分かっているかどうかと、プロファイルの**クローンしていないリポジトリのリクエスト**の設定
（設定 > 連携、[設定リファレンス](config-reference.md)の `review_mode`）によって動作が決まります。

| 設定 | クローンが分かっている | クローンが分からない |
|---|---|---|
| 確認する（既定） | 確認：**ローカルのクローンを開く**（`l`）または **API 経由でレビュー**（`a`） | 確認：**クローンしてからレビュー**（`c`）または **API 経由でレビュー**（`a`） |
| クローンする | クローンを開く | クローンのダイアログを開く |
| API 経由でレビュー | API 経由でレビュー | API 経由でレビュー |

質問は小さなダイアログです：文字キーで選び、**Enter** で強調表示の行を選び、`Esc`、**キャンセル**、`✕`、外側のクリックで閉じ、
**{プロファイル}で記憶する**（`r`。例：GitHub で記憶する）はプロファイルの設定を書き込むので、次回から質問されません
（設定の行で元に戻せます）。`Ctrl+N` でそのコントロールにバッジが表示されます。

- **API 経由でレビュー**は、ホームウィンドウの Radar の上に、ホストから取得したコードでレビューを開きます
  （[クローンなしのレビュー](review.md#クローンなしのレビュー)を参照）。`Esc` または `✕` で Radar に戻ります。パレットの
  *レビュー: ...* の行もこの画面に作用します。
- **クローンしてからレビュー**は、行の元になった接続済みアカウントでクローンのダイアログを開きます（同じリポジトリ一覧で、オーナーごとにグループ化）。リクエストのリポジトリが選択され、既定のクローン先フォルダーが入力されています。どちらかを
  変更してからクローンします。そのアカウントからの通常のクローンと同じサインインが使われます。リポジトリがアカウントの一覧にない場合（メンバーではない場合）は、一覧が開いたまま名前で検索された状態になり、その旨のメモが表示されます。リポジトリを一覧にできないホストでは、アドレスを入力した状態で **URL でクローン** が開きます。クローンが完了すると、新しいリポジトリがホストにリンクされ（PULL REQUESTS ソース、そしてホストに
  Issue があって未設定なら ISSUES ソースも）、そのタブが開き、そこでそのリクエストのレビューが開きます。ダイアログをキャンセルした場合や
  クローンが失敗した場合は、何もリンクされません。
- Azure DevOps と Bitbucket のリクエストにはアプリ内レビューがありません：**レビュー**はリクエストのページをブラウザーで開き、
  ステータスバーにそう表示します。

パレットの *Radar: API 経由でレビュー* と *Radar: クローンしてレビュー...* は、質問を省略します。

フィルターの横にある 2 つのチェックボックス（アカウント全体の一覧に問い合わせている間に表示されます）は、`radar.toml` に保存されます。

| チェックボックス | キー | 既定 | 効果 |
|---|---|---|---|
| `[x] 未クローン` | `a` | オン | クローンが分からないリポジトリの行を一覧にします。オフにすると、クローンが分かっている行だけが残ります。 |
| `[ ] ドラフト` | `d` | オフ | アカウント全体の行のドラフトのリクエストを一覧にします。対象自身のリポジトリのドラフトは常に一覧にされます。 |

どちらも `Ctrl+N` のバッジとパレット（`Radar: 未クローンのリクエストを表示`、`Radar: ドラフトを表示`）にあります。

プロファイルの回答は `radar-account.json` に **5 分間**保持されます：その間に Radar を開き直すと、ホストに問い合わせずに行が表示されます。
**更新**（`r` または `F5`）は、前回の回答の古さに関係なく、すべてのリポジトリとアカウント全体のすべての一覧について常に問い合わせます。速度を落とすよう求めた、またはトークンを拒否したホストには、同じラウンド内では再度問い合わせません。
保持されるのはプロファイルと種類ごとに最大 300 行で、**リポジトリ**の下の行に、ほかに何件あったか、またはプロファイルを読み取れなかった理由が
表示されます（**再接続**で設定 > 連携が開きます）。

## 制限

- アカウント全体の行は、GitHub、GitLab（Self-Managed を含む）、Gitea、Forgejo、Azure DevOps、Bitbucket Data Center、Gerrit の
  プロファイルから取得されます（Bitbucket Cloud を除く）。自分に割り当てられた Issue は最初の 5 つから取得され、Bitbucket と Gerrit には Issue がありません。
- リポジトリごとの一覧では、GitHub、GitLab（Self-Managed を含む）、Gitea、Forgejo、Azure DevOps、Bitbucket、Gerrit のプロファイルが
  使われます。チェック、競合、メンションは最初の 4 つについてのみ取得されます。
- GitLab のメンションは保留中の ToDo からのみ得られます。GitHub、Gitea、Forgejo のチェックは、リポジトリごとに 15 件のリクエストについて問い合わせます。
