# 元に戻す・やり直す

**いつでも元に戻せます。** GitPoulpi がリポジトリに加えた変更はすべて記録されます
（既定で最大 100 件、`general.undo_depth`）。ブランチがたどったすべての位置も、
ほかのプログラムによる移動を含めて記録されます。間違えても、次のどれかで作業を取り戻せます。

| したいこと | 使うもの |
|---|---|
| 直前の操作を取り消す | `Ctrl+Z`（やり直し：`Ctrl+Y` または `Ctrl+Shift+Z`）、またはツールバーの**元に戻す**と**やり直す**ボタン |
| 複数の操作をまとめて、またはずっと前の 1 件を取り消す | **元に戻す履歴**（`Alt+Z`、元に戻すの横の矢印、`編集: 元に戻す履歴...`） |
| 数回前に削除したブランチ、tag、stash、ファイル、ハンクを、**その後の操作を取り消さずに**取り戻す | 元に戻す履歴の**これだけ復元** |
| ほかのプログラムが動かした場合も含め、ブランチを元の位置に戻す | ブランチの **Reflog**（参照のメニューの **Reflog...**） |
| どのブランチからも届かなくなった commit を探す | **失われた作業**（`編集: 失われたCommitsを復旧...`） |
| シェルや **AI エージェント**がブランチ、tag、stash、HEAD に行ったことを取り消す | 同じ `Ctrl+Z`：それらの変更も履歴に入り、**外部**と印が付きます（[GitPoulpi の外で行われた変更](#gitpoulpi-の外で行われた変更)を参照） |

破棄、ファイルの削除、ブランチや tag の削除、hard reset、stash の drop、リモートの削除など、
何かを壊し、かつ元に戻せる操作のあとには、ステータスバーが
「破棄完了 - 元に戻すには Ctrl+Z」のように伝えます（キーは設定している割り当てが表示されます）。
元に戻すのツールチップには、さかのぼれる操作の数が表示されます。

`Ctrl+Z` は、GitPoulpi がリポジトリに対して最後に行ったことを取り消します。`Ctrl+Y`
（または `Ctrl+Shift+Z`）でそれを元に戻します。ツールバーには**元に戻す**と**やり直す**のボタンがあり、
パレットには `編集: 元に戻す` と `編集: やり直す` があります。各ボタンのツールチップには、
それが何を取り消すのかが表示されます（「commit "fix typo" (a81b9e4) を元に戻す」）。

![すべての変更をステージした後のツールバー：元に戻すが点灯し、ツールチップに取り消される操作の名前が表示されている](../images/undo-toolbar.png)

やり直しは、操作をもう一度実行することはありません。記録されていた状態を復元するので、
やり直された commit はまったく同じ commit で、id もタイムスタンプも同じです。

テキストフィールドがキーボードを受け取っている間（commit メッセージ、
フィルターボックス、独自のテキストの元に戻す機能を持つエディター）、`Ctrl+Z` は何もしません。

## 元に戻す履歴

`Alt+Z`（割り当て変更可）、元に戻すボタンの横の矢印、または `編集: 元に戻す履歴...` で、
記録されたすべての操作を新しい順に並べたパネルが開きます。各行には、操作の種類を示すアイコン
（commit、ブランチ、tag、stash、reset、merge など、破棄、ステージ、設定、外部の変更）、
何をしたか（ユーザーの言語で表示）、どれくらい前か、そして状態（**単独で復元可**、理由つきの**ブロック中**、
または**取り消し済み**でやり直し可能）が表示されます。項目が複数の日にまたがるときは、
日ごとに細い見出し（今日、昨日、そのあとは日付）が入ります。見出しに件数が出ます
（「12 件の操作を元に戻せます（最大 100 件）」）。

取り消した操作は、最新の操作の**上**に、区切り線（「取り消し済み - やり直しで戻せます」）の下へ薄く表示され、
次にやり直しで戻るものが区切り線のいちばん近くに来ます。選択は取り消した操作ではなく、最新の操作から始まります。
矢印キーで移動し（見出しと区切り線は飛ばされます）、`Tab` で 3 つのビューを切り替え、
`Esc` で閉じます。選択した行では次の操作ができます。

- **ここまで元に戻す**（`u`）：その操作と、それより新しいすべての操作を新しいものから順に取り消します。
  一覧を示す確認が 1 回あります。デーモンが危険と判断した手順は、実行前にもう一度確認します。
- **これだけ復元**（`r`）：その 1 つの操作が取り除いたものを取り戻し、それ以降の操作はそのまま残します。
  削除したブランチや tag は、持っていた commit に戻ります（名前が使用済みなら別の名前を尋ね、
  空いている名前が入力済みになります）。drop した stash は stash 一覧の先頭に戻ります。
  破棄または削除したファイルは、その後変更されていなければ元の場所に書き戻され、
  変更されていれば隣に `name.restored` として書き出されます（何も上書きしません）。
  削除したリモート、upstream、無視の行、attributes の行は再び追加されます。
  reset、amend、rebase、merge、commit は、古い先端にブランチ `restore/<ブランチ>-<sha>` を作ります。
  現在のブランチとファイルは動きません。確認には実行内容がそのまま表示され、
  復元そのものも新しい操作として記録されるので、`Ctrl+Z` で取り消せます。
- **ここまでやり直す**（`y`）：取り消し済みの行で使います。
- **main を commit が残した位置に復元**（`o`。パネルの外では `Alt+Shift+Z` または
  `編集: ブランチをブロックされた操作が残した位置に復元`）：ほかのプログラムがブランチを動かして
  元に戻すがブロックされたとき、reflog にはその操作が残した位置が記録されています。

行を右クリックする（または `.` を押す）と、同じ操作がメニューで表示されます。

![ブランチを削除して 2 回 commit した後の元に戻す履歴：削除したブランチの行が選択され、単独で復元できる](../images/undo-history.png)

## Reflog

ローカルブランチの参照のメニューに **Reflog...** があります。`編集: Reflog...` は HEAD の reflog を表示し、
元に戻す履歴にもそのタブがあります。ブランチがたどった位置を新しい順に並べます。
短い SHA、記録された理由、どれくらい前か、誰が行ったか（シェルで行った移動も含む）です。
選択した位置のメッセージと変更ファイルは、一覧の横に表示されます。

reflog は 200 件の位置ずつ読み込まれます。それより長い場合は自動的に続きが読まれます：
カーソルを動かす（またはスクロールする）と、一覧の末尾の近くで次のページが取得され、続きがある間は最後の行が **... さらに読み込む** と表示されます。
**さらに読み込む**（`m`、またはパレットの `Reflog: さらに読み込む`）はすぐに取得し、ステータスバーに「読み込んだ位置：N 件」と表示します。
reftable 形式の git を使うリポジトリも、ほかのリポジトリと同じように読まれます。
**Log で表示**（`s`）、**ここにブランチを作成**（`b`）、**`<ブランチ>` をこの位置に復元**（`r`）が使えます。
復元は元に戻せます。ブランチがチェックアウト中で、移動すると上書きされるローカルの変更がある場合は、
その変更をどうするかをドロップダウンで尋ねます。**自分の変更を残す**、soft、mixed、hard です。
hard はファイルへの変更を破棄しますが、先に保存するので `Ctrl+Z` で戻せます（赤字でそう表示されます）。

![main の Reflog：これまでにたどったすべての位置が新しい順に並び、選択した位置の説明が右側に表示されている](../images/reflog.png)

## 失われた作業

`編集: 失われたCommitsを復旧...`（ログの commit メニューにもあります）は、どのブランチ、tag、stash からも
届かなくなった commit を探します。reflog がまだ名前を残しているもの（削除したブランチの commit）、
undo ピンだけが保持しているもの、孤立したものです。一覧はすぐに表示され、孤立した commit の
低速なスキャンはスピナーの表示中に追加されます。インターフェースをブロックすることはありません。
**ここにブランチを作成**（`b`）は選んだ名前で commit を取り戻し、**cherry-pick**（`c`）は現在のブランチに適用し、
**Log で表示**（`s`）はまだ届く commit で使えます。

![失われた作業：削除したブランチの 2 つの commit（reflog で見つかったもの）と、孤立した commit](../images/lost-work.png)

## コマンドパレットから

3 つのビューの行アクションは、すべてコマンドパレットの行としても使えます。そのため、パネルはマウスも
覚えておくべき文字も不要です。パネルを開いたまま `Ctrl+P` を押すと、その上にパレットが開き、
**元に戻す履歴:**、**Reflog:**、**失われた作業:** の行が、表示中のビューの選択行に作用します。

| ビュー | パレットの行 |
|---|---|
| 元に戻す履歴 | `元に戻す履歴: ここまで元に戻す...`、`ここまでやり直す...`、`これだけ復元...`、`ブランチを元の位置に復元...`、`更新`、`閉じる` |
| Reflog | `Reflog: Log で表示`、`ここにブランチを作成...`、`この位置に復元...`、`さらに読み込む`、`更新` |
| 失われた作業 | `失われた作業: Log で表示`、`ここにブランチを作成...`、`Cherry-pick`、`再検索` |

対応するビューが開いていない間、これらの行はグレー表示になり、理由が示されます。3 つの入口である
`編集: 元に戻す履歴...`、`編集: Reflog...`、`編集: 失われたCommitsを復旧...` は、開いているパネルを
それぞれのビューに切り替えます。選択中の行でできない操作は、何もせずに終わるのではなく、ステータスバーに
理由を表示します。たとえば「この操作はすでに取り消し済みです: 「ここまでやり直す」を使ってください」、
その項目を単独では復元できない理由、「戻せるのはブランチまたは HEAD だけです」などです。`...` の行は、
ボタンと同じ確認または名前の入力を開きます。

## 元に戻せるもの

| 領域 | 操作 |
|---|---|
| commit | commit、amend、reword、AI の commit コンポーザー（そのすべての commit を 1 ステップとして） |
| ブランチと tag | 作成、削除、名前変更、upstream の設定または解除、追跡ブランチの作成、tag の作成 / 削除 / 注釈付け、fast-forward、pull request のブランチとしての checkout |
| 移動 | ブランチまたは commit の checkout（detached HEAD を含む） |
| 履歴 | merge（fast-forward または merge commit）、rebase（通常と対話的、完了後）、cherry-pick、revert、reset（soft、mixed、hard）、pull のローカル部分 |
| 作業中の変更 | ステージとステージ解除（ファイル、フォルダー、ハンク、行、すべて）、破棄（ファイル、フォルダー、ハンク、行、ファイルの checkout）、パッチの適用、**ディスクからのファイルの削除**、**無視**（ファイル、拡張子、フォルダー：選んだ `.gitignore` の行）、**バイナリまたはテキストとして扱う**（`.gitattributes` の行） |
| stash | push、apply、pop、drop |
| リモートと設定 | リモートの追加、削除、名前変更、URL または push URL の変更、Git LFS の track と untrack |
| サーバー上 | **リモートのブランチや tag の削除**（参照のメニュー、パレット、`branch delete-remote`、`tag delete-remote`、`tag delete --both`、またはリモートブランチも削除するワークフローの完了から）：下記を参照 |

merge、cherry-pick、revert が競合で止まっている間は、**保存して解決済みにする**、
ステージ、ステージ解除も元に戻せます（それぞれ、その下にあるものより先に取り消されます）。
また、**merge の中止**（または cherry-pick、revert の中止）も元に戻せます。
元に戻すと、停止していた操作全体が、その競合（未解決の各ファイルの 3 つのバージョン）、
すでに解決してステージしたファイル、作業ツリーの競合マーカー、そして merge メッセージとともに戻ります。
やり直すと、再び中止されます。ステージと解決は、操作が終わる（commit または中止される）と
元に戻せなくなります。*ステージ解除*と*すべてステージ解除*は、まだ競合しているファイルには
決して触れません。取り消すべきステージ済みの変更がないからです。

破棄や hard reset で捨てられるものはすべて先に保存されるため、元に戻すと、
未追跡ファイル、実行ビット、シンボリックリンクを含め、正確なバイト列が戻ります。
drop した stash を元に戻すと、同じ commit id の同じ stash が戻ります（元の位置ではなく、
`stash@{0}` として stash リストの先頭に入ります）。リモートの削除を元に戻すと、
そのリモート追跡ブランチ、`origin/HEAD` のエイリアス、それを追跡していたブランチの upstream 設定が戻ります。

### リモートのブランチや tag の削除

削除の前に、GitPoulpi はサーバーに、そのブランチや tag がいま何を指しているかを尋ねて記録します。
リモート、名前、正確な commit です（注釈付き tag では tag オブジェクトそのもので、注釈も保たれます）。
削除が行われるのは、サーバーがまだその値を持っているときだけです。

**元に戻すと、同じ名前、同じ commit のまま、強制せずに push し直します。**
これは他の人にも見えるサーバー上の変更なので、元に戻すは**必ず先に確認し**、その旨を伝えます
（「これを元に戻すと、origin にブランチ topic を 3f2a1c0 で再作成します...」）。項目の手順にも表示されます
（`gitpoulpi undo --dry-run`）。push と同じ認証情報を使います。リモート追跡ブランチも一緒に戻ります。
**やり直し**は同じ安全確認のうえで、もう一度削除します。

次の場合、元に戻すは何も変更せずに拒否されます。

- その後、リモートで**ブランチや tag が再び作られた**、または動かされた場合：
  記録した commit とは別の commit にあり、push すると他の人の作業を上書きしてしまいます（拒否の理由に両方の commit が示されます）。
- その commit（または tag オブジェクト）が**もうリポジトリにない**場合（ガベージコレクションされました）：元に戻せません。

「ローカルとリモートの両方を削除」は**1 件の項目**です。元に戻すとローカルとリモートのブランチや tag が一緒に戻り、
やり直しは両方をもう一度削除します。リモートのブランチだけを削除してもローカルのものは残り、元に戻すときも同じです。
リモートブランチも削除するワークフローの完了は、全体として元に戻せます。

## 元に戻せないものとその理由

- **サーバー上のほとんどのこと**：push、tag の push、LFS の push、ロックとアンロック、
  pull request を開くこと。その状態は他の人と共有されています。push を元に戻すことは、
  force-push や相手側での削除になるため、GitPoulpi はそれを代わりに行いません
  （リモートのブランチや tag の削除は例外です。元に戻すと、サーバーが持っていたものを戻すだけで、
  そこで何かが変わっていれば拒否されます）。そのような操作があっても、元に戻すことが妨げられることはありません。
- **fetch**：サーバーを映すリモート追跡参照を動かすだけです。
  次の fetch で同じことが起きます。
- **rebase の中止**：元に戻す機能は提供されません（rebase はブランチを動かし、
  独自の状態を保持します。中止そのものが元に戻す方法です）。**merge、cherry-pick、revert** の中止は
  記録されます。上を参照してください。
- **worktree の作成**、**パッチファイルの作成**、クローン、初期化、ホスティングの操作
  （pull request、Issue）、AI の呼び出し：これらはリポジトリの履歴の一部ではありません。
- ファイルメニューからの**新しい空のファイルの作成**、merge 後の
  `*.orig` ファイルの自動削除、内蔵エディターでのファイルの保存は
  記録されません。**SSH コマンド**（`core.sshCommand`）や**スパースチェックアウト**の変更も記録されません（失われるものはなく、*オフにする* ですべてのファイルが戻ります）。
- **`.git/info/exclude` または `.git/info/attributes` への書き込み**（無視とバイナリ／テキスト扱いの一覧にある「このクローンのみ」の選択）：これらのファイルは作業ツリーの外にあるため、記録されません。
- **GitPoulpi の外で行われた作業ツリーのファイルの編集**（エディター、スクリプト、コードを書く AI エージェント）は、
  記録されません。そのスナップショットは存在しないため、シェルで行った `git reset --hard` や
  `git checkout -- file` は、未コミットの編集を完全に失わせます。シェルの作業のうち記録されるのは、
  参照にあるものです。次の節を参照してください。

## GitPoulpi の外で行われた変更

AI エージェント（または GitPoulpi の隣のシェル）で作業すると、git の作業の大半はウィンドウの外で行われます：
commit、新しいブランチやワークツリー、ブランチの削除、reset、rebase、stash などです。GitPoulpi はこれらも見ています。
デーモンは前回確認した参照（ローカルブランチ、tag、HEAD、stash の一覧、ワークツリーの一覧）を保持し、
リポジトリが変わって、それが GitPoulpi 自身の操作でなかったときは、
**まとまった変更ごとに 1 件**の項目を元に戻す履歴に、**外部**と印を付けて記録します。
git が記録した理由（`commit: fix login`、`rebase (finish)`、`reset: moving to HEAD~1`、
`checkout: moving from a to b`）と、git が記録した実行者の名前も付きます。
GitPoulpi はシェルと AI エージェントを区別できず、推測もしません。項目が示すのは、外部で行われたことだけです。

- **連続した操作は 1 件です。**2 回の確認の間に行われた 20 回の commit は、最初の値から最後の値までの 1 件の項目になります。
  rebase は終了時に記録される 1 件の項目です（rebase や merge が停止している間は何も記録されません）。
- **削除された参照は固定されます。**消えたブランチ、tag、stash は、何かに削除される前に、
  古い commit のまま `refs/gitpoulpi/undo/` の下に保持されるため、**これだけ復元**（または `Ctrl+Z`）で、
  reflog やガベージコレクションのあとでも、エージェントが削除したブランチを取り戻せます。
- **GitPoulpi が閉じていた間。**スナップショットはジャーナルの隣
  （`.git/gitpoulpi/refs-snapshot.json`）に保存されるため、GitPoulpi が動いていない間に起きたことは次回起動時に見つかり、
  「GitPoulpi の終了中」と印が付きます。
- **`Ctrl+Z` はほかの項目と同じように働きます。**参照が元に戻り、削除されたブランチは作り直され、
  drop された stash は再び保存され、外部の checkout は古いブランチを再びチェックアウトします。
  チェックアウト中のブランチは `git reset --keep` のように戻ります：ファイルは追従し、ローカルの変更が邪魔になるときは
  **拒否して何も変更しません**。やり直しは再適用します。**これだけ復元**も使えます：削除されたブランチが戻り、
  あとの操作はそのままです。動かされたブランチは `restore/<ブランチ>-<sha>` として戻ります。
- **ステータスバーが一度だけ知らせます。**新しい外部の項目が届いたとき、ウィンドウが前面にあれば
  「外部の変更を記録しました - Ctrl+Z で元に戻せます」と表示されます。
- 外部の変更が最新の項目になるため、以前の「外部の変更によるブロック」はほとんど起きなくなります：まず外部の変更を元に戻します。

記録されないもの：リモート追跡ブランチの fetch だけによる移動（サーバーを映すだけのため）、GitPoulpi 自身の隠し参照、
ブランチの変更を伴わずに追加または削除されたワークツリー（それを持つブランチの項目には「ワークツリー <path> を追加」と表示されます。
元に戻しても動くのは参照だけで、ワークツリーは削除されません）、そしてファイルの中身すべて。
`general.journal_outside = false`（設定 > 一般、「GitPoulpi の外での変更を記録」）でオフにできます：
外部の変更は何も記録されず、外部で行われた変更は以前と同じく最新の項目をブロックします。

## 元に戻せない場合

実行する前に、GitPoulpi はその操作が触れたすべてのものが、操作を終えたときのままであるかを確認します。
そうでなければ**何も変更せず**、何が動いたかを伝えます。

- `main` が、commit が残した a81b9e4 ではなく 3f2a1c0 にある（たとえば
  シェルで行った commit）。
- ファイル、インデックス、stash、設定のセクションがその後に変更された。
- merge、rebase、cherry-pick が進行中である。
- 操作の実行中に GitPoulpi が停止したため、操作が完了しなかった
  （その項目には*中断*の印が付き、自動では元に戻されず、`gitpoulpi
  undo --list` が変更しようとしていたものを表示するので、手で直せます）。

元に戻す操作は厳密に後入れ先出しです。最新の項目がブロックされていると、古い項目もブロックされます。
まだ有効な新しい操作の下にある古い操作を元に戻すのは、推測になるからです。自分で元の状態に戻した場合、
その項目は再び有効になります。項目が触れたものに何も触れない変更（別のブランチでのシェルからの
commit、fetch）は、何もブロックしません。

### 解除できないブロックされた項目：履歴から外す

最新の項目が恒久的に詰まっている場合（リポジトリが GitPoulpi の外で先に進んだ、または項目が完了しなかった）、
その下のものも元に戻せません。元に戻すのツールチップと拒否メッセージがそう伝え、抜け道を示します。
パレットの **編集: ブロックされた元に戻す項目を履歴から外す**（先に確認があります）、または
コマンドラインの `gitpoulpi undo-forget` です。履歴から外す操作は、その 1 つの項目をジャーナルから削除するだけです。
リポジトリには決して触れず、その項目はもう元に戻すことも、やり直すこともできません。
その下の項目が最新になります。

次の 2 つのケースは自然に解決します。

- 通常の git で完了させた、競合した merge または rebase：その項目は、次に GitPoulpi が
  リポジトリの状態を読み取ったときに閉じられます。
- **保存して解決済みにする**で解決した、競合した stash の pop または apply のファイル：
  解決したファイルがまだステージ済みで commit されていない間は、元に戻すと競合が戻ります。

## 確認

元に戻すが確認を求めるのは、危険な場合だけです。

- 取り消そうとしている commit（または merge、rebase、cherry-pick、revert）が、
  すでにブランチの upstream にある場合：元に戻すと、公開した履歴を書き換えることになり、
  その結果を force-push しなければならなくなります。
- commit されていない変更があり、元に戻すと作業ツリーが動く場合：
  変更は保持されますが、そのうちの 1 つが書き換えが必要なファイルにあると、
  何も変更せずに元に戻すは停止します。

- 項目がリモートのブランチや tag を削除したものの場合：元に戻すと**サーバーへ push し直す**
  ため（上記を参照）、必ず確認します。それをもう一度そこで削除するやり直しも同様です。

やり直しと、参照を動かすだけの元に戻す操作は、確認しません。逆方向の操作がキー 1 つで行えるからです。

## どこまで遡れるか

`general.undo_depth`（設定 > 一般）は、保持される操作の数です。
既定は **100** で、`0` は無制限を意味します。小さくすると、最も古い項目がすぐに忘れられます。
元に戻した後に新しい操作を始めると、やり直せたはずのものは、どのエディターとも同様に破棄されます。

履歴は worktree ごとに（リンクされた worktree には専用のものがあります）、
git ディレクトリ（`.git/gitpoulpi/journal.json`）に保持されるので、
プログラムを閉じても残り、`git status` や commit に含まれることはありません。

## オフにする

`general.undo_enabled = false`（設定 > 一般、「元に戻す機能を有効化」）で、
機能全体がオフになります（外部の変更の記録も含みます）。何も記録も保持もされないため、ステージ、
破棄、commit が少し速くなります。元に戻すとやり直すのボタンは消え、
`Ctrl+Z` は「元に戻す機能がオフです」と表示します。

**オフにすると履歴は消去されます**：ジャーナルファイルと後述の隠し参照は、
オフの間にデーモンへ最初のリクエストが届いたときに削除されます。
オンに戻すと、空の履歴から始まります。

## 保存されるもの

元に戻すでデータが失われることがないように、項目が必要とするかもしれないすべての commit、
tag オブジェクト、stash、スナップショットは、項目が履歴にある間、`refs/gitpoulpi/undo/` 配下の
隠し参照で保持されます。これらは GitPoulpi 自身の一覧からは除外されますが、シェルの `git log --all` や
`git for-each-ref` には表示され、`git push --mirror` はそれらを push します（代わりに
`git push --all` を使ってください）。項目が履歴から外れたとき、または元に戻す機能をオフにしたときに削除されます。
それ以外のものが削除されることはありません。

## コマンドラインと MCP から

```
gitpoulpi undo [--dry-run] [--expect <id>] [--yes]
gitpoulpi redo [--dry-run] [--expect <id>] [--yes]
gitpoulpi undo --list [--all]
gitpoulpi undo-forget [--dry-run] [--redo] [--expect <id>] [--yes]
```

- `--dry-run` は手順を説明するだけで、何も変更しません。
- `--list` はジャーナルを最新が最後の順に表示し（`--all` は、もうやり直せないが保持されている項目を追加します）、
  各項目の id と状態を示します。
- `--expect <id>` は、その項目がまだ最新でない限り、呼び出しを*古い*として拒否します。
  スクリプト（や 2 つ目のウィンドウ）が、見ていたもの以外を元に戻すことはありません。
- `undo-forget` は、ブロックされた最新の項目をジャーナルから削除します（`--redo`：最新のやり直しの項目）。
  その項目がブロックされていないときは拒否され、`--yes` なしでは終了コード **3** で終了します。
  MCP では変更操作ですが、破壊的ではありません。リポジトリには触れません。
- 終了コード **0** は完了、**2** は拒否（JSON が理由を示します。たとえば削除したリモートブランチが
  再び作られたときは `RemoteRefMoved`）、**3** は危険で `--yes` が必要です
  （リモートのブランチや tag の削除を元に戻す場合で、サーバーへ push します）。

すべてを元に戻さずにさかのぼる：

```
gitpoulpi undo-restore <id> [--name N] [--dry-run]      (also: undo restore <id>)
gitpoulpi reflog [<ref>] [--skip N] [--limit N]
gitpoulpi reflog-restore <ref> <oid> [--mode keep|soft|mixed|hard] [--dry-run]   (also: reflog restore ...)
gitpoulpi lost-commits [--skip N] [--limit N] [--no-deep] [--budget-ms MS]
```

- `undo --list` は、項目ごとに**これだけ復元**で何を戻せるか（`restore.items`）、
  戻せない場合はその理由（`restore.not_restorable`）と、誰が行ったかを示します：
  `"source": "gitpoulpi"`、またはシェルや AI エージェントによる変更の `"source": "outside"`
  （`outside.message` は git の理由、`outside.committer`）。`undo`、`redo`、`undo-restore` は
  外部の項目もほかの項目と同様に扱います。
- `undo-restore <id>` は、その 1 つの項目が取り除いたもの（削除したブランチや tag、drop した stash、
  破棄または削除したファイル、追跡ブランチと upstream つきで削除したリモート、無視の行）を取り戻し、
  それ以降の操作はすべて残します。上書きはしません。その後変更されたファイルは、
  残しておいた版が隣に `<name>.restored` として書き出されます。ブランチ名が使用済みの場合は拒否
  （終了コード 2）され、空いている名前が提案されるので、`--name` で指定します。
  reset、amend、rebase のあとは古い先端に新しいブランチを作り、現在のブランチは動かしません。
  復元はジャーナルの 1 項目なので、`gitpoulpi undo` で取り消せます。
- `reflog` は `HEAD` またはブランチがあった位置を、git が記録した理由つきで表示します。
  シェルで行った操作も含まれます。`reflog-restore` はブランチ（または `HEAD`）をそのいずれかの位置に動かします。
  未 commit の変更があるチェックアウト中のブランチには `--mode` が必要です。これもジャーナルに記録されます。
- `lost-commits` は、どのブランチ、tag、リモート、stash からも届かない commit を表示します。
- シェルでの移動が最新の項目をブロックしたとき、拒否メッセージには、その項目が想定する内容を保持している
  reflog の位置（`reason.RefMoved.restore`）が含まれます。これを `reflog-restore` に渡します。

上記の操作をすべてのインターフェースから元に戻せるように、2 つのコマンドがあります。
`gitpoulpi rm-file <paths>`（作業ツリーからファイルを削除）と
`gitpoulpi ignore <pattern> [--file <path/.gitignore>]`（`.gitignore` に行を追加。
その行がすでにある場合は何も起きません。元に戻すと、ファイルは元の状態に戻るか、
コマンドが作成したものなら削除されます。その後ファイルが編集されていた場合は拒否されます）。

MCP サーバーにはコマンドごとに 1 つのツールがあるので、`undo`、`redo`、`rm-file`、
`ignore` もツールです。`undo`、`redo`、`rm-file` は破壊的に分類されます
（`reset` と同様に制限されます。[MCP とエージェント](mcp-and-agents.md)を参照）。`ignore` は
通常の変更操作です。ジャーナルはリポジトリ内のファイルなので、シェルでの `gitpoulpi
undo` はウィンドウが行ったことを取り消し、ウィンドウはスクリプトが行ったことを元に戻せます。
