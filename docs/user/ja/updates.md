# 更新

GitPoulpi は新しいリリースを確認し、インストール方法に応じて、自分のファイルを置き換えるか、インストールしたプログラムに更新を任せます。あなたの操作なしに、置き換えや再起動が行われることはありません。

## チップとパネル

タイトルバーのアプリ名とリポジトリのパスの間に、実行中のバージョン（`v1.0.0`）が表示されます。新しいリリースが見つかると、チップはアクセントカラーの `v0.2.0 が利用可能` に変わります。

チップをクリックするか、`Ctrl+N` の後に `u` を押すか、コマンドパレット（`Ctrl+P`）で**更新: 更新パネルを表示**を実行すると、更新パネルが開きます。アプリの上に重なるウィンドウで、`Esc`、`q`、閉じる ✕、または外側のクリックで閉じます。パネルには次の内容が表示されます。

- 実行中のバージョンと**インストール方法**：GitPoulpi がこのコンピューターに入った方法です（以下のすべてがこれで決まります）。
- 更新の状況（確認中、パーセント付きのダウンロード中、準備完了、失敗）。
- このインストールの手順に対応するボタンと、ある場合は実際のコマンド。
- 管理者が設定している場合は、管理者からのメッセージ。

すべてのボタンにキー（パネルのヒント行に表示）とパレットのコマンドがあるため、マウスなしでも使えます。

| ボタン | キー | パレットのコマンド |
|---|---|---|
| **更新して再起動**（または**更新を実行**） | `u` | 更新: 今すぐ更新 |
| **コマンドをコピー** | `c` | 更新: 更新コマンドをコピー |
| **ターミナルで開く** | `t` | 更新: 更新コマンドをターミナルで実行 |
| **戻す** | `v` | 更新: 前のバージョンに戻す |
| **リリースノート** | `n` | ヘルプ: リリースノート |
| **このバージョンをスキップ** | `s` | 更新: このバージョンをスキップ |
| **通知を開く**（セキュリティ通知があるときのみ） | `a` | 更新: セキュリティ通知を開く |
| **今すぐ確認** | `r` | 更新: 今すぐ更新を確認 |
| **閉じる** | `Esc` | |

このインストールに当てはまらないコマンドは、パレットでグレー表示になり、理由が付きます（たとえば「このインストールは別の方法で更新します：「更新: 更新パネルを表示」を参照」）。

## インストール方法ごとの動作

| インストール方法 | 確認先 | パネルの動作 | 元のバージョンに戻す |
|---|---|---|---|
| リリースアーカイブ、または `install.sh` | GitHub のリリース | **更新して再起動**：GitPoulpi はアーカイブをダウンロードして検証し、終了してファイルを置き換え、同じターミナルで再び開きます。 | **戻す**で前のファイルに入れ替えます。 |
| Windows インストーラー（自分のみ） | GitHub のリリース | 同じ動作で、確認はありません。Windows では新しいウィンドウで開き直します。 | **戻す**で入れ替えます。 |
| Windows インストーラー（全ユーザー） | GitHub のリリース | 同じ動作ですが、Windows が管理者の承認を求めます。このコンピューター上の他のユーザーの GitPoulpi セッションは終了し、未保存の入力は失われます。拒否した場合は何も変わりません。 | **戻す**で入れ替えます（同じ確認あり）。 |
| Chocolatey | Chocolatey のコミュニティフィード | **更新を実行**が `choco upgrade gitpoulpi -y` を実行します（Windows が管理者の承認を求めます）。 | パネルに `choco install gitpoulpi --version <previous> --allow-downgrade -y` が表示されます。 |
| Chocolatey（社内フィード） | 組織のフィード | **更新を実行**が `choco upgrade gitpoulpi -y --source=<feed>` を実行します。パッケージパラメーターは再送されないため、展開済みの構成は変更されません。 | フィードを付けた同じ `choco install` の行。 |
| winget | GitHub のリリース | **更新を実行**が、使用許諾に同意した状態で `winget upgrade --id GitPoulpi.GitPoulpi --exact --silent` を実行します。マシン全体へのインストールの場合、管理者の承認は winget 自身が求めます。 | パネルに `winget install --id GitPoulpi.GitPoulpi --version <previous>` が表示されます。 |
| Scoop | GitHub のリリース | **更新を実行**が、GitPoulpi が完全に終了した後に `scoop update gitpoulpi` を実行します。 | **戻す**が `scoop reset gitpoulpi@<previous>` を実行します。 |
| Homebrew | GitHub のリリース | **更新を実行**が、このターミナルで `brew upgrade gitpoulpi` を実行します。 | パネルに `brew install gitpoulpi@<previous>` が表示されます。 |
| apt | GitHub のリリース | パネルに `sudo apt update && sudo apt install --only-upgrade gitpoulpi` が表示され、**コマンドをコピー**と**ターミナルで開く**が使えます。GitPoulpi があなたに代わって `sudo` を実行することはありません。このコンピューターに GitPoulpi の apt リポジトリがない場合は、代わりに新しい `.deb` をダウンロードするよう案内されます。 | パネルに `sudo apt install gitpoulpi=<previous>` が表示されます。 |
| MSI パッケージ | GitHub のリリース、または管理者の提供元 | 実行するものはありません：このインストールは管理者が管理しており、パネルには管理者のメッセージが表示されます。 | 提供されません。 |
| AUR | GitHub のリリース | パネルに `yay -S gitpoulpi-bin` が表示されます（`paru` も可。最初に見つかったほう。ヘルパーがなければ `git clone` と `makepkg -si` の手順）。 | 提供されません。 |
| cargo | GitHub のリリース | `cargo-binstall` があれば `cargo binstall gitpoulpi-cli`、なければ `cargo install --locked --git https://github.com/Poulpi-Lab/GitPoulpi --tag releases/v<version> gitpoulpi-cli` がパネルに表示されます。 | 前のタグを指定した同じコマンド。 |
| Docker イメージ | GitHub のリリース | 実行するものはありません：イメージは置き換えるものです。パネルに `docker pull poulpilab/gitpoulpi:<version>` と `:latest` が表示されます。[Docker で実行する](docker.md)を参照してください。 | パネルに `docker pull poulpilab/gitpoulpi:<previous>` が表示されます。 |
| 書き込めないフォルダー内のリリースアーカイブ | GitHub のリリース | パネルには、GitPoulpi がそこでは自分を置き換えられないことと、**ダウンロード**への案内が表示されます。 | 提供されません。 |
| 開発ビルド（`cargo build`） | なし | 更新しません。チップにはバージョンだけが表示され、パネルにはインストール記録がないと表示されます。 | 提供されません。 |

「表示」だけの行は、それ自体では何も実行しません。**ターミナルで開く**は、コマンドを入力済みの状態でターミナルを開くので、Enter を押すのはあなたです。

管理者が確認先を別の場所（社内フィード、ミラー、`latest.json`）に向けていない限り、リリースは常にプロジェクトの GitHub リポジトリから取得されます。[エンタープライズ配布](enterprise-distribution.md)を参照してください。リリースノートは、リリースまたは GitPoulpi に組み込まれた変更履歴のうち、取得できるほうから表示されます。

## 通知と自動

`updates.mode`（[設定 > 同期](settings.md#同期)）：

- **通知**（既定）：1 日に 1 回、バックグラウンドで確認してチップを表示します。ボタンを押すまで何もダウンロードしません。
- **自動**：GitPoulpi が自分のファイルを置き換える場合（リリースアーカイブ、Windows インストーラー）は、更新を見つけ次第、バックグラウンドでダウンロードと検証も行います。チップは**再起動して更新**になり、再起動はあくまであなたが選びます。パッケージマネージャーが更新を担う場合、**自動**は**通知**と同じ動作です。
- **オフ**：リクエストを一切送らず、チップにはバージョンだけが表示されます。

**更新チャンネル**の設定（`updates.channel`）では、**安定版**と**プレリリース**（リリース候補を含む）を選べます。**今すぐ確認**で始めた確認は、1 日 1 回の制限を無視します。ネットワークに接続できない場合や、リポジトリが非公開で github.com のトークンが保存されていない場合、バックグラウンドの確認は静かに失敗し、アプリケーションログに 1 行だけ記録されます。

## 再起動と、その後の表示

**更新して再起動**または**更新を実行**を押すと、セッションを保存してウィンドウを閉じます。作業は `gitpoulpi-updater` という別の小さなプログラムが行うため、置き換え中に GitPoulpi 自身のファイルが使用中にならず、待機中の親プロセスがパッケージマネージャーを妨げることもありません。まず GitPoulpi のバックグラウンドデーモンを停止し（同じユーザーの他のウィンドウと MCP サーバーも閉じます）、更新を行い、新しい `gitpoulpi --version` が期待するバージョンを表示することを確認してから、GitPoulpi をもう一度起動します。Linux と macOS では同じターミナルで、Windows では新しいウィンドウで起動します。確認に失敗した場合は、古いファイルを元に戻します。

次の起動時、ステータスバーに 1 行が表示されます。

- `v1.4.2 に更新しました`
- `更新に失敗しました：<reason>。前のバージョンがそのまま残っています。`
- `更新を中止しました：管理者の承認が拒否されました。何も変更されていません。`

同時に実行される更新は 1 つだけです。GitPoulpi のデータフォルダーにあるロックファイル（書き込める場合はインストールフォルダーにも 1 つ）が 2 つ目を防ぎ、10 分より古いロックは無視されるため、更新がクラッシュしても GitPoulpi が永久にロックされることはありません。新しいロックが存在する間は、CLI とデーモンは起動しません。

## 戻す

GitPoulpi が自分のファイルを置き換える場合、**戻す**は前のファイルに入れ替えて再起動します。前のファイルは、新しいバージョンが起動してから 1 分間 `<name>.old` として残り、その後に削除されるので、戻せるのは更新後の最初の起動の間です。パッケージマネージャーがインストールを担う場合、戻す操作は表にあるコマンドで、パネルがそれを表示または実行します。戻すことで変わるのは GitPoulpi 自身のファイルでありリポジトリではないため、git の元に戻す履歴には含まれません。

## 検証されるもの、拒否されるもの

何かを置き換える前に、GitPoulpi はアーカイブと、その `.minisig` 署名、`.sha256` をダウンロードします。まず、GitPoulpi に組み込まれたプロジェクトのリリース鍵で署名を検証し、署名の信頼済みコメントがこのアーカイブとこのバージョンを指している必要があります。次にハッシュを確認します。次のものは拒否されます：`.minisig` のないリリース（リリースが署名されるようになる前に公開された古いリリースは、更新プログラム経由ではインストールできません。そのバージョンへの固定や戻しも同様です）、別の鍵による署名、別のファイルや別のバージョンに対する署名、`.sha256` のないリリース、一致しないハッシュ、このプラットフォーム用の名前（`gitpoulpi-<version>-<target>.<zip|tar.gz>`）ではないアーカイブ、マーカーが別のバージョンやプラットフォームを指しているアーカイブ、そして GitHub のリリースホスト（すべてのリダイレクト先が対象）または管理者が設定したミラー以外へのダウンロードリンクです。入れ替えは全部成功するか何も行われないかのどちらかです。別のプログラムが実行ファイルのどれかを使用中の場合、GitPoulpi はそのファイル名を示し、何も変更せず、ダウンロードしたものを残して再試行できるようにします。Windows では、全ユーザー向けの更新は昇格したステップで再検証されます。このステップが `.minisig` と `.sha256` を自分でダウンロードして両方をもう一度確認するため、その間にユーザーのダウンロードフォルダーで差し替えられたファイルは拒否されます。パッケージマネージャー（Chocolatey、winget、Scoop、Homebrew、apt、AUR）は自分でパッケージを検証します。そこでは GitPoulpi は何もダウンロードしません。

## セキュリティ通知

プロジェクトは各リリースと並べて `security.json` を公開します。セキュリティ通知の一覧で、識別子、重大度、影響を受けるバージョン（`>=1.2.0, <1.4.3` のような範囲）、修正バージョン、リンク、1 文の概要が含まれます。新しいバージョンを探す毎日の確認が、これも同じ場所から取得します。GitHub ならリポジトリのリリースページ、ミラーなら `latest.json` のあるフォルダー、公開 Chocolatey フィードなら GitHub です。通知が使われるのは、`security.json.minisig` がプロジェクトの鍵で検証できたときだけです。署名のないファイルや署名が不正なファイルは表示されません（無視されたことをアクティビティログに 1 行記録します）。

通知が実行中のバージョンを指していると、チップは赤くなり、**セキュリティ通知：このバージョンが対象**と表示されます。これはパッケージマネージャー管理のものも含め、すべてのインストールで同じです。更新パネルには、各通知の重大度、概要、修正バージョン、リンクが一覧表示されます。**通知を開く**（`a`、またはパレットの**更新: セキュリティ通知を開く**）は、最も重大な通知のリンクをブラウザーで開きます。パッケージマネージャーがインストールを担う場合、パネルには「パッケージマネージャーで更新してください。」が加わります。

更新の確認がオフ（`updates.mode = "off"`）の場合、管理者ポリシーの `check` が `none` の場合、`cargo build` で作ったビルドの場合は、何も取得されず、通知も表示されません。組織独自の NuGet フィードを使っても、GitPoulpi が GitHub に接続することはありません。その通知は、ポリシーの `download_base` ミラーからのみ取得されます。

## 管理者がロックした設定

管理者は、マシン全体のポリシーで、更新モード、チャンネル、固定バージョン、確認先、そして GitPoulpi が自分で更新してよいかどうかを設定できます。設定画面ではこれらの行に**管理者が設定しています**と表示され、パネルには管理者のメッセージが表示されます。自己更新がオフの場合、パネルはファイルを置き換えるボタンの代わりに、コマンドか注記を表示します。読み取れないポリシーファイルは安全側に倒れます：通知のみで、自己更新はしません。管理者側の説明は[エンタープライズ配布](enterprise-distribution.md#ポリシーファイルとレジストリ)にあります。

## 環境変数

`GITPOULPI_UPDATE_API` は、確認先を別の API ルートに向けます（テストで使います）。
