# 기록 다시 쓰기

기록을 다시 쓰면 이미 있는 commit이 바뀝니다. 누가 언제 썼는지, 메시지, 담고 있는
파일, 서명이 대상입니다. GitPoulpi는 **레시피**(범위와 순서가 있는 규칙 목록)와,
가운데 단계를 절대 건너뛰지 않는 세 단계로 이 일을 합니다.

1. **미리보기**는 아무것도 건드리지 않고 새 기록을 계산합니다. 개수, 규칙마다 한
   일, 옮겨질 브랜치와 tag, 바뀐 commit마다 한 행이 나옵니다.
2. **적용**은 로컬 브랜치와 tag를 새 기록으로 옮깁니다. [실행 취소 기록](undo-redo.md)의
   항목 하나이므로 **실행 취소**를 누르면 옮겨진 ref(와 체크아웃된 파일)가 모두
   원래대로 돌아옵니다.
3. **Push**(lease를 쓰는 force push)와 **영구 삭제**는 되돌릴 수 없으므로 따로,
   의도적으로 하는 단계입니다. [결과 push하기](#결과-push하기)와
   [이전 기록 삭제](#이전-기록-삭제-영구-삭제)를 참고하세요.

워크벤치, 팔레트, `gitpoulpi rewrite` 명령, MCP 도구는 같은 엔진을 쓰므로 한 곳에서
만든 미리보기를 다른 곳에서 적용할 수 있습니다. [명령줄에서](#명령줄에서)는 플래그를
나열하고, [AI로 규칙 만들기](#ai로-규칙-만들기)는 설명으로 워크벤치를 채우며,
[AI 에이전트의 제안](#ai-에이전트의-제안)은 에이전트가 여기서 할 수 있는
일과 할 수 없는 일을 설명합니다.

**규칙을 바꾸는 대상별로 나눈 목록**

| 그룹 | 규칙 | 절 |
|---|---|---|
| 작성자 | 작성자 바꾸기, 작성자 익명화, .mailmap 적용 | [작성자와 .mailmap](#작성자와-mailmap) |
| 날짜 | 날짜 이동, 시간대 변경, 허용 시간 안으로 맞추기, 커미터 날짜를 작성자 날짜로 | [날짜](#날짜) |
| 메시지 | 메시지 찾아 바꾸기, 메시지 줄 삭제, 트레일러 추가/제거, 메시지 인코딩 수정 | [메시지](#메시지) |
| 파일 내용과 경로 | 파일 내용 찾아 바꾸기, 기록에서 파일 제거, 큰 파일 제거, 경로 이동/이름 변경, 줄 끝 변환, 실행 비트 제거, 파일 인코딩 변환 | [파일과 경로](#파일과-경로) |
| LFS | LFS로 마이그레이션, LFS에서 파일 되돌리기 | [파일을 Git LFS로 옮기거나 되돌리기](#파일을-git-lfs로-옮기거나-되돌리기) |
| 서명 | 서명 제거 (적용할 때 다시 서명) | [서명](#서명) |
| 스크립트 | Lua, 셸, Python | [스크립트 규칙](#스크립트-규칙) |

**시작하기 전에**

- 미리보기는 아무것도 바꾸지 않습니다. 적용은 로컬 ref만 바꾸며 push는 하지
  않습니다.
- 다시 쓴 commit은 새 ID를 받습니다. 이전 기록을 가진 모든 사람에게 알려야 하며,
  [결과 push하기](#결과-push하기)가 안내문을 써 줍니다.
- push한 비밀 값은 이미 유출된 것입니다. **먼저 교체**하고, 그다음에 다시 쓰고,
  force push하고, 영구 삭제하세요.
- 그대로인 commit은 ID와 서명을 유지합니다.

## 워크벤치

`Ctrl+G Shift+H`(또는 팔레트의 **다시 쓰기: 기록 워크벤치**)를 누르면 Log 위에
다시 쓰기 워크벤치가 열립니다. 도구 모음 버튼은 없습니다. 고급 동작은 팔레트
(`다시 쓰기: ...` 행은 모두 해당 규칙을 이미 추가한 채로 워크벤치를 엽니다),
commit 메뉴의 **기록 다시 쓰기** 하위 메뉴(*이 commit부터 HEAD까지...*,
여러 개를 선택했다면 *선택한 commit...*, *워크벤치 열기...*), 그리고 위의
단축키 조합에 있습니다.

`Ctrl+N`은 워크벤치의 각 컨트롤(범위, 규칙, 칸, 탭, 버튼)에 배지를 표시합니다. 배지를 누르면 그 컨트롤을 클릭한 것과 같은 일을 하며, `Esc`는 배지를 없앱니다([배지](keybindings.md#배지) 참고).

![기록 다시 쓰기 작업대: 범위 표시줄, '작성자 바꾸기' 규칙 두 개의 목록과 선택한 규칙의 필드, 바뀌는 커밋 수를 알려 주는 미리보기 요약](../images/history-rewrite.png)

- **범위 표시줄:** 어떤 ref를 옮길지 정합니다 (현재 브랜치, 모든 로컬 브랜치,
  선택한 브랜치와 tag, 선택한 commit). *Tag* 체크박스도 여기 있고, *이 commit부터
  HEAD까지...*로 연 경우에는 그 commit의 부모 뒤부터 시작하는 체크박스가 더
  나옵니다.
- **규칙:** 번호가 매겨진 목록이며 순서대로 적용됩니다. 체크박스로 규칙을 켜고
  끄고, 화살표로 옮기고, 가위표로 삭제합니다 (*삭제한 규칙 복원*이나 `Ctrl+Z`로
  되살릴 수 있습니다). *규칙 추가*는 종류를 그룹별로 보여 줍니다. 없는 프로그램이
  필요한 규칙은 이유와 함께 회색으로 남습니다.
- **규칙 설정:** 텍스트 필드를 클릭하면 편집하고, 값이 여러 개인 필드를 클릭하면
  목록이 열리며, 체크박스는 뒤집힙니다.
- **미리보기**(`F5`)는 아무것도 건드리지 않고 새 기록을 계산하며 진행 표시줄을
  보여 줍니다. 탭은 다음과 같습니다. **요약**(개수, 규칙별 결과, 경고),
  **Commit**(바뀐 commit마다 한 행, 데몬에서 페이지 단위로 읽음, 필터로 변경됨,
  제거됨, push됨을 고름), **브랜치와 tag**(무엇이 옮겨지는지, 그리고 이미 push된
  보호 브랜치. 각각 체크박스가 있음), **영향**(push된 기록을 다시 쓰면 생기는
  일: lease를 쓰는 force push, 협업자, 서명), **비밀 값**, **작성자 정보**,
  **크기**(아래 참조).
- **commit의 파일:** Commit 탭의 행에서 `Enter`(또는 더블 클릭)를 누르면 내용
  규칙이 그 commit에서 바꾼 파일 목록이 열리고, 옆에 선택한 파일의 diff가
  나옵니다. 가위표, `Esc`, 바깥 클릭으로 닫습니다. 비밀 값 규칙이 제거하는 줄은
  숨깁니다.
- **적용**(`Ctrl+S` 또는 `Ctrl+Enter`)은 미리보기가 규칙과 일치할 때 사용할 수
  있습니다. 기본값이 없는 질문은 매번 묻습니다. 서명된 commit의 서명을 어떻게
  할지, 폴더를 어떻게 추출할지입니다. 결과 패널의 **실행 취소**는 옮긴 ref를
  모두 원래대로 돌려놓습니다.
- **저장 / 불러오기**는 레시피를 저장소(공유)나 나만 쓰도록 보관합니다. 비밀 값은
  저장되지 않습니다.

모든 버튼에는 키가 있습니다. 목록은 설정 > 키보드(컨텍스트 *다시 쓰기*)와
`keybindings.md` 가이드에 있습니다.

### 작성자와 .mailmap

- **작성자 바꾸기**는 이름이나 이메일(문자열 그대로 또는 정규식)로 작성자나
  커미터를 찾아 새 이름이나 이메일을 지정합니다. *적용 대상*은 작성자, 커미터,
  또는 둘 다를 고르고, *tag 작성자도 포함*을 켜면 다시 만들어지는 주석 tag도 따라
  바뀝니다. 실행에서 *지금의 나*를 고르지 않는 한 원래 커미터는 유지됩니다.
- **작성자 익명화**는 모든 작성자 정보를 번호가 붙은 자리 표시자로 바꿉니다
  (`Contributor 1`, `contributor-1@anonymous.invalid`. 두 패턴 모두 바꿀 수 있고
  번호 자리에 `{n}`을 씁니다). 한 번의 실행에서 같은 사람은 항상 같은 번호를
  받으며, *그대로 둘 대상*에 적은 작성자 정보는 바뀌지 않습니다.
- **작성자 정보 탭**(팔레트의 **다시 쓰기: 작성자 정보 Merge (.mailmap)...**도
  같음)은 여러 이름과 이메일로 commit한 사람을 **아무것도 다시 쓰지 않고**
  바로잡는 방법입니다. 범위 표시줄 범위의 모든 이름과 이메일을 각각 작성자와
  커미터로 몇 개의 commit을 썼는지와 함께 나열하고, 저장소의 `.mailmap`이 이미
  매핑한 것에는 `Name <email>(으)로 매핑됨`을 표시합니다. 같은 사람인 작성자
  정보를 선택한 뒤(`Space` 또는 클릭, *모두 선택* / *모두 선택 해제*)
  **다음으로 Merge...**(`m`)를 누르면, 어느 것을 남길지 묻고(commit이 가장 많은
  것이 맨 위) **나머지 작성자 정보마다 `.mailmap`에 한 줄씩 추가합니다**
  (`Name <email> Old Name <old@email>`. 이미 있는 줄은 반복하지 않고, 파일이
  없으면 만듭니다). 아무것도 commit하지 않으니 공유하려면 `.mailmap`을 직접
  commit하세요. Log, blame, 파일 기록에는 대표 이름이 바로 표시됩니다 (설정
  `log.use_mailmap`, 기본값 켜짐. 저장된 commit은 바뀌지 않으므로 force push할
  것이 없습니다). 상태 표시줄에 쓴 내용이 나오고 **실행 취소**(`u`)를 권합니다.
  이전 `.mailmap`을 되돌려 놓으며, 다른 동작처럼 실행 취소 기록의 항목 하나입니다.
  `r`은 목록을 다시 읽습니다.
- **다시 쓰기 대신 `.mailmap`.** 작성자 규칙이 이미 리모트에 있는 commit을
  바꾸려 하면 요약에 *.mailmap은 기록을 다시 쓰지 않고 표시만 바로잡습니다. 대신
  .mailmap을 쓸까요?*와 **.mailmap 사용** 버튼(요약에서 `m`)이 나옵니다. 작성자
  정보 탭이 열리며 규칙이 일치시키는 작성자 정보가 선택되어 있고, 규칙이 새로
  지정할 작성자 정보는 아직 어떤 commit에도 없더라도 남길 대상으로 제안됩니다.
- **`.mailmap` 규칙**(*다시 쓰기: 기록에 .mailmap 적용...* 또는
  `rewrite preview --mailmap`)은 실제로 다시 씁니다. 작성자와 커미터(선택)가
  작업 트리의 `.mailmap`에 적힌 이름이 되며, 결과는 `git log --use-mailmap`이
  보여 주는 것과 같습니다. 예를 들어 공개하기 전처럼 기록 자체에 대표 이름이
  들어 있어야 할 때 쓰세요. 다른 규칙과 똑같은 다시 쓰기입니다 (미리보기, 적용,
  force push).
- **작성자 규칙과 트레일러.** 작성자 규칙은 트레일러에 적힌 사람도 바꿀 수
  있습니다. **트레일러도 함께 변경**(`--map-trailers`)을 켜세요. 값이 정확히
  `Name <email>`이고 규칙의 *일치하는 이메일* / *일치하는 이름*과 맞는 트레일러는
  규칙이 작성자와 커미터에 하는 일과 상관없이 새 이름과 이메일로 바뀝니다. 기본값은
  꺼짐입니다. `Signed-off-by`는 누가 서명했는지를 기록한 것이므로 바꾸는 것은
  별도의 결정입니다.

### 날짜

네 가지 날짜 규칙은 작성자 날짜, 커미터 날짜, 또는 둘 다에 적용됩니다 (규칙 창의
*날짜*).

- **날짜 이동**은 모든 날짜를 일정량만큼 옮깁니다 (`+2h`, `-1d`, `90m`, `1d 2h`).
  각 commit이 작성된 시간대는 유지됩니다.
- **시간대 변경**은 날짜를 다른 UTC 오프셋으로 씁니다. *유지할 것*은 무엇이 그대로
  남는지 정합니다. **시점**(같은 순간이고 시계 표시가 달라짐) 또는 **시계 표시**
  (같은 현지 시각이고 시점이 바뀜)입니다.
- **허용 시간 안으로 맞추기**는 허용 시간(예: `Mon-Fri 18:00-23:30; Sat,Sun
  10:00-20:00`) 밖에 있는 commit을 가장 가까운 허용 시각으로, 또는 이전으로만,
  이후로만 옮깁니다 (*이동 방향*). *부모보다 앞서지 않게*는 기록의 순서를
  지키고, *시드*는 작은 무작위 편차를 재현 가능하게 합니다. 같은 기록에 같은
  시드를 쓰면 같은 날짜가 나옵니다.
- **커미터 날짜를 작성자 날짜로**는 커미터(이름, 이메일, 날짜)를 작성자의 것으로
  맞춥니다. `git commit --amend`나 rebase가 되돌려 놓은 것을 복구하는 용도입니다.

날짜도 다른 규칙과 같은 규칙입니다. 미리보기를 실행하고, **Commit** 탭(행마다 이전
날짜와 새 날짜가 나옴)을 확인한 뒤 적용하세요. commit의 ID는 날짜에 따라 정해지므로
날짜 규칙은 처음 건드린 commit 이후의 모든 commit을 바꿉니다.

### 메시지

- **메시지 찾아 바꾸기**와 **메시지 줄 삭제**는 문자열 그대로 또는 정규식(*정규식*,
  *대소문자 구분*)을 받으며, 바꿀 내용을 비우면 삭제합니다. 유효한 UTF-8이 아닌
  메시지는 이 규칙들이 절대 건드리지 않습니다. 편집하려면 먼저 **메시지 인코딩
  수정**을 실행하세요.
- **트레일러.** *트레일러 추가/제거*(팔레트의 *다시 쓰기: 트레일러 추가/제거...*,
  또는 `--trailer-add`, `--trailer-remove`, `--trailer-map`)는 메시지 끝의
  `Key: value` 줄, 즉 `git interpret-trailers`가 아는 줄(`Signed-off-by`,
  `Co-authored-by`, `Reviewed-by` 등)을 편집합니다. **동작** 드롭다운에서 *추가*
  (**트레일러** 키, **값**, **이미 있을 때**: *추가 (같은 값이 없을 때)*, *기존
  항목 대체*, *해당 commit은 그대로 두기*), *제거*(그 키의 모든 트레일러, 또는
  값에 **값에 포함된 텍스트**가 들어 있는 것만), *값 바꾸기*(**값에서 찾기**를
  **바꿀 내용**으로 바꿈. 예: `Signed-off-by`의 이전 이메일을 새 이메일로)를
  고릅니다. 키는 대소문자를 구분하지 않고 맞춥니다. 트레일러 줄만 바뀌고 메시지의
  나머지는 그대로이며, 트레일러가 아직 없는 메시지에는 빈 줄과 함께 별도의 블록이
  생깁니다. Commit 탭에는 각 변경이 `+Signed-off-by: ...` / `-Co-authored-by: ...`로
  표시됩니다. 메시지의 마지막 단락이 트레일러 블록이며(제목은 절대 아님), 본문의
  `Note: see the ticket` 같은 줄은 마지막 단락에서 다른 트레일러와 함께 있지 않는 한
  트레일러가 아닙니다.
- **메시지 속 commit ID.** **commit ID 갱신**(`--update-message-hashes`, 기본값
  꺼짐. 메시지를 편집하는 규칙의 창 맨 끝에 있음)을 켜면 메시지에 적힌 ID도 다시
  쓰기를 따라갑니다. 다시 쓴 기록의 commit 하나와 정확히 일치하는 16진수 7자 이상의
  축약 ID(`This reverts commit 1a2b3c4`, `see 1a2b3c4d5e`)는 그 commit의 새 ID로
  같은 길이만큼 잘라 바뀝니다. 여러 commit과 일치하거나, 일치하는 것이 없거나,
  다시 쓰기가 나중에 만드는 commit인 경우는 그대로 두며, 요약에 몇 개를 바꾸고
  몇 개를 남겼는지 나옵니다.
- **메시지 인코딩 수정**(*다시 쓰기: 메시지 인코딩 수정...* 또는
  `--fix-message-encoding [--fix-name-encoding]`)은 메시지를 UTF-8로 다시
  인코딩하며, 두 경우를 다룹니다.
  - `encoding` 헤더가 있는 commit(`ISO-8859-1`, `Windows-1252`, `Shift_JIS` 등
    git과 인코딩 표가 아는 모든 것)은 해석해서 UTF-8로 쓰고 헤더를 제거합니다. 어디서
    보든 같은 텍스트로 읽히고 변환이 필요 없습니다. 그 commit의 작성자와 커미터
    이름도 같은 인코딩이었으므로 함께 해석되어, commit이 반쯤 변환된 채로 남는 일은
    없습니다.
  - **깨진 글자(mojibake)**, 즉 UTF-8을 Latin-1이나 Windows-1252로 잘못 읽은 것
    (`Réécriture` 대신 `RÃ©Ã©criture`)은 **원래대로 정확히 복원될 때만** 고칩니다.
    텍스트를 다시 인코딩하면 유효한 UTF-8 바이트가 되어야 하고, 결과를 같은 방식으로
    다시 깨뜨리면 원본이 나와야 합니다. 진짜 글자 옆에 `Ã©`가 있을 뿐인 메시지나 옛
    문자 집합 밖의 문자가 있는 메시지는 통과하지 못하고 그대로 남습니다.

  *이름도 수정*(`--fix-name-encoding`)은 깨진 작성자와 커미터 이름도 같은 방식으로
  고칩니다. 판단할 수 없는 것(알 수 없는 인코딩 이름, 선언한 인코딩으로 유효하지
  않은 바이트, 아무것도 선언하지 않은 UTF-8이 아닌 메시지, 깨진 것처럼 보이지만
  증명할 수 없는 텍스트)은 **그대로 두고 개수만 셉니다**. 요약에 *메시지 n개는
  인코딩을 판단할 수 없어 그대로 두었습니다*가 나오고 `counts.encoding_left`에
  숫자가 있습니다. Commit 탭에는 각 수정이 이전 메시지와 새 메시지, 그리고
  *인코딩* 행(`ISO-8859-1`이 `UTF-8`이 됨)으로 표시됩니다.

### 파일과 경로

- **파일 내용 규칙**(*파일 내용 찾아 바꾸기*, *기록에서 파일 제거*, *큰 파일
  제거*): 입력하는 동안 값을 검사하고 필드 아래에 이유를 표시합니다 (컴파일되지
  않는 패턴, 잘못된 경로 패턴, 1바이트 미만의 크기). 크기에는 단위를 쓸 수
  있습니다 (`500 KiB`, `5 MiB`, `1 GiB`). 슬래시가 없는 경로 패턴은 어느
  깊이에서나 일치합니다. *비밀 값*은 가려진 필드에 입력하며 이번 실행에만 쓰이고
  저장되지 않습니다. 미리보기는 그 값이 있던 줄을 숨깁니다. *빈 commit*은 규칙
  때문에 비게 된 commit을 제거할지(기본값) 유지할지 정합니다. 바이너리 파일과
  크기 한도를 넘는 파일은 그대로 두며 요약 탭에 개수가 표시됩니다.
- **경로 이동.** *경로 이동/이름 변경*(팔레트의 *다시 쓰기: 경로 이동/이름 변경...*)은
  **이동 방식** 드롭다운에서 고르는 세 종류가 있습니다.
  - *경로 이름 변경*(**원래 경로**, **새 경로**. `--move-path FROM=TO`): 이전
    경로가 있던 모든 commit에서 같은 파일과 폴더가 새 경로에 나타납니다. 다른 것은
    바뀌지 않고 모든 파일이 ID를 유지합니다. 새 경로가 이미 있는 commit은 절대
    덮어쓰지 않습니다. 미리보기가 거부되며 충돌하는 commit과 경로를 나열합니다
    (비어 있는 이름을 고르거나, 기존 경로를 먼저 옮기세요). 정확한 경로만
    가능하고 와일드카드는 쓸 수 없습니다.
  - *전체를 폴더 안으로 이동*(**폴더**. `--into-subdir DIR`): 모든 commit의 모든
    경로에 접두사가 붙습니다. 이름 충돌 없이 저장소를 합칠 때 유용합니다.
  - *폴더를 루트로 추출*(**폴더**. `--extract DIR`): 그 폴더가 루트가 되고, 폴더를
    건드리지 않는 commit은 제거되며(폴더를 만든 commit은 부모가 없어짐), 더 이상
    아무것도 합치지 않는 병합은 단순화되고, 폴더의 파일이 하나도 없는 브랜치와 tag는
    삭제됩니다. 어떻게 끝낼지는 **매번** 묻습니다.
    - *새 클론으로 추출하고 새 탭에서 열기*(`--extract-mode clone`): 고른 폴더에 이
      저장소의 사본을 만들고(새 저장소는 추출한 폴더의 이름을 딴 폴더 안에 생김),
      거기서 다시 쓴 뒤 정리해서 새 기록만 담도록 합니다. 폴더가 있는 모든 로컬
      브랜치와 tag가 포함됩니다. 이 저장소는 건드리지 않습니다. 새 저장소에는
      리모트가 없습니다 (원본이 업스트림이 아님).
    - *제자리에서 추출*(`--extract-mode in-place`): 이 저장소의 기록을 다시 씁니다.
      평소처럼 미리보기, 적용, 실행 취소를 거칩니다. 폴더가 없는 브랜치는 삭제되며
      (실행 취소로 복구됨), 체크아웃한 브랜치에는 폴더가 있어야 합니다.
    - *이 저장소의 서브모듈로 추출*(`--extract-mode submodule`): 새 저장소를 클론
      방식으로 만든 다음, 현재 브랜치에 **새 commit 하나**를 만들어 폴더를 그
      서브모듈로 바꿉니다 (`.gitmodules`와 링크). 폴더는 체크아웃된 서브모듈로
      남습니다. 이 저장소의 기록은 다시 쓰지 **않으므로** 이전 commit은 폴더의
      파일을 그대로 가지고 있어 그것을 가리키는 것(tag, 다른 클론)이 깨지지
      않습니다. `.gitmodules`의 URL은 새 저장소의 로컬 경로이므로, 호스트에
      올린 뒤에는 바꾸세요 (`git config -f .gitmodules submodule.<folder>.url`).
      폴더에 편집했거나 추적하지 않는 파일이 있으면 거부됩니다. 실행 취소하면 일반
      폴더로 돌아갑니다.

    요약에는 미리보기가 새 저장소의 기록을 보여 준다는 것과 그것이 어느 폴더로
    가는지가 나옵니다. 추출 뒤에 오는 규칙(이름 변경, 제거)은 추출된 트리에
    적용되며, 클론이나 서브모듈에서는 추출이 첫 번째 경로 규칙이어야 합니다. 경로
    규칙은 내용 규칙 다음에 실행되므로 제거 glob은 원래의 경로를 가리킵니다.

#### 줄 끝, 실행 비트, 파일 인코딩

추가 메뉴의 **내용** 그룹에 있는 세 규칙입니다 (팔레트에서는 *다시 쓰기: 줄 끝
변환...*, *실행 비트 제거...*, *다시 쓰기: 파일 인코딩 변환...*). 셋 모두 **파일**
(glob. 슬래시가 없는 패턴은 어느 깊이에서나 일치하고, 비우면 모든 파일)과
**제외할 파일**을 받습니다. 범위의 모든 commit에서 glob이 가리키는 것만 바꿉니다.
바이너리 파일(처음 8 KiB에 NUL 바이트가 있는 파일)은 절대 건드리지 않으며, 요약에
*그대로 둠*으로 센 개수가 나옵니다.

- **줄 끝 변환**(`--eol lf|crlf|cr --eol-paths GLOB... [--eol-exclude GLOB...]`).
  *변환할 형식*: LF (Linux, macOS), CRLF (Windows), CR (클래식 Mac). 일치하는 텍스트
  파일의 모든 줄 끝이 그 형식이 되므로 줄 끝이 섞인 파일도 하나로 통일되고, 이미
  맞는 파일은 버전이 그대로 유지됩니다. *.gitattributes 따르기*(기본값 꺼짐,
  `--eol-follow-attributes`)는 각 commit 루트의 `.gitattributes`를 읽습니다.
  `-text`나 `binary`로 표시된 파일은 건너뛰고, `eol=lf`나 `eol=crlf`로 표시된
  파일은 고른 형식 대신 그 줄 끝을 유지합니다.
- **실행 비트 제거**(`--strip-exec GLOB... [--strip-exec-exclude GLOB...]`).
  일치하는 파일의 모드가 100755에서 100644로 바뀌며 내용은 건드리지 않습니다.
  파일 패턴이 하나 이상 필요합니다. 모든 실행 파일에서 제거하면 스크립트가
  깨집니다.
- **파일 인코딩 변환**(`--reencode TARGET [--from SOURCE] [--encoding-fallback ENC]
  --encoding-paths GLOB... [--encoding-exclude GLOB...]`). *변환할 형식*: UTF-8(기본값),
  BOM 있는 UTF-8, UTF-16 LE 또는 BE(바이트 순서 표시와 함께 기록), Windows-1252,
  ISO-8859-1. *파일 인코딩*: 기본값은 파일마다 감지합니다 (바이트 순서 표시, 없으면
  올바른 UTF-8, 그것도 아니면 *대체 인코딩*이며 바꾸지 않으면 Windows-1252). 인코딩을
  지정하면 그것을 강제하지만 잘못 고르면 텍스트가 깨집니다 (UTF-8을 Latin-1로 읽으면
  모든 악센트가 두 글자가 됨). 원본 인코딩으로 읽을 수 없거나 대상 인코딩이 담을 수
  없는 문자(ISO-8859-1의 유로 기호)가 있는 파일은 정확히 그대로 남으며 요약에 개수가
  표시됩니다.

규칙은 목록 순서대로 같은 파일에 실행됩니다. 파일을 UTF-16으로 변환한 뒤 줄 끝을
요청하면 그 파일은 건드리지 않습니다 (더 이상 평문 텍스트가 아니므로). 적용은 다른
다시 쓰기처럼 실행 취소 목록의 항목 하나입니다.

### 비밀 값 찾기

- **비밀 값 찾기:** `gitpoulpi rewrite scan-secrets`(와 MCP 도구
  `rewrite_scan_secrets`)는 기록을 한 번 읽어 토큰 접두사(GitHub, GitLab, Slack,
  AWS, Stripe, npm, Google, OpenAI, Anthropic), 개인 키, JWT, URL 속 비밀번호,
  무작위처럼 보이는 `password = value` 줄을 나열합니다. 항목마다 파일, 처음과
  마지막 commit, `ghp_****abcd` 같은 가린 미리보기를 보여 줍니다. 완전하지는
  않으며, 값 자체는 표시, 기록, 저장되지 않습니다. `--remove-finding ID`를 쓰면
  그 항목을 모든 commit에서 제거하는 규칙이 됩니다. push된 비밀 값은 이미 유출된
  것입니다. 먼저 교체한 다음 다시 쓰고, force push하고, 영구 삭제하세요.
- **비밀 값 탭**은 워크벤치에서 같은 일을 범위 표시줄의 범위에 대해 합니다.
  **비밀 값 검사**(`s`)는 검사를 작업으로 실행하고(진행 표시줄에 *검사 중*이
  표시되며 **취소**나 `Esc`로 멈춤), 발견 항목은 종류, 가린 미리보기, 파일, 같은
  값을 가진 다른 파일 수가 한 행으로 나옵니다. 목록 아래에는 처음과 마지막으로
  발견된 commit, 그리고 몇 개의 commit과 파일 버전에 들어 있는지가 표시됩니다.
  읽지 않은 바이너리 파일과 너무 큰 파일의 수, 그리고 검사가 완전하지 않다는
  안내도 나옵니다. 처음에는 모든 항목이 선택되어 있고, **기록에서 제거**(`r`)는
  선택한 항목을 값이 아니라 ID로 지정하는 규칙 하나로 만듭니다. 다른 규칙처럼
  미리보기하고 적용하세요. 다시 쓰기나 범위 변경 뒤에는 항목이 오래된 것이 되며,
  탭이 알려 주니 다시 검사하세요. 워크벤치는 비밀 값 자체를 갖고 있지 않으므로
  보여 줄 수도 없습니다.

### 무엇이 큰지 찾기

- **무엇이 큰지 찾기:** `gitpoulpi rewrite analyze [--top N]`(과 MCP 도구
  `rewrite_analyze`)는 `filter-repo --analyze`와 같은 크기 분석입니다. 경로,
  크기, 처음과 마지막 commit, HEAD에 아직 있는지를 포함한 가장 큰 파일, 가장 큰
  폴더, HEAD에서는 삭제됐지만 기록에 아직 저장된 파일, 그리고 합계를 보여
  줍니다. 크기와 경로만 읽고 파일 내용은 읽지 않으며 아무것도 바꾸지 않습니다.
- **크기 탭**은 워크벤치에서 같은 일을 합니다 (`F7` 또는 팔레트의 *기록 크기
  분석*이 탭을 열고 실행). **크기 분석**(`s`)은 작업으로 실행되며(*분석 중*,
  **취소**나 `Esc`로 멈춤), **표시**(`v`)로 목록을 고릅니다. *파일*(가장 큰 고유
  파일 버전. 각각 *HEAD에 있음*, 아직 있는 파일의 *이전 버전*, *삭제됨*으로
  표시), *폴더*(각 폴더 아래에 저장된 모든 것), *삭제됨*(HEAD에서는 사라졌지만
  기록에 남은 경로)이 있습니다. **정렬**(`o`)은 크기순, 경로순, 삭제된 것 먼저
  중에서 고릅니다. 행을 선택하면(`Space`, 모두 / 없음은 `Alt+A` / `Alt+U`) 탭이
  그 용량을 알려 주는데, 솔직하게 "최대 약"이라고 합니다. 공간은 다시 쓰기, 이전
  객체의 영구 삭제, `gc`를 한 뒤에야 돌아오기 때문입니다. **기록에서 제거**(`r`)는
  선택한 경로를 경로 규칙으로 만들고(특수 문자는 이스케이프, 이미 규칙에 있는
  경로는 중복 추가하지 않음), **... 초과 파일 모두 제거**(`b`, 파일 목록)는
  선택한 가장 작은 파일 바로 아래로 크기 규칙을 씁니다. 다른 규칙처럼
  미리보기하고 적용하세요. 목록에는 가장 큰 200행이 나오며, CLI는 더 있는 개수를
  알려 주고 `--top`으로 더 볼 수 있습니다. 다시 쓰기나 범위 변경 뒤에는 행이
  오래된 것이 되니 다시 분석하세요.

### 서명

- **서명:** 다시 쓴 commit은 서명을 유지할 수 없으므로 (서명은 이전 바이트에 한
  것입니다) 서명된 commit을 다시 쓸 때는 매번 묻습니다. *서명 제거*(먼저 개수가
  표시됨), *서명했던 commit만 다시 서명*, *commit 모두 다시 서명* 중에서 고르며
  기본값은 없습니다. 그대로인 commit은 서명을 유지합니다. 다시 서명은 서명된
  commit을 만들 때와 같은 내 설정을 씁니다. `gpg.format`(`openpgp`, `ssh`,
  `x509`), `user.signingkey`, `gpg.program` / `gpg.ssh.program` /
  `gpg.x509.program`입니다. 질문의 네 번째 행 **서명 확인**(`4`)은 더미 데이터에 한
  번 서명하고 검증합니다. 서명 한 번에 걸리는 시간과, 질문에 나온 commit 수에 맞춘
  실행 예상 시간을 알려 주고, 작동하지 않으면 그 이유(키 없음, 에이전트 잠김,
  프로그램 미설치와 설치 방법)를 알려 줍니다. 미리보기도 기록을 읽기 전에 같은
  테스트를 하고 그 이유와 함께 거부하므로, 잘못된 설정 때문에 일부만 서명된 다시
  쓰기가 남는 일은 없습니다. commit은 **미리보기 중에** 서명됩니다 (commit의 ID에
  서명이 들어 있으므로). 그래서 다시 서명하는 미리보기는 서명 시간만큼 걸리고,
  요약에 *다시 서명한 commit: n개, 소요 시간 12.5 s*가 나오며, 그때 암호 입력
  창이 열릴 수 있으니 먼저 에이전트의 잠금을 푸세요 (서명 확인이 정확히 그 일을
  합니다). **취소**는 서명과 서명 사이에서 멈추며 아무것도 남기지 않습니다. commit
  서명만 다시 만들어지며, 서명된 tag는 여전히 서명을 잃습니다.
- ***서명 제거* 규칙**(추가 메뉴의 *서명* 그룹. 팔레트의 *다시 쓰기: 서명
  제거...*. `--remove-signatures`)은 다른 변경이 없어도 범위의 모든 commit에서
  서명을 제거하며 다시 서명에 대해서는 묻지 않습니다. CLI에서는 `rewrite
  check-signing`과 `--signatures strip|resign-signed|resign-all`을 씁니다.

### 다시 쓰기 실행 취소

**실행 취소**(결과 패널의 버튼, Log에서 `Ctrl+Z`를 누르는 도구 모음의 *실행 취소*,
또는 `gitpoulpi undo`)는 다시 쓰기가 붙들어 둔 이전 commit에서 옮겨진 브랜치, tag,
노트를 모두 되돌리고, 체크아웃된 파일도 함께 되돌립니다. 다시 쓴 브랜치가 이미
업스트림에 있을 때(로컬에서 실행 취소해도 push는 취소되지 않음)와 commit하지 않은
변경이 있을 때는 먼저 묻습니다. 그 변경은 유지되며, 이전 기록이 덮어쓸 파일을
바꿨다면 실행 취소가 대신 멈춥니다 (파일은 `reset --keep`처럼 옮겨집니다). 이전
기록을 [영구 삭제](#이전-기록-삭제-영구-삭제)하면 그 다시 쓰기는 더 이상 실행
취소할 수 없으며, 기록 목록에 *영구 삭제됨*으로 표시됩니다.

## 파일을 Git LFS로 옮기거나 되돌리기

추가 메뉴의 *LFS* 그룹에 있는 두 규칙은 큰 파일이 처음부터 [Git LFS](lfs.md)에
있도록(또는 LFS에서 나오도록) 기록을 다시 씁니다. `git-lfs` 프로그램이 필요하며,
없으면 규칙이 설치 안내와 함께 회색이 되고 미리보기가 거부됩니다. `git lfs
migrate`가 아니라 자체 엔진이므로 다른 규칙과 같은 미리보기, 범위, 실행 취소,
push 보호를 쓸 수 있습니다.

- **LFS로 마이그레이션**(*다시 쓰기: 파일을 LFS로 마이그레이션...* 또는 `--lfs-import
  PATTERN`과 `--lfs-min-size BYTES`). 패턴(`*.psd`, `assets/**`. 슬래시가 없는 패턴은
  어느 깊이에서나 일치)과 일치하고 *다음 크기 이상인 파일만*에 적은 크기 이상인 (비우면
  일치하는 모든 파일) 파일은, 그 파일을 가진 모든 commit에서 LFS 포인터가 됩니다.
  내용은 적용할 때 로컬 LFS 저장소(`.git/lfs/objects`, 같은 내용은 한 번만)로 들어가고,
  포인터를 가진 다시 쓴 commit마다 루트 `.gitattributes`에 `<pattern> filter=lfs
  diff=lfs merge=lfs -text`가 추가됩니다 (없으면 만들고, 다른 줄은 건드리지 않고,
  중복하지 않음). 이미 포인터인 파일은 그대로 둡니다. 요약에 *파일 3개 (12 MiB)가
  LFS로 이동합니다. 기록할 LFS 객체: 3.*이 나오고, Commit 탭에는 commit마다 *big.psd를
  LFS로 이동*이 나열됩니다.
- **LFS에서 파일 되돌리기**(*다시 쓰기: LFS에서 파일 되돌리기...* 또는 `--lfs-export
  PATTERN`). 일치하는 포인터가 다시 실제 파일이 되고, 그 패턴의 `.gitattributes` 줄은
  제거됩니다. 객체가 로컬 LFS 저장소에 있어야 합니다. 일부가 없으면 미리보기가
  목록과 함께 거부되고, `origin`에서 가져오는 **LFS 객체 다운로드** 버튼이 나옵니다.
  그 뒤 미리보기를 다시 실행하세요. 같은 패턴으로 마이그레이션한 뒤 되돌리면 완전히
  같은 commit이 돌아옵니다.

적용한 뒤 체크아웃된 파일은 (포인터가 아닌) 실제 내용이며 **실행 취소**하면 이전
기록이 돌아옵니다. 결과 패널에는 **LFS 객체 전송**(`l`)이 있어 `LFS: Push All
Objects`와 같은 일을 합니다. 새 기록을 push할 때 객체가 없어 나중의 push가 멈추는
일이 없게 하려는 것입니다 (다시 쓴 브랜치를 그냥 push해도 적용이 설치하는 pre-push
훅이 객체를 업로드합니다). 협업자용 안내문에는 git-lfs와 `git lfs pull`이 필요하다고
적힙니다.

알아 둘 점: 적용은 저장소의 LFS 필터(`git lfs install --local`)가 없으면
설치합니다. git이 실제 파일과 포인터를 비교하는 데 필요하기 때문입니다. 루트
`.gitattributes`만 쓰고 하위 폴더의 것은 쓰지 않습니다. 패턴과 일치하지만 최소
크기보다 *작은* 파일은 일반 파일로 남지만 git이 다음 add 때 포인터로 바꾸려 하므로,
commit할 때까지 `git status`에 수정된 것으로 보입니다. 마이그레이션은 큰 파일을
스트리밍하고, 되돌리기는 한 번에 파일 하나만 메모리에 둡니다.

## 결과 push하기

다시 쓰기를 적용해도 push는 하지 않습니다. 리모트에 있던 다시 쓴 브랜치와 tag는
force push가 필요한데, push가 무턱대고 덮어쓰지는 않습니다. 각 ref는 미리볼 때
리모트가 가지고 있던 ID(지금 추적 브랜치가 가리키는 것이 아님)에 lease를 걸어
보내므로, 그 사이 동료가 push했다면 덮어쓰지 않고 그 ref만 거부되며, 서버가
허용하면 ref들을 all-or-nothing(`--atomic`) push 한 번으로 보냅니다. CLI에서는
다음과 같습니다.

```
gitpoulpi rewrite push --dry-run        # 리모트에 물어보기만 하고 보내지 않음
gitpoulpi rewrite push --yes            # 실제로 보냄
gitpoulpi rewrite note                  # 다른 사람들이 실행해야 할 것
gitpoulpi rewrite maps --out ./maps     # commit-map과 ref-map
```

보호 브랜치(설정 `rewrite.protected_branches`, 기본값 `main`, `master`,
`develop`, `release/*`)는 이름을 직접 지정하거나(`--include-protected main`) 전부
포함하지 않는 한 다시 쓸 때와 push할 때 모두 건드리지 않습니다. force push를
받아들일지는 호스트 자체의 브랜치 보호가 정하며, 거부되면 ref별로 표시됩니다.

워크벤치에서는 적용 뒤의 결과 패널이 이 모든 것을 해 줍니다.

- **다시 쓴 ref를 리모트로 보내기**에는 다시 쓰기로 옮겨진 ref 중 리모트에 있는
  것이 체크박스(`Space`)와 함께 나옵니다. 보호 브랜치는 선택 해제된 채 *보호됨*
  표시와 함께 시작하며, 하나씩 선택하거나 *모두 선택* / *모두 선택 해제*
  (`Alt+A` / `Alt+U`)를 쓰세요. **다시 쓴 브랜치 Push**(`p`)는 선택한 것을 보내고,
  결과는 ref마다 한 행입니다 (*push함*, *이미 최신*, *거부됨: 미리 본 뒤 리모트가
  바뀌었습니다*, *거부됨: 호스트가 보호 중*, *건너뜀: 보호된 브랜치*, *push하지
  않음*). 거부된 행에는 **Fetch 후 검토**(`f`)가 있습니다. 워크벤치가 닫히고
  리모트를 fetch하므로 Log에 다른 사람들이 push한 내용이 나옵니다. 아무것도
  덮어쓰지 않습니다. lease가 그들의 작업을 지켜 주며, 다시 시도하기 전에
  미리보기를 다시 실행합니다.
- **안내문 복사**(`c`)는 협업자용 안내문을 클립보드에 넣습니다. git 명령은
  번역하지 않고 그 주변은 인터페이스 언어로 씁니다.
- **commit 대응표 열기**(`m`)는 commit map과 ref map의 위치를 보여 줍니다.
  경로를 클릭하거나 `1` / `2`를 누르면 복사됩니다.

push는 되돌릴 수 없습니다. 나중에 다시 쓰기를 `undo`하더라도 내 저장소만
바뀌며, 실행 취소는 묻기 전에 그렇게 알려 줍니다. 이전 기록을 가진 모든 사람에게
안내문을 보내세요. 안내문에는 브랜치와 tag마다 이전/새 끝점과 실행할 명령(`git
fetch` 다음 `git reset --hard origin/<branch>` 또는 `git rebase --onto`)이
들어 있습니다. 두 대응표는 실행과 함께 24시간 보관되므로, GitLab의 저장소 정리나
스크립트에 필요하면 밖으로 복사해 두세요.

## 호스트가 브랜치를 보호할 때

호스트가 브랜치를 자체적으로 보호해(GitHub 브랜치 보호와 룰셋, GitLab 보호
브랜치, Azure DevOps 브랜치 정책, Bitbucket 브랜치 제한) 다시 쓰기에 필요한 force
push를 거부할 수 있습니다. 저장소가 호스트에 **연결**되어 있으면(사이드바의 pull
request 섹션, [호스트 연동](hosting-integration.md) 참고) 워크벤치가 내 토큰으로
호스트에 어떤 브랜치가 보호되는지 묻습니다.

- 그 브랜치들은 **기본적으로 다시 쓰기에서 제외**됩니다. `rewrite.protected_branches`와
  워크플로의 보호 브랜치와 똑같습니다. Refs 탭에 체크박스와 함께 나열되고 *모두
  선택* / *모두 선택 해제* 버튼이 있으며, *GitHub에서 보호됨*처럼 이유를 알려 줍니다.
- 토큰이 보호 설정을 읽지 못하면(권한 범위가 없거나 관리자가 아님) 워크벤치는
  *호스트의 보호 설정을 알 수 없음*이라고 표시하고, 호스트의 말만 믿고 보호된 것으로
  취급하지 않습니다. 이 때문에 다시 쓰기가 막히는 일은 없습니다. 연결되지 않은
  저장소에는 묻지 않습니다.

보호 브랜치가 가로막을 때(모든 브랜치가 보호되어 미리보기가 거부되었거나, 호스트가
push를 거부했을 때: *거부됨: 호스트가 보호 중*) **통과 방법** 버튼(`Alt+H`)이 세 가지
해결책을 내 공급자와 저장소의 정확한 설정 페이지와 함께 설명합니다 (링크를 선택해
`c`로 복사하거나 `o`로 엽니다). GitPoulpi는 어느 것도 대신 하지 않습니다.

1. 호스트 설정에서 **보호를 잠시 해제**하고, push한 뒤, 다시 켭니다.
2. **새 브랜치 이름으로 다시 쓴 기록을 push**한 다음, 그 브랜치를 기본 브랜치로
   지정하고(또는 이름을 바꾸고), 아무도 쓰지 않게 되면 이전 브랜치를 삭제합니다.
3. **최후의 수단으로 리모트 저장소를 삭제하고 다시 만든 뒤** 모든 것을 push합니다.
   pull / merge request와 리뷰 기록, 이슈, 포크와 이전 기록의 연결, 스타와 워처, CI
   설정과 시크릿과 변수, 웹훅과 배포 키를 잃게 됩니다.

CLI에서는 같은 설명이 `rewrite preview` / `rewrite run`의 JSON(호스트가 범위의
브랜치를 보호할 때), 거부된 `rewrite push`, `rewrite note`에 `protected_by_host`로
나옵니다. `provider`, `branches`, `ways`(각각 `steps`와 `links`), `recreate_loses`,
그리고 전체 설명인 `text`가 들어 있습니다.

## 이전 기록 삭제 (영구 삭제)

다시 쓴 뒤에도 이전 commit은 저장소에 그대로 남아 있습니다. 다시 쓰기의 실행
취소가 그것을 붙들고 있고(그래서 되돌릴 수 있는 것입니다) reflog도 마찬가지입니다.
비밀 값을 없애려고 다시 썼다면 그 비밀 값은 아직 `.git` 폴더 안에 있습니다.
영구 삭제는 이전 기록을 완전히 지웁니다.

```
gitpoulpi rewrite purge                 # 묻기만 함: 삭제되고 잃게 될 것을 나열 (종료 코드 3)
gitpoulpi rewrite purge --yes           # 실제로 삭제
```

다시 쓰기의 실행 취소용 고정 ref를 지우고, 이전 commit을 가리키는 reflog 항목을
만료시키고, `git gc --prune=now`를 실행한 다음, 이전 commit과 파일 버전이 정말
모두 사라졌는지 확인합니다. 확인 대화상자는 먼저 무엇을 잃는지 알려 줍니다.
해당 다시 쓰기(그리고 이전 commit이 필요했던 앞선 작업)는 **더 이상 실행 취소할 수
없으며**, 기록 목록에는 영구 삭제됨으로 표시되어 남습니다. 영구 삭제는 시작하면
중단할 수 없고 되돌릴 수도 없습니다. 리모트는 건드리지 않습니다.

이전 기록을 붙들고 있는 것이 하나라도 있으면 영구 삭제가 막히고 아무것도
바뀌지 않습니다. 목록에 항목마다 할 일이 나옵니다. 다시 쓰기에 포함되지 않은
브랜치나 tag, 이전 기록 위에 있는 stash(삭제하거나, 이전 기록이 남는 것을
감수하고 유지), HEAD가 이전 기록에 있는 다른 작업 트리, 아직 이전 기록을 가리키는
리모트 추적 브랜치(다시 쓴 브랜치를 push한 뒤 fetch)입니다. stash 목록과 다른
브랜치의 reflog는 건드리지 않습니다.

push된 비밀 값은 이미 유출된 것이니 **먼저 교체하세요**. 영구 삭제 뒤의 응답에는
리모트마다 호스트에서 더 필요한 일이 나옵니다. GitHub는 캐시된 화면과 pull
request ref에 이전 commit을 계속 접근 가능하게 두므로 GitHub Support에 연락하거나
저장소를 삭제하고 다시 만들어야 하고, GitLab에는 `commit-map`
(`gitpoulpi rewrite maps --out DIR`)을 받는 저장소 정리와 하우스키핑이 있으며,
Azure DevOps와 Bitbucket은 지원 요청이나 새 저장소가 필요하고, 클론이나 포크를
가진 모든 사람에게는 이전 기록이 남아 있습니다.

### 영구 삭제 화면

워크벤치에서는 다시 쓰기 결과 패널에 **이전 기록 영구 삭제...** 버튼(키 `e`)이
있고, 팔레트에는 **다시 쓰기: 이전 기록 영구 삭제...**가 있습니다 (아직 영구
삭제하지 않은 가장 최근의 다시 쓰기에 적용되며, 워크벤치를 닫은 뒤에도 됩니다).
화면에는 영구 삭제가 지우는 것과 잃게 되는 것(실행 취소가 함께 사라지는 작업.
*실행 취소도 사라짐*으로 표시된 것은 다시 쓰기가 아니지만 이전 commit이
필요했던 작업)이 나오고, 이어서 아직 이전 기록을 붙들고 있는 것이 한 행씩
나옵니다.

- 리모트 추적 브랜치: **Fetch**가 리모트에서 갱신합니다.
- stash: 한 번도 commit하지 않은 작업이므로 **삭제**는 먼저 확인을 묻습니다.
- 브랜치, tag, 작업 트리 또는 다른 ref: **이름 복사**를 누른 뒤 그것이 있는
  곳에서 처리합니다 (브랜치는 다시 쓰거나 삭제, 작업 트리는 다시 쓴 브랜치를
  체크아웃).

확인은 고칠 때마다 다시 실행되며, **다시 확인**(`r`)으로 원할 때 실행할 수
있습니다. **영구 삭제**(`p`)는 남은 것이 없을 때만 사용할 수 있습니다. 마지막
질문은 번호가 붙고 기본 선택이 없습니다 (`1`은 완전히 삭제, `2`는 모든 것을 그대로
둠). 이어서 실행되며, 화면이 지금 어느 단계인지 보여 주고 중단할 수 없다고
알려 줍니다. 결과는 이 클론에서 이전 기록이 사라졌는지, 아니면 이전 객체가 몇 개
남았는지를 알려 줍니다. 그 아래에 리모트마다 해야 할 단계가 나옵니다 (링크는
복사할 수 있음). 가위표, `Esc`, 바깥 클릭으로 화면을 닫지만 영구 삭제가 실행되는
동안은 닫히지 않습니다.

MCP에서는 `config.toml`의 `[mcp]` 표에 `allow_history_purge = true`를 지정하지
않으면 영구 삭제 도구가 없습니다.


## 스크립트 규칙

*규칙 추가 > 스크립트*(또는 팔레트의 **다시 쓰기: 스크립트 실행...**)는 Lua 스크립트
규칙을 추가하고 워크벤치 위에 편집기를 엽니다. 규칙의 *스크립트* 줄에서 `Enter`를
누르면 다시 열립니다. 편집기에는 작은 템플릿이 들어 있습니다.

- **언어**(규칙 창의 한 행): *Lua (내장)*, *셸 스크립트*, *Python*, *Lua (설치된
  것)*. 내장 Lua가 아닌 것은 모두 [외부 스크립트](#외부-스크립트-셸-python-lua)이며
  샌드박스가 없습니다. 설정에서 꺼져 있거나 인터프리터가 없는 언어는 목록에서
  회색으로 이유와 함께 표시됩니다 (고르면 무엇을 해야 하는지 알려 줌). 아직 작성하지
  않은 스크립트의 언어를 바꾸면 템플릿이 바뀝니다.
- **스크립트**는 줄 번호가 있는 텍스트 편집기입니다. 입력하는 내용이 곧바로
  규칙이 되며, 따로 확정할 것은 없습니다.
- 그 아래의 **검사** 줄에는 `확인: rewrite_commit 있음`이 나오거나, 문제가 줄 번호와
  함께 나열됩니다 (`script:3: ...`. 여백의 번호가 빨간색). 입력을 멈추고 잠시
  뒤에 실행되며, 키를 누르고 있는 동안에는 실행되지 않습니다.
- **매개변수**에는 스크립트 머리말의 `--! param` 줄마다 한 행이 있고, 필드 옆에
  레이블이 표시됩니다. 텍스트, 숫자, 또는 참/거짓 체크박스입니다. 지운 값은 머리말의
  기본값으로 돌아가며, 기본값이 없는 텍스트 매개변수는 미리보기 전에 채워야 합니다.
- **파일**(저장소 안의 경로. 시작은 `.gitpoulpi/rewrite/script.lua`)에는
  **파일에서 불러오기...**(텍스트를 교체)와 **파일로 저장...**이 있습니다.
- **선택 항목 테스트**는 Log에서 선택한 commit에, 선택한 것이 없으면 최신 20개에
  스크립트를 실행하며 아무것도 쓰지 않습니다. 표에는 commit(짧은 ID)마다 바뀔 모든
  필드가 `old -> new`로, 그리고 스크립트의 `log(...)` 줄이 나옵니다. **취소**는
  기다리기를 멈춥니다. 스크립트가 실패하면 commit과 이유가 표시됩니다.
- 가위표, 편집기 바깥 클릭, `Esc`로 닫습니다. `Tab`과 `Shift+Tab`은 편집기,
  매개변수, 파일, 버튼, 결과 사이를 옮기고 `F5`는 테스트합니다.

미리보기는 컴파일되지 않는 스크립트를 거부합니다. 미리보기 창에 줄 번호와 함께
*스크립트가 실패했습니다*가 표시되며 (commit에서 실패했다면 짧은 ID와 이유).
스크립트가 없는 빌드에서는 종류가 추가 메뉴에 회색으로 남습니다.

## AI로 스크립트 작성

AI를 켜면([AI 도우미](ai.md)) 스크립트 편집기에 `✦ AI로 작성...` 버튼이 생기고,
팔레트에는 `✦ 다시 쓰기: AI로 스크립트 작성...`이 생깁니다. 이것은 새 스크립트
규칙이 있는 워크벤치를 대화상자와 함께 엽니다. **보내기**를 누르기 전에는 아무것도
전송되지 않으며, 대화상자는 입력하는 동안 실제로 나갈 텍스트를 그대로 보여 줍니다.

- **스크립트가 무엇을 해야 하나요?** 자기 말로 적습니다: *밤에 만든 commit을 모두
  다음 날 아침으로 옮기기*, *예전 이메일을 새 이메일로 바꾸기, 2024년 이전만*.
- **commit N개의 샘플 보내기**(기본 꺼짐): 선택하면 "선택 항목 테스트"가 쓰는
  commit(Log에서 선택한 것, 없으면 최신 20개)의 작성자, 날짜, 제목이 함께 전송되어
  모델이 데이터가 어떻게 생겼는지 볼 수 있습니다. 파일 내용이나 commit 본문은
  보내지 않습니다. 체크박스를 끄면 commit 데이터는 컴퓨터 밖으로 나가지 않습니다.
- **전송되는 내용**에는 지침(고정된 스크립트 규약, 이어서 내 AI 지침)과 내 요청,
  그리고 어느 프로필이 받는지가 나옵니다. `Tab`으로 이동하고 화살표로 스크롤합니다.
- **보내기**(`Tab`으로 이동해 `Enter`). 모델이 작업하는 동안 대화상자는 기다리며
  `Esc`로 요청을 취소합니다. 실패하면 이유와 함께 대화상자가 남아 다시 시도할 수
  있습니다.

답은 직접 입력한 스크립트와 같은 데몬 검사를 거치며, 컴파일 오류는 모델에게 한 번
돌려보냅니다. 그 뒤 스크립트가 **편집기의 텍스트를 교체**하고(편집기에 시작
템플릿이 아닌 내용이 있으면 대화상자가 그렇게 알려 줌), 텍스트를 바꿀 때까지
편집기 제목에 *✦ AI가 작성함: 미리보기 전에 읽어 보세요*가 표시됩니다. 대신 테스트,
미리보기, 적용을 해 주는 일은 없습니다. 읽어 보고 **선택 항목 테스트**를 누른 다음,
다른 스크립트처럼 미리보기하세요. 스크립트는 직접 작성한 것과 같은 샌드박스에서
실행됩니다 (파일, 시계, 네트워크 없음).

명령줄에서는 `gitpoulpi ai rewrite-script "<instruction>" [--sample N]`이 스크립트와
그에 대한 `rewrite script check` 결과를 JSON으로 출력하며 아무것도 실행하지
않습니다 (여전히 컴파일되지 않으면 종료 코드 2). 설정 > AI의 *기록 다시 쓰기
스크립트* 프로필을 사용합니다.

## AI로 규칙 만들기

AI를 켜면([AI 도우미](ai.md)) 워크벤치의 저장과 불러오기 옆에 `✦ AI로 규칙 만들기...`
버튼이 생기고, `Alt+I` 키(설정 > 키보드의 *AI로 다시 쓰기 규칙 만들기*, 컨텍스트
*다시 쓰기*)도 쓸 수 있으며, 팔레트에는 `✦ 다시 쓰기: AI로 규칙 만들기...`가 생깁니다.
AI가 꺼져 있거나 AI가 없는 빌드에서는 버튼과 팔레트 행이 없습니다. 기록을 어떻게
다시 써야 하는지 자기 말로 설명하면(*내 예전 이메일 a@b.org를 c@d.org로 바꾸기*,
*전체 기록에서 secrets.txt 제거*, *내 날짜를 두 시간 옮기기*) 모델이 규칙과 설정을
제안하고, 그것이 **워크벤치를 채웁니다**. **보내기**를 누르기 전에는 아무것도
전송되지 않으며, 대화상자는 입력하는 동안 실제로 나갈 텍스트를 그대로 보여 줍니다.

- **기록을 어떻게 다시 쓸까요?** 여러 줄 필드입니다. `Enter`는 줄 바꿈,
  `Ctrl+Enter`나 `Ctrl+S`는 보내기, `Esc`와 가위표는 취소입니다.
- **범위, 브랜치와 tag 이름, 기록의 작성자도 함께 보내기**(기본 꺼짐): 선택하면
  범위 표시줄의 범위, 브랜치와 tag 이름, 그리고 Log에 보이는 최신 commit(최대 20개)의
  서로 다른 작성자(이름과 이메일)가 함께 전송되어 모델이 이메일을 정확히 쓸 수
  있습니다(명령줄의 `ai rewrite-rules --context`는 대신 최신 commit 200개를 읽습니다). 파일 내용이나 commit 메시지는 보내지 않습니다. 체크박스를 끄면 설명과
  고정된 지침만 컴퓨터 밖으로 나갑니다.
- **현재 규칙 대체**(워크벤치에 이미 규칙이 있을 때만, 기본 꺼짐): 기본적으로 새
  규칙은 기존 규칙 뒤에 추가됩니다. 선택하면 기존 규칙을 대체합니다 (답에 적힌 범위와
  설정은 어느 쪽이든 적용됩니다).
- **전송되는 내용**에는 지침(규칙 어휘, 이어서 내 AI 지침)과 내 요청, 그리고 어느
  프로필이 받는지가 나옵니다. `Tab`으로 이동하고 화살표로 스크롤합니다.

모델은 이 페이지의 모든 규칙 종류를 쓸 수 있지만 **스크립트**(코드이므로 *AI로
스크립트 작성*이 검토할 수 있게 스크립트를 보여 줌)와 *파일 내용 찾아 바꾸기*의 비밀
값 형식(비밀 값은 모델에 절대 넘기지 않으므로 비밀 값 탭을 쓰세요)은 예외입니다.
범위는 현재 브랜치, 모든 로컬 브랜치와 tag, 또는 실제로 있는 브랜치와 tag의 이름으로
정할 수 있고, *Tag*, *커미터*, *빈 commit*, *메시지 속 축약 ID* 옵션도 정할 수
있습니다. 워크벤치가 표현할 수 없는 것(*3월부터* 같은 날짜 제한, commit 범위)은
추측하지 않고 모델이 메모로 알려 줍니다. 서명을 어떻게 할지는 모델이 정하지 않으며,
적용할 때 묻습니다.

**AI는 규칙과 설정만 준비합니다.** 미리보기, 적용, 실행은 절대 하지 않습니다. 답은
불러온 레시피처럼 워크벤치에 복사되고, 화면의 미리보기는 최신이 아니게 되며,
미리보기와 적용(그 질문과 확인 포함)은 언제나처럼 직접 합니다. 각 규칙은 편집기와
엔진이 쓰는 검사로 하나씩 해석하고 검사하며, 통과하지 못한 규칙은 제외됩니다.
제외된 것이 있거나 모델이 메모를 남겼다면 규칙이 들어간 뒤 목록이 표시되고
(*제외됨 (유효한 규칙은 유지됨)*, 각 항목에 위치, 이름, 이유), `Enter`나 `Esc`로
닫습니다. 규칙을 읽고 편집한 다음 미리보기하세요.

명령줄에서는 `gitpoulpi ai rewrite-rules "<description>" [--context]`가 제안을
JSON(`rewrite preview --recipe-json`이 읽는 `recipe`, `problems`, `notes`,
`applied: false`)으로 출력하며 아무것도 실행하지 않습니다 (제외된 것이 있으면 종료
코드 2). MCP 도구는 `ai_rewrite_rules`입니다. 설정 > AI의 *기록 다시 쓰기 규칙*
프로필을 사용합니다.

## Lua 스크립트

스크립트 규칙은 모든 commit에서 내 함수를 실행합니다. 샌드박스 안의 평범한 Lua
5.4이며 파일, 시계, 프로세스, 모듈, `pcall`이 없습니다. 같은 기록에 같은
스크립트를 실행하면 항상 같은 결과가 나오고, 호출이 1천만 개 명령어, 64 MiB,
5초를 넘으면 commit을 알려 주는 오류와 함께 멈춥니다.

```lua
--! name: Replace an email
--! param old_email: text "Email to replace"
--! param new_email: text "New email"
function rewrite_commit(c, ctx)
  if c.author.email == ctx.params.old_email then
    return { author = { email = ctx.params.new_email } }
  end
end
```

`c`에는 `id`, `parents`, `tree`, `author`와 `committer`(`name`, `email`, `time`,
`offset_minutes`), `message`, `signed`가 들어 있습니다. `ctx`에는 `index`,
`total`, `params`, `state`(`state = {...}`를 반환하면 다음 commit으로 데이터를
넘김), `window.before` / `window.after`(`--! window: N`으로 지정)가 들어
있습니다. 바뀌는 것만 반환하세요: `author`, `committer`, `message`. 도우미:
`regex_replace`, `regex_match`, `stable_hash`, `rand`, `weekday`, `hour`, `log`, 그리고
메시지용으로 `trailers(message)`(`{key, value}`의 목록),
`set_trailer(message, key, value)`(그 키의 트레일러를 교체하며, 네 번째 인자 `"add"`나
`"skip"`으로 동작을 바꿈), `remove_trailer(message, key)`, `at("2024-03-05
18:30", offset_minutes)`(오프셋 기준의 날짜를 Unix 시간으로)이 있습니다.

명령줄에서는 `gitpoulpi rewrite script check my.lua`가 스크립트를 컴파일하고,
`gitpoulpi rewrite script test my.lua --commit HEAD --param old_email=a@b`가
아무것도 쓰지 않고 무엇이 바뀔지 보여 주며,
`gitpoulpi rewrite preview --script my.lua --script-param old_email=a@b`가
전체 다시 쓰기를 계획합니다.


## 외부 스크립트 (셸, Python, Lua)

Lua 스크립트와 같은 규약이지만 내 컴퓨터의 프로그램이 실행합니다. *셸
스크립트*(bash 또는 sh. Windows에서는 PowerShell이나 모든 `.ps1`), *Python*,
*Lua (설치된 것)*(내장이 아닌 내가 설치한 `lua`. JSON 라이브러리가 없으므로
템플릿은 패턴으로 줄을 읽음)입니다. **샌드박스가 없습니다. 외부 스크립트는 내
권한으로 실행되어** 내가 읽거나 바꿀 수 있는 모든 것에 접근할 수 있습니다. 규칙
창과 편집기 제목이 그렇게 알려 줍니다.

동작 방식: GitPoulpi가 실행마다 스크립트를 한 번 시작하고, 표준 입력으로 한 줄에
JSON 요청 하나(commit의 필드, `params`, 지난 답이 돌려준 `state`)를 보냅니다.
스크립트는 표준 출력으로 JSON 한 줄로 답하며, 필드는 Lua 스크립트가 반환하는 것과
같고(`author`, `committer`, `message`, `state`, `log`), 포기하려면
`{"error": "text"}`를 보냅니다. 진단 정보는 표준 오류로 출력하세요. commit의 `log`
줄로 표시됩니다. 머리말 줄은 셸과 Python에서는 `#!`로(`#! name: ...`,
`#! param old: text "Old"`. shebang 줄은 그대로 shebang), Lua에서는 `--!`로
시작합니다.

```sh
#!/bin/sh
#! name: Uppercase author names
while IFS= read -r line; do
  name=$(printf '%s' "$line" | sed -n 's/.*"author":{[^}]*"name":"\([^"]*\)".*/\1/p' | tr 'a-z' 'A-Z')
  printf '{"author":{"name":"%s"}}\n' "$name"
done
```

**스크립트가 받는 것.** `PATH`, `HOME` / `USERPROFILE`, `SYSTEMROOT`, `TEMP` /
`TMP`, `LANG`을 뺀 빈 환경, 작업 폴더로 쓰는 새 임시 폴더(스크립트 자신의 사본이
들어 있음), 저장소 경로는 받지 않습니다. **시간 제한:** 답마다
`rewrite.script_timeout_ms`(5000), 전체 실행에 `rewrite.script_total_timeout_s`
(3600). 초과하거나, 충돌하거나, JSON이 아닌 것을 출력하거나, 작업이 취소되면
GitPoulpi가 스크립트와 그것이 시작한 모든 것을 종료하고, 다시 쓰기는 commit과
이유를 알리며 멈춥니다. 아무것도 옮겨지지 않은 상태입니다.

**어떤 언어를 쓸 수 있는가.** `config.toml`의 `rewrite.external_scripts`가
나열합니다. 기본값은 `["shell"]`이고 `"python"`과 `"lua"`는 `config.toml`에 직접
추가합니다 (`[rewrite]`, `external_scripts = ["shell", "python"]`. 목록은
`gitpoulpi config set`으로 설정할 수 없음). 목록에 없는 언어는 워크벤치에서
회색이 되고 CLI와 MCP가 거부하며(`scripts_disabled`), 목록에 있어도 인터프리터를
찾지 못하면 설치 안내와 함께 회색이 됩니다(`tool_missing`).

**신뢰.** 언어가 켜져 있어도 스크립트는 정확히 그 텍스트를 신뢰한 뒤에만
실행됩니다. 워크벤치에서 직접 입력한 스크립트는 내 것이라 바로 실행되지만, 공유
레시피나 저장소의 파일에서 온 스크립트는 그렇지 않습니다. 미리보기와 *선택 항목
테스트*가 멈추고 *이 스크립트를 신뢰할까요?*를 번호가 붙은 두 가지 답으로 묻습니다
(기본 선택 없음. `1`은 신뢰하고 계속, `2`는 신뢰하지 않음, `Esc`는 그대로 둠).
신뢰하면 이 저장소에 텍스트의 SHA-256이 기억되므로 스크립트가 바뀌면 다시 묻고,
클론한 저장소가 저절로 내 컴퓨터에서 코드를 실행할 수는 없습니다. 명령줄에서는
파일을 읽은 뒤 `gitpoulpi rewrite script trust FILE`을 실행하세요 (`preview`,
`run`, `script check`, `script test`의 `--trust`는 신뢰하고 이어서 진행). MCP의
에이전트는 아무것도 신뢰할 수 없으며, 내가 이전에 신뢰한 스크립트만 실행할 수
있습니다.

**검사.** 편집기 아래 검사 줄은 신뢰하지 않는 스크립트에 *아직 신뢰하지 않음*을
표시합니다(아무것도 시작하지 않음). 신뢰하는 스크립트는 GitPoulpi가 가짜
commit(`"dry_run": true`)으로 한 번 시작해 답이 규약을 따르는지 확인합니다.
`gitpoulpi rewrite script check FILE`도 같은 일을 하고 `trust`, `hash`,
`interpreter`를 보고합니다.


## 명령줄에서

`gitpoulpi rewrite`(와 같은 이름의 MCP 도구)는 스크립트와 에이전트를 위해 같은
엔진을 실행합니다. **레시피**는 워크벤치가 저장하는 TOML 또는 JSON 파일이며
(`--recipe FILE`, 표준 입력은 `-`), 플래그는 레시피 자체의 규칙 뒤에 규칙을
더합니다.

```
gitpoulpi rewrite preview --recipe fix.toml --all     # 계획만 세우고 아무것도 바꾸지 않음
gitpoulpi rewrite apply --run ID --digest D           # 검토한 계획을 실행
gitpoulpi rewrite run --fix-message-encoding --signatures strip --yes
gitpoulpi undo                                        # 모든 것을 되돌림
```

- 플래그로 쓰는 규칙: `--set-name` / `--set-email`과 `--match-email`(작성자),
  `--mailmap`, `--shift-dates`, `--replace-message FIND=WITH`, `--trailer-add`,
  `--trailer-remove`, `--trailer-map`, `--fix-message-encoding`
  (`--fix-name-encoding`), `--remove-path`, `--remove-blobs-over`,
  `--replace-content`, `--eol`(`--eol-paths`), `--strip-exec`, `--reencode`
  (`--encoding-paths`), `--move-path`, `--into-subdir`, `--extract`,
  `--lfs-import`, `--lfs-export`, `--script`, `--remove-signatures`,
  `--remove-finding`. 범위는 현재 브랜치, `--all-local`, 또는 `--ref R`(여러 번
  지정 가능)이며 `--since REV`부터입니다.
- **기본값이 없는 질문**은 플래그입니다. 서명된 commit이 바뀔 때는 `--signatures
  strip|resign-signed|resign-all`, 추출에는 `--extract-mode`입니다. 이것들이
  없으면 응답은 거부 또는 `needs_choice`(종료 코드 3)이며 추측하지 않습니다.
- **종료 코드:** 0 완료, 1 오류(읽을 수 없는 레시피, 잘못된 플래그), 2 이유와 함께
  거부(`stale`, `signature_choice_needed`, `dirty_paths_touched`, `empty_scope`
  등), 3 답해야 할 질문 또는 `--yes`가 필요한 push된 ref.
- `preview`는 계획을 저장소에 보관하므로 `apply`는 나중의 명령, 데몬을 다시 시작한
  뒤, 다른 프런트엔드에서도 동작합니다. 다이제스트와 더 이상 맞지 않는 계획은
  `stale`입니다.

[CLI 참조](cli-reference.md)에 모든 플래그가 있고, [MCP와 에이전트](mcp-and-agents.md)는
에이전트가 쓸 수 있는 도구를 설명합니다 (영구 삭제 도구는 켜지 않으면 없고,
에이전트는 스크립트를 신뢰할 수 없습니다).

## AI 에이전트의 제안

에이전트는 다시 쓰기를 **제안**할 수는 있지만 실행할 수는 없습니다. `gitpoulpi ui
propose rewrite --recipe FILE|-`(MCP 도구 `ui_propose_rewrite`. `[mcp]
allow_ui_propose = true`로 켜기 전에는 꺼짐)은 실행 중인 내 창에서 워크벤치를 열어
레시피의 규칙을 목록에 미리 채우고 보라색 배너 *✦ <agent>이(가) 제안함: 기록 다시
쓰기 (규칙 3개) · Ctrl+Enter 수락 · Esc 거부*를 표시합니다.

- **아무것도 실행되지 않습니다.** 미리보기, 적용, push, 영구 삭제 모두 없으며,
  제안은 규칙만 채웁니다. 규칙을 읽고, 원하면 편집하고, **미리보기**를 한 뒤 내 키로
  직접 적용합니다. 워크벤치를 닫으면 제안이 거부됩니다.
- **에이전트가 넣을 수 없는 것:** 스크립트(미리볼 때 실행되므로), 50개를 넘는 규칙,
  비밀 값(보내기 전에 레시피에서 제거됨). 그런 제안은 이유와 함께 거부됩니다.
- 에이전트는 `ui state`에서 결과를 읽을 수 있습니다 (제안대로 규칙을 적용했으면
  `accepted`, 먼저 바꿨으면 `accepted_edited`, 닫았으면 `rejected`). 제안은 한 번에
  하나이며, 내 다른 대화상자가 열려 있는 동안에는 거부됩니다.

## 도구

기록 다시 쓰기의 대부분은 Git 외에 아무것도 필요 없습니다. 작성자와 커미터
바꾸기, `.mailmap` 적용, 익명화, 날짜 이동과 허용 시간 맞추기, 메시지와
트레일러 다시 쓰기, 내용 바꾸기, 경로나 큰 blob 제거, 경로 이동은 모두
GitPoulpi 안에서 실행됩니다.

**Lua 스크립트는 내장되어 있습니다.** 인터프리터가 GitPoulpi에 들어 있으므로 Lua
스크립트에는 별도 도구도 설정도 필요 없습니다. 셸, Python, 설치된 Lua 스크립트에는
인터프리터가 필요하며(아래 표 참조) [외부 스크립트](#외부-스크립트-셸-python-lua)에
설명되어 있습니다.

일부 기능은 외부 프로그램을 씁니다. GitPoulpi가 그 프로그램을 확인합니다
(`PATH`에서 찾고, Windows에서는 `PATHEXT`와 Git for Windows 자체의 `usr/bin`도
확인하며, 2초 안에 `--version`에 답해야 합니다). 결과는 1분 동안 캐시되고
"다시 확인"을 누르면 다시 확인합니다. 없는 프로그램이 필요한 규칙은 목록에
회색으로 남아 이유와 설치 방법을 보여 주고, 미리보기는 아무것도 실행하기 전에
거부합니다.

| 기능 | 도구 | 참고 |
|---|---|---|
| commit 다시 서명 | `gpg`(OpenPGP), `ssh-keygen`(`gpg.format = ssh`) 또는 `gpgsm`(`gpg.format = x509`) | SSH와 X.509 서명에는 `user.signingkey`도 필요합니다. `gpg.program`, `gpg.ssh.program`, `gpg.x509.program`을 따릅니다. |
| LFS 마이그레이션(LFS 규칙 둘) | `git-lfs` 3.0 이상 | LFS 창과 같은 확인입니다. |
| Python 스크립트 | `python` 3.8 이상 (Windows에서는 `py -3`) | 기본적으로 꺼져 있습니다. `rewrite.external_scripts`에 `"python"`을 추가하세요. |
| Lua (설치된 것) 스크립트 | `lua5.4`, `lua54`, `lua` 또는 `luajit` | 기본적으로 꺼져 있습니다. `rewrite.external_scripts`에 `"lua"`를 추가하세요. |
| 셸 스크립트 | `bash`, `pwsh`(PowerShell) 또는 `sh` | 기본적으로 켜져 있습니다(`"shell"`). PowerShell 스크립트(`.ps1` 파일, `pwsh` shebang, Windows의 모든 셸 스크립트)는 `pwsh` 또는 `powershell`이 필요하고, POSIX 스크립트는 `bash` 또는 `sh`가 필요합니다 (Windows에서는 Git for Windows가 제공). |

설치 안내 (Windows 먼저):

- Windows: Git for Windows에 `gpg`, `ssh-keygen`, `bash`, `sh`, Git LFS가
  들어 있습니다. 없다면 `winget install GnuPG.GnuPG`, 설정 > 선택적 기능 >
  OpenSSH 클라이언트, `winget install GitHub.GitLFS`,
  `winget install Python.Python.3.12`, `winget install DEVCOM.Lua`,
  `winget install Microsoft.PowerShell`.
- Linux: 배포판 패키지(`gnupg`, `openssh`, `git-lfs`, `python3`, `lua5.4`, `bash`,
  `powershell`).
- macOS: `brew install gnupg git-lfs python lua powershell`. `ssh-keygen`과 `sh`는
  내장되어 있습니다.
