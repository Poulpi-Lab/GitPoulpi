# 실행 취소와 다시 실행

**언제든 되돌아갈 수 있습니다.** GitPoulpi가 저장소에 가하는 모든 변경은 기록되며(기본값은 최대 100개 작업, `general.undo_depth`), 다른 프로그램이 한 이동을 포함해 브랜치가 거쳐 간 모든 위치도 기록됩니다. 실수를 했다면 다음 중 하나로 작업을 되찾을 수 있습니다.

| 하려는 일 | 사용할 것 |
|---|---|
| 마지막 일 되돌리기 | `Ctrl+Z`(다시 실행: `Ctrl+Y` 또는 `Ctrl+Shift+Z`) 또는 도구 모음의 **실행 취소**와 **다시 실행** 버튼 |
| 여러 일을 한꺼번에, 또는 오래전의 일 하나를 되돌리기 | **실행 취소 기록**(`Alt+Z`, 실행 취소 옆의 화살표, `편집: 실행 취소 기록...`) |
| 여러 작업 전에 제거한 브랜치, tag, stash, 파일, hunk를 **그 뒤에 한 일을 되돌리지 않고** 되찾기 | 실행 취소 기록의 **이것만 복원** |
| 다른 프로그램이 옮겼더라도 브랜치를 원래 위치로 되돌리기 | 브랜치의 **Reflog**(ref 메뉴의 `Reflog...`) |
| 어떤 브랜치에서도 닿지 않는 commit 찾기 | **잃어버린 작업**(`편집: 잃어버린 Commits 복구...`) |
| 셸이나 **AI 에이전트**가 브랜치, tag, stash, HEAD에 한 일 되돌리기 | 같은 `Ctrl+Z`: 그 변경도 기록에 있으며 **외부**로 표시됩니다([GitPoulpi 밖에서 한 변경](#gitpoulpi-밖에서-한-변경) 참고) |

무언가를 파괴하면서 실행 취소할 수 있는 모든 동작(버리기, 파일 삭제, 브랜치나 tag 삭제, hard reset, stash drop, 리모트 제거) 뒤에는 상태 표시줄이 "버리기 완료 - 실행 취소는 Ctrl+Z"처럼 알려 줍니다. 키는 지정해 둔 대로 표시됩니다. 실행 취소 툴팁에는 몇 개의 작업까지 되돌아갈 수 있는지 표시됩니다.

`Ctrl+Z`는 GitPoulpi가 저장소에 대해 마지막으로 한 일을 되돌립니다. `Ctrl+Y`(또는 `Ctrl+Shift+Z`)는 다시 적용합니다. 도구 모음에는 **실행 취소**와 **다시 실행** 버튼이 있고, 팔레트에는 `편집: 실행 취소`와 `편집: 다시 실행`이 있으며, 각 버튼의 툴팁에는 무엇을 되돌릴지 표시됩니다("실행 취소: Commit \"fix typo\" (a81b9e4)").

![모든 변경 사항 스테이징 후의 도구 모음: 실행 취소 버튼이 켜져 있고 툴팁에 되돌릴 작업이 표시됨](../images/undo-toolbar.png)

다시 실행은 작업을 다시 실행하지 않습니다. 기록해 둔 상태를 복원하므로, 다시 실행한 commit은 id와 타임스탬프까지 똑같은 바로 그 commit입니다.

텍스트 필드가 키보드를 쥐고 있는 동안(commit 메시지, 필터 상자, 자체 텍스트 실행 취소를 가진 편집기)에는 `Ctrl+Z`가 동작하지 않습니다.

## 실행 취소 기록

`Alt+Z`(다시 지정 가능), 실행 취소 버튼 옆의 화살표 또는 `편집: 실행 취소 기록...`은 기록된 모든 작업을 최신순으로 나열한 패널을 엽니다. 작업 종류를 나타내는 아이콘(commit, 브랜치, tag, stash, reset, merge 등, 버리기, 스테이징, 설정, 외부 변경), 무엇을 했는지(사용 중인 언어로), 얼마 전인지, 상태(**단독 복원 가능**, 이유가 붙은 **차단됨**, 다시 실행할 수 있는 **취소됨**)가 표시됩니다. 항목이 여러 날에 걸쳐 있으면 날짜마다 얇은 머리글(오늘, 어제, 그다음은 날짜)이 그날의 첫 항목 앞에 나옵니다. 머리글에는 개수가 표시됩니다("작업 12개를 실행 취소할 수 있습니다(최대 100개)").

실행 취소한 작업은 최신 작업의 **위쪽**, 구분선("취소됨 - 다시 실행하면 돌아옵니다") 아래에 흐리게 표시되며, 다시 실행으로 돌아올 다음 항목이 구분선에 가장 가깝습니다. 선택은 이들이 아니라 최신 작업에서 시작합니다. 화살표 키로 이동하고(머리글과 구분선은 건너뜀), `Tab`은 세 보기를 전환하며, `Esc`는 닫습니다. 선택한 행에서는 다음을 할 수 있습니다.

- **여기까지 실행 취소**(`u`): 그 작업과 그보다 새로운 모든 작업을 최신 것부터 실행 취소합니다. 모두 나열한 확인을 한 번 거칩니다. 데몬이 위험하다고 판단한 단계는 실행 전에 다시 묻습니다.
- **이것만 복원**(`r`): 그 작업 하나가 제거한 것을 되찾고, 그 뒤에 한 일은 모두 그대로 둡니다. 삭제한 브랜치나 tag는 가졌던 commit에 돌아옵니다(이름이 이미 사용 중이면 다른 이름을 묻고, 비어 있는 이름을 채워 줍니다). 버린 stash는 stash 목록의 맨 위에 다시 놓입니다. 버리거나 삭제한 파일은 그 이후 손대지 않았다면 제자리에 다시 쓰고, 아니면 옆에 `name.restored`로 씁니다(아무것도 덮어쓰지 않습니다). 제거한 리모트, upstream, ignore 줄, attributes 줄은 다시 추가됩니다. reset, amend, rebase, merge, commit은 이전 끝에 `restore/<branch>-<sha>` 브랜치를 만듭니다. 현재 브랜치와 파일은 움직이지 않습니다. 확인 창에 실행할 내용이 그대로 표시되며, 복원은 새 작업이므로 `Ctrl+Z`로 되돌릴 수 있습니다.
- 취소된 행에서는 **여기까지 다시 실행**(`y`).
- **main을(를) Commit이(가) 남긴 위치로 복원**(`o`, 패널 밖에서는 `Alt+Shift+Z` 또는 `편집: 브랜치를 차단된 작업이 남긴 위치로 복원`): 다른 프로그램이 브랜치를 옮겨 실행 취소가 막혔을 때, 그 작업이 브랜치를 어디에 남겼는지 reflog가 기억하고 있습니다.

행을 오른쪽 클릭하거나 `.`을 누르면 같은 동작이 메뉴로 나옵니다.

![브랜치 하나를 삭제하고 commit 두 개를 만든 뒤의 실행 취소 기록: 삭제한 브랜치의 행이 선택되어 있고 단독으로 복원할 수 있음](../images/undo-history.png)

## Reflog

로컬 브랜치의 ref 메뉴에는 **Reflog...**가 있고, `편집: Reflog...`는 HEAD의 reflog를 보여 주며, 실행 취소 기록에도 그 탭이 있습니다. 브랜치가 거쳐 간 위치를 최신순으로 나열합니다. 짧은 SHA, 기록된 이유, 얼마 전인지, 누가 했는지가 표시되며 셸에서 한 이동도 포함됩니다. 선택한 위치의 메시지와 변경된 파일은 목록 옆에 표시됩니다. 동작은 **Log에서 보기**(`s`), **여기에 브랜치 만들기**(`b`), **`<branch>`을(를) 이 위치로 복원**(`r`)입니다. 복원은 실행 취소할 수 있습니다. 브랜치가 체크아웃되어 있고 덮어쓰지 않고는 옮길 수 없는 로컬 변경 사항이 있으면 드롭다운이 변경 사항을 어떻게 할지 묻습니다. **내 변경 사항 유지**, **Soft: 브랜치만 이동**, **Mixed: 이동하고 파일 변경은 유지**, **Hard: 내 변경 사항 버리기** 중에서 고릅니다. Hard는 파일의 변경 사항을 버리지만 먼저 저장하므로 `Ctrl+Z`로 되돌릴 수 있습니다(빨간색으로 알려 줍니다).

reflog는 한 번에 200개 위치씩 읽습니다. 더 긴 reflog는 저절로 이어집니다: 목록 끝 가까이로 커서를 옮기거나(또는 스크롤하면) 다음 페이지를 가져오고, 다음 페이지가 있는 동안 마지막 행에 **... 더 불러오기**가 표시됩니다. **더 불러오기**(`m`, 또는 팔레트의 `Reflog: 더 불러오기`)는 즉시 가져오며 상태 표시줄에 "불러온 위치: N"이라고 알려 줍니다. git의 reftable 형식을 쓰는 저장소도 다른 저장소와 똑같이 읽습니다.

![main의 Reflog: 브랜치가 거쳐 간 모든 위치가 최신순으로 나오고, 선택한 위치의 설명이 오른쪽에 표시됨](../images/reflog.png)

## 잃어버린 작업

`편집: 잃어버린 Commits 복구...`(Log의 commit 메뉴에도 있음)는 어떤 브랜치, tag, stash에서도 닿지 않는 commit을 찾습니다. reflog가 아직 기억하는 것(삭제한 브랜치의 commit), 실행 취소 핀만 붙들고 있는 것, 어디에도 연결되지 않은(dangling) 것입니다. 목록은 즉시 나타나고, dangling commit을 찾는 더 느린 검색은 스피너가 도는 동안 채워지며, 인터페이스를 막지 않습니다.

![잃어버린 작업: 삭제한 브랜치의 commit 두 개(reflog로 찾음)와 dangling commit](../images/lost-work.png)

**여기에 브랜치 만들기**(`b`)는 고른 이름으로 commit을 되찾고, **Cherry-pick**(`c`)은 현재 브랜치에 적용하며, **Log에서 보기**(`s`)는 아직 닿을 수 있는 commit에서 동작합니다.

## 명령 팔레트에서

세 보기의 모든 행 동작은 명령 팔레트 행으로도 있으므로 패널을 마우스 없이, 외울 글자
없이 쓸 수 있습니다. 패널이 열려 있을 때 `Ctrl+P`를 누르세요. 팔레트가 그 위에 열리고,
**실행 취소 기록:**, **Reflog:**, **잃어버린 작업:** 행이 화면에 있는 보기에서 선택한
행에 대해 동작합니다.

| 보기 | 팔레트 행 |
|---|---|
| 실행 취소 기록 | `실행 취소 기록: 여기까지 실행 취소...`, `여기까지 다시 실행...`, `이것만 복원...`, `브랜치를 원래 위치로 복원...`, `새로 고침`, `닫기` |
| Reflog | `Reflog: Log에서 보기`, `여기에 브랜치 만들기...`, `이 위치로 복원...`, `더 불러오기`, `새로 고침` |
| 잃어버린 작업 | `잃어버린 작업: Log에서 보기`, `여기에 브랜치 만들기...`, `Cherry-pick`, `다시 검사` |

해당 보기가 열려 있지 않으면 행이 (이유와 함께) 회색으로 표시됩니다. 세 가지 여는 행,
`편집: 실행 취소 기록...`, `편집: Reflog...`, `편집: 잃어버린 Commits 복구...`는 열려 있는
패널을 해당 보기로 전환하기도 합니다. 선택한 행이 할 수 없는 동작은 아무 일도 하지 않는
대신 상태 표시줄에 이유를 알려 줍니다. "이미 실행 취소한 작업입니다: 여기까지 다시 실행을
사용하세요", 항목을 단독으로 복원할 수 없는 이유, "브랜치 또는 HEAD만 되돌릴 수
있습니다" 등입니다. `...` 행은 버튼과 같은 확인 또는 이름 입력 창을 엽니다.

## 실행 취소할 수 있는 것

| 영역 | 작업 |
|---|---|
| Commit | commit, amend, 메시지 수정(reword), AI commit 작성기(모든 commit을 한 단계로) |
| 브랜치와 tag | 만들기, 삭제, 이름 바꾸기, upstream 설정 또는 해제, 추적 브랜치 만들기, tag 만들기 / 삭제 / 주석 달기, fast-forward, pull request를 브랜치로 체크아웃 |
| 이동 | 브랜치 또는 commit 체크아웃(detached HEAD 포함) |
| 기록 | merge(fast-forward 또는 merge commit), rebase(일반 및 대화형, 끝난 뒤), cherry-pick, revert, reset(soft, mixed, hard), pull의 로컬 부분 |
| 작업 변경 사항 | 스테이징과 스테이징 해제(파일, 폴더, hunk, 줄, 모두), 버리기(파일, 폴더, hunk, 줄, 파일 체크아웃), 패치 적용, **디스크에서 파일 삭제**, **무시**(파일, 확장자 또는 폴더: `.gitignore` 줄), **바이너리 또는 텍스트로 처리**(`.gitattributes` 줄) |
| Stash | push, apply, pop, drop |
| 리모트와 설정 | 리모트 추가, 제거, 이름 바꾸기, URL 또는 push URL 변경, Git LFS track 및 untrack |
| 서버 | **리모트의 브랜치나 tag 삭제**(ref의 메뉴, 팔레트, `branch delete-remote`, `tag delete-remote`, `tag delete --both`, 또는 리모트 브랜치도 삭제하는 워크플로 마무리): 아래 참고 |

merge, cherry-pick, revert가 충돌 때문에 멈춰 있는 동안에는 **저장 및 해결됨으로 표시**, 스테이징, 스테이징 해제도 실행 취소할 수 있고(각각 그 아래에 있는 것보다 먼저 되돌려짐), **Merge 중단**(또는 cherry-pick, revert 중단)도 실행 취소할 수 있습니다. 실행 취소하면 멈춰 있던 작업 전체가 돌아옵니다. 충돌(해결되지 않은 각 파일의 세 버전), 이미 해결되어 스테이징된 파일, 작업 트리의 충돌 표시, merge 메시지가 포함됩니다. 다시 실행하면 다시 중단합니다. 스테이징과 해결은 작업이 끝나면(commit 또는 중단) 더 이상 실행 취소할 수 없습니다. *스테이징 해제*와 *모두 스테이징 해제*는 아직 충돌 상태인 파일은 건드리지 않습니다. 되돌릴 스테이징 변경이 없기 때문입니다.

버리기나 hard reset으로 사라지는 모든 것은 먼저 보관되므로, 실행 취소하면 정확한 바이트 그대로 돌아옵니다. 추적되지 않은 파일, 실행 비트, 심볼릭 링크도 포함됩니다. 삭제한 stash를 실행 취소하면 같은 commit id의 같은 stash가 돌아옵니다(예전 위치가 아니라 stash 목록의 맨 위에 `stash@{0}`으로 들어갑니다). 리모트 제거를 실행 취소하면 그 리모트 추적 브랜치, `origin/HEAD` 별칭, 그 리모트를 추적하던 브랜치의 upstream 설정이 돌아옵니다.

### 리모트의 브랜치나 tag 삭제

삭제하기 전에 GitPoulpi는 서버에 그 브랜치나 tag가 지금 무엇을 가리키는지 물어 기록합니다. 리모트, 이름, 정확한 commit이며(주석 tag는 주석이 보존되도록 tag 객체 자체) 서버가 여전히 그 값을 가지고 있을 때만 삭제합니다.

**실행 취소는 다시 push합니다.** 같은 이름, 같은 commit으로, 강제하지 않고 push합니다. 다른 사람들이 보는 서버를 바꾸는 일이므로 실행 취소는 **항상 먼저 묻고** 그 사실을 알려 줍니다("이것을 실행 취소하면 origin에 브랜치 topic을 3f2a1c0...에 다시 만듭니다"). 항목의 단계에도 표시됩니다(`gitpoulpi undo --dry-run`). push와 같은 자격 증명을 사용합니다. 리모트 추적 브랜치도 함께 돌아옵니다. **다시 실행**은 같은 안전 장치로 다시 삭제합니다.

실행 취소는 다음 경우 아무것도 바꾸지 않고 거부합니다.

- 그 사이 리모트에 브랜치나 tag가 **다시 만들어졌거나** 옮겨졌을 때: 기록된 것과 다른 commit에 있으며, push하면 다른 사람의 작업을 덮어쓰게 됩니다(거부 메시지가 두 commit을 모두 알려 줍니다).
- commit(또는 tag 객체)이 **더 이상 저장소에 없을 때**(가비지 컬렉션됨): 실행 취소를 할 수 없습니다.

"로컬과 리모트에서 삭제"는 **하나의 항목**입니다. 실행 취소는 로컬과 리모트의 브랜치나 tag를 함께 복원하고, 다시 실행은 둘 다 다시 삭제합니다. 리모트 브랜치만 삭제하면 로컬 브랜치는 그대로 두며, 실행 취소도 마찬가지입니다. 리모트 브랜치도 삭제하는 워크플로 마무리는 전체를 실행 취소할 수 있습니다.

## 실행 취소할 수 없는 것과 그 이유

- **서버에 있는 대부분의 것**: push, tag push, LFS push, 잠금과 잠금 해제, pull request 열기. 이 상태는 다른 사람과 공유되며, push를 실행 취소하려면 force-push나 상대편에서의 삭제가 필요한데 GitPoulpi는 대신 그렇게 하지 않습니다. (리모트의 브랜치나 tag 삭제는 예외입니다. 실행 취소는 서버가 가지고 있던 것만 되돌려 놓고, 그 사이 무언가 바뀌었으면 거부합니다.) 이런 작업 때문에 실행 취소가 막히는 일도 없습니다.
- **Fetch**: 서버를 반영하는 리모트 추적 ref만 옮깁니다. 다음 fetch가 같은 일을 다시 합니다.
- **rebase 중단**: 실행 취소를 제공하지 않습니다(rebase는 브랜치를 옮기고 자체 상태를 유지하며, 중단 자체가 되돌리는 방법입니다). **merge, cherry-pick, revert**의 중단은 위에서 설명했듯이 기록됩니다.
- **워크트리 만들기**, **패치 파일 만들기**, clone, init, 호스팅 동작(pull request, 이슈), AI 호출: 저장소 기록의 일부가 아닙니다.
- 파일 메뉴에서 **새 빈 파일 만들기**, merge 후 `*.orig` 파일 자동 삭제, 내장 편집기에서 파일 저장은 기록되지 않습니다. **SSH 명령**(`core.sshCommand`)이나 **스파스 체크아웃** 변경도 마찬가지입니다(잃는 것은 없으며 *끄기*가 모든 파일을 되돌립니다).
- **`.git/info/exclude` 또는 `.git/info/attributes`에 쓰기**(무시 및 바이너리/텍스트 처리 목록의 "이 클론에만 적용" 선택): 이 파일들은 작업 트리 밖에 있어 기록되지 않습니다.
- **GitPoulpi 밖에서 한 작업 트리의 파일 편집**(편집기, 스크립트, 코드를 쓰는 AI 에이전트)은 기록하지 않습니다. 그 스냅샷이 없으므로 셸에서 `git reset --hard`나 `git checkout -- file`을 하면 commit하지 않은 편집은 영영 사라집니다. 셸의 작업 중 기록되는 것은 ref에 있는 것입니다. 다음 절을 참고하세요.

## GitPoulpi 밖에서 한 변경

AI 에이전트(또는 GitPoulpi 옆의 셸)와 일하면 git 작업 대부분이 창 밖에서 일어납니다. commit, 새 브랜치와 워크트리, 삭제한 브랜치, reset, rebase, stash 같은 것들입니다. GitPoulpi는 이것도 봅니다. 데몬은 마지막으로 본 ref(로컬 브랜치, tag, HEAD, stash 목록, 워크트리 목록)를 보관하고, 저장소가 바뀌었는데 GitPoulpi가 한 일이 아니면 실행 취소 기록에 **일관된 변경마다 항목 하나**를 **외부**로 표시하여 기록합니다. git이 남긴 이유(`commit: fix login`, `rebase (finish)`, `reset: moving to HEAD~1`, `checkout: moving from a to b`)와 그 일을 한 사람으로 git이 기록한 이름이 함께 붙습니다. GitPoulpi는 셸과 AI 에이전트를 구별할 수 없으며 추측하지 않습니다. 항목은 밖에서 했다는 것만 알려 줍니다.

- **연속된 작업은 항목 하나입니다.** 두 번 살펴본 사이에 만든 commit 스무 개는 첫 값에서 마지막 값까지의 항목 하나입니다. rebase는 끝날 때 기록되는 항목 하나입니다(rebase나 merge가 멈춰 있는 동안에는 아무것도 기록하지 않습니다).
- **삭제된 ref는 고정됩니다.** 사라진 브랜치, tag, stash는 무엇이 정리하기 전에 `refs/gitpoulpi/undo/` 아래에 옛 commit으로 유지됩니다. 그래서 reflog와 가비지 컬렉션 뒤에도 **이것만 복원**(또는 `Ctrl+Z`)으로 에이전트가 삭제한 브랜치를 되살릴 수 있습니다.
- **GitPoulpi가 닫혀 있는 동안.** 스냅샷은 저널 옆(`.git/gitpoulpi/refs-snapshot.json`)에 저장되므로 GitPoulpi가 실행되지 않는 동안 일어난 일은 다음 시작 때 발견되어 "GitPoulpi가 닫혀 있는 동안"으로 표시됩니다.
- **`Ctrl+Z`는 이 항목에도 다른 항목처럼 동작합니다.** ref가 되돌아가고, 삭제된 브랜치가 다시 만들어지고, drop한 stash가 다시 저장되고, 밖에서 한 checkout은 이전 브랜치를 다시 체크아웃합니다. 체크아웃된 브랜치는 `git reset --keep`처럼 되돌아갑니다. 파일이 따라가며, 로컬 변경 하나가 방해되면 **거부하고 아무것도 바꾸지 않습니다**. 다시 실행하면 다시 적용합니다. **이것만 복원**도 됩니다. 삭제된 브랜치는 돌아오고 그 뒤의 작업은 그대로 남습니다. 이동한 브랜치는 `restore/<branch>-<sha>`로 돌아옵니다.
- **상태 표시줄이 한 번 알려 줍니다.** 새 외부 항목이 도착했고 창이 앞에 있으면 "외부 변경을 기록했습니다 - Ctrl+Z로 실행 취소"라고 합니다.
- 외부 변경이 이제 최신 항목이므로, 예전의 "외부 변경에 막힘" 거부는 대부분 사라집니다. 외부 변경을 먼저 실행 취소하면 됩니다.

기록하지 않는 것은 리모트 추적 브랜치의 fetch만 하는 이동(서버를 반영하므로), GitPoulpi 자체의 숨은 ref, 브랜치 변경 없이 추가하거나 제거한 워크트리(그것이 가진 브랜치의 항목에 "worktree 추가 <path>"라고 표시되며, 실행 취소는 ref만 옮기고 워크트리를 제거하지 않음), 파일 안의 모든 것입니다. `general.journal_outside = false`(설정 > 일반, "GitPoulpi 밖에서 한 변경 기록")는 이를 끕니다. 밖에서 한 변경은 아무것도 기록되지 않고, 예전처럼 최신 항목을 막습니다.

## 실행 취소가 거부될 때

동작하기 전에 GitPoulpi는 작업이 건드린 모든 것이 작업이 남긴 상태 그대로인지 확인합니다. 그렇지 않으면 **아무것도 변경하지 않고** 무엇이 바뀌었는지 알려 줍니다.

- `main`이 Commit이 남긴 a81b9e4가 아니라 3f2a1c0에 있습니다(예: 셸에서 만든 commit).
- 파일, 인덱스, stash, 설정 섹션이 그 이후에 변경되었습니다.
- merge, rebase, cherry-pick이 진행 중입니다.
- 실행되는 동안 GitPoulpi가 중지되어 작업이 끝나지 않았습니다(항목에 *중단됨*으로 표시되고, 자동으로 실행 취소되지 않으며, `gitpoulpi undo --list`가 변경하려던 내용을 보여 주므로 직접 고칠 수 있습니다).

실행 취소는 엄격하게 후입선출입니다. 가장 최근 항목이 막혀 있으면 오래된 항목도 막힙니다. 아직 유효한 더 새로운 작업 아래의 오래된 작업을 실행 취소하는 것은 추측일 뿐이기 때문입니다. 직접 상태를 되돌려 놓으면 항목은 다시 유효해집니다. 항목이 건드린 것과 무관한 변경(다른 브랜치의 셸 commit, fetch)은 아무것도 막지 않습니다.

### 지울 수 없는 막힌 항목: 잊기

가장 최근 항목이 영구히 막혀 있으면(GitPoulpi 밖에서 저장소가 바뀌었거나 항목이 끝나지 않았을 때) 그 아래의 어느 것도 실행 취소할 수 없습니다. 이때 실행 취소 툴팁과 거부 메시지가 이를 알리고 빠져나가는 방법을 안내합니다. 팔레트의 **편집: 막힌 실행 취소 항목 잊기**(먼저 확인함) 또는 명령줄의 `gitpoulpi undo-forget`입니다. 잊기는 기록에서 그 항목 하나만 제거하며, 저장소는 건드리지 않고, 그 항목은 더 이상 실행 취소하거나 다시 실행할 수 없습니다. 그 아래 항목이 가장 최근 항목이 됩니다.

저절로 정리되는 경우가 둘 있습니다.

- 일반 git으로 끝낸 충돌 상태의 merge 또는 rebase: GitPoulpi가 다음에 저장소 상태를 읽을 때 항목이 닫힙니다.
- **저장 및 해결됨으로 표시**로 해결한 충돌 상태의 stash pop 또는 apply의 파일: 해결된 파일이 아직 스테이징되어 있고 commit되지 않은 동안에는 실행 취소가 충돌을 되돌려 놓습니다.

## 확인

실행 취소는 위험할 때만 묻습니다.

- 되돌리려는 commit(또는 merge, rebase, cherry-pick, revert)이 이미 브랜치의 upstream에 있는 경우: 실행 취소는 공개한 기록을 다시 쓰는 것이므로 결과를 force-push해야 합니다.
- commit하지 않은 변경 사항이 있는데 실행 취소가 작업 트리를 옮기는 경우: 변경 사항은 유지되지만, 그중 하나라도 다시 써야 하는 파일에 있으면 실행 취소는 아무것도 바꾸지 않고 중단됩니다.

- 항목이 리모트의 브랜치나 tag를 삭제한 경우: 실행 취소는 **서버로 다시 push**하므로(위 참고) 항상 묻고, 거기서 다시 삭제하는 다시 실행도 마찬가지입니다.

다시 실행과, ref만 옮기는 모든 실행 취소는 묻지 않습니다. 반대 방향이 키 하나 거리에 있기 때문입니다.

## 얼마나 거슬러 갈 수 있나

`general.undo_depth`(설정 > 일반)는 보관하는 작업 수입니다. 기본값은 **100**이며 `0`은 무제한입니다. 값을 낮추면 가장 오래된 항목이 즉시 사라집니다. 실행 취소한 뒤 새 작업을 시작하면, 어느 편집기에서나 그렇듯 다시 실행할 수 있던 것이 버려집니다.

기록은 워크트리별로(연결된 워크트리는 자체 기록을 가집니다) git 디렉터리(`.git/gitpoulpi/journal.json`)에 보관되므로 프로그램을 닫아도 남아 있으며 `git status`나 commit에 포함되지 않습니다.

## 끄기

`general.undo_enabled = false`(설정 > 일반, "실행 취소 사용")는 이 기능 전체를 끕니다(외부 변경의 기록도 함께). 아무것도 기록하거나 보관하지 않으므로 스테이징, 버리기, commit이 조금 더 빨라집니다. 실행 취소와 다시 실행 버튼이 사라지고 `Ctrl+Z`는 "실행 취소가 꺼져 있습니다"라고 알립니다.

**끄면 기록이 삭제됩니다**. 꺼져 있는 동안 데몬에 처음 요청이 도달할 때 기록 파일과 아래에 설명한 숨은 ref가 삭제됩니다. 다시 켜면 빈 기록에서 시작합니다.

## 저장되는 것

실행 취소가 데이터를 잃지 않도록, 항목이 필요로 할 수 있는 모든 commit, tag 객체, stash, 스냅샷은 그 항목이 기록에 있는 동안 `refs/gitpoulpi/undo/` 아래의 숨은 ref로 유지됩니다. GitPoulpi 자체 목록에서는 제외되지만 셸의 `git log --all`이나 `git for-each-ref`에는 보이며, `git push --mirror`는 이를 push합니다(대신 `git push --all`을 사용하세요). 항목이 기록에서 밀려나거나 실행 취소를 끄면 삭제됩니다. 그 밖의 것은 삭제되지 않습니다.

## 명령줄과 MCP에서

```
gitpoulpi undo [--dry-run] [--expect <id>] [--yes]
gitpoulpi redo [--dry-run] [--expect <id>] [--yes]
gitpoulpi undo --list [--all]
gitpoulpi undo-forget [--dry-run] [--redo] [--expect <id>] [--yes]
```

- `--dry-run`은 단계를 설명하고 아무것도 변경하지 않습니다.
- `--list`는 기록을 가장 최근 항목이 마지막이 되도록 출력하며(`--all`은 더 이상 다시 실행할 수는 없지만 아직 보관 중인 항목을 추가), 각 항목의 id와 상태를 보여 줍니다.
- `--expect <id>`는 그 항목이 여전히 가장 최근 항목이 아니면 *stale*로 거부합니다. 스크립트(또는 두 번째 창)가 살펴본 것과 다른 것을 실행 취소하는 일이 없습니다.
- `undo-forget`은 막힌 가장 최근 항목을 기록에서 제거합니다(`--redo`: 가장 최근 다시 실행 항목). 그 항목이 막혀 있지 않으면 거부하고, `--yes`가 없으면 종료 코드 **3**으로 끝납니다. MCP에서는 변경 작업이지만 파괴적이지는 않습니다. 저장소는 건드리지 않습니다.
- 종료 코드 **0**은 완료, **2**는 거부됨(JSON에 이유가 표시됨. 예를 들어 삭제한 리모트 브랜치가 다시 만들어졌으면 `RemoteRefMoved`), **3**은 위험하여 `--yes`가 필요함(리모트의 브랜치나 tag 삭제를 실행 취소하는 경우로, 서버로 push합니다)입니다.

뒤의 작업을 모두 실행 취소하지 않고 되돌아가기:

```
gitpoulpi undo-restore <id> [--name N] [--dry-run]      (also: undo restore <id>)
gitpoulpi reflog [<ref>] [--skip N] [--limit N]
gitpoulpi reflog-restore <ref> <oid> [--mode keep|soft|mixed|hard] [--dry-run]   (also: reflog restore ...)
gitpoulpi lost-commits [--skip N] [--limit N] [--no-deep] [--budget-ms MS]
```

- `undo --list`는 모든 항목에 대해 **이것만 복원**으로 무엇을 되찾을 수 있는지(`restore.items`), 또는 왜 아무것도 되찾을 수 없는지(`restore.not_restorable`)를 보여 주고, 누가 했는지도 알려 줍니다. `"source": "gitpoulpi"`, 또는 셸이나 AI 에이전트가 한 변경이면 `"source": "outside"`와 `outside.message`(git이 남긴 이유), `outside.committer`입니다. `undo`, `redo`, `undo-restore`는 외부 항목도 다른 항목처럼 다룹니다.
- `undo-restore <id>`는 그 항목 하나가 제거한 것(삭제한 브랜치나 tag, 버린 stash, 버리거나 삭제한 파일, 추적 브랜치와 upstream까지 포함한 제거된 리모트, ignore 줄)을 되찾고 이후의 모든 작업을 그대로 둡니다. 덮어쓰지 않습니다. 그 사이에 바뀐 파일은 보관해 둔 버전을 옆에 `<name>.restored`로 받습니다. 이미 사용 중인 브랜치 이름은 거부(종료 코드 2)되며 비어 있는 이름을 제안하므로 `--name`으로 지정하세요. reset, amend, rebase 뒤에는 이전 끝에 새 브랜치를 만들 뿐 현재 브랜치를 옮기지 않습니다. 복원은 저널 항목 하나이므로 `gitpoulpi undo`로 되돌릴 수 있습니다.
- `reflog`는 `HEAD`나 브랜치가 있었던 위치를 git이 기록한 이유와 함께 나열하며 셸에서 한 일도 포함합니다. `reflog-restore`는 브랜치(또는 `HEAD`)를 그 위치 중 하나로 옮깁니다. commit하지 않은 변경 사항이 있는 체크아웃된 브랜치에는 `--mode`가 필요합니다. 이것도 저널에 기록됩니다.
- `lost-commits`는 어떤 브랜치, tag, 리모트, stash에서도 닿지 않는 commit을 나열합니다.
- 셸에서의 이동이 가장 최근 항목을 막으면, 거부 결과에 그 항목이 기대하는 상태를 가진 reflog 위치(`reason.RefMoved.restore`)가 담기며, 이를 `reflog-restore`에 넘기면 됩니다.

위의 동작을 모든 화면에서 실행 취소할 수 있도록 명령 두 개가 있습니다. `gitpoulpi rm-file <paths>`(작업 트리에서 파일 삭제)와 `gitpoulpi ignore <pattern> [--file <path/.gitignore>]`(`.gitignore`에 줄 추가. 이미 있는 줄이면 아무 일도 일어나지 않으며, 실행 취소는 파일을 원래대로 되돌리거나 명령이 만든 파일이면 제거하고, 그 이후 파일이 편집되었으면 거부함)입니다.

MCP 서버에는 명령마다 도구가 하나씩 있으므로 `undo`, `redo`, `rm-file`, `ignore`도 도구입니다. `undo`, `redo`, `rm-file`은 파괴적으로 분류되어(`reset`과 같이 제한됨, [MCP와 에이전트](mcp-and-agents.md) 참고) `ignore`는 일반 변경 작업입니다. 기록은 저장소 안의 파일이므로, 셸의 `gitpoulpi undo`는 창이 한 일을 되돌리고 창은 스크립트가 한 일을 실행 취소할 수 있습니다.
