# Referência da CLI

`gitpoulpi` sem subcomando abre a janela; com um subcomando, é um cliente git
com suporte a scripts. Todo comando passa pelo mesmo daemon em segundo plano que
a janela, então uma alteração feita por um script aparece ao vivo em um
GitPoulpi aberto. As ferramentas MCP que um agente recebe são geradas a partir
desses mesmos comandos ([MCP e agentes](mcp-and-agents.md)). `gitpoulpi <command> --help`
mostra todas as opções.

## Opções globais

| Opção | Efeito |
|---|---|
| `--json` | Imprime o resultado como JSON. Os erros também são JSON: `{"error": "..."}` no stdout, código de saída 1. Uma operação do git que falha acrescenta `"detail": {"operation", "command", "exit_code", "stderr"}` (o comando git executado, com os segredos ocultados, o código de saída dele e o fim do seu stderr; para a biblioteca git embutida `"git2": {"class", "code", "message"}`) e uma falha que o daemon soube nomear acrescenta `"context": {"operation", "label", "args", "repo", "frontend", "request", "job"}` (a operação, o nome dela para uma pessoa, seus argumentos principais com os segredos ocultados, o repositório, quem pediu, o id da requisição e, em um fetch ou push, o número do job); as ferramentas MCP devolvem o mesmo objeto. Sem `--json` as linhas vão para o stderr. |
| `--repo <path>` | O repositório sobre o qual agir (padrão: o que contém o diretório atual, como o git). |
| `-s, --session <name>` | A sessão (daemon) com a qual conversar. Padrão: derivada da raiz do repositório, de modo que tudo o que é aberto dentro de um repositório compartilha um daemon e dois repositórios têm dois. |
| `--backend git2\|system` | Backend de um daemon que este comando inicia (um que já esteja em execução mantém o seu). |
| `--cwd-file <file>` | Onde a janela grava a pasta da aba ativa ao sair (usado por `shell-init`). |
| `-a, --add [path]`, `--no-raise` | Abre uma pasta em uma nova aba do GitPoulpi que já está aberto, em vez de iniciar outro; veja [Adicionar uma pasta à janela aberta](#adicionar-uma-pasta-à-janela-aberta). Não aceita subcomando. |
| `-l, --lang <lang>` | Idioma só do texto de `--help`: `en`, `fr`, `es`, `pt-BR`, `pt-PT`, `it`, `de`, `zh-CN`, `ja`, `ko`, `ru`, `uk`, `pl`, `cs`, `nl`, `sv`, `tr`. Veja [Ajuda traduzida](#ajuda-traduzida). |

### Adicionar uma pasta à janela aberta

`gitpoulpi --add [path]` (`-a`; `gp -a` e o alias de comando `gpa` executam o mesmo
código) abre `path` (padrão: o diretório atual, resolvido para o repositório que o contém)
em uma nova aba de um GitPoulpi que já está aberto, de modo que uma pasta em que você
entra com `cd` em um terminal não inicia uma segunda janela.

- Uma *sessão em execução* é aquela cujo daemon responde e que tem uma janela do GitPoulpi anexada. As janelas
  cujo usuário desativou **Permitir que agentes de IA controlem a visualização** não se anunciam e não são encontradas (o mesmo
  limite de `gitpoulpi launch`).
- Uma sessão em execução: ela recebe a aba (ou mostra a aba, se esse repositório já estiver aberto), sua janela
  vai para o primeiro plano quando a área de trabalho permite (Windows, WezTerm, Hyprland; `--no-raise` dispensa isso), e uma
  linha diz qual sessão a recebeu.
- Várias: elas são listadas, numeradas, com o número de abas e os nomes dos repositórios; digite o número e Enter
  (uma linha vazia ou Esc e depois Enter cancela, código de saída 130). Sem um terminal na entrada padrão, o comando falha e
  pede para passar `--session NAME`. `-s NAME` dispensa a pergunta.
- Nenhuma (ou `-s NAME` nomeia uma sessão que não está em execução): o GitPoulpi inicia normalmente neste terminal nessa
  pasta, exatamente como `gp [path]`.
- A janela aplica na hora, como uma escolha sua (sem chip de confirmação, sem marca de agente), a menos que você esteja
  digitando em um formulário ali: então a janela oferece a aba no chip da linha de status e o código de saída é 3. Uma pasta
  que não está dentro de um repositório é recusada (código de saída 1).

`--json` imprime um objeto: `{"action": "joined", "session", "repo", "already_open", "raised", "outcome": {...}}`
(`outcome` é a resposta da janela, como em `ui show`) ou `{"action": "cancelled"}`; os erros são `{"error": "..."}`.
Códigos de saída: 0 a aba está aberta, 3 oferecida no chip, 1 recusada ou com falha, 130 cancelada. Não há ferramenta MCP
para isso: um agente que quer mostrar um repositório ao usuário usa `ui show tab`.

### Ajuda traduzida

`gitpoulpi --help` está em inglês. Acrescente `-l` para ler as explicações em
outro idioma: `gitpoulpi -l fr --help`, `gitpoulpi -l de commit --help`. Só as
explicações e os títulos de seção são traduzidos. Os nomes de comandos, opções,
nomes de valores e valores possíveis não mudam, de modo que scripts e agentes
veem a mesma interface. O idioma da ajuda não é lido do ambiente: a saída só
muda quando você informa `-l`. As descrições das ferramentas MCP estão sempre em
inglês.

As revisões aceitam tudo o que o git aceita (`HEAD~2`, uma branch, uma tag, um
sha curto). Hunks e linhas são numerados como o `gitpoulpi --json diff` os
numera.

**Consultar**

| Comando | O que faz |
|---|---|
| `status` | Arquivos staged, unstaged, untracked e em conflito. |

| `log --format mermaid [--detail structure\|refs\|subjects\|full] [--orientation lr\|tb] [--fence] [--range A..B] [--limit N] [--subject-width N]` | Os commits como um script `gitGraph` do Mermaid, o mesmo que o popup [Copiar como gitGraph do Mermaid](log-and-history.md#copiando-commits-como-um-gitgraph-do-mermaid) do Log produz. `--range A..B` é `git log A..B` (um `A` sozinho significa `A..HEAD`); senão os primeiros `--limit` commits (padrão 30). | `diff [--staged] [--path P] [--name-only]` | Diff do diretório de trabalho (ou do que está em stage), como hunks e linhas; `--name-only` lista só os arquivos alterados e o estado deles. |
| `diff --from <rev> [--to <rev\|worktree>] [--name-only]` | Compara duas revisões, ou uma revisão com o diretório de trabalho (`--to` é `worktree` por padrão: alterações em stage e fora dele dos arquivos rastreados). A mesma lista da [comparação](log-and-history.md#comparando-commits) do Log. |

Não disponível via MCP. |
| `blame <path> [--at REV]` | Quem mudou cada linha. Segue renomeações de arquivo inteiro. | `file-history <path> [--at REV] [--skip N] [--limit N]` | Os commits que mudaram um arquivo, do mais recente ao mais antigo, **seguindo renomeações** (`git log --follow`). | `conflicts show <path> [--conflict N]` | Um arquivo em conflito: rótulos dos painéis, os três lados, as regiões de conflito A/B numeradas (`--json` é o documento completo). |
| `conflicts resolve <path> --side ours\|theirs\|base` | Resolve um arquivo com um dos lados (`--ours` / `--theirs` são atalhos). |
| `conflicts resolve <path> --both [--theirs-first]` | Mantém os dois lados de todo conflito (A e depois B, ou B e depois A). |
| `conflicts resolve <path> --pick 1=a,2=ba [--default a\|b]` | Uma escolha por conflito: `a` ours, `b` theirs, `ab`, `ba`, `none`. Recusado com `pick_incomplete` a menos que todo conflito tenha uma ou que `--default` seja informado. |
| `conflicts resolve <path> --content-file F\|- [--encoding L]` | Grava o texto final informado (UTF-8, ou codificado como `L`). |
| `conflicts resolve <path> --delete` | Aceita uma exclusão (conflitos de exclusão/modificação): `git rm`. |
| `conflicts resolve ... [--no-stage] [--expect base,ours,theirs]` | `--no-stage` salva sem marcar como resolvido; `--expect` é a proteção contra dados obsoletos (oids de stage, `-` para nenhum). |
| `conflicts unresolve <path>` | Volta a marcar como em conflito um arquivo resolvido durante esta operação. |
| `conflicts check` | Mesclar HEAD na branch de onde ela partiu daria conflito? `{"status": "conflicts"\|"clean"\|"no-base"\|"disabled", "head", "base_ref", "base", "base_source": "globs"\|"pull-request", "files": [...]}`. Um merge feito em memória (nada muda na árvore de trabalho, no índice nem nas refs; exige git 2.38 ou mais novo com o backend do sistema, senão `disabled`). Somente leitura; também é a ferramenta MCP `conflicts_check`. Veja [Resolver conflitos de merge](merge-conflicts.md#prevenção-de-conflitos). |
| `conflicts state` | O merge, rebase, cherry-pick ou revert em andamento (`null` quando não há). |
| `conflicts abort` | Aborta essa operação (destrutivo: descarta as resoluções feitas desde então). |
| `conflicts skip` | Pula o cherry-pick ou revert em andamento (ou o commit em que um rebase parou): HEAD, índice e árvore de trabalho voltam para HEAD. A saída para um commit que ficou vazio; um merge não tem o que pular (destrutivo, não pode ser desfeito). |
| `conflicts am-continue` | Continua o `git am` em andamento depois que você resolveu e fez stage dos arquivos do patch (`{"outcome":"Completed"}` ou `"Stopped"`). |
| `conflicts am-skip` | Pula o patch em que o `git am` parou. |
| `conflicts am-abort` | Aborta o `git am` (destrutivo: a branch volta ao que era antes do `am`). |
| `job list` | As tarefas em segundo plano do daemon, das mais antigas para as mais novas: cada fetch, push, pull, clone e transferência LFS é uma tarefa desde o momento em que é recebido (na fila, em andamento ou encerrado nos últimos 30 s). JSON: id, kind, state, phase, progress, `not_cancellable`, `error`. |
| `job cancel <id>` | Para uma tarefa. Recusado (saída 1, nada muda) depois do ponto em que parar é seguro. Ctrl+C em um comando que iniciou uma tarefa cancela essa tarefa. |
| `job wait <id> [--timeout S]` | Bloqueia até a tarefa terminar e imprime o estado final; saída 0 quando `Done`, 1 quando falhou, foi cancelada ou esgotou o tempo. |
| `index-lock show` | O `index.lock` do repositório (`null` quando não há): caminho, idade em segundos, `stale` (mais antigo que 10 s). |
| `index-lock remove` | Exclui um `index.lock` obsoleto. Recusado enquanto tiver menos de 10 s ou quando não existir. |
| `rebase-plan [<upstream>] [--root]` | Os commits que um rebase interativo reaplicaria, do mais antigo ao mais novo. |

| Comando | O que faz |
|---|---|

[--param NAME=VALUE...] [--language L] [--trust]`, `rewrite script trust FILE` (and `--script FILE --script-param NAME=VALUE [--script-language L] [--trust]` on `preview`/`run`) | Reescrita de histórico a partir de uma receita (o TOML que o painel da TUI salva, ou JSON; as opções acrescentam regras depois das da própria receita e substituem o escopo e as opções dela). `tools` lista as ferramentas externas que a reassinatura e os scripts exigem (`{tools: [...]}`). **Assinaturas**: quando commits assinados são reescritos, `--signatures` é obrigatório (`strip` as remove, `resign-signed` assina de novo só os que eram assinados, `resign-all` assina todo commit reescrito); caso contrário a prévia é recusada como `signature_choice_needed`; os commits que continuam como estão mantêm a assinatura. A reassinatura usa a configuração do próprio repositório (`gpg.format` openpgp, ssh ou x509, `user.signingkey`, `gpg.*.program`) e acontece na prévia (o id de um commit assinado inclui a assinatura): `counts.resigned` e `counts.signing_millis` do plano dizem quantos e quanto tempo levou. Uma configuração que não assina é recusada antes de tudo como `signing_failed` (ou `tool_missing`), antes de qualquer leitura. `rewrite check-signing` executa só esse teste (assina e verifica uma carga fictícia uma vez) e imprime `{format, tool, millis}`, o tempo de uma assinatura, para estimar uma execução (sai com 2 e o motivo quando falha; pode abrir um pedido de frase secreta). `--remove-signatures` adiciona a regra que remove a assinatura de todo commit do escopo, mesmo onde nada mais muda; esses commits não precisam de resposta em `--signatures`. `--fix-message-encoding` adiciona a regra que recodifica as mensagens para UTF-8: um commit com cabeçalho `encoding` (ISO-8859-1, Shift_JIS...) é decodificado e o cabeçalho sai, e UTF-8 que foi lido antes como Latin-1 ou Windows-1252 (`RÃ©Ã©criture`) só é reparado quando a ida e volta é exata; o que não dá para decidir fica como está e é contado em `counts.encoding_left`. Os nomes de um commit cujo cabeçalho sai são decodificados junto, e `--fix-name-encoding` repara também nomes corrompidos em outros lugares. `preview` monta o plano sem alterar nada e imprime `{run, digest, counts, refs, warnings, per_rule, rows, rows_total}` (os primeiros `--limit` commits alterados, padrão 50, ou `--all`) e o guarda no daemon da sessão e em disco, no diretório git do repositório (`gitpoulpi/rewrite/<run>/`): `apply --run ID --digest D` funciona em um comando posterior, após reiniciar o daemon ou a partir de outra interface, sem `daemon start`; um plano guardado que não corresponde mais ao seu digest é `stale`. Só `rows` precisa do daemon que fez a prévia (um em execução, por exemplo o da TUI ou `daemon start`), então use `preview --all` para ver todas as linhas em um único comando. As regras de identidade e de anonimização reescrevem o tagger das tags anotadas recriadas só quando a receita define `include_taggers`. `rows` percorre a execução por páginas `{run, filter, offset, total, rows}` (no máximo 200 por página). `apply` executa o plano que você revisou (seu `run` e `digest`) como UMA entrada de desfazer e imprime `{run, moved, commits_changed}`; `undo` devolve tudo. Nunca faz push: uma ref já publicada exige o seu push forçado depois. `run` faz a prévia e aplica em um só comando (sem precisar de daemon) e imprime `{plan, outcome}`. `discard` descarta uma execução (duas vezes não causa problema). As regras de trailer (`--trailer-add CHAVE=VALOR`, `--trailer-remove CHAVE`, `--trailer-map CHAVE:ANTIGO=NOVO`, repetíveis, nessa ordem depois de `--replace-message`) editam as linhas `Chave: valor` do último parágrafo de cada mensagem com a gramática do `git interpret-trailers`: `--trailer-add` ignora uma mensagem que já tem exatamente esse trailer, `--trailer-remove` leva todo trailer da chave, `--trailer-map` substitui texto literal nos valores da chave; o resto da mensagem não é tocado (uma receita também pode definir `if_exists` como `replace` ou `skip`, um padrão `find` em `remove` e padrões `regex`). `--map-trailers` (exige as opções de identidade) faz a regra de identidade ajustar também os trailers `Nome <e-mail>` que casam. `--update-message-hashes` substitui nas mensagens os ids abreviados de commit (7+ caracteres hexadecimais) pelos novos ids do mesmo tamanho quando exatamente um commit reescrito casa; `counts.message_hashes_updated` e `counts.message_hashes_left` (ambíguos, desconhecidos ou criados depois) do plano dizem o que aconteceu. As regras de conteúdo (`remove_paths`, `remove_blobs_over` e `content_replace` da receita, ou as opções `--remove-path`, `--remove-blobs-over`, `--replace-content`) reescrevem os arquivos de todos os commits: cada arquivo único é lido uma vez, arquivos binários são ignorados e contados (`counts.blobs_skipped_binary`), um commit que uma regra deixa vazio é descartado (`counts.commits_dropped`, linhas com `new: null`; `--prune-empty never` o mantém) e seus filhos passam para o pai dele, e os arquivos em checkout acompanham a nova árvore. Recusado com `dirty_paths_touched` quando um arquivo com alterações locais é um que a reescrita mudaria, `checked_out_elsewhere` quando uma branch reescrita está em checkout em outro worktree, `partial_clone` em um clone parcial. As regras de caminho (`--move-path DE=PARA`, repetível; `--into-subdir DIR`; `--extract DIR`, ou `move_paths` da receita) renomeiam um arquivo ou pasta, movem o repositório inteiro para um subdiretório ou mantêm só um subdiretório como nova raiz; elas atuam sobre trees, então cada arquivo mantém o seu id, e rodam depois das regras de conteúdo. Uma renomeação nunca sobrescreve: onde o novo caminho já existe em algum commit, a prévia é recusada como `path_collision` (saída 2), com os ids curtos dos commits e os caminhos em `refused.detail`. `--extract` é **perguntado a cada vez**: sem `--extract-mode` (`clone`, `in-place` ou `submodule`) nada é pré-visualizado e a resposta é `{"needs_choice":{choice:"extract_mode", options, prompt}}` com código de saída 3. `in-place` reescreve este repositório como qualquer regra (uma entrada de desfazer; branches e tags que não têm nada da pasta são excluídas, linhas com `refs[].new: null`; a branch em checkout precisa ter a pasta, senão `empty_scope`). `clone` e `submodule` pré-visualizam o histórico que o novo repositório terá sobre todas as branches locais e tags, nada é enviado nem protegido ali, e são aplicados com a pasta do novo repositório: `--target CAMINHO` em `run`, ou em `apply` (um `rewrite apply` de um plano assim sem `--target` é recusado como `invalid_rule`; a pasta não pode existir (ou deve estar vazia) nem ficar dentro do repositório). `clone` faz um `git clone --no-local` deste repositório ali, reescreve-o com a receita, remove o remoto, expira os reflogs e poda os objetos antigos, então ele guarda só o histórico extraído; este repositório não é tocado e nada é registrado no diário (`outcome.moved` fica vazio). `submodule` faz o mesmo e depois adiciona um commit na branch atual que troca a pasta por um submódulo do novo repositório (a URL em `.gitmodules` é o caminho local dele), o inicializa e o registra no diário (`outcome.moved` tem a branch; `undo` a move de volta e libera o submódulo); o histórico não é reescrito, então os commits antigos mantêm a pasta. Arquivos editados ou não rastreados na pasta, ou um HEAD desanexado, o recusam. Ordem quando combinadas: as regras de conteúdo (`--replace-content`, `--remove-blobs-over`, `--lfs-import`, `--lfs-export`) e `--remove-path` rodam primeiro sobre os caminhos originais, depois as regras de caminho; um padrão de LFS e um glob de remoção, portanto, nomeiam os caminhos originais, e as linhas de `.gitattributes` de uma importação são adicionadas na raiz original e depois acompanham os arquivos. **Regras de LFS** (`lfs_import { patterns, min_size }` e `lfs_export { patterns }` da receita, ou `--lfs-import PADRÃO...` com `--lfs-min-size BYTES`, e `--lfs-export PADRÃO...`) exigem o `git-lfs` (senão `tool_missing`): uma importação transforma os arquivos que casam em ponteiros da spec v1 em cada commit, grava o conteúdo no armazenamento LFS local ao aplicar (atomicamente, uma vez por conteúdo) e adiciona `<padrão> filter=lfs diff=lfs merge=lfs -text` ao `.gitattributes` da raiz de cada commit reescrito que contém um ponteiro (o resto do arquivo não é tocado); uma exportação transforma de volta em arquivos os ponteiros que casam e remove essas linhas, e é recusada como `lfs_objects_missing` (`detail`: um `<oid> <caminho>` por linha) quando os objetos não estão no armazenamento local (faça antes `lfs fetch`). `counts.lfs_blobs`, `lfs_bytes`, `lfs_objects`, `lfs_restored` e `lfs_run` do plano dizem o que acontece, as linhas listam os caminhos `lfs_imported` / `lfs_exported`, e os arquivos em checkout continuam com o conteúdo real (o apply instala os filtros LFS do repositório quando faltam). Envie os objetos depois com `lfs push --all`. **Regras de texto** (`line_endings`, `strip_exec` e `reencode` da receita, ou `--eol`, `--strip-exec`, `--reencode`): `--eol lf\|crlf\|cr --eol-paths GLOB...` dá a todo arquivo de texto que os globs nomeiam esse final de linha (finais mistos ficam uniformes; `--eol-exclude` deixa arquivos como estão; `--eol-follow-attributes` lê o `.gitattributes` da raiz de cada commit: arquivos `-text`/`binary` são ignorados e arquivos `eol=` mantêm o próprio final); `--strip-exec GLOB...` transforma o modo 100755 em 100644 nos arquivos que casam (pelo menos um glob, `--strip-exec-exclude` para poupar alguns); `--reencode utf-8\|utf-8-bom\|utf-16le\|utf-16be\|windows-1252\|iso-8859-1 --encoding-paths GLOB...` converte os arquivos de texto para essa codificação, a partir de `--from ORIGEM` ou, por padrão, detectada por arquivo (marca de ordem de bytes, UTF-8 válido, senão `--encoding-fallback`, padrão `windows-1252`). Elas rodam na etapa de conteúdo com as outras regras de conteúdo, na ordem da receita. Arquivos binários são ignorados e contados (`counts.blobs_skipped_binary`); arquivos que a codificação de origem não consegue ler ou que o destino não comporta continuam como estão e são contados em `counts.blobs_skipped_undecodable`; `counts.blobs_changed` é o número de novas versões de arquivo, e as linhas listam os caminhos alterados como `modified`. `diff` mostra o que as regras fizeram em um arquivo de um commit de uma execução visualizada (`{kind, binary, redacted, old_size, new_size, hunks}`); as linhas que uma regra de segredos remove ficam ocultas. Os scripts Lua (`--script FILE`, pode repetir, executados em ordem depois das outras regras; o arquivo é embutido na receita) chamam `rewrite_commit(c, ctx)` em cada commit e podem devolver novos `author` / `committer` (`name`, `email`, `time`, `offset_minutes`) e `message`, além do `state` levado à chamada seguinte; o cabeçalho `--!` do script declara seus parâmetros, janela e necessidades. A sandbox não tem arquivos, relógio, processos nem módulos e limita instruções (10 milhões por chamada), memória (64 MiB) e tempo (5 s por chamada). `script check` imprime `{header, functions, problems}` (saída 2 quando `problems` não está vazio); `script test` executa um script em alguns commits sem gravar nada e imprime `{rows: [{commit, fields, log}]}`. Um script que falha é recusado como `script_failed` com `refused.script = {commit, reason}`. **Scripts externos** (linguagem `shell`, `python` ou `lua-external`: `--script-language` / `--language`, por padrão a extensão do arquivo `.sh`, `.bash`, `.ps1`, `.py`, `.lua`, senão o Lua embutido) rodam como um processo próprio, com os seus direitos e sem isolamento: uma requisição JSON por linha na entrada padrão, uma resposta JSON por linha na saída padrão, com os mesmos campos acima, `"error": "texto"` para desistir e diagnósticos na saída de erro (eles voltam como o `log` do commit). O ambiente é limpo (só `PATH`, `HOME`/`USERPROFILE`, `SYSTEMROOT`, `TEMP`/`TMP` e `LANG` são repassados), o diretório de trabalho é um temporário novo, `rewrite.script_timeout_ms` (5000) limita cada resposta e `rewrite.script_total_timeout_s` (3600) a passagem inteira; em um timeout, uma falha ou um cancelamento, toda a árvore de processos é encerrada e a reescrita é recusada como `script_failed` (o commit e o motivo), sem nada movido. Quais linguagens existem é a configuração `rewrite.external_scripts` (padrão `["shell"]`; acrescente `"python"` ou `"lua"` você mesmo): uma linguagem desativada é recusada como `scripts_disabled`, e um interpretador ausente como `tool_missing` (`rewrite tools` os lista). **Confiança**: um script externo só roda quando uma pessoa confiou no texto exato dele: `rewrite script trust ARQUIVO` (ou `--trust` em `preview`, `run`, `script check` e `script test`, que faz isso no mesmo comando) guarda o SHA-256 do arquivo para este repositório, e um script alterado pergunta de novo. Um script sem confiança é recusado como `script_not_trusted` com `refused.script = {hash}` e nunca é iniciado, nem por `script check`, que informa `{trust: "untrusted", hash}` com código de saída 2; para um script confiável, `script check` o inicia uma vez com um commit inventado (`"dry_run": true`) para conferir a resposta e imprime também `interpreter`. O servidor MCP não pode confiar: ele não tem a ferramenta `rewrite script trust` nem o argumento `trust`, então um agente só executa um script em que uma pessoa já confiou antes. `scan-secrets` lê o histórico do escopo (a branch atual, `--all-local` ou `--ref`) uma vez e imprime `{findings: [{id, rule, path, more_paths, first_commit, last_commit, commits, blobs, preview}], commits, blobs_scanned, blobs_skipped_binary, blobs_skipped_large}`: a regra que casou (prefixos de token, chaves privadas, JWTs, senhas em URLs, linhas `password = valor` com cara de aleatórias), uma `preview` ocultada como `ghp_****abcd` e nunca o valor; não é exaustivo e só lê. `analyze` é a análise de tamanho (como `filter-repo --analyze`): uma passagem pelo histórico do escopo que imprime `{blobs, folders, deleted, top, commits, blobs_total, bytes_total, disk_total, bytes_in_head, bytes_history_only, deleted_paths, blobs_cut, folders_cut, deleted_cut}`. `blobs` são os maiores blobs únicos, até `--top` (padrão 50, no máximo 5000), do maior para o menor, cada um `{path, more_paths, blob, size, disk_size, first_commit, last_commit, state}` (`state` é `in_head`, `replaced` para uma versão antiga de um arquivo que ainda está no HEAD, ou `deleted`; `last_commit` é o commit que o removeu, senão o que o adicionou; `disk_size` é o tamanho no banco de objetos, e um delta empacotado conta como o delta); `folders` são `{path, size, blobs, in_head}` (os bytes de blobs únicos já guardados sob ela); `deleted` são caminhos que saíram do HEAD mas que o histórico ainda guarda, `{path, versions, size, first_commit, last_commit}`. `bytes_history_only` é o que remover tudo o que só o histórico guarda liberaria, aproximadamente, e só depois de apagar os objetos antigos e rodar um gc; só lê e nunca muda uma ref. Transforme uma linha em regra com `--remove-path CAMINHO` (ou a pasta) ou `--remove-blobs-over BYTES`. `--remove-finding ID` (pode repetir, ou `all`) adiciona uma regra que remove esses achados de todos os commits: o daemon varre o mesmo escopo de novo e resolve os ids sozinho, então o valor nunca chega à linha de comando, a uma receita ou a um log. Um segredo que foi publicado está vazado: troque-o primeiro. Segredos nunca vão na linha de comando nem em uma receita salva: `--secrets-file F` (um por linha) preenche as regras de segredos `content_replace` da receita e nunca é repetido na saída. Códigos de saída: 0 concluído; 1 erro (receita ilegível, opções inválidas); 2 recusado, impresso como `{"refused":{reason, message, detail}}` com o motivo `stale` (digest incorreto, execução desconhecida, uma ref se moveu desde a prévia), `no_rule`, `invalid_rule`, `empty_scope`, `shallow`, `signature_choice_needed`, ...; 3 o plano move refs que já estão em um remoto e falta `--yes`, impresso como `{"needs_confirmation":{prompt}}`, nada mudou (`run` também descarta a prévia). |

| `alias status`, `alias create <name> [--add]`, `alias remove [name]` | O alias de comando (`gp` ou qualquer nome) e, com `--add`, a variante de adicionar (`gpa`, que executa `gitpoulpi --add`: um script `/bin/sh` marcado no Linux e no macOS, um `.cmd` no Windows): JSON com o estado e o `kind` (`open` ou `add`) de cada alias que o GitPoulpi criou (`installed`, `outdated`, `foreign`), a pasta bin e o destino. `create` também informa avisos (o nome já executa algo no PATH, o alias próprio do PowerShell) e se a pasta bin está no PATH; ele recusa um arquivo que não é do GitPoulpi. `remove` sem nome remove todos os aliases que o GitPoulpi criou. Sem daemon; os instaladores chamam estes comandos. |
| `path status`, `path add`, `path remove` | O GitPoulpi no PATH do usuário, para novos terminais: um bloco marcado nos arquivos de inicialização do shell (Linux, macOS) ou `HKCU\Environment` (Windows). `status` é `not_added`, `added`, `outdated` ou `on_path` (já está lá, mas não pelo GitPoulpi). `remove` tira só o que `add` colocou. |
| `uninstall [--keep-files]` | Remove os aliases de comando, as entradas do PATH, os atalhos e as entradas do menu do gerenciador de arquivos que o GitPoulpi criou e, em uma instalação de versão, os arquivos do programa (o que `install.sh --uninstall` e o desinstalador do Windows executam). Recusa uma build sem o marcador `.gitpoulpi-dist` (uma build do cargo). Não está disponível para agentes MCP. |
| `launch [--new-window] [-- COMMAND...]`, `launch [--new-window] --folder DIR` | O que os atalhos do GitPoulpi executam: mostra a janela de um GitPoulpi já aberto (`ui.reuse_window`); caso contrário, inicia COMMAND (o comando do terminal). JSON: `{"action":"raised"}` ou `{"action":"started","reason":...}`. Nunca inicia um daemon; não é uma ferramenta MCP. `--new-window` sempre inicia COMMAND (motivo `new_window`); no Windows, manter Shift pressionado ao clicar no atalho ou no ícone da barra de tarefas tem o mesmo efeito. `--folder DIR` é o que a entrada **Abrir no GitPoulpi** do gerenciador de arquivos executa: com `ui.reuse_window` ativado e uma janela aberta, o repositório que contém DIR vira uma aba da janela focada mais recentemente (`{"action":"joined",...}`); caso contrário, o terminal de `ui.launch_terminal` inicia o GitPoulpi em DIR. |
| `mcp serve --stdio \| --http [ADDR] [--allow-remote] [--ui-control auto\|ask\|off]` | O servidor MCP ([MCP e agentes](mcp-and-agents.md)). Sem `ADDR`, `--http` usa `[mcp] bind` (padrão `127.0.0.1:8808`). `--http` exige o token bearer, a menos que `[mcp] http_auth` esteja desativado; `--allow-remote` é recusado, a menos que a autenticação esteja ativada e o tráfego seja criptografado (`[mcp] tls`, ou `behind_proxy`). |
| `mcp token [--show] [--copy] [--rotate]` | O token bearer do endpoint HTTP do MCP, como JSON `{token_hint, path, rotated}` (o token é criado no primeiro uso). `--show` acrescenta o `token` completo para colar no cabeçalho `Authorization: Bearer` de um cliente; `--copy` o coloca na área de transferência pelo terminal (OSC 52) sem imprimi-lo; `--rotate` o substitui e o antigo para de funcionar na hora. Não é uma ferramenta MCP: um agente não pode ler nem substituir a chave que protege o próprio servidor. Veja [MCP e agentes](mcp-and-agents.md#acessando-o-endpoint-de-outra-máquina). |
| `completions bash\|zsh\|fish\|powershell\|elvish` | Um script de autocompletar do shell no stdout. |
| `shell-init bash\|zsh\|fish\|pwsh [--name gp]` | Uma função wrapper (`gp`) que faz `cd` para a pasta da aba ativa quando você sai com *Sair e cd aqui*: `eval "$(gitpoulpi shell-init bash)"`. Veja [Seguindo a pasta da aba ativa](following-the-tab-folder.md). |

### Espaços de trabalho e busca

Um **espaço de trabalho** é um grupo nomeado de repositórios, opcionalmente com um
perfil de commit padrão. Ele fica em `workspaces.toml`, ao lado de `config.toml`,
compartilhado por todas as sessões e pela janela; por isso os comandos `workspace` não
iniciam nenhum daemon (só `add` e `create --add` pedem a um a URL `origin` de cada
repositório). Um repositório pode estar em vários espaços de trabalho. Os caminhos são
comparados como nos favoritos e na lista de recentes.

| Comando | O que faz |
|---|---|
| `workspace list`, `workspace show <id>` | `{workspaces: [...]}` / `{workspace}`: `id` (um slug, estável ao renomear), `name`, `color`, `description`, `profile`, `profile_exists` e `repos: [{path, exists, remote}]` (`remote` é a URL `origin` registrada quando o repositório foi adicionado, sem credenciais). |
| `workspace create <nome> [--add CAMINHO]... [--profile ID] [--color C] [--description T]` | Cria um espaço de trabalho e o exibe; dois espaços de trabalho não podem ter o mesmo nome. `--add` é repetível e não é `--repo`, que escolhe o repositório em que um comando roda. |
| `workspace rename <id> <nome>`, `workspace delete <id>` | Renomear mantém o id. Excluir nunca toca nos repositórios. |
| `workspace add <id> <caminho>...`, `workspace remove <id> <caminho>...` | `add` registra a raiz e a URL `origin` de cada repositório (um caminho que não existe, ou que não está dentro de um repositório, é recusado com uma mensagem e nada é salvo: só um repositório que some depois continua listado, marcado como ausente); `remove` também aceita o caminho de um repositório que sumiu do disco. |
| `workspace set-profile <id> <perfil>` / `--none` | O id de `[[profiles]]` com que os commits são feitos nos repositórios do espaço de trabalho. Um id que não nomeia nenhum perfil é salvo (`profile_exists: false`) e não se aplica. |
| `workspace set-ai-instructions <id> [--action <a>] [--mode append\|replace] (--text T \| --clear)` | As instruções de IA do espaço de trabalho, para toda ação ou para uma (`commit_message`, `code_review`, ...). `append` as acrescenta depois das globais, `replace` as usa no lugar delas. Valem para todo repositório do espaço de trabalho, antes das do próprio repositório. `workspace show` as imprime como `ai_instructions`. |
| `commit -m M [--workspace ID]` | Faz o commit com o perfil do espaço de trabalho quando o repositório está nele e o perfil existe; senão `general.active_profile`; senão a identidade do próprio repositório. Sem `--workspace` (ou `GITPOULPI_WORKSPACE`) nada muda: um commit nunca adivinha um espaço de trabalho pela participação, já que um repositório pode estar em vários. Um id desconhecido é um erro. |
| `search <consulta> [--workspace ID] [--kind K]... [--limit N]` | Busca aproximada (fuzzy) em branches (locais e remotas), tags, worktrees, stashes, mensagens de commit e nas pull/merge requests e issues dos caches de hospedagem, do repositório atual ou de todos os repositórios do espaço de trabalho (`GITPOULPI_WORKSPACE` substitui a opção). A versão da janela é a [Busca](search.md). |

`search` responde `{query, workspace, hits, partial, repos}`. Cada resultado é
`{kind, label, detail, target, score, positions, repo}`: `kind` é `branch`, `tag`,
`commit`, `stash`, `worktree`, `repo`, `pull_request` ou `issue`; `positions` são os
caracteres coincidentes de `label` a realçar; `target` diz aonde ir
(`{type: "ref", name}` com o nome completo da ref, `{type: "commit", id}`,
`{type: "stash", index, id}`, `{type: "worktree", path}`,
`{type: "repo", path}`, `{type: "pull_request", number}`, `{type: "issue", number}`);
os resultados são combinados entre os repositórios por `score`, o melhor primeiro. A
coincidência é a da paleta de comandos: a consulta literal, depois literal em qualquer
ponto, depois seus caracteres em ordem (mais cedo e mais curto vencem). O corpo de um
commit só é buscado quando o assunto não coincide e a consulta tem três caracteres ou
mais. Um prefixo restringe a busca e não faz parte do texto: `b:` branches, `t:` tags,
`c:` commits, `s:` stashes, `w:` worktrees, `r:` repositórios (só em espaço de
trabalho), `pr:` (ou `mr:`) pull/merge requests, `i:` issues, `#` ambos; `--kind`
(repetível, mesmos nomes) também filtra. `partial` é verdadeiro quando os commits de um
repositório foram cortados em
[`search.commit_limit`](config-reference.md#search-a-busca-no-espaço-de-trabalho);
`repos` diz de cada repositório se ele foi buscado (`reason` quando não: um caminho
que sumiu do disco é informado, nunca fatal). Um comando avulso monta primeiro o índice
de cada repositório; com uma janela aberta na mesma sessão, o daemon já o tem pronto.
As pull/merge requests e issues são lidas do cache de hospedagem de cada repositório (o
arquivo que a janela mantém em `.gitpoulpi/hosting-cache.json`) e nunca de um host: um
repositório cuja janela nunca as carregou não tem nenhuma para encontrar, e um cache
ausente ou gravado pela metade simplesmente não dá resultados.

**Mostrar coisas na janela aberta** (`ui`; todo comando também aceita
`--viewer <id>` e `--launch`)

| Comando | O que faz |
|---|---|
| `ui viewers [--all-sessions]`, `ui state [--text]` | As janelas abertas; o que uma mostra. |
| `ui show commit <rev> [--also R] [--files] [--focus refs\|log\|status]`, `ui show ref <name>`, `ui show pr <n>`, `ui show issue <n>`, `ui show wip [path] [--staged] [--composer]` | Seleciona algo. |
| `ui show diff <path> [--rev R \| --unstaged \| --staged] [--line N] [--side old\|new] [--split \| --inline] [--whole-file \| --hunks] [--highlight A-B]` | Abre um diff em uma linha. |
| `ui show file <path> [--rev R \| --worktree \| --index] [--blame \| --history] [--line N] [--column C] [--highlight A-B]` | Abre um arquivo, o blame ou o histórico dele. |
| `ui show tab [path]`, `ui show home [--filter F]`, `ui show search <query>`, `ui show palette [query]`, `ui show keys [topic]`, `ui show settings [page] [--setting KEY]` | Vai para uma aba, o Início, a barra de busca, a paleta, a ajuda, uma página das Configurações. `gitpoulpi ui show settings --help` lista os nomes das páginas. |
| `ui highlight <A[:C]-B[:C]> [--no-scroll]`, `ui notify <message>`, `ui back` | Dá cor a linhas; um aviso (toast); desfaz a última mudança de visualização. |
| `ui show conflict <path> [--conflict N]` | Abre o editor de merge em um arquivo em conflito, no conflito N (nada é escolhido nem salvo). |
| `ui propose reword <rev> -m M`, `ui propose commit-message <summary> [--body B]`, `ui propose branch <name> [--start-point R]`, `ui propose tag <name> [--target R] [-m M]` | Abre um diálogo pré-preenchido que você confirma (precisa de `[mcp] allow_ui_propose = true`). |
| `ui propose split <rev> --plan <file\|->` | Abre o editor de divisão sobre um commit, preenchido com um plano (o JSON de `split-commit --plan`) para você revisar, editar e aplicar; nada é dividido até você aplicar. Mesma barreira das outras propostas. |
| `ui propose resolution <path> (--pick 1=a,2=ba,... [--default a\|b] \| --content-file F)` | Abre o editor de merge com uma resolução já escolhida (ou o arquivo inteiro como texto) para você revisar; o seu Salvar e marcar resolvido é a única confirmação. Mesma barreira das outras propostas. |
| `ui propose rewrite --recipe <file\|->` | Abre o painel de reescrita de histórico com uma receita (TOML ou JSON, como em `rewrite preview --recipe`) já preenchida, para você pré-visualizar e aplicar; nada é reescrito, apagado nem enviado até você fazê-lo. Uma proposta traz no máximo 50 regras, nenhum script (um script rodaria na prévia) e nenhum valor secreto. Mesma barreira das outras propostas. |

Códigos de saída: 0 aplicado, 3 adiado para o usuário, 1 nos demais casos.
Detalhes e as regras que a janela segue: [MCP e agentes](mcp-and-agents.md#mostrar-coisas-ao-usuário).

## Notas

- **Sessões.** `gitpoulpi session list` mostra cada sessão com `live` / `stale`
  (decidido conectando-se à porta dela). O nome derivado é
  `<folder>-<hash of the path>`.
- **Sem perguntas interativas.** Nada faz perguntas: operações arriscadas ou
  precisam de uma opção (`--yes`, `--force-with-lease`) ou são recusadas com um
  motivo.
- **Fora da CLI**: `checkout --file` (restaurar um arquivo) existe só na janela.
