# Referência da CLI

`gitpoulpi` sem subcomando abre a janela; com um, é um cliente git automatizável.
Cada comando passa pelo mesmo daemon em segundo plano que a janela, por isso uma
alteração feita a partir de um script aparece em direto num GitPoulpi aberto. As
ferramentas MCP que um agente recebe são geradas a partir destes mesmos comandos
([MCP e agentes](mcp-and-agents.md)). `gitpoulpi <command> --help` mostra todas
as opções.

## Opções globais

| Opção | Efeito |
|---|---|
| `--json` | Imprime o resultado em JSON. Os erros também são JSON: `{"error": "..."}` no stdout, código de saída 1. Uma operação do git que falha acrescenta `"detail": {"operation", "command", "exit_code", "stderr"}` (o comando git executado, com os segredos ocultados, o código de saída e o fim do seu stderr; para a biblioteca git integrada `"git2": {"class", "code", "message"}`); as ferramentas MCP devolvem o mesmo objeto. Sem `--json` as linhas vão para o stderr. |
| `--repo <path>` | O repositório sobre o qual atuar (predefinição: o que envolve a pasta atual, como o git). |
| `-s, --session <name>` | A sessão (daemon) com que falar. Predefinição: derivada da raiz do repositório, de modo que tudo o que se abre dentro de um repositório partilha um daemon e dois repositórios têm dois. |
| `--backend git2\|system` | Backend para um daemon que este comando inicia (um que já esteja a correr mantém o seu). |
| `--cwd-file <file>` | Onde a janela escreve a pasta do separador ativo ao sair (usado pelo `shell-init`). |
| `-a, --add [path]`, `--no-raise` | Abre uma pasta num novo separador do GitPoulpi que já está aberto, em vez de iniciar outro; veja [Adicionar uma pasta à janela aberta](#adicionar-uma-pasta-à-janela-aberta). Não aceita subcomando. |
| `-l, --lang <lang>` | Idioma apenas do texto de `--help`: `en`, `fr`, `es`, `pt-BR`, `pt-PT`, `it`, `de`, `zh-CN`, `ja`, `ko`, `ru`, `uk`, `pl`, `cs`, `nl`, `sv`, `tr`. Veja [Ajuda traduzida](#ajuda-traduzida). |

### Adicionar uma pasta à janela aberta

`gitpoulpi --add [path]` (`-a`; `gp -a` e o alias de comando `gpa` executam o mesmo código) abre `path`
(predefinição: a pasta atual, resolvida para o repositório que a contém) num novo separador de um GitPoulpi
que já está aberto, de modo que uma pasta em que entra com `cd` num terminal não inicia uma segunda janela.

- Uma *sessão aberta* é uma cujo daemon responde e que tem uma janela do GitPoulpi associada. As janelas
  cujo utilizador desativou **Permitir que agentes de IA controlem a vista** não se anunciam e não são
  encontradas (o mesmo limite de `gitpoulpi launch`).
- Uma sessão aberta: recebe o separador (ou mostra-o, se esse repositório já estiver aberto), a sua janela
  passa para a frente se o ambiente de trabalho o permitir (Windows, WezTerm, Hyprland; `--no-raise` dispensa
  isso) e uma linha diz que sessão o recebeu.
- Várias: são listadas, numeradas, com o número de separadores e os nomes dos repositórios; escreva o número
  e Enter (uma linha vazia ou Esc e depois Enter cancela, código de saída 130). Sem terminal no stdin o comando
  falha e diz para indicar `--session NOME`. `-s NOME` dispensa a pergunta.
- Nenhuma (ou `-s NOME` indica uma sessão que não está aberta): o GitPoulpi inicia normalmente neste terminal,
  nessa pasta, exatamente como `gp [path]`.
- A janela aplica-o de imediato, como escolha sua (sem chip de confirmação, sem marca de agente), exceto se
  estiver a escrever num formulário aí: nesse caso a janela oferece o separador no chip da barra de estado e o código de
  saída é 3. Uma pasta que não está dentro de um repositório é recusada (código de saída 1).

`--json` imprime um objeto: `{"action": "joined", "session", "repo", "already_open", "raised", "outcome": {...}}`
(`outcome` é a resposta da janela, como em `ui show`) ou `{"action": "cancelled"}`; os erros são `{"error": "..."}`.
Códigos de saída: 0 o separador está aberto, 3 oferecido no chip, 1 recusado ou falhado, 130 cancelado. Não há
nenhuma ferramenta MCP para isto: um agente que queira mostrar um repositório ao utilizador usa `ui show tab`.

### Ajuda traduzida

`gitpoulpi --help` está em inglês. Junte `-l` para ler as explicações noutro
idioma: `gitpoulpi -l fr --help`, `gitpoulpi -l de commit --help`. Só as
explicações e os títulos das secções são traduzidos. Os nomes dos comandos, as
opções, os nomes de valores e os valores possíveis não mudam, por isso os scripts
e os agentes veem a mesma interface. O idioma da ajuda não é lido do ambiente: a
saída só muda quando indica `-l`. As descrições das ferramentas MCP estão sempre
em inglês.

As revisões aceitam tudo o que o git aceita (`HEAD~2`, uma branch, uma tag, um
sha curto). Os hunks e as linhas são numerados como o `gitpoulpi --json diff` os
numera.

[--param NAME=VALUE...] [--language L] [--trust]`, `rewrite script trust FILE` (e `--script FILE --script-param NAME=VALUE [--script-language L] [--trust]` em `preview`/`run`) | Reescrita do histórico a partir de uma receita (o TOML que o painel de reescrita do TUI guarda, ou JSON; as opções acrescentam regras depois das da receita e substituem o seu âmbito e opções). `tools` lista as ferramentas externas de que voltar a assinar e os scripts precisam (`{tools: [...]}`). **Assinaturas**: quando commits assinados são reescritos, `--signatures` é obrigatório (`strip` remove-as, `resign-signed` volta a assinar só os que estavam assinados, `resign-all` assina todos os commits reescritos), senão a pré-visualização é recusada como `signature_choice_needed`; os commits que ficam como estão mantêm a assinatura. Voltar a assinar usa a configuração do próprio repositório (`gpg.format` openpgp, ssh ou x509, `user.signingkey`, `gpg.*.program`) e acontece na pré-visualização (o id de um commit assinado inclui a sua assinatura): `counts.resigned` e `counts.signing_millis` do plano dizem quantos e quanto tempo demorou. Uma configuração que não assina é recusada logo no início como `signing_failed` (ou `tool_missing`), antes de se ler o que quer que seja. `rewrite check-signing` corre só esse teste (assina e verifica uma vez um conteúdo fictício) e mostra `{format, tool, millis}`, o tempo de uma assinatura, para estimar uma execução (código de saída 2 com o motivo quando falha; pode abrir um pedido de frase-passe). `--remove-signatures` acrescenta a regra que retira a assinatura de todos os commits do âmbito, mesmo onde mais nada muda; esses commits não precisam de resposta a `--signatures`. `--fix-message-encoding` acrescenta a regra que recodifica as mensagens para UTF-8: um commit com um cabeçalho `encoding` (ISO-8859-1, Shift_JIS...) é descodificado e o cabeçalho desaparece, e o UTF-8 que foi lido como Latin-1 ou Windows-1252 (`RÃ©Ã©criture`) só é reparado quando a ida e volta é exata; o que não se consegue decidir fica como está e é contado em `counts.encoding_left`. Os nomes de um commit cujo cabeçalho desaparece são descodificados com ele, e `--fix-name-encoding` repara também nomes deturpados noutros sítios. `preview` planeia sem alterar nada e mostra o plano `{run, digest, counts, refs, warnings, per_rule, rows, rows_total}` (os primeiros `--limit` commits alterados, 50 por predefinição, ou `--all`) e guarda-o no daemon da sessão e em disco, na pasta git do repositório (`gitpoulpi/rewrite/<run>/`): `apply --run ID --digest D` funciona a partir de um comando posterior, depois de reiniciar o daemon ou a partir de outra interface, sem `daemon start`; um plano guardado que já não corresponde ao seu digest é `stale`. Só `rows` precisa do daemon que pré-visualizou (um em execução, por exemplo o do TUI ou `daemon start`), por isso use `preview --all` para ver todas as linhas num só comando. As regras de identidade e de anonimização só reescrevem o tagger das tags anotadas recriadas quando a receita define `include_taggers`. `rows` pagina a execução `{run, filter, offset, total, rows}` (no máximo 200 por página). `apply` executa o plano que reviu (o seu `run` e `digest`) como UMA entrada de desfazer e mostra `{run, moved, commits_changed}`; `undo` repõe tudo. Nunca envia: uma ref já enviada exige o seu push forçado depois. `run` pré-visualiza e aplica num só comando (não precisa de daemon) e mostra `{plan, outcome}`. `discard` descarta uma execução (duas vezes não faz mal). As regras de trailers (`--trailer-add KEY=VALUE`, `--trailer-remove KEY`, `--trailer-map KEY:OLD=NEW`, repetíveis, por essa ordem depois de `--replace-message`) editam as linhas `Key: value` do último parágrafo de cada mensagem com a gramática do `git interpret-trailers`: `--trailer-add` ignora uma mensagem que já tem exatamente esse trailer, `--trailer-remove` retira todos os trailers dessa chave, `--trailer-map` substitui texto literal nos valores dessa chave; o resto da mensagem não é tocado (uma receita também pode definir `if_exists` como `replace` ou `skip`, um padrão `find` em `remove` e padrões `regex`). `--map-trailers` (precisa das opções de identidade) faz com que a regra de identidade também altere os trailers `Name <email>` que correspondem. `--update-message-hashes` substitui nas mensagens os ids abreviados de commits (7 ou mais carateres hexadecimais) pelos novos ids do mesmo comprimento quando corresponde exatamente um commit reescrito; `counts.message_hashes_updated` e `counts.message_hashes_left` (ambíguos, desconhecidos ou criados depois) do plano dizem o que aconteceu. As regras de conteúdo (`remove_paths`, `remove_blobs_over` e `content_replace` da receita, ou as opções `--remove-path`, `--remove-blobs-over`, `--replace-content`) reescrevem os ficheiros de cada commit: cada ficheiro único é lido uma vez, os ficheiros binários são ignorados e contados (`counts.blobs_skipped_binary`), um commit que uma regra deixa vazio é descartado (`counts.commits_dropped`, linhas com `new: null`; `--prune-empty never` mantém-no) e os seus filhos passam para o pai, e os ficheiros em checkout seguem a nova árvore. Recusado com `dirty_paths_touched` quando um ficheiro com alterações locais é um que a reescrita alteraria, `checked_out_elsewhere` quando uma branch reescrita está em checkout noutro worktree, `partial_clone` num clone parcial. As regras de caminhos (`--move-path FROM=TO`, repetível; `--into-subdir DIR`; `--extract DIR`, ou `move_paths` da receita) renomeiam um ficheiro ou pasta, movem todo o repositório para uma subpasta ou mantêm só uma subpasta como nova raiz; atuam sobre árvores, por isso cada ficheiro mantém o seu id, e correm depois das regras de conteúdo. Um renomear nunca substitui: onde o novo caminho já existe em algum commit, a pré-visualização é recusada como `path_collision` (código de saída 2), com os ids curtos dos commits e os caminhos em `refused.detail`. `--extract` é **perguntado de cada vez**: sem `--extract-mode` (`clone`, `in-place` ou `submodule`) nada é pré-visualizado e a resposta é `{"needs_choice":{choice:"extract_mode", options, prompt}}` com código de saída 3. `in-place` reescreve este repositório como qualquer regra (uma entrada de desfazer; as branches e tags que não têm nada da pasta são eliminadas, linhas com `refs[].new: null`; a branch em checkout tem de ter a pasta, senão `empty_scope`). `clone` e `submodule` pré-visualizam o histórico que o novo repositório vai conter, sobre todas as branches e tags locais, sem nada enviado nem protegido, e aplicam-se com a pasta do novo repositório: `--target PATH` em `run`, ou em `apply` (um `rewrite apply` de um plano destes sem `--target` é recusado como `invalid_rule`; a pasta não pode existir (ou tem de estar vazia) nem estar dentro do repositório). `clone` faz aí um `git clone --no-local` deste repositório, reescreve-o com a receita, remove o remoto, expira os reflogs e poda os objetos antigos, pelo que contém só o histórico extraído; este repositório não é tocado e nada fica no diário (`outcome.moved` vem vazio). `submodule` faz o mesmo e depois acrescenta um commit na branch atual que substitui a pasta por um submódulo do novo repositório (o URL em `.gitmodules` é o seu caminho local), inicializa-o e regista-o no diário (`outcome.moved` tem a branch; `undo` repõe-na e liberta o submódulo); o histórico não é reescrito, por isso os commits antigos mantêm a pasta. Ficheiros editados ou não acompanhados na pasta, ou um HEAD solto, recusam-no. Ordem quando se combinam: as regras de conteúdo (`--replace-content`, `--remove-blobs-over`, `--lfs-import`, `--lfs-export`) e `--remove-path` correm primeiro sobre os caminhos originais, depois as regras de caminhos; um padrão LFS e um glob de remoção indicam por isso os caminhos originais, e as linhas do `.gitattributes` de uma importação são acrescentadas na raiz original e depois movem-se com os ficheiros. **Regras LFS** (`lfs_import { patterns, min_size }` e `lfs_export { patterns }` da receita, ou `--lfs-import PATTERN...` com `--lfs-min-size BYTES`, e `--lfs-export PATTERN...`) precisam do `git-lfs` (senão `tool_missing`): uma importação transforma os ficheiros correspondentes em ponteiros da especificação v1 em todos os commits, escreve o conteúdo no armazenamento LFS local ao aplicar (de forma atómica, uma vez por conteúdo) e acrescenta `<pattern> filter=lfs diff=lfs merge=lfs -text` ao `.gitattributes` da raiz de cada commit reescrito que contém um ponteiro (o resto do ficheiro não é tocado); uma exportação transforma os ponteiros correspondentes de volta nos ficheiros e remove essas linhas, e é recusada como `lfs_objects_missing` (`detail`: um `<oid> <path>` por linha) quando os objetos não estão no armazenamento local (antes, `lfs fetch`). `counts.lfs_blobs`, `lfs_bytes`, `lfs_objects`, `lfs_restored` e `lfs_run` do plano dizem o que acontece, as linhas listam os caminhos `lfs_imported` / `lfs_exported`, e os ficheiros em checkout continuam a ser o conteúdo real (ao aplicar, instala os filtros LFS do repositório se faltarem). Envie os objetos depois com `lfs push --all`. **Regras de texto** (`line_endings`, `strip_exec` e `reencode` da receita, ou `--eol`, `--strip-exec`, `--reencode`): `--eol lf\|crlf\|cr --eol-paths GLOB...` dá a todos os ficheiros de texto que os globs indicam esse fim de linha (os fins de linha misturados ficam uniformes; `--eol-exclude` deixa ficheiros em paz; `--eol-follow-attributes` lê o `.gitattributes` da raiz de cada commit: os ficheiros `-text`/`binary` são ignorados e os `eol=` mantêm o seu próprio fim de linha); `--strip-exec GLOB...` transforma o modo 100755 em 100644 nos ficheiros correspondentes (pelo menos um glob, `--strip-exec-exclude` para poupar alguns); `--reencode utf-8\|utf-8-bom\|utf-16le\|utf-16be\|windows-1252\|iso-8859-1 --encoding-paths GLOB...` converte os ficheiros de texto para essa codificação, a partir de `--from SOURCE` ou, por omissão, detetada por ficheiro (marca de ordem de bytes, UTF-8 válido, senão `--encoding-fallback`, por omissão `windows-1252`). Correm na fase de conteúdo, com as outras regras de conteúdo, pela ordem da receita. Os ficheiros binários são ignorados e contados (`counts.blobs_skipped_binary`); os ficheiros que a codificação de origem não consegue ler ou que o destino não consegue guardar ficam como estão e são contados em `counts.blobs_skipped_undecodable`; `counts.blobs_changed` é o número de novas versões de ficheiros, e as linhas listam os caminhos alterados como `modified`. `diff` mostra o que as regras fizeram a um ficheiro de um commit de uma execução pré-visualizada (`{kind, binary, redacted, old_size, new_size, hunks}`); as linhas que uma regra de segredos remove ficam ocultas. Os scripts Lua (`--script FILE`, repetível, executados por ordem depois das outras regras; o ficheiro é incorporado na receita) chamam `rewrite_commit(c, ctx)` em cada commit e podem devolver novos `author` / `committer` (`name`, `email`, `time`, `offset_minutes`) e `message`, mais o `state` passado à chamada seguinte; o cabeçalho `--!` do script declara os seus parâmetros, janela e necessidades. A sandbox não tem ficheiros, relógio, processos nem módulos e limita as instruções (10 milhões por chamada), a memória (64 MiB) e o tempo (5 s por chamada). `script check` mostra `{header, functions, problems}` (saída 2 quando `problems` não está vazio); `script test` executa um script em alguns commits sem escrever nada e mostra `{rows: [{commit, fields, log}]}`. Um script que falha é recusado como `script_failed` com `refused.script = {commit, reason}`. **Scripts externos** (linguagem `shell`, `python` ou `lua-external`: `--script-language` / `--language`, por omissão a extensão do ficheiro `.sh`, `.bash`, `.ps1`, `.py`, `.lua`, senão o Lua integrado) correm como um processo próprio, com as suas permissões e sem sandbox: um pedido JSON por linha no stdin, uma resposta JSON por linha no stdout, com os mesmos campos acima, `"error": "texto"` para desistir, diagnósticos no stderr (voltam como o `log` do commit). O ambiente é limpo (só passam `PATH`, `HOME`/`USERPROFILE`, `SYSTEMROOT`, `TEMP`/`TMP` e `LANG`), a pasta de trabalho é uma pasta temporária nova, `rewrite.script_timeout_ms` (5000) limita cada resposta e `rewrite.script_total_timeout_s` (3600) a passagem completa; num timeout, numa falha ou num cancelamento, toda a árvore de processos é morta e a reescrita é recusada como `script_failed` (o commit e o motivo), sem nada movido. Que linguagens existem é a definição `rewrite.external_scripts` (por omissão `["shell"]`; acrescente `"python"` ou `"lua"` você mesmo): uma linguagem desativada é recusada como `scripts_disabled`, um interpretador em falta como `tool_missing` (`rewrite tools` lista-os). **Confiança**: um script externo só corre quando uma pessoa confiou no seu texto exato: `rewrite script trust FILE` (ou `--trust` em `preview`, `run`, `script check` e `script test`, que o faz no mesmo comando) regista o SHA-256 do ficheiro para este repositório, e um script alterado volta a perguntar. Um script sem confiança é recusado como `script_not_trusted` com `refused.script = {hash}` e nunca é iniciado, nem sequer por `script check`, que indica `{trust: "untrusted", hash}` com código de saída 2; para um de confiança, `script check` inicia-o uma vez com um commit fictício (`"dry_run": true`) para verificar a resposta e mostra também `interpreter`. O servidor MCP não pode confiar: não tem a ferramenta `rewrite script trust` nem o argumento `trust`, por isso um agente só pode executar um script em que uma pessoa já confiou. `scan-secrets` lê o histórico do âmbito (a branch atual, `--all-local` ou `--ref`) uma vez e mostra `{findings: [{id, rule, path, more_paths, first_commit, last_commit, commits, blobs, preview}], commits, blobs_scanned, blobs_skipped_binary, blobs_skipped_large}`: a regra que correspondeu (prefixos de tokens, chaves privadas, JWTs, palavras-passe em URLs, linhas `password = valor` de aspeto aleatório), uma `preview` ocultada como `ghp_****abcd` e nunca o valor; não é exaustivo e é só leitura. `analyze` é a análise de tamanhos (como `filter-repo --analyze`): uma passagem pelo histórico do âmbito que mostra `{blobs, folders, deleted, top, commits, blobs_total, bytes_total, disk_total, bytes_in_head, bytes_history_only, deleted_paths, blobs_cut, folders_cut, deleted_cut}`. Os `blobs` são os `--top` (50 por omissão, no máximo 5000) maiores blobs únicos, o maior primeiro, cada um `{path, more_paths, blob, size, disk_size, first_commit, last_commit, state}` (`state` é `in_head`, `replaced` para uma versão antiga de um ficheiro que ainda está em HEAD, ou `deleted`; `last_commit` é o commit que o removeu, senão o que o acrescentou; `disk_size` é o tamanho na base de dados de objetos, um delta empacotado conta como o delta); as `folders` são `{path, size, blobs, in_head}` (bytes de blobs únicos alguma vez guardados por baixo); os `deleted` são caminhos que saíram de HEAD mas que o histórico ainda guarda, `{path, versions, size, first_commit, last_commit}`. `bytes_history_only` é o que remover tudo o que só o histórico guarda libertaria, aproximadamente, e só depois de uma purga dos objetos antigos e de um gc; é só leitura e nunca altera uma ref. Transforme uma linha numa regra com `--remove-path CAMINHO` (ou a pasta) ou `--remove-blobs-over BYTES`. `--remove-finding ID` (repetível, ou `all`) acrescenta uma regra que remove esses resultados de todos os commits: o daemon pesquisa o mesmo âmbito de novo e resolve os ids por si, por isso o valor nunca chega à linha de comandos, a uma receita nem a um registo. Um segredo que foi enviado está comprometido: renove-o primeiro. Os segredos nunca vão na linha de comandos nem numa receita guardada: `--secrets-file F` (um por linha) preenche as regras de segredos `content_replace` da receita e nunca é repetido na saída. Códigos de saída: 0 feito; 1 erro (receita ilegível, opções inválidas); 2 recusado, mostrado como `{"refused":{reason, message, detail}}` com o motivo `stale` (digest errado, execução desconhecida, uma ref mudou desde a pré-visualização), `no_rule`, `invalid_rule`, `empty_scope`, `shallow`, `signature_choice_needed`, ...; 3 o plano move refs que já estão num remoto e falta `--yes`, mostrado como `{"needs_confirmation":{prompt}}`, nada mudou (`run` também descarta a sua pré-visualização). |

### Áreas de trabalho e pesquisa

Uma **área de trabalho** é um grupo nomeado de repositórios, opcionalmente com um
perfil de commit predefinido. Vive em `workspaces.toml`, junto a `config.toml`,
partilhada por todas as sessões e pela janela, pelo que os comandos `workspace` não
iniciam nenhum daemon (só `add` e `create --add` pedem a um o URL de `origin` de
cada repositório). Um repositório pode estar em várias áreas de trabalho. Os
caminhos comparam-se como os favoritos e a lista de recentes.

| Comando | O que faz |
|---|---|
| `workspace list`, `workspace show <id>` | `{workspaces: [...]}` / `{workspace}`: `id` (um slug, estável ao renomear), `name`, `color`, `description`, `profile`, `profile_exists` e `repos: [{path, exists, remote}]` (`remote` é o URL de `origin` registado ao adicionar o repositório, sem credenciais). |
| `workspace create <name> [--add PATH]... [--profile ID] [--color C] [--description T]` | Cria uma área de trabalho e mostra-a; duas áreas de trabalho não podem ter o mesmo nome. `--add` é repetível e não é `--repo`, que escolhe o repositório onde um comando é executado. |
| `workspace rename <id> <name>`, `workspace delete <id>` | Renomear mantém o id. Eliminar nunca toca nos repositórios. |
| `workspace add <id> <path>...`, `workspace remove <id> <path>...` | `add` regista a raiz e o URL de `origin` de cada repositório (um caminho que não existe, ou que não está dentro de um repositório, é recusado com uma mensagem e nada é guardado: só um repositório que desaparece mais tarde continua listado, marcado como em falta); `remove` aceita também o caminho de um repositório que já não está no disco. |
| `workspace set-profile <id> <profile>` / `--none` | O id de `[[profiles]]` com que se fazem os commits nos repositórios da área de trabalho. Um id que não corresponde a nenhum perfil é guardado (`profile_exists: false`) e não se aplica. |
| `workspace set-ai-instructions <id> [--action <a>] [--mode append\|replace] (--text T \| --clear)` | As instruções de IA da área de trabalho, para todas as ações ou para uma (`commit_message`, `code_review`, ...). `append` junta-as depois das globais, `replace` usa-as em vez delas. Aplicam-se a todos os repositórios da área de trabalho, antes das do próprio repositório. `workspace show` imprime-as como `ai_instructions`. |
| `commit -m M [--workspace ID]` | Faz o commit com o perfil da área de trabalho quando o repositório está nela e o perfil existe; senão `general.active_profile`; senão a identidade do próprio repositório. Sem `--workspace` (ou `GITPOULPI_WORKSPACE`) nada muda: um commit nunca adivinha uma área de trabalho pela pertença, já que um repositório pode estar em várias. Um id desconhecido é um erro. |
| `search <query> [--workspace ID] [--kind K]... [--limit N]` | Pesquisa aproximada em branches (locais e remotos), tags, worktrees, stashes, mensagens de commit e nos pull/merge requests e issues das caches de alojamento, do repositório atual ou de todos os repositórios da área de trabalho (`GITPOULPI_WORKSPACE` substitui a opção). A versão da janela é [Pesquisa](search.md). |

`search` responde `{query, workspace, hits, partial, repos}`. Cada resultado é
`{kind, label, detail, target, score, positions, repo}`: `kind` é `branch`,
`tag`, `commit`, `stash`, `worktree`, `repo`, `pull_request` ou `issue`;
`positions` são os carateres de `label` que coincidiram, para realçar; `target`
diz para onde ir (`{type: "ref", name}` com o nome completo da ref,
`{type: "commit", id}`, `{type: "stash", index, id}`, `{type: "worktree", path}`,
`{type: "repo", path}`, `{type: "pull_request", number}`,
`{type: "issue", number}`); os resultados são fundidos entre repositórios por
`score`, o melhor primeiro. A correspondência é a da paleta de comandos: a consulta
tal e qual, depois tal e qual em qualquer sítio, depois os seus carateres por ordem
(o mais cedo e o mais curto ganham). O corpo de um commit só é pesquisado quando o
assunto não coincide e a consulta tem três carateres ou mais. Um prefixo restringe
a pesquisa e não faz parte do texto: `b:` branches, `t:` tags, `c:` commits, `s:`
stashes, `w:` worktrees, `r:` repositórios (só em áreas de trabalho), `pr:` (ou
`mr:`) pull/merge requests, `i:` issues, `#` ambos; `--kind` (repetível, mesmos
nomes) também filtra. `partial` é verdadeiro quando os commits de um repositório
foram cortados em [`search.commit_limit`](config-reference.md#search-a-pesquisa-na-área-de-trabalho);
`repos` diz, para cada repositório, se foi pesquisado (`reason` quando não: um
caminho que desapareceu do disco é comunicado, nunca fatal). Um comando avulso
constrói primeiro o índice de cada repositório; com uma janela aberta na mesma
sessão, o daemon já o tem pronto. Os pull/merge requests e as issues são lidos da
cache de alojamento de cada repositório (o ficheiro que a janela mantém em
`.gitpoulpi/hosting-cache.json`) e nunca de um host: um repositório cuja janela
nunca os carregou não tem nenhum para encontrar, e uma cache em falta ou escrita a
meio simplesmente não dá resultados.

**Mostrar coisas na janela aberta** (`ui`; cada comando aceita também
`--viewer <id>` e `--launch`)

| Comando | O que faz |
|---|---|
| `ui viewers [--all-sessions]`, `ui state [--text]` | As janelas abertas; o que uma mostra. |
| `ui show commit <rev> [--also R] [--files] [--focus refs\|log\|status]`, `ui show ref <name>`, `ui show pr <n>`, `ui show issue <n>`, `ui show wip [path] [--staged] [--composer]` | Seleciona algo. |
| `ui show diff <path> [--rev R \| --unstaged \| --staged] [--line N] [--side old\|new] [--split \| --inline] [--whole-file \| --hunks] [--highlight A-B]` | Abre um diff numa linha. |
| `ui show file <path> [--rev R \| --worktree \| --index] [--blame \| --history] [--line N] [--column C] [--highlight A-B]` | Abre um ficheiro, o seu blame ou histórico. |
| `ui show tab [path]`, `ui show home [--filter F]`, `ui show search <query>`, `ui show palette [query]`, `ui show keys [topic]`, `ui show settings [page] [--setting KEY]` | Vai para um separador, o Início, a barra de pesquisa, a paleta, a ajuda, uma página das Definições. `gitpoulpi ui show settings --help` lista os nomes das páginas. |
| `ui highlight <A[:C]-B[:C]> [--no-scroll]`, `ui notify <message>`, `ui back` | Realça linhas; um aviso (toast); desfaz a última alteração de vista. |

## Notas

- **Sessões.** `gitpoulpi session list` mostra cada sessão com `live` / `stale`
  (decidido ligando-se à sua porta). O nome derivado é
  `<folder>-<hash of the path>`.
- **Sem perguntas interativas.** Nada faz perguntas: as operações arriscadas ou
  precisam de uma opção (`--yes`, `--force-with-lease`) ou são recusadas com um
  motivo.
- **Não está na CLI**: `checkout --file` (restaurar um ficheiro) existe só na
  janela.
