# Рабочие процессы ветвления

Рабочий процесс ветвления говорит GitPoulpi, как ваша команда пользуется ветками: какие живут вечно (`main`,
`develop`, `production`), какие - краткоживущие тематические ветки (`feature/...`, `hotfix/...`), как они
называются и где каждая начинается и заканчивается. Это Git Flow, который можно настраивать: фиксированные имена,
префиксы и суффиксы или шаблоны с подстановками, так что ветки, которые бот создаёт по задаче, распознаются так же,
как ваши собственные.

Эта страница описывает модель, файл, готовые шаблоны, определение и импорт, команды только для чтения, действия,
которые начинают, завершают, синхронизируют и продвигают ветки (CLI, MCP и приложение), и экраны приложения:
редактор настроек, сгруппированную боковую панель, меню `Flow` и его окна.

## Понятия

- **Базовая ветка** живёт долго. У базовой ветки может быть **родитель** (`develop` вливается в `main`); у основной
  ветки (trunk) его нет. Базовая ветка может перечислять несколько допустимых имён (`main` или `master`, `develop`
  или `dev`): используется то, которое существует.
- **Тип тематической ветки** - это вид краткоживущей ветки (feature, bugfix, release, hotfix, support...). У него
  есть **шаблон имени**, **родитель** (откуда ветка начинается и куда завершается) и способ завершения.
- Каждая ветка **классифицируется**: базовая (по имени), тематическая ветка какого-то типа (по шаблону) или
  неклассифицированная.
- **Родитель ветки** определяется по порядку: тот, что записан, когда GitPoulpi создал ветку
  (`git config branch.<name>.gitpoulpi-parent`), иначе `git-town-branch.<name>.parent` из Git Town, если он есть,
  иначе родитель её типа.

## Где это хранится

| Что | Где | В commit'е |
|---|---|---|
| Общий рабочий процесс | `.gitpoulpi/workflow.toml` в репозитории | Да, вами: GitPoulpi записывает его только по вашей просьбе |
| Ваши собственные правки | `[workflow]` в `.gitpoulpi/repo-state.toml` | Нет (этот файл игнорируется) |

Каталог состояния игнорирует сам себя (`.gitpoulpi/.gitignore`), кроме `workflow.toml`, который предназначен для
commit'а. Действующий рабочий процесс - это общий файл с вашим переопределением поверх: базовая ветка с тем же
именем или тематический тип с тем же id заменяется; новые добавляются; `disable_bases` и `disable_topics` убирают
общие только для вас.

При сохранении поверх существующего файла сохраняются ключи, которых эта версия не знает (от более новой версии
GitPoulpi или от коллеги), но не комментарии и не порядок ключей.

## Файл

```toml
template = "git-flow"          # git-flow | github-flow | gitlab-flow | trunk | custom (информативно)

[[base]]
name = "main"
names = ["master"]             # другие написания той же ветки
protected = true               # никогда не удаляется, прямые commit'ы подозрительны

[[base]]
name = "develop"
names = ["dev"]
parent = "main"
merge = "merge"                # merge | squash | rebase | fast-forward
tag_on_merge = false
# environment = true           # ветка окружения (GitLab Flow): продвигается вниз по цепочке

[[topic]]
id = "feature"
label = "Feature"
pattern = "feature/{slug}"
patterns = ["features/{slug}"] # другие имена, которые тоже подходят; по ним ветки не создаются
# regex = "^feat-(?P<slug>.+)$"  # тоже подходит; именованные группы становятся полями
parent = "develop"             # откуда начинается и цель завершения по умолчанию
finish = [{ into = "develop", merge = "squash" }]
finish_mode = "merge-request"  # local-merge | merge-request | ask
delete_after_finish = true

[hooks]                        # команды оболочки по выбору, всегда показываются перед запуском
after_start = []
before_finish = ["cargo test"]

[issue_flow]                   # процессы, управляемые хостом, см. ниже
mode = "local"                 # local | host-creates-branch | bot
```

`merge`, `finish`, `finish_mode` и `hooks` управляют [действиями](#действия) ниже; `issue_flow` управляет
[процессами, управляемыми хостом](#процессы-управляемые-хостом).

### Шаблоны имён

Текст с `{подстановками}`:

| Подстановка | Что подходит | Из чего создаётся |
|---|---|---|
| `{slug}` | произвольный текст; может содержать `/`, если стоит последним | текст в нижнем регистре, без диакритики, `-` между словами, не больше 50 символов |
| `{issue}` | цифры (`123`) | `123` или `#123` |
| `{issue_key}` | ключ в трекере (`PROJ-123`) | как задано |
| `{user}` | имя без `/` | в виде slug |
| `{date}` | `2026-10-16` или `20261016` | как задано |
| `{version}` | `1.2.0`, `v1.2`, `1.2.0-rc1` | как задано |
| `{n}` | цифры | как задано |

Всё остальное - буквально, поэтому префиксы и суффиксы - просто текст: `feature/{slug}`,
`{user}/{issue}-{slug}-wip`, `bot/{issue_key}`. Каждая подстановка может встречаться один раз, а между двумя
подстановками нужен текст. Шаблон должен давать допустимые имена веток (правила `git check-ref-format`): без
пробелов, без `~ ^ : ? * [ \`, без `..`, без компонента, начинающегося с `.` или заканчивающегося на `.lock`.

`regex` служит только для распознавания (он привязан с обоих концов); используйте его для имён, которые не
выражаются шаблоном. Именованные группы становятся полями ветки.

### Какой тип побеждает

1. Ветка с именем базовой (любым из её имён) - это эта базовая ветка.
2. Иначе кандидатом становится каждый подходящий шаблон каждого типа: `pattern`, затем `patterns`, затем `regex`,
   тип за типом в порядке файла. Побеждает тот, что задаёт больше всего буквальных символов (`release/{version}`
   лучше `{user}/{slug}`, а тот лучше голого `{slug}`); у regex считается его буквальный префикс. Ничья достаётся
   более раннему в файле.
3. Иначе ветка неклассифицирована.

Неработающий шаблон или regex сообщается как предупреждение и пропускается; остальное продолжает работать.

## Шаблоны

| Шаблон | Базовые ветки | Тематические ветки |
|---|---|---|
| `git-flow` | `main` или `master`; `develop` или `dev` (родитель - main) | `feature/` и `bugfix/` (от develop), `release/` (от develop, в main и develop, с тегом), `hotfix/` (от main, в main и develop, с тегом), `support/` (от main); написания во множественном числе (`features/`, `releases/`...) тоже подходят |
| `github-flow` | `main` | `feature/` или любое имя, от main, запрос на слияние в main, squash, затем удаляется |
| `gitlab-flow` | `main`; `pre-production` и `production` (ветки окружения, цепочка main, pre-production, production) | `feature/` или любое имя от main; `release/{version}` как цель cherry-pick |
| `trunk` | `main` | краткоживущие `{user}/{slug}` от main, с перебазированием |
| `custom` | нет | нет |

Ветки окружения подходят и под именами `preprod`, `staging` и `prod`. Шаблон - это отправная точка: выведите его
командой `flow config init` и отредактируйте файл.

## Определение и импорт

`gitpoulpi flow detect` ранжирует шаблоны по веткам, которые есть в репозитории, с оценкой из 100 и найденными
конкретными именами (`master` вместо `main`, `dev` вместо `develop`, `features/` вместо `feature/`). Базовые ветки
дают 60 баллов, доля остальных веток, которые распознают специфические шаблоны шаблона, - 40, а долгоживущая ветка
другого шаблона (`develop` у кандидата GitHub Flow) отнимает 25.

`gitpoulpi flow import --from git-flow` читает классические настройки git-flow (`gitflow.branch.master`,
`gitflow.branch.develop`, `gitflow.prefix.feature|bugfix|release|hotfix|support|versiontag`) из собственного
`.git/config` репозитория; `--from git-town` читает `git-town.main-branch` и `git-town.perennial-branches`
(родитель каждой ветки, `git-town-branch.<name>.parent`, подхватывается как записанный родитель). Ничего не
применяется молча: команда выводит TOML, а `--write` создаёт `.gitpoulpi/workflow.toml`, только если его ещё нет.

## Команды

Все они принимают `--json`; сервер MCP предоставляет их как инструменты (`flow_status`, `flow_templates`,
`flow_detect`, `flow_config_show` читают; действия описаны ниже).

| Команда | Что делает |
|---|---|
| `gitpoulpi flow status` | Каждая локальная и удалённая ветка: вид (базовая, тематическая, неклассифицированная), тип тематической ветки и поля, родитель и откуда он взят (`recorded`, `git_town`, `type`, `base`), а для локальных веток - на сколько commit'ов она опережает (`ahead`) родителя и отстаёт (`behind`) от него. Также предупреждения, найденные в определении, ранжированное определение шаблона и настройки другого инструмента, которые можно импортировать. |
| `gitpoulpi flow templates` | Шаблоны выше с их полным определением. Репозиторий не нужен. |
| `gitpoulpi flow detect` | Ранжированные шаблоны с найденными базовыми ветками и типами. |
| `gitpoulpi flow config [--show-effective]` | Общий файл (его путь, существует ли он, разобранный рабочий процесс, неизвестные ключи) или, с `--show-effective`, рабочий процесс, по которому классифицируются ваши ветки. `flow config show` - то же самое. |
| `gitpoulpi flow config init --template <t> [--write]` | Вывести TOML шаблона; `--write` создаёт `.gitpoulpi/workflow.toml` и отказывается перезаписывать существующий. |
| `gitpoulpi flow import --from git-flow\|git-town [--write]` | Как описано выше. |

Счётчики опережения и отставания считаются не больше чем для 300 локальных веток за вызов.

Файл рабочего процесса, который нельзя прочитать (неверный TOML, значение неверного типа), - это ошибка с именем
файла; он никогда не игнорируется молча.

## Действия

`start`, `finish`, `sync`, `promote` и `set-parent` действуют на репозиторий. Каждое сначала **планирует**: выводит
каждый шаг git, который выполнит, с командой git, которой он соответствует, предупреждения, что нельзя отменить, и
всё, что мешает. Пока вы не подтвердите, ничего не меняется. Каждый запуск - **одна запись в истории отмен**
(`gitpoulpi undo` возвращает вместе ветки, tag, удалённую ветку, записанного родителя и checkout).

| Команда | Что делает |
|---|---|
| `gitpoulpi flow start <type> [name=value ...] [--from <ref>] [--publish]` | Называет ветку по шаблону типа (`flow start feature "Login form"` создаёт `feature/login-form`; `flow start release version=1.2.0` создаёт `release/1.2.0`; просто слово - это `slug`; `user` и `date` по умолчанию - вы и сегодня), создаёт её от родителя типа или от `--from` (ветка, удалённая ветка или tag), переключается на неё и записывает её родителя. `--publish` отправляет её с `-u` (`undo` это не отменяет). |
| `gitpoulpi flow finish [<branch>]` | Для каждой цели `finish` типа по порядку: переключиться на цель и влить ветку по стратегии цели (`merge`: всегда commit слияния; `squash`: один commit с заголовком из `--title` или из имени ветки; `rebase`: перебазировать ветку на цель, затем fast-forward; `fast-forward`), создать tag, если он есть у цели (`tag = "v{version}"`, аннотированный), затем переключиться на родителя и удалить локальную ветку, если так сказано в типе (`--delete` / `--keep` переопределяют это; `--delete-remote` удаляет её и на remote, отменить нельзя). С `finish_mode = "merge-request"` (или `--mode merge-request`) только отправляет ветку и открывает pull или merge request в родителя, с `--title`, `--draft`, `--assignee`, `--reviewer`, `--label`, `--milestone` и `--integration` (отменить нельзя; локально ничего не вливается и не удаляется). `--mode local-merge` переопределяет тип `merge-request`, а тип с `ask` требует одного из двух. |
| `gitpoulpi flow sync [<branch>] [--stack] [--rebase\|--merge]` | Приводит в ветку commit'ы родителя: слияние или перебазирование, если стратегия ветки `rebase` (или `--rebase`). С `--stack` - и ветки, чей родитель эта (записан через `set-parent`), рекурсивно, по порядку. Возвращается на ветку, на которой вы были. |
| `gitpoulpi flow promote <env-branch>` | Ветки окружения GitLab Flow: вливает в неё ветку, от которой она зависит (`main` в `pre-production`, `pre-production` в `production`), одним шагом и возвращается. Делает fast-forward, когда может. |
| `gitpoulpi flow set-parent <branch> <parent>` / `--clear` | Записывает (или убирает) `branch.<name>.gitpoulpi-parent`. Отказывается создавать цикл. Можно отменить. |

Ветка, начатая от другого места, завершается там: когда записанный родитель (из `--from` или `set-parent`)
отличается от родителя типа, первая цель завершения - записанный родитель.

### Подтверждение, планирование, скрипты

| Флаг | Значение |
|---|---|
| `--dry-run` | Вывести план в виде JSON (`{"plan": ...}`) и остановиться. Код выхода 1, если что-то мешает. |
| `--yes` | Выполнить без вопроса. |
| ни того, ни другого | В терминале: план показывается и вас спрашивают. Иначе (скрипт, `--json`, агент) план возвращается как `{"needs_confirmation": {"plan": ...}}` с кодом выхода 3 и без изменений. `start` без `--publish` и хуков, `set-parent` и `--abort` подтверждения не требуют. |
| `--run-hooks` / `--no-hooks` | См. [хуки](#хуки). |
| `--autostash` | Спрятать в stash локальные изменения, мешающие checkout или слиянию, и вернуть их после, независимо от `general.auto_stash`. |

Заблокированный план называет причину: базовая ветка там, где нужна тематическая, имя, которое уже существует,
отсутствующее поле (`release/{version}` требует `version=...`), существующий tag, целевая ветка, отстающая от
своего remote (`--allow-behind` продолжает всё равно), уже идущее слияние или перебазирование, ненастроенный
рабочий процесс.

С настройкой **auto-stash** (`general.auto_stash`) рабочие изменения, мешающие checkout или слиянию, прячутся в
stash и возвращаются вокруг действия точно так же, как при обычном checkout; при `never` действие останавливается,
ничего не изменив.

### Конфликты

Слияние или перебазирование, остановившееся на конфликтах, оставляет обычное состояние конфликта (плашку
конфликта, `gitpoulpi conflicts ...`), а процесс запоминается. Код выхода 2, `status: "conflicted"`, пути в
`conflicts`. Разрешите файлы и отметьте их разрешёнными, затем:

- `gitpoulpi flow finish --continue` делает commit слияния (или продолжает перебазирование, или делает commit
  squash с его сообщением) и выполняет оставшиеся шаги;
- `gitpoulpi flow finish --abort` прерывает слияние или перебазирование, возвращается на ветку, с которой процесс
  начался, и забывает остальное. Уже выполненные шаги (первая цель двойного завершения вместе с её tag) остаются:
  `undo` их возвращает.

Процесс, остановленный упавшим хуком, возобновляется так же (`--continue` выполняет этот шаг снова). Запуск с
конфликтом и его продолжение - две записи отмены.

### Запросы на слияние

Ветку отправляет демон; для открытия запроса нужен ваш токен хостинга, поэтому CLI делает это тем же кодом, что и
`gitpoulpi hosting pr` (интеграция, подходящая к remote, иначе готовая веб-страница хоста, напечатанная как URL).
Результат несёт `merge_request` (что запрошено) и `opened` (что ответил хост) или `open_error`, если ветка
отправлена, но запрос открыть не удалось.

### Хуки

`[hooks]` в файле рабочего процесса перечисляет команды оболочки (`after_start`, `before_finish`). Они приходят из
файла, общего для вашей команды, поэтому **никогда не запускаются, пока вы не попросите**: `--run-hooks` или ответ
«да» на вопрос, который терминал задаёт после их перечисления. План всегда их перечисляет, с `hooks_run: false`,
когда они не запустятся. Хук выполняется в оболочке с репозиторием как рабочей папкой и заданными
`GITPOULPI_FLOW_ACTION` / `GITPOULPI_FLOW_BRANCH`; его точная команда, код выхода и весь вывод есть в результате.
Хук, завершившийся с ненулевым кодом, останавливает процесс на этом месте (хук `before_finish` выполняется до
каких-либо изменений, поэтому это обычная ошибка; после хука `after_start` ветка существует, и процесс можно
продолжить или прервать). `--no-hooks` пропускает их без вопроса. Хук может делать что угодно, поэтому `undo`
возвращает только изменения git.

### Для агентов (MCP)

Инструменты - `flow_start`, `flow_finish`, `flow_sync`, `flow_promote` и `flow_set_parent` (finish, sync и promote
помечены как разрушающие, поэтому их ограничивает `allow_mutations`). Они работают по схеме «сначала план, потом
выполнение»: вызовите с `dry_run: true`, чтобы получить план (обычный результат), затем снова с `yes: true`, чтобы
выполнить его. Без того и другого вызов отклоняется и несёт план, так что ничего не запускается случайно. Хуки
запускаются только с явным `run_hooks: true`; план перечисляет их (`hooks`, `hooks_run`), чтобы агент мог заранее
показать пользователю команды. После конфликта - `continue_: true` (флаг называется `--continue`) или
`abort: true`.

### Отмена

| Действие | Что делает `undo` |
|---|---|
| start | Удаляет ветку, забывает её родителя, снова переключается на прежнюю ветку. |
| finish | Восстанавливает каждую сдвинутую ветку, tag, удалённую ветку и checkout за один шаг. Отправленная ветка, удаление на remote и открытый запрос остаются (план об этом говорит). |
| sync | Возвращает каждую обновлённую ветку, а у текущей - и файлы. |
| promote | Возвращает ветку окружения. |
| set-parent | Восстанавливает прежнего записанного родителя. |

## Процессы, управляемые хостом

Для команд, где работу начинает задача: задача пишется по шаблону, а хост (GitLab, GitHub, Gitea, Forgejo) или бот
создаёт ветку и запрос на слияние. GitPoulpi создаёт задачу, ждёт то, что создаст хост, и подхватывает это:
локальную ветку, отслеживающую удалённую, с записанным родителем (цель запроса на слияние), переключённую. Нужно,
чтобы раздел ЗАДАЧИ был привязан к трекеру (`gitpoulpi hosting link issues`); привязка PULL REQUESTS говорит, где
находятся ветки и запросы (проект ЗАДАЧ, если она не привязана).

```toml
[issue_flow]
mode = "bot"                         # local | host-creates-branch | bot
issue_title = "[{type}] {title}"     # {type} {title} {user} {date}
issue_labels = ["workflow::{type}"]  # бот часто срабатывает по метке
description_template = ".github/ISSUE_TEMPLATE/feature.md"   # файл репозитория
branch_from_issue = "{type}/{issue}-{slug}"   # как хост или бот называет ветку
wait_for = "branch-or-mr"            # branch | mr | branch-or-mr
timeout_secs = 600                   # как долго `wait` опрашивает
merge_request = true                 # host-creates-branch: ещё и черновик запроса
assignees = []
```

`{type}` в `branch_from_issue` - это id типа тематической ветки; остальное - обычные подстановки
[шаблона имени](#шаблоны-имён) (`{issue}`, `{slug}`, `{issue_key}`...). Ветка принадлежит задаче 12, когда она
подходит под этот шаблон с `{issue}`, равным 12 (`feature/12-login` подходит, `feature/120-x` - нет).

| Режим | После создания задачи |
|---|---|
| `local` | Ничего на хосте. С `--pick-up` - `flow start` типа с номером и заголовком задачи (отменяется как любой start). |
| `host-creates-branch` | GitPoulpi создаёт ветку **на хосте** от родителя типа (GitLab: API веток; GitHub: `createLinkedBranch`, так что задача показывает её в разделе Development; Gitea/Forgejo: API веток) и **черновик** запроса со строкой `Closes #12`. Хост, который отказывается принимать пустой запрос (GitHub: пока нет commit'ов), оставляет ветку и сообщает об этом предупреждением. |
| `bot` | Ничего: бот (обработчик webhook, задача CI, GitHub App) создаёт ветку и запрос. `--wait` опрашивает, пока не выполнится `wait_for`. |

Что `wait` просматривает у каждого провайдера: собственные связи хоста (GitLab `issues/:iid/related_merge_requests`
и `closed_by`; у GitHub связанные ветки и pull request'ы `connected` / `cross-referenced` из хронологии), ветки,
чьё имя подходит под `branch_from_issue`, и открытые запросы, чья исходная ветка подходит. Он опрашивает с растущей
паузой (1, 2, 3, 5, 8, затем каждые 10 с), пока не выполнится `wait_for` или не истечёт `timeout_secs`, а хост,
который медлит или ненадолго недоступен после ответа, опрашивается повторно. Источник, которого хост не даёт (у
Gitea нет связей задач), пропускается; когда не работают все источники, ответом становится первая ошибка.

| Команда | Что делает |
|---|---|
| `gitpoulpi flow issue new --type <t> --title "..." [--body T \| --body-file F] [--label L] [--assignee A] [--milestone M] [--wait] [--pick-up] [--timeout S] [--integration ID] [--dry-run]` | Создаёт задачу по шаблону (`issue_title`, `issue_labels`, файл описания, `--body` вместо него) и продолжает, как сказано в режиме. `--dry-run` выводит, что было бы создано (`{"plan": ...}`), и ничего не создаёт. `--pick-up` в режиме `bot` сначала ждёт. Код выхода 4: время ожидания вышло (задача существует; `flow issue wait` продолжает ждать). |
| `gitpoulpi flow issue wait <#12> [--type t] [--for branch\|mr\|branch-or-mr] [--timeout S] [--once] [--pick-up]` | Опрашивает то, что хост создал для задачи, с прогрессом в stderr в терминале; Ctrl+C отменяет. `--once` смотрит один раз. Код выхода 4: пока ничего. |
| `gitpoulpi flow pick-up <#12 \| !5 \| branch> [--remote R] [--parent B] [--no-fetch] [--dry-run]` | Выполняет fetch, создаёт локальную ветку, отслеживающую `origin/<branch>`, записывает её родителя и переключается на неё. `#12` ищет на хосте ветку или запрос задачи, `!5` - запрос, всё остальное - имя ветки. Родитель - цель запроса (`--parent` переопределяет), иначе родитель типа. `--yes` не нужен: действие локальное и отменяемое, как `start`. `--dry-run` всё равно делает fetch (он двигает только ссылки удалённого отслеживания, а плану нужно увидеть ветку). |

`pick-up` - одна запись в истории отмен: `gitpoulpi undo` удаляет ветку, забывает родителя и снова переключается на
прежнюю ветку (fetch остаётся, как любой fetch). Он планируется, как остальные действия: `--dry-run` выводит его
план (`create_branch`, `set_upstream`, `checkout`, `record_parent`) и действуют обычные препятствия (рабочие
изменения следуют настройке auto-stash). Запрос - `{"action": "pick_up", "branch": ..., "parent": ...}`.

Задачи, созданные процессом, **отслеживаются** (`watched_issues` в `.gitpoulpi/repo-state.toml`, никогда не
попадает в commit): после каждого fetch приложение сопоставляет удалённые ветки с `branch_from_issue` и сообщает,
когда появилась ветка отслеживаемой задачи. Подхват закрывает вопрос.

### Для агентов (процессы, управляемые хостом)

Инструменты - `flow_issue_new`, `flow_issue_wait` и `flow_pick_up` (запись, сеть; их ограничивает
`allow_mutations`). `flow_issue_new` с `dry_run: true` возвращает план; `flow_issue_wait` блокируется до `timeout`
секунд, поэтому агенту дайте короткий и вызовите его снова (`once: true` отвечает сразу). Оба возвращают JSON с
`found` (`branches`, `requests`) и `timed_out`.

### Процессы, управляемые хостом, в приложении

Если есть рабочий процесс и привязанный трекер, меню Flow получает *Новая задача (<тип>)...* (по одной на тип;
палитра `Flow: новая задача (<тип>)...` и `Flow: новая задача...`) и *Подхватить ветку, созданную хостом...*
(палитра `Flow: подхватить ветку хоста...`).

- **Новая задача** спрашивает тип (выпадающий список) и заголовок; показывает, откуда берётся описание и кто
  создаёт ветку. *Подхватить ветку, когда она появится* включено по умолчанию. *Создать задачу* создаёт её, затем в
  режиме `bot` показывает **карточку ожидания**: индикатор, чего она ждёт, прошедшее время и время, когда она
  сдастся, и **Не ждать** (`Esc`). Остановка не теряет задачу: она остаётся отслеживаемой. Когда ветка появляется,
  она подхватывается, и строка состояния об этом сообщает.
- **Появилась ветка** - карточка, которая открывается, когда fetch принёс ветку отслеживаемой задачи (если не
  открыто другое окно): *Подхватить* берёт её под контроль, *Позже* закрывает карточку (она не предлагается снова,
  пока приложение не перезапущено).
- **Подхватить** принимает `#12`, `!5` или имя ветки и показывает, что нашлось, прежде чем подхватить.

Всё выполняется в фоне; вызов дольше 150 мс показывает индикатор.

### Проверка на стенде

`scripts/fake-gitlab-bot.sh` - бот-заменитель для Docker GitLab (`scripts/test-bench.sh`): он следит за проектом на

### Настройки > Рабочий процесс

**Настройки > Настройки репозитория > Рабочий процесс** редактирует определение. Он работает с черновиком и ничего
не сохраняет, пока вы не нажмёте кнопку сохранения.

- **Шаблон** - выпадающий список готовых шаблонов; выбор шаблона заменяет базовые ветки и типы ниже на шаблон (ваши
  хуки и процесс задач остаются).
- **Определить по веткам** читает имена веток этого репозитория и показывает ближайший шаблон с его оценкой,
  найденные имена баз (`master` вместо `main`), сколько веток распознаёт каждый тип с примерами и оценку каждого
  шаблона. **Использовать найденный процесс** загружает его в черновик.
- Когда в репозитории лежит конфигурация другого инструмента (`gitflow.*` от Git Flow, `git-town.*` от Git Town),
  предлагается **Импортировать**, и она загружает импортированное определение в черновик. Ничего не применяется,
  пока вы не нажмёте.
- **Базовые ветки**, **Типы веток** и их **Правила завершения** - это один [список](settings.md#списки)
  с группами на вкладке **Правила**; вкладка **Общие** содержит остальное (шаблон, определение, хуки,
  процесс задач). Выберите элемент, чтобы
  править его справа (имя и другие имена, родитель, защита, стратегия слияния, tag при слиянии, ветка
  окружения; название, шаблон имени, другие шаблоны, регулярное выражение, родитель, режим завершения, удалить
  после завершения). **+ Добавить ▾** выбирает, что добавить (правило завершения относится к выбранному типу
  ветки); добавление, дублирование, удаление и перетаскивание работают как в любом списке Настроек, а элементы
  перемещаются внутри своей группы. Строка
  **Шаблон имени** перечисляет подстановки (`{slug} {issue} {issue_key} {user} {date} {version} {n}`); под ней
  живой просмотр показывает существующие ветки, подходящие под шаблон, и имя, которое он создал бы, а шаблон,
  который не разбирается, объясняет почему красным прямо под полем (набранное не теряется).
- **Хуки** - команды оболочки, по одной на строку (`После начала`, `Перед завершением`), правятся в многострочном
  редакторе (`Ctrl+S` сохраняет, `Esc` отменяет). Они выполняют команды на вашем компьютере: страница об этом
  предупреждает, а окна показывают их перед запуском.
- **Процесс задач** содержит поля, которые используют [процессы, управляемые хостом](#процессы-управляемые-хостом)
  (режим, заголовок и метки задачи, шаблон ветки, чего ждать), они хранятся в файле рабочего процесса.
- **Проблемы** перечисляет, что в определении не так (несуществующий родитель, неработающий шаблон).
- Панель, закреплённая внизу страницы, показывает **● Не сохранено** (или **Нет изменений**).
  **Сохранить в общий файл** записывает черновик в `.gitpoulpi/workflow.toml` (сделайте для него commit),
  сохраняя ключи, которых эта версия не знает, и вносит в него ваше переопределение. **Только для меня**
  хранит лишь отличие от общего файла в состоянии вашего репозитория (`.gitpoulpi/repo-state.toml`, не попадает
  в commit). **Отбросить изменения** читает сохранённое заново. Закрытие настроек с несохранённым черновиком
  сначала спрашивает.

### Боковая панель

LOCAL и REMOTE сгруппированы по рабочему процессу: сначала базовые ветки, каждая с отметкой `[базовая]`
(`[базовая, защищена]`, если защищена), затем по папке на каждый тип тематических веток с названием типа и числом
веток (`Feature (3)`), затем ветки, которые не заняты ни одним типом, в папке «Прочие». Папки сворачиваются как
любые папки; обычные деревья возвращаются через *Flow > Показывать ветки обычными списками* (строка меню Flow) или
команду палитры `Flow: переключить группировку веток`. Если задержать указатель на ветке, подсказка показывает её
тип, родителя и на сколько она отстаёт от родителя (и опережает его).

### Меню Flow и его окна

Кнопка **Flow** на панели инструментов (`Ctrl+G Shift+W`, палитра `Flow: открыть меню`) перечисляет *Начать <Тип>...* для
каждого типа тематических веток, *Завершить текущую ветку...*, *Синхронизировать с родителем...*, *Продвинуть...*
(ветки окружения GitLab Flow), *Задать родителя...*, переключатель группировки и *Настройки рабочего процесса...*.
В палитре те же команды (`Flow: начать Feature...` создаётся для каждого типа).

- **Начать** - форма, построенная по шаблону имени типа: по полю на подстановку. У `{issue}` и `{issue_key}`
  есть выпадающий список задач привязанного трекера, который заодно заполняет `{slug}` заголовком задачи;
  `{version}` предлагает версию после вашего старшего tag'а релиза; `{user}` - ваш активный профиль; `{date}` -
  сегодня. Строка показывает имя ветки, которое даёт шаблон (или почему оно невозможно: недопустимая ссылка, имя уже
  занято). «Начать с» - выпадающий список (родитель типа первым), а *Опубликовать ветку* отправляет новую ветку.
- **Завершить**, **Синхронизировать**, **Продвинуть** и **Задать родителя** спрашивают нужное, затем показывают
  **предпросмотр**, который считает демон (тот же план, что печатает `gitpoulpi flow ... --dry-run`): каждый шаг по
  порядку, предупреждения (цель отстаёт от remote, ветки, построенные на этой) и **препятствия** (цель не существует,
  цель отстаёт от remote), которые выключают кнопку запуска и говорят почему. Шаги, которые нельзя вернуть
  (отправка, удаление удалённой ветки, запрос на слияние), помечены `!` и цветом, со строкой «Отмена не вернёт: ...».
  Хуки, которые запустились бы, перечислены под предупреждением с флажком *Запустить хуки* (по умолчанию выключен).
  Если режим завершения типа - `ask`, «Завершить» сначала спрашивает *Завершить через*: локальное слияние или
  открытие pull либо merge request.
- Затем действие выполняется с отметкой на каждом шаге (индикатор через 150 мс), и окно показывает, как прошёл
  каждый шаг. Всё действие - **одна запись отмены**: `Ctrl+Z` возвращает начало, завершение, синхронизацию или
  продвижение сразу (история отмен читается как `Flow finish feature/login`); отправки, удаления на remote и
  запросы на слияние остаются, как сказал предпросмотр.
- **Конфликт** останавливает действие кнопками **Продолжить** и **Прервать**. Окно можно закрыть, чтобы разрешить
  конфликт обычными инструментами для конфликтов, и снова открыть командой палитры
  `Flow: продолжить или прервать остановленное действие...` (это же строка меню Flow, пока действие остановлено);
  «Продолжить» отказывает, пока остаются файлы в конфликте, и оставляет обе кнопки. «Прервать» возвращает на ветку,
  с которой действие началось; уже выполненные шаги остаются (отмена их возвращает).
- Завершение через **запрос на слияние** отправляет ветку, затем открывает обычную форму *Создать pull request*
  (*Создать merge request* в GitLab) с заполненными полями: цель - родитель ветки, заголовок берётся из ветки (и
  задачи). Кнопки метаданных (исполнители, рецензенты, метки, этап) работают как в любом pull request. Если ни одна
  интеграция не отвечает за remote, вместо этого в браузере открывается URL сравнения (и показывается в строке
  состояния).
- Тексты шагов и препятствий английские, как у CLI; собственный текст окна переведён. Рабочее дерево с изменениями
  следует настройке `auto-stash`.

Всё это доступно с клавиатуры и из палитры, а каждый выпадающий список - комбобокс (Enter открывает, набор
фильтрует, Enter выбирает).

Строки, управляемые хостом (*Новая задача (<тип>)...*, *Подхватить ветку, созданную хостом...*), описаны
[выше](#процессы-управляемые-хостом-в-приложении).
