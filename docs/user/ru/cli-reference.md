# Справочник по CLI

`gitpoulpi` без подкоманды открывает окно; с подкомандой это скриптуемый git-клиент.
Каждая команда идёт через тот же фоновый демон, что и окно, поэтому изменение,
сделанное из скрипта, сразу появляется в открытом GitPoulpi. MCP-инструменты,
которые получает агент, генерируются из этих же команд ([MCP и агенты](mcp-and-agents.md)).
`gitpoulpi <команда> --help` показывает все флаги.

## Глобальные флаги

| Флаг | Действие |
|---|---|
| `--json` | Вывести результат в JSON. Ошибки тоже в JSON: `{"error": "..."}` в stdout, код выхода 1. Неудавшаяся операция git добавляет `"detail": {"operation", "command", "exit_code", "stderr"}` (выполненная команда git с замаскированными секретами, её код возврата и конец её stderr; для встроенной библиотеки git `"git2": {"class", "code", "message"}`); инструменты MCP возвращают тот же объект. Без `--json` строки идут в stderr. |
| `--repo <path>` | Репозиторий, с которым работать (по умолчанию тот, в котором находится текущая папка, как у git). |
| `-s, --session <name>` | Сессия (демон), с которой говорить. По умолчанию выводится из корня репозитория: всё, что открыто внутри одного репозитория, делит один демон, а два репозитория получают два. |
| `--backend git2\|system` | Бэкенд для демона, который запускает эта команда (уже работающий сохраняет свой). |
| `--cwd-file <file>` | Куда окно записывает папку активной вкладки при выходе (используется `shell-init`). |
| `-l, --lang <lang>` | Язык только текста `--help`: `en`, `fr`, `es`, `pt-BR`, `pt-PT`, `it`, `de`, `zh-CN`, `ja`, `ko`, `ru`, `uk`, `pl`, `cs`, `nl`, `sv`, `tr`. См. [Переведённая справка](#переведённая-справка). |
| `-a, --add [path]`, `--no-raise` | Открыть папку новой вкладкой уже запущенного GitPoulpi вместо запуска ещё одного; см. [Добавление папки в открытое окно](#добавление-папки-в-открытое-окно). Подкоманд не принимает. |

### Добавление папки в открытое окно

`gitpoulpi --add [path]` (`-a`; `gp -a` и псевдоним команды `gpa` выполняют тот же
код) открывает `path` (по умолчанию текущую папку, приведённую к содержащему её
репозиторию) новой вкладкой уже запущенного GitPoulpi, так что папка, в которую вы
перешли командой `cd` в терминале, не запускает второе окно.

- *Запущенная сессия* - та, чей демон отвечает и к которой подключено окно GitPoulpi. Окна, в которых
  выключено **Разрешить ИИ-агентам управлять видом**, о себе не сообщают и не находятся (то же
  ограничение у `gitpoulpi launch`).
- Одна запущенная сессия: она получает вкладку (или показывает её, если этот репозиторий уже открыт),
  её окно выходит на передний план, когда рабочий стол это позволяет (Windows, WezTerm, Hyprland;
  `--no-raise` это пропускает), и одна строка сообщает, какая сессия её получила.
- Несколько: они выводятся нумерованным списком с числом вкладок и названиями репозиториев; введите
  номер и Enter (пустая строка или Esc, затем Enter отменяет, код выхода 130). Без терминала на stdin команда
  завершается ошибкой и просит передать `--session NAME`. `-s NAME` снимает вопрос.
- Ни одной (или `-s NAME` называет сессию, которая не запущена): GitPoulpi запускается как обычно в этом
  терминале, в этой папке, точно как `gp [path]`.
- Окно применяет это сразу, как ваш собственный выбор (без чипа подтверждения и отметки агента), если только
  вы не вводите текст в форме: тогда окно предлагает вкладку в чипе строки состояния, а код выхода 3.
  Папка вне репозитория отклоняется (код выхода 1).

`--json` выводит один объект: `{"action": "joined", "session", "repo", "already_open", "raised", "outcome": {...}}`
(`outcome` - ответ окна, как у `ui show`) или `{"action": "cancelled"}`; ошибки имеют вид `{"error": "..."}`.
Коды выхода: 0 вкладка открыта, 3 предложена в чипе, 1 отклонено или ошибка, 130 отменено. MCP-инструмента для
этого нет: агент, который хочет показать репозиторий пользователю, использует `ui show tab`.

### Переведённая справка

`gitpoulpi --help` выводится на английском. Добавьте `-l`, чтобы читать пояснения
на другом языке: `gitpoulpi -l fr --help`, `gitpoulpi -l de commit --help`.
Переводятся только пояснения и заголовки разделов. Названия команд, флаги, имена
значений и допустимые значения не меняются, поэтому скрипты и агенты видят один и
тот же интерфейс. Язык справки не берётся из окружения: вывод меняется, только
если вы указали `-l`. Описания MCP-инструментов всегда на английском.

Ревизии принимают всё, что принимает git (`HEAD~2`, ветку, tag, короткий sha).
Hunk'и и строки нумеруются так, как их нумерует `gitpoulpi --json diff`.

## Команды

**Просмотр**

| Команда | Что делает |
|---|---|
| `status` | Файлы в индексе, вне индекса, неотслеживаемые и с конфликтами. |
| `log [--graph] [--limit N] [--skip N] [--path P] [--count]` | История; `--skip` + `--limit` листают её, `--path` даёт историю файла. `--count` выводит только `{"total": N}` - число commit'ов, которые охватывает обход (`--limit`/`--skip` игнорируются), то самое число после косой черты в строке состояния TUI (`500 / 2500 commit'ов`). |
| `log --format mermaid [--detail structure\|refs\|subjects\|full] [--orientation lr\|tb] [--fence] [--range A..B] [--limit N] [--subject-width N]` | Commit'ы в виде скрипта Mermaid `gitGraph`, того же, что делает окно [Копировать как Mermaid gitGraph](log-and-history.md#копирование-commitов-как-mermaid-gitgraph) в Log. `--range A..B` - это `git log A..B` (просто `A` означает `A..HEAD`); иначе берутся первые `--limit` commit'ов (по умолчанию 30). Детализация, направление и ограждение по умолчанию берутся из `ui.mermaid_*`. С `--json`: `{format, detail, commits, text}`; обычный вывод - это сам скрипт. |
| `diff [--staged] [--path P] [--name-only]` | Diff рабочего дерева (или индекса) в виде hunk'ов и строк; `--name-only` перечисляет только изменённые файлы и их статус. |
| `diff --from <rev> [--to <rev\|worktree>] [--name-only]` | Сравнивает две ревизии или ревизию с рабочим деревом (`--to` по умолчанию `worktree`: проиндексированные и непроиндексированные изменения отслеживаемых файлов). Тот же список, что и [сравнение](log-and-history.md#сравнение-commitов) в Log. |
| `show <path> [--at REV \| --staged \| --worktree] [--raw [--output FILE]]` | Содержимое файла в ревизии, в индексе или на диске. Изображение несёт `image: {format, width, height}` в `--json` (читается из его заголовка). `--raw` пишет точные байты в stdout или в `--output FILE` (указатель LFS даёт свой локальный объект). Недоступно через MCP. |
| `blame <path> [--at REV]` | Кто изменил каждую строку. Учитывает переименования целых файлов. Каждая строка несёт свой commit, время автора и коммиттера, `orig_path` (имя файла в этом commit'е) и `previous` (`[родитель, путь]`: где повторить blame, чтобы увидеть строку до этого commit'а; отсутствует у строки, появившейся в корневом commit'е или в commit'е, чей родитель не содержит файла). |
| `file-history <path> [--at REV] [--skip N] [--limit N]` | Commit'ы, изменившие файл, новые первыми, **с учётом переименований** (`git log --follow`). Каждая запись содержит commit, родителей, автора, время автора и коммиттера, описание, `path` файла в этом commit'е, `change` (`Added`, `Modified`, `Deleted`, `{Renamed: {from}}`) и числа строк `added`/`removed` (null для бинарного файла). `--limit` по умолчанию 100; `more` сообщает, есть ли более старые записи; `--skip` + `--limit` листают. Merge перечисляется, только если отличается от каждого родителя, с числами относительно первого родителя. В отличие от `log --path`, переименование не обрывает историю. |
| `conflicts list [--names-only]` | Файлы с конфликтами и текст трёх их сторон; `--names-only` - дешёвый список (путь, вид, oid стадий). |
| `conflicts show <path> [--conflict N]` | Один файл с конфликтами: подписи панелей, три стороны, пронумерованные области конфликтов A/B (`--json` даёт документ целиком). |
| `conflicts resolve <path> --side ours\|theirs\|base` | Разрешить файл одной из сторон (`--ours` / `--theirs` - сокращения). |
| `conflicts resolve <path> --both [--theirs-first]` | Оставить обе стороны каждого конфликта (A затем B или B затем A). |
| `conflicts resolve <path> --pick 1=a,2=ba [--default a\|b]` | Выбор для каждого конфликта: `a` наш, `b` чужой, `ab`, `ba`, `none`. Отклоняется с `pick_incomplete`, если выбор задан не для каждого конфликта и нет `--default`. |
| `conflicts resolve <path> --content-file F\|- [--encoding L]` | Записать заданный итоговый текст (UTF-8 или в кодировке `L`). |
| `conflicts resolve <path> --delete` | Принять удаление (конфликты delete/modify): `git rm`. |
| `conflicts resolve ... [--no-stage] [--expect base,ours,theirs]` | `--no-stage` сохраняет без пометки «разрешено»; `--expect` - защита от устаревших данных (oid стадий, `-` для отсутствующей). |
| `conflicts unresolve <path>` | Вернуть файл, разрешённый во время этой операции, в состояние конфликта. |
| `conflicts check` | Привёл бы merge HEAD в ветку, от которой он ответвился, к конфликту? `{"status": "conflicts"\|"clean"\|"no-base"\|"disabled", "head", "base_ref", "base", "base_source": "globs"\|"pull-request", "files": [...]}`. Слияние в памяти (рабочее дерево, индекс и ссылки не меняются; нужен git 2.38 или новее с системным бэкендом, иначе `disabled`). Только чтение; также инструмент MCP `conflicts_check`. См. [Разрешение конфликтов слияния](merge-conflicts.md#предотвращение-конфликтов). |
| `conflicts state` | Идущие merge, rebase, cherry-pick или revert (`null`, если ничего нет). |
| `conflicts abort` | Прервать эту операцию (разрушительно: отбрасывает сделанные с тех пор разрешения). |
| `conflicts skip` | Пропустить идущий cherry-pick или revert (или commit, на котором остановился rebase): HEAD, индекс и рабочее дерево возвращаются к HEAD. Выход из пустого шага; у слияния пропускать нечего (разрушительно, не отменяется). |
| `conflicts am-continue` | Продолжить идущий `git am` после того, как вы разрешили и добавили в индекс файлы патча (`{"outcome":"Completed"}` или `"Stopped"`). |
| `conflicts am-skip` | Пропустить патч, на котором остановился `git am`. |
| `conflicts am-abort` | Прервать `git am` (разрушительно: ветка возвращается к состоянию до `am`). |
| `job list` | Фоновые задачи демона, от старых к новым: каждый fetch, push, pull, clone и передача LFS становится задачей с момента получения (в очереди, выполняется или завершилась за последние 30 с). JSON: id, kind, state, phase, progress, `not_cancellable`, `error`. |
| `job cancel <id>` | Остановить задачу. Отклоняется (код 1, ничего не меняется), если остановка уже небезопасна. Ctrl+C у команды, запустившей задачу, отменяет эту задачу. |
| `job wait <id> [--timeout S]` | Ждать окончания задачи и вывести её итоговое состояние; код 0 при `Done`, 1 при ошибке, отмене или тайм-ауте. |
| `index-lock show` | `index.lock` репозитория (`null`, если нет): путь, возраст в секундах, `stale` (старше 10 с). |
| `index-lock remove` | Удалить устаревший `index.lock`. Отклоняется, пока ему меньше 10 с, или если его нет. |
| `rebase-plan [<upstream>] [--root]` | Commit'ы, которые повторил бы интерактивный rebase, от старых к новым. |

**Индекс и commit**

| Команда | Что делает |
|---|---|
| `stage --file F \| --folder D \| --all [--hunk N [--lines a,b]] [--allow-sensitive]` | Добавить в индекс файл, папку, всё, hunk или несколько строк. Добавление файла, папки или `--all`, которое внесло бы конфиденциальный файл (закрытый ключ, `.env`, распознанный токен: `[privacy]` в [справочнике по конфигурации](config-reference.md#privacy-конфиденциальные-файлы)), отклоняется с кодом выхода 2 и `{error: "sensitive_files", files: [{path, reason}]}` (правило и маскированный фрагмент, но не значение); ничего не добавляется. `--allow-sensitive` всё равно добавляет их. |
| `unstage` (те же флаги) | Обратное действие. |
| `discard --file F [--hunk N [--lines a,b]]` | Отбросить изменения вне индекса (целый файл: все изменения, неотслеживаемый файл удаляется). Можно отменить. |
| `rm-file <paths>...` | Удалить файлы из рабочего дерева. Можно отменить. |
| `ignore <pattern> [--file <.gitignore>]` | Дописать шаблон в `.gitignore` (или в `.git/info/exclude` с `--file .git/info/exclude`). Можно отменить, кроме `.git/info/exclude`. |
| `convert <paths>... (--encoding <name> \| --eol lf\|crlf\|cr \| --indent spaces:<n>\|tabs:<n>)` | Переписывает кодировку, окончания строк или отступы файлов рабочего дерева. Двоичные, отсутствующие и не поддающиеся кодированию файлы пропускаются и перечисляются в отчёте. Одна запись отмены на всю пачку. |
| `treat binary\|text <paths>... [--extension \| --folder] [--file <.gitattributes>]` | Заставляет git считать файлы двоичными (`binary`) или текстовыми (`text diff`), записывая правило `.gitattributes`, по умолчанию в файл в корне. Отменяется, кроме `.git/info/attributes`. |
| `commit -m <msg> [--amend] [--no-verify]` / `commit --ai` | Сделать commit; `--ai` пишет сообщение встроенным ИИ. Хуки репозитория `pre-commit` / `commit-msg` выполняются, если их не пропустить через `--no-verify` (с этого значения начинается «Пропустить хуки» в Настройки > Commit). |
| `split-source <commit>` | Изменения commit'а, пронумерованные для разделения: `{commit, parent, message, files:[{path, status, whole_only, hunks:[{id, lines:[{origin, content}], ...}]}]}`. Файлы с `whole_only` (двоичные, только смена режима, добавленные, удалённые, подмодули, lfs) можно назначить только целиком. Только чтение. |
| `split-commit <commit> --plan <file\|-> [--rest-message M] [--sign] [--dry-run]` | Разделить commit текущей ветки на несколько, от старого к новому. План: `{"parts":[{"message":"feat: parser","pieces":[{"path":"src/parse.rs","hunk":0},{"path":"src/parse.rs","hunk":1,"lines":[2,3]},{"path":"logo.png"}]}]}`; часть без `hunk` - это весь файл, `lines` - индексы в `lines` hunk'а. Каждое изменение должно быть назначено ровно один раз; `--rest-message` помещает всё, что осталось вне плана, в последний commit. Последний новый commit сохраняет исходное дерево, поэтому потомки, индекс и рабочее дерево не меняются; для уже отправленного commit'а затем нужен force push, а подписи в переписанном диапазоне отбрасываются, если не указать `--sign`. Выводит `{created, previous_head, new_head, replayed}`; один `undo` возвращает всё. `--dry-run` выводит `{dry_run, valid, refusal, parts, unassigned}` и ничего не меняет. Отказ выводит `{"refused":{reason, message, unassigned}}` с кодом выхода 2. |

Правила трейлеров (`--trailer-add KEY=VALUE`, `--trailer-remove KEY`, `--trailer-map KEY:OLD=NEW`, можно повторять, в таком порядке после `--replace-message`) правят строки `Key: value` последнего абзаца каждого сообщения по грамматике `git interpret-trailers`: `--trailer-add` пропускает сообщение, где такой трейлер уже есть в точности, `--trailer-remove` убирает все трейлеры с этим ключом, `--trailer-map` заменяет дословный текст в значениях этого ключа; остальное сообщение не меняется (рецепт может также задать `if_exists` `replace` или `skip`, шаблон `find` у `remove` и шаблоны `regex`). `--map-trailers` (нужны флаги личности) заставляет правило личности менять и подходящие трейлеры `Name <email>`. `--update-message-hashes` заменяет в сообщениях сокращённые id commit'ов (7+ шестнадцатеричных символов) новыми id той же длины, когда подходит ровно один переписанный commit; `counts.message_hashes_updated` и `counts.message_hashes_left` плана (неоднозначные, неизвестные или созданные позже) говорят, что произошло. Правила содержимого (`remove_paths`, `remove_blobs_over` и `content_replace` рецепта или флаги `--remove-path`, `--remove-blobs-over`, `--replace-content`) переписывают файлы каждого commit'а: каждый уникальный файл читается один раз, двоичные файлы пропускаются и считаются (`counts.blobs_skipped_binary`), commit, который правило оставило пустым, удаляется (`counts.commits_dropped`, строки с `new: null`; `--prune-empty never` оставляет его), его потомки переходят на его родителя, а файлы в рабочем дереве следуют за новым деревом. Отказ `dirty_paths_touched`, если файл с локальными изменениями входит в те, что изменило бы переписывание, `checked_out_elsewhere`, если переписываемая ветка открыта в другом рабочем дереве, `partial_clone` в частичном клоне. Правила путей (`--move-path FROM=TO`, можно повторять; `--into-subdir DIR`; `--extract DIR` или `move_paths` рецепта) переименовывают файл или папку, переносят весь репозиторий в подпапку или оставляют только подпапку как новый корень; они работают с деревьями, поэтому у каждого файла сохраняется его id, и выполняются после правил содержимого. Переименование никогда не перезаписывает: если новый путь существует в каком-то commit'е, предпросмотр отклоняется как `path_collision` (код выхода 2), а короткие id commit'ов и пути указаны в `refused.detail`. `--extract` **спрашивается каждый раз**: без `--extract-mode` (`clone`, `in-place` или `submodule`) предпросмотра нет, а ответ - `{"needs_choice":{choice:"extract_mode", options, prompt}}` с кодом выхода 3. `in-place` переписывает этот репозиторий, как любое правило (одна запись отмены; ветки и tag'и, где от папки ничего нет, удаляются, строки с `refs[].new: null`; в текущей ветке папка должна быть, иначе `empty_scope`). `clone` и `submodule` показывают в предпросмотре историю, которую получит новый репозиторий, по всем локальным веткам и tag'ам, ничего не отправляется и ничего не защищается, а применяются они с папкой нового репозитория: `--target PATH` у `run` или у `apply` (`rewrite apply` такого плана без `--target` отклоняется как `invalid_rule`; папка не должна существовать или должна быть пустой и не лежать внутри репозитория). `clone` делает там `git clone --no-local` этого репозитория, переписывает его по рецепту, убирает remote, истекает reflog и вычищает старые объекты, так что в нём остаётся только вынесенная история; этот репозиторий не затрагивается и ничего не журналируется (`outcome.moved` пуст). `submodule` делает то же, затем добавляет в текущую ветку один commit, который заменяет папку подмодулем нового репозитория (URL в `.gitmodules` - его локальный путь), инициализирует его и журналирует (в `outcome.moved` есть ветка; `undo` возвращает её и освобождает подмодуль); история не переписывается, поэтому старые commit'ы сохраняют папку. Изменённые или неотслеживаемые файлы в папке, а также отсоединённый HEAD блокируют его. Порядок при сочетании: сначала по исходным путям идут правила содержимого (`--replace-content`, `--remove-blobs-over`, `--lfs-import`, `--lfs-export`) и `--remove-path`, затем правила путей; шаблон LFS и шаблон удаления поэтому называют исходные пути, а строки `.gitattributes` при переносе в LFS добавляются в исходном корне и затем перемещаются вместе с файлами. **Правила LFS** (`lfs_import { patterns, min_size }` и `lfs_export { patterns }` рецепта или `--lfs-import PATTERN...` с `--lfs-min-size BYTES` и `--lfs-export PATTERN...`) требуют `git-lfs` (иначе `tool_missing`): перенос превращает подходящие файлы в указатели spec v1 в каждом commit'е, при применении записывает содержимое в локальное хранилище LFS (атомарно, по одному разу на каждое содержимое) и добавляет `<pattern> filter=lfs diff=lfs merge=lfs -text` в корневой `.gitattributes` каждого переписанного commit'а, где есть указатель (остальной файл не меняется); возврат превращает подходящие указатели обратно в файлы и убирает эти строки и отклоняется как `lfs_objects_missing` (`detail`: по одной строке `<oid> <path>`), если объектов нет в локальном хранилище (сначала `lfs fetch`). `counts.lfs_blobs`, `lfs_bytes`, `lfs_objects`, `lfs_restored` и `lfs_run` плана говорят, что происходит, строки перечисляют пути `lfs_imported` / `lfs_exported`, а файлы в рабочем дереве остаются настоящим содержимым (при применении устанавливаются фильтры LFS репозитория, если их нет). Затем отправьте объекты командой `lfs push --all`. **Текстовые правила** (`line_endings`, `strip_exec` и `reencode` рецепта или `--eol`, `--strip-exec`, `--reencode`): `--eol lf\|crlf\|cr --eol-paths GLOB...` задаёт каждому текстовому файлу, названному шаблонами, это окончание строк (смешанные окончания становятся единообразными; `--eol-exclude` не трогает файлы; `--eol-follow-attributes` читает корневой `.gitattributes` каждого commit'а: файлы `-text`/`binary` пропускаются, а файлы с `eol=` сохраняют своё окончание); `--strip-exec GLOB...` меняет режим 100755 на 100644 у подходящих файлов (нужен хотя бы один шаблон, `--strip-exec-exclude` щадит часть файлов); `--reencode utf-8\|utf-8-bom\|utf-16le\|utf-16be\|windows-1252\|iso-8859-1 --encoding-paths GLOB...` преобразует текстовые файлы в эту кодировку, из `--from SOURCE` или, по умолчанию, определяемой для каждого файла (метка порядка байтов, корректный UTF-8, иначе `--encoding-fallback`, по умолчанию `windows-1252`). Они выполняются на этапе содержимого вместе с другими правилами содержимого, в порядке рецепта. Двоичные файлы пропускаются и считаются (`counts.blobs_skipped_binary`); файлы, которые не читаются в исходной кодировке или не вмещаются в целевую, остаются как есть и считаются в `counts.blobs_skipped_undecodable`; `counts.blobs_changed` - число новых версий файлов, а строки перечисляют изменённые пути как `modified`. `diff` показывает, что правила сделали с одним файлом одного commit'а из проверенного запуска (`{kind, binary, redacted, old_size, new_size, hunks}`); строки, которые удаляет правило секретов, скрыты. Lua-скрипты (`--script FILE`, можно повторять, выполняются по порядку после остальных правил; файл встраивается в рецепт) вызывают `rewrite_commit(c, ctx)` на каждом commit'е и могут вернуть новые `author` / `committer` (`name`, `email`, `time`, `offset_minutes`) и `message`, а также `state`, передаваемое следующему вызову; заголовок скрипта `--!` объявляет его параметры, окно и требования. В песочнице нет файлов, часов, процессов и модулей, а число инструкций (10 миллионов на вызов), память (64 МиБ) и время (5 с на вызов) ограничены. `script check` печатает `{header, functions, problems}` (код выхода 2, если `problems` не пуст); `script test` запускает скрипт на нескольких commit'ах, ничего не записывая, и печатает `{rows: [{commit, fields, log}]}`. Упавший скрипт отклоняется как `script_failed` с `refused.script = {commit, reason}`. **Внешние скрипты** (язык `shell`, `python` или `lua-external`: `--script-language` / `--language`, по умолчанию по расширению файла `.sh`, `.bash`, `.ps1`, `.py`, `.lua`, иначе встроенный Lua) выполняются отдельным процессом с вашими правами, без песочницы: по одному JSON-запросу в строке на stdin, по одному JSON-ответу в строке на stdout, с теми же полями, что выше, `"error": "text"`, чтобы сдаться, диагностика в stderr (она возвращается как `log` commit'а). Окружение очищено (передаются только `PATH`, `HOME`/`USERPROFILE`, `SYSTEMROOT`, `TEMP`/`TMP` и `LANG`), рабочий каталог - новый временный, `rewrite.script_timeout_ms` (5000) ограничивает каждый ответ, а `rewrite.script_total_timeout_s` (3600) - весь прогон; при тайм-ауте, сбое или отмене убивается всё дерево процессов, а переписывание отклоняется как `script_failed` (с commit'ом и причиной), ничего не сдвинув. Какие языки доступны, задаёт параметр `rewrite.external_scripts` (по умолчанию `["shell"]`; `"python"` или `"lua"` добавьте сами): выключенный язык отклоняется как `scripts_disabled`, отсутствующий интерпретатор - как `tool_missing` (`rewrite tools` их перечисляет). **Доверие**: внешний скрипт запускается, только если человек доверился именно его тексту: `rewrite script trust FILE` (или `--trust` у `preview`, `run`, `script check` и `script test`, что делает это в той же команде) запоминает SHA-256 файла для этого репозитория, а изменённый скрипт спросит снова. Недоверенный скрипт отклоняется как `script_not_trusted` с `refused.script = {hash}` и никогда не запускается, даже командой `script check`, которая сообщает `{trust: "untrusted", hash}` с кодом выхода 2; для доверенного `script check` один раз запускает его с выдуманным commit'ом (`"dry_run": true`), чтобы проверить ответ, и печатает ещё `interpreter`. MCP-сервер доверять не может: у него нет инструмента `rewrite script trust` и аргумента `trust`, поэтому агент запускает только скрипт, которому человек доверился раньше. `scan-secrets` один раз читает историю области (текущая ветка, `--all-local` или `--ref`) и печатает `{findings: [{id, rule, path, more_paths, first_commit, last_commit, commits, blobs, preview}], commits, blobs_scanned, blobs_skipped_binary, blobs_skipped_large}`: сработавшее правило (префиксы токенов, закрытые ключи, JWT, пароли в URL, похожие на случайные строки `password = value`), скрытый `preview` вида `ghp_****abcd` и никогда само значение; поиск неполный, и он только читает. `analyze` - анализ размеров (как `filter-repo --analyze`): один проход по истории области, печатает `{blobs, folders, deleted, top, commits, blobs_total, bytes_total, disk_total, bytes_in_head, bytes_history_only, deleted_paths, blobs_cut, folders_cut, deleted_cut}`. `blobs` - `--top` (по умолчанию 50, не больше 5000) самых больших уникальных блобов, сначала самые большие, каждый `{path, more_paths, blob, size, disk_size, first_commit, last_commit, state}` (`state` - `in_head`, `replaced` для старой версии файла, который ещё есть в HEAD, или `deleted`; `last_commit` - commit, удаливший его, иначе добавивший; `disk_size` - размер в базе объектов, упакованная дельта считается как дельта); `folders` - `{path, size, blobs, in_head}` (байты уникальных блобов, когда-либо хранившихся ниже); `deleted` - пути, ушедшие из HEAD, но всё ещё хранящиеся в истории, `{path, versions, size, first_commit, last_commit}`. `bytes_history_only` - сколько примерно освободило бы удаление всего, что держит только история, и только после очистки старых объектов и gc; команда только читает и никогда не меняет ссылки. Превратите строку в правило через `--remove-path PATH` (или папку) либо `--remove-blobs-over BYTES`. `--remove-finding ID` (можно повторять, или `all`) добавляет правило, которое убирает эти находки из каждого commit'а: демон заново сканирует ту же область и сам разрешает id, поэтому значение не попадает ни в командную строку, ни в рецепт, ни в журнал. Отправленный секрет считается скомпрометированным: сначала перевыпустите его. Секреты не попадают ни в командную строку, ни в сохранённый рецепт: `--secrets-file F` (по одному в строке) заполняет правила секретов `content_replace` рецепта и никогда не выводится обратно. Push нельзя отменить: remote сохранит новую историю, даже если вы сделаете `undo` переписывания здесь (отмена просит подтверждения и говорит об этом). `note` печатает `{run, refs: [{name, short, kind, remote, old, new}], text, protected_by_host?}` (`protected_by_host` как выше, когда репозиторий привязан к хостингу и тот защищает одну из этих веток): что должен выполнить каждый, у кого осталась старая история (`git fetch`, затем `git reset --hard origin/<branch>` либо `git rebase --onto origin/<branch> <old tip> <branch>` для локальной работы; `git fetch <remote> +refs/tags/<tag>:refs/tags/<tag>` для tag'ов). `maps` печатает (или с `--out` копирует) `commit-map` и `ref-map` в формате git-filter-repo: строка заголовка, затем `old new` в строке (удалённый commit отображается в сорок нулей), для очистки репозитория в GitLab или для скриптов; печатает `{run, dir, commit_map, ref_map, copied}`. |
| `rewrite purge [--entry ID...\|--latest\|--all] [--yes]` | После переписывания: навсегда удалить из этого клона старую историю, чтобы утёкший секрет не остался в папке `.git`. Снимает точки отмены этого переписывания (и любой более ранней операции, чьи точки удерживают те же старые commit'ы), истекает записи reflog, которые называют старые commit'ы (только эти reflog; список stash'ей не затрагивается), запускает `gc --prune=now` и проверяет через `cat-file`, что каждого старого объекта больше нет. Эти операции остаются в `undo --list` как `Purged`, а `undo` / `redo` для них отклоняется с типизированной причиной (`{"refused":{"reason":{"Purged":{"entry":N}}}}`, код выхода 2). После запуска это нельзя остановить и нельзя отменить. Всё, что ещё удерживает старую историю, **блокирует очистку, и ничего не меняется**: ветка или tag вне переписывания, stash на старой истории, отсоединённый HEAD другого рабочего дерева, remote-tracking ссылка (отправьте переписанные ветки, затем `fetch`), ссылка notes или replace, точка отмены операции другого рабочего дерева. Без `--yes` ничего не происходит: `{"needs_confirmation":{prompt, check}}` с кодом выхода 3, где `check` - `{entries:[{id, label, rewrite}], already_purged, outcome:{status, blockers:[{kind, name, commits}], old_commits, old_blobs, old_objects, reflogs, reflog_entries, pins_dropped, runs_removed}, hosts:[{remote, host, steps}], prompt}`. С `--yes` и без блокировок печатает `{outcome:{status, remaining, ...}, hosts}`; `status` - `purged` (проверено), `incomplete` (`remaining` старых объектов ещё в хранилище объектов: их держит индекс или альтернативное хранилище) или `blocked`. Код выхода 4, если очистка заблокирована или неполна, и 2, если запись не является переписыванием. `--entry` - id записи журнала из `undo --list` (можно повторять), `--latest` (по умолчанию) - последнее ещё не очищенное переписывание, `--all` - все переписывания истории отмены. Remote она никогда не затрагивает: `hosts` перечисляет по каждому remote шаги, которые ещё нужны на хосте (сначала перевыпустите секрет; GitHub: обратитесь в поддержку, чтобы убрать кэшированные страницы и ссылки запросов на слияние, или удалите репозиторий и создайте заново; GitLab: загрузите `commit-map` (`rewrite maps --out DIR`) в Settings > Repository > Maintenance и запустите housekeeping; Azure DevOps: обращение в поддержку или пересоздание; Bitbucket: поддержка или пересоздание; всё остальное: `reflog expire` и `gc --prune=now` на сервере). Через MCP инструмент `rewrite_purge` не отображается, пока не задано `[mcp] allow_history_purge = true`. |

### Рабочие пространства и поиск

**Рабочее пространство** - именованная группа репозиториев, при желании с
профилем commit'ов по умолчанию. Оно хранится в `workspaces.toml` рядом с
`config.toml` и общее для всех сеансов и для окна, поэтому команды `workspace` не
запускают демон (его спрашивают только `add` и `create --add`, чтобы получить URL
`origin` каждого репозитория). Репозиторий может входить в несколько рабочих
пространств. Пути сравниваются так же, как в избранном и списке недавних.

| Команда | Что делает |
|---|---|
| `workspace list`, `workspace show <id>` | `{workspaces: [...]}` / `{workspace}`: `id` (слаг, не меняется при переименовании), `name`, `color`, `description`, `profile`, `profile_exists` и `repos: [{path, exists, remote}]` (`remote` - URL `origin`, записанный при добавлении репозитория, без учётных данных). |
| `workspace create <name> [--add PATH]... [--profile ID] [--color C] [--description T]` | Создаёт рабочее пространство и выводит его; два рабочих пространства не могут иметь одно имя. `--add` можно повторять, и это не `--repo`, который выбирает репозиторий, где выполняется команда. |
| `workspace rename <id> <name>`, `workspace delete <id>` | Переименование сохраняет id. Удаление никогда не трогает репозитории. |
| `workspace add <id> <path>...`, `workspace remove <id> <path>...` | `add` записывает корень и URL `origin` каждого репозитория (путь, которого нет или который не внутри репозитория, отклоняется с сообщением, и ничего не сохраняется: в списке остаётся, с пометкой «отсутствует», только репозиторий, исчезнувший позже); `remove` принимает и путь репозитория, которого уже нет на диске. |
| `workspace set-profile <id> <profile>` / `--none` | Id из `[[profiles]]`, с которым делаются commit'ы в репозиториях рабочего пространства. Id, не названный ни одним профилем, сохраняется (`profile_exists: false`) и не применяется. |
| `workspace set-ai-instructions <id> [--action <a>] [--mode append\|replace] (--text T \| --clear)` | ИИ-инструкции рабочего пространства, для каждого действия или для одного (`commit_message`, `code_review`, ...). `append` добавляет их после общих, `replace` использует вместо них. Они действуют для каждого репозитория рабочего пространства, перед собственными инструкциями репозитория. `workspace show` выводит их как `ai_instructions`. |
| `commit -m M [--workspace ID]` | Делает commit с профилем рабочего пространства, если репозиторий входит в него и профиль существует; иначе `general.active_profile`; иначе собственная идентичность репозитория. Без `--workspace` (или `GITPOULPI_WORKSPACE`) ничего не меняется: commit никогда не угадывает рабочее пространство по членству, ведь репозиторий может входить в несколько. Неизвестный id - ошибка. |
| `search <query> [--workspace ID] [--kind K]... [--limit N]` | Нечёткий поиск по веткам (локальным и удалённым), tag'ам, worktree, stash'ам, сообщениям commit'ов, а также по pull/merge request и задачам из кешей хостингов, в текущем репозитории или во всех репозиториях рабочего пространства (`GITPOULPI_WORKSPACE` заменяет флаг). Версия в окне - [Поиск](search.md). |

`search` отвечает `{query, workspace, hits, partial, repos}`. Каждый результат -
`{kind, label, detail, target, score, positions, repo}`: `kind` - это `branch`,
`tag`, `commit`, `stash`, `worktree`, `repo`, `pull_request` или `issue`;
`positions` - совпавшие символы `label`, которые нужно подсветить; `target`
говорит, куда перейти (`{type: "ref", name}` с полным именем ссылки,
`{type: "commit", id}`, `{type: "stash", index, id}`, `{type: "worktree", path}`,
`{type: "repo", path}`, `{type: "pull_request", number}`,
`{type: "issue", number}`); результаты разных репозиториев объединяются по
`score`, лучший первым. Сопоставление такое же, как у палитры команд: запрос
дословно, затем дословно где угодно, затем его символы по порядку (раньше и
короче - лучше). Тело commit'а ищется, только если не совпал его заголовок, а
запрос содержит три символа или больше. Префикс сужает поиск и не входит в
текст: `b:` ветки, `t:` tag'и, `c:` commit'ы, `s:` stash'и, `w:` worktree, `r:`
репозитории (только для рабочего пространства), `pr:` (или `mr:`) pull/merge
request, `i:` задачи, `#` и те и другие; `--kind` (можно повторять, те же имена)
тоже фильтрует. `partial` равно true, когда commit'ы репозитория обрезаны по
[`search.commit_limit`](config-reference.md#search-поиск-по-рабочему-пространству);
`repos` сообщает по каждому репозиторию, был ли он просмотрен (`reason`, если
нет: путь, исчезнувший с диска, попадает в отчёт и никогда не фатален).
Разовая команда сначала строит индекс каждого репозитория; если на том же
сеансе открыто окно, у демона он уже прогрет. Pull/merge request и задачи
читаются из кеша хостинга каждого репозитория (файл, который окно хранит в
`.gitpoulpi/hosting-cache.json`) и никогда не с хоста: у репозитория, в окне
которого их ни разу не загружали, искать нечего, а отсутствующий или записанный
не до конца кеш - просто отсутствие результатов.

**Показ в открытом окне** (`ui`; каждая команда принимает также
`--viewer <id>` и `--launch`)

| Команда | Что делает |
|---|---|
| `ui viewers [--all-sessions]`, `ui state [--text]` | Открытые окна; что показывает одно из них. |
| `ui show commit <rev> [--also R] [--files] [--focus refs\|log\|status]`, `ui show ref <name>`, `ui show pr <n>`, `ui show issue <n>`, `ui show wip [path] [--staged] [--composer]` | Выбрать что-то. |
| `ui show diff <path> [--rev R \| --unstaged \| --staged] [--line N] [--side old\|new] [--split \| --inline] [--whole-file \| --hunks] [--highlight A-B]` | Открыть diff на нужной строке. |
| `ui show file <path> [--rev R \| --worktree \| --index] [--blame \| --history] [--line N] [--column C] [--highlight A-B]` | Открыть файл, его blame или историю. |
| `ui show tab [path]`, `ui show home [--filter F]`, `ui show search <query>`, `ui show palette [query]`, `ui show keys [topic]`, `ui show settings [page] [--setting KEY]` | Перейти на вкладку, на вкладку «Главная», в строку поиска, в палитру, в справку, на страницу Настроек. `gitpoulpi ui show settings --help` перечисляет названия страниц. |
| `ui highlight <A[:C]-B[:C]> [--no-scroll]`, `ui notify <message>`, `ui back` | Подкрасить строки; всплывающее уведомление; отменить последнюю смену вида. |
| `ui show conflict <path> [--conflict N]` | Открыть редактор слияния на файле с конфликтами, на конфликте N (ничего не выбирается и не сохраняется). |
| `ui propose reword <rev> -m M`, `ui propose commit-message <summary> [--body B]`, `ui propose branch <name> [--start-point R]`, `ui propose tag <name> [--target R] [-m M]` | Открыть заполненный диалог, который вы подтверждаете (нужен `[mcp] allow_ui_propose = true`). |
| `ui propose split <rev> --plan <file\|->` | Открыть редактор разделения над commit'ом, заполненный планом (JSON для `split-commit --plan`), чтобы вы его проверили, поправили и применили; пока вы этого не сделаете, ничего не разделяется. Тот же шлюз, что у остальных предложений. |
| `ui propose rewrite --recipe <file\|->` | Открыть окно переписывания истории с уже заполненным рецептом (TOML или JSON, как у `rewrite preview --recipe`), чтобы вы выполнили предпросмотр и применили его; пока вы этого не сделаете, ничего не переписывается, не очищается и не отправляется. В предложении не больше 50 правил, нет скрипта (он выполнился бы при предпросмотре) и нет секретных значений. Тот же шлюз, что у остальных предложений. |
| `ui propose resolution <path> (--pick 1=a,2=ba,... [--default a\|b] \| --content-file F)` | Открыть редактор слияния с уже выбранным разрешением (или всем файлом как текстом), чтобы вы его проверили; единственное подтверждение - ваше «Сохранить и разрешить». Тот же шлюз, что у остальных предложений. |

Коды выхода: 0 - применено, 3 - отложено на решение пользователя, 1 - иначе.
Подробности и правила, которым следует окно: [MCP и агенты](mcp-and-agents.md#показ-пользователю).

## Примечания

- **Сессии.** `gitpoulpi session list` показывает каждую сессию с пометкой `live` / `stale`
  (определяется подключением к её порту). Выводимое имя - это
  `<папка>-<хеш пути>`.
- **Никаких интерактивных вопросов.** Ничего не спрашивается: рискованные операции
  либо требуют флага (`--yes`, `--force-with-lease`), либо отклоняются с причиной.
- **Нет в CLI**: `checkout --file` (восстановить один файл) есть только в окне.
