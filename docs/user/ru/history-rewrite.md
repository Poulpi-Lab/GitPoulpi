# Переписывание истории

Переписывание истории меняет уже существующие commit'ы: кто их написал и когда, их
сообщения, файлы в них, их подписи. GitPoulpi делает это через **рецепт** (область и
упорядоченный список правил) тремя шагами, из которых средний пропустить нельзя:

1. **Предпросмотр** вычисляет новую историю, ничего не трогая: счётчики, что сделало
   каждое правило, какие ветки и tag'и сдвинутся, по строке на каждый изменённый
   commit.
2. **Применить** переносит на неё ваши локальные ветки и tag'и. Это одна запись
   [истории отмены](undo-redo.md): **Отменить** возвращает на место все сдвинутые
   ссылки (и файлы в рабочем дереве).
3. **Push** (force push с lease) и **Очистка** - отдельные, осознанные шаги, потому что
   их нельзя отменить: см. [Отправка результата](#отправка-результата) и
   [Удаление старой истории](#удаление-старой-истории-очистка).

Окно переписывания, палитра, команды `gitpoulpi rewrite` и инструменты MCP работают на
одном движке, поэтому предпросмотр, сделанный в одном месте, применяется в другом.
[Из командной строки](#из-командной-строки) перечисляет флаги;
[Правила от ИИ](#правила-от-ии) заполняет окно переписывания по описанию;
[Предложения от ИИ-агентов](#предложения-от-ии-агентов) объясняют, что агент здесь может
и чего не может.

**Правила по тому, что они меняют**

| Группа | Правила | Раздел |
|---|---|---|
| Авторы | Заменить автора, Анонимизировать авторов, Применить .mailmap | [Авторы и .mailmap](#авторы-и-mailmap) |
| Даты | Сдвинуть даты, Сменить часовой пояс, Ограничить часами, Дата коммитера = дата автора | [Даты](#даты) |
| Сообщения | Найти и заменить, Удалить строки, Добавить или убрать трейлер, Исправить кодировку сообщений | [Сообщения](#сообщения) |
| Содержимое файлов и пути | Найти и заменить в файлах, Убрать файлы из истории, Убрать большие файлы, Переместить или переименовать пути, Преобразовать окончания строк, Убрать бит исполняемости, Преобразовать кодировку файлов | [Файлы и пути](#файлы-и-пути) |

**Прежде чем начать**

- Предпросмотр ничего не меняет. «Применить» меняет только ваши локальные ссылки и
  никогда ничего не отправляет.
- Переписанные commit'ы получают новые id. Всех, у кого осталась старая история,
  нужно предупредить: памятку для них пишет [Отправка результата](#отправка-результата).
- Отправленный секрет считается скомпрометированным. **Сначала перевыпустите его**, затем
  перепишите историю, сделайте force push и очистку.
- Commit'ы, которые остаются как есть, сохраняют свои id и подписи.

## Окно переписывания

`Ctrl+G Shift+H` (или **Переписывание: окно истории** в палитре) открывает окно
переписывания поверх Log. Кнопки на панели инструментов у него нет: расширенные
действия собраны в палитре (каждая строка `Переписывание: ...` открывает окно с уже
добавленным правилом), в подменю **Переписать историю** меню commit'а
(*От этого commit'а до HEAD...*, *Выбранные commit'ы...* при нескольких выбранных,
*Открыть окно переписывания...*) и за этим сочетанием.

`Ctrl+N` показывает значок на каждом элементе окна переписывания (область, правила, поля, вкладки, кнопки); нажатие на значок делает то же, что щелчок по этому элементу, а `Esc` убирает значки (см. [Значки](keybindings.md#значки)).

![Верстак переписывания истории: полоса области, список из двух правил «Заменить автора» с полями выбранного правила и сводка предпросмотра о том, сколько коммитов изменится](../images/history-rewrite.png)

- **Панель области:** какие ссылки сдвинутся (текущая ветка, все локальные ветки,
  выбранные ветки и tag'и, выбранные commit'ы), флажок *Tags* и, после
  *От этого commit'а до HEAD...*, флажок «начать после родителя этого commit'а».
- **Правила:** нумерованный список, правила применяются по порядку. Флажок включает
  или выключает правило, стрелки двигают его, крестик удаляет (*Вернуть удалённое
  правило* или `Ctrl+Z` возвращает его). *Добавить правило* показывает виды правил по
  группам. Правило, которому нужна недостающая программа, остаётся серым, с указанием
  причины.
- **Параметры правила:** щелчок по текстовому полю даёт его править; щелчок по полю с
  несколькими значениями открывает список; флажки переключаются.
- **Предпросмотр** (`F5`) вычисляет новую историю, ничего не трогая, и показывает
  индикатор выполнения. Вкладки: **Итог** (счётчики, что сделало каждое правило,
  предупреждения), **Commits** (по строке на каждый изменённый commit, подгружаются из
  демона страницами; фильтр показывает изменённые, удалённые или уже отправленные),
  **Ветки и tag'и** (что сдвигается и защищённые ветки, уже отправленные, у каждой
  свой флажок), **Последствия** (что значит переписать отправленную историю: force push
  с lease, коллеги, подписи), **Секреты**, **Авторы** и **Размер** (см. ниже).
- **Файлы commit'а:** `Enter` (или двойной щелчок) по строке на вкладке Commits
  открывает файлы, которые в нём изменили правила содержимого, а рядом - diff
  выбранного файла. Закрывают его крестик, `Esc` или щелчок вне окна. Удалённые строки
  правила секретов скрыты.
- **Применить** (`Ctrl+S` или `Ctrl+Enter`) доступно, когда предпросмотр соответствует
  правилам. Вопросы без значения по умолчанию задаются каждый раз: что делать с
  подписями подписанных commit'ов и как выносить папку. В панели результата есть кнопка
  **Отменить**: она возвращает все сдвинутые ссылки на место.
- **Сохранить / Загрузить** хранят рецепт в репозитории (для всех) или только для вас;
  секретные значения не сохраняются никогда.

У каждой кнопки есть клавиша: список в Настройки > Клавиатура и мышь (контекст
*Переписывание истории*) и в руководстве `keybindings.md`.

### Авторы и .mailmap

- **Заменить автора** находит автора или коммитера по имени и/или email (дословно или
  регулярным выражением) и задаёт новое имя и/или email. Поле *Применить к* выбирает
  автора, коммитера или обоих; *Также авторы tag'ов* заставляет следовать за ними
  аннотированные tag'и, которые создаются заново. Исходный коммитер сохраняется, если
  в запуске не выбрано *я, сейчас*.
- **Анонимизировать авторов** заменяет каждую личность нумерованной заглушкой
  (`Contributor 1`, `contributor-1@anonymous.invalid`; оба шаблона можно изменить, `{n}`
  обозначает номер). Один и тот же человек в одном запуске всегда получает один и тот
  же номер; личности из списка *Не трогать* остаются как есть.
- **Вкладка «Авторы»** (а также **Переписывание: merge авторов (.mailmap)...** в
  палитре) исправляет человека, который коммитил под несколькими именами и email,
  **ничего не переписывая**. Она перечисляет все имена и email области с панели
  области, сколько commit'ов каждый написал и закоммитил, и какие уже сопоставлены
  `.mailmap` репозитория (`сопоставлен с Name <email>`). Отметьте личности, которые
  принадлежат одному человеку (`Space` или щелчок; *Отметить все* / *Снять все*),
  затем **Merge в...** (`m`; без перевода терминов git - **Объединить в...**): диалог
  спросит, какая из них остаётся (первой стоит та, у которой больше всего commit'ов), и
  **добавит в `.mailmap` по строке на каждую другую личность**
  (`Name <email> Old Name <old@email>`; уже имеющаяся строка не повторяется, а
  недостающий файл создаётся). Ничего не коммитится: закоммитьте `.mailmap` сами, чтобы
  поделиться им. Log, blame и история файла сразу показывают каноническое имя
  (параметр `log.use_mailmap`, по умолчанию включён; сохранённые commit'ы никогда не
  меняются, так что force push не нужен). Строка состояния сообщает, что записано, и
  предлагает **Отменить** (`u`): она возвращает прежний `.mailmap` (это одна запись
  истории отмены, как у любого другого действия). `r` читает список заново.
- **`.mailmap` вместо переписывания.** Когда правило автора меняет commit'ы, которые
  уже на remote, на вкладке «Итог» появляется *Отображение можно исправить через
  .mailmap, не переписывая историю. Использовать .mailmap?* с кнопкой **Использовать
  .mailmap** (`m` на «Итоге»). Она открывает вкладку «Авторы» с отмеченными
  личностями, которые затрагивает правило, а личность, которую правило установило бы,
  предлагается как остающаяся, хотя ни один commit её пока не несёт.
- **Правило `.mailmap`** (*Переписывание: применить .mailmap к истории...* или
  `rewrite preview --mailmap`) именно переписывает: авторы и коммитеры (по вашему
  выбору) становятся такими, как их называет `.mailmap` рабочего дерева, то есть как
  показывает `git log --use-mailmap`. Используйте его, когда сама история должна нести
  канонические имена, например перед публикацией; это такое же переписывание, как любое
  другое (предпросмотр, «Применить», force push).
- **Правила личности и трейлеры.** Правило личности может менять и людей, названных в
  трейлерах: отметьте **Менять и трейлеры** (`--map-trailers`). Каждый трейлер, значение
  которого в точности `Name <email>` и подходит под *Email равен* / *Имя равно* правила,
  получает новое имя и email, что бы правило ни делало с автором и коммитером. По
  умолчанию это выключено: `Signed-off-by` фиксирует, кто подписал, поэтому менять его -
  отдельное решение.

### Даты

Четыре правила дат работают с датой автора, датой коммитера или с обеими (*Даты* на
панели правила).

- **Сдвинуть даты** смещает каждую дату на заданную величину (`+2h`, `-1d`, `90m`,
  `1d 2h`). Часовой пояс, в котором был написан каждый commit, сохраняется.
- **Сменить часовой пояс** записывает даты с другим смещением UTC. Поле *Сохранять*
  говорит, что остаётся неизменным: **момент времени** (тот же миг, на часах другое
  время) или **показания часов** (то же местное время, миг меняется).
- **Ограничить часами** переносит каждый commit, выпавший за разрешённые часы (например
  `Mon-Fri 18:00-23:30; Sat,Sun 10:00-20:00`), на ближайшее разрешённое время, только
  раньше или только позже (*Направление*). *Не раньше родителя* сохраняет порядок
  истории; *Начальное значение* делает небольшой случайный разброс воспроизводимым: то
  же значение на той же истории даёт те же даты.
- **Дата коммитера = дата автора** задаёт коммитера (имя, email и дату) как у автора,
  то есть возвращает то, что испортили `git commit --amend` или rebase.

Даты - такие же правила, как остальные: сделайте предпросмотр, проверьте вкладку
**Commits** (в каждой строке старая и новая дата), затем примените. Id commit'а зависит
от его дат, поэтому правило дат меняет каждый commit после первого, которого коснулось.

### Сообщения

- **Найти и заменить в сообщениях** и **Удалить строки сообщений** принимают дословный
  текст или регулярное выражение (*Регулярное выражение*, *Учитывать регистр*); пустая
  замена удаляет. Сообщение, которое не является корректным UTF-8, они не трогают:
  сначала выполните **Исправить кодировку сообщений**, если хотите его править.
- **Трейлеры.** *Добавить или убрать трейлер* (*Переписывание: добавить или убрать
  трейлеры...* в палитре или `--trailer-add`, `--trailer-remove`, `--trailer-map`)
  правит строки `Ключ: значение` в конце сообщения, те, что знает `git
  interpret-trailers` (`Signed-off-by`, `Co-authored-by`, `Reviewed-by`...). Список
  **Действие** предлагает *Добавить* (**Трейлер** - ключ, его **Значение** и **Если уже
  есть**: *Добавить (кроме точных копий)*, *Заменить существующие* или *Не трогать
  commit*), *Убрать* (все трейлеры с этим ключом или только те, чьё значение содержит
  **Значение содержит**) или *Изменить значение* (**Найти в значении** и **Заменить
  на**, например старый email на новый в `Signed-off-by`). Ключи сопоставляются без
  учёта регистра. Меняются только строки трейлеров, остальное сообщение остаётся в
  точности как было, а сообщение, где трейлеров ещё нет, получает пустую строку и
  отдельный блок. Вкладка Commits показывает каждое изменение как
  `+Signed-off-by: ...` / `-Co-authored-by: ...`. Блок трейлеров - это последний абзац
  сообщения (но не заголовок), поэтому строка вроде `Note: see the ticket` в тексте не
  считается трейлером, если только она не стоит одна в последнем абзаце вместе с
  другими трейлерами.
- **Id commit'ов в сообщениях.** **Обновить id commit'ов** (`--update-message-hashes`,
  по умолчанию выключено; в конце панелей правил, которые правят сообщения) заставляет
  id, написанные в сообщениях, следовать за переписыванием: сокращённый id из 7 и
  более шестнадцатеричных символов (`This reverts commit 1a2b3c4`, `see 1a2b3c4d5e`),
  который называет ровно один commit переписанной истории, заменяется новым id этого
  commit'а, обрезанным до той же длины. Если id подходит под несколько commit'ов, не
  подходит ни под один или называет commit, который переписывание создаст позже, он
  остаётся как есть; «Итог» сообщает, сколько id заменено и сколько оставлено.
- **Исправить кодировку сообщений** (*Переписывание: исправить кодировку сообщений...*
  или `--fix-message-encoding [--fix-name-encoding]`) перекодирует сообщения в UTF-8 в
  двух случаях:
  - Commit с заголовком `encoding` (`ISO-8859-1`, `Windows-1252`, `Shift_JIS`, любая
    кодировка, известная git и таблицам кодировок) декодируется и записывается в UTF-8,
    а заголовок убирается: текст читается одинаково везде, без преобразования. Имена
    автора и коммитера этого commit'а были в той же кодировке и декодируются вместе с
    ним, поэтому commit никогда не остаётся преобразованным наполовину.
  - **Кракозябры**, то есть UTF-8, который когда-то прочли как Latin-1 или Windows-1252
    (`RÃ©Ã©criture` вместо `Réécriture`), исправляются, **только если обратное
    преобразование точное**: текст должен закодироваться обратно в байты, корректные
    для UTF-8, а повторная порча результата тем же способом должна дать исходный
    текст. Сообщение, которое просто содержит `Ã©` рядом с настоящими буквами или
    символы вне старых алфавитов, проверку не проходит и остаётся как есть.

  Флажок *Исправить и имена* (`--fix-name-encoding`) так же исправляет испорченные имена
  автора и коммитера. То, что определить нельзя (неизвестное имя кодировки, байты,
  недопустимые в заявленной кодировке, сообщение не в UTF-8 без заявленной кодировки,
  текст, который выглядит испорченным, но это не доказано), **остаётся как есть и
  подсчитывается**: «Итог» сообщает *сообщений оставлено как есть: их кодировку нельзя
  определить*, а число лежит в `counts.encoding_left`. Вкладка Commits показывает каждое
  исправление со старым и новым сообщением и строкой *кодировка* (`ISO-8859-1` меняется
  на `UTF-8`).

### Файлы и пути

- **Правила содержимого файлов** (*Найти и заменить в файлах*, *Убрать файлы из
  истории*, *Убрать большие файлы*): панель проверяет каждое значение по мере ввода и
  показывает причину под полем (шаблон, который не компилируется, неверный шаблон пути,
  размер меньше одного байта). Размеры принимают единицы (`500 KiB`, `5 MiB`, `1 GiB`).
  Шаблон пути без слеша совпадает на любой глубине. *Секретные значения* вводятся в
  скрытое поле, используются только в этом запуске и не сохраняются; предпросмотр
  скрывает строки, где они были. Поле *Пустые commit'ы* определяет, удалять ли commit,
  который правила сделали пустым (по умолчанию), или оставить. Двоичные файлы и файлы
  больше лимита размера остаются как есть и учитываются на вкладке «Итог».
- **Перемещение путей.** *Переместить или переименовать пути* (*Переписывание:
  переместить или переименовать пути...* в палитре) бывает трёх видов, выбираемых в
  списке **Действие**:
  - *Переименовать путь* (**Откуда**, **Куда**; `--move-path FROM=TO`): те же файлы и
    папки появляются по новому пути в каждом commit'е, где был старый; больше ничего не
    меняется, у каждого файла сохраняется его id. Commit, где новый путь уже
    существует, никогда не перезаписывается: предпросмотр отклоняется и перечисляет
    commit'ы и пути, которые конфликтуют (выберите свободное имя или сначала переместите
    существующий путь). Только точные пути, без шаблонов.
  - *Поместить всё в папку* (**Папка**; `--into-subdir DIR`): каждый путь в каждом
    commit'е получает префикс. Полезно, чтобы объединять репозитории без конфликтов
    имён.
  - *Сделать папку корнем* (**Папка**; `--extract DIR`): папка становится корнем,
    commit'ы, которые её не затрагивают, отбрасываются (commit, создающий её, остаётся
    без родителя), слияния, которые больше ничего не соединяют, упрощаются, а ветки и
    tag'и, где от папки ничего нет, удаляются. **Каждый раз** спрашивается, чем это
    закончится:
    - *В новый клон, открытый в новой вкладке* (`--extract-mode clone`): копия этого
      репозитория создаётся в выбранной вами папке (у нового репозитория внутри будет
      папка с именем вынесенной), переписывается там и очищается так, чтобы хранить
      только новую историю, все локальные ветки и tag'и, где есть эта папка. Этот
      репозиторий не затрагивается. У нового репозитория нет remote (оригинал не является
      его upstream).
    - *На месте: история этого репозитория переписывается* (`--extract-mode in-place`):
      обычное переписывание, предпросмотр, «Применить», отмена. Ветки без этой папки
      удаляются (отмена возвращает их); в текущей ветке она должна быть.
    - *Как подмодуль этого репозитория* (`--extract-mode submodule`): новый репозиторий
      создаётся как в случае клона, затем **один новый commit** в текущей ветке заменяет
      папку подмодулем на его основе (`.gitmodules` и ссылка), а сама папка остаётся как
      подмодуль в рабочем дереве. История этого репозитория **не** переписывается: его
      старые commit'ы сохраняют файлы папки, поэтому ничто, что на них указывает (tag'и,
      другие клоны), не ломается. URL в `.gitmodules` - это локальный путь нового
      репозитория: измените его (`git config -f .gitmodules submodule.<folder>.url`),
      когда он появится на хостинге. Изменённые или неотслеживаемые файлы в папке
      блокируют действие. Отмена возвращает обычную папку.

    «Итог» сообщает, что предпросмотр показывает историю нового репозитория и в какую
    папку он попадёт. Правила, идущие после выноса (переименование, удаление),
    применяются к вынесенному дереву; для клона или подмодуля вынос должен быть первым
    правилом путей. Правила путей выполняются после правил содержимого, поэтому шаблон
    удаления называет пути такими, какими они были.

#### Окончания строк, бит исполняемости и кодировки файлов

Три правила в группе **Содержимое** меню добавления (или строки палитры
*Переписывание: преобразовать окончания строк...*, *Убрать бит исполняемости...* и
*Переписывание: преобразовать кодировку файлов...*). Все три принимают **Файлы** (globs;
шаблон без слеша совпадает на любой глубине; пусто означает все файлы) и **Кроме
файлов**. Они меняют только то, что названо шаблонами, в каждом commit'е области.
Двоичные файлы (нулевой байт в первых 8 КиБ) не трогаются никогда: «Итог» считает их
как *оставлены как есть*.

- **Преобразовать окончания строк** (`--eol lf|crlf|cr --eol-paths GLOB...
  [--eol-exclude GLOB...]`). *Преобразовать в*: LF (Linux, macOS), CRLF (Windows) или CR
  (классический Mac). Все окончания строк подходящего текстового файла становятся
  выбранным, поэтому файл со смешанными окончаниями получается единообразным; файлы,
  которые и так в порядке, сохраняют свою версию нетронутой. *Учитывать .gitattributes*
  (по умолчанию выключено, `--eol-follow-attributes`) читает корневой `.gitattributes`
  каждого commit'а: файлы с `-text` или `binary` пропускаются, а файлы с `eol=lf` или
  `eol=crlf` сохраняют это окончание вместо выбранного вами.
- **Убрать бит исполняемости** (`--strip-exec GLOB... [--strip-exec-exclude GLOB...]`).
  У подходящих файлов режим 100755 меняется на 100644; их содержимое не меняется. Нужен
  хотя бы один шаблон файлов: если снять бит у всех исполняемых файлов, скрипты
  перестанут работать.
- **Преобразовать кодировку файлов** (`--reencode TARGET [--from SOURCE]
  [--encoding-fallback ENC] --encoding-paths GLOB... [--encoding-exclude GLOB...]`).
  *Преобразовать в*: UTF-8 (по умолчанию), UTF-8 с BOM, UTF-16 LE или BE (с меткой
  порядка байтов), Windows-1252 или ISO-8859-1. *Кодировка файлов*: по умолчанию
  кодировка каждого файла определяется (метка порядка байтов, иначе корректный UTF-8,
  иначе *Запасная*, Windows-1252, если вы её не меняли); назовите кодировку, чтобы
  задать её принудительно, но неверный выбор даёт неверный текст (UTF-8, прочитанный как
  Latin-1, удваивает каждый диакритический знак). Файл, который нельзя прочитать в
  исходной кодировке, или тот, где есть символ, которого целевая кодировка не хранит
  (знак евро в ISO-8859-1), остаётся в точности как есть и подсчитывается в «Итоге».

Правила выполняются в порядке списка, над одним и тем же файлом: если файл
преобразовать в UTF-16, а затем запросить окончания строк, он останется нетронутым (это
уже не обычный текст). «Применить» - одна запись в списке отмены, как у любого
переписывания.

### Поиск секретов

- **Поиск секретов:** `gitpoulpi rewrite scan-secrets` (и MCP-инструмент
  `rewrite_scan_secrets`) один раз читает историю и перечисляет префиксы токенов
  (GitHub, GitLab, Slack, AWS, Stripe, npm, Google, OpenAI, Anthropic), закрытые ключи,
  JWT, пароли в URL и похожие на случайные строки `password = value`; для каждой находки
  указаны файл, первый и последний commit и скрытый фрагмент вида `ghp_****abcd`. Поиск
  неполный, а само значение не показывается, не журналируется и не сохраняется.
  `--remove-finding ID` превращает находку в правило, которое убирает её из каждого
  commit'а. Отправленный секрет считается скомпрометированным: сначала перевыпустите
  его, затем перепишите историю, сделайте force push и очистку.
- **Вкладка «Секреты»** делает то же из окна переписывания для области с панели
  области: **Искать секреты** (`s`) запускает поиск как задачу (индикатор подписан
  *Поиск*, **Отмена** или `Esc` останавливает его). Каждая находка - строка с видом,
  скрытым фрагментом, файлом и числом других файлов, где она есть; под списком: первый и
  последний commit, где её видели, и сколько commit'ов и версий файлов её содержат.
  Вкладка сообщает, сколько двоичных файлов и файлов сверх лимита не читалось, и что
  поиск неполный. Сначала все находки отмечены; **Удалить из истории** (`r`) превращает
  отмеченные в одно правило, которое называет их по id (никогда по значению), и вы
  делаете предпросмотр и применяете его как любое другое. После переписывания или смены
  области находки устаревают: вкладка об этом скажет, повторите поиск. Окно
  переписывания никогда не хранит значение секрета и потому не может его показать.

### Что занимает место

- **Что занимает место:** `gitpoulpi rewrite analyze [--top N]` (и MCP-инструмент
  `rewrite_analyze`) - анализ размеров, как `filter-repo --analyze`: самые большие файлы
  с путём, размером, первым и последним commit'ом и признаком, остались ли они в HEAD,
  самые большие папки, файлы, удалённые из HEAD, но всё ещё хранящиеся в истории, и
  итоги. Он читает только размеры и пути, но не содержимое файлов, и ничего не меняет.
- **Вкладка «Размер»** делает то же из окна переписывания (`F7` или *Анализ размеров
  истории* в палитре открывает её и запускает анализ): **Анализ размеров** (`s`) -
  задача (*Анализ*, **Отмена** или `Esc` останавливает её). **Показать** выбирает список
  (`v`): *Файлы* (самые большие уникальные версии файлов, каждая с пометкой *в HEAD*,
  *старая версия* файла, который ещё есть, или *удалён*), *Папки* (всё, что когда-либо
  хранилось внутри каждой) или *Удалённые* (пути, которых уже нет в HEAD, но история их
  хранит). **Порядок** (`o`) - по размеру, по пути или сначала удалённые. Отметьте
  строки (`Space`, `Alt+A` / `Alt+U` - все / ни одной): вкладка покажет, сколько они
  занимают, честно как «до примерно», потому что место вернётся только после
  переписывания, очистки старых объектов и `gc`. **Удалить из истории** (`r`) превращает
  отмеченные пути в правило путей (спецсимволы экранируются, путь, уже входящий в
  правило, второй раз не добавляется); **Удалить все файлы больше ...** (`b`, список
  «Файлы») пишет правило размера чуть ниже самого маленького отмеченного файла. Делайте
  предпросмотр и применяйте их как любые другие правила. В списках показаны 200 самых
  больших строк; CLI сообщает, сколько ещё, а `--top` выводит их. После переписывания
  или смены области строки устаревают: повторите анализ.

### Подписи

- **Подписи:** переписанный commit не может сохранить подпись (она подписывала старые
  байты), поэтому, когда переписываются подписанные commit'ы, вас каждый раз
  спрашивают: *Удалить подписи* (сначала показывается их число), *Подписать заново
  только ранее подписанные commit'ы* или *Подписать заново все переписанные commit'ы*.
  Значения по умолчанию нет. Commit'ы, которые остаются как есть, сохраняют свои
  подписи. Повторная подпись использует вашу собственную настройку, так же как подписанный
  commit: `gpg.format` (`openpgp`, `ssh` или `x509`), `user.signingkey` и `gpg.program` /
  `gpg.ssh.program` / `gpg.x509.program`. Четвёртая строка вопроса, **Проверить
  подписание** (`4`), один раз подписывает пробные данные и проверяет подпись: она
  сообщает, сколько занимает одна подпись, и оценивает время прогона для числа commit'ов,
  о которых идёт речь, или говорит, почему подписание не работает (нет ключа, агент
  заблокирован, программа не установлена, с подсказкой, как её установить).
  Предпросмотр делает ту же проверку до чтения истории и отказывает с этой причиной,
  поэтому неисправная настройка никогда не оставит наполовину подписанное переписывание.
  Commit'ы подписываются **во время предпросмотра** (их id содержат подпись), поэтому
  предпросмотр с повторной подписью занимает время подписания, «Итог» сообщает *Commit'ов
  подписано заново: n, за 12.5 с*, а запрос парольной фразы может открыться тогда же:
  сначала разблокируйте агент (именно это делает «Проверить подписание»). **Отмена**
  останавливает между двумя подписями и ничего не оставляет. Заново создаются только
  подписи commit'ов; подписанный tag по-прежнему теряет подпись.
- **Правило «Убрать подписи»** (меню добавления, группа *Подписи*; *Переписывание: убрать
  подписи...* в палитре; `--remove-signatures`) снимает подпись с каждого commit'а
  области, даже если больше ничего не меняется, и ничего не спрашивает о повторной
  подписи. Из CLI: `rewrite check-signing` и `--signatures strip|resign-signed|resign-all`.

### Отмена переписывания

**Отменить** (кнопка панели результата, кнопка «Отмена» на панели инструментов с
`Ctrl+Z` в Log или `gitpoulpi undo`) возвращает на место все сдвинутые ветки, tag'и и
заметки, а вместе с ними и файлы в рабочем дереве, из старых commit'ов, которые
удерживает переписывание. Сначала она спрашивает, если переписанная ветка уже лежит на
своём upstream (локальная отмена не отменяет push) и если у вас есть незакоммиченные
изменения: они сохраняются, а изменённый вами файл, который старая история
перезаписала бы, останавливает отмену (файлы перемещаются так же, как при
`reset --keep`). Отмена перестаёт быть возможной для переписывания, когда вы
[очистите](#удаление-старой-истории-очистка) его старую историю; список истории тогда
помечает его как *очищено*.

## Перенос файлов в Git LFS и из него

Два правила в группе *LFS* меню добавления переписывают историю так, чтобы большие
файлы с самого начала лежали в [Git LFS](lfs.md) (или покинули его). Им нужна программа
`git-lfs`: без неё правила серые, с подсказкой по установке, а предпросмотр
отклоняется. Это наш собственный движок, а не `git lfs migrate`, поэтому у вас есть
предпросмотр, область, отмена и защита push, как у любого другого правила.

- **Перенести файлы в LFS** (*Переписывание: перенести файлы в LFS...* или
  `--lfs-import PATTERN` вместе с `--lfs-min-size BYTES`). Каждый файл, который подходит
  под шаблоны (`*.psd`, `assets/**`; шаблон без слеша совпадает на любой глубине) и не
  меньше размера из поля *Только файлы размером от* (пусто: все подходящие), становится
  указателем LFS в каждом commit'е, где он есть. Его содержимое попадает в локальное
  хранилище LFS (`.git/lfs/objects`, по одному разу на каждое различное содержимое) при
  «Применить», а в корневом `.gitattributes` в каждом переписанном commit'е, где есть
  указатель, появляется строка `<pattern> filter=lfs diff=lfs merge=lfs -text` (файл
  создаётся, если его не было, остальные строки не трогаются, дубликаты не
  добавляются). Файл, который уже является указателем, остаётся как есть. «Итог»
  сообщает вроде *3 файла (12 МиБ) переносятся в LFS. Объектов LFS к записи: 3.*, а
  вкладка Commits по каждому commit'у перечисляет *переносит big.psd в LFS*.
- **Вернуть файлы из LFS** (*Переписывание: вернуть файлы из LFS...* или
  `--lfs-export PATTERN`). Подходящие указатели снова становятся настоящими файлами, а
  строки `.gitattributes` для этих шаблонов убираются. Объекты должны быть в локальном
  хранилище LFS: если каких-то нет, предпросмотр отклоняется со списком и кнопкой
  **Скачать объекты LFS**, которая загружает их с `origin`; после этого сделайте
  предпросмотр заново. Перенос в LFS, за которым следует возврат по тем же шаблонам,
  возвращает в точности те же commit'ы.

После «Применить» файлы в рабочем дереве - настоящее содержимое (а не указатели), а
**Отменить** возвращает старую историю. В панели результата есть **Отправить объекты
LFS** (`l`): то же, что `LFS: Push All Objects`, чтобы новую историю можно было
отправить, не упираясь потом в недостающие объекты (обычный push переписанных веток тоже
загружает их через хук pre-push, который ставит «Применить»). В памятке для коллег
сказано, что им нужны git-lfs и `git lfs pull`.

Полезно знать: «Применить» устанавливает фильтры LFS репозитория (`git lfs install
--local`), если их нет, потому что git нужны они, чтобы сравнивать настоящие файлы с
указателями. Записывается только корневой `.gitattributes`, вложенные - никогда. Файл
*меньше* минимального размера, подходящий под шаблон, остаётся обычным файлом, но git
захочет превратить его в указатель при следующем add, поэтому `git status` показывает
его изменённым, пока вы его не закоммитите. Перенос в LFS обрабатывает большие файлы
потоком, а возврат держит в памяти по одному файлу за раз.

## Отправка результата

Применение переписывания никогда ничего не отправляет. Переписанные ветки и tag'и,
которые были на remote, требуют force push, но слепо он не форсируется: каждая ссылка
уходит с lease на id, который был на remote при предпросмотре (а не на то, что сейчас
говорит ваша отслеживающая ветка), так что чужой push в промежутке отклоняется для этой
ссылки, а не затирается, и ссылки уходят одним push «всё или ничего» (`--atomic`), где
это позволяет сервер. Из командной строки:

```
gitpoulpi rewrite push --dry-run        # спрашивает remote, ничего не отправляет
gitpoulpi rewrite push --yes            # отправляет
gitpoulpi rewrite note                  # что должны выполнить остальные
gitpoulpi rewrite maps --out ./maps     # commit-map и ref-map
```

Защищённые ветки (параметр `rewrite.protected_branches`, по умолчанию `main`, `master`,
`develop`, `release/*`) при отправке не затрагиваются, и при переписывании, и снова при
push, пока вы не назовёте их (`--include-protected main`) или не включите все. Решение,
принять ли force push, всё равно остаётся за защитой веток на хостинге; его отказ
показывается для каждой ссылки.

В окне переписывания всё это делает панель результата после «Применить»:

- **Отправка переписанных ссылок на remote** перечисляет ссылки, сдвинутые
  переписыванием и имеющиеся на каком-либо remote, у каждой флажок (`Space`).
  Защищённые ветки сначала не отмечены, рядом с ними пометка *защищена*: отмечайте их по
  одной или используйте *Отметить все* / *Снять все* (`Alt+A` / `Alt+U`). **Push
  переписанные ветки** (`p`) отправляет отмеченные; ответ - по строке на ссылку
  (*отправлена*, *уже актуальна*, *отклонено: remote изменился после предпросмотра*,
  *отклонено: ветка защищена на хостинге*, *пропущено: защищённая ветка*, *не
  отправлена*). У отклонённой строки есть **Fetch и проверить** (`f`): окно закрывается,
  а remote загружаются, так что Log показывает, что отправили другие. Ничего не
  затирается: lease защищает их работу, и перед новой попыткой вы снова делаете
  предпросмотр.
- **Копировать памятку** (`c`) кладёт в буфер обмена памятку для коллег: текст на языке
  интерфейса, команды git остаются без перевода.
- **Открыть карту commit'ов** (`m`) показывает, где лежат карта commit'ов и карта ссылок;
  щелчок по пути (или `1` / `2`) копирует его.

Push нельзя отменить: если после него вы сделаете `undo` переписывания, изменится только
ваш репозиторий, и отмена предупредит об этом, прежде чем спросит. Отправьте памятку
всем, у кого осталась старая история: в ней старая и новая вершина каждой ветки и tag'а
и команды (`git fetch`, затем `git reset --hard origin/<branch>` или `git rebase
--onto`). Обе карты хранятся 24 часа вместе с запуском; скопируйте их, если они нужны
очистке репозитория в GitLab или скрипту.

## Когда хостинг защищает ветку

Хостинг может сам защищать ветку (защита веток и rulesets в GitHub, protected branches в
GitLab, политики веток в Azure DevOps, ограничения веток в Bitbucket) и отклонять force
push, который нужен переписыванию. Если репозиторий **привязан** к хостингу (раздел
запросов на слияние в боковой панели, см. [Интеграции с хостингами и трекерами задач](hosting-integration.md)),
окно переписывания спрашивает хостинг, какие ветки он защищает, с вашим собственным
токеном:

- Эти ветки **по умолчанию не входят в переписывание**, как и защищённые ветки из
  `rewrite.protected_branches` и рабочего процесса: на вкладке «Ветки и tag'и» они
  перечислены, у каждой свой флажок и кнопки *Отметить все* / *Снять все*, а причина
  указана так: *защищена в GitHub*.
- Если токен не может прочитать защиту (ему не хватает прав или вы не администратор),
  окно пишет *Защита на хостинге неизвестна* и ничего не считает защищённым по слову
  хостинга. Переписывание из-за этого никогда не блокируется. Репозиторий, не привязанный
  к хостингу, не опрашивается вовсе.

Когда защищённая ветка мешает (предпросмотр отклонён, потому что все ветки защищены,
или хостинг отклонил push: *отклонено: ветка защищена на хостинге*), кнопка **Как
обойти** (`Alt+H`) объясняет три выхода с точной страницей настроек вашего хостинга и
репозитория (выберите ссылку и скопируйте её клавишей `c` или откройте клавишей `o`).
GitPoulpi ни один из них не выполняет за вас:

1. **Временно снять защиту** в настройках хостинга, сделать push, затем вернуть её.
2. **Сделать push переписанной истории под новым именем ветки**, затем сделать эту ветку
   веткой по умолчанию (или переименовать) и удалить старую, когда ею перестанут
   пользоваться.
3. **В крайнем случае удалить и заново создать репозиторий на хостинге** и отправить
   всё. Так теряются запросы на слияние и их ревью, задачи, связь форков со старой
   историей, звёзды и подписчики, настройки CI, секреты и переменные, а также вебхуки и
   deploy-ключи.

Из CLI тот же текст возвращается как `protected_by_host` в JSON команд `rewrite preview`
/ `rewrite run` (когда хостинг защищает ветку из области), отклонённого `rewrite push` и
`rewrite note`: `provider`, `branches`, `ways` (у каждого свои `steps` и `links`),
`recreate_loses` и всё объяснение целиком как `text`.

## Удаление старой истории (очистка)

После переписывания старые commit'ы всё ещё лежат в вашем репозитории: их хранит отмена
переписывания (на этом она и держится) и reflog. Если вы переписывали историю, чтобы
избавиться от секрета, этот секрет по-прежнему в папке `.git`. Очистка безвозвратно
удаляет старую историю:

```
gitpoulpi rewrite purge                 # спрашивает: перечисляет, что удалится и пропадёт (код выхода 3)
gitpoulpi rewrite purge --yes           # выполняет
```

Она снимает точки отмены этого переписывания, истекает записи reflog, которые называют
старые commit'ы, запускает `git gc --prune=now` и затем проверяет, что каждый старый
commit и каждая версия файла действительно исчезли. Подтверждение заранее говорит, что
вы теряете: **отмена станет невозможна** для этого переписывания (и для любой более
ранней операции, чья отмена тоже нуждалась в старых commit'ах); в списке истории они
остаются с пометкой «очищено». Очистку нельзя остановить после запуска и нельзя
отменить. Remote она не затрагивает.

Очистку блокирует всё, что ещё удерживает старую историю, и тогда ничего не меняется.
Список называет каждое такое место и что с ним делать: ветка или tag, которые не входили
в переписывание, stash на старой истории (удалите его или оставьте и примите, что старая
история останется), другое рабочее дерево, чей HEAD на ней, и remote-tracking ветки,
которые всё ещё указывают на старую историю (отправьте переписанные ветки, затем сделайте
fetch). Ваш список stash'ей и reflog других веток не затрагиваются.

Отправленный секрет считается скомпрометированным: **сначала перевыпустите его**. После
очистки ответ перечисляет, что ещё нужно на хостинге, по каждому remote: GitHub
оставляет старые commit'ы доступными в кэшированных страницах и ссылках запросов на
слияние (обратитесь в поддержку GitHub или удалите репозиторий и создайте заново), у
GitLab есть очистка репозитория, которая принимает `commit-map`
(`gitpoulpi rewrite maps --out DIR`), и housekeeping, Azure DevOps и Bitbucket требуют
обращения в поддержку или нового репозитория, а у всех, у кого есть клон или форк,
старая история остаётся.

### Экран очистки

В окне переписывания в панели результата есть кнопка **Очистить старую историю...**
(клавиша `e`), а в палитре - **Переписывание: очистить старую историю...** (она работает
с последним ещё не очищенным переписыванием, в том числе после закрытия окна). Экран
перечисляет, что удалит очистка и что вы потеряете (операции, чья отмена уйдёт вместе с
ней; те, что с пометкой *отмена тоже пропадёт*, не являются переписываниями, но
нуждались в старых commit'ах), затем то, что ещё удерживает старую историю, по строке на
каждое:

- remote-tracking ветка: **Fetch** обновляет их с remote;
- stash: **Удалить** сначала спрашивает, ведь stash - это работа, которую вы так и не
  закоммитили;
- ветка, tag, рабочее дерево или другая ссылка: **Копировать имя**, а затем
  разберитесь с ней там, где она находится (перепишите или удалите ветку, переключите
  рабочее дерево на переписанную ветку).

После каждого исправления проверка запускается снова, а **Проверить снова** (`r`)
запускает её по требованию. **Очистить** (`p`) доступно, только когда ничего не осталось.
Оно задаёт последний вопрос, пронумерованный и без значения по умолчанию (`1` очищает
безвозвратно, `2` оставляет всё как было), затем выполняется; экран показывает текущий
шаг и говорит, что остановить её нельзя. Итог сообщает, что старой истории в этом клоне
больше нет, или сколько старых объектов ещё осталось. Ниже - шаги для каждого remote
(ссылку можно скопировать). Крестик, `Esc` и щелчок вне окна закрывают экран, кроме
времени, пока идёт очистка.

Через MCP инструмента очистки нет, пока вы не зададите `allow_history_purge = true` в
таблице `[mcp]` файла `config.toml`.

## Правило «Скрипт»

*Добавить правило > Скрипт* (или **Переписывание: запустить скрипт...** в палитре)
добавляет правило с Lua-скриптом и открывает его редактор поверх окна переписывания;
`Enter` на строке *Скрипт* правила открывает его снова. Редактор начинается с небольшого
шаблона.

- **Язык** (строка панели правила): *Lua (встроенный)*, *Shell-скрипт*, *Python* или
  *Lua (установленный)*. Всё, кроме встроенного Lua, - это [внешний
  скрипт](#внешние-скрипты-shell-python-lua): без песочницы; язык, выключенный в
  настройках или без найденного интерпретатора, в списке серый, с причиной рядом (выбор
  такого языка подскажет, что делать). Если вы ещё не писали скрипт, смена языка
  подменяет шаблон.
- **Скрипт** - текстовый редактор с номерами строк. То, что вы набираете, сразу и есть
  правило; подтверждать ничего не нужно.
- Под ним строка **проверки** показывает `OK: найдено rewrite_commit` или перечисляет
  проблемы со строкой (`script:3: ...`; номер подсвечен красным на поле). Проверка
  запускается через мгновение после того, как вы перестали печатать, и никогда - пока
  зажата клавиша.
- **Параметры**: по строке на каждую строку `--! param` в заголовке скрипта, с подписью
  рядом с полем: текст, число или флажок для истина/ложь. Очищенное значение возвращается
  к значению заголовка по умолчанию; текстовый параметр без значения по умолчанию нужно
  заполнить до предпросмотра.
- **Файл** (путь внутри репозитория, для начала `.gitpoulpi/rewrite/script.lua`) с
  кнопками **Загрузить из файла...** (заменяет текст) и **Сохранить в файл...**.
- **Пробный запуск** запускает скрипт на commit'ах, выбранных в Log, а если не выбрано
  ни одного - на 20 самых новых, и ничего не записывает. Таблица перечисляет каждый
  commit (короткий id), все поля, которые он изменил бы, в виде `old -> new`, и строки
  `log(...)` скрипта. **Отмена** прекращает ожидание. Если скрипт падает, показаны commit
  и причина.
- Крестик, щелчок вне редактора и `Esc` закрывают его; `Tab` и `Shift+Tab` переходят
  между редактором, параметрами, файлом, кнопками и результатами; `F5` запускает
  пробный запуск.

Предпросмотр отказывает скрипту, который не компилируется: панель предпросмотра пишет
*скрипт завершился с ошибкой* и строку (а при сбое на commit'е - его короткий id и
причину). В сборке без скриптов этот вид остаётся в меню добавления, серым.

## Скрипт от ИИ

Когда ИИ включён ([Помощь ИИ](ai.md)), в редакторе скрипта есть кнопка
`✦ Написать с ИИ...`, а в палитре - `✦ Переписывание: написать скрипт с помощью ИИ...`:
она открывает окно переписывания с новым правилом «Скрипт» и открытым диалогом. Ничего
не отправляется, пока вы не нажмёте **Отправить**: диалог по мере набора показывает
точный текст, который уйдёт.

- **Что должен делать скрипт?** Своими словами: *перенести каждый commit, сделанный
  ночью, на следующее утро*, *заменить мой старый email новым, только до 2024 года*.
- **Отправить выборку commit'ов** (выключено): если отметить, добавляются автор, дата и
  тема тех commit'ов, на которых работал бы «Пробный запуск» (выбранные в Log, иначе 20
  самых новых), чтобы модель увидела, как выглядят ваши данные. Содержимое файлов и тела
  commit'ов не отправляются никогда. Пока флажок снят, данные commit'ов не покидают
  компьютер.
- **Что отправляется** - панель только для чтения на чуть более тёмном фоне, свёрнутая при
  открытии диалога (тогда он короткий). Щёлкните её заголовок, нажмите `Alt+W` или перейдите
  к ней клавишей `Tab` и нажмите `Enter`, чтобы показать её: она перечисляет инструкции
  (фиксированный контракт скрипта, затем ваши инструкции для ИИ) и ваш запрос, со своей
  полосой прокрутки (перетаскивайте её, крутите колесо над панелью или используйте стрелки,
  `PageUp`, `PageDown`, `Home` и `End`, пока на ней фокус). Профиль, который их получит,
  указан строкой выше. Диалог растёт под панель в пределах экрана.
- **Отправить** (`Tab` до кнопки, `Enter`). Пока модель работает, диалог ждёт, а `Esc`
  отменяет запрос. При ошибке диалог остаётся с причиной, чтобы можно было повторить.

Ответ проверяет та же проверка демона, что и набранный скрипт; ошибка компиляции один
раз отправляется обратно модели. Затем скрипт **заменяет текст в редакторе** (диалог
предупреждает, если в редакторе лежит не исходный шаблон), а заголовок редактора
показывает *✦ написано ИИ: прочитайте до предпросмотра*, пока вы не измените текст.
Скрипт никогда не запускается, не идёт в предпросмотр и не применяется за вас: прочитайте
его, нажмите **Пробный запуск**, затем делайте предпросмотр, как для любого скрипта. Он
работает в той же песочнице, что и написанный вами (без файлов, часов и сети).

Из командной строки: `gitpoulpi ai rewrite-script "<instruction>" [--sample N]` выводит
скрипт и результат `rewrite script check` для него в виде JSON и ничего не запускает (код
выхода 2, если он всё ещё не компилируется). Используется профиль *Скрипт переписывания
истории* из Настройки > ИИ.

## Правила от ИИ

Когда ИИ включён ([Помощь ИИ](ai.md)), в окне переписывания рядом с «Сохранить» и
«Загрузить» есть кнопка `✦ Создать правила с ИИ...`, клавиша `Alt+I` (*Создать правила
переписывания с помощью ИИ* в Настройки > Клавиатура и мышь, контекст *Переписывание истории*), а в
палитре - `✦ Переписывание: создать правила с помощью ИИ...`. Если ИИ выключен или в
сборке нет ИИ, ни кнопки, ни строки палитры нет. Вы своими словами описываете, как
нужно переписать историю (*заменить мой старый адрес a@b.org на c@d.org*, *убрать
secrets.txt из всей истории*, *сдвинуть мои даты на два часа*), а модель предлагает
правила и настройки, которые **заполняют окно переписывания**. Ничего не отправляется,
пока вы не нажмёте **Отправить**: диалог по мере набора показывает точный текст, который
уйдёт.

- **Как нужно переписать историю?** Многострочное поле: `Enter` - новая строка,
  `Ctrl+Enter` или `Ctrl+S` отправляет, `Esc` и крестик отменяют.
- **Отправить область, названия веток и tag'ов и авторов истории** (выключено): если
  отметить, добавляются область с панели области, названия веток и tag'ов и разные
  авторы (имя и email) самых новых commit'ов, которые показывает Log (не больше 20
  commit'ов), чтобы модель могла точно назвать ваш email (`ai rewrite-rules --context` в
  командной строке вместо этого читает 200 самых новых commit'ов). Содержимое файлов и
  сообщения commit'ов не отправляются никогда. Пока флажок снят, компьютер покидают только ваше
  описание и фиксированные инструкции.
- **Заменить текущие правила** (только если в окне уже есть правила; выключено): по
  умолчанию новые правила добавляются после ваших; если отметить, они их заменяют
  (область и настройки, которые указывает ответ, применяются в любом случае).
- **Что отправляется** - панель только для чтения на чуть более тёмном фоне, отдельно от
  полей над ней, и **свёрнутая** при открытии диалога (тогда он короткий). Щёлкните её
  заголовок, нажмите `Alt+W` или перейдите к ней клавишей `Tab` и нажмите `Enter`, чтобы
  показать её: она перечисляет инструкции (словарь правил, затем ваши инструкции для ИИ) и
  ваш запрос и имеет свою полосу прокрутки (перетаскивайте её, крутите колесо над панелью
  или используйте стрелки, `PageUp`, `PageDown`, `Home` и `End`, пока на ней фокус).
  Профиль, который их получит, указан строкой выше. Диалог растёт под панель в пределах
  экрана. У поля описания появляется своя полоса прокрутки, когда текст не помещается.

Модель может использовать любой вид правил с этой страницы, кроме **Скрипта** (это код:
*Скрипт от ИИ* показывает скрипт на проверку) и формы *Найти и заменить в файлах* с
секретными значениями (секретные значения никогда не передаются модели: используйте
вкладку «Секреты»). Она может задать областью текущую ветку, все локальные ветки и tag'и
или существующие ветки и tag'и по именам, а также параметры *Tags*, *коммиттер*,
*Пустые commit'ы* и *сокращённые id в сообщениях*. То, что окно переписывания не умеет
выразить (ограничение по дате вроде *с марта*, диапазон commit'ов), не угадывается:
модель говорит об этом в замечании. Что делать с подписями, модель никогда не решает:
вас спросят при применении.

**ИИ только готовит правила и настройки.** Он никогда ничего не запускает в
предпросмотр, не применяет и не выполняет: ответ копируется в окно переписывания, как
загруженный вами рецепт, предпросмотр на экране устаревает, а «Предпросмотр» и
«Применить» (с их вопросами и подтверждениями), как всегда, за вами. Каждое правило
разбирается и проверяется отдельно той же проверкой, что используют редактор и движок;
правило, не прошедшее её, пропускается. Если что-то пропущено или модель сделала
замечание, после добавления правил появляется список (*Пропущено (допустимые правила
сохранены)*, у каждого пункта номер, название и причина), его закрывают `Enter` или
`Esc`. Прочитайте правила, при необходимости измените их, затем запустите предпросмотр.

Из командной строки: `gitpoulpi ai rewrite-rules "<description>" [--context]` выводит
предложение в виде JSON (`recipe`, который читает `rewrite preview --recipe-json`,
`problems`, `notes` и `applied: false`) и ничего не запускает (код выхода 2, если что-то
пропущено). Инструмент MCP - `ai_rewrite_rules`. Используется профиль *Правила
переписывания истории* из Настройки > ИИ.

## Lua-скрипты

Правило-скрипт запускает вашу функцию на каждом commit'е. Это обычный Lua 5.4 в
песочнице: без файлов, часов, процессов, модулей и `pcall`; один и тот же скрипт на одной
и той же истории всегда даёт один и тот же результат, а вызов, который перешагнул 10
миллионов инструкций, 64 МиБ или 5 секунд, останавливается с ошибкой, называющей commit.

```lua
--! name: Replace an email
--! param old_email: text "Email to replace"
--! param new_email: text "New email"
function rewrite_commit(c, ctx)
  if c.author.email == ctx.params.old_email then
    return { author = { email = ctx.params.new_email } }
  end
end
```

`c` содержит `id`, `parents`, `tree`, `author` и `committer` (`name`, `email`, `time`,
`offset_minutes`), `message` и `signed`. `ctx` содержит `index`, `total`, `params`,
`state` (верните `state = {...}`, чтобы передать данные следующему commit'у) и
`window.before` / `window.after` (задаются через `--! window: N`). Возвращайте только то,
что меняется: `author`, `committer`, `message`. Помощники: `regex_replace`,
`regex_match`, `stable_hash`, `rand`, `weekday`, `hour`, `log`, а для сообщений
`trailers(message)` (список `{key, value}`), `set_trailer(message, key, value)` (заменяет
трейлеры с этим ключом; четвёртый аргумент `"add"` или `"skip"` меняет это поведение),
`remove_trailer(message, key)` и `at("2024-03-05 18:30", offset_minutes)` (дата в
заданном смещении как время Unix).

Из командной строки: `gitpoulpi rewrite script check my.lua` компилирует скрипт,
`gitpoulpi rewrite script test my.lua --commit HEAD --param old_email=a@b` показывает, что
он изменил бы, ничего не записывая, а
`gitpoulpi rewrite preview --script my.lua --script-param old_email=a@b` строит план всего
переписывания.

## Внешние скрипты (shell, Python, Lua)

Тот же контракт, что у Lua-скрипта, но выполняет его программа на вашем компьютере:
*Shell-скрипт* (bash или sh; PowerShell в Windows или любой `.ps1`), *Python* и *Lua
(установленный)* (ваш собственный `lua`, а не встроенный; в нём нет библиотеки JSON,
поэтому шаблон разбирает строку по шаблону). **Они не в песочнице: внешний скрипт
работает с вашими правами** и может читать и менять всё, что доступно вам. Об этом
говорят панель правила и заголовок редактора.

Как они общаются: GitPoulpi запускает скрипт один раз за прогон и присылает ему по
одному JSON-запросу в строке на стандартный ввод (поля commit'а, `params`, `state`,
возвращённый прошлым ответом); он отвечает одной JSON-строкой на стандартный вывод с
теми же полями, что возвращает Lua-скрипт (`author`, `committer`, `message`, `state`,
`log`), или `{"error": "text"}`, чтобы сдаться. Диагностику печатайте в стандартный
поток ошибок: она появится как строки `log` этого commit'а. Строки заголовка начинаются
с `#!` для shell и Python (`#! name: ...`, `#! param old: text "Old"`; строка shebang
остаётся shebang) и с `--!` для Lua.

```sh
#!/bin/sh
#! name: Uppercase author names
while IFS= read -r line; do
  name=$(printf '%s' "$line" | sed -n 's/.*"author":{[^}]*"name":"\([^"]*\)".*/\1/p' | tr 'a-z' 'A-Z')
  printf '{"author":{"name":"%s"}}\n' "$name"
done
```

**Что он получает.** Пустое окружение, кроме `PATH`, `HOME` / `USERPROFILE`,
`SYSTEMROOT`, `TEMP` / `TMP` и `LANG`; новую временную папку как рабочую (в ней своя
копия скрипта); путь к репозиторию не передаётся. **Ограничения по времени:**
`rewrite.script_timeout_ms` (5000) на каждый ответ и `rewrite.script_total_timeout_s`
(3600) на весь прогон. Если лимит превышен, скрипт падает, печатает не JSON или задача
отменена, GitPoulpi убивает скрипт и всё, что он запустил, а переписывание останавливается
с указанием commit'а и причины; ничего не сдвинуто.

**Какие языки доступны.** Их перечисляет `rewrite.external_scripts` в `config.toml`: по
умолчанию `["shell"]`; `"python"` и `"lua"` добавьте сами в `config.toml` (`[rewrite]`,
`external_scripts = ["shell", "python"]`; список нельзя задать через `gitpoulpi config
set`). Язык, которого нет в списке, в окне переписывания серый, а CLI и MCP отказывают
(`scripts_disabled`); язык из списка, чей интерпретатор не найден, серый с подсказкой по
установке (`tool_missing`).

**Доверие.** Даже когда язык включён, скрипт запускается только после того, как вы
доверились именно его тексту. Скрипт, который вы набрали в окне переписывания, ваш и
запускается сразу; скрипт из общего рецепта или файла репозитория - нет: предпросмотр и
«Пробный запуск» останавливаются и спрашивают *Доверять этому скрипту?* с двумя
пронумерованными ответами без выбранного по умолчанию (`1` - доверять и продолжить, `2` -
нет, `Esc` оставляет как есть). Доверие запоминает SHA-256 текста для этого репозитория,
так что изменённый скрипт спросит снова, а клонированный репозиторий не может сам
запустить код у вас. Из командной строки прочитайте файл, затем
`gitpoulpi rewrite script trust FILE` (или `--trust` у `preview`, `run`, `script check` и
`script test`: доверяет и идёт дальше). Агент через MCP ничему доверять не может: он
запускает только скрипт, которому вы доверились раньше.

**Проверка.** Строка проверки под редактором для недоверенного скрипта говорит *Скрипту
ещё не доверяют* (ничего не запускалось); доверенный GitPoulpi запускает один раз с
выдуманным commit'ом (`"dry_run": true`) и проверяет, что ответ соответствует контракту.
`gitpoulpi rewrite script check FILE` делает то же и сообщает `trust`, `hash` и
`interpreter`.

## Из командной строки

`gitpoulpi rewrite` (и MCP-инструменты с теми же именами) запускает тот же движок для
скриптов и агентов. **Рецепт** - это файл TOML или JSON, тот, что сохраняет окно
переписывания (`--recipe FILE` или `-` для стандартного ввода), а флаги добавляют правила
после собственных правил рецепта.

```
gitpoulpi rewrite preview --recipe fix.toml --all     # план, ничего не меняет
gitpoulpi rewrite apply --run ID --digest D           # выполнить проверенный вами план
gitpoulpi rewrite run --fix-message-encoding --signatures strip --yes
gitpoulpi undo                                        # возвращает всё на место
```

- Правила в виде флагов: `--set-name` / `--set-email` с `--match-email` (личность),
  `--mailmap`, `--shift-dates`, `--replace-message FIND=WITH`, `--trailer-add`,
  `--trailer-remove`, `--trailer-map`, `--fix-message-encoding`
  (`--fix-name-encoding`), `--remove-path`, `--remove-blobs-over`, `--replace-content`,
  `--eol` (`--eol-paths`), `--strip-exec`, `--reencode` (`--encoding-paths`),
  `--move-path`, `--into-subdir`, `--extract`, `--lfs-import`, `--lfs-export`, `--script`,
  `--remove-signatures`, `--remove-finding`. Область - текущая ветка, `--all-local` или
  `--ref R` (можно повторять), начиная с `--since REV`.
- **Вопросы без значения по умолчанию** задаются флагами: `--signatures
  strip|resign-signed|resign-all`, когда меняются подписанные commit'ы, и `--extract-mode`
  для выноса. Без них ответ - отказ или `needs_choice` (код выхода 3), но не догадка.
- **Коды выхода:** 0 готово; 1 ошибка (нечитаемый рецепт, неверные флаги); 2 отказ с
  причиной (`stale`, `signature_choice_needed`, `dirty_paths_touched`, `empty_scope`,
  ...); 3 вопрос, на который нужно ответить, или отправленные ссылки, которым нужен
  `--yes`.
- `preview` хранит план в репозитории, поэтому `apply` работает из более поздней команды,
  после перезапуска демона или из другого интерфейса; план, который больше не совпадает
  со своим дайджестом, - это `stale`.

В [справочнике CLI](cli-reference.md) есть все флаги, а [MCP и агенты](mcp-and-agents.md)
говорят, какие инструменты получает агент (инструмента очистки нет, пока вы его не
включите, а агент не может довериться скрипту).

## Предложения от ИИ-агентов

Агент может **предложить** переписывание, но не выполнить его. `gitpoulpi ui propose
rewrite --recipe FILE|-` (MCP-инструмент `ui_propose_rewrite`, выключен, пока не задано
`[mcp] allow_ui_propose = true`) открывает окно переписывания в вашем запущенном окне с
правилами рецепта, уже стоящими в списке, и фиолетовой плашкой *✦ Предложено: <агент>:
переписывание истории (3 правила) · Ctrl+Enter принять · Esc отклонить*.

- **Ничего не выполняется.** Ни предпросмотр, ни «Применить», ни push, ни очистка:
  предложение только заполняет правила. Вы читаете их, при желании правите, делаете
  **Предпросмотр** и применяете своей клавишей. Закрытие окна отклоняет предложение.
- **Чего агент не может в него положить:** скрипт (он выполнился бы при предпросмотре),
  больше 50 правил, секретные значения (они убираются из рецепта до отправки).
  Такое предложение отклоняется с указанием причины.
- Агент может прочитать исход в `ui state` (`accepted`, когда вы применили правила как
  предложено, `accepted_edited`, когда сначала изменили их, `rejected`, когда закрыли
  окно). Одно предложение за раз; оно отклоняется, пока открыт другой ваш диалог.

## Инструменты

Большинству переписываний истории не нужно ничего, кроме Git: смена авторов и
коммитеров, применение `.mailmap`, анонимизация, сдвиг дат или ограничение их часами,
правка сообщений и трейлеров, замена содержимого, удаление путей или больших файлов и
перемещение путей выполняются внутри GitPoulpi.

**Lua-скрипты встроены.** Интерпретатор входит в GitPoulpi, поэтому для Lua-скрипта не
нужны ни дополнительная программа, ни настройка. Скриптам на shell, Python и
установленном Lua нужен свой интерпретатор (см. таблицу ниже); они описаны в разделе
[Внешние скрипты](#внешние-скрипты-shell-python-lua).

Некоторые возможности используют внешнюю программу. GitPoulpi проверяет её наличие
(программа ищется в `PATH`, в Windows ещё через `PATHEXT` и собственный `usr/bin` Git for
Windows, и должна ответить на `--version` за 2 секунды); ответ кэшируется на минуту, а
«Проверить снова» спрашивает заново. Правило, которому нужна недостающая программа,
остаётся в списке серым, с причиной и подсказкой по установке, а предпросмотр отказывает
до запуска чего-либо.

| Возможность | Инструмент | Примечания |
|---|---|---|
| Повторная подпись commit'ов | `gpg` (OpenPGP), `ssh-keygen` (`gpg.format = ssh`) или `gpgsm` (`gpg.format = x509`) | Для подписи SSH и X.509 нужен ещё `user.signingkey`. Учитываются `gpg.program`, `gpg.ssh.program` и `gpg.x509.program`. |
| Перенос в LFS (два правила LFS) | `git-lfs` 3.0 или новее | Та же проверка, что в панели LFS. |
| Скрипты Python | `python` 3.8 или новее (`py -3` в Windows) | По умолчанию выключены: добавьте `"python"` в `rewrite.external_scripts`. |
| Скрипты на установленном Lua | `lua5.4`, `lua54`, `lua` или `luajit` | По умолчанию выключены: добавьте `"lua"` в `rewrite.external_scripts`. |
| Shell-скрипты | `bash`, `pwsh` (PowerShell) или `sh` | По умолчанию включены (`"shell"`). Скрипту PowerShell (файл `.ps1`, shebang `pwsh` или любой shell-скрипт в Windows) нужен `pwsh` или `powershell`; POSIX-скрипту - `bash` или `sh` (в Windows их даёт Git for Windows). |

Подсказки по установке, сначала Windows:

- Windows: Git for Windows включает `gpg`, `ssh-keygen`, `bash`, `sh` и Git LFS. Иначе
  `winget install GnuPG.GnuPG`, Параметры > Дополнительные компоненты > Клиент OpenSSH,
  `winget install GitHub.GitLFS`, `winget install Python.Python.3.12`,
  `winget install DEVCOM.Lua`, `winget install Microsoft.PowerShell`.
- Linux: пакеты дистрибутива (`gnupg`, `openssh`, `git-lfs`, `python3`, `lua5.4`, `bash`,
  `powershell`).
- macOS: `brew install gnupg git-lfs python lua powershell`; `ssh-keygen` и `sh`
  встроены.
