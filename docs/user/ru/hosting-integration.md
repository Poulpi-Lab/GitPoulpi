# Интеграции с хостингами и трекерами задач

GitPoulpi подключается к следующим продуктам:

- **Хостинг** (pull request, задачи, клонирование из вашего аккаунта, ключи SSH):
  GitHub, GitHub Enterprise, GitLab, GitLab Self-Managed, Azure DevOps,
  Azure DevOps Server, Bitbucket, Bitbucket Data Center, Gitea и Forgejo
  (включая Codeberg). **Gerrit Code Review** - хостинг только для ревью: его
  изменения и есть pull request, задач в нём нет.
- **Трекеры задач** (только задачи): Jira Cloud, Jira Data Center, Trello,
  Linear, YouTrack (Cloud и Server) и Redmine.
- **Локальные заметки Markdown** (только задачи, без токена, без сети): папка с заметками Markdown, например папка хранилища Obsidian, см. [Локальные задачи и Obsidian](local-issues.md).

Каждая интеграция использует **персональный токен**. Аккаунта GitPoulpi и входа
через OAuth нет. Интеграции необязательны и **включаются отдельно для каждого
репозитория**: пока вы не свяжете репозиторий, ничего не загружается. Токен
хранится в вашем хранилище учётных данных (credential helper), а не в
`config.toml`. Обычным операциям `git` (fetch, pull, push) интеграция не нужна:
они используют учётные данные, которые уже есть у вашего `git`.

**Куда идти дальше.** Эта страница - настройка: токены, подключение, связывание
репозитория, ключи SSH. Когда учётная запись подключена:

- разделы PULL REQUESTS и ЗАДАЧИ на боковой панели, доска задач, создание pull
  request'а или задачи, значок на панели инструментов и ссылки в сообщениях
  commit'ов: **[Pull request'ы и задачи](pull-requests-and-issues.md)**;
- окно одной задачи или запроса с комментариями, написанием и публикацией от
  имени: **[Беседы](conversations.md)**;
- чтение и ревью запроса с обсуждениями кода и отложенным ревью:
  **[Ревью pull request'а](review.md)**;
- pull request'ы и задачи всего рабочего пространства в одном списке:
  **[Radar](radar.md)**.

## 1. Создайте токен на хосте

В форме подключения есть ссылка «Создать токен на <хост>». Она открывает
страницу токенов хоста с уже отмеченными нужными правами. Если делать вручную:

| Хост | Где | Права |
|---|---|---|
| GitHub, GitHub Enterprise | Settings > Developer settings > Personal access tokens (classic) > Generate new token | `repo` (репозитории, pull request, задачи), `read:user` (кто вы), `admin:public_key` (только чтобы добавлять и удалять ключи SSH) |
| GitLab, GitLab Self-Managed | User settings > Access tokens > Add new token | `api`, `read_user` |
| Azure DevOps | User settings > Personal access tokens, на странице `dev.azure.com/<organization>/_usersSettings/tokens` | `Code (Read & write)`, `Work Items (Read & write)`. Создавайте токен **для этой организации**, а не для «All accessible organizations»: глобальные токены перестанут работать 2026-12-01. |
| Azure DevOps Server | Та же страница на вашем сервере (`https://<server>/<collection>/_usersSettings/tokens`) | Те же два права |
| Bitbucket | `id.atlassian.com/manage-profile/security/api-tokens` > Create API token with scopes | `read:user:bitbucket`, `read:workspace:bitbucket`, `read:repository:bitbucket`, `write:repository:bitbucket`, `read:pullrequest:bitbucket`, `write:pullrequest:bitbucket`. Для ключей SSH ещё `read:ssh-key:bitbucket`, `write:ssh-key:bitbucket`, `delete:ssh-key:bitbucket`. |
| Bitbucket Data Center | Аватар профиля > Manage account > HTTP access tokens | `Repository (Read & write)`, `Projects (Read)` |
| Gitea, Forgejo (Codeberg) | Settings > Applications > Generate New Token, на странице `<хост>/user/settings/applications` | Чтение `user`; чтение и запись `repository`, `issue` и `user` (последнее для ключей SSH). Gitea не показывает права постфактум, поэтому GitPoulpi не может предупредить о недостающем: отклонённый вызов сам об этом говорит. |
| Linear | Settings > Account > Security & access > Personal API keys > New API key (`linear.app/settings/account/security`) | Read, write, create issues. Ключ действует от вашего имени. |
| YouTrack (Cloud и Server) | Ваш профиль > Account Security > New token, на странице `<хост>/users/me?tab=account-security` | Право `YouTrack`. Постоянный токен действует от вашего имени. |
| Gerrit | Settings > HTTP Credentials > Generate new token (свежие серверы; старые: Generate new password), на странице `<хост>/settings/#HTTPCredentials` | Нет. Токен - это **пароль HTTP**, он действует от вашего имени; имя пользователя вводится рядом. |
| Redmine | My account > API access key > Show, на странице `<хост>/my/account`. Администратор должен включить **Administration > Settings > API > Enable REST web service**. | Нет. Ключ действует от вашего имени. |
| Jira Cloud | `id.atlassian.com/manage-profile/security/api-tokens` > Create API token (классический, без scopes) | Нет. Токен действует от вашего имени. |
| Jira Data Center | Profile > Personal Access Tokens | Нет. Токен действует от вашего имени. |
| Trello | Сначала **ключ API** на `trello.com/apps/admin` (создайте Power-Up, затем сгенерируйте ключ API). Затем **токен** на `trello.com/1/authorize?...&key=<ваш ключ>`. | `read`, `write` |

Назовите токен, например, «GitPoulpi» и задайте срок действия. Скопируйте токен:
хост показывает его только один раз.

## 2. Подключите его

1. Нажмите `Ctrl+,` и выберите **Интеграции**.
2. Выберите продукт слева. Продукты разделены на две группы: **Хостинг** и
   **Трекеры задач**.
3. Нажмите **Подключить**. Чтобы добавить второй аккаунт того же продукта,
   используйте **+ Добавить профиль**.

   ![Страница «Интеграции»: продукты слева и кнопка «Подключить» для GitHub](../images/settings-integrations.png)

4. Заполните форму и вставьте токен. Пока вы вводите, токен виден открытым
   текстом, поэтому убедитесь, что за вами никто не смотрит. Форма перечисляет
   нужные права.

   ![Форма подключения: поле «Персональный токен доступа», права repo, read:user и admin:public_key, ссылка для создания токена на github.com и кнопки «Подключить» и «Отмена»](../images/settings-connect.png)

5. Нажмите **Подключить**. GitPoulpi проверяет токен на хосте в фоновом режиме.
   Затем на странице появляется карточка с вашим именем и логином, зелёная
   надпись «Подключено» и раздел «Ключ SSH». Токен без одного из нужных прав всё
   равно подключается, а недостающие права перечисляются красным.

На карточке: **Изменить** снова открывает форму. **Отключить** удаляет токен и
сохраняет профиль. **Удалить** удаляет и то и другое после подтверждения.

Клавиши на странице «Интеграции»: `Tab` / `Shift+Tab` переходят между списком
продуктов, полосой профилей и формой. `a` добавляет профиль, `e` изменяет его,
`d` или `Delete` удаляет, `o` открывает страницу токена, `Esc` возвращает на
шаг назад.

### Что запрашивает каждая форма

Ссылка «Создать токен» работает только после того, как вы заполните хост или
организацию.

- **GitHub, GitLab:** только токен. **GitHub Enterprise** и
  **GitLab Self-Managed** дополнительно спрашивают **Домен хоста**
  (`gitlab.example.com`; https, если не указать `http://`). Имени без точки
  (служба Docker или машина в локальной сети) нужен порт или `http://`: `gitea:3000`,
  `http://nas`. Собственный сервер может работать по
  обычному http, например локальный контейнер по адресу `http://localhost:8080`. Токен, отправленный
  по обычному http, передаётся без шифрования, поэтому используйте http только в
  локальной или доверенной сети.
- **Azure DevOps:** **Организация**, то есть имя в
  `dev.azure.com/<organization>`. Адрес вида `https://<org>.visualstudio.com`
  тоже принимается. Для двух организаций нужны два профиля. Репозиторий
  использует профиль той организации, которая указана в его remote. **Azure
  DevOps Server** запрашивает **URL коллекции**, например
  `tfs.corp/tfs/DefaultCollection`. GitPoulpi не использует системный credential
  helper для Azure DevOps: Git Credential Manager хранит там токен входа, а не
  персональный токен доступа.
- **Bitbucket:** **Эл. почта аккаунта Atlassian** и токен API. Если почта не
  указана, токен отправляется как bearer-токен: так используйте токен доступа
  рабочего пространства или репозитория. GitPoulpi находит ваши рабочие
  пространства по токену. **Bitbucket Data Center:** **URL сервера** и токен
  HTTP-доступа.
- **Gitea, Forgejo:** **Домен хоста** и токен. **Forgejo** начинает с
  `https://codeberg.org`: для собственного сервера замените его. У Gitea
  публичного значения по умолчанию нет. Адрес `http://localhost:3000` работает
  для локального сервера. Оба вида используют один клиент (Forgejo - форк Gitea
  с тем же `/api/v1`); токен отправляется как `Authorization: token <токен>`.
  Системный credential helper для них не используется.
- **Jira Cloud:** **URL сайта** (`acme.atlassian.net`), **Эл. почта аккаунта
  Atlassian** и классический токен API. Токены Jira с ограниченными правами
  (scoped) не поддерживаются. **Jira Data Center:** **URL сервера** и
  персональный токен доступа.
- **Trello:** **Ключ API** и **токен**. Ключ API публичный, поэтому он хранится
  в `config.toml` (как `account`). Токен секретный и попадает в credential
  helper. В форме две ссылки: «Получить ключ API в Trello» и, после ввода
  ключа, «Создать токен». Ключ и токен передаются в заголовке, а не в URL.

- **Linear:** только **ключ API**: у Linear один общедоступный хост, поэтому
  вводить адрес не нужно. Ключ отправляется как есть в заголовке
  `Authorization` (для личных ключей Linear `Bearer` не принимает). Чтобы
  ссылки `ENG-12` в сообщениях commit'ов открывали нужную страницу, сохраните в
  профиле URL вашего рабочего пространства (`https://linear.app/acme`, из CLI:
  `--url`); сами строки задач всегда несут точный адрес.
- **YouTrack:** **URL сайта** (`acme.youtrack.cloud` для Cloud, иначе ваш
  сервер, с контекстным путём, если он есть, например `host/youtrack`) и
  постоянный токен, отправляемый как `Authorization: Bearer`. Один и тот же
  клиент обслуживает Cloud и Server (`<url>/api`).
- **Gerrit:** **URL сервера** (с контекстным путём, если он есть), ваше **Имя
  пользователя** и пароль HTTP как токен. Они передаются обычной аутентификацией
  HTTP basic; GitPoulpi работает с REST API сервера по пути `/a/` и игнорирует
  строку `)]}'`, с которой начинается каждый ответ. Имя пользователя не секрет и
  хранится в `config.toml` (как `account`), пароль попадает в credential helper.
  Репозиторий привязывается к *проекту* Gerrit в PULL REQUESTS (там перечислены
  его изменения); задач в Gerrit нет, а изменение создаётся push'ем (см. *Push на
  ревью* в [Ревью](review.md#gerrit)).
- **Redmine:** **URL сайта** вашего Redmine (с подпутём, если он есть, например
  `host/redmine`) и ваш ключ API, отправляемый как `X-Redmine-API-Key`. Если
  Redmine отвечает 403 или страницей HTML, REST-сервис выключен (попросите
  администратора или включите его в **Administration > Settings > API**).

Jira, Trello, Linear, YouTrack и Redmine - только трекеры задач: без pull request, без репозиториев для
клонирования и без ключей SSH. В Bitbucket задач нет (Atlassian закрыл Bitbucket
Issues). Вместо этого свяжите раздел ЗАДАЧИ репозитория Bitbucket с проектом
Jira.

## 3. Где хранится токен

Токен хранится в системном **credential helper** (Git Credential Manager в
Windows, libsecret или `pass` в Linux, Keychain в macOS). Для этого используется
закрытая запись, которую нельзя спутать с учётными данными настоящего хоста.
Токен никогда не записывается в `config.toml` и никогда не выводится.

Если credential helper не настроен или отказывается принять токен, GitPoulpi
хранит токен **в памяти только на время этого сеанса** и сообщает вам об этом.
После перезапуска подключитесь заново.

GitPoulpi ищет токен профиля в таком порядке:

1. Переменная окружения `GITPOULPI_TOKEN_<PROFILE ID>`. Используйте её, чтобы
   передать токен, не сохраняя его, например в CI.
2. Токен, сохранённый для профиля (`token_ref`).
3. Только для профилей GitHub и GitLab: системный credential helper для этого
   хоста, если другой включённый профиль не использует тот же хост.

Каждый профиль - это запись `[[integrations]]` в `config.toml`. См.
[справочник по конфигурации](config-reference.md#integrations-хостинги-и-трекеры-задач).

## Проверка безопасности

Сохранённый токен безопасен лишь настолько, насколько безопасен адрес, на который он отправляется. Поэтому GitPoulpi запоминает для каждой интеграции, к чему она была подключена, и останавливается, когда это меняется:

- **Адрес.** При первом использовании интеграции (или подключении) её адрес записывается в `trust.toml` в закрытой папке данных, доступной только пользователю (`<data>/private/`), а не в `config.toml`: правка конфигурации никогда не сможет расширить то, чему доверяют. Если адрес в конфигурации больше не совпадает с записанным, на него ничего не отправляется, а токен даже не читается. Разные написания одного адреса (`HTTPS://Git.Example.com:443/`) - один и тот же адрес; похожий хост - нет.
- **Учётная запись.** После подключения токена, а затем примерно раз в сутки (и один раз за запуск для токена из `GITPOULPI_TOKEN_*` или помощника учётных данных) GitPoulpi спрашивает у хоста, кому принадлежит токен, и сравнивает **id** учётной записи, а не логин. Токен, который теперь принадлежит другому человеку, останавливается.
- **Сертификат.** Серверы, сертификат которых не ведёт цепочкой к известному центру (частный центр сертификации, самоподписанный сервер), принимаются только для того точного ключа, который вы приняли, а рукопожатие TLS по-прежнему доказывает, что сервер владеет этим ключом. При строгой привязке ключ должен совпадать, даже если сертификат ведёт цепочкой к публичному корню; цена - что каждая смена ключа спрашивает снова, поэтому режим включается по желанию. Публичные хосты (github.com, gitlab.com, codeberg.org, bitbucket.org, dev.azure.com, `*.atlassian.net`, ...) записи о сертификате не хранят.
- **Обычный http.** Адрес `http://`, не являющийся loopback, отклоняется, если вы не разрешили его для этой интеграции.

Каждый запрос также ограничен собственным адресом интеграции (а для публичного хоста - его хостом API, например `api.github.com`): запрос куда-либо ещё отклоняется до отправки, а перенаправление на другой адрес не выполняется.

**Интеграции, подключённые до появления этой проверки,** получают свою запись молча, из конфигурации в том виде, какой она была, при первом использовании после обновления: они сохраняют нынешний уровень доверия, и ничто ничего не спрашивает.

### Из командной строки

Остановленная команда завершается с кодом выхода 2 и выводит, что изменилось (см. [справочник по CLI](cli-reference.md)). `gitpoulpi hosting integrations trust <id>` показывает, чему доверено; `--accept-origin <url>`, `--accept-account <id>`, `--accept-certificate <sha256>`, `--strict-tls on|off` и `--allow-insecure-http on|off` принимают по одному, называя точное значение. После принятия нового адреса введите токен заново. Отключение (`hosting logout`) или удаление интеграции удаляет её токен, запись о доверии и то, что было закэшировано из неё (сохранённые списки репозиториев диалога клонирования, списки аккаунта Radar и черновики удалённых ревью её хоста).

Агент (MCP) ничего принять не может: ему сообщается, что проверка безопасности требует вас.

### В терминальном интерфейсе

Остановленный запрос открывает диалог **Проверка безопасности интеграции** поверх того, чем вы занимались. Он сообщает, что изменилось (старый и новый адрес, старая и новая учётная запись с их id или старый и новый сертификат в виде небольшой таблицы с отпечатком SHA-256 группами по четыре символа, субъектом, издателем и сроком действия), и что токен не отправлен. Ответы пронумерованы:

1. **Отключить** удаляет сохранённый токен, запись о доверии и то, что было закэшировано из интеграции.
2. **Доверять** новому адресу, учётной записи или сертификату (для незашифрованного адреса: **Разрешить обычный http**).
3. **Отмена** ничего не меняет.

Пока вы не нажмёте стрелку или цифру, ни один ответ не выделен, так что случайный Enter ничего не принимает. Esc и крестик закрытия отменяют; щелчок снаружи диалога ничего не делает. Длинный текст прокручивается колесом, Page Up/Page Down или полосой прокрутки. Несколько проверок встают в очередь (по одной на интеграцию и вид изменения) и задаются одна за другой. Отменённая проверка не появляется снова, пока ничего не изменилось; **Интеграции: проверка безопасности** в палитре команд возвращает её.

После того как вы доверились новому **адресу**, форма интеграции открывается с полем токена в фокусе и подсказкой «Рекомендуется ввести токен заново»: сохранённый токен туда никогда не отправлялся. В форме намеренно изменённый адрес принимается вместе с токеном, введённым для него; без токена форма попросит его.

В форме есть и два переключателя. **Строгая привязка сертификата** (для адреса https) закрепляет ключ сертификата, который сервер предъявляет при подключении. **Разрешить обычный http (без шифрования)** предлагается только для адреса `http://`, не являющегося этой машиной, с красным предупреждением о том, что токен передаётся открытым текстом. Карточка подключённой интеграции показывает закреплённый отпечаток.

### Что токен может делать и до какого срока

Подключение также спрашивает у хоста, что может токен. GitHub (классические токены), GitLab и Bitbucket (когда он присылает области действия) сообщают свои области: карточка показывает жёлтую строку «У этого токена больше прав, чем нужно GitPoulpi» со списком областей сверх используемых GitPoulpi, причём чувствительные (например, `delete_repo`, `admin:org`, `sudo`) выделены красным, с советом использовать токен с точными правами и сроком действия. Классический токен GitHub (`ghp_...`) получает этот совет, даже когда его области точны. У токена GitHub с точными правами нельзя спросить его разрешения, поэтому показывается только срок действия. Карточка показывает дату истечения, когда хост её сообщает. Токен без срока действия не показывает напоминания, а остальные продукты не сообщают областей и не вызывают предупреждения. Те же поля есть в JSON команд `hosting integrations login` и `test` (`excess_scopes`, `token_flavor`, `recommend_fine_grained`, `expires_at`). Они читаются при подключении, поэтому карточка показывает их для сеанса, который подключился.

## 4. Свяжите репозиторий

Связывание явное и выполняется для каждого репозитория отдельно. Когда профиль
подключён, на боковой панели Refs после TAGS появляются раздел **PULL REQUESTS**
и раздел **ЗАДАЧИ**. В каждом разделе два выпадающих списка: провайдер и проект.

- Список провайдеров **предлагает** аккаунты, соответствующие remote
  репозитория (сначала `origin`), в виде строк вроде
  `owner/name · origin · GitHub`. Один выбор задаёт и провайдера, и проект.
- Автоматически ничего не связывается. Jira, Trello, Linear, YouTrack и Redmine
  никогда не предлагаются, потому что их не называет ни один remote: выберите их
  сами.
- **Нет (отвязать этот репозиторий)** в начале списка отвязывает раздел. Заново
  он сам не свяжется.
- Связь сохраняется в файле `.gitpoulpi/repo-state.toml` репозитория.

Два раздела связываются **независимо**. Например, pull request могут идти из
Azure DevOps, а задачи - из Jira.

| Провайдер | Проект для PULL REQUESTS | Проект для ЗАДАЧ |
|---|---|---|
| GitHub, GitLab | `owner/name`, `group/sub/proj` | то же |
| Azure DevOps | `Project/Repo` (организация берётся из профиля) | `Project` (рабочие элементы) |
| Gitea, Forgejo | `owner/name` | то же |
| Bitbucket | `workspace/slug` (Data Center: `PROJ/slug`) | нет: свяжите Jira |
| Jira | нет | ключ проекта, например `ABC` |
| Trello | нет | доска |
| Linear | нет | ключ команды, например `ENG` (команды перечислены) |
| YouTrack | нет | короткое имя проекта, например `ABC` |
| Gerrit | имя проекта Gerrit, например `team/tool` | нет |
| Redmine | нет | идентификатор проекта, например `bench` (последняя часть адреса проекта) |

Список проектов для ЗАДАЧ поддерживает поиск. Можно также ввести проект,
которого в списке нет.

**Дополнительный запрос.** У источника задач под выпадающим списком проектов
есть необязательная строка фильтра. Она объединяется с проектом через AND:

- Jira: фрагмент **JQL** (`component = UI AND labels = backend`).
- Azure DevOps: условие **WIQL** (`[System.AssignedTo] = @Me`).
- YouTrack: **запрос YouTrack** (`#Unresolved Type: Bug`, `tag: ui or tag: ux`).
  Он берётся в скобки, поэтому `or` не может расширить проект. Ваш `sort by:`
  заменяет `sort by: updated desc` по умолчанию.
- Redmine: нет (хватает фильтров состояния и «назначенные мне» в разделе).
- Linear: нет (хватает фильтров состояния и «назначенные мне» в разделе).
- Trello: выпадающий список, где вы отмечаете **списки** для показа. Если ничего
  не отмечено, показываются все открытые списки.
- GitHub и GitLab его игнорируют.

`Enter` сохраняет введённый запрос, `Esc` отбрасывает его. Палитра:
*Задачи: изменить запрос / списки...*.

Из CLI: `gitpoulpi hosting link pulls --id <profile>` (или `issues`),
`--clear` для отвязки, `--filter` для дополнительного запроса. См.
[справочник по CLI](cli-reference.md#команды).

### Клонирование из подключённой учётной записи

Подключённый профиль (GitHub, GitLab, Gitea, Forgejo, Azure DevOps, Bitbucket, Gerrit) также служит источником в диалоге **Клонировать** (вкладка «Главная», кнопка **Клонировать**, или `c` на вкладке управления репозиториями). Каждый профиль перечислен под **Клонировать по URL** как отдельный источник (`GitHub · name`, `GitLab · name`); GitHub и GitLab никогда не смешиваются. Выберите один, и загрузятся его репозитории, сгруппированные по владельцу: сначала ваша учётная запись, затем по одной секции на организацию или группу (`quarry/tools` для подгруппы GitLab), каждая под заголовком с числом. Замок отмечает приватный репозиторий.

![Диалог клонирования на подключённой учётной записи GitHub: одна секция на владельца и замок у приватного репозитория](../images/clone-hosted.png)

Поле поиска фильтрует сразу по всем секциям (имя, полный путь и описание); секция без совпадений исчезает. `Enter` на строке заполняет клон HTTPS-адресом этого репозитория и именем папки.

![Диалог клонирования: поиск сужает список до одной организации](../images/clone-hosted-search.png)

Список профиля, который вы уже открывали, показывается сразу из сохранённой копии,
пока хост опрашивается заново (*обновление...* рядом с названием поля); когда ответ приходит,
новые репозитории появляются, а исчезнувшие пропадают, при этом выделенный и выбранный
репозиторий остаются на месте. Если обновление не удалось, сохранённый список остаётся с
пометкой, а причина указана в «Журнале активности».

Если хост отклоняет токен, вместо списка диалог показывает *не удалось получить список репозиториев* с причиной (а сохранённая копия удаляется); остальные источники продолжают работать.

## 5. Ключи SSH

### Ключ SSH для профиля

У подключённого профиля под карточкой есть раздел **Ключ SSH**. Если ключа нет,
выберите одно из:

- **Ключ по умолчанию**: ваш ssh-agent или `~/.ssh`. Ничего не меняется.
- **Создать новый ключ**: необязательное название (по умолчанию
  `GitPoulpi <хост> <дата>`). Если отмечено **Добавить открытый ключ на <хост>**,
  GitPoulpi загружает его, если на хосте его ещё нет. Ключ записывается без
  парольной фразы в `~/.ssh/gitpoulpi_<profile id>_ed25519` и `.pub`.
  `ssh-keygen` не нужен. Существующий файл никогда не перезаписывается.
- **Свой ключ**: введите путь или нажмите **Обзор**, чтобы выбрать файл закрытого
  ключа, затем нажмите **Использовать этот ключ**.

Когда ключ привязан, раздел показывает `название (SHA256:...)` и кнопки:

- **Убрать**: отвязать ключ и удалить его на хосте, если его добавил GitPoulpi.
- **Удалить**: то же, плюс удаление файлов ключа после подтверждения, в котором
  перечислены оба пути.

### Ключ SSH для одного репозитория

Чтобы репозиторий использовал определённый ключ, откройте меню вкладки (`Ctrl+T`
или правый щелчок по вкладке) и выберите **SSH и учётные данные...** либо
выполните команду палитры *Репозиторий: SSH и учётные данные...* и выберите в
разделе SSH **Файл ключа** (или **Ключ учётной записи** для ключа профиля
интеграции). Выбор хранится в закрытой папке GitPoulpi: ничего не записывается
ни в репозиторий, ни в конфигурацию git. См.
[Настройки](settings.md#настройки-репозитория-ssh-и-учётные-данные).

Если у репозитория ещё есть собственный `core.sshCommand` от прежнего
закрепления «Ключ SSH для этого репозитория», он показан на этой странице только
для чтения, рядом с кнопкой **Перенести в GitPoulpi**.

CLI и MCP: `gitpoulpi repo-auth` (выбор для репозитория) и, для самого
закрепления `core.sshCommand`, `gitpoulpi ssh-command show | set --key <file> |
clear`.

Глобальный ключ из **Настройки > SSH и учётные данные** (*Путь к закрытому ключу*
или *Создать пару ключей*) действует для каждого репозитория без собственного
выбора. Файл ключа или закрепление репозитория главнее.

## 6. Защита веток при переписывании истории

Когда вы переписываете историю ([окно переписывания](history-rewrite.md)), GitPoulpi спрашивает
хостинг, какие ветки он защищает, чтобы по умолчанию не включать их в переписывание. Он спрашивает
только о репозитории, который вы **привязали** (раздел запросов на слияние или задач на боковой панели либо
закреплённый профиль), с токеном этого профиля, а токен, который не может это прочитать, просто даёт
«неизвестно»: ничего не ломается. Что отвечает каждый провайдер и что нужно токену:

| Хостинг | Что читается | Что нужно токену |
|---|---|---|
| GitHub (и Enterprise Server) | флаг `protected` у веток и действующие rulesets веток (шаблоны `~DEFAULT_BRANCH`, `~ALL` и `refs/heads/...`) | классический токен с `repo` (`public_repo` для публичного репозитория) или токен с точными правами и Metadata (read). Ruleset, который токен не может прочитать, отмечается, а классические правила учитываются |
| GitLab (gitlab.com и self-managed) | `protected_branches` (имена и шаблоны с `*`) | `read_api` и роль, которой видны настройки репозитория |
| Azure DevOps (Services и Server) | включённые блокирующие политики веток репозитория (области `Exact`, `Prefix` и `DefaultBranch`) | Code (read). Право «force push» - это параметр безопасности, оно не читается |
| Bitbucket Cloud | ограничения веток, останавливающие push (`push`, `force`, `delete`) | `repository:admin`. Ограничение по модели ветвления не разрешается |
| Bitbucket Data Center | права веток, останавливающие force push (`fast-forward-only`, `pull-request-only`, `read-only`) | администратор репозитория |

Страница настроек защиты (а также ветки по умолчанию и удаления репозитория) строится из URL remote
репозитория для GitHub, GitLab, Azure DevOps и Bitbucket, даже если репозиторий не привязан, и показывается
вместе с тремя выходами, когда хостинг отклоняет push.

## 7. Списки по всему аккаунту в Radar

Обычно Radar следит за клонированными вами репозиториями. Профиль может также
перечислять всё, что вас касается на всём хостинге, клонированное и нет, тремя переключателями
в своей таблице `[integrations.radar]` (все выключены по умолчанию; см.
[справочник конфигурации](config-reference.md#integrationsradar-списки-по-всему-аккаунту)):

- **запросы на ревью**: открытые запросы, где просят вашего ревью;
- **открытые запросы**: все открытые запросы вашего собственного пространства имён и каждой организации или
  группы, где вы состоите, либо указанных вами пространств имён. Никогда не весь хостинг;
  **Пространства имён** профиля (по одному в строке в Настройки > Интеграции > Radar, при желании как регулярные выражения)
  ограничивают все три списка: строка соответствует полному пути репозитория, если равна ему или является префиксом
  пути, оканчивающимся на `/` (`ptm` оставляет `ptm/produits/x`, но не `ptmx/y`); применяется к строкам, которые
  возвращает хостинг, а также на стороне сервера, где поиск хостинга это позволяет (квалификаторы GitHub `user:` / `repo:`);
- **назначенные задачи**: открытые задачи, назначенные вам.

Отвечают GitHub, GitLab (включая самостоятельно размещаемый), Gitea, Forgejo, Azure DevOps (Services
и Server), Bitbucket Data Center и Gerrit. Как спрашивается каждый:

| Хостинг | Запросы | Задачи |
|---|---|---|
| Azure DevOps | активные pull request'ы всей организации (`searchCriteria.reviewerId` для ждущих вас; запрос, за который вы уже проголосовали, исключается); если сервер отклоняет маршрут уровня организации, первые 20 проектов опрашиваются по одному. `namespaces` - имена проектов | рабочие элементы, назначенные вам, не в состоянии Done, Closed или Removed |
| Bitbucket Data Center | ваша панель: роль `REVIEWER` без одобрения для запросов на ревью, `AUTHOR` и `PARTICIPANT` для открытых запросов; `namespaces` - ключи проектов | нет (в Data Center нет трекера задач; заметка об этом) |
| Gerrit | `is:open reviewer:self -owner:self -is:ignored`; открытые запросы - `is:open projects:<prefix>` для каждого пространства имён (префикс пути проекта) или ваши собственные и просмотренные изменения, если ничего не указано; изменение work-in-progress считается черновиком | нет |

У Bitbucket Cloud строк уровня аккаунта нет: у него нет конечной точки, перечисляющей
запросы по репозиториям, а опрос каждого репозитория потребовал бы слишком много
вызовов. Клонированные репозитории сохраняют свои списки, а `gitpoulpi hosting
radar --id <bitbucket>` говорит об этом. Если изменений в Gerrit больше, чем он
отдаёт за раз, список помечается как обрезанный с заметкой.

Черновики не включаются, пока вы их не оставите. Каждый список ограничен: 300 строк каждого вида, с
заметкой о том, сколько их было ещё, а в GitHub - несколько вызовов поиска за
раунд, потому что его API поиска допускает только 30 в минуту. Пространство имён, которое токен
прочитать не может, становится заметкой, а остальные всё равно загружаются; отклонённый токен или
лимит запросов приводит к ошибке только этого профиля. Ответы используются повторно пять минут
(`radar-account.json` в папке конфигурации).

В Настройки > Интеграции у подключённого профиля хостинга кода есть блок **Radar**
под его ключом SSH: по флажку на каждый список (*Запросы, ждущие моего ревью*,
*Все открытые запросы*, *Включать черновики*, *Задачи, назначенные мне*, последний
отсутствует у хостингов без задач), поле *Пространства имён* (по одной записи в строке: имя, соответствующее этой
группе или владельцу и всему, что ниже, либо регулярное выражение в каждой строке
при включённом *Регулярные выражения*; пусто - ваше собственное и все, где вы
состоите) и выбор *Запрос из репозитория, который не клонирован*:
*Спрашивать*, *Клонировать* или *Ревью через API*.
Всё сохраняется сразу при изменении. Хостинги без запроса уровня аккаунта (Bitbucket
Cloud) показывают вместо этого одну строку с пояснением. К блоку ведёт команда палитры
*Настройки: параметры Radar для профиля...*, а поиск по настройкам находит каждый
элемент по его подписи.

Из командной строки: `gitpoulpi hosting integrations radar <id> --review-requests on`
включает список, `gitpoulpi hosting radar --json` выводит списки (а
`--refresh` обходит кэш). У ИИ-агентов те же две команды через MCP
(`hosting_radar`, `hosting_integrations_radar`).

## 8. Работа от имени бота GitHub App

Проект, который не должен показывать имя человека, может делать всё на хостинге через **GitHub App**: каждый
комментарий, ревью, закрытие или повторное открытие и смена меток тогда выглядят как `<app-slug>[bot]`. Это
работает для одного репозитория за раз, а остальные ваши репозитории остаются на вашем токене.

1. Создайте GitHub App для организации с правами **Issues** и **Pull requests** *Read & write* (и *Contents: read*,
   чтобы pull request'ы можно было перечислять и проверять) и установите его в репозиторий.
2. Напишите небольшой скрипт, который выводит **токен установки** на стандартный вывод (закрытый ключ App подписывает
   короткоживущий JWT, который обменивается на токен, действующий один час). GitPoulpi ключ никогда не видит.
3. В **Настройки > Настройки репозитория > SSH и учётные данные** выберите под HTTPS **Команда токена**, введите
   скрипт как **Команду** и хостинг (`github.com`) в **Хосты** и отметьте **Использовать для API хостинга (задачи,
   pull requests)**. Сохраните и подтвердите команду (человек всегда подтверждает её, с её SHA-256). Из командной
   строки: `gitpoulpi repo-auth set --https token-command --hosts github.com --use-for-hosting --yes --command ./app-token.sh`.

Что меняется для этого репозитория:

- Его вызовы задач и pull request'ов (список, создание, комментирование, ревью, merge, закрытие, метки) используют
  токен команды, с тем же 30-секундным пределом, кэшем в памяти и вычищением, что и собственный вход git. Если
  хостинг отвечает 401, потому что токен истёк, команда запрашивается ещё один раз. Если команда не может
  выполниться, вызов отклоняется: личный токен никогда не служит запасным вариантом.
- «Меня» нет: токен установки не может спросить, кто он. Заголовок раздела называет профиль с **(бот App)**, а
  фильтры, построенные на «мне» (*Назначенные мне*, *Мои*, *Ждут моего ревью*), нечему сопоставлять. Ничего не
  показывается как ошибка.
- **Публиковать как.** Каждое сообщение, которое публикует GitPoulpi, показывается с именем, от которого оно
  публикуется (*Публикация как my-app[bot] (бот GitHub App)* под заголовком [беседы](conversations.md#публикация-от-имени) и в её поле
  комментария; `posted_as` в ответе CLI). С личным токеном это ваш логин (`GET /user`). С токеном App это имя
  **Публиковать как**, например `my-app[bot]`: задайте его для всех репозиториев в **Настройки > Интеграции**
  (`general.hosting_post_as`, также `gitpoulpi config set general.hosting_post_as my-app[bot]`) или для одного
  репозитория в **Настройки > Настройки репозитория > SSH и учётные данные > Хостинг**, где оно имеет приоритет. Если
  оно пусто, GitPoulpi спрашивает GitHub (GraphQL `viewer { login }`), а иначе узнаёт имя по автору первого
  опубликованного им комментария и хранит его вместе с репозиторием. По этому имени опознаются и ваши комментарии,
  поэтому изменение и удаление предлагаются только для них (комментарии App должны ещё и принадлежать учётной записи
  бота); пока оно неизвестно, можно менять только комментарии, опубликованные этой установкой.
- App нельзя назначить. Сочетайте эту настройку с блокировкой назначения ниже.
- Включение и выключение **Использовать для API хостинга** требует человека, как и новая команда.

Так токен репозитория используют только профили GitHub; остальные хостинги сохраняют собственный токен профиля.
(Токен доступа проекта или группы GitLab - тоже бот: это токен профиля, он показывается как *бот проекта*, и ничего
настраивать не нужно.)

### Блокировка назначения в репозитории

В **Настройки > Настройки репозитория > SSH и учётные данные** есть строка **Назначение** (**Разрешено** по
умолчанию или **Заблокировано**; сохраняется сразу). При блокировке назначение в задачах и pull request'ах этого
репозитория невозможно, кто бы ни просил:

- выбор исполнителей убирается из форм новой задачи и нового pull request'а (с пояснением почему), команда палитры
  *Хостинг: изменить исполнителей...* неактивна с указанием причины, а меню строки сообщает об этом вместо открытия;
- каждый клиент отклоняет назначение до отправки чего-либо, включая исполнителей, переданных при создании задачи
  или pull request'а: CLI отвечает `{"refused": {"reason": "assignment_blocked", ...}}` с кодом выхода 2, а агент по
  MCP получает тот же отказ;
- уже назначенные исполнители остаются видны (только чтение).

`gitpoulpi hosting assignment` показывает настройку, `--block` включает блокировку, а `--allow` снова выключает её;
снова разрешить может только человек (сервер MCP не может).

## 9. Из командной строки

```
echo $TOKEN | gitpoulpi hosting login --id my-gitlab --token-stdin
gitpoulpi hosting integrations list --json
gitpoulpi hosting prs --mine --json
gitpoulpi hosting edit-url --branch my-branch --open
gitpoulpi hosting open pr 12 --browser
gitpoulpi hosting pr-edit 12 --add-reviewer ann --add-label bug --milestone v1.0
gitpoulpi hosting radar --what review --json
gitpoulpi hosting assignment --block
```

Все команды см. в [справочнике по CLI](cli-reference.md#команды). Токен никогда
не принимается аргументом, а сервер MCP не предлагает `hosting login`, поэтому
токен никогда не проходит через агента. `hosting login` печатает `stored: "os"`, если токен хранит
системное хранилище учётных данных, либо `stored: "session"` и `store_error`, если
хранилище отказало и токен живёт в памяти только на время этого сеанса.

## Устранение неполадок

| Симптом | Что делать |
|---|---|
| *Подключить* завершается ошибкой аутентификации | Токен неверный, просрочен или отозван. Создайте новый. |
| Право перечислено красным | У токена его нет. Подключение работает, но эта функция - нет. Добавьте право на хосте, затем нажмите **Изменить** и вставьте новый токен. |
| На боковой панели нет раздела PULL REQUESTS | Нет подключённого включённого профиля. Подключите профиль, затем свяжите репозиторий в выпадающем списке раздела. |
| Строка *Подключить заново* в списке | Токен потерян (перезапуск без credential helper) или просрочен. Щёлкните по строке, чтобы открыть профиль. |
| Не работает self-managed экземпляр | Проверьте, что в **Домене хоста** нет пути и что ваш компьютер доверяет сертификату экземпляра. |

## Известные ограничения

- **Pull request из форков:** Azure DevOps и Bitbucket не умеют делать checkout
  запроса из форка (см. [Действия над строкой](pull-requests-and-issues.md#действия-над-строкой)). Azure
  DevOps не умеет создавать pull request из форка.
- **Trello** показывает не больше первых 1000 карточек доски. Сузьте выбор
  фильтром списков. **Jira**, **Linear** и **YouTrack** перечисляют не больше 500
  задач за одно обновление. Сузьте выбор фрагментом JQL или запросом YouTrack.
- **Linear** принимает одного исполнителя на задачу: если в выборщике выбрать
  нескольких, отправляется первый. Его «этап» - это **цикл** команды (этапы
  проектов не используются). У **YouTrack** это поле `Fix versions`; у версии
  нет номера, поэтому выборщик нумерует невыпущенные по их положению в проекте.
  Pull request нет ни в одном из этих трекеров.
- **Redmine** принимает одного исполнителя на задачу (первого из выборщика),
  меток в нём нет, и он перечисляет не больше 500 задач за одно обновление.
  Исполнители - участники проекта (люди и группы), они различаются отображаемым
  именем. Колонки канбан-доски - статусы задач, а перенос карточки меняет статус;
  действуют правила рабочего процесса Redmine по умолчанию (роль, которой такой
  переход не разрешён, получает отказ, и карточка возвращается). «Resolved» в
  данных Redmine по умолчанию не закрытый статус: колонка «Закрытые» - это
  статусы «Closed» и «Rejected».
- У **Bitbucket Data Center** нет ссылок для браузера на новые pull request,
  ветки и commit'ы. Страницы pull request открываются как обычно.
- **Azure DevOps** не показывает аватары авторов. Фильтры «мои» и «ждут моей
  проверки» требуют конечной точки, которая может отказать персональным токенам
  доступа. В этом случае профиль подключается без имени пользователя, и эти два
  фильтра недоступны. Недействительный токен получает страницу входа вместо
  ошибки; GitPoulpi сообщает об этом как об отклонённом токене.
- **Gitea и Forgejo:** черновик - это запрос, заголовок которого начинается с
  `WIP:` (при создании у сервера нет флага черновика). В рецензентах запроса
  числится каждый, кто уже сделал ревью, а отзыв запроса на ревью убирает только
  ожидающие. Pull request из локальной ветки форка проверяются через
  `refs/pull/<n>/head`, как в GitHub. Упоминания ищутся фильтром сервера
  `mentioned_by`. Сервер не показывает права токена, поэтому недостающее
  обнаруживается только когда вызов отклонён.
- **Доска задач** переносит карточки в любом источнике задач. В Jira перенос выполняет переход рабочего процесса,
  ведущий в колонку; переход, который запрашивает поля (например, резолюцию), Jira отклоняет, и карточка
  возвращается с её сообщением. В Azure DevOps рабочий элемент, у типа которого нет целевого состояния, возвращается
  с причиной.
- **Bitbucket:** паролей приложений больше нет; используйте токен API.
  Репозитории перечисляются по рабочим пространствам.
- **Jira Cloud:** работают только классические токены API (ни scoped-токенов, ни
  OAuth). Новая задача Jira получает описание простым текстом.
- **Беседы:** сначала загружаются 300 самых новых записей (остальное - **Загрузить старые**); комментарий, правка или
  удаление, опубликованные из GitPoulpi, - внешнее действие и отсюда не отменяются; чего не может каждый хостинг,
  описано в [таблице](conversations.md#чего-не-может-каждый-хостинг). В Gerrit сообщение или комментарий нельзя изменить или
  удалить, а текст Gerrit - простой.
- Создание pull request, рабочего элемента, задачи или карточки происходит на
  хосте и **не может быть отменено** из GitPoulpi. Checkout запроса отменяется
  как обычно.
