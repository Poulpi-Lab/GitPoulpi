# Git LFS

Git LFS («Large File Storage») хранит большие файлы (файлы дизайна, видео, наборы данных) вне истории репозитория: вместо них git хранит небольшой текстовый *указатель* из трёх строк, а настоящее содержимое лежит на сервере LFS и в локальном кэше в `.git/lfs`.

Для всего этого GitPoulpi не нужна учётная запись. LFS использует учётные данные, которые уже использует ваш remote (ваш credential helper git или ssh-agent).

## Что требует программу `git-lfs`, а что нет

GitPoulpi запускает стандартную программу `git-lfs` для всего, что преобразует или перемещает файлы (install, track, fetch, pull, push, блокировки).

Чтение *состояния* LFS программы не требует: использует ли репозиторий LFS, какие файлы являются указателями, их размер и хранится ли настоящий объект уже локально.

| | требует `git-lfs` |
|---|---|
| `gitpoulpi lfs status` (сообщает, что программы нет, вместо ошибки) | нет |
| `gitpoulpi lfs files` | нет |
| install / track / untrack / prune | да |
| fetch / pull / push | да |
| блокировки | да |

## Установка `git-lfs`

- **Windows**: входит в Git for Windows; либо `winget install GitHub.GitLFS`.
- **Debian / Ubuntu**: `apt install git-lfs`.
- **macOS**: `brew install git-lfs`.
- Остальное: https://git-lfs.com

Требуется версия 3.0 или новее. После установки GitPoulpi заметит её в течение минуты (или сразу по `lfs status`).

## Если `git-lfs` отсутствует

GitPoulpi из-за этого никогда не падает и не завершается:

- `gitpoulpi lfs status` выполняется успешно и сообщает `git-lfs: not installed` (сообщение CLI остаётся английским) со ссылкой на установку.
- Операция, которой нужна программа, завершается с понятным сообщением, оканчивающимся ссылкой на установку (`https://git-lfs.com`), и ненулевым кодом возврата; через MCP инструмент возвращает это сообщение.
- Репозиторий, использующий LFS, всё равно открывается; его большие файлы просто отображаются как указатели, пока программа не установлена.

## Просмотр файлов LFS

```
gitpoulpi lfs status            # программа, шаблоны, фильтры, хук
gitpoulpi lfs files             # файлы-указатели в индексе, с размером и пометкой local/not downloaded
gitpoulpi lfs files --at v1.0   # ... по состоянию на ревизию
gitpoulpi show big.bin --at HEAD  # сообщает "Git LFS object, 12.3 MB, sha256:..." вместо текста указателя
```

## Настройка репозитория: install, track, untrack

```
gitpoulpi lfs install                 # фильтры и хуки для ЭТОГО репозитория (git lfs install --local)
gitpoulpi lfs install --user          # вместо этого в глобальную конфигурацию git (никогда не молча)
gitpoulpi lfs track '*.psd'           # отправлять *.psd через LFS
gitpoulpi lfs track '*.psd' --lockable   # ... и сделать их доступными только для чтения до блокировки
gitpoulpi lfs track '*.bin' --renormalize  # ... и заново добавить в индекс уже попавшие в commit *.bin как указатели
gitpoulpi lfs untrack '*.psd'
gitpoulpi lfs prune                   # удалить старые, уже отправленные объекты из локального хранилища
```

- По умолчанию `install` пишет в собственные `.git/config` и хуки репозитория, поэтому ваша глобальная конфигурация git не затрагивается, пока вы не передадите `--user`.
- `track` и `untrack` правят `.gitattributes` и оставляют его **вне индекса**: он отображается как обычное изменение рабочего дерева, которое вы сами добавляете в commit. Файлы, добавленные *после* начала отслеживания, сохраняются как указатели со следующим commit'ом.
- Файлы, **уже попавшие в commit** как обычное содержимое, остаются обычными в истории. `--renormalize` повторно добавляет их в индекс, чтобы следующий commit заменил их указателями. Чтобы перенести их и во все прошлые commit'ы, используйте правило переписывания истории *Перенести файлы в LFS* (см. [Переписывание истории](history-rewrite.md#перенос-файлов-в-git-lfs-и-из-него)); оно собственное, а не `git lfs migrate`.
- Берите шаблон в кавычки, чтобы оболочка его не раскрывала.
- Через MCP это обычные изменяющие операции (`lfs_install`, `lfs_track`, `lfs_untrack`, `lfs_prune`), подчиняющиеся ограничениям `[mcp]` в `config.toml`.

## Передача объектов: fetch, pull, push

```
gitpoulpi lfs fetch [--remote origin] [--all]   # загрузить объекты в локальное хранилище; рабочее дерево не меняется
gitpoulpi lfs pull  [--remote origin]           # fetch, затем заменить файлы-указатели настоящим содержимым
gitpoulpi lfs push  [--remote origin] [--all]   # отправить объекты текущей ветки (или всех ссылок с --all)
```

- Remote по умолчанию - основной remote репозитория, как у `fetch` и `push`.
- Учётные данные - обычные для вашего remote (credential helper, ssh-agent). GitPoulpi никогда не требует собственную учётную запись.
- `pull` устанавливает фильтры LFS для этого репозитория, если их нет: без них git-lfs загружает объекты, но не заменяет указатели, и последующий checkout вернул бы указатели.
- MCP рассматривает `lfs push` как `push`: деструктивный инструмент (он меняет remote).
- Окно показывает ход передачи (файлы и байты) в строке состояния. CLI дожидается результата.

### Запись содержимого: `lfs checkout`

```
gitpoulpi lfs checkout [<path>...]   # без сети: записать настоящее содержимое поверх файлов-указателей из локального хранилища
```

Он ничего не загружает (это делает `lfs pull`); объекты, которых нет в локальном хранилище, остаются указателями. Как и `pull`, он сначала устанавливает фильтры LFS репозитория, если ни один не настроен. Как и любую операцию LFS, его нельзя отменить; см. [Отмена и повтор](undo-redo.md). Через MCP это `lfs_checkout` (запись, не деструктивная).

### Кнопка LFS на панели инструментов, а также pull / push

На панели инструментов после **Pop** есть кнопка **`LFS ▾`** (скрыта, если `git.lfs_enabled` выключен, а также в репозитории, где LFS не инициализирован и не используется в его `.gitattributes`: см. [Настройки > LFS](settings.md#настройки-репозитория-lfs)). Щелчок открывает выпадающее меню: **Fetch всех файлов LFS** (`lfs fetch --all`), **Checkout всех файлов LFS** (`lfs checkout`), **Pull всех файлов LFS** (`lfs pull`), **Push всех файлов LFS** (`lfs push --all`, объекты всех ссылок) и **Очистить локальное хранилище LFS** (`lfs prune`). Каждая строка есть и команда палитры (`LFS: fetch всех объектов`, `LFS: checkout всех файлов`, `LFS: pull объектов`, `LFS: push всех объектов`, `LFS: очистить локальные объекты`). `LFS: открыть меню` открывает выпадающее меню. У каждой есть сочетание с `Ctrl+G`: `l` для меню, затем `Shift+F`, `Shift+K`, `Shift+L`, `Shift+J` и `Shift+V` для строк. Изменить их можно в **Настройки > Клавиатура и мышь**. Если `git-lfs` отсутствует, каждая строка ведёт к диалогу установки.

![Выпадающее меню LFS на панели инструментов: fetch, checkout, pull и push всех файлов LFS и очистка локального хранилища](../images/lfs-menu.png)

**Pull и push сами обрабатывают LFS.** В репозитории, использующем LFS, при установленном `git-lfs` обычный `pull` сначала проверяет, что фильтры LFS репозитория установлены, а обычный `push` проверяет его хук `pre-push`. Если чего-то не хватает, GitPoulpi перед передачей запускает `git lfs install --local` (только для этого репозитория), а строка состояния показывает «фильтры LFS установлены». Без хука push не отправил бы объекты LFS. Отключается через `git.lfs_autofix_filters = false` (**Настройки > Git и кодировка > Устанавливать фильтры LFS перед pull и push**). Обычный `push` по-прежнему отправляет только объекты отправляемой ветки, а не всех ссылок; очистка никогда не выполняется неявно.

## Блокировки файлов

Некоторые файлы нельзя слить (файл Photoshop, уровень игры, двоичный ресурс). *Блокировки* Git LFS позволяют одному человеку сказать «я это редактирую»: никто другой не может заблокировать файл или отправить в него изменения, пока он не разблокирован.

```
gitpoulpi lfs locks  [--remote origin]              # кто держит какой файл (ваши отмечены)
gitpoulpi lfs lock   assets/hero.psd [--remote origin]
gitpoulpi lfs unlock assets/hero.psd [--remote origin] [--force]
```

- Блокировка - функция **сервера LFS** (она есть у GitHub, GitLab и Gitea). Обращение идёт с собственными учётными данными remote; у GitPoulpi нет своей учётной записи.
- Если сервер не поддерживает блокировку, `lock` завершается с сообщением об этом (типизированная ошибка `LfsLockingUnsupported`). `locks` на таком сервере ничего не перечисляет - это же сообщает и сам git-lfs.
- Отслеживание шаблона с `--lockable` (`lfs track '*.psd' --lockable`) делает эти файлы доступными только для чтения, пока вы их не заблокируете.
- `unlock` чужой блокировки отклоняется; `--force` её снимает, поэтому MCP считает `lfs_unlock` деструктивным инструментом. `lfs_locks` - только чтение.

## Клонирование репозитория LFS

`gitpoulpi clone <url>` (и диалог «Клонировать репозиторий» в TUI) извлекает репозиторий *без* запуска фильтров LFS, затем, если репозиторий использует LFS и `git-lfs` установлен, загружает объекты командой `git lfs pull` (устанавливая фильтры для этого репозитория, если ни один не настроен) и показывает это отдельным этапом, «Загрузка объектов LFS». `--no-lfs` пропускает этот шаг и оставляет указатели.

Клонирование **никогда не завершается ошибкой из-за LFS**: если `git-lfs` отсутствует или загрузка не удалась, клонирование всё равно проходит успешно, а большие файлы остаются указателями; состояние LFS репозитория объясняет причину, а `gitpoulpi lfs pull` завершит работу, когда проблема будет устранена.

## В терминальном интерфейсе

- **Значок `LFS`.** У файла, хранящегося через Git LFS, после имени в списках «Файлы unstaged» и «Файлы staged» панели Status и в списке изменённых файлов commit'а стоит небольшой значок `LFS`. **Только LFS** (`o` при фокусе на панели Status или на Log, флажок на панели инструментов списков файлов или **Файлы: только LFS** в палитре) сужает эти списки до файлов LFS. Он показывается, только если в репозитории такие файлы есть. Файл считается файлом LFS, когда его путь в индексе - указатель: это то же чтение, что даёт значок (один пакетный вызов `git` на обновление, ничего для репозитория без атрибутов `filter=lfs`).
- **Карточка diff.** Открытие diff файла LFS показывает карточку вместо текста указателя: `Объект Git LFS`, `1.2 MB -> 1.4 MB`, короткие старый и новый oid и информацию о том, хранится ли новый объект локально или `не загружен`. Нажмите `r`, чтобы увидеть diff самого указателя, и ещё раз `r` для возврата. К файлу LFS применимо только добавление в индекс на уровне файла (hunk и строк для добавления нет). Под карточкой **Открыть в программе по умолчанию** и **Открыть в** (`o`, `Shift+O` или палитра) открывают настоящий файл, а не указатель: см. [Открыть в](open-in.md#файлы-git-lfs).
- **Просмотр файла** для файла LFS показывает `объект Git LFS, 12.3 MB, sha256:ab12cd34...` и подсказывает, где взять содержимое.
- **Баннер.** Если репозиторий использует LFS, а `git-lfs` отсутствует или старше 3.0, об этом сообщает баннер в панели Status. Щёлкните по нему (или используйте команду палитры *LFS: открыть страницу установки*), чтобы открыть https://git-lfs.com. Больше ничего не меняется: окно открывается, diff работают, большие файлы просто отображаются как указатели.
- **Меню файла и палитра.** Щёлкните правой кнопкой по изменённому файлу в панели Status: *Отслеживать через LFS: этот файл* / *Отслеживать через LFS: это расширение* для обычного файла; *Заблокировать файл (LFS)*, *Разблокировать файл (LFS)* или *Принудительно разблокировать (LFS, чужая блокировка)* для файла LFS, в зависимости от того, кто держит блокировку. В строке заблокированного файла показано `заблокировал you` / `заблокировал <имя>`. Всё это есть и командами палитры (`Ctrl+P`, введите `LFS`): инициализировать, отслеживать или прекратить отслеживание шаблона, fetch, pull или push объектов, очистить, показать блокировки, открыть страницу установки.
- **Сбой действия объясняется.** Если действие LFS не удалось, потому что `git-lfs` отсутствует, диалог содержит сообщение и кнопку *Открыть страницу установки*.
- **Настройки.** В *Настройки > LFS* (для репозитория) видно, инициализирован ли LFS, перечислены отслеживаемые шаблоны и есть кнопка **Настроить LFS здесь**. В **Git и кодировка** (для репозитория) есть переключатель **Git LFS**, строка **Программа git-lfs** только для чтения и кнопка **Инициализировать LFS для этого репозитория**.
- Выключенный **Git LFS** (`git.lfs_enabled = false`, см. [справочник по конфигурации](config-reference.md)) скрывает всё перечисленное. Собственные фильтры LFS в git продолжают работать.
- Состояние LFS считывается вскоре после открытия репозитория, после каждого изменения, при ручном обновлении, при изменении `.gitattributes` и каждые десять секунд для репозитория, использующего LFS.

## Известные ограничения

- Репозиторий, шаблоны LFS которого лежат только во *вложенном* `.gitattributes` (не в корневом и не в `.git/info/attributes`), определяется как использующий LFS лишь после появления хранилища объектов LFS (`.git/lfs`), но не раньше.
- Сам `git lfs migrate` не используется. Перенос файлов в LFS и из LFS по всей истории - это правила переписывания истории *Перенести файлы в LFS* / *Вернуть файлы из LFS*: они работают с локальным клоном, записывается только корневой `.gitattributes`, а объекты после этого всё равно нужно отправить (*Отправить объекты LFS* в панели результата или `lfs push --all`).
