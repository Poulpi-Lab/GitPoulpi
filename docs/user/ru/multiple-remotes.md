# Несколько remote для одной ветки

Многие репозитории живут больше чем на одном хосте: основной (`origin`), зеркало на другом хосте, резервная копия. GitPoulpi позволяет ветке делать push во все из них одним щелчком и, по желанию, подтягивать изменения больше чем с одного remote, не меняя того, что делает обычный git. Аккаунт для этого не нужен, а всё хранится в собственном `.git/config` репозитория, так что обычный git и другие инструменты продолжают работать.

## Цели push и источники pull

- **Upstream** - это собственное понятие git (`branch.<name>.remote` и `merge`). Это *основной* remote ветки. GitPoulpi никогда не меняет его работу.
- **Цель push** - дополнительный remote, на который ветка тоже делает push. Кнопка Push отправляет ветку в upstream и в каждую цель push.
- **Источник pull** - дополнительный remote, с которого pull тоже забирает commit'ы. По умолчанию выключен, пока вы не включите его (флажок **и Pull**): слияние двух remote, которые вы не выбирали, - не то, чего кто-либо хочет по умолчанию.

У цели может быть другое имя ветки на этом remote (`backup` получает `feat-x`).

## Диалог Remote

Щёлкните ветку правой кнопкой и выберите **Remote ветки <branch>...** (он есть и в выпадающем списке Push, в палитре как `Git: Remote ветки...`, и по щелчку на значке `⇉3` в строке ветки в разделе Refs). Диалог перечисляет каждый remote репозитория:

| Столбец | Значение |
|---|---|
| Remote, Ветка | Remote и имя ветки на нём. **Переименовать на remote...** меняет это имя для выбранной строки. |
| Push | Отметьте, чтобы сделать remote целью push этой ветки. |
| и Pull | Отметьте, чтобы pull тоже интегрировал этот remote. Upstream подтягивается всегда. |
| Состояние | Как ветка соотносится с ним: синхронно, впереди, позади, новая, несвязана. |

Строка «remote удалён» называет remote, который ветка всё ещё упоминает, но которого в репозитории больше нет; **Убрать** забывает его. Тот же диалог задаёт upstream (список **Upstream**), а **Сбросить upstream** сбрасывает его. **Применить** записывает всё как одно отменяемое изменение.

Репозиторий может также давать каждой новой ветке одни и те же дополнительные цели: **Настройки > Git и кодировка** (страница репозитория), «Дополнительные цели push для новых веток» (флажок на каждый remote). Они копируются в ветку, когда она впервые получает upstream; существующие ветки не затрагиваются.

## Push

- **Кнопка Push** на ветке с дополнительными целями: делает push во все. Когда каждый remote просто принимает новые commit'ы, выполнение идёт сразу, а окно хода работы показывает, как каждый remote получает галочку. Если нужно решение (на remote есть commit'ы, которых нет у вас), вместо этого открывается диалог плана.
- **Push ▾** (стрелка рядом с кнопкой; а также сама кнопка, когда **Кнопка «Push»** в настройках установлена в **спрашивать**):
  - `Push во все (origin, gitlab, backup)`
  - `Push только в <remote>`, по одному на каждый remote ветки
  - `Push в выбранные remote...`: есть всегда, для любой ветки, даже с единственным remote
  - `Remote ветки <branch>...`
- Контекстное меню ветки и палитра (`Git: Push во все цели`, `Git: push на remote...`, `Git: Push в выбранные remote...`) предлагают те же действия с теми же названиями.

**Push в выбранные remote...** открывает список всех remote репозитория, отмеченных по upstream и целям ветки. Выбор действует только для этого push; отметьте **Запомнить для этой ветки**, чтобы сохранить его как цели push ветки.

### План

Перед групповым push GitPoulpi смотрит на каждый remote (быстрый запрос и загрузка с этого remote, только если он отличается), так что проблема на третьем remote видна до начала первого push. Диалог перечисляет каждый remote с тем, как ветка соотносится с ним и что будет сделано:

| Ситуация | Действие по умолчанию | Также предлагается |
|---|---|---|
| На remote нет ветки или не хватает части commit'ов | Push | Пропустить |
| Remote впереди (нового для него у вас нет) | Fast-forward из него | Пропустить |
| Remote отличается, потому что вы сделали rebase или amend уже отправленного | Force push (lease) | Merge, Rebase, Пропустить |
| На remote есть чужие commit'ы | Merge из него (Rebase, если **Кнопка «Pull»** установлена в rebase) | Rebase, Force push (lease), Пропустить |
| История ничего не разделяет с вашей | Пропустить | Force push (lease) |
| Хост отклонил ветку (защищённая) | Пропустить | нет: force тоже был бы отклонён |

Действие каждой строки - это список, который можно менять (Left/Right перебирают его, Enter открывает, `s` пропускает строку). Merge показывает, будет ли конфликт и в каких файлах. **Force push** всегда подтверждается, называет remote и число заменяемых commit'ов, всегда использует lease (никогда не голый force) и не отменяется: в результате указано, какой commit был заменён, и команда, которая возвращает его. **Пропустить проблемные** ставит «Пропустить» во всех проблемных строках. **Запустить** (Ctrl+Enter) начинает выполнение.

Сначала выполняются merge, fast-forward и rebase, в порядке списка, чтобы ваша ветка пришла в итоговое состояние один раз; затем push уходят по одному remote за раз, начиная с upstream. Атомарного «всё или ничего» между remote нет: каждый заканчивается собственным результатом, а сбой на одном (сеть, hook) не останавливает остальные. **Повторить неудачные** (или `Git: повторить неудачные push`) пробует их снова. Закрытие окна хода работы никогда не останавливает выполнение; `Git: показать групповой push` возвращает его.

### Конфликты и «Продолжить»

Если merge или rebase выполнения остановился на конфликтах, диалог закрывается, и дальше работают обычная полоса merge и редактор конфликтов. Полоса над Log сообщает `Групповой push приостановлен (gitlab): разрешите конфликты, завершите, затем «Продолжить».` и содержит кнопки **Продолжить** и **Прервать группу**.

- Разрешите конфликты и завершите merge или rebase (в GitPoulpi или обычным git).
- **Продолжить** неактивна, пока это не сделано, и она **никогда не нажимается за вас**: ничего не продолжается само. Нажмите её (или выполните `Git: продолжить групповой push`), и выполнение снова делает push на каждый remote с вашей новой вершины. После rebase remote, который всё ещё хранит старые commit'ы, возвращается в диалог плана (теперь ему нужен force push), а не получает force молча.
- **Прервать группу** (с подтверждением; `Git: прервать групповой push`) отбрасывает merge или rebase, начатые выполнением, и забывает это выполнение. Уже сделанные push остаются.

Полоса переживает перезапуск GitPoulpi, и CLI видит то же сохранённое выполнение.

## Pull

- Кнопка **Pull** подтягивает upstream точно как раньше, если у ветки нет источников pull: тогда она подтягивает upstream и каждый источник по порядку, каждый в режиме, заданном **Кнопка «Pull»** в настройках (merge, только fast-forward или rebase). Источник, который нельзя перемотать fast-forward, сливается (или перебазируется) как upstream; при только fast-forward источник, которому нужно больше, сначала спрашивает.
- **Pull ▾** добавляет `Pull из всех источников (origin + gitlab)`, когда есть источники, и `Pull только из <remote>` для каждого remote ветки: разовый pull ветки этого remote, что бы ни говорили флажки.
- В палитре есть `Git: Pull из всех источников` и `Git: Pull из одного remote...`.
- Pull, остановившийся на конфликтах, оставляет ту же полосу, подписанную как групповой pull.

## Настройки

Все четыре находятся в **Настройки > Git и кодировка**.

| Настройка | По умолчанию | Значение |
|---|---|---|
| **Кнопка «Push»** | сразу | сразу делает push; спрашивать сначала открывает меню Push. |
| **Кнопка «Pull»** | merge | Режим кнопки Pull (merge, только fast-forward или rebase) и источников pull. |
| **Проверять все remote перед push** | включено | Смотреть на каждый remote перед групповым push (CLI следует этому; `--no-preflight` отключает для одного вызова). |
| **Дополнительные цели push для новых веток** (для репозитория) | нет | Remote, на которые новая ветка тоже делает push. |

## Из командной строки

```
gitpoulpi branch upstream add gitlab --pull      # a push target that is also a pull source
gitpoulpi branch upstream list                    # what the branch is set up for
gitpoulpi push --all-targets                      # upstream plus every target
gitpoulpi push --to gitlab --to backup:feat-x     # exactly these, this once
gitpoulpi pull --all-sources                      # upstream plus every pull source
gitpoulpi remote-group plan                       # what a grouped push would do, nothing changed
gitpoulpi remote-group continue                   # after resolving and concluding a stop
```

Когда remote требует решения, команда отвечает планом (код выхода 3) и ничего не меняет; ответить на него можно через `--resolve gitlab=merge`. Все флаги - в [справочнике CLI](cli-reference.md). У MCP-сервера те же инструменты.

## С обычным git

Цели - это обычные ключи конфигурации, так что скрипт или алиас могут использовать их без GitPoulpi:

```
git config --get-all branch.feature.gitpoulpi-push-to     # one value per line: remote or remote:branch

# push the current branch to its upstream and to every target
git config alias.pushall '!b=$(git symbolic-ref --short HEAD); git push; for t in $(git config --get-all branch.$b.gitpoulpi-push-to); do r=${t%%:*}; d=${t#*:}; [ "$d" = "$t" ] && d=$b; git push "$r" "$b:$d"; done'
```

Значение - это `<remote>` (то же имя ветки) или `<remote>:<branch>`; строка `d=${t#*:}` как раз это и разбирает. Простой алиас не смотрит на remote заранее, не предлагает merge и не может продолжить после конфликта: для этого и нужен диалог.

## Полезно знать

- Два remote, указывающие на один адрес, замечаются («gitlab и mirror: push на один и тот же URL»); второй по умолчанию пропускается.
- Хост с защищённой веткой отклоняет force push; строка сообщает об этом и предлагает только «Пропустить».
