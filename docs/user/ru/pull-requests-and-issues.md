# Pull request'ы и задачи

Чтение, создание и ведение pull / merge request'ов и задач с боковой панели, с доски и с панели инструментов. Сначала подключите учётную запись и свяжите репозиторий: см. [Интеграции с хостингами и трекерами задач](hosting-integration.md). Всё, что сказано об одной задаче или одном запросе (комментарии, ревью, обсуждения), описано в [Беседах](conversations.md); чтение и ревью запроса - в [Ревью pull request'а](review.md).

## Pull request и задачи на боковой панели

### PULL REQUESTS

В разделе есть заголовок со счётчиком и кнопкой `+` (создать pull request),
выпадающие списки провайдера и проекта, строка поиска и выпадающий список
состояния (*Открытые*, *Merged / закрытые*, *Все*). Далее идут четыре группы,
у каждой свой счётчик:

- **Мои pull requests**: вы автор.
- **Назначенные мне**.
- **Ждут моей проверки**: вас запросили в рецензенты.
- **Все pull requests**: в начале свёрнута.

Строка поиска фильтрует все группы (заголовок, номер, автор, ветка). Каждое
изменение выпадающего списка состояния снова запрашивает хост.

Строка начинается с символа состояния: `●` открыт (зелёный), `○` черновик, `◆`
merged (фиолетовый), `✕` закрыт (красный). Запрос для ветки, на которой вы
находитесь, выделен жирным. Строки выглядят как `#12  заголовок` (GitHub,
Bitbucket) или `!53  заголовок` (GitLab, Azure DevOps).

### ЗАДАЧИ

Заголовок раздела называет провайдера: `ЗАДАЧИ GITHUB`, `ЗАДАЧИ JIRA` и так
далее. Для Azure DevOps он читается как `РАБОЧИЕ ЭЛЕМЕНТЫ ...`, для Trello как
`КАРТОЧКИ ...`. Под выпадающими списками: строка поиска, выпадающий список
состояния (*Открытые*, *Назначенные мне*, *Закрытые*, *Все*) и сами задачи.
Строка Jira выглядит как `ABC-12  заголовок`; если боковая панель достаточно
широкая, тип и статус показываются приглушённо.

### Действия над строкой

- `Enter` или двойной щелчок открывает строку: pull request - в [ревью](review.md) (GitHub, GitLab, Gitea,
  Forgejo, Gerrit), задачу, а также запрос в Azure DevOps или Bitbucket - как [беседу](conversations.md) в окне,
  а всё остальное - в браузере. Пункт меню строки **Открыть в браузере** всегда открывает браузер.
- Правый щелчок или `.` открывает меню строки:
  - **Открыть беседу** (задачи и запросы, у которых нет окна ревью), **Открыть в браузере**, **Копировать URL**,
    **Копировать номер**.
  - Для pull request: **Править на <провайдер>**, **Checkout исходной
    ветки**, **Commit'ы исходной ветки**. Для запроса из форка checkout
    называется **Checkout pull request (форк)**, а просмотр неактивен.
  - Для задачи: **Создать ветку из задачи**. Открывается запрос имени новой ветки
    с именем вроде `12-fix-the-thing` (или `ABC-123-fix-the-thing` для Jira).
  - В GitHub, GitLab, Gitea и Forgejo у строки pull request есть ещё **Ревью...**
    (также **Enter** на строке): ревью в приложении, см.
    [Ревью pull request](review.md).
  - В GitHub, GitLab, Gitea и Forgejo у обеих строк есть ещё **Изменить
    исполнителей...**, **Изменить метки...** и **Задать этап...** (а у pull
    request - ещё **Изменить рецензентов...**): см.
    [Исполнители, рецензенты, метки и этап](#исполнители-рецензенты-метки-и-этап).
- У пункта **Править на <провайдер>** есть ещё три способа вызова: карандаш `✎`
  у правого края строки pull request при наведении или выборе, клавиша `e` на
  выбранной строке и команда палитры *Интеграции: править связанный pull request
  на хостинге* (для запроса ветки, на которой вы находитесь).
- Если исходной ветки ещё нет в репозитории, GitPoulpi сообщает об этом. Сначала
  сделайте fetch (`Ctrl+G f`).

**Checkout pull request.** GitPoulpi загружает запрос в локальную ветку `pr/<n>`
(`mr/<n>` в GitLab), которая отслеживает его, и переключается на неё. В GitHub,
GitLab, Gitea и Forgejo это работает и для форков (GitPoulpi загружает специальную head-ссылку
хоста). Azure DevOps и Bitbucket загружают исходную ветку запроса. Запрос из
форка там отклоняется: добавьте форк как remote и переключитесь на его ветку
самостоятельно. Отмена возвращает на прежнюю ветку. CLI:
`gitpoulpi hosting checkout-pr <n>`.

**Ревью pull request из командной строки (и для агента).** В GitHub (включая
Enterprise), GitLab (включая self-managed), Gitea и Forgejo запрос можно
прочитать и просмотреть, не выходя из GitPoulpi: `hosting review show <n>`
(файлы, состояние слияния, проверки), `hosting review threads <n>` (обсуждения
ревью и беседа), `hosting review comment`, `hosting review reply`,
`hosting review resolve` и `hosting review submit <n> --event
approve|request-changes|comment --comment path:line[:side]:text`. Diff берётся из
вашего репозитория, а не с хоста: `hosting review fetch <n>` загружает head
запроса в `refs/gitpoulpi/pr/<n>`, а его целевую ветку - в
`refs/gitpoulpi/pr/<n>-base` (ни то, ни другое не ветка, ничего не
переключается). Номера строк - из этого diff: `new` - строка в head, `old` -
строка в merge base. В GitLab нет состояния ревью «запросить изменения»: там
команда отклоняется, ничего не отправляется. Gitea и Forgejo принимают
комментарий только к одной строке (без диапазонов); обсуждение - это комментарии
к одной строке файла. Gitea умеет разрешать обсуждение, Forgejo 11 - нет (у
хоста нет для этого конечной точки: вызов так и говорит). Ответ на сервере без
конечной точки ответов публикуется как ревью из одного комментария к той же
строке. Gitea отказывается одобрять или отклонять ваш собственный запрос.
Без клона: добавьте `--project owner/name` (GitLab: `group/project`) к `review show`, `threads`,
`comment`, `reply`, `resolve`, `submit` и `suggest`, чтобы вести ревью проекта, не являющегося текущим репозиторием;
`hosting review diff <n> --project P` читает diff (hunk'и по файлам) из API хостинга, а
`hosting file <path> --project P [--ref R]` читает файл в заданной ревизии (GitHub, GitLab, Gitea, Forgejo и Gerrit; в Gerrit diff
набора патчей читается файл за файлом, а файл берётся из ветки или, для id коммита, из коммита). Файл, который хостинг
не показывает в diff (слишком большой), помечается как `omitted`.
Инструменты MCP - те же команды (`hosting_review_show`, `hosting_review_submit`, `hosting_review_diff`,
`hosting_file`...).

### Исполнители, рецензенты, метки и этап

В GitHub (включая Enterprise), GitLab (включая self-managed), Gitea и Forgejo
можно менять, кому назначены pull request или задача, кто её рецензирует, её
метки и этап, не выходя из GitPoulpi. Другие провайдеры ничего из этого не
показывают.

- **Меню строки**: **Изменить исполнителей...**, **Изменить рецензентов...**
  (только pull request), **Изменить метки...**, **Задать этап...**.
- **Палитра**: `Хостинг: изменить исполнителей...`, `Хостинг: изменить
  рецензентов...`, `Хостинг: изменить метки...`, `Хостинг: задать этап...`
  сначала перечисляют запросы и задачи боковой панели на выбор. В
  [Radar](radar.md) те же четыре действуют на выбранную строку.
- Выборщик открывается сразу и загружает с хоста людей или метки проекта (и то,
  что есть у элемента сейчас). Строка с индикатором появляется примерно через
  150 мс. Введите текст для фильтра (нечёткое совпадение), `Вверх` / `Вниз`
  перемещают, `Space` отмечает или снимает отметку, `Enter` применяет, `Esc`
  отменяет, `Tab` доходит до кнопок. Щелчок по строке отмечает её, колесо
  прокручивает. У людей показан значок с инициалами, у меток - их цвет.
- Этап - выпадающий список (со строкой **Без этапа**, чтобы его снять).
- После **Применить** хост обновляется, а списки и Radar показывают
  изменение после следующего обновления, которое начинается сразу.

В формах создания (pull request, задача) те же варианты выбора есть как ряд
кнопок: `Исполнители: нет`, `Рецензенты: нет`, `Метки: нет`, `Этап: нет`. В
GitHub, GitLab, Gitea и Forgejo кнопка «Метки» заменяет поле меток, вводимых
текстом, в форме задачи. Если хост принял новый pull request, но отклонил
некоторые его метки или людей, строка состояния об этом сообщает.

CLI: `gitpoulpi hosting members|labels|milestones`, `hosting pr-edit <n>`,
`hosting issue edit <n>` и `--assignee`, `--reviewer`, `--label`, `--milestone`
у `hosting pr` и `hosting issue create`; см.
[справочник по CLI](cli-reference.md).

### Клавиши в разделах

| Клавиша | Действие |
|---|---|
| `Enter` / двойной щелчок | открыть беседу в GitPoulpi там, где она есть у хостинга (pull request в GitHub, GitLab, Gitea или Gerrit открывает ревью), иначе браузер |
| `o` | открыть строку в браузере |
| `.` / правый щелчок | меню строки |
| `e` | править выбранный pull request на хосте |
| `n` | новый pull request (PULL REQUESTS) или новая задача (ЗАДАЧИ) |
| `v` | открыть выпадающий список состояния |
| `r` | обновить |
| `Enter` / `Space` на заголовке | свернуть или развернуть раздел |

### Переподключение и офлайн

Если токена нет, он отклонён или ему не хватает прав, первая строка раздела
читается как `Подключить заново (токен отклонён)`. Щёлкните по ней или нажмите
`Enter`, чтобы открыть профиль в **Настройки > Интеграции**.

Если хост недоступен, последние списки остаются на экране, а заголовок
показывает, как давно они обновлялись (`· обновлено 5 мин назад`). Последний ответ также кэшируется на
диске (`.gitpoulpi/hosting-cache.json`), поэтому списки появляются раньше, чем
отвечает сеть.

## Доска задач

Кнопка **Доска** в заголовке ЗАДАЧИ (палитра: `Задачи: открыть доску`) показывает задачи связанного источника как
канбан-доску поверх окна. Колонки зависят от источника:

| Источник | Колонки | Перенос карточки |
|---|---|---|
| Локальные заметки Markdown | статусы (`statuses` профиля, затем любые другие используемые) | переписывает `status` заметки |
| GitHub, GitLab, Gitea, Forgejo | **Открытые**, затем выбранные вами метки, затем **Закрытые** | меняет метку статуса; в **Закрытые** закрывает задачу, в колонку снова - открывает её |
| Trello | открытые списки доски слева направо | переносит карточку в список |
| Redmine | статусы задач | меняет статус задачи (действуют правила рабочего процесса Redmine) |
| Jira (Cloud и Data Center) | статусы проекта, сначала «к выполнению», в конце «готово» | выполняет переход рабочего процесса, ведущий в колонку (`GET`, затем `POST .../transitions`); если такого перехода нет, карточка возвращается, а строка состояния говорит `no transition from X to Y` |
| Azure DevOps (Services и Server) | состояния типов рабочих элементов проекта, по категориям состояний | задаёт `System.State`; рабочий элемент, у типа которого нет состояния колонки, возвращается с причиной (`a Bug has no state Done`) |

В проекте GitHub или GitLab кнопка **Колонки** (или `c`, или `Доска: задать метки колонок...`) спрашивает метки,
которые служат колонками, по порядку, например `status::todo, status::doing, status::review`. Она предлагает метки
проекта, похожие на статусы. Выбор сохраняется для репозитория. Без меток доска - «Открытые / Закрытые». Перенос
карточки трогает только перечисленные вами метки статуса: остальные её метки остаются. Доска хоста перечисляет
открытые задачи и 60 последних закрытых.

Переход Jira, который требует обязательные поля (например, резолюцию), Jira отклоняет, и карточка возвращается с
сообщением самой Jira: такой переход сделайте на сайте.

Та же доска доступна скриптам и агентам: `gitpoulpi hosting board` выводит колонки с карточками, а
`gitpoulpi hosting board move <card> <column>` переносит карточку (см. [справочник по CLI](cli-reference.md)).

Карточка показывает номер, название, исполнителей инициалами, метки и этап. Перетащите её в другую колонку, или
`Shift+←` / `Shift+→`, или `Доска: перенести карточку в...` (`m`). Она переносится сразу; примерно через 150 мс
индикатор сообщает, что хост ещё работает, а если хост отказывает, карточка возвращается и строка состояния говорит
почему. `Enter` открывает [беседу](conversations.md) задачи в GitPoulpi, а когда вы её закроете, доска возвращается; `e` меняет исполнителей, метки и этап; `n`
начинает новую задачу в выбранной колонке; `a`, `l`, `M` и `/` фильтруют по исполнителю, метке, этапу и тексту,
`x` сбрасывает фильтры; `r` читает хост заново. Доска перечитывается, когда обновляются списки боковой панели. В
Radar доски нет.

## Создайте pull request

Откройте форму кнопкой `+` в заголовке PULL REQUESTS, клавишей `n` в разделе или
командой палитры *Pull requests: создать pull request...*. В меню ветки тоже
есть пункт **Создать pull request из <ветка>...**.

В форме есть:

- Одна вкладка на каждый подключённый профиль, поддерживающий pull request
  (`Left` / `Right` на полосе вкладок).
- Поля выбора **Из репозитория / Ветка** и **В репозиторий / Ветка**. Длинные
  списки поддерживают поиск. Можно ввести ветку или репозиторий, которых в
  списках нет.
- **Заголовок**, заполненный темой верхнего commit'а.
- **Описание** в несколько строк (`Enter` добавляет новую строку, `Tab` выходит
  из поля).
- Кнопки **Исполнители**, **Рецензенты**, **Метки** и **Этап** (GitHub, GitLab,
  Gitea и Forgejo), которые открывают выборщик.
- **Отправить как черновик**.
- При включённом [ИИ](ai.md): **Создать заголовок и описание**.

Форма открывается с профилем, репозиторием и ветками текущей ветки
(`feature -> main`). Другой исходный репозиторий создаёт запрос из форка.

**Создать pull request** (или `Ctrl+S`) создаёт запрос на хосте. Результат
открывается в браузере, а строка состояния называет его.

## Создайте задачу

Когда в разделе ЗАДАЧИ выбран провайдер **и** проект, в его заголовке есть
кнопка `+` (*Новая задача*). Также: `n` в разделе или команда палитры
*Хостинг: новая задача...*.

В форме есть **Заголовок** (обязательно), **Описание** (несколько строк) и
**Метки** (через запятую, например `bug, ui`; в GitHub, GitLab, Gitea и Forgejo
вместо этого кнопки «Метки», «Исполнители» и «Этап» открывают выборщик). Jira и Azure DevOps добавляют
выпадающий список **Тип**. Trello добавляет выпадающий список **Список**. Linear
и YouTrack добавляют выпадающий список **Статус** (состояние рабочего процесса
или значение `State`, с которого начинается задача). Redmine добавляет выпадающий
список **Тип** с трекерами проекта (Bug, Feature, Support...); меток в нём нет,
поэтому кнопки «Метки» для него нет, а метка, заданная в командной строке,
отклоняется. Эти списки форма заполняет данными хоста при открытии.

**Создать задачу** (или `Ctrl+S`) создаёт её на хосте. `Esc` или **Отмена**
закрывает форму. Если хост отказывает (токен отклонён, не хватает прав, неизвестный
проект, неизвестная метка), форма показывает причину и сохраняет введённое. При
успехе строка состояния называет новую задачу, а раздел ЗАДАЧИ обновляется.

CLI: `gitpoulpi hosting issue create --title ... [--body ... | --body-file ...]
[--label ...] [--type ...] [--list ...]`.

## Создание на веб-странице самого хоста

В форме «Новая задача» и в форме создания pull request вверху справа есть кнопка
**Создать на <провайдер>**. Клавиша - `Alt+W`. Она открывает в браузере веб-форму
хоста, заполненную тем, что вы уже ввели. Диалог остаётся открытым. Токен не
нужен, вызов API не выполняется, поэтому кнопка работает и после ошибки API.

- В GitHub нет параметра URL для *черновика*, поэтому флажок черновика не
  переносится. В GitLab к заголовку добавляется префикс `Draft: `.
- GitLab принимает метки только по id, поэтому они добавляются в конец описания
  как быстрое действие `/label ~"x"`.
- Очень длинное описание обрезается, чтобы URL не превышал 6000 символов, с
  пометкой `[...truncated: paste the rest]`.
- У Bitbucket Data Center нет адреса веб-формы, поэтому кнопки **Создать на
  <провайдер>** там нет.

CLI: `gitpoulpi hosting issue create ... --web` и `gitpoulpi hosting pr --web`
выводят тот же URL.

## Значок на панели инструментов

На конце панели инструментов (по умолчанию справа) значок показывает запрос для ветки, на которой вы
находитесь: `GH #12` (GitHub), `GL !53` (GitLab), `AZ !12` (Azure DevOps) или
`BB #12` (Bitbucket). Цвет показывает состояние: зелёный - открыт, серый -
черновик, фиолетовый - merged, красный - закрыт.

- Наведите курсор, чтобы увидеть заголовок, состояние и `источник → цель`.
- Щёлкните по нему или нажмите `Ctrl+G g`, чтобы открыть запрос в браузере.
- Правый щелчок открывает **Открыть в браузере**, **Копировать URL**,
  **Обновить** и **Сменить профиль**.

Отправленная ветка без запроса показывает тусклый значок `+ PR`. Щёлкните по
нему, чтобы создать pull request. Значка нет, если ни один профиль не подходит,
ветка не отправлена или хост недоступен. В узком окне значок скрывается, чтобы
оставить место кнопкам панели инструментов.

## Когда обновляются списки

Списки обновляются:

- при открытии репозитория;
- при смене текущей ветки;
- после push или fetch;
- через каждые *Обновление pull requests и Issues (мин.)*
  (`general.hosting_refresh_minutes`, по умолчанию 5, `0` отключает таймер;
  **Настройки > Интеграции**);
- при закрытии Настроек;
- когда вы нажимаете `r`, запускаете *Интеграции: обновить pull requests и
  задачи* или меняете фильтр.

Запросы никогда не блокируют окно.

Хосты ограничивают число вызовов. GitPoulpi отправляет обратно `ETag` последнего
ответа, поэтому неизменившийся список обходится дёшево (в GitHub бесплатно).
Когда хост сообщает, что вызовов осталось мало, строка состояния говорит об
этом. Когда они закончились, GitPoulpi перестаёт обращаться к этому хосту до
сброса лимита, а списки остаются как есть.

## Терминология

GitHub, Azure DevOps и Bitbucket говорят «pull request». GitLab говорит «merge
request». **Термин для запроса на ревью** (`ui.pr_terminology`, в
**Настройки > Интеграции**) выбирает слово для каждой подписи, меню, команды палитры
и сообщения:

- **Авто (по хостингу)**: следует провайдеру, связанному с репозиторием («Pull
  Request», пока ничего не связано).
- **Pull Request** или **Merge Request**: всегда это слово.

Изменение применяется сразу. CLI и MCP всегда говорят «pull/merge request». На
этой странице используется «pull request».

## Ссылки в сообщениях commit'ов и именах веток

Когда задачи или pull request репозитория связаны, ссылки в сообщении commit'а в
сведениях о commit'е подчёркиваются. Щелчок открывает связанную страницу.
Клавиатура: команда палитры *Интеграции: открыть ссылку из commit'а (#задача /
!запрос)...* (меню, если в сообщении несколько ссылок). У репозитория без связей
ссылок нет.

Что считается ссылкой, зависит от провайдера раздела ЗАДАЧИ:

| ЗАДАЧИ связаны с | В сообщении | В имени ветки |
|---|---|---|
| GitHub, GitLab, Gitea, Forgejo | `#123` | `123-fix-login` |
| Azure DevOps | `#123` и `AB#123` | `123-fix-login` |
| Jira | `ABC-123`, только если `ABC` - ключ связанного проекта. Тексты вроде `UTF-8`, `SHA-256` или `ISO-8601` никогда не становятся ссылками. | `ABC-123` в любом месте имени (`feature/ABC-123-x`), в верхнем регистре |
| Linear | `ENG-123`, только если `ENG` - ключ связанной команды (или команды из списка команд профиля). `UTF-8` никогда не становится ссылкой. | собственный `branchName` Linear, когда вы создаёте ветку из задачи; `ENG-123` в любом месте имени читается обратно |
| YouTrack | `ABC-123`, только если `ABC` - короткое имя связанного проекта (или проекта из списка проектов профиля) | `ABC-123` в любом месте имени |
| Redmine | `#123`, только если Redmine - связанный источник ЗАДАЧ (источник pull request сохраняет свой знак) | `123-fix-login` |
| Trello | адрес `https://trello.com/c/<shortLink>`; `#12` только если у карточки в кэше номер 12 | `12-fix-login` |

| PULL REQUESTS связаны с | В сообщении |
|---|---|
| GitLab, Azure DevOps | `!45` |
| GitHub, Bitbucket, Gitea, Forgejo | `#45` |

Если `#N` подходит обоим спискам, побеждает задача. CLI:
`gitpoulpi hosting refs --message TEXT | --commit REV | --branch NAME`.

**В беседах.** Текст задачи или запроса читается по грамматике его хостинга, которая шире таблицы выше:
`owner/repo#7`, `!7`, `GH-7`, `@login`, id commit'ов и другие формы, перечисленные в
[Перекрёстных ссылках](conversations.md#перекрёстные-ссылки). Сначала сопоставляются связанные источники репозитория, поэтому
ключ Jira в комментарии GitHub по-прежнему открывает свою задачу в приложении. `gitpoulpi hosting markdown --body TEXT --id I`
показывает, что приложение находит в тексте.

### Вставка ссылки на задачу

В композиторе commit'а кнопка `#▾` у правого края поля «Заголовок» открывает список
связанных задач с фильтром. Задача, названная в имени текущей ветки, идёт первой
с пометкой *(из ветки)*. `Enter` или щелчок вставляет её ссылку (`ABC-123`, `#12`,
`AB#12`) в позицию курсора. Клавиатура: `Alt+R` в композиторе. Палитра:
*Commit: вставить ссылку на задачу...*. Если список задач не связан, кнопка
неактивна и сообщает *сначала свяжите список задач на боковой панели*.
GitPoulpi никогда не добавляет ссылку сам.
