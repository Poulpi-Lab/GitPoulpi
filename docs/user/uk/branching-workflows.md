# Робочі процеси гілок

Робочий процес гілок підказує GitPoulpi, як ваша команда використовує гілки: які
живуть вічно (`main`, `develop`, `production`), які є короткоживучими тематичними
гілками (`feature/...`, `hotfix/...`), як вони називаються і де кожна починається
та завершується. Це Git Flow, який можна налаштувати: фіксовані назви, префікси й
суфікси або шаблони із заповнювачами, тож гілки, які бот створює з issue,
розпізнаються так само, як ваші власні.

Ця сторінка охоплює модель, файл, готові шаблони, визначення й імпорт, команди
лише для читання, дії, що починають, завершують, синхронізують і просувають гілки
(CLI, MCP і застосунок), а також екрани застосунку: редактор налаштувань, згруповану
бічну панель, меню `Flow` та його діалоги.

## Поняття

- **Базова гілка** живе довго. Базова гілка може мати **батьківську** (`develop`
  вливається в `main`); в основної лінії її немає. Базова гілка може перелічувати
  кілька можливих назв (`main` або `master`, `develop` або `dev`): використовується
  та, що існує.
- **Тип гілки** (topic type) - це різновид короткоживучої гілки (feature, bugfix,
  release, hotfix, support...). Він має **шаблон назви**, **батьківську гілку**
  (звідки починається і куди завершується) і спосіб завершення.
- Кожна гілка **класифікується**: базова (за назвою), тематична гілка певного типу
  (за шаблоном) або некласифікована.
- **Батьківська гілка** визначається в такому порядку: записана, коли GitPoulpi
  створив гілку (`git config branch.<name>.gitpoulpi-parent`), інакше
  `git-town-branch.<name>.parent` від Git Town, якщо є, інакше батьківська гілка її
  типу.

## Де це зберігається

| Що | Де | Чи комітиться |
|---|---|---|
| Спільний робочий процес | `.gitpoulpi/workflow.toml` у репозиторії | Так, вами: GitPoulpi записує його лише на ваше прохання |
| Ваші власні правки | `[workflow]` у `.gitpoulpi/repo-state.toml` | Ні (цей файл ігнорується) |

Каталог стану ігнорує сам себе (`.gitpoulpi/.gitignore`), крім `workflow.toml`,
який призначений для commit'у. Чинний робочий процес - це спільний файл із вашим
перевизначенням зверху: базова гілка з тією самою назвою чи тип гілки з тим самим
id замінюється; нові додаються; `disable_bases` і `disable_topics` вилучають спільні
записи лише для вас.

Збереження поверх наявного файлу зберігає ключі, яких ця версія не знає (новішого
GitPoulpi, колеги), але не коментарі й не порядок ключів.

## Файл

```toml
template = "git-flow"          # git-flow | github-flow | gitlab-flow | trunk | custom (довідково)

[[base]]
name = "main"
names = ["master"]             # інші написання тієї самої гілки
protected = true               # ніколи не видаляється, прямі commit'и підозрілі

[[base]]
name = "develop"
names = ["dev"]
parent = "main"
merge = "merge"                # merge | squash | rebase | fast-forward
tag_on_merge = false
# environment = true           # гілка середовища (GitLab Flow): просувається за потоком

[[topic]]
id = "feature"
label = "Feature"
pattern = "feature/{slug}"
patterns = ["features/{slug}"] # ще назви, що теж збігаються; ніколи не використовуються для створення
# regex = "^feat-(?P<slug>.+)$"  # теж збігається; іменовані групи стають полями
parent = "develop"             # звідки починається і куди завершується типово
finish = [{ into = "develop", merge = "squash" }]
finish_mode = "merge-request"  # local-merge | merge-request | ask
delete_after_finish = true

[hooks]                        # команди оболонки за бажанням, завжди показуються перед виконанням
after_start = []
before_finish = ["cargo test"]

[issue_flow]                   # потоки під керуванням хоста, див. нижче
mode = "local"                 # local | host-creates-branch | bot
```

`merge`, `finish`, `finish_mode` і `hooks` керують [діями](#дії) нижче;
`issue_flow` керує [потоками під керуванням хоста](#потоки-під-керуванням-хоста).

### Шаблони назв

Текст із `{заповнювачами}`:

| Заповнювач | Збігається з | Утворюється з |
|---|---|---|
| `{slug}` | вільний текст; може містити `/`, якщо стоїть останнім | текст у нижньому регістрі, без діакритики, з `-` між словами, не більше 50 символів |
| `{issue}` | цифри (`123`) | `123` або `#123` |
| `{issue_key}` | ключ трекера (`PROJ-123`) | як задано |
| `{user}` | ім'я без `/` | перетворюється на slug |
| `{date}` | `2026-10-16` або `20261016` | як задано |
| `{version}` | `1.2.0`, `v1.2`, `1.2.0-rc1` | як задано |
| `{n}` | цифри | як задано |

Усе інше - буквальний текст, тож префікси й суфікси - це просто текст:
`feature/{slug}`, `{user}/{issue}-{slug}-wip`, `bot/{issue_key}`. Кожен заповнювач
може з'явитися один раз, а між двома заповнювачами потрібен текст. Шаблон має
давати чинні назви гілок (правила `git check-ref-format`): без пробілів, без
`~ ^ : ? * [ \`, без `..`, без компонента, що починається з `.` або закінчується
на `.lock`.

`regex` потрібен лише для розпізнавання (він прив'язаний з обох кінців); користуйтеся
ним для назв, яких жоден шаблон не виразить. Іменовані групи стають полями гілки.

### Який тип перемагає

1. Гілка, названа як базова (будь-якою з її назв), є цією базовою гілкою.
2. Інакше кандидатами є кожен шаблон кожного типу, що збігається: `pattern`, потім
   `patterns`, потім `regex`, тип за типом у порядку файлу. Перемагає той, що
   фіксує найбільше буквальних символів (`release/{version}` б'є `{user}/{slug}`,
   який б'є голий `{slug}`); regex рахує свій буквальний префікс. Нічия
   дістається тому, що раніше у файлі.
3. Інакше гілка некласифікована.

Зламаний шаблон чи regex повідомляється як попередження і пропускається; решта
працює далі.

## Шаблони

| Шаблон | Базові гілки | Типи гілок |
|---|---|---|
| `git-flow` | `main` або `master`; `develop` або `dev` (батьківська main) | `feature/` і `bugfix/` (від develop), `release/` (від develop, у main і develop, з tag'ом), `hotfix/` (від main, у main і develop, з tag'ом), `support/` (від main); множинні написання (`features/`, `releases/`...) теж збігаються |
| `github-flow` | `main` | `feature/` або будь-яка назва, від main, merge request у main, squash, потім видаляється |
| `gitlab-flow` | `main`; `pre-production` і `production` (гілки середовищ, ланцюжок main, pre-production, production) | `feature/` або будь-яка назва від main; `release/{version}` як ціль cherry-pick |
| `trunk` | `main` | короткоживучі `{user}/{slug}` від main, з rebase |
| `custom` | немає | немає |

Гілки середовищ також збігаються як `preprod`, `staging` і `prod`. Шаблон - це
відправна точка: виведіть його через `flow config init`, відредагуйте файл.

## Визначення та імпорт

`gitpoulpi flow detect` ранжує шаблони для гілок, що є в репозиторії, з оцінкою зі
100 і конкретними знайденими назвами (`master` замість `main`, `dev` замість
`develop`, `features/` замість `feature/`). Базові гілки дають 60 балів, частка
інших гілок, яку розпізнають специфічні шаблони, - 40, а довгоживуча гілка іншого
шаблону (`develop` у кандидаті GitHub Flow) забирає 25.

`gitpoulpi flow import --from git-flow` читає класичні налаштування git-flow
(`gitflow.branch.master`, `gitflow.branch.develop`,
`gitflow.prefix.feature|bugfix|release|hotfix|support|versiontag`) із власного
`.git/config` репозиторію; `--from git-town` читає `git-town.main-branch` і
`git-town.perennial-branches` (батьківська гілка кожної гілки,
`git-town-branch.<name>.parent`, підхоплюється як записана батьківська). Нічого не
застосовується мовчки: команда виводить TOML, а `--write` створює
`.gitpoulpi/workflow.toml`, лише якщо його не існує.

## Команди

Усі приймають `--json`; сервер MCP відкриває їх як інструменти (`flow_status`,
`flow_templates`, `flow_detect`, `flow_config_show` читають; дії описано нижче).

| Команда | Що робить |
|---|---|
| `gitpoulpi flow status` | Кожна локальна й віддалена гілка: вид (базова, тематична, некласифікована), тип гілки та поля, батьківська гілка і звідки вона взялася (`recorded`, `git_town`, `type`, `base`), а для локальних гілок - на скільки commit'ів вона випереджає (`ahead`) батьківську і відстає (`behind`) від неї. Також попередження, знайдені у визначенні, ранжоване визначення та налаштування інших інструментів, які можна імпортувати. |
| `gitpoulpi flow templates` | Наведені вище готові шаблони з повним визначенням. Не потребує репозиторію. |
| `gitpoulpi flow detect` | Ранжовані шаблони зі знайденими базовими гілками й типами. |
| `gitpoulpi flow config [--show-effective]` | Спільний файл (його шлях, чи існує, розібраний робочий процес, невідомі ключі) або, з `--show-effective`, робочий процес, за яким класифікуються ваші гілки. `flow config show` - те саме. |
| `gitpoulpi flow config init --template <t> [--write]` | Вивести TOML шаблону; `--write` створює `.gitpoulpi/workflow.toml` і відмовляється перезаписувати наявний. |
| `gitpoulpi flow import --from git-flow\|git-town [--write]` | Як описано вище. |

Лічильники ahead/behind обчислюються щонайбільше для 300 локальних гілок за виклик.

Файл робочого процесу, який неможливо прочитати (хибний TOML, значення неправильного
типу), - це помилка, що називає файл; її ніколи не ігнорують мовчки.

## Дії

`start`, `finish`, `sync`, `promote` і `set-parent` діють на репозиторій. Кожна
спершу **планує**: перелічує кожен крок git, який виконає, з командою git, до якої він
зводиться, попередження, що не можна скасувати, і все, що її блокує. Нічого не
змінюється, доки ви не підтвердите. Кожен запуск - **один запис в історії
скасувань** (`gitpoulpi undo` одразу повертає гілки, tag, видалену гілку, записану
батьківську гілку й checkout).

| Команда | Що робить |
|---|---|
| `gitpoulpi flow start <type> [name=value ...] [--from <ref>] [--publish]` | Називає гілку за шаблоном типу (`flow start feature "Login form"` створює `feature/login-form`; `flow start release version=1.2.0` створює `release/1.2.0`; голе слово - це `slug`; `user` і `date` типово беруться від вас і з сьогоднішньої дати), створює її від батьківської гілки типу або `--from` (гілка, віддалена гілка чи tag), робить checkout і записує її батьківську гілку. `--publish` робить push з `-u` (`undo` цього не скасовує). |
| `gitpoulpi flow finish [<branch>]` | Для кожної цілі `finish` типу, по черзі: робить checkout цілі й merge гілки зі стратегією цілі (`merge`: завжди merge commit; `squash`: один commit із заголовком `--title` або з назви гілки; `rebase`: rebase гілки на ціль, потім fast-forward; `fast-forward`), створює tag, якщо він є в цілі (`tag = "v{version}"`, анотований), потім робить checkout батьківської гілки й видаляє локальну гілку, якщо так сказано в типі (`--delete` / `--keep` це перевизначають; `--delete-remote` також видаляє її на remote, не скасовується). З `finish_mode = "merge-request"` (або `--mode merge-request`) лише робить push гілки й відкриває pull чи merge request у батьківську гілку, з `--title`, `--draft`, `--assignee`, `--reviewer`, `--label`, `--milestone` і `--integration` (не скасовується; локально нічого не зливається й не видаляється). `--mode local-merge` перевизначає тип `merge-request`, а тип зі значенням `ask` потребує одного з двох. |
| `gitpoulpi flow sync [<branch>] [--stack] [--rebase\|--merge]` | Вносить commit'и батьківської гілки в гілку: merge або rebase, коли стратегія гілки `rebase` (або `--rebase`). З `--stack` також гілки, батьківська гілка яких - ця (записана через `set-parent`), рекурсивно, по черзі. Повертається на гілку, на якій ви були. |
| `gitpoulpi flow promote <env-branch>` | Гілки середовищ GitLab Flow: робить merge у неї гілки, нижче за потоком від якої вона стоїть (`main` у `pre-production`, `pre-production` у `production`), одним кроком і повертається. Робить fast-forward, коли може. |
| `gitpoulpi flow set-parent <branch> <parent>` / `--clear` | Записує (або вилучає) `branch.<name>.gitpoulpi-parent`. Відмовляє на цикл. Можна скасувати. |

Гілка, розпочата з іншого місця, завершується там: коли записана батьківська гілка
(з `--from` або `set-parent`) відрізняється від батьківської гілки типу, першою
ціллю завершення стає записана батьківська гілка.

### Підтвердження, планування, скрипти

| Прапорець | Значення |
|---|---|
| `--dry-run` | Вивести план як JSON (`{"plan": ...}`) і зупинитися. Код виходу 1, коли щось його блокує. |
| `--yes` | Виконати без запиту. |
| жоден | У терміналі: план показується і вас питають. В іншому разі (скрипт, `--json`, агент) план повертається як `{"needs_confirmation": {"plan": ...}}` з кодом виходу 3 і без жодних змін. `start` без `--publish` чи хуків, `set-parent` і `--abort` не потребують підтвердження. |
| `--run-hooks` / `--no-hooks` | Див. [хуки](#хуки). |
| `--autostash` | Сховати локальні зміни, що заважають checkout чи merge, і повернути їх після, що б не казало `general.auto_stash`. |

Заблокований план називає причину: базова гілка там, де потрібна тематична, назва,
що вже існує, відсутнє поле (`release/{version}` потребує `version=...`), tag, що
існує, цільова гілка, яка відстає від свого remote (`--allow-behind` усе одно
продовжує), merge чи rebase, що вже триває, робочий процес, який не налаштовано.

З налаштуванням **auto-stash** (`general.auto_stash`) робочі зміни, що заважають
checkout чи merge, ховаються і повертаються навколо дії точно так само, як для
звичайного checkout; з `never` дія зупиняється, нічого не змінивши.

### Конфлікти

Merge чи rebase, що зупинився на конфліктах, лишає звичайний стан конфлікту
(банер конфлікту, `gitpoulpi conflicts ...`), а потік запам'ятовується. Код виходу
2, `status: "conflicted"`, шляхи в `conflicts`. Вирішіть файли й позначте їх
вирішеними, потім:

- `gitpoulpi flow finish --continue` робить commit merge (або продовжує rebase, або
  робить commit squash з його повідомленням) і виконує решту кроків;
- `gitpoulpi flow finish --abort` перериває merge чи rebase, повертається на гілку,
  з якої почався потік, і забуває решту. Уже виконані кроки (перша ціль подвійного
  завершення з її tag'ом) лишаються: `undo` їх повертає.

Потік, зупинений хуком, що завершився помилкою, відновлюється так само (`--continue`
виконує цей крок знову). Запуск із конфліктом і його продовження - це два записи
скасування.

### Merge request

Демон робить push гілки; для відкриття запиту потрібен ваш токен хостингу, тож CLI
робить це тим самим кодом, що й `gitpoulpi hosting pr` (інтеграція, що відповідає
remote, інакше попередньо заповнена вебсторінка хоста, виведена як URL). Результат
містить `merge_request` (про що просили) і `opened` (що відповів хост) або
`open_error`, коли гілку відправлено, але запит відкрити не вдалося.

### Хуки

`[hooks]` у файлі робочого процесу перелічує команди оболонки (`after_start`,
`before_finish`). Вони походять із файлу, яким ділиться ваша команда, тож **ніколи не
виконуються без вашого прохання**: `--run-hooks` або відповідь «так» на запитання,
яке термінал ставить після їх переліку. План завжди їх перелічує, з `hooks_run: false`,
коли вони не виконуватимуться. Хук виконується в оболонці з репозиторієм як робочою
папкою та заданими `GITPOULPI_FLOW_ACTION` / `GITPOULPI_FLOW_BRANCH`; його точна
команда, код виходу й увесь вивід є в результаті. Хук, що завершується ненульовим
кодом, зупиняє потік на цьому місці (хук `before_finish` виконується до будь-яких
змін, тож це звичайна помилка; після хука `after_start` гілка вже існує, і потік
можна продовжити чи перервати). `--no-hooks` пропускає їх без запиту. Хук може
робити що завгодно, тож `undo` повертає лише зміни git.

### Для агентів (MCP)

Інструменти - `flow_start`, `flow_finish`, `flow_sync`, `flow_promote` і
`flow_set_parent` (finish, sync і promote позначені як руйнівні, тож їх обмежує
`allow_mutations`). Вони працюють за схемою «план, потім виконання»: викличте з
`dry_run: true`, щоб отримати план (звичайний результат), потім знову з `yes: true`,
щоб виконати його. Без жодного з них виклик відхиляється і несе план, тож нічого не
виконується випадково. Хуки виконуються лише з явним `run_hooks: true`; план
перелічує їх (`hooks`, `hooks_run`), щоб агент міг спершу показати користувачеві
команди. Після конфлікту - `continue_: true` (прапорець - `--continue`) або
`abort: true`.

### Скасування

| Дія | Що робить `undo` |
|---|---|
| start | Видаляє гілку, забуває її батьківську гілку, знову робить checkout попередньої гілки. |
| finish | Відновлює кожну гілку, яку було переміщено, tag, видалену гілку й checkout - одним кроком. Відправлена гілка, віддалене видалення і відкритий merge request лишаються (план про це каже). |
| sync | Повертає кожну оновлену гілку, разом із файлами для гілки з checkout. |
| promote | Повертає гілку середовища. |
| set-parent | Відновлює попередню записану батьківську гілку. |

## Потоки під керуванням хоста

Команди, де роботу починає issue: issue пишеться за шаблоном, а хост (GitLab,
GitHub, Gitea, Forgejo) або бот створює гілку та merge request. GitPoulpi створює
issue, чекає на те, що створює хост, і підхоплює це: локальна гілка, що відстежує
віддалену, із записаною батьківською гілкою (ціль merge request) і checkout. Для цього
розділ ISSUES має бути прив'язаний до трекера (`gitpoulpi hosting link issues`);
прив'язка PULL REQUESTS каже, де живуть гілки й запити (проєкт ISSUES, коли її
не прив'язано).

```toml
[issue_flow]
mode = "bot"                         # local | host-creates-branch | bot
issue_title = "[{type}] {title}"     # {type} {title} {user} {date}
issue_labels = ["workflow::{type}"]  # бот часто спрацьовує на мітку
description_template = ".github/ISSUE_TEMPLATE/feature.md"   # файл репозиторію
branch_from_issue = "{type}/{issue}-{slug}"   # як хост або бот називає гілку
wait_for = "branch-or-mr"            # branch | mr | branch-or-mr
timeout_secs = 600                   # як довго `wait` опитує
merge_request = true                 # host-creates-branch: ще й чернетка запиту
assignees = []
```

`{type}` у `branch_from_issue` - це id типу гілки; решта - звичайні токени
[шаблону назви](#шаблони-назв) (`{issue}`, `{slug}`, `{issue_key}`...). Гілка
належить issue 12, коли вона збігається з цим шаблоном, а `{issue}` дорівнює 12
(`feature/12-login` збігається, `feature/120-x` - ні).

| Режим | Після створення issue |
|---|---|
| `local` | Нічого на хості. З `--pick-up` - `flow start` типу з номером і заголовком issue (скасовується, як і будь-який start). |
| `host-creates-branch` | GitPoulpi створює гілку **на хості** від батьківської гілки типу (GitLab: API гілок; GitHub: `createLinkedBranch`, тож issue показує її в розділі Development; Gitea/Forgejo: API гілок) і **чернетку** запиту із `Closes #12`. Хост, що відмовляє порожньому запиту (GitHub: ще немає commit'ів), лишає гілку і повідомляє про це попередженням. |
| `bot` | Нічого: бот (обробник вебхука, завдання CI, GitHub App) створює гілку й запит. `--wait` опитує, доки не виконається `wait_for`. |

На що дивиться `wait` для кожного провайдера: власні посилання хоста (GitLab
`issues/:iid/related_merge_requests` і `closed_by`; зв'язані гілки GitHub і pull
request'и `connected` / `cross-referenced` з хронології), гілки, назва яких
відповідає `branch_from_issue`, і відкриті запити, гілка-джерело яких відповідає.
Він опитує з дедалі більшою паузою (1, 2, 3, 5, 8, потім кожні 10 с), доки не
виконається `wait_for` або не мине `timeout_secs`, а хост, що повільний чи недовго
недоступний після відповіді, опитується повторно. Джерело, якого хост не пропонує
(у Gitea немає посилань на issue), пропускається; коли відмовляють усі джерела,
відповіддю є перша помилка.

| Команда | Що робить |
|---|---|
| `gitpoulpi flow issue new --type <t> --title "..." [--body T \| --body-file F] [--label L] [--assignee A] [--milestone M] [--wait] [--pick-up] [--timeout S] [--integration ID] [--dry-run]` | Створює issue за шаблоном (`issue_title`, `issue_labels`, файл опису, `--body` замість нього) і продовжує, як каже режим. `--dry-run` виводить, що було б створено (`{"plan": ...}`), і нічого не створює. `--pick-up` у режимі `bot` спершу чекає. Код виходу 4: очікування вичерпано (issue існує; `flow issue wait` чекає далі). |
| `gitpoulpi flow issue wait <#12> [--type t] [--for branch\|mr\|branch-or-mr] [--timeout S] [--once] [--pick-up]` | Опитує, що хост створив для issue, з прогресом у stderr у терміналі; Ctrl+C скасовує. `--once` дивиться один раз. Код виходу 4: поки нічого. |
| `gitpoulpi flow pick-up <#12 \| !5 \| branch> [--remote R] [--parent B] [--no-fetch] [--dry-run]` | Виконує fetch, створює локальну гілку, що відстежує `origin/<branch>`, записує її батьківську гілку і робить checkout. `#12` шукає на хості гілку чи запит issue, `!5` - запит, будь-що інше - назва гілки. Батьківська гілка - це ціль запиту (`--parent` це перевизначає), інакше батьківська гілка типу. Не потребує `--yes`: це локально й скасовується, як `start`. `--dry-run` усе одно виконує fetch (він лише пересуває remote-tracking refs, а плану потрібно побачити гілку). |

`pick-up` - один запис в історії скасувань: `gitpoulpi undo` видаляє гілку, забуває
батьківську гілку й знову робить checkout попередньої гілки (fetch лишається, як
і кожен fetch). Він планується так само, як інші дії: `--dry-run` виводить його план
(`create_branch`, `set_upstream`, `checkout`, `record_parent`), і діють звичайні
блокувальники (робочі зміни підпорядковуються налаштуванню auto-stash). Запит -
це `{"action": "pick_up", "branch": ..., "parent": ...}`.

Issue, створені потоком, **відстежуються** (`watched_issues` у
`.gitpoulpi/repo-state.toml`, ніколи не комітяться): після кожного fetch застосунок
зіставляє віддалені гілки з `branch_from_issue` і повідомляє, коли з'явилася гілка
для відстежуваного issue. Підхоплення це закриває.

### Для агентів (під керуванням хоста)

Інструменти - `flow_issue_new`, `flow_issue_wait` і `flow_pick_up` (запис, мережа;
їх обмежує `allow_mutations`). `flow_issue_new` з `dry_run: true` повертає план;
`flow_issue_wait` блокує до `timeout` секунд, тож давайте агентові короткий і
викликайте знову (`once: true` відповідає одразу). Обидва повертають JSON з `found`
(`branches`, `requests`) і `timed_out`.

### Потоки під керуванням хоста в застосунку

З робочим процесом і прив'язаним трекером у меню Flow з'являються *Нове issue типу
<Тип>...* (по одному на тип; палітра `Flow: нове issue типу <Тип>...` і
`Flow: нове issue...`) та *Підхопити гілку, створену хостом...* (палітра
`Flow: підхопити гілку хоста...`).

- **Нове issue** питає тип (випадаючий список) і заголовок; показує, звідки береться
  опис і хто створює гілку. *Підхопити гілку, коли вона з'явиться* увімкнено типово.
  *Створити issue* створює його, а в режимі `bot` показує **картку очікування**:
  індикатор, на що чекає, минулий час і час, коли відмовиться, та **Не чекати**
  (`Esc`). Зупинка не губить issue: воно лишається відстежуваним. Коли гілка є, її
  підхоплюють, і рядок стану про це каже.
- **З'явилася гілка** - картка, що відкривається, коли fetch приніс гілку
  відстежуваного issue (якщо не відкрито іншого діалогу): *Підхопити* перейме її,
  *Пізніше* закриває картку (її не пропонують знову до перезапуску застосунку).
- **Підхопити** приймає `#12`, `!5` або назву гілки й показує, що знайдено, перш ніж
  її підхопити.

Усе виконується у фоні; виклик, що триває понад 150 мс, показує індикатор.

### Налаштування > Робочий процес

*Налаштування > Налаштування репозиторію > Робочий процес* редагує визначення. Воно
працює з чернеткою і нічого не зберігає, доки ви не натиснете кнопку збереження.

- **Шаблон** - випадаючий список готових шаблонів; вибір замінює базові гілки й типи
  гілок нижче готовим шаблоном (ваші хуки та потік issue лишаються).
- **Визначити за гілками** читає назви гілок цього репозиторію і показує найближчий
  шаблон з оцінкою, знайдені назви баз (`master` замість `main`), скільки гілок
  розпізнає кожен тип гілки, з прикладами, та оцінку кожного шаблону.
  **Використати визначений робочий процес** завантажує його в чернетку.
- Коли репозиторій містить конфігурацію іншого інструмента (`gitflow.*` від Git Flow,
  `git-town.*` від Git Town), пропонується **Імпортувати** - воно завантажує
  імпортоване визначення в чернетку. Нічого не застосовується, доки ви його не
  натиснете.
- **Базові гілки**, **Типи гілок** та їхні **Правила завершення** - це один
  [список](settings.md#списки) із групами на вкладці **Правила**; вкладка
  **Загальні** містить решту (шаблон, визначення, хуки, потік issue). Виберіть елемент, щоб змінити його праворуч (назва
  та інші назви, батьківська гілка, захищена, стратегія merge, tag при merge, гілка
  середовища; підпис, шаблон назви, інші шаблони, регулярний вираз, батьківська
  гілка, режим завершення, видалення після завершення). **+ Додати ▾** пропонує, що
  додати (правило завершення належить до вибраного типу гілки); додавання,
  дублювання, видалення й перетягування працюють, як в усіх списках Налаштувань, а
  елементи рухаються в межах своєї групи. Рядок **шаблону назви** перелічує токени
  (`{slug} {issue} {issue_key} {user} {date} {version} {n}`); під ним жива попередня
  версія показує наявні гілки, що відповідають шаблону, і назву, яку він створив би,
  а шаблон, що не розбирається, пояснює причину червоним просто під полем (нічого з
  набраного не втрачається).
- **Хуки** - команди оболонки, по одній на рядок (`Після початку`, `Перед
  завершенням`), які редагуються в багаторядковому редакторі (`Ctrl+S` зберігає,
  `Esc` скасовує). Вони виконують команди на вашому комп'ютері: сторінка про це
  каже, а діалоги показують їх перед виконанням.
- **Потік issue** містить поля, які використовують [потоки під керуванням
  хоста](#потоки-під-керуванням-хоста) (режим, заголовок і мітки issue, шаблон
  гілки, на що чекати); вони зберігаються у файлі робочого процесу.
- **Проблеми** перелічує, що у визначенні не так (батьківська гілка, якої не існує,
  зламаний шаблон).
- Смуга, закріплена внизу сторінки, показує **● Не збережено** (або **Без змін**).
  **Зберегти у спільний файл** записує чернетку в `.gitpoulpi/workflow.toml`
  (зробіть його commit), зберігаючи ключі, яких ця версія не знає, і вбудовує в нього
  ваше власне перевизначення. **Лише для мене** зберігає лише відмінність від
  спільного файлу у вашому стані репозиторію (`.gitpoulpi/repo-state.toml`, не
  комітиться). **Відкинути зміни** знову читає збережене. Якщо закрити Налаштування з
  незбереженою чернеткою, програма спершу спитає.

### Бічна панель

LOCAL і REMOTE групуються за робочим процесом: спершу базові гілки, кожна з
позначкою `[базова]` (`[базова, захищена]`, коли захищена), потім по одній папці на
тип гілки з назвою за її підписом і кількістю гілок (`Feature (3)`), потім гілки,
яких не займає жоден тип, у розділі `Інші`. Папки згортаються, як і будь-які
папки; звичайні дерева повертаються через *Flow > Групувати гілки за типом* (рядок
меню Flow) або команду палітри `Flow: перемкнути групування гілок`. Наведення на
гілку показує її тип, батьківську гілку і наскільки вона позаду (і попереду)
батьківської.

### Меню Flow та його діалоги

Кнопка **Flow** на панелі інструментів (`Ctrl+G Shift+W`, палітра `Flow: відкрити меню`)
перелічує *Почати <Тип>...* для кожного типу гілки, *Завершити поточну гілку...*,
*Синхронізувати з батьківською...*, *Просунути...* (гілки середовищ GitLab Flow),
*Задати батьківську...*, перемикач групування та *Налаштування робочого процесу...*.
Палітра має ті самі команди (`Flow: почати Feature...` створюється для кожного
типу).

- **Почати** - це форма, побудована за шаблоном назви типу: поле на кожен токен.
  `{issue}` і `{issue_key}` мають випадаючий список issue прив'язаного трекера, який
  також заповнює `{slug}` із заголовка issue; `{version}` пропонує версію після
  вашого найвищого tag'а релізу; `{user}` - це ваш активний профіль; `{date}` -
  сьогодні. Рядок показує назву гілки, яку дає шаблон (або чому не може: недійсний
  ref, назву вже зайнято). *Почати з* - випадаючий список (спершу батьківська гілка
  типу), а *Опублікувати* робить push нової гілки.
- **Завершити**, **Синхронізувати**, **Просунути** і **Задати батьківську** питають
  те, що їм потрібно, потім показують **попередній перегляд**, який обчислює демон
  (той самий план, що виводить `gitpoulpi flow ... --dry-run`): кожен крок по
  порядку, попередження (ціль позаду свого remote, гілки, побудовані на цій) і
  **перешкоди** (ціль, якої не існує, ціль позаду свого remote), які вимикають
  кнопку виконання й кажуть чому. Кроки, які не можна повернути (push, видалення
  віддаленої гілки, merge request), позначені `!` і підсвічені, з рядком «Скасування
  не поверне: ...». Хуки, що виконувалися б, перелічені під попередженням, із
  прапорцем *Виконати хуки* (типово вимкнено). Коли режим завершення типу - `ask`,
  Завершити спершу питає *Завершити через*: злити локально чи відкрити pull або
  merge request.
- Потім дія виконується з позначкою на кожен крок (індикатор після 150 мс), а діалог
  показує, як пройшов кожен крок. Уся дія - **один запис скасування**: `Ctrl+Z`
  одразу повертає start, finish, sync чи promote (Історія скасувань читається як
  `Flow finish feature/login`); push'і, віддалені видалення та merge request'и
  лишаються, як і казав попередній перегляд.
- **Конфлікт** зупиняє дію з кнопками **Продовжити** і **Перервати**. Діалог можна
  закрити, щоб вирішити конфлікт звичайними інструментами конфліктів, потім знову
  відкрити командою палітри `Flow: продовжити або перервати зупинену дію...` (це
  також рядок меню Flow, поки дія зупинена); Продовжити відмовляє, доки файли ще в
  конфлікті, і зберігає обидві кнопки. Перервати повертається на гілку, з якої
  почалася дія; уже виконані кроки лишаються (undo їх повертає).
- Завершення через **merge request** робить push гілки, потім відкриває звичайну
  форму *Створити pull request* (*Створити merge request* у GitLab) із
  попередньо заповненими полями: ціль - батьківська гілка, заголовок береться з
  гілки (і issue). Кнопки метаданих (виконавці, рев'юери, мітки, віха) працюють, як
  у будь-якому pull request. Коли жодна інтеграція не відповідає за remote, натомість
  у браузері відкривається URL порівняння (і показується в рядку стану).
- Тексти кроків і перешкод англійські, як і в CLI; власний текст діалогу
  перекладено. Робоче дерево зі змінами підпорядковується налаштуванню `auto-stash`.

Кожен із цих елементів досяжний з клавіатури й палітри, а кожен випадаючий
список - це combobox (Enter відкриває, набір фільтрує, Enter вибирає).

Рядки під керуванням хоста (*Нове issue типу <Тип>...*, *Підхопити гілку, створену
хостом...*) описано [вище](#потоки-під-керуванням-хоста-в-застосунку).
