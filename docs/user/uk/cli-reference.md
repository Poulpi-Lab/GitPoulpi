# Довідник CLI

`gitpoulpi` без підкоманди відкриває вікно; з підкомандою це git-клієнт, яким можна
керувати зі скриптів. Кожна команда працює через той самий фоновий демон, що й вікно,
тож зміна зі скрипта одразу з'являється у відкритому GitPoulpi. Інструменти MCP, які
отримує агент, генеруються з цих самих команд ([MCP та агенти](mcp-and-agents.md)).
`gitpoulpi <command> --help` показує всі прапорці.

## Глобальні прапорці

| Прапорець | Дія |
|---|---|
| `--json` | Вивести результат у JSON. Помилки теж у JSON: `{"error": "..."}` у stdout, код завершення 1. Невдала операція git додає `"detail": {"operation", "command", "exit_code", "stderr"}` (виконану команду git із замаскованими секретами, її код завершення та кінець її stderr; для вбудованої бібліотеки git `"git2": {"class", "code", "message"}`), а збій, який демон зміг назвати, додає `"context": {"operation", "label", "args", "repo", "frontend", "request", "job"}` (операція, її назва для людини, її основні аргументи із замаскованими секретами, репозиторій, хто запитав, id запиту і, для fetch чи push, номер його завдання); інструменти MCP повертають той самий об'єкт. Без `--json` рядки йдуть у stderr. |
| `--repo <path>` | Репозиторій, з яким працювати (типово той, що містить поточну папку, як у git). |
| `-s, --session <name>` | Сесія (демон), з якою працювати. Типово виводиться з кореня репозиторію, тож усе, що відкрито в одному репозиторії, ділить один демон, а два репозиторії мають два. |
| `--backend git2\|system` | Бекенд для демона, який запускає ця команда (демон, що вже працює, залишає свій). |
| `--cwd-file <file>` | Куди вікно записує папку активної вкладки при виході (використовує `shell-init`). |
| `-a, --add [path]`, `--no-raise` | Відкрити папку новою вкладкою вже запущеного GitPoulpi замість запуску ще одного; див. [Додати папку до відкритого вікна](#додати-папку-до-відкритого-вікна). Підкоманд не приймає. |
| `-l, --lang <lang>` | Мова лише тексту `--help`: `en`, `fr`, `es`, `pt-BR`, `pt-PT`, `it`, `de`, `zh-CN`, `ja`, `ko`, `ru`, `uk`, `pl`, `cs`, `nl`, `sv`, `tr`. Див. [Перекладена довідка](#перекладена-довідка). |

### Додати папку до відкритого вікна

`gitpoulpi --add [path]` (`-a`; `gp -a` і псевдонім команди `gpa` виконують той самий
код) відкриває `path` (типово поточну теку, зведену до репозиторію, що її містить) новою вкладкою
вже запущеного GitPoulpi, тож тека, у яку ви перейшли командою `cd` у терміналі, не
запускає друге вікно.

- *Запущена сесія* - це та, чий демон відповідає і до якої підключено вікно GitPoulpi. Вікна,
  де вимкнено **Дозволити ШІ-агентам керувати виглядом**, себе не оголошують і не знаходяться (те саме
  обмеження має `gitpoulpi launch`).
- Одна запущена сесія: вона отримує вкладку (або показує вкладку, якщо цей репозиторій уже відкрито), її вікно
  виходить на передній план, якщо стільниця це дозволяє (Windows, WezTerm, Hyprland; `--no-raise` це пропускає),
  а рядок повідомляє, яка сесія її отримала.
- Кілька: команда виводить їх нумерованим списком із кількістю вкладок і назвами репозиторіїв; введіть номер і Enter
  (порожній рядок або Esc, потім Enter скасовує, код завершення 130). Без терміналу на stdin команда
  завершується помилкою й радить вказати `--session NAME`. `-s NAME` пропускає запитання.
- Жодної (або `-s NAME` називає сесію, яку не запущено): GitPoulpi запускається як звичайно в цьому терміналі, у цій
  теці, точно як `gp [path]`.
- Вікно застосовує це одразу, як ваш власний вибір (без чипа підтвердження, без позначки агента), крім випадку, коли ви
  вводите щось у формі: тоді вікно пропонує вкладку в чипі рядка стану, а код завершення дорівнює 3. Тека,
  що не лежить у репозиторії, відхиляється (код 1).

`--json` виводить один об'єкт: `{"action": "joined", "session", "repo", "already_open", "raised", "outcome": {...}}`
(`outcome` - відповідь вікна, як для `ui show`) або `{"action": "cancelled"}`; помилки мають вигляд `{"error": "..."}`.
Коди завершення: 0 вкладку відкрито, 3 запропоновано в чипі, 1 відхилено або збій, 130 скасовано. Інструмента MCP для цього
немає: агент, що хоче показати вам репозиторій, використовує `ui show tab`.

### Перекладена довідка

`gitpoulpi --help` англійською. Додайте `-l`, щоб читати пояснення іншою мовою:
`gitpoulpi -l fr --help`, `gitpoulpi -l de commit --help`. Перекладено лише пояснення
та заголовки розділів. Назви команд, прапорці, назви значень і можливі значення не
змінюються, тож скрипти й агенти бачать той самий інтерфейс. Мова довідки не береться
із середовища: вивід змінюється, лише коли ви вказуєте `-l`. Описи інструментів MCP
завжди англійською.

Ревізії приймають усе, що приймає git (`HEAD~2`, гілку, tag, короткий sha).
Hunk'и та рядки нумеруються так, як їх нумерує `gitpoulpi --json diff`.

## Команди

**Перегляд**

| Команда | Що робить |
|---|---|
| `status` | Файли в індексі, поза індексом, невідстежувані та з конфліктами. |
| `log [--graph] [--limit N] [--skip N] [--path P] [--count]` | Історія; `--skip` + `--limit` розбивають її на сторінки, `--path` дає історію файлу. `--count` виводить лише `{"total": N}` - кількість комітів, які охоплює обхід (`--limit` і `--skip` ігноруються), тобто число після скісної риски в рядку стану TUI (`500 / 2500 commits`). |
| `log --format mermaid [--detail structure\|refs\|subjects\|full] [--orientation lr\|tb] [--fence] [--range A..B] [--limit N] [--subject-width N]` | Commit'и як скрипт Mermaid `gitGraph`, той самий, що створює вікно [Копіювати як Mermaid gitGraph](log-and-history.md#копіювання-commitів-як-mermaid-gitgraph) у Log. `--range A..B` - це `git log A..B` (голе `A` означає `A..HEAD`); інакше перші `--limit` commit'ів (типово 30). Деталізація, напрямок і огорожа типово беруться з `ui.mermaid_*`. З `--json`: `{format, detail, commits, text}`; звичайний вивід - це скрипт. |
| `diff [--staged] [--path P] [--name-only]` | Diff робочого дерева (або індексу) у вигляді hunk'ів і рядків; `--name-only` перелічує лише змінені файли та їхній статус. |
| `diff --from <rev> [--to <rev\|worktree>] [--name-only]` | Порівнює дві ревізії або ревізію з робочим деревом (`--to` типово `worktree`: зміни staged і unstaged у відстежуваних файлах). Той самий список, що й [порівняння](log-and-history.md#порівняння-commitів) у Log. |
| `show <path> [--at REV \| --staged \| --worktree] [--raw [--output FILE]]` | Вміст файлу в ревізії, в індексі або на диску. Зображення має `image: {format, width, height}` у `--json` (читається з його заголовка). `--raw` записує точні байти в stdout або в `--output FILE` (вказівник LFS дає свій локальний об'єкт). Недоступно через MCP. |
| `blame <path> [--at REV]` | Хто змінив кожен рядок. Враховує перейменування цілих файлів. Кожен рядок несе свій commit, час автора й коміттера, `orig_path` (назву файлу в цьому commit'і) і `previous` (`[батько, шлях]`: де повторити blame, щоб побачити рядок до цього commit'у; відсутній у рядка, що з'явився в кореневому commit'і або в commit'і, чий батько не має файлу). |
| `file-history <path> [--at REV] [--skip N] [--limit N]` | Commit'и, що змінили файл, найновіші першими, **з урахуванням перейменувань** (`git log --follow`). Кожен запис містить commit, батьків, автора, час автора й коміттера, опис, `path` файлу в цьому commit'і, `change` (`Added`, `Modified`, `Deleted`, `{Renamed: {from}}`) і кількості рядків `added`/`removed` (null для двійкового файлу). `--limit` типово 100; `more` каже, чи є старіші записи; `--skip` + `--limit` розбивають на сторінки. Merge перелічується, лише якщо відрізняється від кожного з батьків, з числами відносно першого батька. На відміну від `log --path`, перейменування не обриває історію. |
| `conflicts list [--names-only]` | Файли з конфліктами з текстом їхніх трьох сторін; `--names-only` - дешевий перелік (шлях, тип, oid'и стадій). |
| `conflicts show <path> [--conflict N]` | Один файл із конфліктом: підписи панелей, три сторони, пронумеровані області конфліктів A/B (`--json` - повний документ). |
| `conflicts resolve <path> --side ours\|theirs\|base` | Вирішити файл однією стороною (`--ours` / `--theirs` - скорочення). |
| `conflicts resolve <path> --both [--theirs-first]` | Залишити обидві сторони кожного конфлікту (A, потім B, або B, потім A). |
| `conflicts resolve <path> --pick 1=a,2=ba [--default a\|b]` | Вибір для кожного конфлікту: `a` ours, `b` theirs, `ab`, `ba`, `none`. Відхиляється з `pick_incomplete`, якщо вибір є не для кожного конфлікту й не задано `--default`. |
| `conflicts resolve <path> --content-file F\|- [--encoding L]` | Записати наданий остаточний текст (UTF-8 або в кодуванні `L`). |
| `conflicts resolve <path> --delete` | Прийняти видалення (конфлікти видалено/змінено): `git rm`. |
| `conflicts resolve ... [--no-stage] [--expect base,ours,theirs]` | `--no-stage` зберігає без позначення вирішеним; `--expect` - захист від застарілого стану (oid'и стадій, `-` для відсутньої). |
| `conflicts unresolve <path>` | Повернути в стан конфлікту файл, вирішений під час цієї операції. |
| `conflicts check` | Чи конфліктуватиме злиття HEAD у гілку, від якої його створено? `{"status": "conflicts"\|"clean"\|"no-base"\|"disabled", "head", "base_ref", "base", "base_source": "globs"\|"pull-request", "files": [...]}`. Злиття в пам'яті (у робочому дереві, індексі та refs нічого не змінюється; потрібен git 2.38 або новіший із системним бекендом, інакше `disabled`). Лише читання; те саме робить інструмент MCP `conflicts_check`. Див. [Вирішення конфліктів merge](merge-conflicts.md#запобігання-конфліктам). |
| `conflicts state` | Поточні merge, rebase, cherry-pick або revert (`null`, якщо немає). |
| `conflicts abort` | Перервати цю операцію (руйнівно: відкидає вирішення, зроблені відтоді). |
| `conflicts skip` | Пропустити поточний cherry-pick або revert (або commit, на якому зупинився rebase): HEAD, індекс і робоче дерево повертаються до HEAD. Вихід із порожнього; у merge нема чого пропускати (руйнівно, не скасовується). |
| `conflicts am-continue` | Продовжити поточний `git am` після того, як ви вирішили й додали в індекс файли патча (`{"outcome":"Completed"}` або `"Stopped"`). |
| `conflicts am-skip` | Пропустити патч, на якому зупинився `git am`. |
| `conflicts am-abort` | Перервати `git am` (руйнівно: гілка повертається до стану перед `am`). |
| `job list` | Фонові завдання демона, найстаріші першими: кожні fetch, push, pull, clone і передача LFS стають завданням, щойно запит отримано (у черзі, виконується або завершено протягом останніх 30 с). JSON: id, kind, state, phase, progress, `not_cancellable`, `error`. |
| `job cancel <id>` | Зупинити завдання. Відхиляється (код виходу 1, нічого не змінюється), коли безпечно зупинити вже не можна. Ctrl+C у команді, що запустила завдання, скасовує це завдання. |
| `job wait <id> [--timeout S]` | Чекати завершення завдання й вивести його підсумковий стан; код виходу 0 для `Done`, 1 для помилки, скасування чи перевищення часу. |
| `index-lock show` | `index.lock` репозиторію (`null`, якщо немає): шлях, вік у секундах, `stale` (старший за 10 с). |
| `index-lock remove` | Видалити застарілий `index.lock`. Відхиляється, поки він молодший за 10 с або коли його немає. |
| `rebase-plan [<upstream>] [--root]` | Commit'и, які відтворив би інтерактивний rebase, від найстарішого. |

**Staging і commit**

| Команда | Що робить |
|---|---|
| `stage --file F \| --folder D \| --all [--hunk N [--lines a,b]] [--allow-sensitive]` | Додати в індекс файл, папку, усе, hunk або окремі рядки. Додавання файлу, папки чи `--all`, що додало б чутливий файл (приватний ключ, `.env`, розпізнаний токен: `[privacy]` у [довіднику конфігурації](config-reference.md#privacy-чутливі-файли)), відхиляється з кодом виходу 2 і `{error: "sensitive_files", files: [{path, reason}]}` (правило й замаскований попередній перегляд, ніколи значення); нічого не додається. `--allow-sensitive` усе одно додає їх. |
| `stage --paths A B ...` | Додати в індекс кілька файлів чи папок як ОДНУ операцію: один запис журналу, один крок `undo` (перейменований файл - це його старий і новий шлях, як `status` показує `renamed_from`). Не поєднується з `--folder`, `--hunk`, `--lines` чи `--all`. |
| `unstage` (ті самі прапорці, зокрема `--paths`) | Навпаки. |
| `discard --file F [--hunk N [--lines a,b]]` | Відкинути зміни поза індексом (для цілого файлу: усі зміни, невідстежуваний файл видаляється, а також папки, що через це стають порожніми). Можна скасувати. |
| `rm-file <paths>...` | Видалити файли з робочого дерева. Можна скасувати. |
| `ignore <pattern> [--file <.gitignore>]` | Додати шаблон у `.gitignore` (або в `.git/info/exclude` через `--file .git/info/exclude`). Можна скасувати, крім запису в `.git/info/exclude`. |
| `convert <paths>... (--encoding <name> \| --eol lf\|crlf\|cr \| --indent spaces:<n>\|tabs:<n>)` | Переписує кодування, закінчення рядків або відступи файлів робочого дерева. Двійкові, відсутні та такі, що не кодуються, файли пропускаються й перелічуються у звіті. Один запис скасування на всю партію. |
| `treat binary\|text <paths>... [--extension \| --folder] [--file <.gitattributes>]` | Змушує git вважати файли двійковими (`binary`) або текстовими (`text diff`), записуючи правило `.gitattributes`, типово в кореневий файл. Можна скасувати, крім запису в `.git/info/attributes`. |
| `commit -m <msg> [--amend] [--no-verify]` / `commit --ai` | Commit; `--ai` пише повідомлення вбудованим ШІ. Хуки репозиторію `pre-commit` / `commit-msg` виконуються, доки `--no-verify` їх не пропустить (саме це позначено за замовчуванням у «Пропускати хуки git» в Налаштування > Commit). |
| `split-source <commit>` | Зміни commit'у, пронумеровані для розділення: `{commit, parent, message, files:[{path, status, whole_only, hunks:[{id, lines:[{origin, content}], ...}]}]}`. Файли з `whole_only` (binary, mode_only, added, deleted, submodule, lfs) можна призначити лише цілком. Лише читання. |
| `split-commit <commit> --plan <file\|-> [--rest-message M] [--sign] [--dry-run]` | Розділяє commit поточної гілки на кілька, від найстарішого. План: `{"parts":[{"message":"feat: parser","pieces":[{"path":"src/parse.rs","hunk":0},{"path":"src/parse.rs","hunk":1,"lines":[2,3]},{"path":"logo.png"}]}]}`; елемент без `hunk` - це весь файл, `lines` - індекси в `lines` hunk'а. Кожну зміну потрібно призначити рівно один раз; `--rest-message` кладе все, що план не призначив, в останній commit. Останній новий commit зберігає початкове дерево, тож нащадки, індекс і робоче дерево не змінюються; для надісланого commit'у потім потрібен force push, а підписи в переписаному діапазоні відкидаються, якщо не вказано `--sign`. Виводить `{created, previous_head, new_head, replayed}`; один `undo` повертає все. `--dry-run` виводить `{dry_run, valid, refusal, parts, unassigned}` і нічого не змінює. Відмова виводить `{"refused":{reason, message, unassigned}}` з кодом виходу 2. |

Скрипт без довіри відхиляється як `script_not_trusted` з `refused.script = {hash}` і ніколи не запускається, навіть `script check`, який повідомляє `{trust: "untrusted", hash}` з кодом завершення 2; для скрипту з довірою `script check` запускає його один раз із вигаданим комітом (`"dry_run": true`), щоб перевірити відповідь, і виводить ще й `interpreter`. Сервер MCP не вміє довіряти: у ньому немає інструмента `rewrite script trust` і аргументу `trust`, тож агент може запускати лише скрипт, якому раніше довірила людина. `scan-secrets` один раз читає історію області (поточна гілка, `--all-local` або `--ref`) і виводить `{findings: [{id, rule, path, more_paths, first_commit, last_commit, commits, blobs, preview}], commits, blobs_scanned, blobs_skipped_binary, blobs_skipped_large}`: правило, що спрацювало (префікси токенів, приватні ключі, JWT, паролі в URL, рядки `password = value`, схожі на випадкові), прихований `preview` на кшталт `ghp_****abcd` і ніколи саме значення; пошук не вичерпний і лише читає. `analyze` - аналіз розмірів (як `filter-repo --analyze`): один прохід історією області, що виводить `{blobs, folders, deleted, top, commits, blobs_total, bytes_total, disk_total, bytes_in_head, bytes_history_only, deleted_paths, blobs_cut, folders_cut, deleted_cut}`. `blobs` - це `--top` (типово 50, не більше 5000) найбільших унікальних blob, найбільші першими, кожен `{path, more_paths, blob, size, disk_size, first_commit, last_commit, state}` (`state` - `in_head`, `replaced` для старої версії файлу, що досі є в HEAD, або `deleted`; `last_commit` - коміт, що його видалив, інакше той, що додав; `disk_size` - розмір у базі об'єктів, пакована дельта рахується як дельта); `folders` - `{path, size, blobs, in_head}` (байти унікальних blob, будь-коли збережених під папкою); `deleted` - шляхи, що зникли з HEAD, але історія їх досі тримає, `{path, versions, size, first_commit, last_commit}`. `bytes_history_only` - те, що звільнило б видалення всього, що тримає лише історія, приблизно й лише після очищення старих об'єктів та gc; команда лише читає й ніколи не змінює ref. Перетворіть рядок на правило через `--remove-path PATH` (або папку) чи `--remove-blobs-over BYTES`. `--remove-finding ID` (можна повторювати, або `all`) додає правило, що прибирає ці знахідки з кожного коміту: демон шукає в тій самій області ще раз і сам зіставляє id, тож значення ніколи не потрапляє в командний рядок, рецепт чи журнал. Секрет, що потрапив на remote, уже витік: спершу замініть його. Секрети ніколи не потрапляють у командний рядок чи збережений рецепт: `--secrets-file F` (по одному на рядок) заповнює правила секретів `content_replace` у рецепті й ніколи не виводиться. Коди завершення: 0 - виконано; 1 - помилка (нечитабельний рецепт, хибні прапорці); 2 - відмова, що виводиться як `{"refused":{reason, message, detail}}` з причиною `stale` (хибний digest, невідомий запуск, ref змінився після перегляду), `no_rule`, `invalid_rule`, `empty_scope`, `shallow`, `signature_choice_needed`, ...; 3 - план переміщує ref, які вже на remote, а `--yes` не вказано, виводиться як `{"needs_confirmation":{prompt}}`, нічого не змінено (`run` також відкидає свій перегляд). |

| Команда | Що робить |
|---|---|
| `autostash start-over [--dry-run] [--yes]` | За наявного відкладеного auto-stash: відкинути зміни у файлах stash'а (копія зберігається в `refs/gitpoulpi-backup/`), скасувати операцію, що зробила auto-stash, повернути stash на початковий commit. Віддалені гілки стеження, які видалив remote, очищаються, якщо `general.auto_prune` не вимкнено; `--prune` примусово вмикає це. Кожен fetch також оновлює відомості про tag'и кожного remote (`remote` у `tag list`) і чистить цей запис навіть без `--prune`. `--prune-tags` (Налаштування: Автоочищення tag'ів) видаляє ще й локальні tag'и, які видалив remote: лише ті, що були на ньому, і ніколи не той, якого ви не надсилали; відповідь перелічує їх як `pruned_tags` (git 2.41+). |

| `push --all-targets\|--to <remote>[:<dst>]... [--branch B] [--resolve REMOTE=push\|ff\|merge\|rebase\|force\|skip]... Спершу складає план (remote опитуються, див. `remote-group plan`). Код 0: на кожен remote push виконано, він актуальний або пропущений; 4: якийсь remote завершився помилкою, відхилив push, невідомий або його не пробували, або merge чи rebase зупинився на конфліктах (`stopped`); 2: відмова (`remote_group_pending`: чекає збережений запуск, `detached_head`, `checked_out_elsewhere`, `bad_resolve`, `action_not_allowed`). Розбіжний remote типово отримує rebase замість merge, коли `git.pull_mode` дорівнює rebase. Без цих прапорців `push` не змінюється. |

Без демона; їх викликають інсталятори. |

Недоступна агентам MCP. |

| `mcp serve --stdio \| --http [ADDR] [--allow-remote] [--ui-control auto\|ask\|off]` | Сервер MCP ([MCP та агенти](mcp-and-agents.md)). ### Робочі простори та пошук

**Робочий простір** - це іменована група репозиторіїв, за потреби з типовим профілем
commit'ів. Він лежить у `workspaces.toml` поруч із `config.toml`, спільний для всіх
сесій і для вікна, тож команди `workspace` не запускають демона (лише `add` і
`create --add` питають його про URL `origin` кожного репозиторію). Репозиторій може
входити до кількох робочих просторів. Шляхи порівнюються так само, як в обраному й
у списку нещодавніх.

| Команда | Що робить |
|---|---|
| `workspace list`, `workspace show <id>` | `{workspaces: [...]}` / `{workspace}`: `id` (слаг, стабільний при перейменуванні), `name`, `color`, `description`, `profile`, `profile_exists` і `repos: [{path, exists, remote}]` (`remote` - URL `origin`, записаний під час додавання репозиторію, без облікових даних). |
| `workspace create <name> [--add PATH]... [--profile ID] [--color C] [--description T]` | Створює робочий простір і виводить його; два робочі простори не можуть мати однакову назву. `--add` можна повторювати, і це не `--repo`, що вибирає репозиторій, у якому виконується команда. |
| `workspace rename <id> <name>`, `workspace delete <id>` | Перейменування зберігає id. Видалення ніколи не зачіпає репозиторії. |
| `workspace add <id> <path>...`, `workspace remove <id> <path>...` | `add` записує корінь і URL `origin` кожного репозиторію (шлях, якого не існує або який не всередині репозиторію, відхиляється з повідомленням, і нічого не зберігається: лише репозиторій, що зник пізніше, лишається в списку з позначкою «відсутній»); `remove` приймає й шлях репозиторію, якого вже немає на диску. |
| `workspace set-profile <id> <profile>` / `--none` | Id із `[[profiles]]`, від імені якого роблять commit'и в репозиторіях робочого простору. Id, що не називає жодного профілю, зберігається (`profile_exists: false`) і не діє. |
| `workspace set-ai-instructions <id> [--action <a>] [--mode append\|replace] (--text T \| --clear)` | Інструкції ШІ робочого простору для кожної дії або для однієї (`commit_message`, `code_review`, ...). `append` додає їх після глобальних, `replace` використовує замість них. Вони діють для кожного репозиторію робочого простору, перед власними інструкціями репозиторію. `workspace show` друкує їх як `ai_instructions`. |
| `commit -m M [--workspace ID]` | Робить commit від імені профілю робочого простору, коли репозиторій у ньому й профіль існує; інакше `general.active_profile`; інакше власна особа репозиторію. Без `--workspace` (або `GITPOULPI_WORKSPACE`) нічого не змінюється: commit ніколи не вгадує робочий простір за членством, бо репозиторій може бути в кількох. Невідомий id - помилка. |
| `search <query> [--workspace ID] [--kind K]... [--limit N]` | Нечіткий пошук за гілками (локальними й віддаленими), tag'ами, worktrees, stash'ами, повідомленнями commit'ів, а також запитами на злиття та issues з кешів хостингу, у поточному репозиторії чи в усіх репозиторіях робочого простору (`GITPOULPI_WORKSPACE` замінює прапорець). Версія для вікна - [Пошук](search.md). |

`search` відповідає `{query, workspace, hits, partial, repos}`. Кожен збіг - це
`{kind, label, detail, target, score, positions, repo}`: `kind` - `branch`, `tag`,
`commit`, `stash`, `worktree`, `repo`, `pull_request` або `issue`; `positions` - символи
`label`, що збіглися, для підсвічування; `target` каже, куди перейти
(`{type: "ref", name}` з повною назвою ref, `{type: "commit", id}`,
`{type: "stash", index, id}`, `{type: "worktree", path}`,
`{type: "repo", path}`, `{type: "pull_request", number}`, `{type: "issue", number}`);
збіги зливаються по репозиторіях за `score`, найкращі першими. Збіг - як у палітри
команд: запит дослівно, потім дослівно будь-де, потім його символи по порядку
(раніші й коротші перемагають). Тіло commit'у шукається лише тоді, коли тема не
збігається, а запит має три символи чи більше. Префікс звужує пошук і не є частиною
тексту: `b:` гілки, `t:` tag'и, `c:` commit'и, `s:` stash'і, `w:` worktrees, `r:`
репозиторії (лише для робочого простору), `pr:` (або `mr:`) запити на злиття, `i:`
issues, `#` обидва останні; `--kind` (можна повторювати, ті самі назви) теж фільтрує.
`partial` істинне, коли commit'и репозиторію обрізано на
[`search.commit_limit`](config-reference.md#search-пошук-у-робочому-просторі); `repos`
каже для кожного репозиторію, чи його переглянуто (`reason`, коли ні: шлях, якого
немає на диску, повідомляється й ніколи не фатальний). Одноразова команда спершу
будує індекс кожного репозиторію; коли вікно відкрите на тій самій сесії, демон його
вже має теплим. Запити на злиття та issues читаються з кешу хостингу кожного
репозиторію (файл, який веде вікно в `.gitpoulpi/hosting-cache.json`) і ніколи з
хостингу: репозиторій, чиє вікно їх ніколи не завантажувало, не має що знаходити, а
відсутній чи недописаний кеш - це просто відсутність збігів.

**Показ у відкритому вікні** (`ui`; кожна команда також приймає
`--viewer <id>` і `--launch`)

| Команда | Що робить |
|---|---|
| `ui viewers [--all-sessions]`, `ui state [--text]` | Відкриті вікна; що показує одне з них. |
| `ui show commit <rev> [--also R] [--files] [--focus refs\|log\|status]`, `ui show ref <name>`, `ui show pr <n> [--view details\|conversation]`, `ui show issue <n> [--view details\|conversation]`, `ui show wip [path] [--staged] [--composer]` | Вибрати щось. |

## Нотатки

- **Сесії.** `gitpoulpi session list` показує кожну сесію з `live` / `stale`
  (визначається підключенням до її порту). Виведена назва має вигляд
  `<folder>-<hash of the path>`.
- **Жодних інтерактивних запитів.** Нічого не запитується: ризиковані операції
  або потребують прапорця (`--yes`, `--force-with-lease`), або відхиляються з причиною.
- **Немає в CLI**: `checkout --file` (відновити один файл) є лише у вікні.
