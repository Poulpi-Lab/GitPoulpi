# Бесіди

Подання бесіди для issue, робочого елемента, картки або pull / merge request. Потрібні обліковий запис і прив'язаний репозиторій: див. [Інтеграції хостингів і трекерів issues](hosting-integration.md); списки, що її відкривають, описано в [Pull requests та issues](pull-requests-and-issues.md); рев'ю коду - у [Рев'ю pull або merge request](review.md).

**Бесіда** - це все, що сказано про одне issue, робочий елемент, картку, зміну або pull / merge request: опис,
коментарі, рев'ю, обговорення коду й події (мітки, призначення, зміни стану, надсилання). GitPoulpi читає її з
хостингу, показує відформатованою й дає змогу відповісти, не виходячи з вікна.

### Як відкрити

| Звідки | Як |
|---|---|
| Рядок ISSUES | `Enter` або подвійне клацання; пункт меню рядка **Відкрити бесіду**; команда палітри *Хостинг: відкрити бесіду issue...* (список issues на екрані). Пункт меню рядка **Відкрити в браузері** лишає браузер. |
| Рядок PULL REQUESTS в Azure DevOps чи Bitbucket | `Enter` або **Відкрити бесіду**. У GitHub, GitLab, Gitea, Forgejo і Gerrit рядок відкриває [рев'ю](review.md), чия сторінка огляду - це та сама бесіда (хронологія, клавіші й поле коментаря під нею). |
| Картка [дошки issues](pull-requests-and-issues.md#дошка-issues) | `Enter` або подвійне клацання. |
| [Radar](radar.md) | `i` на рядку issue чи запиту, пункт меню рядка **Відкрити бесіду** або *Radar: відкрити бесіду issue*. |
| Посилання в іншій бесіді | Клацніть його (або `l`, а потім виберіть): `#7`, `!12`, `ABC-12` пов'язаного джерела відкриваються в застосунку й кладуться в стек «Назад». |
| Агент | `gitpoulpi ui show issue <n> --view conversation` (також `ui show pr`), див. [довідник CLI](cli-reference.md). |

**Репозиторії, які не клоновано.** Рядок Radar репозиторію, клона якого у вас немає, теж відкриває його бесіду:
поданню потрібні лише профіль інтеграції та проєкт, тож Radar розміщує його у власному вікні, а `Esc` повертає
Radar. Те, що потребує клона, пропущено: посилання на commit відкривається на хостингу замість Log, а «Дати ШІ
читати репозиторій» сіре з причиною (див. [розділ про ШІ](ai.md#допомога-в-написанні-на-хостингу)). Запит
клонованого репозиторію має замість цього рев'ю (`e`), а **Відкрити бесіду** в Radar каже, що для нього тут немає
бесіди для читання; issue клонованого репозиторію відкриває її на вкладці цього репозиторію.

Issue хостингу, який їх не має для читання (у Bitbucket і Gerrit немає issues), відкриває браузер, як і раніше, і
збірка без функції `conversation` робить те саме скрізь ([власні збірки](custom-builds.md)).

### Подання

Подання на все вікно: заголовок (стан, хто й коли відкрив, мітки, кількість коментарів, **Показати події**,
**Назад**, **Оновити**, **Відкрити в браузері**), рядок **Публікація від**, часова шкала, а під нею поле коментаря.

![Бесіда issue #7: опис із посиланням на #9, два коментарі, подія мітки, показана через Показати події, і порожнє поле Новий коментар із Запис, Перегляд і Поруч](../images/issue-conversation.png)

![Сторінка Огляд merge request !58: опис, нерозв'язане й розв'язане обговорення коду з посиланнями на файл і рядок, коментарі, Відповісти й Цитувати на вибраному обговоренні та поле коментаря](../images/pr-conversation.png)

- Часова шкала читається від найстарішого до найновішого й починається з найновішого вікна (не більше 300 записів).
  **Завантажити старіші** вгорі (`m`, команда палітри *Бесіда: завантажити старіші записи*) читає попереднє вікно,
  показуючи, скільки ще лишилося, коли хостинг це повідомляє.
- Коментар показує автора, дату, мітку `змінено`, мітку `бот` для ботів, `внутр.` для приватних нотаток і кнопки
  **Відповісти**, **Цитувати**, **Змінити**, **Видалити** та **Посилання**, які дозволяє вибраний запис.
  Обговорення коду показує `path:line`, `вирішено` або `не вирішено`, `застаріло` та свої коментарі. Рев'ю
  показує свій вердикт.
- Події - це по одному приглушеному рядку (*carol додав(ла) мітку lfs*). **Показати події** (`v`) їх ховає; вибір
  зберігається для кожного репозиторію. Хостинги без історії подій (YouTrack, робочі елементи Azure DevOps,
  локальні нотатки) такого прапорця не мають.
- Текст показується як Markdown: заголовки, вкладені списки й списки завдань, цитати, сповіщення в стилі GitHub,
  підсвічений код, таблиці, посилання, зображення як `[image: alt]`. Текст, що надійшов у власній розмітці
  хостингу, спершу перетворюється (див. [Перетворення розмітки](#перетворення-розмітки)). Блок коду `mermaid`
  отримує кнопку **Відкрити діаграму**, що показує джерело діаграми в переглядачі з прокруткою (`Enter` його
  копіює); у палітрі є *Бесіда: відкрити діаграму запису*. Потрібна збірка з `conversation` і `mermaid`.
- В Огляді рев'ю `path:line` обговорення коду - це посилання на код (`G`, *Бесіда: відкрити код обговорення*;
  див. [Рев'ю](review.md)); у бесіді, відкритій окремо (задача, рядок Radar), сторінки коду немає.
- Подання читає дані знову кожні 60 секунд і за `F5` (**Оновити**).

**Клавіші.** Кожна має кнопку, пункт меню або рядок палітри (*Бесіда: ...*), а `Ctrl+N` позначає кнопки номерами.

| Клавіша | Дія |
|---|---|
| `Вгору`, `Вниз`, `Ctrl+J`, `Ctrl+K`, `j`, `k` | Попередній / наступний запис |
| `PageUp`, `PageDown`, `Home`, `End`, колесо, смуга прокрутки | Прокрутка |
| `Tab`, `Shift+Tab` | Часова шкала, поле коментаря, а потім кнопки заголовка |
| `r` | Відповісти: в обговорення вибраного запису або з цитатою його тексту, коли хостинг не має обговорень |
| `Q` | Процитувати вибраний запис у новому коментарі |
| `c` | Новий коментар |
| `e`, `d` | Змінити, видалити один зі своїх коментарів (перед видаленням є запитання) |
| `l`, `Enter` | Посилання запису: `Enter` переходить за єдиним або відкриває їхнє меню |
| `y`, `o` | Копіювати адресу запису, відкрити її в браузері |
| `n` | Наступний непрочитаний запис |
| `v`, `m`, `F5` | Показати чи сховати події, Завантажити старіші, Оновити |
| `Alt+Left`, `Backspace` | Назад по стеку «Назад» |
| `q`, `Esc` | Закрити (спершу питає, коли в полі є текст) |

### Написання

**Новий коментар** (`c` або `Tab` до поля), **Відповісти** (`r`), **Цитувати** (`Q`) і **Змінити** (`e`) використовують
один редактор Markdown: **Запис**, **Перегляд** і **Поруч** (`Alt+P` міняє «Запис» і «Перегляд», `Alt+L` вмикає
«Поруч» і потребує вікна завширшки 100 стовпців). `Ctrl+Enter` (також `Ctrl+S` і `Alt+Enter`) або **Надіслати**
публікує, **Скасувати** прибирає поле, а `Alt+E` відкриває **Написати зі ШІ**, коли ШІ ввімкнено ([розділ про
ШІ](ai.md#допомога-в-написанні-на-хостингу)). Перегляд розкладається тим самим засобом відображення, що й часова
шкала, з тими самими посиланнями. Коли хостинг не приймає Markdown, у нижньому рядку названо розмітку, якою
надсилається текст (*Надсилається як Jira wiki markup*, *Надсилається як Textile*).

![Відповідь на issue, що пишеться в поданні Поруч: чернетка Markdown ліворуч, її відрендерений перегляд праворуч і Надіслати](../images/issue-reply-composer.png)

- Коментар одразу додається до часової шкали й займає своє місце, коли хостинг відповість. Якщо хостинг відмовляє,
  запис зникає, а поле відкривається знову з вашим текстом і причиною.
- Ненадісланий текст зберігається для кожного елемента (`remote-conversations.toml` у каталозі конфігурації) і чекає
  там наступного разу, коли ви відкриєте це поле; надсилання чи відкидання його видаляє. Закриття поля з текстом
  спершу питає.
- **Відповісти** в обговоренні (обговорення рев'ю, обговорення GitLab, коментар Linear, обговорення Bitbucket чи
  Azure DevOps) публікує в це обговорення. Де хостинг має лише плоский список, **Відповісти** починає новий коментар
  з процитованим вибраним записом (`> **author**`), так само, як **Цитувати**.
- **Внутрішня нотатка** (прапорець, `Alt+I`): у GitLab і Redmine коментар видно лише учасникам проєкту. Показується
  лише на хостингах, що мають такі нотатки, і лише для нового коментаря.
- Публікація - це дія назовні: нічого не журналюється й **нічого не можна скасувати з GitPoulpi**. Без з'єднання
  поле лишається, **Надіслати** сіре з причиною, а заголовок каже, що показано збережену копію.

**Хто може змінювати чи видаляти.** Лише ваші власні коментарі мають **Змінити** і **Видалити**. Спершу враховується
слово самого хостингу, коли воно є (`viewerCanUpdate` і `viewerCanDelete` у GitHub, `can_edit` в інших), потім ваш
логін порівнюється з автором коментаря без урахування регістру; коментарі бота App мають іще походити з облікового
запису бота. Поки логін бота GitHub App невідомий, враховуються лише коментарі, опубліковані цим встановленням
(репозиторій зберігає їхні id): нічого не вгадується за іменем. В обговоренні **Змінити** і **Видалити** діють на
останній коментар у ньому, що ваш. Хостинг, який не вміє змінювати чи видаляти (див. [таблицю](#чого-не-вміє-кожен-хостинг)),
показує кнопки сірими з причиною.

### Публікація від імені

Рядок під заголовком каже, від чийого імені публікуються ваші повідомлення, і той самий рядок є в кожному полі:

| Рядок | Значення |
|---|---|
| *Публікація від ann (особистий токен)* | Токен профілю: ваш власний логін (`GET /user`). |
| *Публікація від ci-bot (команда токена репозиторію)* | Для API хостингу використовується [команда токена](hosting-integration.md#8-дії-від-імені-бота-github-app) репозиторію. |
| *Публікація від my-app[bot] (бот GitHub App)* | Токен встановлення. Ім'я береться з **Публікувати як**, інакше з хостингу. |
| *Публікація від бота GitHub App (його ім'я поки невідоме: задайте «Публікувати як» у налаштуваннях)* | Ім'я не налаштовано й поки не дізнано. |
| *Публікація від ... (бот проєкту)* | Токен доступу проєкту чи групи GitLab. |
| *Запис від kai (локальна нотатка)* | Папка нотаток Markdown: `local.me` профілю, інакше підключений користувач. |
| *Ім'я, від якого ви публікуватимете, поки невідоме. Задайте «Публікувати як» у налаштуваннях.* | Нічого не вдалося дізнатися. |

**Публікувати як** - це ім'я: для GitHub App це `my-app[bot]`. Задайте його для всіх репозиторіїв у **Налаштування >
Інтеграції > Публікувати як** (`general.hosting_post_as`) або для одного репозиторію в **Налаштування > Налаштування
репозиторію > SSH і облікові дані > Хостинг**, де воно перекриває глобальне. Якщо лишити порожнім, GitPoulpi запитує
GitHub (GraphQL `viewer { login }`, на що токен встановлення може відповісти, а може й ні), а якщо не вийшло,
дізнається ім'я з автора першого коментаря, який опублікує, і зберігає його разом із репозиторієм. Особистому токену
воно ніколи не потрібне. Див. [Дії від імені бота GitHub App](hosting-integration.md#8-дії-від-імені-бота-github-app).

### Перехресні посилання

Посилання в бесіді підкреслені й клікабельні. Спершу зіставляються пов'язані джерела ISSUES і PULL REQUESTS
репозиторію, тож `ABC-12` пов'язаного проєкту Jira відкривається в застосунку навіть у коментарі GitHub; те, що
додає власна граматика хостингу, відкриває його сторінку після підтвердження посилання. Id commit'а відкривається в
Log, коли репозиторій клоновано й id має щонайменше 7 символів, інакше на хостингу. Ніщо всередині фрагмента коду,
блоку коду, посилання Markdown, адреси e-mail чи URL не є посиланням, і `C#1`, `UTF-8`, `SHA-256` та `ISO-8601` теж
не є.

| Хостинг | Розпізнається |
|---|---|
| GitHub | `#7`, `GH-7`, `owner/repo#7`, `owner/repo@sha`, `@login`, id commit'ів |
| GitLab | `#7`, `!7`, `group/project#7`, `group/project!7`, `project#7` (сусідній проєкт), `@user`, `~label` і `%milestone` як мітки-чипи, id commit'ів |
| Gitea, Forgejo | `#7`, `!7`, `owner/repo#7`, `owner/repo@sha`, `@user`, id commit'ів |
| Azure DevOps | `#7`, `!7`, `AB#7`, `@user` |
| Bitbucket | згадки `@user`, `{uuid}`, id commit'ів |
| Gerrit | значення `Change-Id` (`I` і 40 шістнадцяткових цифр), id commit'ів |
| Redmine | `#7`, ревізії `r123`, `commit:abc1234` |
| Jira, Linear, YouTrack | `ABC-12`, лише для проєкту чи команди пов'язаного джерела |
| Trello | адреси карток (`trello.com/c/...`) |
| Локальні нотатки | `[[note]]`, `[[note\|alias]]` і відносні посилання `.md` на іншу нотатку папки |

`gitpoulpi hosting markdown --body T --id I` виводить, що застосунок робить із текстом, разом із посиланнями.

### Перетворення розмітки

Хостинги, що не розмовляють Markdown, перетворюються в обидва боки, тож ви скрізь читаєте й пишете Markdown. Те, що
перетворювач не розуміє, лишається читабельним текстом.

- **Jira** (Cloud і Data Center) зберігає коментарі як вікірозмітку через API v2. Прочитане перетворюється на
  Markdown; написане вами перетворюється на вікірозмітку, а в нижньому рядку стоїть *Надсилається як Jira wiki
  markup*.
- **Redmine** форматує текст як Textile або Markdown, чого API не повідомляє: це GitPoulpi підказує рядок профілю
  **Формат тексту на сервері** (Налаштування > Інтеграції, `markup`, типово Textile). Textile перетворюється на
  Markdown для читання й назад на Textile для запису.
- **Azure DevOps Server** повертає коментарі робочих елементів як HTML і приймає їх як HTML: вони показуються як
  Markdown, перетворений із нього, і записуються як HTML. Azure DevOps Services та обговорення pull request
  приймають Markdown.
- **Gerrit** - це простий текст: він не відображається як Markdown, а написане вами надсилається як набране.
- Кожен імпортер спершу прибирає керівні й escape-послідовності, тож коментар не може зрушити термінал.

### Збережена копія, Завантажити старіші, непрочитане

- Кожна відкрита вами бесіда зберігається (`<каталог стану>/conversations/<інтеграція>/<проєкт>/<вид>-<n>.json`,
  лише для користувача, без токена, не більше 2 МБ на файл, зберігається 50 найновіших файлів). Вона малюється
  одразу, коли елемент відкривається, а оновлюється за нею. Коли хостинг недоступний, збережена копія лишається на
  екрані під *Офлайн: показано копію, збережену 3 хв тому (причина)*, а «Надіслати» сіре.
- **Непрочитане:** те, що ви бачили востаннє, запам'ятовується для кожної бесіди (зберігається 200 останніх).
  Новіші записи від інших отримують смугу акценту й мітку `нове`, а `n` переходить до наступного. Бесіда, яку ви
  відкриваєте вперше, нічого нового не має.

### Чого не вміє кожен хостинг

Кожне «ні» нижче - це справжнє обмеження: елемент схований або сірий із причиною, а CLI відповідає помилкою з
назвою хостингу ще до надсилання будь-чого.

|---|---|---|---|---|---|---|---|
| GitHub | issues, pull requests | pull requests | обидва | pull requests | так | ні | GitHub Markdown |
| GitLab | issues, merge requests | так (обговорення) | обидва | merge requests | так | так | GitLab Markdown |
| Gitea | issues, pull requests | pull requests | обидва | pull requests | так | ні | Markdown |
| Forgejo | issues, pull requests | pull requests | обидва | ні (хостинг не має кінцевої точки) | так | ні | Markdown |

Також: жоден хостинг не дозволяє починати нове обговорення на рядку з бесіди (робіть це в рев'ю), а реакції
показуються лише в GitHub. Текст, довший за той, що приймає хостинг, відхиляється (GitHub 65 536 символів, GitLab
1 000 000, Azure DevOps 150 000, Jira 32 767, Trello 16 384): CLI перевіряє заздалегідь, а в застосунку показується
власне повідомлення хостингу, і ваш текст зберігається. Локальна нотатка зберігає свої коментарі в завершальному
розділі `## Comments` самого файлу нотатки, по одному запису `### author - time`, тож Obsidian і оболонка теж їх
бачать.

У командному рядку ті самі бесіди - це `gitpoulpi hosting issue comments`, `issue comment`, `comment-edit` і
`comment-delete`, а також `hosting review conversation` (див. [довідник CLI](cli-reference.md)); для агентів це
інструменти MCP з тими самими назвами (див. [MCP та агенти](mcp-and-agents.md)).
