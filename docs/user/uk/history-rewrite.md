# Переписування історії

Переписування історії змінює commit'и, які вже існують: хто їх написав і коли,
їхні повідомлення, файли в них, їхні підписи. GitPoulpi робить це за допомогою
**рецепта** (область і впорядкований список правил) та трьох кроків, серед яких
середній ніколи не пропускається:

1. **Перегляд** обчислює нову історію, нічого не чіпаючи: кількості, що зробило
   кожне правило, гілки й tag'и, які переміщуються, по одному рядку на змінений
   commit.
2. **Застосувати** переміщує ваші локальні гілки й tag'и на неї. Це один запис
   [історії скасувань](undo-redo.md): **Скасувати** повертає кожен переміщений ref
   (і файли в робочому дереві) на місце.
3. **Push** (force push із lease) і **Очищення** (purge) - окремі свідомі кроки, бо
   їх неможливо скасувати: див. [Надсилання результату](#надсилання-результату) і
   [Видалення старої історії](#видалення-старої-історії-purge).

Майстерня, палітра, команди `gitpoulpi rewrite` та інструменти MCP працюють на тому
самому рушії, тож перегляд, зроблений в одному, застосовує інший.
[З командного рядка](#з-командного-рядка) перелічує прапорці;
[Створити правила за допомогою ШІ](#створити-правила-за-допомогою-ші) заповнює майстерню за описом; розділ
[Пропозиції від ШІ-агентів](#пропозиції-від-ші-агентів) каже, що агент може тут
робити, а чого не може.

**Правила за тим, що вони змінюють**

| Група | Правила | Розділ |
|---|---|---|
| Автори | Замінити автора, Анонімізувати авторів, Застосувати .mailmap | [Автори й .mailmap](#автори-й-mailmap) |
| Дати | Зсунути дати, Змінити часовий пояс, Обмежити годинами, Дата комітера = дата автора | [Дати](#дати) |
| Повідомлення | Пошук і заміна, Видалити рядки, Додати або видалити трейлер, Виправити кодування повідомлень | [Повідомлення](#повідомлення) |
| Вміст файлів і шляхи | Пошук і заміна у файлах, Прибрати файли з історії, Прибрати великі файли, Перемістити або перейменувати шляхи, Перетворити кінці рядків, Прибрати біт виконання, Перетворити кодування файлів | [Файли й шляхи](#файли-й-шляхи) |
| LFS | Перенести файли в LFS, Повернути файли з LFS | [Перенесення файлів у Git LFS або з нього](#перенесення-файлів-у-git-lfs-або-з-нього) |
| Підписи | Прибрати підписи (і повторне підписування під час «Застосувати») | [Підписи](#підписи) |
| Скрипт | Lua, shell, Python | [Правило «Скрипт»](#правило-скрипт) |

**Перш ніж почати**

- Перегляд нічого не змінює. «Застосувати» змінює лише ваші локальні ref і ніколи
  нічого не надсилає.
- Переписані commit'и отримують нові id. Усіх, хто має стару історію, треба
  повідомити: нотатку пише [Надсилання результату](#надсилання-результату).
- Секрет, що потрапив на remote, уже витік. **Спершу замініть його**, а потім
  перепишіть історію, зробіть force push і очищення (purge).
- Commit'и, які лишаються як є, зберігають свої id та підписи.

## Майстерня

`Ctrl+G Shift+H` (або **Переписування: майстерня історії** у палітрі) відкриває
майстерню переписування поверх Log. Кнопки на панелі інструментів для неї немає:
розширені дії живуть у палітрі (кожен рядок `Переписування: ...` відкриває
майстерню з уже доданим правилом), у підменю **Переписати історію** меню commit'у
(*Від цього коміту до HEAD...*, *Вибрані коміти...*, коли виділено кілька, та
*Відкрити майстерню...*) і за хордом.

`Ctrl+N` показує значок на кожному елементі майстерні (область, правила, поля, вкладки, кнопки); натискання значка робить те саме, що клацання на цьому елементі, а `Esc` прибирає значки (див. [Значки](keybindings.md#значки)).

![Майстерня переписування історії: рядок області, список із двох правил «Замінити автора» з полями вибраного правила та підсумок попереднього перегляду про те, скільки комітів зміниться](../images/history-rewrite.png)

- **Рядок області:** які ref рухаються (поточна гілка, усі локальні гілки, вибрані
  гілки й tag'и, вибрані commit'и), прапорець *Tag'и* і, після *Від цього коміту
  до HEAD...*, поле для початку після батька цього commit'у.
- **Правила:** нумерований список; правила застосовуються по порядку. Прапорець
  вмикає або вимикає правило, стрілки переміщують його, хрестик видаляє (*Відновити
  видалене правило* або `Ctrl+Z` повертає його). *Додати правило* показує види
  правил за групами. Правило, якому потрібна відсутня у вас програма, лишається
  сірим із поясненням причини.
- **Параметри правила:** клацання по текстовому полю редагує його; клацання по
  полю з кількома значеннями відкриває їхній список; прапорці перемикаються.
- **Перегляд** (`F5`) обчислює нову історію, нічого не чіпаючи, і показує
  індикатор поступу. Вкладки: **Підсумок** (кількості, що зробило кожне правило,
  попередження), **Коміти** (по одному рядку на змінений commit, сторінками від
  демона; фільтр показує змінені, видалені або надіслані), **Гілки й tag'и** (що
  рухається, а також захищені гілки, які вже надіслано, кожна з прапорцем),
  **Вплив** (що означає переписування надісланої історії: force push із lease,
  співавтори, підписи), а також **Секрети**, **Особи** і **Розмір** (див. нижче).
- **Файли commit'у:** `Enter` (або подвійне клацання) на рядку вкладки Коміти
  відкриває файли, які в ньому змінили правила вмісту, а поруч - diff вибраного
  файлу. Хрестик, `Esc` або клацання поза вікном закриває його. Видалені рядки
  правила секретів приховано.
- **Застосувати** (`Ctrl+S` або `Ctrl+Enter`) доступне, коли перегляд відповідає
  правилам. Питання без типової відповіді задаються щоразу: що робити з підписами
  підписаних commit'ів і як виносити папку. Панель результату пропонує
  **Скасувати**, що повертає кожен переміщений ref на місце.
- **Зберегти / Відкрити** зберігають рецепт у репозиторії (спільно) або лише для
  вас; секретні значення не зберігаються ніколи.

Кожна кнопка має клавішу: список є в Налаштуваннях > Клавіатура (контекст
*Rewrite*) і в посібнику `keybindings.md`.

### Автори й .mailmap

- **Замінити автора** зіставляє автора чи комітера за іменем і/або email
  (буквально або регулярним виразом) і задає нове ім'я та/або email. *Застосувати
  до* вибирає автора, комітера або обох; *Також автори tag'ів* змушує наново
  створені анотовані tag'и йти слідом. Початковий комітер зберігається, доки запуск
  не скаже *я, зараз*.
- **Анонімізувати авторів** замінює кожну особу нумерованим підставним значенням
  (`Contributor 1`, `contributor-1@anonymous.invalid`; обидва шаблони можна змінити,
  `{n}` - це номер). Та сама людина в одному запуску завжди отримує той самий
  номер; особи, яких ви внесли до *Не чіпати*, лишаються як є.
- **Вкладка «Особи»** (також **Переписування: Merge осіб (.mailmap)...** у
  палітрі) - спосіб виправити людину, яка робила commit'и під кількома іменами й
  email, **нічого не переписуючи**. Вона перелічує кожне ім'я й email області з
  рядка області, з кількістю commit'ів, які кожне написало й закомітило, і
  позначає ті, що `.mailmap` репозиторію вже зіставляє (`зіставлено з Name <email>`).
  Позначте особи, що є однією людиною (`Space` або клацання; *Вибрати всі* /
  *Зняти всі*), потім **Merge у...** (`m`): діалог питає, яка з них залишається
  (першою йде та, що має найбільше commit'ів), і **додає до `.mailmap` по одному
  рядку на кожну іншу особу** (`Name <email> Old Name <old@email>`; рядок, що вже
  є, не повторюється, а файл створюється, якщо його немає). Нічого не комітиться:
  закомітьте `.mailmap` самі, щоб поділитися ним. Log, blame та історія файлу
  одразу показують канонічне ім'я (налаштування `log.use_mailmap`, типово
  ввімкнене; збережені commit'и не змінюються, тож force push не потрібен).
  Рядок стану каже, що записано, і пропонує **Скасувати** (`u`), що повертає
  попередній `.mailmap` (це один запис історії скасувань, як і будь-яка інша
  дія). `r` читає список знову.
- **`.mailmap` замість переписування.** Коли правило автора змінює commit'и, які
  вже є на remote, Підсумок каже *Файл .mailmap виправляє відображення без
  переписування. Використати .mailmap?* із кнопкою **Використати .mailmap**
  (`m` на Підсумку). Вона відкриває вкладку «Особи» з позначеними особами, які
  збігаються з правилом, а особу, яку встановило б правило, пропонує як ту, що
  залишається, навіть якщо жоден commit її ще не містить.
- **Правило `.mailmap`** (*Переписування: застосувати .mailmap до історії...* або
  `rewrite preview --mailmap`) саме переписує: автори й комітери (на ваш вибір)
  стають такими, як їх називає `.mailmap` робочого дерева, тобто тим, що показує
  `git log --use-mailmap`. Користуйтеся ним, коли сама історія має містити
  канонічні імена, наприклад перед її публікацією; це переписування, як і будь-яке
  інше (перегляд, Застосувати, force push).
- **Правила особи й трейлери.** Правило особи може також змінювати людей, названих
  у трейлерах: позначте **Застосувати й до трейлерів** (`--map-trailers`). Кожен
  трейлер, значенням якого є саме `Name <email>`, що збігається з *Email дорівнює* /
  *Ім'я дорівнює* правила, отримує нове ім'я й email, що б правило не робило з
  автором і комітером. Типово вимкнено: `Signed-off-by` фіксує, хто підписав, тож
  його зміна - окреме рішення.

### Дати

Чотири правила дат діють на дату автора, дату комітера або обидві (*Дати* на
панелі правила).

- **Зсунути дати** переносить кожну дату на вказану величину (`+2h`, `-1d`, `90m`,
  `1d 2h`). Часовий пояс, у якому написано кожен commit, зберігається.
- **Змінити часовий пояс** записує дати в іншому зсуві UTC. *Зберегти* каже, що
  лишається: **момент** (той самий момент, годинник показує інакше) або **місцевий
  час** (той самий місцевий час, момент змінюється).
- **Обмежити годинами** переносить кожен commit, що потрапляє поза дозволені години
  (наприклад `Mon-Fri 18:00-23:30; Sat,Sun 10:00-20:00`), на найближчий дозволений
  час, лише раніше або лише пізніше (*Напрям*). *Не раніше за батьківський*
  зберігає порядок історії; *Початкове значення* робить невеликий випадковий
  розкид відтворюваним: те саме значення на тій самій історії дає ті самі дати.
- **Дата комітера = дата автора** задає комітера (ім'я, email і дату) такими, як
  в автора, - те, що `git commit --amend` чи rebase скасували.

Дати - це правила, як і решта: перегляд, перевірте вкладку **Коміти** (кожен рядок
показує стару й нову дату), потім застосуйте. Id commit'у залежить від його дат, тож
правило дат змінює кожен commit після першого, якого воно торкнулося.

### Повідомлення

- **Пошук і заміна в повідомленнях** та **Видалити рядки повідомлень** беруть
  буквальний текст або регулярний вираз (*Регулярний вираз*, *Враховувати регістр*);
  порожня заміна видаляє. Повідомлення, що не є коректним UTF-8, вони ніколи не
  чіпають: спершу виконайте **Виправити кодування повідомлень**, якщо хочете його
  редагувати.
- **Трейлери.** *Додати або видалити трейлер* (*Переписування: додати або видалити
  трейлери...* у палітрі, або `--trailer-add`, `--trailer-remove`, `--trailer-map`)
  править рядки `Key: value` в кінці повідомлення, ті, які знає `git
  interpret-trailers` (`Signed-off-by`, `Co-authored-by`, `Reviewed-by`...). Список
  **Дія** вибирає *Додати* (ключ **Трейлер**, його **Значення** та **Якщо він уже
  є**: *Додати (якщо не збігається)*, *Замінити наявні* або *Не чіпати commit*),
  *Видалити* (кожен трейлер цього ключа або лише ті, чиє значення містить
  **Значення містить**) чи *Змінити значення* (**Знайти в значенні** стає **Замінити
  на**, наприклад старий email на новий у `Signed-off-by`). Ключі зіставляються без
  урахування регістру. Змінюються лише рядки трейлерів, решта повідомлення лишається
  точно такою, як була, а повідомлення, що ще не має трейлерів, отримує порожній
  рядок і власний блок. Вкладка «Коміти» показує кожну зміну як `+Signed-off-by: ...` /
  `-Co-authored-by: ...`. Останній абзац повідомлення - його блок трейлерів (ніколи
  не заголовок), тож рядок на кшталт `Note: see the ticket` у тілі не є трейлером,
  якщо він не сам в останньому абзаці разом з іншими трейлерами.
- **Id commit'ів у повідомленнях.** **Оновити id commit'ів** (`--update-message-hashes`,
  типово вимкнено; наприкінці панелей правил, що редагують повідомлення) змушує
  id, записані в повідомленнях, іти слідом за переписуванням: скорочений id із 7 чи
  більше шістнадцяткових символів (`This reverts commit 1a2b3c4`, `see 1a2b3c4d5e`),
  що називає рівно один commit переписаної історії, замінюється новим id цього
  commit'у, обрізаним до тієї самої довжини. Id, що збігається з кількома commit'ами,
  з жодним або з commit'ом, який переписування створить пізніше, лишається як є;
  Підсумок каже, скільки замінено і скільки лишено.
- **Виправити кодування повідомлень** (*Переписування: виправити кодування
  повідомлень...* або `--fix-message-encoding [--fix-name-encoding]`) перекодовує
  повідомлення в UTF-8, у двох випадках:
  - commit із заголовком `encoding` (`ISO-8859-1`, `Windows-1252`, `Shift_JIS`,
    будь-яке кодування, яке знають git і таблиці кодувань) декодується й
    записується як UTF-8, а заголовок зникає: текст читається однаково всюди, без
    перетворень. Імена автора й комітера цього commit'у були в тому самому кодуванні
    й декодуються разом із ним, тож commit ніколи не лишається наполовину
    перетвореним.
  - **Кракозябри** (mojibake) - UTF-8, колись прочитане як Latin-1 чи Windows-1252
    (`RÃ©Ã©criture` замість `Réécriture`), - виправляються **лише тоді, коли
    круговий перехід точний**: текст має закодуватися назад у байти, що є коректним
    UTF-8, а спотворення результату тим самим способом має дати оригінал.
    Повідомлення, що просто містить `Ã©` поруч зі справжніми літерами або символи
    поза старими абетками, цього не проходить і лишається як є.

  *Виправити й імена* (`--fix-name-encoding`) так само виправляє зіпсовані імена
  автора й комітера. Те, що не вдається визначити (невідома назва кодування, байти,
  недійсні в оголошеному кодуванні, повідомлення не в UTF-8, що нічого не оголошує,
  текст, схожий на зіпсований, але не доведено), **лишається як є й
  підраховується**: Підсумок каже *n повідомлень залишено як є: їхнє кодування
  неможливо визначити*, а `counts.encoding_left` містить число. Вкладка «Коміти»
  показує кожне виправлення зі старим і новим повідомленням та рядком *encoding*
  (`ISO-8859-1` стає `UTF-8`).

### Файли й шляхи

- **Правила вмісту файлів** (*Пошук і заміна у файлах*, *Прибрати файли з історії*,
  *Прибрати великі файли*): панель перевіряє кожне значення під час введення й
  показує причину під полем (шаблон, що не компілюється, хибний шаблон шляху,
  розмір менший за один байт). Розміри приймають одиниці (`500 KiB`, `5 MiB`,
  `1 GiB`). Шаблон шляху без похилої риски збігається на будь-якій глибині.
  *Секретні значення* вводяться в маскованому полі, використовуються лише для
  цього запуску й ніколи не зберігаються; перегляд ховає рядки, у яких вони були.
  *Порожні коміти* визначає, чи видаляти commit, який правила залишили порожнім
  (типово), чи зберігати його. Двійкові файли й файли, більші за обмеження,
  лишаються без змін і враховуються в Підсумку.
- **Переміщення шляхів.** *Перемістити або перейменувати шляхи* (*Переписування:
  перемістити або перейменувати шляхи...* у палітрі) має три види, що вибираються у
  списку **Дія**:
  - *Перейменувати шлях* (**Звідки**, **Куди**; `--move-path FROM=TO`): ті самі
    файли й папки з'являються за новим шляхом у кожному commit'і, що мав старий;
    більше нічого не змінюється, кожен файл зберігає свій id. Commit, де новий шлях
    уже існує, ніколи не перезаписується: перегляд відхиляється й перелічує commit'и
    та шляхи, що конфліктують (виберіть вільну назву або спершу перемістіть наявний
    шлях). Лише точні шляхи, без шаблонів.
  - *Перемістити все в папку* (**Папка**; `--into-subdir DIR`): кожен шлях кожного
    commit'у отримує префікс. Корисно, щоб об'єднати репозиторії без конфліктів назв.
  - *Винести папку в корінь* (**Папка**; `--extract DIR`): папка стає коренем,
    commit'и, що її не зачіпають, відкидаються (commit, що її створює, не має
    батька), злиття, які вже нічого не з'єднують, спрощуються, а гілки й tag'и, що не
    мають нічого з папки, видаляються. **Щоразу** питають, як це закінчиться:
    - *У новий клон, відкритий у новій вкладці* (`--extract-mode clone`): копія цього
      репозиторію створюється у вибраній вами папці (новий репозиторій отримує
      всередині папку з назвою винесеної), там переписується й чиститься так, щоб
      містити лише нову історію, кожну локальну гілку й tag, що мають папку. Цей
      репозиторій не чіпається. Новий репозиторій не має remote (оригінал не є його
      upstream).
    - *На місці: історію цього репозиторію переписано* (`--extract-mode in-place`):
      звичайне переписування, перегляд, «Застосувати», скасування. Гілки без папки
      видаляються (скасування повертає їх); у поточної гілки папка має бути.
    - *Як підмодуль цього репозиторію* (`--extract-mode submodule`): новий
      репозиторій створюється, як у випадку клону, а потім **один новий commit** у
      поточній гілці замінює папку підмодулем із нього (`.gitmodules` і посилання),
      папка лишається як витягнутий підмодуль. Історію цього репозиторію **не**
      переписано: його старі commit'и зберігають файли папки, тож ніщо, що на них
      вказує (tag'и, інші клони), не ламається. URL у `.gitmodules` - це локальний
      шлях нового репозиторію: змініть його (`git config -f .gitmodules
      submodule.<folder>.url`), щойно він житиме на хості. Змінені чи невідстежувані
      файли в папці його відхиляють. Скасування повертає звичайну папку.
    Підсумок каже, що перегляд показує історію нового репозиторію й до якої папки
    вона піде. Правила, що йдуть після винесення (перейменування, видалення),
    діють на винесене дерево; для клону чи підмодуля винесення має бути першим
    правилом шляхів. Правила шляхів виконуються після правил вмісту, тож glob
    видалення називає шляхи такими, якими вони були.

#### Кінці рядків, біт виконання й кодування файлів

Три правила в групі **Вміст** меню «Додати» (або рядки палітри *Переписування:
перетворити кінці рядків...*, *Прибрати біт виконання...* і *Переписування:
перетворити кодування файлів...*). Усі три беруть **Файли** (glob; шаблон без
похилої риски збігається на будь-якій глибині; порожньо означає кожен файл) і
**Крім файлів**. Вони змінюють лише те, що називають glob, у кожному commit'і області.
Двійкові файли (байт NUL у перших 8 КіБ) ніколи не чіпаються: Підсумок враховує їх
як *залишені як є*.

- **Перетворити кінці рядків** (`--eol lf|crlf|cr --eol-paths GLOB...
  [--eol-exclude GLOB...]`). *Перетворити на*: LF (Linux, macOS), CRLF (Windows) або
  CR (класичний Mac). Кожен кінець рядка відповідного текстового файлу стає цим, тож
  файл зі змішаними кінцями виходить однорідним; файли, що вже правильні, зберігають
  свою версію без змін. *Враховувати .gitattributes* (типово вимкнено,
  `--eol-follow-attributes`) читає кореневий `.gitattributes` кожного commit'у:
  файли з `-text` чи `binary` пропускаються, а файли з `eol=lf` чи `eol=crlf`
  зберігають цей кінець замість вибраного вами.
- **Прибрати біт виконання** (`--strip-exec GLOB... [--strip-exec-exclude
  GLOB...]`). Відповідні файли переходять з режиму 100755 на 100644; їхній вміст не
  змінюється. Потрібен щонайменше один шаблон файлів: зняття виконуваності з усіх
  зламало б ваші скрипти.
- **Перетворити кодування файлів** (`--reencode TARGET [--from SOURCE]
  [--encoding-fallback ENC] --encoding-paths GLOB... [--encoding-exclude
  GLOB...]`). *Перетворити на*: UTF-8 (типово), UTF-8 з BOM, UTF-16 LE або BE
  (з позначкою порядку байтів), Windows-1252 чи ISO-8859-1. *Кодування файлів*:
  типово кодування кожного файлу визначається (позначка порядку байтів, інакше
  коректний UTF-8, інакше *Запасне*, Windows-1252, якщо ви його не змінили);
  назвіть кодування, щоб примусити його, але хибний вибір дає хибний текст (UTF-8,
  прочитане як Latin-1, подвоює кожен акцент). Файл, якого вихідне кодування не
  читає, або що містить символ, якого цільове не може зберегти (знак євро в
  ISO-8859-1), лишається точно як є й підраховується в Підсумку.

Правила виконуються в порядку списку, над тим самим файлом: перетворення файлу на
UTF-16 і наступний запит на кінці рядків лишають його як є (він уже не звичайний
текст). Застосування - один запис у списку скасувань, як і будь-яке переписування.

### Пошук секретів

- **Пошук секретів:** `gitpoulpi rewrite scan-secrets` (і інструмент MCP
  `rewrite_scan_secrets`) один раз читає історію й перелічує префікси токенів
  (GitHub, GitLab, Slack, AWS, Stripe, npm, Google, OpenAI, Anthropic), приватні
  ключі, JWT, паролі в URL і рядки `password = value`, схожі на випадкові; для
  кожного показує файл, перший і останній commit та прихований фрагмент на
  кшталт `ghp_****abcd`. Пошук не вичерпний, а саме значення ніколи не
  показується, не журналюється й не зберігається. `--remove-finding ID`
  перетворює знахідку на правило, що прибирає її з кожного commit'у. Секрет, який
  потрапив на remote, уже витік: спершу замініть його, а потім перепишіть
  історію, зробіть force push і очищення (purge).
- **Вкладка «Секрети»** робить те саме з майстерні для області з рядка області:
  **Шукати секрети** (`s`) запускає пошук як завдання (індикатор поступу має
  підпис *Пошук*, **Скасувати** або `Esc` зупиняє його). Кожна знахідка - це
  рядок із видом, прихованим фрагментом, файлом і кількістю інших файлів, що
  його містять; під списком показано перший і останній commit, де її бачили,
  і скільки commit'ів та версій файлів її містять. Вкладка повідомляє, скільки
  двійкових і завеликих файлів не прочитано, і що пошук не вичерпний. Усі
  знахідки спершу позначено; **Прибрати з історії** (`r`) перетворює позначені
  на одне правило, яке називає їх за id (ніколи за значенням), і ви
  переглядаєте та застосовуєте його як будь-яке інше. Після переписування чи
  зміни області знахідки застарівають: вкладка про це каже, шукайте знову.
  Майстерня ніколи не тримає значення секрету, тому й показати його не може.

### Пошук того, що важить

- **Пошук того, що важить:** `gitpoulpi rewrite analyze [--top N]` (і інструмент
  MCP `rewrite_analyze`) - це аналіз розмірів, як `filter-repo --analyze`:
  найбільші файли з шляхом, розміром, першим і останнім commit'ом та ознакою, чи
  вони ще є в HEAD, найбільші папки, файли, видалені з HEAD, які історія досі
  зберігає, і підсумки. Він читає лише розміри й шляхи, ніколи вміст файлів, і
  нічого не змінює.
- **Вкладка «Розмір»** робить те саме з майстерні (`F7` або *Проаналізувати
  розміри історії* в палітрі відкриває її й запускає аналіз): **Проаналізувати
  розміри** (`s`) - це завдання (*Аналіз*, **Скасувати** або `Esc` зупиняє його).
  **Показати** вибирає список (`v`): *Файли* (найбільші унікальні версії файлів,
  кожна з позначкою *у HEAD*, *стара версія* файлу, що досі є, або *видалено*),
  *Папки* (усе, що будь-коли зберігалося під кожною) чи *Видалені* (шляхи, яких
  уже немає в HEAD, але історія їх тримає). **Сортування** (`o`) - за розміром,
  за шляхом або спершу видалені. Позначайте рядки (`Space`, `Alt+A` / `Alt+U` -
  усі / жодного): вкладка каже, скільки вони містять, чесно - «до приблизно», бо
  місце повертається лише після переписування, очищення старих об'єктів і `gc`.
  **Прибрати з історії** (`r`) перетворює позначені шляхи на правило шляхів
  (спеціальні символи екрануються, шлях, що вже є в правилі, вдруге не
  додається); **Прибрати кожен файл понад ...** (`b`, у списку Файли) пише
  правило за розміром трохи нижче за найменший позначений файл. Переглядайте й
  застосовуйте їх як будь-які інші правила. Списки показують 200 найбільших
  рядків; CLI каже, скільки ще є, а `--top` перелічує їх. Після переписування чи
  зміни області рядки застарівають: аналізуйте знову.

### Підписи

- **Підписи:** переписаний commit не може зберегти свій підпис (він підписував старі
  байти), тож коли переписуються підписані commit'и, вас щоразу питають: *Прибрати
  підписи* (спершу показується кількість), *Підписати знову лише ті commit'и, що були
  підписані* або *Підписати знову кожен переписаний commit*. Типової відповіді немає.
  Commit'и, що лишаються як є, зберігають свої. Повторне підписування використовує
  ваші власні налаштування, так само як підписаний commit: `gpg.format` (`openpgp`,
  `ssh` або `x509`), `user.signingkey` і `gpg.program` / `gpg.ssh.program` /
  `gpg.x509.program`. Четвертий рядок запитання, **Перевірити підписування** (`4`),
  один раз підписує пробні дані й перевіряє їх: каже, скільки триває один підпис, і
  оцінює запуск для кількості commit'ів, про які питають, або чому це не працює
  (немає ключа, агент заблоковано, програму не встановлено, з порадою, як її
  встановити). Перегляд робить той самий тест ще до читання історії й відхиляється з
  цією причиною, тож зламане налаштування ніколи не лишає наполовину підписаного
  переписування. Commit'и підписуються **під час перегляду** (їхні id містять підпис),
  тож перегляд із повторним підписуванням забирає час на підпис, Підсумок каже
  *Commit'и підписано знову: n, за 12.5 s*, а запит парольної фрази може відкритися
  саме тоді: спершу розблокуйте агент (Перевірити підписування робить саме це).
  **Скасувати** зупиняє між двома підписами й нічого не лишає. Повторно створюються
  лише підписи commit'ів; підписаний tag усе одно втрачає підпис.
- **Правило *Прибрати підписи*** (меню «Додати», група *Підписи*; *Переписування:
  прибрати підписи...* у палітрі; `--remove-signatures`) прибирає підпис кожного
  commit'у в області, навіть де більше нічого не змінюється, і нічого не питає про
  повторне підписування. З CLI: `rewrite check-signing` і
  `--signatures strip|resign-signed|resign-all`.

### Скасування переписування

**Скасувати** (кнопка панелі результату, *Скасувати* на панелі інструментів із
`Ctrl+Z` у Log або `gitpoulpi undo`) повертає кожну переміщену гілку, tag і нотатку на
місце, а разом із ними й файли в робочому дереві, зі старих commit'ів, які
закріплює переписування. Воно питає спершу, коли переписана гілка вже на своєму
upstream (локальне скасування не скасовує push) і коли у вас є незакомічені зміни:
їх збережено, а файл, який ви змінили й який стара історія перезаписала б,
зупиняє скасування (файли рухаються так, як їх рухає `reset --keep`). Скасування
перестає бути можливим для переписування, щойно ви [очистите](#видалення-старої-історії-purge)
його стару історію; список історії тоді позначає його *очищено*.

## Перенесення файлів у Git LFS або з нього

Два правила групи *LFS* меню «Додати» переписують історію так, щоб великі файли
від початку жили в [Git LFS](lfs.md) (або залишали його). Їм потрібна програма
`git-lfs`: без неї правила сірі з порадою щодо встановлення, а перегляд
відхиляється. Це власний рушій GitPoulpi, не `git lfs migrate`, тож ви отримуєте
перегляд, область, скасування й захист push, як і в будь-якого іншого правила.

- **Перенести файли в LFS** (*Переписування: перенести файли в LFS...* або
  `--lfs-import PATTERN` з `--lfs-min-size BYTES`). Кожен файл, що збігається з
  шаблонами (`*.psd`, `assets/**`; шаблон без похилої риски збігається на будь-якій
  глибині) і має щонайменше розмір *Лише файли від* (порожньо: кожен збіг), стає
  вказівником LFS у кожному commit'і, що його містить. Його вміст потрапляє в
  локальне сховище LFS (`.git/lfs/objects`, один раз на різний вміст) під час
  «Застосувати», а кореневий `.gitattributes` отримує `<pattern> filter=lfs diff=lfs
  merge=lfs -text` у кожному переписаному commit'і, що має вказівник (створюється,
  якщо його немає, інші рядки не чіпаються, дублікатів немає). Файл, що вже є
  вказівником, лишається як є. Підсумок каже *3 файли (12 MiB) переходять у LFS.
  Об'єктів LFS для запису: 3.*, а вкладка «Коміти» перелічує *переносить big.psd у
  LFS* для кожного commit'у.
- **Повернути файли з LFS** (*Переписування: повернути файли з LFS...* або
  `--lfs-export PATTERN`). Вказівники, що збігаються, знову стають справжніми
  файлами, а рядки `.gitattributes` для цих шаблонів прибираються. Об'єкти мають
  бути в локальному сховищі LFS: коли якихось немає, перегляд відхиляється зі
  списком і кнопкою **Завантажити об'єкти LFS**, що завантажує їх з `origin`;
  після цього знову зробіть перегляд. Імпорт, за яким іде експорт тих самих
  шаблонів, повертає точно ті самі commit'и.

Після «Застосувати» файли в робочому дереві - справжній вміст (не вказівники), а
**Скасувати** повертає стару історію. Панель результату має **Надіслати об'єкти LFS**
(`l`): те саме, що `LFS: Push All Objects`, щоб нову історію можна було надіслати,
не зупиняючись згодом на відсутніх об'єктах (звичайний push переписаних гілок також
вивантажує їх через хук pre-push, який установлює «Застосувати»). Нотатка для
співавторів каже, що їм потрібні git-lfs і `git lfs pull`.

Варто знати: «Застосувати» встановлює фільтри LFS репозиторію (`git lfs install
--local`), коли їх немає, бо git потребує їх, щоб порівнювати справжні файли з
вказівниками. Записується лише кореневий `.gitattributes`, ніколи вкладений. Файл
*менший* за мінімальний розмір, що збігається з шаблоном, лишається звичайним
файлом, але git захоче перетворити його на вказівник при наступному додаванні, тож
`git status` показує його зміненим, доки ви його не закомітите. Імпорт читає великі
файли потоком, експорт тримає в пам'яті по одному файлу.

## Надсилання результату

Застосування переписування ніколи нічого не надсилає. Переписані гілки й tag'и,
що були на remote, потребують force push, і цей push ніколи не примушує сліпо:
кожен ref надсилається з lease на id, який був на remote під час перегляду (а не
на той, що показує ваша гілка відстеження зараз), тож push колеги в проміжку
буде відхилено для цього ref замість перезапису, а ref надсилаються одним
push «все або нічого» (`--atomic`), де сервер це дозволяє. З CLI:

```
gitpoulpi rewrite push --dry-run        # asks the remote, sends nothing
gitpoulpi rewrite push --yes            # sends it
gitpoulpi rewrite note                  # what the others must run
gitpoulpi rewrite maps --out ./maps     # commit-map and ref-map
```

Захищені гілки (налаштування `rewrite.protected_branches`, типово `main`,
`master`, `develop`, `release/*`) не чіпаються, коли їх уже надіслано, ні під
час переписування, ні під час push, доки ви не назвете їх (`--include-protected
main`) або не включите всі. Власний захист гілок хоста й далі вирішує, чи
прийме він force push; його відмову показано для кожного ref.

У майстерні все це робить панель результату після Застосувати:

- **Надіслати переписані ref на remote** перелічує ref, які переписування
  пересунуло й які має remote, кожен із прапорцем (`Space`). Захищені гілки
  спершу не позначені, з приміткою *захищено*: позначайте їх по одній або
  скористайтеся *Вибрати всі* / *Зняти всі* (`Alt+A` / `Alt+U`). **Push
  переписаних гілок** (`p`) надсилає позначені; відповідь - це рядок на кожен
  ref (*надіслано*, *уже актуально*, *відхилено: remote змінився після
  перегляду*, *відхилено: захищено хостом*, *пропущено: захищена гілка*, *не
  надіслано*). Відхилений рядок має **Fetch і перевірити** (`f`): майстерня
  закривається, а remote завантажуються, тож Log показує, що надіслали інші.
  Нічого не перезаписується: lease захищає їхню роботу, а перед новою спробою ви
  знову робите перегляд.
- **Копіювати нотатку** (`c`) кладе нотатку для співавторів у буфер обміну, мовою
  інтерфейсу навколо неперекладених команд git.
- **Відкрити мапу commit'ів** (`m`) показує, де лежать мапа commit'ів і мапа ref;
  клацання по шляху (або `1` / `2`) копіює його.

Push не можна скасувати: якщо потім зробити `undo` переписування, зміниться лише
ваш репозиторій, і скасування каже про це ще до запиту. Надішліть нотатку всім,
хто має стару історію: вона перелічує старий і новий кінець кожної гілки й tag'а
та команди (`git fetch`, потім `git reset --hard origin/<branch>` або
`git rebase --onto`). Обидві мапи зберігаються 24 години разом із запуском;
скопіюйте їх, якщо вони потрібні для очищення репозиторію GitLab або скрипту.

## Коли хост захищає гілку

Ваш хост може сам захищати гілку (захист гілок і rulesets на GitHub, protected
branches на GitLab, політики гілок Azure DevOps, обмеження гілок Bitbucket) і
відхиляти force push, потрібний переписуванню. Коли репозиторій **прив'язано** до
хоста (розділ запитів на бічній панелі, див. [Інтеграція з хостингом](hosting-integration.md)),
майстерня питає хост, які гілки той захищає, вашим власним токеном:

- Ці гілки **типово не входять у переписування**, так само як захищені гілки з
  `rewrite.protected_branches` і робочого процесу: вкладка «Гілки й tag'и» перелічує
  їх із прапорцем кожну та кнопками *Вибрати всі* / *Зняти всі* і каже чому:
  *захищено на GitHub*.
- Якщо токен не може прочитати захист (бракує області доступу або ви не
  адміністратор), майстерня каже *Захист на хості невідомий* і нічого не вважає
  захищеним за словом хоста. Переписування ніколи не блокується цим. Репозиторій, що
  не прив'язаний, ніколи не опитується.

Коли захищена гілка заважає (перегляд відхилено, бо кожна гілка захищена, або хост
відхилив push: *відхилено: захищено хостом*), кнопка **Як це обійти** (`Alt+H`)
пояснює три виходи з точною сторінкою налаштувань вашого провайдера й репозиторію
(виберіть посилання й скопіюйте його `c` або відкрийте `o`). GitPoulpi ніколи не
робить жодного з них за вас:

1. **Тимчасово зняти захист** у налаштуваннях хоста, зробити push, а потім
   повернути його.
2. **Зробити push переписаної історії під новою назвою гілки**, потім зробити цю
   гілку типовою (або перейменувати), а стару видалити, коли нею ніхто не
   користуватиметься.
3. **Як крайній засіб, видалити й заново створити віддалений репозиторій** і
   надіслати все. Це втрачає pull / merge запити з їхнім рев'ю, issues, зв'язок
   форків зі старою історією, зірки й спостерігачів, налаштування CI, секрети й
   змінні, а також вебхуки та ключі розгортання.

З CLI той самий текст повертається як `protected_by_host` у JSON `rewrite preview` /
`rewrite run` (коли хост захищає гілку області), відхиленого `rewrite push` і
`rewrite note`: `provider`, `branches`, `ways` (кожен зі своїми `steps` і `links`),
`recreate_loses` і все пояснення як `text`.

## Видалення старої історії (purge)

Після переписування старі commit'и все ще лежать у вашому репозиторії: їх тримає
скасування переписування (саме це робить його скасовним), а також reflog. Якщо ви
переписували, щоб позбутися секрету, цей секрет досі лежить у папці `.git`.
Очищення (purge) остаточно видаляє стару історію:

```
gitpoulpi rewrite purge                 # asks: lists what is deleted and lost (exit code 3)
gitpoulpi rewrite purge --yes           # does it
```

Воно скидає закріплення скасування цього переписування, завершує дію записів
reflog, що називають старі commit'и, виконує `git gc --prune=now`, а потім
перевіряє, що кожен старий commit і версія файлу справді зникли. Підтвердження
наперед каже, що ви втрачаєте: **скасувати стане неможливо** для цього
переписування (і для будь-якої ранішої операції, чиє скасування теж потребувало
старих commit'ів); вони лишаються в списку історії з позначкою «очищено».
Очищення не можна зупинити після початку й не можна скасувати. Remote воно не
чіпає.

Усе, що ще тримає стару історію, блокує очищення, і тоді нічого не змінюється.
Список називає кожну таку річ і що з нею робити: гілка чи tag, що не входили в
переписування, stash на старій історії (видаліть його або залиште й змиріться,
що стара історія лишається), інший worktree, чий HEAD на ній, і гілки
віддаленого відстеження, що досі вказують на стару історію (надішліть
переписані гілки, потім зробіть fetch). Ваш список stash'ів і reflog інших гілок
не чіпаються ніколи.

Секрет, що потрапив на remote, уже витік: **спершу замініть його**. Після
очищення відповідь перелічує, що ще потрібно від хоста, для кожного remote:
GitHub тримає старі commit'и доступними в кешованих сторінках і ref запитів на
рев'ю (зверніться до GitHub Support або видаліть і створіть репозиторій заново),
у GitLab є очищення репозиторію, що приймає `commit-map` (`gitpoulpi rewrite maps
--out DIR`) разом із housekeeping, Azure DevOps і Bitbucket потребують звернення
до підтримки або нового репозиторію, а в усіх, хто має клон чи форк, стара
історія лишається.

### Екран очищення

У майстерні панель результату переписування має кнопку **Очистити стару
історію...** (клавіша `e`), а палітра - **Переписування: очистити стару
історію...** (вона діє на найновіше переписування, яке ще не очищено, і після
закриття майстерні). Екран перелічує, що очищення видаляє і що ви втрачаєте
(операції, чиє скасування зникає разом із ним; ті, що з позначкою *скасування
теж зникне*, не є переписуваннями, але потребували старих commit'ів), а потім
те, що ще тримає стару історію, по одному рядку:

- гілка віддаленого відстеження: **Fetch** оновлює їх із remote;
- stash: **Видалити** спершу питає, бо stash - це робота, яку ви не комітили;
- гілка, tag, worktree чи інший ref: **Копіювати назву**, а потім розберіться з
  ним там, де він живе (перепишіть або видаліть гілку, виконайте checkout
  переписаної гілки в worktree).

Перевірка запускається знову після кожного виправлення, а **Перевірити ще раз**
(`r`) запускає її на вимогу. **Очистити** (`p`) доступне, лише коли нічого не
лишилося. Воно ставить останнє питання з номерами й без типової відповіді (`1`
очищає остаточно, `2` лишає все як було), потім виконується; екран показує
поточний крок і каже, що зупинити його не можна. Підсумок повідомляє, що старої
історії в цьому клоні більше немає, або скільки старих об'єктів ще лишилося.
Нижче - кроки для кожного remote (посилання можна скопіювати). Хрестик, `Esc` і
клацання поза вікном закривають екран, крім часу, коли очищення виконується.

Через MCP інструмента очищення не існує, доки ви не задасте
`allow_history_purge = true` у таблиці `[mcp]` файлу `config.toml`.

## Правило «Скрипт»

*Додати правило > Скрипт* (або **Переписування: запустити скрипт...** у палітрі)
додає правило зі скриптом Lua й відкриває його редактор поверх майстерні; `Enter`
на рядку *Скрипт* цього правила відкриває його знову. Редактор починає з
невеликого шаблону.

- **Мова** (рядок панелі правила): *Lua (вбудована)*, *Shell-скрипт*, *Python*
  або *Lua (встановлена)*. Усе, крім вбудованої Lua, - це
  [зовнішній скрипт](#зовнішні-скрипти-shell-python-lua): без пісочниці, а мова,
  вимкнена в налаштуваннях або без інтерпретатора, у списку сіра з причиною
  поруч (вибір такої мови каже, що робити). Зміна мови скрипту, який ви ще не
  писали, міняє шаблон.
- **Скрипт** - текстовий редактор із номерами рядків. Те, що ви друкуєте, і є
  правилом; нічого підтверджувати не треба.
- Під ним рядок **перевірки** каже `OK: функцію rewrite_commit знайдено` або
  перелічує проблеми з рядками (`script:3: ...`; номер на полі червоний).
  Перевірка запускається за мить після того, як ви перестали друкувати, і ніколи,
  поки утримується клавіша.
- **Параметри** мають по рядку на кожен рядок `--! param` заголовка скрипту, з
  підписом біля поля: текст, число або прапорець так/ні. Значення, яке ви
  очистили, повертається до типового із заголовка; текстовий параметр без
  типового значення треба заповнити до Перегляду.
- **Файл** (шлях усередині репозиторію, для початку `.gitpoulpi/rewrite/script.lua`)
  з кнопками **Відкрити з файлу...** (замінює текст) і **Зберегти у файл...**.
- **Тест на вибраному** запускає скрипт на commit'ах, які ви вибрали в Log, або
  на 20 найновіших, якщо нічого не вибрано, і нічого не записує. Таблиця
  перелічує кожен commit (короткий id), кожне поле, яке він змінив би, як
  `старе -> нове`, і рядки `log(...)` скрипту. **Скасувати** припиняє чекання.
  Якщо скрипт завершується помилкою, показано commit і причину.
- Хрестик, клацання поза редактором і `Esc` закривають його; `Tab` і `Shift+Tab`
  переходять між редактором, параметрами, файлом, кнопками й результатами; `F5`
  запускає тест.

Перегляд відмовляє скрипту, що не компілюється: панель Перегляду каже *помилка в
скрипті* з рядком (а для помилки на commit'і - його короткий id і причину). У
збірці без скриптів цей вид правила лишається в меню «Додати», сірим.

## Написати скрипт за допомогою ШІ

Коли ШІ ввімкнено ([Допомога ШІ](ai.md)), у редакторі скрипту є кнопка
`✦ Написати за допомогою ШІ...`, а в палітрі - `✦ Переписування: написати скрипт
за допомогою ШІ...`, що відкриває майстерню з новим правилом «Скрипт» і
відкритим діалогом. Нічого не надсилається, доки ви не натиснете **Надіслати**:
діалог під час друку показує точний текст, який піде.

- **Що має робити скрипт?** Вашими словами: *перенести кожен commit, зроблений
  уночі, на наступний ранок*, *замінити мій старий email на новий, лише до
  2024*.
- **Надіслати зразок із N commit'ів** (вимкнено): коли позначено, автор, дата й
  тема commit'ів, які взяв би «Тест на вибраному» (ваше виділення в Log, інакше
  20 найновіших), додаються, щоб модель бачила, як виглядають ваші дані. Ніколи
  вміст файлів чи тіла commit'ів. Коли прапорець знято, дані commit'ів не
  залишають комп'ютер.
- **Що надсилається** - панель лише для читання на трохи темнішому тлі, згорнута
  під час відкриття діалогу (тоді діалог короткий). Клацніть її заголовок,
  натисніть `Alt+W` або перейдіть до неї через `Tab` і натисніть `Enter`, щоб
  показати: вона перелічує інструкції (фіксований контракт скрипту, потім ваші
  інструкції для ШІ) і ваш запит, з власною смугою прокручування (перетягуйте її,
  користуйтеся колесом над панеллю або стрілками, `PageUp`, `PageDown`, `Home` і
  `End`, поки вона має фокус). Профіль, який їх отримає, вказано в рядку вище.
  Діалог збільшується під панель у межах екрана.
- **Надіслати** (`Tab` до нього, `Enter`). Поки модель працює, діалог чекає, а
  `Esc` скасовує запит. Якщо вона зазнає невдачі, діалог лишається з причиною,
  щоб ви могли спробувати ще раз.

Відповідь перевіряє той самий демон, що й набраний скрипт; помилку компіляції
один раз повертають моделі. Потім скрипт **замінює текст у редакторі** (діалог
каже про це, коли в редакторі є щось, окрім заготовки), а заголовок редактора
показує *✦ написано ШІ: прочитайте перед переглядом*, доки ви не змінили текст.
Його ніколи не тестують, не переглядають і не застосовують за вас: прочитайте,
натисніть **Тест на вибраному**, потім зробіть Перегляд, як для будь-якого
скрипту. Скрипт працює в тій самій пісочниці, що й написаний вами (без файлів,
годинника, мережі).

З командного рядка: `gitpoulpi ai rewrite-script "<instruction>" [--sample N]`
виводить скрипт і результат `rewrite script check` для нього як JSON і нічого не
запускає (код виходу 2, якщо він усе ще не компілюється). Використовується
профіль *Скрипт переписування історії* з Налаштувань > ШІ.

## Створити правила за допомогою ШІ

Коли ШІ ввімкнено ([Допомога ШІ](ai.md)), у майстерні є кнопка
`✦ Створити правила за допомогою ШІ...` поруч зі Зберегти й Відкрити, клавіша `Alt+I`
(*Створити правила переписування за допомогою ШІ* у Налаштування > Клавіатура й миша,
контекст *Майстерня переписування історії*), а в палітрі - `✦ Переписування: створити
правила за допомогою ШІ...`. Коли ШІ вимкнено або збірка не має ШІ, кнопки й рядка
палітри немає. Ви своїми словами описуєте, як потрібно переписати історію (*замінити
мою стару адресу a@b.org на c@d.org*, *прибрати secrets.txt з усієї історії*,
*зсунути мої дати на дві години*), а модель пропонує правила й налаштування, які
**заповнюють майстерню**. Нічого не надсилається, доки ви не натиснете **Надіслати**:
діалог під час друку показує точний текст, який піде.

- **Як потрібно переписати історію?** Багаторядкове поле: `Enter` - новий рядок,
  `Ctrl+Enter` або `Ctrl+S` надсилає, `Esc` і хрестик скасовують.
- **Надіслати область, назви гілок і tag'ів та авторів історії** (вимкнено): коли
  позначено, додаються область із рядка області, назви гілок і tag'ів та різні автори
  (ім'я й email) найновіших commit'ів, які показує Log (не більше 20 commit'ів), щоб
  модель могла точно назвати ваш email (у командному рядку `ai rewrite-rules --context`
  натомість читає 200 найновіших commit'ів). Ніколи вміст файлів чи повідомлення commit'ів.
  Коли прапорець знято, комп'ютер залишають лише ваш опис і фіксовані інструкції.
- **Замінити поточні правила** (лише коли в майстерні вже є правила; вимкнено): типово
  нові правила додаються після наявних; коли позначено, вони їх замінюють (область і
  налаштування, названі у відповіді, застосовуються в обох випадках).
- **Що надсилається** - панель лише для читання на трохи темнішому тлі, окремо від
  полів над нею, і **згорнута** під час відкриття діалогу (тоді діалог короткий).
  Клацніть її заголовок, натисніть `Alt+W` або перейдіть до неї через `Tab` і
  натисніть `Enter`, щоб показати: вона перелічує інструкції (словник правил, потім
  ваші інструкції для ШІ) і ваш запит та має власну смугу прокручування
  (перетягуйте її, користуйтеся колесом над панеллю або стрілками, `PageUp`,
  `PageDown`, `Home` і `End`, поки вона має фокус). Профіль, який їх отримає,
  вказано в рядку вище. Діалог збільшується під панель у межах екрана. Поле опису
  отримує власну смугу прокручування, коли текст не вміщається.

Модель може використовувати будь-який вид правил із цієї сторінки, крім **Скрипт**
(це код: *Написати скрипт за допомогою ШІ* показує скрипт на перевірку) і форми
*Пошук і заміна у файлах* із секретними значеннями (секретні значення ніколи не
передаються моделі: використовуйте вкладку «Секрети»). Вона може задати областю
поточну гілку, усі локальні гілки й tag'и або названі гілки й tag'и, що існують, а
також опції *Tag'и*, *committer*, *порожні коміти* і *скорочені id у повідомленнях*.
Те, чого майстерня не вміє виразити (межу дат на кшталт *з березня*, діапазон
commit'ів), модель не вгадує: вона каже про це в примітці. Що станеться з підписами,
модель ніколи не вирішує: вас спитають під час застосування.

**ШІ лише готує правила й налаштування.** Він нічого не переглядає, не застосовує й
не запускає: відповідь копіюється в майстерню, як завантажений рецепт, попередній
перегляд на екрані застаріває, а Перегляд і Застосування (з їхніми запитаннями й
підтвердженнями) залишаються за вами, як завжди. Кожне правило окремо розбирається й
перевіряється тією самою перевіркою, що й у редакторі та рушії; правило, що не пройшло
перевірку, пропускається. Коли щось пропущено або модель зробила примітку, після
додавання правил це показує список (*Пропущено (чинні правила збережено)*, кожен
пункт із номером, назвою й причиною), а `Enter` або `Esc` закриває його. Прочитайте
правила, за потреби змініть, потім зробіть Перегляд.

З командного рядка: `gitpoulpi ai rewrite-rules "<description>" [--context]` виводить
пропозицію як JSON (`recipe`, який читає `rewrite preview --recipe-json`, `problems`,
`notes` і `applied: false`) і нічого не запускає (код виходу 2, коли щось пропущено).
Інструмент MCP - `ai_rewrite_rules`. Використовується профіль *Правила переписування
історії* з Налаштувань > ШІ.

## Скрипти Lua

Правило скрипта запускає вашу функцію на кожному commit'і. Це звичайний Lua 5.4 у
пісочниці: без файлів, годинника, процесів, модулів і `pcall`; той самий скрипт на
тій самій історії завжди дає той самий результат, а виклик, що перевищує 10
мільйонів інструкцій, 64 MiB або 5 секунд, зупиняється з помилкою, яка називає
commit.

```lua
--! name: Replace an email
--! param old_email: text "Email to replace"
--! param new_email: text "New email"
function rewrite_commit(c, ctx)
  if c.author.email == ctx.params.old_email then
    return { author = { email = ctx.params.new_email } }
  end
end
```

`c` містить `id`, `parents`, `tree`, `author` і `committer` (`name`, `email`,
`time`, `offset_minutes`), `message` та `signed`. `ctx` містить `index`, `total`,
`params`, `state` (поверніть `state = {...}`, щоб передати дані наступному
commit'у) і `window.before` / `window.after` (задайте `--! window: N`). Повертайте
лише те, що змінюється: `author`, `committer`, `message`. Допоміжні функції:
`regex_replace`, `regex_match`, `stable_hash`, `rand`, `weekday`, `hour`, `log`, а для повідомлень `trailers(message)` (список `{key, value}`), `set_trailer(message, key, value)` (замінює трейлери цього ключа; четвертий аргумент `"add"` або `"skip"` змінює це), `remove_trailer(message, key)` та `at("2024-03-05 18:30", offset_minutes)` (дата зі зсувом як Unix-час).

З командного рядка: `gitpoulpi rewrite script check my.lua` компілює скрипт,
`gitpoulpi rewrite script test my.lua --commit HEAD --param old_email=a@b` показує,
що він змінив би, нічого не записуючи, а
`gitpoulpi rewrite preview --script my.lua --script-param old_email=a@b` планує
все переписування.

## Зовнішні скрипти (shell, Python, Lua)

Той самий контракт, що й у скрипту Lua, але його виконує програма на вашому
комп'ютері: *Shell-скрипт* (bash або sh; PowerShell у Windows чи будь-який
`.ps1`), *Python* і *Lua (встановлена)* (ваш власний `lua`, а не вбудований; у
нього немає бібліотеки JSON, тож шаблон читає рядок за шаблоном). **Вони не
працюють у пісочниці: зовнішній скрипт виконується з вашими правами** і може
читати чи змінювати все, що можете ви. Про це кажуть панель правила та заголовок
редактора.

Як він спілкується: GitPoulpi запускає скрипт один раз за запуск і надсилає
йому один JSON-запит на рядок у стандартний ввід (поля commit'у, `params`,
`state`, повернутий попередньою відповіддю); він відповідає одним рядком JSON у
стандартний вивід, з тими самими полями, що повертає скрипт Lua (`author`,
`committer`, `message`, `state`, `log`), або `{"error": "text"}`, щоб здатися.
Діагностику виводьте у стандартний потік помилок: вона з'являється як рядки
`log` цього commit'у. Рядки заголовка починаються з `#!` для shell і Python
(`#! name: ...`, `#! param old: text "Old"`; рядок shebang лишається shebang) і з
`--!` для Lua.

```sh
#!/bin/sh
#! name: Uppercase author names
while IFS= read -r line; do
  name=$(printf '%s' "$line" | sed -n 's/.*"author":{[^}]*"name":"\([^"]*\)".*/\1/p' | tr 'a-z' 'A-Z')
  printf '{"author":{"name":"%s"}}\n' "$name"
done
```

**Що він отримує.** Порожнє середовище, окрім `PATH`, `HOME` / `USERPROFILE`,
`SYSTEMROOT`, `TEMP` / `TMP` і `LANG`; нову тимчасову папку як робочу (із
власною копією скрипту); шляху до репозиторію він не отримує. **Обмеження часу:**
`rewrite.script_timeout_ms` (5000) на кожну відповідь і
`rewrite.script_total_timeout_s` (3600) на весь прохід. Коли ліміт перевищено,
скрипт завершується аварійно, виводить щось не в JSON або завдання скасовано,
GitPoulpi вбиває скрипт і все, що він запустив, а переписування зупиняється з
вказанням commit'у й причини; нічого не пересунуто.

**Які мови існують.** Їх перелічує `rewrite.external_scripts` у `config.toml`:
типово `["shell"]`; `"python"` і `"lua"` додайте самі в `config.toml`
(`[rewrite]`, `external_scripts = ["shell", "python"]`; список не можна задати
через `gitpoulpi config set`). Мова, якої немає в списку, у майстерні сіра, а CLI
і MCP відмовляють (`scripts_disabled`); мова зі списку, чий інтерпретатор не
знайдено, сіра з підказкою зі встановлення (`tool_missing`).

**Довіра.** Навіть коли мову ввімкнено, скрипт запускається лише після того, як
ви довірили його точному тексту. Скрипт, який ви набрали в майстерні, - ваш і
працює одразу; той, що прийшов зі спільним рецептом або файлом репозиторію, ні:
Перегляд і *Тест на вибраному* зупиняються й питають *Довіряти цьому скрипту?* з
двома пронумерованими відповідями без попередньо вибраної (`1` - довіряти й
продовжити, `2` - не довіряти, `Esc` лишає як є). Довіра запам'ятовує SHA-256
тексту для цього репозиторію, тож змінений скрипт питає знову, а клонований
репозиторій не може сам виконати код на вашому комп'ютері. З командного рядка
прочитайте файл, потім `gitpoulpi rewrite script trust FILE` (або `--trust` у
`preview`, `run`, `script check` і `script test`, що довіряє й іде далі). Агент
через MCP не може довіряти нічому: він може запускати лише скрипт, якому ви
довірили раніше.

**Перевірка.** Рядок перевірки під редактором для скрипту без довіри каже *Ще не
довірено* (нічого не запущено); для скрипту з довірою GitPoulpi запускає його
один раз із вигаданим commit'ом (`"dry_run": true`) і перевіряє, чи відповідь
відповідає контракту. `gitpoulpi rewrite script check FILE` робить те саме й
повідомляє `trust`, `hash` та `interpreter`.

## З командного рядка

`gitpoulpi rewrite` (і однойменні інструменти MCP) запускає той самий рушій, для
скриптів і агентів. **Рецепт** - це файл TOML або JSON, той самий, що зберігає
майстерня (`--recipe FILE` або `-` для стандартного вводу), а прапорці додають
правила після власних правил рецепта.

```
gitpoulpi rewrite preview --recipe fix.toml --all     # план, нічого не змінює
gitpoulpi rewrite apply --run ID --digest D           # виконати план, який ви переглянули
gitpoulpi rewrite run --fix-message-encoding --signatures strip --yes
gitpoulpi undo                                        # повертає все назад
```

- Правила як прапорці: `--set-name` / `--set-email` з `--match-email` (особа),
  `--mailmap`, `--shift-dates`, `--replace-message FIND=WITH`, `--trailer-add`,
  `--trailer-remove`, `--trailer-map`, `--fix-message-encoding`
  (`--fix-name-encoding`), `--remove-path`, `--remove-blobs-over`,
  `--replace-content`, `--eol` (`--eol-paths`), `--strip-exec`, `--reencode`
  (`--encoding-paths`), `--move-path`, `--into-subdir`, `--extract`,
  `--lfs-import`, `--lfs-export`, `--script`, `--remove-signatures`,
  `--remove-finding`. Область - поточна гілка, `--all-local` або `--ref R`
  (можна повторювати), від `--since REV`.
- **Запитання без типової відповіді** - це прапорці: `--signatures
  strip|resign-signed|resign-all`, коли змінюються підписані commit'и, і
  `--extract-mode` для винесення. Без них відповідь - відмова або `needs_choice`
  (код завершення 3), ніколи не здогад.
- **Коди завершення:** 0 - виконано; 1 - помилка (нечитабельний рецепт, хибні
  прапорці); 2 - відмова з причиною (`stale`, `signature_choice_needed`,
  `dirty_paths_touched`, `empty_scope`, ...); 3 - запитання, на яке треба відповісти,
  або надіслані ref, що потребують `--yes`.
- `preview` зберігає план у репозиторії, тож `apply` працює з пізнішої команди,
  після перезапуску демона чи з іншого фронтенду; план, що більше не збігається зі
  своїм digest, має стан `stale`.

У [довіднику CLI](cli-reference.md) є кожен прапорець, а
[MCP та агенти](mcp-and-agents.md) кажуть, які інструменти отримує агент (інструмента
очищення не існує, доки ви його не ввімкнете, а агент не може довіряти скрипту).

## Пропозиції від ШІ-агентів

Агент може **запропонувати** переписування, але не виконати його. `gitpoulpi ui propose
rewrite --recipe FILE|-` (інструмент MCP `ui_propose_rewrite`, вимкнений, доки не
`[mcp] allow_ui_propose = true`) відкриває майстерню у вашому запущеному вікні з
правилами рецепта вже в списку та фіолетовим банером *✦ Запропонував <агент>:
переписування історії (3 правила) · Ctrl+Enter приймає · Esc відхиляє*.

- **Нічого не виконується.** Жодного перегляду, застосування, push чи очищення:
  пропозиція лише заповнює правила. Ви читаєте їх, за бажання редагуєте,
  робите **Перегляд** і застосовуєте власною клавішею. Закриття майстерні відхиляє
  пропозицію.
- **Чого агент не може в неї вкласти:** скрипт (він запускався б під час перегляду),
  понад 50 правил, секретні значення (їх вилучають із рецепта до надсилання).
  Таку пропозицію відхиляють із причиною.
- Агент може прочитати результат у `ui state` (`accepted`, коли ви застосували
  правила як запропоновано, `accepted_edited`, коли спершу їх змінили, `rejected`,
  коли ви закрили). Одна пропозиція за раз; її відхиляють, поки відкрито інший ваш
  діалог.

## Інструменти

Більшість переписувань історії не потребує нічого, крім Git: зміна авторів і
комітерів, застосування `.mailmap`, анонімізація, зсув дат або обмеження їх
годинами, переписування повідомлень і трейлерів, заміна вмісту, видалення шляхів
чи великих blob'ів і переміщення шляхів - усе це виконується всередині GitPoulpi.

**Скрипти Lua вбудовано.** Інтерпретатор уже є в GitPoulpi, тож скрипту Lua не
потрібні ні інструмент, ні налаштування. Скриптам shell, Python і встановленої
Lua потрібен свій інтерпретатор (див. таблицю нижче), а описано їх у розділі
[Зовнішні скрипти](#зовнішні-скрипти-shell-python-lua).

Деякі можливості використовують зовнішню програму. GitPoulpi перевіряє її
наявність (програму шукають у вашому `PATH`, у Windows також через `PATHEXT` і
власний `usr/bin` Git for Windows, і вона має відповісти на `--version` протягом
2 секунд); відповідь кешується на хвилину, а «Перевірити ще раз» питає знову.
Правило, якому потрібна відсутня програма, лишається в списку сірим, з причиною та
способом встановлення, а Перегляд відмовляє ще до будь-якого виконання.

| Можливість | Інструмент | Примітки |
|---|---|---|
| Повторне підписування commit'ів | `gpg` (OpenPGP), `ssh-keygen` (`gpg.format = ssh`) або `gpgsm` (`gpg.format = x509`) | Для підписів SSH і X.509 потрібен ще й `user.signingkey`. `gpg.program`, `gpg.ssh.program` і `gpg.x509.program` враховуються. |
| Міграція в LFS (два правила LFS) | `git-lfs` 3.0 або новіший | Та сама перевірка, що й на панелі LFS. |
| Скрипти Python | `python` 3.8 або новіший (`py -3` у Windows) | Типово вимкнено: додайте `"python"` до `rewrite.external_scripts`. |
| Скрипти Lua (встановлена) | `lua5.4`, `lua54`, `lua` або `luajit` | Типово вимкнено: додайте `"lua"` до `rewrite.external_scripts`. |
| Shell-скрипти | `bash`, `pwsh` (PowerShell) або `sh` | Типово ввімкнено (`"shell"`). Скрипту PowerShell (файл `.ps1`, shebang `pwsh` або будь-який shell-скрипт у Windows) потрібен `pwsh` або `powershell`; скрипту POSIX - `bash` або `sh` (у Windows їх постачає Git for Windows). |

Підказки зі встановлення, спершу Windows:

- Windows: Git for Windows містить `gpg`, `ssh-keygen`, `bash`, `sh` і Git LFS.
  Інакше `winget install GnuPG.GnuPG`, Параметри > Додаткові компоненти > Клієнт
  OpenSSH, `winget install GitHub.GitLFS`, `winget install Python.Python.3.12`,
  `winget install DEVCOM.Lua`, `winget install Microsoft.PowerShell`.
- Linux: пакети дистрибутива (`gnupg`, `openssh`, `git-lfs`, `python3`, `lua5.4`,
  `bash`, `powershell`).
- macOS: `brew install gnupg git-lfs python lua powershell`; `ssh-keygen` і `sh`
  вбудовано.
