# Інтеграції хостингів і трекерів issues

GitPoulpi підключається до таких продуктів:

- **Хостинг** (pull requests, issues, клонування з вашого облікового запису,
  ключі SSH): GitHub, GitHub Enterprise, GitLab, GitLab self-managed,
  Azure DevOps, Azure DevOps Server, Bitbucket, Bitbucket Data Center, Gitea і
  Forgejo (зокрема Codeberg). **Gerrit Code Review** - хостинг лише для рев'ю: його зміни - це
  pull requests, issues у ньому немає.
- **Трекери issues** (лише issues): Jira Cloud, Jira Data Center, Trello,
  Linear, YouTrack (Cloud і Server) та Redmine.
- **Локальні нотатки Markdown** (лише issues, без токена, без мережі): тека з нотатками Markdown, наприклад тека сховища Obsidian, див. [Локальні issues і Obsidian](local-issues.md).

Кожна інтеграція використовує **персональний токен**. Немає ні облікового запису
GitPoulpi, ні входу через OAuth. Інтеграції необов'язкові й **вмикаються
окремо для кожного репозиторію**: нічого не завантажується, доки ви не прив'яжете
репозиторій. Ваш токен зберігається в помічнику облікових даних, ніколи в
`config.toml`. Звичайним операціям `git` (fetch, pull, push) інтеграція не
потрібна: вони використовують облікові дані, які ваш `git` уже має.

**Куди далі.** Ця сторінка - налаштування: токени, підключення, прив'язка
репозиторію, ключі SSH. Коли обліковий запис підключено:

- розділи PULL REQUESTS та ISSUES на бічній панелі, дошка issues, створення
  pull request чи issue, чип на панелі інструментів і посилання в повідомленнях
  commit'ів: **[Pull requests та issues](pull-requests-and-issues.md)**;
- подання одного issue чи запиту в застосунку з коментарями, написанням і
  публікацією від імені: **[Бесіди](conversations.md)**;
- читання й рев'ю запиту з обговореннями коду та незавершеним рев'ю:
  **[Рев'ю pull або merge request](review.md)**;
- pull requests та issues цілого робочого простору в одному списку:
  **[Radar](radar.md)**.

## 1. Створіть токен на хостингу

Форма підключення містить посилання *Згенерувати токен на <хост>*. Воно відкриває
сторінку токенів хостингу з уже вибраними потрібними правами (scopes). Щоб зробити це вручну:

| Хостинг | Де | Scopes |
|---|---|---|
| GitHub, GitHub Enterprise | Settings > Developer settings > Personal access tokens (classic) > Generate new token | `repo` (репозиторії, pull requests, issues), `read:user` (хто ви), `admin:public_key` (лише для додавання чи видалення ключів SSH) |
| GitLab, GitLab self-managed | User settings > Access tokens > Add new token | `api`, `read_user` |
| Azure DevOps | User settings > Personal access tokens, на `dev.azure.com/<organization>/_usersSettings/tokens` | `Code (Read & write)`, `Work Items (Read & write)`. Створюйте токен **для конкретної організації**, а не для «All accessible organizations»: глобальні токени перестають працювати 2026-12-01. |
| Azure DevOps Server | Та сама сторінка на вашому сервері (`https://<server>/<collection>/_usersSettings/tokens`) | Ті самі два scopes |
| Bitbucket | `id.atlassian.com/manage-profile/security/api-tokens` > Create API token with scopes | `read:user:bitbucket`, `read:workspace:bitbucket`, `read:repository:bitbucket`, `write:repository:bitbucket`, `read:pullrequest:bitbucket`, `write:pullrequest:bitbucket`. Для ключів SSH також `read:ssh-key:bitbucket`, `write:ssh-key:bitbucket`, `delete:ssh-key:bitbucket`. |
| Bitbucket Data Center | Фото профілю > Manage account > HTTP access tokens | `Repository (Read & write)`, `Projects (Read)` |
| Gitea, Forgejo (Codeberg) | Settings > Applications > Generate New Token, на `<хост>/user/settings/applications` | Читання `user`; читання й запис `repository`, `issue` і `user` (останнє для ключів SSH). Gitea не показує scopes постфактум, тож GitPoulpi не може попередити про відсутній: відхилений виклик про це каже. |
| Linear | Settings > Account > Security & access > Personal API keys > New API key (`linear.app/settings/account/security`) | Читання, запис, створення issues. Ключ діє від вашого імені. |
| YouTrack (Cloud і Server) | Ваш профіль > Account Security > New token, на `<хост>/users/me?tab=account-security` | Scope `YouTrack`. Постійний токен діє від вашого імені. |
| Gerrit | Settings > HTTP Credentials > Generate new token (нові сервери; старіші: Generate new password), на `<хост>/settings/#HTTPCredentials` | Немає. Токен - це **пароль HTTP** і діє від вашого імені; ім'я користувача вказується поруч. |
| Redmine | My account > API access key > Show, на `<хост>/my/account`. Адміністратор має ввімкнути **Administration > Settings > API > Enable REST web service**. | Немає. Ключ діє від вашого імені. |
| Jira Cloud | `id.atlassian.com/manage-profile/security/api-tokens` > Create API token (класичний тип, без scopes) | Немає. Токен діє від вашого імені. |
| Jira Data Center | Profile > Personal Access Tokens | Немає. Токен діє від вашого імені. |
| Trello | Спершу **ключ API** з `trello.com/apps/admin` (створіть Power-Up, потім згенеруйте ключ API). Потім **токен** з `trello.com/1/authorize?...&key=<ваш ключ>`. | `read`, `write` |

Дайте токену назву на кшталт «GitPoulpi» і термін дії. Скопіюйте токен: хостинг
показує його лише один раз.

## 2. Підключіть його

1. Натисніть `Ctrl+,` і виберіть **Інтеграції**.
2. Виберіть продукт ліворуч. Продукти поділено на дві групи: **Хостинг** і
   **Трекери issues**.
3. Натисніть **Підключити**. Щоб додати другий обліковий запис того самого продукту,
   скористайтеся **+ Додати профіль**.

   ![Сторінка «Інтеграції»: продукти ліворуч і кнопка «Підключити» для GitHub](../images/settings-integrations.png)

4. Заповніть форму й вставте токен. Токен показується відкритим текстом, поки ви
   його вводите, тож переконайтеся, що ніхто не дивиться. Форма перелічує
   потрібні їй scopes.

   ![Форма підключення: поле Personal Access Token, scopes repo, read:user і admin:public_key, посилання для генерації токена на github.com та кнопки «Підключити» й «Скасувати»](../images/settings-connect.png)

5. Натисніть **Підключити**. GitPoulpi перевіряє токен на хостингу у фоні. Потім
   сторінка показує картку з вашим іменем і логіном, зелене *Підключено* та
   розділ ключів SSH. Токен, якому бракує якогось із потрібних scopes, усе одно
   підключається, а відсутні scopes перелічено червоним.

На картці: **Змінити** знову відкриває форму. **Відключити** видаляє токен і
залишає профіль. **Видалити** прибирає обидва, після підтвердження.

Клавіатура на сторінці «Інтеграції»: `Tab` / `Shift+Tab` переходять зі списку
продуктів до смуги профілів і форми. `a` додає профіль, `e` змінює його, `d` або
`Delete` видаляє, `o` відкриває сторінку токенів, `Esc` повертає на крок назад.

### Що просить кожна форма

Посилання *Згенерувати токен* працює лише після заповнення хоста чи організації.

- **GitHub, GitLab:** лише токен. **GitHub Enterprise** і **GitLab self-managed**
  також просять **Домен хоста** (`gitlab.example.com`; https, якщо не вказати `http://`). Назві без крапки
  (служба Docker або машина в локальній мережі) потрібен порт або `http://`: `gitea:3000`,
  `http://nas`. Власний сервер може працювати через
  звичайний http, наприклад локальний контейнер за адресою `http://localhost:8080`. Токен, надісланий
  через звичайний http, передається без шифрування, тож використовуйте http лише
  в локальній або довіреній мережі.
- **Azure DevOps:** **Організація**, назва в `dev.azure.com/<organization>`.
  Адреса `https://<org>.visualstudio.com` теж приймається. Дві організації
  потребують двох профілів. Репозиторій використовує профіль організації, названої
  в його remote'і. **Azure DevOps Server** просить **URL колекції**, наприклад
  `tfs.corp/tfs/DefaultCollection`. Для Azure DevOps GitPoulpi не використовує
  системний помічник облікових даних: Git Credential Manager зберігає там токен
  входу, а не персональний токен доступу.
- **Bitbucket:** ваша **Ел. пошта облікового запису Atlassian** і токен API. Якщо пошту
  не задано, токен надсилається як bearer-токен: використовуйте це для токена
  доступу робочого простору чи репозиторію. GitPoulpi знаходить ваші робочі
  простори за токеном. **Bitbucket Data Center:** **URL сервера** і токен
  HTTP-доступу.
- **Gitea, Forgejo:** **Домен хоста** і токен. **Forgejo** починає з
  `https://codeberg.org`: замініть його для власного сервера. У Gitea типової
  публічної адреси немає. Адреса `http://localhost:3000` працює для локального сервера.
  Обидва види використовують один клієнт (Forgejo - форк Gitea з тим самим
  `/api/v1`); токен надсилається як `Authorization: token <token>`. Системний
  помічник облікових даних для них не використовується.
- **Jira Cloud:** **URL сайту** (`acme.atlassian.net`), ваша **Ел. пошта облікового
  запису Atlassian** і класичний токен API. Токени Jira зі scopes не
  підтримуються. **Jira Data Center:** **URL сервера** і персональний токен
  доступу.
- **Trello:** **ключ API** і **токен**. Ключ API публічний, тому його зберігають у
  `config.toml` (в `account`). Токен секретний і йде до помічника облікових даних.
  У формі два посилання: *Отримати ключ API в Trello* і, після введення ключа,
  *Згенерувати токен*. Ключ і токен надсилаються в заголовку, ніколи в URL.

- **Linear:** лише **ключ API**: у Linear один публічний хост, тож
  адреси вводити не треба. Ключ надсилається як є в заголовку `Authorization`
  (персональні ключі Linear не приймають `Bearer`). Щоб посилання `ENG-12`
  у повідомленнях commit'ів відкривали потрібну сторінку, збережіть URL профілю
  зі своїм робочим простором (`https://linear.app/acme`, з CLI: `--url`); самі
  рядки issues завжди несуть точну адресу.
- **YouTrack:** **URL сайту** (`acme.youtrack.cloud` для Cloud, інакше ваш власний
  сервер, зі шляхом контексту, якщо він є, наприклад
  `host/youtrack`) і постійний токен, що надсилається як `Authorization: Bearer`.
  Той самий клієнт обслуговує Cloud і Server (`<url>/api`).

- **Gerrit:** **URL сервера** (зі шляхом контексту, якщо він є), ваше **Ім'я користувача** і пароль
  HTTP як токен. Вони передаються як базова автентифікація HTTP; GitPoulpi спілкується з REST API `/a/`
  сервера й ігнорує рядок `)]}'`, з якого починається кожна відповідь. Ім'я користувача не секретне й зберігається в
  `config.toml` (як `account`), пароль іде до помічника облікових даних. Репозиторій прив'язується до *проєкту*
  Gerrit у PULL REQUESTS (там перелічені його зміни); issues у Gerrit немає, а зміна створюється
  надсиланням (див. *Надсилання на рев'ю* в [Рев'ю](review.md#gerrit)).
- **Redmine:** **URL сайту** вашого Redmine (з підшляхом, якщо він є,
  наприклад `host/redmine`) і ваш ключ API, що надсилається як `X-Redmine-API-Key`. Якщо
  Redmine відповідає 403 або сторінкою HTML, веб-служба REST вимкнена (попросіть
  адміністратора або ввімкніть її в **Administration > Settings > API**).

Jira, Trello, Linear, YouTrack і Redmine - лише трекери issues: без pull requests, без репозиторіїв для
клонування й без ключів SSH. У Bitbucket немає issues (Atlassian закрила
Bitbucket Issues). Натомість прив'яжіть розділ ISSUES репозиторію Bitbucket до
проєкту Jira.

## 3. Де зберігається токен

Токен зберігається в **помічнику облікових даних** вашої системи (Git Credential
Manager у Windows, libsecret або `pass` у Linux, Keychain у macOS). Він
використовує приватний запис, який не можна сплутати з обліковими даними
справжнього хоста. Він ніколи не записується в `config.toml` і не показується.

Якщо помічника облікових даних не налаштовано або він відмовляється прийняти токен,
GitPoulpi тримає токен **у пам'яті лише на цей сеанс** і повідомляє вам про це.
Після перезапуску підключіться знову.

GitPoulpi шукає токен профілю в такому порядку:

1. Змінна середовища `GITPOULPI_TOKEN_<ID ПРОФІЛЮ>`. Використовуйте її, щоб
   передати токен без зберігання, наприклад у CI.
2. Токен, збережений для профілю (`token_ref`).
3. Лише для профілів GitHub і GitLab: системний помічник облікових даних для хоста,
   коли жоден інший увімкнений профіль не використовує той самий хост.

Кожен профіль - це запис `[[integrations]]` у `config.toml`. Див.
[довідник конфігурації](config-reference.md#integrations-хостинги-й-трекери-issues).

## Перевірка безпеки

Збережений токен безпечний рівно настільки, наскільки безпечна адреса, на яку його надсилають. Тому GitPoulpi запам'ятовує для кожної інтеграції, до чого її підключено, і зупиняється, коли це змінюється:

- **Адреса.** Коли інтеграцію вперше використовують (або підключають), її адресу записують у `trust.toml`, у приватній теці даних лише для користувача (`<data>/private/`), а не в `config.toml`: редагування конфігурації ніколи не розширить те, чому довіряють. Якщо адреса в конфігурації вже не та, що записана, на неї нічого не надсилається, а токен навіть не читається. Різні написання однієї адреси (`HTTPS://Git.Example.com:443/`) - це та сама адреса; схожий хост - ні.
- **Обліковий запис.** Після підключення токена, а потім приблизно раз на добу (і раз за запуск для токена, що походить із `GITPOULPI_TOKEN_*` чи з помічника облікових даних), GitPoulpi питає хост, кому належить токен, і порівнює **id** облікового запису, а не логін. Токен, що тепер належить комусь іншому, зупиняється.
- **Сертифікат.** Сервери, сертифікат яких не прив'язується до відомого центру (приватний ЦС, самопідписаний сервер), приймаються лише за точним ключем, який ви прийняли, а рукостискання TLS усе одно доводить, що сервер має цей ключ. Із суворою фіксацією ключ має збігатися, навіть коли сертифікат прив'язується до публічного кореня; ціна - що кожна ротація ключа питає знову, тому це вмикається за бажанням. Публічні хости (github.com, gitlab.com, codeberg.org, bitbucket.org, dev.azure.com, `*.atlassian.net`, ...) не мають запису сертифіката.
- **Звичайний http.** Адреса `http://` не на loopback відхиляється, якщо ви не дозволили її для цієї інтеграції.

Кожен запит також обмежений власною адресою інтеграції (а для публічного хоста - його хостом API, як-от `api.github.com`): запит будь-куди ще відхиляється ще до надсилання, а перенаправлення на іншу адресу не виконується.

**Інтеграції, підключені до появи цієї перевірки,** отримують свій запис мовчки, із конфігурації, якою вона була, при першому використанні після оновлення: вони зберігають сьогоднішній рівень довіри, і ніхто нічого не питає.

### З командного рядка

Зупинена команда завершується з кодом виходу 2 і виводить, що змінилося (див. [довідник CLI](cli-reference.md)). `gitpoulpi hosting integrations trust <id>` показує, чому довіряють; `--accept-origin <url>`, `--accept-account <id>`, `--accept-certificate <sha256>`, `--strict-tls on|off` і `--allow-insecure-http on|off` приймають по одній речі, називаючи точне значення. Після прийняття нової адреси введіть токен ще раз. Від'єднання (`hosting logout`) чи видалення інтеграції видаляє її токен, її запис довіри й усе, що кешувалося з неї (збережені списки репозиторіїв діалогу клонування, списки облікового запису Radar і чернетки віддалених рев'ю її хоста).

Агент (MCP) нічого не може прийняти: йому кажуть, що перевірці безпеки потрібні ви.

### У терміналі (TUI)

Зупинений запит відкриває діалог **Перевірка безпеки інтеграції** поверх того, що ви робили. Він каже, що змінилося (стара й нова адреса, старий і новий обліковий запис з їхніми id або старий і новий сертифікат у вигляді малої таблиці з відбитком SHA-256 групами по чотири, суб'єктом, видавцем і строком дії) і що токен не надіслано. Відповіді пронумеровано:

1. **Від'єднати** видаляє збережений токен, запис довіри й усе, що кешувалося з інтеграції.
2. **Довіряти** новій адресі, обліковому запису чи сертифікату (для незашифрованої адреси: **Дозволити звичайний http**).
3. **Скасувати** нічого не змінює.

Жодну відповідь не виділено, доки ви не натиснете стрілку чи цифру, тож випадковий Enter нічого не приймає. Esc і хрестик закриття скасовують; клацання поза діалогом нічого не робить. Довгий текст прокручується колесом, Page Up/Page Down або scrollbar. Кілька перевірок стають у чергу (по одній на інтеграцію й вид зміни) і запитуються одна за одною. Скасована перевірка не з'являється знову, поки не змінюється; **Інтеграції: переглянути перевірку безпеки** в палітрі команд повертає її.

Після того як ви довірили нову **адресу**, форма інтеграції відкривається з полем токена у фокусі й підказкою «Радимо ввести токен ще раз»: збережений токен ніколи не надсилався туди. У формі адреса, змінена навмисно, приймається разом із токеном, введеним для неї; без токена форма просить його.

Форма має також два перемикачі. **Сувора фіксація сертифіката** (для адреси https) закріплює ключ сертифіката, який сервер показує під час підключення. **Дозволити звичайний http (без шифрування)** пропонується лише для адреси `http://`, що не на цій машині, з червоним попередженням, що токен передається відкритим текстом. Підключена картка показує закріплений відбиток.

### Що може токен і до коли

Підключення також питає хост, що може токен. GitHub (класичні токени), GitLab і Bitbucket (коли він надсилає scopes) повідомляють свої scopes: картка показує жовтий рядок «Цей токен має більше прав, ніж потрібно GitPoulpi» зі scopes понад ті, що використовує GitPoulpi, чутливі з них (як-от `delete_repo`, `admin:org`, `sudo`) червоним, із порадою надавати перевагу детальному токену з терміном дії. Класичний токен GitHub (`ghp_...`) отримує цю пораду, навіть коли його scopes точні. У детального токена GitHub не можна спитати його дозволи, тож показується лише його термін дії. Картка показує дату спливання, коли хост її повідомляє. Токен без терміну дії не показує нагадування, а інші продукти не повідомляють scopes і не викликають попередження. Ті самі поля є в JSON `hosting integrations login` і `test` (`excess_scopes`, `token_flavor`, `recommend_fine_grained`, `expires_at`). Вони читаються під час підключення, тож картка показує їх для сеансу, що підключав.

## 4. Прив'яжіть репозиторій

Прив'язка явна й окрема для кожного репозиторію. Коли профіль підключено, бічна
панель Refs показує розділ **PULL REQUESTS** і розділ **ISSUES** після TAGS.
Кожен розділ має два випадаючі списки: провайдер і проєкт.

- Список провайдерів **пропонує** облікові записи, що відповідають remote'ам
  репозиторію (спершу `origin`), у вигляді рядків на кшталт
  `owner/name · origin · GitHub`. Один вибір задає і провайдера, і проєкт.
- Нічого не прив'язується автоматично. Jira, Trello, Linear, YouTrack і Redmine ніколи не пропонуються, бо
  жоден remote їх не називає: виберіть їх самі.
- **Немає (відв'язати цей репозиторій)** угорі списку відв'язує розділ. Після цього
  ніщо не прив'яже його само.
- Прив'язка записується у файл `.gitpoulpi/repo-state.toml` репозиторію.

Обидва розділи прив'язуються **окремо**. Наприклад, pull requests можуть
надходити з Azure DevOps, а issues - з Jira.

| Провайдер | Проєкт PULL REQUESTS | Проєкт ISSUES |
|---|---|---|
| GitHub, GitLab | `owner/name`, `group/sub/proj` | так само |
| Azure DevOps | `Project/Repo` (організація береться з профілю) | `Project` (work items) |
| Gitea, Forgejo | `owner/name` | так само |
| Bitbucket | `workspace/slug` (Data Center: `PROJ/slug`) | немає: прив'яжіть Jira |
| Jira | немає | ключ проєкту, наприклад `ABC` |
| Trello | немає | дошка |
| Linear | немає | ключ команди, наприклад `ENG` (команди перелічені) |
| YouTrack | немає | коротка назва проєкту, наприклад `ABC` |
| Gerrit | назва проєкту Gerrit, наприклад `team/tool` | немає |
| Redmine | немає | ідентифікатор проєкту, наприклад `bench` (остання частина адреси проєкту) |

Список проєктів ISSUES можна фільтрувати. Можна також ввести проєкт, якого немає у
списку.

**Додатковий запит.** Джерело issues має необов'язковий рядок фільтра під списком
проєктів. Він поєднується (AND) із проєктом:

- Jira: фрагмент **JQL** (`component = UI AND labels = backend`).
- Azure DevOps: умова **WIQL** (`[System.AssignedTo] = @Me`).
- YouTrack: **запит YouTrack** (`#Unresolved Type: Bug`, `tag: ui or tag: ux`).
  Він береться в дужки, тож `or` не може розширити проєкт. Ваш `sort by:`
  замінює типовий `sort by: updated desc`.
- Redmine: немає (фільтрів стану й «призначені мені» розділу досить).
- Linear: немає (фільтрів стану й «призначені мені» розділу
  досить).
- Trello: список, де ви позначаєте **списки** для показу. Без позначок
  показуються всі відкриті списки.
- GitHub і GitLab його ігнорують.

`Enter` зберігає введений запит, `Esc` скасовує. Палітра:
*Issues: змінити запит / списки...*.

З CLI: `gitpoulpi hosting link pulls --id <profile>` (або `issues`),
`--clear` для відв'язування, `--filter` для додаткового запиту. Див.
[довідник CLI](cli-reference.md#команди).

### Клонування з підключеного облікового запису

Підключений профіль (GitHub, GitLab, Gitea, Forgejo, Azure DevOps, Bitbucket, Gerrit) також є джерелом у діалозі **Клонувати** (кнопка **Клонувати** на вкладці Головна або `c` на вкладці керування). Кожен профіль наведено в **Клонувати за URL** як окреме джерело (`GitHub · name`, `GitLab · name`); GitHub і GitLab ніколи не змішуються. Виберіть один, і завантажаться його репозиторії, згруповані за власником: спершу ваш обліковий запис, потім по одній секції на організацію чи групу (`quarry/tools` для підгрупи GitLab), кожна під заголовком із кількістю. Замок позначає приватний репозиторій.

![Діалог клонування на підключеному обліковому записі GitHub: одна секція на власника і замок біля приватного репозиторію](../images/clone-hosted.png)

Поле пошуку фільтрує одразу по всіх секціях (назва, повний шлях і опис); секція без збігів зникає. `Enter` на рядку заповнює клон HTTPS-адресою цього репозиторію та назвою папки.

![Діалог клонування: пошук звужує список до однієї організації](../images/clone-hosted-search.png)

Список профілю, який ви вже відкривали, одразу показується зі збереженої копії, поки хост опитується знову (*оновлення...* біля підпису); коли відповідь надходить, нові репозиторії з'являються, а зниклі зникають, і виділений та вибраний репозиторій лишаються на місці. Якщо оновлення не вдається, збережений список лишається з приміткою, а причину записано в Журналі активності.

Якщо хост відхиляє токен, замість списку діалог показує *не вдалося отримати список репозиторіїв* із причиною (а збережену копію видалено); решта джерел працює далі.

## 5. Ключі SSH

### Ключ SSH для профілю

Підключений профіль має розділ **Ключ SSH** під своєю карткою. Без ключа виберіть:

- **Типовий ключ**: ваш ssh-agent або `~/.ssh`. Нічого не змінюється.
- **Згенерувати новий ключ**: необов'язкова назва (типово `GitPoulpi <хост> <дата>`).
  Якщо позначено **Додати публічний ключ на <хост>**, GitPoulpi надсилає його,
  якщо хостинг його ще не має. Ключ записується без парольної фрази в
  `~/.ssh/gitpoulpi_<id профілю>_ed25519` і `.pub`. `ssh-keygen` не потрібен.
  Наявний файл ніколи не перезаписується.
- **Власний ключ**: введіть шлях або **Огляд** для файлу приватного ключа, потім
  натисніть **Використати цей ключ**.

Коли ключ прикріплено, розділ показує `назва (SHA256:...)` з кнопками:

- **Видалити**: відкріпити ключ і видалити його на хостингу, якщо GitPoulpi додав
  його туди.
- **Видалити файли**: те саме, а також видалити файли ключа, після підтвердження,
  що перелічує обидва шляхи.

### Ключ SSH для репозиторію

Щоб репозиторій використовував певний ключ, відкрийте меню вкладки (`Ctrl+T` або
праве клацання на вкладці) і виберіть **SSH і облікові дані...**, або виконайте команду
палітри *Repository: SSH і облікові дані...*, а в розділі SSH виберіть **Файл ключа**
(або **Ключ облікового запису** для ключа профілю інтеграції). Вибір зберігається в
приватній теці GitPoulpi: нічого не записується в репозиторій чи в конфігурацію git.
Див. [Налаштування](settings.md#лише-для-репозиторію-ssh-і-облікові-дані).

Репозиторій, який досі має власний `core.sshCommand` від колишнього закріплення
«Ключ SSH для цього репозиторію», показує його на цій сторінці лише для читання з
кнопкою **Перенести в GitPoulpi**.

CLI і MCP: `gitpoulpi repo-auth` (вибір для репозиторію) і, для самого закріплення
`core.sshCommand`, `gitpoulpi ssh-command show | set --key <file> | clear`.

Глобальний ключ із Налаштування > SSH і облікові дані (*Шлях до приватного
ключа* або *Згенерувати пару ключів*) застосовується до кожного репозиторію без
власного вибору. Ключ або закріплення репозиторію мають перевагу.

## 6. Захист гілок для переписування історії

Коли ви переписуєте історію ([майстерня](history-rewrite.md)), GitPoulpi питає хост, які гілки той
захищає, щоб типово не включати їх у переписування. Питає лише для репозиторію, який ви **прив'язали**
(розділ запитів чи issues на бічній панелі або закріплений профіль), токеном цього профілю, а токен, що не
може це прочитати, просто дає «невідомо»: нічого не ламається. Що відповідає кожен провайдер і що потрібно
токену:

| Хост | Що читається | Що потрібно токену |
|---|---|---|
| GitHub (і Enterprise Server) | прапорець `protected` гілок і активні набори правил гілок (шаблони `~DEFAULT_BRANCH`, `~ALL` і `refs/heads/...`) | класичний токен із `repo` (`public_repo` для публічного) або дрібнозернистий токен із Metadata (read). Набір правил, якого токен не може прочитати, названо, класичні правила все одно враховуються |
| GitLab (gitlab.com і self-managed) | `protected_branches` (назви й шаблони `*`) | `read_api` і роль, що може бачити налаштування репозиторію |
| Azure DevOps (Services і Server) | ввімкнені політики гілок репозиторію, що блокують (області `Exact`, `Prefix` і `DefaultBranch`) | Code (read). Дозвіл «force push» - це параметр безпеки, його не читають |
| Bitbucket Cloud | обмеження гілок, що зупиняють push (`push`, `force`, `delete`) | `repository:admin`. Обмеження на моделі розгалуження не розв'язується |
| Bitbucket Data Center | дозволи гілок, що зупиняють force push (`fast-forward-only`, `pull-request-only`, `read-only`) | адміністратор репозиторію |

Сторінку налаштувань захисту (а також типової гілки й видалення репозиторію) будують із віддаленої URL
репозиторію для GitHub, GitLab, Azure DevOps і Bitbucket, навіть коли репозиторій не прив'язано, і показують
із трьома способами обійти захист, коли хост відхиляє push.


## 7. Списки на рівні облікового запису в Radar

Radar зазвичай стежить за репозиторіями, які ви клонували. Профіль також може
показувати все, що вас стосується на всьому хості, клоновано чи ні, трьома перемикачами в
таблиці `[integrations.radar]` (усі типово вимкнені; див.
[довідник конфігурації](config-reference.md#integrationsradar-списки-на-рівні-облікового-запису)):

- **запити на рев'ю**: відкриті запити, що просять вашого рев'ю;
- **відкриті запити**: усі відкриті запити вашого власного простору імен і кожної організації чи
  групи, учасником якої ви є, або просторів імен, які ви назвете. Ніколи не весь хост;
  **Простори імен** профілю (по одному на рядок у Налаштування > Інтеграції > Radar, за бажання
  як регулярні вирази) обмежують усі три списки: рядок збігається з повним шляхом репозиторію, коли
  дорівнює йому або є префіксом шляху на `/` (`ptm` залишає `ptm/produits/x`, але не `ptmx/y`), і
  застосовується до рядків, які повертає хост, а також на боці сервера там, де пошук хоста це
  дозволяє (кваліфікатори GitHub `user:` / `repo:`);
- **призначені issues**: відкриті issues, призначені вам.

Відповідають GitHub, GitLab (зокрема self-managed), Gitea, Forgejo, Azure DevOps (Services
і Server), Bitbucket Data Center і Gerrit. Як питають кожного:

| Хост | Запити | Issues |
|---|---|---|
| Azure DevOps | активні pull request'и всієї організації (`searchCriteria.reviewerId` для тих, що чекають на вас; запит, за який ви вже проголосували, пропускається); коли сервер відхиляє маршрут рівня організації, перші 20 проєктів питаються по одному. `namespaces` - це назви проєктів | work items, призначені вам, що не Done, Closed чи Removed |
| Bitbucket Data Center | ваша панель: роль `REVIEWER` без схвалення для запитів на рев'ю, `AUTHOR` і `PARTICIPANT` для відкритих запитів; `namespaces` - це ключі проєктів | немає (Data Center не має трекера issues; примітка про це каже) |
| Gerrit | `is:open reviewer:self -owner:self -is:ignored`; відкриті запити - це `is:open projects:<prefix>` для кожного простору імен (префікс шляху проєкту) або ваші власні й переглянуті зміни, коли жодного не названо; зміна work-in-progress - це чернетка | немає |

Bitbucket Cloud не має рядків рівня облікового запису: він не пропонує кінцевої точки, що перелічує
запити між репозиторіями, а питати кожен репозиторій було б забагато
викликів. Його клоновані репозиторії зберігають власні списки, і `gitpoulpi hosting
radar --id <bitbucket>` про це каже. Коли Gerrit має більше змін, ніж межа, яку він
повертає, список позначається обрізаним з приміткою.

Чернетки пропускаються, якщо ви їх не залишите. Кожен список обмежений: 300 рядків кожного виду, з
приміткою, скільки ще було, а на GitHub кілька викликів пошуку за
раунд, бо його API пошуку дозволяє лише 30 на хвилину. Простір імен, який токен
не може прочитати, стає приміткою, а решта все одно завантажується; відхилений токен або
ліміт запитів валить лише цей профіль. Відповіді використовуються повторно п'ять хвилин
(`radar-account.json` у папці конфігурації).

У Налаштування > Інтеграції підключений профіль code-host має блок **Radar**
під своїм ключем SSH: по прапорцю на кожен список (*Запити, що чекають на моє рев'ю*,
*Усі відкриті запити*, *Включати чернетки*, *Issues, призначені мені*, останній
відсутній для хостів без issues), поле *Простори імен* (один запис на рядок: ім'я, що
збігається з цією групою чи власником і всім, що нижче, або регулярний вираз на рядок, коли
позначено *Регулярні вирази*; порожньо означає ваш власний і кожен, до якого ви належите) і вибір *Запит із репозиторію, який не клоновано*:
*Питати*, *Клонувати* або *Рев'ю через API*.
Усе зберігається, щойно ви змінюєте. Хости без запиту рівня облікового запису (Bitbucket
Cloud) замість цього показують один рядок із поясненням. Палітра команд досягає блоку
через *Налаштування: параметри Radar профілю...*, а пошук у Налаштуваннях знаходить кожен
елемент за його підписом.

З командного рядка: `gitpoulpi hosting integrations radar <id> --review-requests on`
вмикає список, `gitpoulpi hosting radar --json` друкує списки (а
`--refresh` обходить кеш). ШІ-агенти мають ті самі дві команди через MCP
(`hosting_radar`, `hosting_integrations_radar`).

## 8. Дії від імені бота GitHub App

Проєкт, який не повинен показувати чиєсь ім'я, може робити все на хостингу через **GitHub App**: кожен коментар,
рев'ю, закриття чи повторне відкриття й зміна мітки тоді з'являється як `<app-slug>[bot]`. Це працює для одного
репозиторію за раз і лишає ваші інші репозиторії на вашому власному токені.

1. Створіть GitHub App для організації з дозволами **Issues** і **Pull requests**, виставленими на *Read & write* (і
   *Contents: read*, щоб pull requests можна було перелічувати й рев'ювати), і встановіть його в репозиторій.
2. Напишіть невеликий скрипт, що виводить **токен встановлення** у стандартний вивід (приватний ключ App підписує
   короткоживучий JWT, який обмінюється на токен, чинний одну годину). GitPoulpi ніколи не бачить ключа.
3. У **Налаштування > Налаштування репозиторію > SSH і облікові дані** виберіть **Команда токена** під HTTPS,
   введіть скрипт як **Команда**, а хост (`github.com`) у **Хости** і позначте **Використовувати для API хостингу
   (issues, pull requests)**. Збережіть і підтвердьте команду (людина завжди підтверджує її разом із SHA-256). З
   командного рядка: `gitpoulpi repo-auth set --https token-command --hosts github.com --use-for-hosting --yes
   --command ./app-token.sh`.

Що змінюється для цього репозиторію:

- Його виклики issues і pull request (перелік, створення, коментування, рев'ю, злиття, закриття, мітки)
  використовують токен команди з тим самим 30-секундним лімітом, кешем у пам'яті й маскуванням, що й вхід git. Коли
  хостинг відповідає 401, бо токен прострочився, команду питають ще раз. Якщо команда не може виконатися, виклик
  відхиляється: ваш особистий токен ніколи не є запасним варіантом.
- Немає «мене»: токен встановлення не може спитати, хто він. Заголовок розділу називає профіль із **(бот App)**, а
  фільтри, побудовані на «мені» (*Призначені мені*, *Мої*, *Чекають мого рев'ю*), нічого не мають із чим
  зіставляти. Нічого не показується як помилка.
- **Публікувати як.** Кожне повідомлення, яке публікує GitPoulpi, показується з іменем, від якого його опубліковано
  (*Публікація від my-app[bot] (бот GitHub App)* під заголовком [бесіди](conversations.md#публікація-від-імені) і в її полі
  коментаря; `posted_as` у відповіді CLI). З особистим токеном це ваш логін (`GET /user`). З токеном App це ім'я
  **Публікувати як**, наприклад `my-app[bot]`: задайте його для всіх репозиторіїв у **Налаштування > Інтеграції**
  (`general.hosting_post_as`, також `gitpoulpi config set general.hosting_post_as my-app[bot]`) або для одного
  репозиторію в **Налаштування > Налаштування репозиторію > SSH і облікові дані > Хостинг**, де воно перемагає.
  Якщо лишити порожнім, GitPoulpi питає GitHub (GraphQL `viewer { login }`), а інакше дізнається ім'я з автора
  першого коментаря, який опублікує, і зберігає його разом із репозиторієм. Це ім'я також те, за чим розпізнаються
  ваші власні коментарі, тож змінювати й видаляти пропонується лише їх (коментарі App мають іще походити з
  облікового запису бота); поки воно невідоме, змінювати можна лише коментарі, опубліковані цим встановленням.
- App не можна призначити. Поєднайте це налаштування із заблокованим призначенням нижче.
- Увімкнення чи вимкнення **Використовувати для API хостингу** потребує людини, як і нова команда.

Лише профілі GitHub використовують токен репозиторію так; інші хостинги лишають власний токен профілю. (Токен
доступу проєкту чи групи GitLab - теж бот: це токен профілю, показаний як *бот проєкту*, і нічого налаштовувати не
треба.)

### Блокування призначення в репозиторії

У **Налаштування > Налаштування репозиторію > SSH і облікові дані** є рядок **Призначення** (типово **Дозволено**,
або **Заблоковано**; зберігається одразу). Коли заблоковано, призначення в issues і pull requests цього репозиторію
неможливе, хто б не просив:

- вибір виконавців прибрано з форм нового issue й нового pull request (із приміткою про причину), команда палітри
  *Хостинг: змінити виконавців...* сіра з причиною, а меню рядка каже про це замість відкривати вибір;
- кожен клієнт відхиляє призначення ще до надсилання будь-чого, зокрема виконавців, переданих під час створення
  issue чи pull request: CLI відповідає `{"refused": {"reason": "assignment_blocked", ...}}` з кодом виходу 2, а
  агент через MCP отримує ту саму відмову;
- наявні виконавці лишаються видимими (лише для читання).

`gitpoulpi hosting assignment` показує налаштування, `--block` його вмикає, а `--allow` вимикає знову; дозволити
знову може лише людина (сервер MCP не може).

## 9. З командного рядка

```
echo $TOKEN | gitpoulpi hosting login --id my-gitlab --token-stdin
gitpoulpi hosting integrations list --json
gitpoulpi hosting prs --mine --json
gitpoulpi hosting edit-url --branch my-branch --open
gitpoulpi hosting open pr 12 --browser
gitpoulpi hosting pr-edit 12 --add-reviewer ann --add-label bug --milestone v1.0
gitpoulpi hosting radar --what review --json
gitpoulpi hosting assignment --block
```

Кожну команду див. у [довіднику CLI](cli-reference.md#команди). Токен ніколи не
приймається як аргумент, а сервер MCP не надає `hosting login`, тож токен ніколи
не проходить через агента. `hosting login` виводить `stored: "os"`, коли сховище
облікових даних ОС зберігає токен, або `stored: "session"` разом із `store_error`, коли сховище
відмовило, а токен лежить у пам'яті лише на цей сеанс.

## Усунення несправностей

| Симптом | Що робити |
|---|---|
| *Підключити* завершується помилкою автентифікації | Токен хибний, прострочений або відкликаний. Створіть новий. |
| Scope перелічено червоним | Токен його не має. Підключення працює, але ця функція - ні. Додайте scope на хостингу, потім **Змінити** і вставте новий токен. |
| На бічній панелі немає розділу PULL REQUESTS | Жоден увімкнений профіль не підключено. Підключіть один, потім прив'яжіть репозиторій у випадаючому списку розділу. |
| Рядок *Підключити знову* у списку | Токен втрачено (перезапуск без помічника облікових даних) або він прострочений. Клацніть рядок, щоб відкрити профіль. |
| Інстанс self-managed завершується помилкою | Переконайтеся, що **Домен хоста** не має шляху і що ваш комп'ютер довіряє сертифікату інстансу. |

## Відомі обмеження

- **Pull requests з форків:** Azure DevOps і Bitbucket не можуть зробити checkout
  запиту з форка (див. [Дії над рядком](pull-requests-and-issues.md#дії-над-рядком)). Azure DevOps не може
  створити pull request з форка.
- **Trello** показує щонайбільше перші 1000 карток дошки. Скористайтеся фільтром
  списків, щоб звузити. **Jira**, **Linear** і **YouTrack** перелічують щонайбільше 500
  issues за оновлення. Скористайтеся фрагментом JQL або запитом YouTrack, щоб звузити.
- **Linear** приймає одного виконавця на issue: якщо у вибірці ви позначите кількох,
  надсилається перший. Його «віха» - це **цикл** команди (віхи проєктів
  не використовуються). У **YouTrack** це поле `Fix versions`; версія
  не має номера, тож вибірка нумерує невипущені за їхньою
  позицією в проєкті. Жоден із трекерів не має pull requests.
- **Redmine** приймає одного виконавця на issue (першого з вибірки), не має міток
  і перелічує щонайбільше 500 issues за оновлення. Виконавці - це учасники проєкту
  (люди й групи), і їх розрізняють за відображуваним іменем. Колонки дошки Kanban -
  це статуси issues, а переміщення картки змінює статус; діють типові
  правила робочого процесу Redmine (роль, якій такий перехід не дозволено, отримує
  відмову, і картка повертається). «Resolved» у типових даних Redmine не є закритим статусом:
  колонка «Закриті» - це статуси «Closed» і «Rejected».
- **Bitbucket Data Center** не має посилань для браузера для нових pull requests,
  гілок чи commit'ів. Сторінки pull requests відкриваються як звичайно.
- **Azure DevOps** не показує аватарів авторів. Фільтри «мої» та «чекають мого
  рев'ю» потребують кінцевої точки, що може відхиляти персональні токени доступу.
  У такому разі профіль підключається без імені користувача, і ці два фільтри
  недоступні. Недійсний токен призводить до сторінки входу замість помилки; GitPoulpi
  повідомляє про це як про відхилений токен.
- **Gitea і Forgejo:** чернетка - це запит, заголовок якого починається з `WIP:`
  (у сервера немає прапорця чернетки під час створення). Запит перелічує як рев'юерів
  усіх, хто вже його переглянув, а відкликання запиту на рев'ю прибирає лише
  незавершені. Pull requests з локальної гілки форка checkout'яться
  через `refs/pull/<n>/head`, як у GitHub. Згадки шукаються фільтром
  сервера `mentioned_by`. Сервер не показує scopes токена, тож
  відсутній виявляється лише коли виклик відхиляється.
- **Дошка issues** переміщує картки в кожному джерелі issues. У Jira переміщення виконує перехід робочого процесу, що
  веде до колонки; перехід, який вимагає полів (наприклад, резолюцію), Jira відхиляє, і картка повертається з її
  повідомленням. В Azure DevOps тип робочого елемента без цільового стану повертається з причиною.
- **Bitbucket:** паролів застосунків більше не існує; використовуйте токен API.
  Репозиторії перелічуються робочий простір за робочим простором.
- **Jira Cloud:** працюють лише класичні токени API (без токенів зі scopes, без
  OAuth). Нове issue Jira отримує опис простим текстом.
- **Бесіди:** спершу завантажуються найновіші 300 записів (решта через **Завантажити старіші**); коментар, зміна чи
  видалення, опубліковані з GitPoulpi, - це дія назовні й не скасовуються з нього; чого не вміє кожен хостинг, є в
  [таблиці](conversations.md#чого-не-вміє-кожен-хостинг). У Gerrit повідомлення чи коментар не можна ні змінити, ні видалити, а текст
  Gerrit - простий.
- Створення pull request, work item, issue чи картки відбувається на хостингу й
  **не може бути скасоване** з GitPoulpi. Checkout запиту можна скасувати як
  звичайно.
