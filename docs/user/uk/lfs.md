# Git LFS

Git LFS («Large File Storage») тримає великі файли (файли дизайну, відео, набори даних) поза історією репозиторію: git зберігає замість них трирядковий текстовий *покажчик*, а справжній вміст лежить на сервері LFS і в локальному кеші в `.git/lfs`.

GitPoulpi не потребує для цього жодного облікового запису. LFS використовує облікові дані, які вже використовує ваш remote (ваш credential helper git або ssh-agent).

## Що потребує програми `git-lfs`, а що ні

GitPoulpi запускає стандартну програму `git-lfs` для всього, що перетворює чи переміщує файли (install, track, fetch, pull, push, блокування).

Читання *стану* LFS програми не потребує: чи використовує репозиторій LFS, які файли є покажчиками, який їхній розмір і чи справжній об'єкт уже збережено локально.

| | потребує `git-lfs` |
|---|---|
| `gitpoulpi lfs status` (повідомляє, що програми немає, замість того щоб завершитися помилкою) | ні |
| `gitpoulpi lfs files` | ні |
| install / track / untrack / prune | так |
| fetch / pull / push | так |
| блокування | так |

## Встановлення `git-lfs`

- **Windows**: постачається з Git for Windows; або `winget install GitHub.GitLFS`.
- **Debian / Ubuntu**: `apt install git-lfs`.
- **macOS**: `brew install git-lfs`.
- Решта: https://git-lfs.com

Потрібна версія 3.0 або новіша. Після встановлення GitPoulpi помічає це протягом хвилини (або одразу під час `lfs status`).

## Коли `git-lfs` немає

GitPoulpi через це ніколи не аварійно не завершується й не виходить:

- `gitpoulpi lfs status` виконується успішно й каже `git-lfs: not installed` з посиланням на встановлення.
- Операція, що потребує програми, завершується помилкою з чітким повідомленням, яке закінчується посиланням на встановлення (`https://git-lfs.com`), і ненульовим кодом завершення; через MCP інструмент повертає це повідомлення.
- Репозиторій, що використовує LFS, усе одно відкривається; його великі файли просто показуються як покажчики, доки програму не встановлено.

## Перегляд файлів LFS

```
gitpoulpi lfs status            # program, patterns, filters, hook
gitpoulpi lfs files             # pointer files in the index, with size and local/not downloaded
gitpoulpi lfs files --at v1.0   # ... as of a revision
gitpoulpi show big.bin --at HEAD  # reports "Git LFS object, 12.3 MB, sha256:..." instead of pointer text
```

## Налаштування репозиторію: install, track, untrack

```
gitpoulpi lfs install                 # filters + hooks for THIS repository (git lfs install --local)
gitpoulpi lfs install --user          # into your global git config instead (never done silently)
gitpoulpi lfs track '*.psd'           # route *.psd through LFS
gitpoulpi lfs track '*.psd' --lockable   # ... and make them read-only until locked
gitpoulpi lfs track '*.bin' --renormalize  # ... and re-stage already-committed *.bin as pointers
gitpoulpi lfs untrack '*.psd'
gitpoulpi lfs prune                   # delete old, already-pushed objects from the local store
```

- `install` типово пише у власні `.git/config` і hooks репозиторію, тож ваша глобальна конфігурація git ніколи не змінюється, якщо ви не передасте `--user`.
- `track` і `untrack` редагують `.gitattributes` і залишають його **без stage**: він показується як звичайна зміна робочого дерева, яку ви комітите самі. Файли, додані *після* track, зберігаються як покажчики в наступному commit'і.
- Файли, які **вже закомічено** як звичайний вміст, залишаються звичайними в історії. `--renormalize` повторно додає їх у stage, щоб ваш наступний commit замінив їх покажчиками. Щоб перенести їх і в усіх минулих commit'ах, скористайтеся правилом переписування історії *Перенести файли в LFS* (див. [Переписування історії](history-rewrite.md#перенесення-файлів-у-git-lfs-або-з-нього)); воно власне для GitPoulpi, це не `git lfs migrate`.
- Беріть шаблон у лапки, щоб оболонка його не розгортала.
- Через MCP це звичайні мутації (`lfs_install`, `lfs_track`, `lfs_untrack`, `lfs_prune`), що підпадають під обмеження `[mcp]` у `config.toml`.

## Переміщення об'єктів: fetch, pull, push

```
gitpoulpi lfs fetch [--remote origin] [--all]   # download objects into the local store; working tree untouched
gitpoulpi lfs pull  [--remote origin]           # fetch, then replace pointer files with the real content
gitpoulpi lfs push  [--remote origin] [--all]   # upload the current branch's objects (or every ref with --all)
```

- Remote типово є типовим remote репозиторію, як у `fetch` і `push`.
- Облікові дані ті, що зазвичай у вашого remote (credential helper, ssh-agent). GitPoulpi ніколи не просить власного облікового запису.
- `pull` встановлює фільтри LFS для цього репозиторію, якщо їх немає: без них git-lfs завантажує об'єкти, але пропускає заміну покажчиків, і пізніший checkout повернув би покажчики.
- MCP розглядає `lfs push` як `push`: руйнівний інструмент (він змінює remote).
- Вікно показує перебіг передачі (файли та байти) у рядку стану. CLI чекає на результат.

### Checkout вмісту: `lfs checkout`

```
gitpoulpi lfs checkout [<path>...]   # offline: write real content over the pointer files, from the local store
```

Він ніколи нічого не завантажує (це `lfs pull`); об'єкти, яких немає в локальному сховищі, залишаються покажчиками. Як і `pull`, він спершу встановлює фільтри LFS репозиторію, коли жодного не налаштовано. Як і кожну операцію LFS, його не можна скасувати; див. [Скасування й повторення](undo-redo.md). Через MCP це `lfs_checkout` (запис, не руйнівний).

### Кнопка LFS на панелі інструментів, а також pull / push

На панелі інструментів після **Pop** є кнопка **`LFS ▾`** (прихована, коли `git.lfs_enabled` вимкнено, і в репозиторії, де LFS не ініціалізовано й не використано в його `.gitattributes`: див. [Налаштування > LFS](settings.md#лише-для-репозиторію-lfs)). Клацання відкриває випадаючий список: **Fetch усіх файлів LFS** (`lfs fetch --all`), **Checkout усіх файлів LFS** (`lfs checkout`), **Pull усіх файлів LFS** (`lfs pull`), **Push усіх файлів LFS** (`lfs push --all`, об'єкти кожного ref) і **Очистити локальне сховище LFS** (`lfs prune`). Кожен рядок є також командою палітри (`LFS: fetch усіх об'єктів`, `LFS: Checkout усіх файлів`, `LFS: pull об'єктів`, `LFS: push усіх об'єктів`, `LFS: очистити локальні об'єкти`). `LFS: відкрити меню` відкриває випадаючий список. Кожен має комбінацію `Ctrl+G`: `l` для меню, потім `Shift+F`, `Shift+K`, `Shift+L`, `Shift+J` і `Shift+V` для рядків. Змінити їх можна в *Налаштування > Клавіатура й миша*. Коли `git-lfs` немає, кожен рядок веде до діалогу встановлення.

![Випадаючий список LFS на панелі інструментів: fetch, checkout, pull і push усіх файлів LFS та очищення локального сховища](../images/lfs-menu.png)

**Pull і push самі дбають про LFS.** У репозиторії, що використовує LFS, із встановленим `git-lfs` звичайний `pull` спершу перевіряє, що фільтри LFS репозиторію встановлено, а звичайний `push` перевіряє його hook `pre-push`. Коли чогось бракує, GitPoulpi перед передачею запускає `git lfs install --local` (лише цей репозиторій), а рядок стану каже «фільтри LFS встановлено». Без hook push не вивантажив би жодних об'єктів LFS. Вимкніть це через `git.lfs_autofix_filters = false` (*Налаштування > Git і кодування > Встановлювати фільтри LFS перед pull і push*). Звичайний `push` і далі вивантажує лише об'єкти надісланої гілки, ніколи не всіх ref; prune ніколи не буває неявним.

## Блокування файлів

Деякі файли не можна злити (файл Photoshop, рівень, двійковий ресурс). *Блокування* Git LFS дають одній людині змогу сказати «я це редагую»: ніхто інший не може заблокувати цей файл чи надіслати до нього зміни, доки його не розблоковано.

```
gitpoulpi lfs locks  [--remote origin]              # who holds which file (yours are marked)
gitpoulpi lfs lock   assets/hero.psd [--remote origin]
gitpoulpi lfs unlock assets/hero.psd [--remote origin] [--force]
```

- Блокування є можливістю **сервера LFS** (її мають GitHub, GitLab і Gitea). Воно досягається власними обліковими даними remote; GitPoulpi не має власного облікового запису.
- Сервер без блокувань змушує `lock` завершитися помилкою з повідомленням про це (типізована `LfsLockingUnsupported`). `locks` на такому сервері нічого не перелічує, що саме й повідомляє сам git-lfs.
- Відстеження шаблону з `--lockable` (`lfs track '*.psd' --lockable`) робить ці файли доступними лише для читання, доки ви їх не заблокуєте.
- `unlock` чужого блокування відхиляється; `--force` ламає його, тому MCP розглядає `lfs_unlock` як руйнівний інструмент. `lfs_locks` лише читає.

## Клонування репозиторію LFS

`gitpoulpi clone <url>` (і діалог «Клонувати» в TUI) робить checkout репозиторію *без* запуску фільтрів LFS, а потім, коли репозиторій використовує LFS і `git-lfs` встановлено, завантажує об'єкти через `git lfs pull` (встановлюючи фільтри для цього репозиторію, якщо жодного не налаштовано) і показує це як окрему фазу, *Завантаження об'єктів LFS*. `--no-lfs` пропускає цей крок і залишає покажчики.

Клонування **ніколи не завершується помилкою через LFS**: якщо `git-lfs` немає або завантаження не вдалося, клонування все одно успішне, а великі файли залишаються покажчиками; статус LFS репозиторію пояснює чому, а `gitpoulpi lfs pull` завершить справу, щойно проблему буде усунено.

## У текстовому інтерфейсі

- **Мітка `LFS`.** Файл, збережений через Git LFS, має невелику мітку `LFS` після імені в списках Unstaged і Staged панелі Status та у списку змінених файлів commit'у.
- **Картка diff.** Відкриття diff файлу LFS показує картку замість тексту покажчика: `Об'єкт Git LFS`, `1.2 MB -> 1.4 MB`, короткі старий і новий oid та чи новий об'єкт збережено локально, чи він `не завантажено`. Натисніть `r`, щоб побачити сирий diff покажчика, ще раз `r`, щоб повернутися. До файлу LFS застосовний лише stage на рівні файлу (немає hunk чи рядків для stage). Під карткою **Відкрити типовою програмою** і **Відкрити в** (`o`, `Shift+O` або палітра) відкривають справжній файл, ніколи не покажчик: див. [Відкрити в](open-in.md#файли-git-lfs).
- **Перегляд файлу** файлу LFS каже `Об'єкт Git LFS, 12.3 MB, sha256:ab12cd34...` і де взяти вміст.
- **Банер.** Для репозиторію, що використовує LFS, коли `git-lfs` немає або він старіший за 3.0, банер на панелі Status повідомляє про це. Клацніть його (або скористайтеся пунктом палітри *LFS: відкрити сторінку встановлення*), щоб відкрити https://git-lfs.com. Більше нічого не змінюється: вікно відкривається, diff працюють, великі файли просто показуються як покажчики.
- **Меню файлу й палітра.** Клацніть змінений файл на панелі Status правою кнопкою: *Відстежувати через LFS: цей файл* / *це розширення* для звичайного файлу; *Заблокувати файл (LFS)*, *Розблокувати файл (LFS)* або *Примусово розблокувати (LFS, чуже блокування)* для файлу LFS залежно від того, хто тримає його блокування. Рядок заблокованого файлу каже `заблоковано: <ім'я>`. Усе є також командою палітри (`Ctrl+P`, введіть `LFS`): ініціалізувати, відстежувати чи не відстежувати шаблон, fetch, pull або push об'єктів, очистити, показати блокування, відкрити сторінку встановлення.
- **Невдала дія сама пояснює себе.** Якщо дія LFS не вдалася, бо `git-lfs` немає, діалог несе повідомлення і кнопку *Відкрити сторінку встановлення*.
- **Налаштування.** *Налаштування > LFS* (для кожного репозиторію) показує, чи ініціалізовано LFS, перелічує відстежувані шаблони й має кнопку **Налаштувати LFS тут**. *Git і кодування* (для кожного репозиторію) має перемикач **Git LFS**, рядок лише для читання **Програма git-lfs** і кнопку **Ініціалізувати LFS для цього репозиторію**.
- Якщо **Git LFS** вимкнено (`git.lfs_enabled = false`, див. [довідник конфігурації](config-reference.md)), усе це приховано. Власні фільтри LFS git усе одно працюють.
- Стан LFS читається невдовзі після відкриття репозиторію, після кожної зміни, під час ручного оновлення, коли змінюється `.gitattributes`, і кожні десять секунд для репозиторію, що використовує LFS.

## Відомі обмеження

- Репозиторій, шаблони LFS якого лежать лише у *вкладеному* `.gitattributes` (не кореневому й не `.git/info/attributes`), визначається як такий, що використовує LFS, лише коли має сховище об'єктів LFS (`.git/lfs`).
- Сам `git lfs migrate` не використовується. Перенесення файлів у LFS чи з нього по всій історії - це правила переписування історії *Перенести файли в LFS* / *Повернути файли з LFS*: вони працюють над локальним клоном, записується лише кореневий `.gitattributes`, а об'єкти все одно треба надіслати потім (*Надіслати об'єкти LFS* у панелі результату або `lfs push --all`).
