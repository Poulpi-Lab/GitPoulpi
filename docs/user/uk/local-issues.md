# Локальні issues і Obsidian

Тримайте свої issues як папку нотаток Markdown: без облікового запису, без токена, без мережі. Папка може бути всередині
репозиторію (`docs/issues/`, закомічена разом із кодом) або будь-де на диску, наприклад підпапкою
сховища [Obsidian](https://obsidian.md). GitPoulpi читає й записує нотатки. Obsidian, будь-який редактор чи shell можуть змінювати
їх водночас, а списки слідом оновлюються.

![Локальні issues Markdown на бічній панелі з меню рядка однієї нотатки: відкрити нотатку, закрити її, змінити її мітки чи віху](../images/local-issues.png)

## Налаштування

1. **Налаштування > Інтеграції > Трекери issues > Локальний Markdown > Додати профіль.** Введіть папку або натисніть
   **Огляд...** і виберіть її. Відносна папка (`docs/issues`) читається відносно кожного репозиторію, до якого вона прив'язана;
   абсолютна (`/home/me/Vault/Projects/Issues`) однакова всюди. Вводити токен не потрібно.
   - CLI: `gitpoulpi hosting integrations add --kind local_markdown --path docs/issues`.
2. У репозиторії відкрийте розділ **ISSUES** бічної панелі, виберіть провайдера **Локальний Markdown - <назва>** (папка
   вибирається разом із ним; список репозиторіїв показує папку та її прямі підпапки, якщо вам потрібна інша).
   - CLI: `gitpoulpi hosting link issues --id <profile>` (папка профілю - типовий `--project`).

Саме по собі нічого не прив'язується: як і кожне джерело issues, воно вмикається окремо для кожного репозиторію.

## Коментарі до нотатки

`Enter` на рядку нотатки в розділі ISSUES або на її картці відкриває її бесіду: текст нотатки, а потім коментарі.
Коментарі зберігаються в самому файлі нотатки, в останньому розділі `## Comments`, по одному запису
`### <автор> - <час UTC>` (змінений додає `(edited <час>)`). Нічого вище цього заголовка ніколи не чіпається, тож
Obsidian і оболонка читають і змінюють той самий файл. Ви можете писати, змінювати й видаляти коментарі локального
автора (`local.me` профілю, інакше підключений користувач, ім'я, яке використовує *Призначені мені*); чужих - ні.
Поле - це звичайний редактор Markdown із переглядом, а *Запис від <ім'я> (локальна нотатка)* називає автора. Нічого
не йде мережею. Нотатка із заголовком `## Comments`, який ви написали вручну, читається як така.

## Нотатки

Одна нотатка на issue, названа `<id>-<slug>.md` (`12-crash-on-empty-name.md`), з блоком frontmatter:

```yaml
---
id: 12
title: Crash on empty name
status: todo
assignees: [kai]
labels: [bug]
milestone: v0.1
created: 2026-10-14
updated: 2026-10-14T09:30:00
---
Free Markdown. GitPoulpi never rewrites the body.
```

- Нові issues отримують `max(id) + 1`.
- GitPoulpi записує лише властивості, якими володіє (`title`, `status`, `assignees`, `labels`, `milestone`, `updated`).
  **Усі інші властивості, тіло, кінці рядків і порядок ключів зберігаються байт у байт.** Запис
  атомарний (тимчасовий файл, потім перейменування).
- Читання поблажливе: нотатка без `id` бере його з назви файлу, нотатка без `status` має `todo`, нотатка
  без frontmatter бере заголовок із першого `# heading`. Файл, що не є issue (`readme.md`), ігнорується.
- Статус - довільний текст. **Відкрите** означає «не статус виконано».

### Коментарі в нотатці

Коментар до нотатки записується в саму нотатку, в останній розділ `## Comments` (без мережі, і в Obsidian він
читається нормально):

```markdown
(текст нотатки)

## Comments

### kai - 2026-11-15T10:00:00Z
Перший коментар, **будь-який Markdown**.

### ann - 2026-11-15T11:30:00Z (edited 2026-11-15T12:00:00Z)
Другий.
```

- Запис починається з рядка, що точно дорівнює `### <автор> - <час UTC>`, з ` (edited <час UTC>)` після зміни; його
  текст триває до наступного запису. Розділ - це останній заголовок `## Comments` поза блоком коду, і він іде до кінця
  файлу, тож нічого не пишіть після нього.
- Рядок коментаря, який читався б як запис або як заголовок, зберігається з початковою зворотною скісною рискою
  (`\### ...`, яку Markdown показує як той самий текст) і читається назад без неї.
- Публікація додає в кінець і лишає все вище байт у байт (разом із кінцями рядків); зміна чи видалення переписує
  лише розділ. Публікація також зсуває `updated` нотатки (нотатці без frontmatter його не дають).
- Автор - це локальний автор профілю («я» з налаштувань Локальних issues). Змінювати чи видаляти можна лише власні
  коментарі; id коментаря - це його час і автор, а дві публікації в одну секунду розрізняються зсувом другої на
  секунду.
- Відповідей, внутрішніх коментарів і історії подій для нотатки немає.

## Що можна робити

| У розділі ISSUES | Клавіатура / палітра |
|---|---|
| Нове issue (`+` або `n`): заголовок, опис, статус, виконавці, мітки, віха | `Хостинг: нове issue...` |
| Змінити виконавців / мітки / віху з меню рядка. Виберіть із того, що папка вже використовує, або **введіть нову мітку чи логін** і виберіть рядок `Додати «...»` | `Хостинг: змінити мітки...` і подібні |
| **Закрити issue** / **Відкрити issue знову** (задає статус «виконано» або перший інший) | `Локальні issues: закрити issue...` / `відкрити issue знову...` |
| **Відкрити нотатку** (ваша типова програма для `.md`) | `Інтеграції: відкрити issue...` |
| **Відкрити в Obsidian** (лише коли папка всередині сховища, тобто вище є папка `.obsidian/`) | `Локальні issues: відкрити в Obsidian...` |
| Фільтри: Відкриті / Закриті / Усі, «Призначені мені» | випадаючий список фільтра |

«Призначені мені» збігається з налаштуванням `me` профілю, інакше з ім'ям підключеного облікового запису, інакше з назвою профілю.

Гілки й commit'и працюють, як для GitHub: «Створити гілку з issue» дає `12-crash-on-empty-name`, а `#12` у повідомленні
commit'у або `12-...` у назві гілки розпізнаються.

Зміни, зроблені поза GitPoulpi (Obsidian, shell, `git pull`), з'являються приблизно за секунду: назви файлів папки
та часи зміни перевіряються в фоновому потоці, ніколи не в потоці малювання.

## Файл конфігурації

У `config.toml`, поруч із профілем (кожен ключ необов'язковий):

```toml
[[integrations]]
id = "vault"
kind = "local_markdown"
url = "/home/me/Vault/Projects/Issues"
token_ref = "integration:vault"

[integrations.local]
statuses = ["todo", "doing", "review", "done"]   # the board's column order
done_status = "done"                            # closes an issue
reference_prefix = "LOC"                         # shown as LOC-12 instead of #12
me = "kai"                                       # who "assigned to me" means
```

Статуси, які використовують нотатки, але яких немає в `statuses`, ідуть після перелічених. `statuses` - це порядок колонок
[дошки](#дошка-kanban) (`gitpoulpi hosting issue options` його друкує).

## Дошка Kanban

![Дошка папки нотаток: одна колонка на статус, картки з виконавцями, мітками та віхою](../images/issue-board.png)

Якщо ви працюєте сам або в команді, що тримає issues поруч із кодом, папка також є дошкою Kanban.
**Заголовок ISSUES > Дошка** або **Issues: відкрити дошку** в палітрі відкриває її поверх вікна; `Esc` закриває.

- **Колонки** - це статуси: спершу ті, що перелічені в `statuses`, у цьому порядку, потім будь-який інший статус, який використовує нотатка.
  Порожня колонка все одно показується. Кожен заголовок несе кількість карток.
- **Картки** показують номер issue, заголовок (два рядки), виконавців як ініціали, мітки та віху.
  Коли колонки не вміщуються всі, дошка прокручується вбік (смуга під нею, коліщатко з `Shift` або стрілки).
- **Перемістіть картку**, перетягнувши її на іншу колонку (колонка підсвічується під вказівником), клавішами
  `Shift+Вліво` / `Shift+Вправо` або через **Дошка: перемістити картку до...** (`m`), випадаючий список колонок. Картка переміщується
  одразу; `status` нотатки переписується, як у [розділі про нотатки](#нотатки), більше нічого у файлі. Якщо запис
  не вдається, картка повертається, а помилка з'являється в рядку стану.
- **Відкрийте** картку клавішею `Enter` або подвійним клацанням: [бесіда](hosting-integration.md#5c-бесіди) нотатки відкривається у вікні, з текстом нотатки та її коментарями (пункт меню картки **Відкрити нотатку** відкриває файл у вашій типовій програмі для `.md`). `e` змінює її
  виконавців, мітки чи віху, `.` або праве клацання відкриває меню картки, `n` починає нове issue у вибраній
  колонці (форма після закриття повертається до дошки).
- **Фільтруйте** за виконавцем (`a`), міткою (`l`), віхою (`M`) або текстом (`/`); `x` їх очищає. Фільтри - це
  випадаючі списки: введіть текст, щоб звузити, `Enter` вибирає.
- **Наживо**: нотатка, змінена з Obsidian чи shell, переміщує свою картку за секунду.

Кожен жест миші має клавішу клавіатури та команду палітри (**Дошка: ...**, перелічені на сторінці
[скорочень клавіатури](keybindings.md)).

## Obsidian Bases

**Палітра: `Локальні issues: створити Obsidian Base`** (CLI: `gitpoulpi hosting issue base`) один раз записує `issues.base` поруч із
нотатками: подання *таблиці* та подання *kanban*, згруповане за `status` у порядку `statuses`. Відкрийте його в Obsidian, щоб
побачити ті самі issues там як дошку. GitPoulpi ніколи не змінює наявний файл `.base` (ваш чи попередній): він
відмовляється й каже про це. Формат відповідає синтаксису Bases в Obsidian
(<https://obsidian.md/help/bases/syntax>); для подання kanban потрібен свіжий Obsidian.

## CLI і MCP

Ті самі команди, що й для кожного джерела issues, працюють і тут: `hosting issues`, `hosting issue create [--list <status>]`,
`hosting issue edit <n> --add-label ...`, `hosting open issue <n>`, `hosting refs`. Ще чотири призначені для нотаток:
`hosting issue close <n>`, `hosting issue reopen <n>`, `hosting issue move <n> --status <s>` і `hosting issue base`.
Див. [Довідник CLI](cli-reference.md).

## Обмеження

- Нову **віху** не можна ввести у вибірці (виберіть ту, яку папка вже використовує), але `milestone:` у нотатці може
  бути будь-яким і з'являється, щойно його збережено.
- Issues - це лише нотатки безпосередньо в папці (не в підпапках).
- Видалення немає: видаліть нотатку у файловому менеджері чи Obsidian (його кошик - ваш).
