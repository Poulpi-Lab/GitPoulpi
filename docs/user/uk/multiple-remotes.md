# Кілька remote для однієї гілки

Багато репозиторіїв живуть більш ніж на одному хості: основний (`origin`), дзеркало на іншому хості, резервна копія. GitPoulpi дає змогу гілці робити push на всі з них одним клацанням і, за бажанням, отримувати зміни більш ніж з одного remote, не змінюючи того, що робить звичайний git. Жоден обліковий запис для цього не потрібен, а все зберігається у власному `.git/config` репозиторію, тож звичайний git та інші інструменти й далі працюють.

## Цілі push і джерела pull

- **Upstream** - це власне поняття git (`branch.<name>.remote` і `merge`). Це *основний* remote гілки. GitPoulpi ніколи не змінює його роботу.
- **Ціль push** - це додатковий remote, на який гілка також робить push. Кнопка Push надсилає гілку на upstream і на кожну ціль push.
- **Джерело pull** - це додатковий remote, з якого pull також бере коміти. Воно вимкнене, доки ви його не ввімкнете (прапорець **Pull теж**): зливати два remote, яких ви не обирали, - не те, чого хтось хоче за замовчуванням.

Ціль може використовувати іншу назву гілки на цьому remote (`backup` отримує `feat-x`).

## Діалог Remote

Клацніть гілку правою кнопкою та виберіть **Remote гілки <branch>...** (також у випадному списку Push, у палітрі як `Git: Remote гілки...` і клацанням по значку `⇉3` у рядку гілки в секції Refs). Він показує кожен remote репозиторію:

| Стовпець | Значення |
|---|---|
| Remote, Гілка | Remote і назва гілки на ньому. **Перейменувати на remote...** змінює цю назву для вибраного рядка. |
| Push | Позначте, щоб зробити remote ціллю push цієї гілки. |
| Pull теж | Позначте, щоб pull також інтегрував цей remote. Upstream отримується завжди. |
| Стан | Де гілка стоїть відносно нього: синхронно, попереду, позаду, нова, без зв'язку. |

Рядок із позначкою «remote зник» називає remote, який гілка ще згадує, але якого в репозиторії вже немає; **Прибрати** забуває його. Той самий діалог задає upstream (список **Upstream**), а **Скинути upstream** його очищає. **Застосувати** записує все як одну зміну, яку можна скасувати.

Репозиторій також може дати кожній новій гілці ті самі додаткові цілі: **Налаштування > Git і кодування** (сторінка репозиторію), «Додаткові цілі push для нових гілок» (прапорець на кожен remote). Їх копіюють у гілку, коли вона вперше отримує upstream; наявних гілок це не торкається.

## Push

- **Кнопка Push** на гілці з додатковими цілями: надсилає на всі. Коли кожен remote просто приймає нові коміти, виконується одразу, а вікно виконання показує, як кожен remote перетворюється на галочку. Якщо щось потребує рішення (на remote є коміти, яких у вас немає), натомість відкривається діалог плану.
- **Push ▾** (стрілка біля кнопки; також сама кнопка, коли **Кнопка Push** у Налаштуваннях має значення **питати**):
  - `Push на всі (origin, gitlab, backup)`
  - `Push лише на <remote>`, по одному на кожен remote гілки
  - `Push на вибрані remote...`: є завжди, для будь-якої гілки, навіть з одним remote
  - `Remote гілки <branch>...`
- Контекстне меню гілки та палітра (`Git: Push на всі цілі`, `Git: Push на remote...`, `Git: Push на вибрані remote...`) пропонують ті самі дії з тими самими назвами.

**Push на вибрані remote...** відкриває список усіх remote репозиторію, позначених за upstream і цілями гілки. Це лише для цього push; позначте **Запам'ятати для гілки**, щоб зберегти вибір як цілі push гілки.

### План

Перед груповим push GitPoulpi дивиться на кожен remote (швидкий запит і завантаження з цього remote лише тоді, коли він відрізняється), тож проблему на третьому remote видно ще до початку першого push. Діалог перелічує кожен remote зі станом гілки відносно нього й тим, що буде зроблено:

| Ситуація | Типова дія | Також пропонується |
|---|---|---|
| На remote немає нічого з гілки або бракує деяких комітів | Push | Пропустити |
| Remote попереду (у вас немає для нього нічого нового) | Перемотати з нього | Пропустити |
| Remote відрізняється, бо ви зробили rebase або виправили те, що надсилали | Force push (lease) | Merge, Rebase, Пропустити |
| На remote є чужі коміти | Merge з нього (Rebase, коли **Кнопка Pull** має значення rebase) | Rebase, Force push (lease), Пропустити |
| Історія не має нічого спільного з вашою | Пропустити | Force push (lease) |
| Хост відмовив гілці (захищена) | Пропустити | жодної: force теж було б відхилено |

Дія кожного рядка - це список, який можна змінити (Вліво/Вправо перемикає, Enter відкриває, `s` пропускає рядок). Merge показує, чи буде конфлікт і в яких файлах. **Force push** завжди підтверджується, називає remote і скільки комітів він замінює, завжди використовує lease (ніколи голий force) і не скасовується: результат каже, який коміт замінено, і команду, що його повертає. **Пропустити проблемні** ставить Пропустити в кожному проблемному рядку. **Запустити** (Ctrl+Enter) починає виконання.

Merge, fast-forward і rebase виконуються першими, у порядку списку, тож ваша гілка досягає остаточного стану один раз; потім push ідуть по одному remote за раз, upstream першим. Атомарного «все або нічого» між remote немає: кожен завершується власним результатом, а збій на одному (мережа, хук) не зупиняє інші. **Повторити невдалі** (або `Git: Повторити невдалий push`) пробує їх знову. Закриття вікна виконання ніколи не зупиняє запуск; `Git: Показати груповий push` повертає його.

### Конфлікти і «Продовжити»

Якщо merge або rebase запуску зупиняється на конфліктах, діалог закривається, і керування беруть звичайний банер merge та редактор конфліктів. Смуга над Log повідомляє `Груповий push призупинено (gitlab): розв'яжіть конфлікти, завершіть, потім Продовжити.` з кнопками **Продовжити** і **Скасувати групу**.

- Розв'яжіть конфлікти й завершіть merge або rebase (у GitPoulpi або звичайним git).
- **Продовжити** сіра, доки це не зроблено, і її **ніколи не натискають за вас**: ніщо не триває саме. Натисніть її (або виконайте `Git: Продовжити груповий push`), і запуск знову робить push на кожен remote з вашого нового кінчика. Після rebase remote, що ще тримає старі коміти, повертається до діалогу плану (йому тепер потрібен force push) замість того, щоб його мовчки force-нули.
- **Скасувати групу** (з підтвердженням; `Git: Скасувати груповий push`) відкидає merge або rebase, які почав запуск, і забуває запуск. Уже виконані push залишаються.

Смуга переживає перезапуск GitPoulpi, а CLI бачить той самий збережений запуск.

## Pull

- Кнопка **Pull** отримує upstream точно як раніше, якщо в гілки немає джерел pull: тоді вона отримує upstream і кожне джерело по черзі, кожне в режимі, заданому **Кнопкою Pull** у Налаштуваннях (merge, лише fast-forward або rebase). Джерело, яке не можна перемотати fast-forward, зливається (або перебазовується) як upstream; за режиму лише fast-forward джерело, якому треба більше, спершу питає.
- **Pull ▾** додає `Pull з усіх джерел (origin + gitlab)`, коли є джерела, і `Pull лише з <remote>` для кожного remote гілки: разовий pull гілки цього remote, що б не казали прапорці.
- У палітрі є `Git: Pull з усіх джерел` і `Git: Pull з одного remote...`.
- Pull, що зупиняється на конфліктах, залишає ту саму смугу з позначкою групового pull.

## Налаштування

Усі чотири на сторінці **Налаштування > Git і кодування**.

| Параметр | Типово | Значення |
|---|---|---|
| **Кнопка Push** | одразу | одразу робить push; питати спершу відкриває меню Push. |
| **Кнопка Pull** | merge | Режим кнопки Pull (merge, лише fast-forward або rebase) і джерел pull. |
| **Перевіряти всі remote перед push** | увімк. | Дивитися на кожен remote перед груповим push (CLI слідує цьому; `--no-preflight` вимикає це для одного виклику). |
| **Додаткові цілі push для нових гілок** (для репозиторію) | немає | Remote, на які нова гілка також робить push. |

## З командного рядка

```
gitpoulpi branch upstream add gitlab --pull      # a push target that is also a pull source
gitpoulpi branch upstream list                    # what the branch is set up for
gitpoulpi push --all-targets                      # upstream plus every target
gitpoulpi push --to gitlab --to backup:feat-x     # exactly these, this once
gitpoulpi pull --all-sources                      # upstream plus every pull source
gitpoulpi remote-group plan                       # what a grouped push would do, nothing changed
gitpoulpi remote-group continue                   # after resolving and concluding a stop
```

Коли remote потребує рішення, команда відповідає планом (код 3) і нічого не змінює; відповісти можна через `--resolve gitlab=merge`. Усі прапорці дивіться в [довіднику CLI](cli-reference.md). Сервер MCP має ті самі інструменти.

## Зі звичайним git

Цілі - це звичайні ключі конфігурації, тож скрипт або псевдонім може користуватися ними без GitPoulpi:

```
git config --get-all branch.feature.gitpoulpi-push-to     # one value per line: remote or remote:branch

# push the current branch to its upstream and to every target
git config alias.pushall '!b=$(git symbolic-ref --short HEAD); git push; for t in $(git config --get-all branch.$b.gitpoulpi-push-to); do r=${t%%:*}; d=${t#*:}; [ "$d" = "$t" ] && d=$b; git push "$r" "$b:$d"; done'
```

Значення - це `<remote>` (та сама назва гілки) або `<remote>:<branch>`, що саме й розбирає рядок `d=${t#*:}`. Простий псевдонім не дивиться на remote заздалегідь, не пропонує merge і не може продовжити після конфлікту: для цього є діалог.

## Варто знати

- Два remote з однією адресою помічаються («gitlab і mirror: push на ту саму URL-адресу»); другий типово пропускається.
- Хост із захищеною гілкою відхиляє force push; рядок каже про це й пропонує лише Пропустити.
