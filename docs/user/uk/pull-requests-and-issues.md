# Pull requests та issues

Читання, створення й керування pull / merge requests та issues з бічної панелі, дошки й панелі інструментів. Спершу підключіть обліковий запис і прив'яжіть репозиторій: див. [Інтеграції хостингів і трекерів issues](hosting-integration.md). Усе, що стосується одного issue чи запиту (коментарі, рев'ю, обговорення), описано в розділі [Бесіди](conversations.md); читання й рев'ю запиту - у [Рев'ю pull або merge request](review.md).

## Pull requests та issues на бічній панелі

### PULL REQUESTS

Розділ має заголовок із лічильником і `+` (створити pull request), списки
провайдера й проєкту, поле пошуку та список станів (*Відкриті*, *Merged /
закриті*, *Усі*). Далі йдуть чотири групи, кожна зі своїм лічильником:

- **Мої pull requests**: ви їх автор.
- **Призначені мені**.
- **Чекають мого рев'ю**: вас запрошено рев'юером.
- **Усі pull requests**: спершу згорнуто.

Поле пошуку фільтрує кожну групу (заголовок, номер, автор, гілка). Кожна зміна
списку станів знову опитує хостинг.

Рядок починається символом стану: `●` відкритий (зелений), `○` чернетка, `◆`
merged (фіолетовий), `✕` закритий (червоний). Запит поточної гілки виділено
жирним. Рядки мають вигляд `#12  заголовок` (GitHub, Bitbucket) або `!53  заголовок`
(GitLab, Azure DevOps).

### ISSUES

Заголовок розділу називає провайдера: `GITHUB ISSUES`, `JIRA ISSUES` тощо. Для
Azure DevOps він має вигляд `... РОБОЧІ ЕЛЕМЕНТИ`, а для Trello `... КАРТКИ`. Під
випадаючими списками: поле пошуку, список станів (*Відкриті*, *Призначені мені*,
*Закриті*, *Усі*) та issues. Рядок Jira має вигляд `ABC-12  заголовок`, а тип і
статус блякнуть, коли бічна панель достатньо широка.

![Розділ ISSUES на бічній панелі з відкритим контекстним меню issue #7, першим пунктом Відкрити бесіду](../images/issues-sidebar.png)

### Дії над рядком

- `Enter` або подвійне клацання відкриває рядок: pull request у [рев'ю](review.md) (GitHub, GitLab, Gitea,
  Forgejo, Gerrit), issue, а також запит у Azure DevOps чи Bitbucket - як [бесіду](conversations.md) у вікні, а решту - у
  вашому браузері. Пункт меню рядка **Відкрити в браузері** завжди відкриває браузер.
- Праве клацання або `.` відкриває меню рядка:
  - **Відкрити бесіду** (issues і запити, що не мають подання рев'ю), **Відкрити в браузері**, **Копіювати URL**,
    **Копіювати номер**.
  - Для pull request: **Змінити на <провайдер>**, **Checkout вихідної гілки**,
    **Переглянути commit'и вихідної гілки**. Для запиту з форка checkout має
    вигляд **Checkout pull request (форк)**, а **Переглянути** неактивне.
  - Для issue: **Створити гілку з issue**. Це відкриває введення нової гілки з
    назвою на кшталт `12-fix-the-thing` (або `ABC-123-fix-the-thing` для Jira).
  - У GitHub, GitLab, Gitea і Forgejo рядок pull request має також **Рев'ю...**
    (також **Enter** на рядку): рев'ю в застосунку, див.
    [Рев'ю pull або merge request](review.md).
  - У GitHub, GitLab, Gitea і Forgejo обидва види рядків мають також **Змінити виконавців...**,
    **Змінити мітки...** і **Задати віху...** (а в pull request - ще **Змінити рев'юерів...**):
    див. [Виконавці, рев'юери, мітки й віха](#виконавці-ревюери-мітки-й-віха).
- **Змінити на <провайдер>** має ще три шляхи: олівець `✎` на правому краї
  рядка pull request, на який наведено курсор або який вибрано, `e` на вибраному
  рядку і команда палітри *Інтеграції: змінити пов'язаний pull request на хості*
  (для запиту поточної гілки).
- Якщо вихідної гілки ще немає в репозиторії, GitPoulpi повідомляє про це. Спершу
  зробіть fetch (`Ctrl+G f`).

**Checkout pull request.** GitPoulpi отримує запит у локальну гілку `pr/<n>`
(`mr/<n>` у GitLab), що його відстежує, і перемикається на неї. У GitHub, GitLab, Gitea і Forgejo
це працює й для форків (GitPoulpi отримує спеціальний head ref хостингу).
Azure DevOps і Bitbucket отримують вихідну гілку запиту. Запит із форка там
відхиляється: додайте форк як remote і зробіть checkout його гілки самі.
Скасування повертає попередню гілку. CLI: `gitpoulpi hosting checkout-pr <n>`.

**Рев'ю pull request з командного рядка (і для агента).** У GitHub
(зокрема Enterprise), GitLab (зокрема self-managed), Gitea і Forgejo запит можна
прочитати й зробити його рев'ю, не залишаючи GitPoulpi: `hosting review show <n>` (файли,
стан злиття, перевірки), `hosting review threads <n>` (обговорення рев'ю та
бесіда), `hosting review comment`, `hosting review reply`, `hosting review resolve`
і `hosting review submit <n> --event approve|request-changes|comment
--comment path:line[:side]:text`. Diff береться з вашого репозиторію, а не з
хостингу: `hosting review fetch <n>` завантажує head запиту в
`refs/gitpoulpi/pr/<n>`, а його цільову гілку в `refs/gitpoulpi/pr/<n>-base`
(жодне з них не є гілкою, нічого не checkout'иться). Номери рядків - з цього
diff: `new` - рядок у head, `old` - рядок у merge base. У GitLab
немає стану рев'ю «вимагати змін»: його там відхиляють, нічого не надсилаючи.
Gitea і Forgejo приймають коментар лише до одного рядка (без діапазонів); обговорення - це
коментарі до одного рядка файлу. Gitea може вирішити обговорення, Forgejo 11 - ні
(у хоста немає для цього кінцевої точки: виклик про це каже). Відповідь на сервері
без кінцевої точки відповідей публікується як рев'ю з одного коментаря на тому самому рядку.
Gitea відмовляється схвалювати чи відхиляти ваш власний запит.
Без клону: додайте `--project owner/name` (GitLab: `group/project`) до `review show`, `threads`,
`comment`, `reply`, `resolve`, `submit` і `suggest`, щоб зробити рев'ю проєкту, який не є поточним репозиторієм,
`hosting review diff <n> --project P` читає diff (hunk'и по файлах) з API хостингу, а
`hosting file <path> --project P [--ref R]` читає файл у певній ревізії (GitHub, GitLab, Gitea, Forgejo і Gerrit; у Gerrit diff
набору патчів читається файл за файлом, а файл береться з гілки або, для id commit'у, з commit'у). Файл, якого хостинг
не показує в diff (завеликий), позначається `omitted`.
Інструменти MCP - ті самі команди (`hosting_review_show`, `hosting_review_submit`, `hosting_review_diff`,
`hosting_file`...).

### Виконавці, рев'юери, мітки й віха

У GitHub (зокрема Enterprise), GitLab (зокрема self-managed), Gitea і
Forgejo можна змінювати, кому призначено pull request чи issue, хто робить його рев'ю, його мітки
та віху, не залишаючи GitPoulpi. Інші провайдери нічого з цього не показують.

- **Меню рядка**: **Змінити виконавців...**, **Змінити рев'юерів...** (лише pull
  requests), **Змінити мітки...**, **Задати віху...**.
- **Палітра**: *Хостинг: змінити виконавців...*, *Хостинг: змінити рев'юерів...*,
  *Хостинг: змінити мітки...*, *Хостинг: задати віху...* спершу показують
  запити й issues бічної панелі для вибору. У
  [Radar](radar.md) ті самі чотири діють на вибраний рядок.
- Вибірка відкривається одразу й завантажує з хоста людей чи мітки проєкту (і те, що
  має елемент зараз). Рядок з індикатором з'являється приблизно за 150 мс.
  Введіть текст для фільтрації (нечіткий збіг), `Вгору` / `Вниз` рухають, `Пробіл` позначає чи
  знімає позначку, `Enter` застосовує, `Esc` скасовує, `Tab` переходить до кнопок. Клацання
  по рядку позначає його, а коліщатко прокручує. Люди мають значок з ініціалами,
  мітки - свій колір.
- Віха - це випадаючий список (з **Без віхи**, щоб очистити).
- Після **Застосувати** хост оновлюється, а списки та Radar показують
  зміну після свого наступного оновлення, яке починається одразу.

Форми створення (pull request, issue) мають ті самі вибори як ряд
кнопок: `Виконавці: немає`, `Рев'юери: немає`, `Мітки: немає`,
`Віха: немає`. У GitHub, GitLab, Gitea і Forgejo кнопка Мітки замінює введене
поле міток у формі issue. Якщо хост приймає новий pull request, але
відхиляє деякі його мітки чи людей, рядок стану про це каже.

CLI: `gitpoulpi hosting members|labels|milestones`, `hosting pr-edit <n>`,
`hosting issue edit <n>` і `--assignee`, `--reviewer`, `--label`,
`--milestone` у `hosting pr` та `hosting issue create`; див.
[довідник CLI](cli-reference.md).

### Клавіші в розділах

| Клавіша | Дія |
|---|---|
| `Enter` / подвійне клацання | відкрити бесіду в GitPoulpi, якщо хостинг її має (pull request у GitHub, GitLab, Gitea чи Gerrit відкриває рев'ю), інакше браузер |
| `o` | відкрити рядок у браузері |
| `.` / праве клацання | меню рядка |
| `e` | змінити вибраний pull request на хостингу |
| `n` | новий pull request (PULL REQUESTS) або нове issue (ISSUES) |
| `v` | відкрити список станів |
| `r` | оновити |
| `Enter` / `Space` на заголовку | згорнути або розгорнути розділ |

### Повторне підключення й офлайн

Коли токена немає, його відхилено або йому бракує scope, перший рядок розділу має
вигляд `Підключити знову (токен відхилено)`. Клацніть його або натисніть `Enter`, щоб
відкрити профіль у Налаштування > Інтеграції.

Коли хостинг недосяжний, останні списки залишаються на екрані, а заголовок показує
їхній вік (`· 5m old`). Остання відповідь також кешується на диску
(`.gitpoulpi/hosting-cache.json`), тож списки з'являються раніше, ніж відповість мережа.

## Дошка issues

Кнопка **Дошка** в заголовку ISSUES (палітра: **Issues: відкрити дошку**) показує issues прив'язаного джерела як дошку Kanban
поверх вікна. Колонки залежать від джерела:

| Джерело | Колонки | Переміщення картки |
|---|---|---|
| Локальні нотатки Markdown | статуси (`statuses` профілю, потім будь-які інші, що використовуються) | переписує `status` нотатки |
| GitHub, GitLab, Gitea, Forgejo | **Відкриті**, потім вибрані вами мітки, потім **Закриті** | міняє мітку статусу; до **Закриті** закриває issue, знову до колонки - відкриває |
| Trello | відкриті списки дошки, зліва направо | переміщує картку до списку |
| Redmine | статуси issues | змінює статус issue (діють правила робочого процесу Redmine) |
| Jira (Cloud і Data Center) | статуси проєкту, спершу «зробити», наприкінці «виконано» | виконує перехід робочого процесу, що веде до колонки (`GET`, потім `POST .../transitions`); без такого переходу картка повертається, а рядок стану каже `no transition from X to Y` |
| Azure DevOps (Services і Server) | стани типів робочих елементів проєкту, за категорією стану | задає `System.State`; робочий елемент, чий тип не має стану колонки, повертається з причиною (`a Bug has no state Done`) |

У проєкті GitHub чи GitLab **Колонки** (або `c`, або **Дошка: задати мітки колонок...**) питають мітки, що є
колонками, по порядку, наприклад `status::todo, status::doing, status::review`. Вони пропонують мітки проєкту, що
схожі на статуси. Вибір зберігається для репозиторію. Без міток дошка має вигляд Відкриті / Закриті. Переміщення картки
чіпає лише перелічені вами мітки статусу: її інші мітки лишаються. Дошка хоста перелічує відкриті issues і 60 останніх
закритих.

Перехід Jira, що вимагає обов'язкових полів (наприклад, резолюцію), Jira відхиляє, і картка повертається зі
власним повідомленням Jira: зробіть це на сайті.

Та сама дошка доступна скриптам і агентам: `gitpoulpi hosting board` виводить колонки з їхніми картками, а
`gitpoulpi hosting board move <card> <column>` переміщує одну (див. [довідник CLI](cli-reference.md)).

Картка показує номер, заголовок, виконавців як ініціали, мітки та віху. Перетягніть її на іншу колонку,
або `Shift+Вліво` / `Shift+Вправо`, або **Дошка: перемістити картку до...** (`m`). Вона переміщується одразу; приблизно за 150 мс індикатор
каже, що хост ще працює, а якщо хост відмовляє, картка повертається, і рядок стану пояснює причину. `Enter` відкриває
[бесіду](conversations.md) issue у GitPoulpi, а коли ви її закриваєте, дошка повертається; `e` змінює виконавців, мітки та віху; `n` починає нове issue у
вибраній колонці; `a`, `l`, `M` і `/` фільтрують за виконавцем, міткою, віхою й текстом, `x` очищає фільтри; `r`
читає хост знову. Дошка читає знову, коли оновлюються списки бічної панелі. У Radar дошки немає.

## Створення pull request

Відкрийте форму через `+` заголовка PULL REQUESTS, `n` у розділі або команду
палітри *Pull requests: створити pull request...*. Меню гілки також має **Почати
pull request з <гілка>...**.

Форма має:

- Вкладку для кожного підключеного профілю, що має pull requests (`Left` / `Right`
  на смузі вкладок).
- Списки **З репозиторію / Гілка** і **До репозиторію / Гілка**. Довгі списки
  можна фільтрувати. Можна ввести гілку чи репозиторій, яких списки не показують.
- **Заголовок**, заповнений темою commit'у на верхівці.
- **Опис**, багаторядковий (`Enter` додає рядок, `Tab` виходить із поля).
- Кнопки **Виконавці**, **Рев'юери**, **Мітки** та **Віха** (GitHub,
  GitLab, Gitea і Forgejo), що відкривають вибірку.
- **Надіслати як чернетку**.
- Коли ввімкнено [ШІ](ai.md): **Згенерувати заголовок і опис**.

Форма відкривається з профілем, репозиторієм і гілками поточної гілки
(`feature -> main`). Інший вихідний репозиторій створює запит із форка.

**Створити pull request** (або `Ctrl+S`) створює запит на хостингу. Результат
відкривається у вашому браузері, а рядок стану його називає.

## Створення issue

Коли розділ ISSUES має і провайдера, **і** проєкт, його заголовок має `+`
(*+ Нове issue*). Також: `n` у розділі або команда палітри
*Хостинг: нове issue...*.

Форма має **Заголовок** (обов'язковий), **Опис** (багаторядковий) і **Мітки**
(через кому, наприклад `bug, ui`; у GitHub, GitLab, Gitea і Forgejo натомість вибірку відкривають кнопки
Мітки, Виконавці та Віха). Jira та Azure DevOps додають список **Тип**.
Trello додає список **Список**. Linear і YouTrack
додають список **Статус** (стан робочого процесу, або значення `State`, з яким
починає issue). Redmine додає список **Тип** з трекерами проєкту (Bug, Feature,
Support...); міток у ньому немає, тож кнопки Мітки для нього немає, а мітка,
указана в командному рядку, відхиляється. Форма заповнює ці
списки з хостингу під час відкриття.

**Створити issue** (або `Ctrl+S`) створює його на хостингу. `Esc` або **Скасувати**
закриває форму. Якщо хостинг відмовляє (токен відхилено, бракує scope, невідомий
проєкт, невідома мітка), форма показує причину й зберігає введене вами. У разі
успіху рядок стану називає нове issue, а розділ ISSUES оновлюється.

CLI: `gitpoulpi hosting issue create --title ... [--body ... | --body-file ...]
[--label ...] [--type ...] [--list ...]`.

## Створення на вебсторінці хостингу

Форма «Нове issue» і форма «Створити pull request» мають кнопку
**Створити на <провайдер>** угорі праворуч. Клавіша - `Alt+W`. Вона відкриває
вебформу хостингу у вашому браузері, заповнену тим, що ви ввели досі. Діалог
залишається відкритим. Вона не просить токена й не робить викликів API, тож
працює й після помилки API.

- У GitHub немає параметра URL для *чернетки*, тому прапорець чернетки не
  переноситься. GitLab отримує префікс заголовка `Draft: `.
- GitLab приймає мітки лише за id, тому їх додають як швидку дію `/label ~"x"`
  наприкінці опису.
- Дуже довгий опис обрізається, щоб URL залишався коротшим за 6000 символів, із
  приміткою `[...truncated: paste the rest]`.
- У Bitbucket Data Center немає адреси вебформи, тому кнопки
  **Створити на <провайдер>** там немає.

CLI: `gitpoulpi hosting issue create ... --web` і `gitpoulpi hosting pr --web`
виводять той самий URL.

## Чип на панелі інструментів

На кінці панелі інструментів (типово праворуч) чип показує запит поточної
гілки: `GH #12` (GitHub), `GL !53` (GitLab), `AZ !12` (Azure DevOps) або
`BB #12` (Bitbucket). Його колір вказує стан: зелений відкритий, сірий чернетка,
фіолетовий merged, червоний закритий.

- Наведіть на нього курсор, щоб побачити заголовок, стан і `source → target`.
- Клацніть його або натисніть `Ctrl+G g`, щоб відкрити запит у браузері.
- Праве клацання дає **Відкрити в браузері**, **Копіювати URL**, **Оновити** і
  **Змінити профіль**.

Гілка, надіслана без запиту, показує приглушений чип `+ PR`. Клацніть його, щоб
почати pull request. Чипа немає, коли жоден профіль не підходить, коли гілку
не надіслано або коли хостинг був недосяжний. У вузькому вікні чип
ховається, щоб залишити місце для кнопок панелі інструментів.

## Коли списки оновлюються

Списки оновлюються:

- під час відкриття репозиторію;
- коли змінюється поточна гілка;
- після push або fetch;
- кожні *Оновлення Pull Requests та Issues (хвилини)*
  (`general.hosting_refresh_minutes`, типово 5, `0` вимикає таймер;
  Налаштування > Інтеграції);
- коли ви закриваєте Налаштування;
- коли ви натискаєте `r`, запускаєте *Інтеграції: оновити pull requests і issues* або
  змінюєте фільтр.

Запити ніколи не блокують вікно.

Хостинги обмежують кількість викликів. GitPoulpi надсилає назад `ETag` останньої
відповіді, тож незмінний список коштує мало (у GitHub - нічого). Коли хостинг
повідомляє, що викликів залишилося мало, рядок стану каже про це. Коли їх не
залишилося, GitPoulpi припиняє опитувати цей хостинг до скидання ліміту, а списки
залишаються як є.

## Термінологія

GitHub, Azure DevOps і Bitbucket кажуть «pull request». GitLab каже «merge
request». *Термінологія запитів на рев'ю* (`ui.pr_terminology`, у Налаштування >
Інтеграції) вибирає слово для кожної мітки, меню, команди палітри й повідомлення:

- **Авто (за хостом)**: залежить від пов'язаного провайдера репозиторію («Pull
  Request», доки нічого не прив'язано).
- **Pull Request** або **Merge Request**: завжди це слово.

Зміна застосовується одразу. CLI і MCP завжди кажуть «pull/merge request». Ця
сторінка каже «pull request».

## Посилання в повідомленнях commit'ів і назвах гілок

Коли issues або pull requests репозиторію прив'язано, посилання в повідомленні
commit'у в Подробицях commit'у підкреслюються. Клацання відкриває пов'язану сторінку.
Клавіатура: команда палітри *Інтеграції: відкрити посилання commit'у (#issue / !request)...*
(меню, коли в повідомленні кілька посилань). Репозиторій без нічого прив'язаного
не має посилань.

Що вважається посиланням, залежить від провайдера розділу ISSUES:

| ISSUES прив'язано до | У повідомленні | В назві гілки |
|---|---|---|
| GitHub, GitLab, Gitea, Forgejo | `#123` | `123-fix-login` |
| Azure DevOps | `#123` і `AB#123` | `123-fix-login` |
| Jira | `ABC-123`, лише коли `ABC` - ключ прив'язаного проєкту. Текст на кшталт `UTF-8`, `SHA-256` чи `ISO-8601` ніколи не є посиланням. | `ABC-123` будь-де в назві (`feature/ABC-123-x`), великими літерами |
| Linear | `ENG-123`, лише коли `ENG` - ключ прив'язаної команди (або команди зі списку команд профілю). `UTF-8` ніколи не є посиланням. | Власний `branchName` Linear, коли ви створюєте гілку з issue; `ENG-123` будь-де в назві зчитується назад |
| YouTrack | `ABC-123`, лише коли `ABC` - коротка назва прив'язаного проєкту (або одного зі списку проєктів профілю) | `ABC-123` будь-де в назві |
| Redmine | `#123`, лише коли Redmine - прив'язане джерело ISSUES (джерело pull requests зберігає свій власний знак) | `123-fix-login` |
| Trello | адреса `https://trello.com/c/<shortLink>`; `#12` лише коли кешована картка має номер 12 | `12-fix-login` |

| PULL REQUESTS прив'язано до | У повідомленні |
|---|---|
| GitLab, Azure DevOps | `!45` |
| GitHub, Bitbucket, Gitea, Forgejo | `#45` |

Коли обидва списки збігаються з `#N`, перемагає issue. CLI:
`gitpoulpi hosting refs --message TEXT | --commit REV | --branch NAME`.

**У бесідах.** Текст issue чи запиту читається за граматикою його хостингу, ширшою за таблицю вище: `owner/repo#7`,
`!7`, `GH-7`, `@login`, id commit'ів та інші форми, перелічені в [Перехресних посиланнях](conversations.md#перехресні-посилання).
Спершу зіставляються пов'язані джерела репозиторію, тож ключ Jira в коментарі GitHub усе одно відкриває своє issue в
застосунку. `gitpoulpi hosting markdown --body TEXT --id I` показує, що застосунок знаходить у тексті.

### Вставлення посилання на issue

У композері commit'ів кнопка `#▾` на правому краї поля «Заголовок» відкриває список
пов'язаних issues з фільтром. Issue, назване поточною гілкою, іде першим із
позначкою *(з гілки)*. `Enter` або клацання вставляє його посилання (`ABC-123`,
`#12`, `AB#12`) у позицію курсора. Клавіатура: `Alt+R` у композері. Палітра:
*Commit: вставити посилання на issue...*. Якщо список issues не прив'язано, кнопка
неактивна й каже *спершу пов'яжіть список issue на бічній панелі*. GitPoulpi
ніколи не додає посилання сам.
