# Оновлення

GitPoulpi перевіряє наявність новіших випусків і, залежно від того, як його встановлено, або замінює власні файли, або передає оновлення програмі, що його встановила. Нічого не замінюється й не перезапускається без вашої дії.

## Чип і панель

Рядок заголовка показує запущену версію (`v1.0.0`) між назвою застосунку та шляхом до репозиторію. Коли відомо про новіший випуск, чип перетворюється на `доступна v0.2.0` кольором акценту.

Клацніть по чипу, натисніть `Ctrl+N`, потім `u`, або виконайте в палітрі команд (`Ctrl+P`) **Оновлення: показати панель оновлення**: відкриється панель оновлення. Це вікно поверх застосунку: `Esc`, `q`, хрестик закриття чи клацання поза ним закриває його. Вона показує:

- запущену версію та **Встановлено через**: як GitPoulpi потрапив на цей комп'ютер (від цього залежить усе нижче);
- як стоїть оновлення (перевірка, завантаження з відсотками, готово, збій);
- кнопки процедури цього встановлення і точну команду, коли вона є;
- рядок від вашого адміністратора, коли він його задав.

Кожна кнопка має клавішу (надруковану в рядку підказки панелі) і команду палітри, тож панель працює без миші:

| Кнопка | Клавіша | Команда палітри |
|---|---|---|
| **Оновити й перезапустити** (або **Виконати оновлення**) | `u` | Оновлення: оновити зараз |
| **Копіювати команду** | `c` | Оновлення: скопіювати команду оновлення |
| **Відкрити в терміналі** | `t` | Оновлення: виконати команду оновлення в терміналі |
| **Повернути** | `v` | Оновлення: повернути попередню версію |
| **Нотатки до випуску** | `n` | Довідка: нотатки до випуску |
| **Пропустити цю версію** | `s` | Оновлення: пропустити цю версію |
| **Відкрити сповіщення** (лише зі сповіщенням безпеки) | `a` | Оновлення: відкрити сповіщення безпеки |
| **Перевірити зараз** | `r` | Оновлення: перевірити зараз |
| **Закрити** | `Esc` | |

Команда, що не стосується цього встановлення, у палітрі сіра з причиною (наприклад, «це встановлення оновлюється іншим способом: див. Оновлення: показати панель оновлення»).

## Що відбувається для кожного встановлення

| Встановлено через | Перевірка | Що робить панель | Повернення |
|---|---|---|---|
| Архів випуску або `install.sh` | Випуски GitHub | **Оновити й перезапустити**: GitPoulpi завантажує й перевіряє архів, закривається, замінює свої файли й знову відкривається в тому самому терміналі. | **Повернути** міняє попередні файли назад. |
| Інсталятор Windows, лише для мене | Випуски GitHub | Те саме, без запиту. У Windows він знову відкривається в новому вікні. | **Повернути** міняє назад. |
| Інсталятор Windows, усі користувачі | Випуски GitHub | Те саме, але Windows просить підтвердження адміністратора. Сеанси GitPoulpi інших користувачів на комп'ютері закриваються, що втрачає їхній незбережений ввід. Якщо ви відмовитеся, нічого не змінюється. | **Повернути** міняє назад, з тим самим запитом. |
| Chocolatey | Спільнотна стрічка Chocolatey | **Виконати оновлення** виконує `choco upgrade gitpoulpi -y` (Windows просить підтвердження адміністратора). | Панель показує `choco install gitpoulpi --version <previous> --allow-downgrade -y`. |
| Chocolatey, внутрішня стрічка | Стрічка вашої організації | **Виконати оновлення** виконує `choco upgrade gitpoulpi -y --source=<feed>`. Параметри пакунка не надсилаються знову, тож розгорнута конфігурація лишається недоторканою. | Той самий рядок `choco install` зі стрічкою. |
| winget | Випуски GitHub | **Виконати оновлення** виконує `winget upgrade --id GitPoulpi.GitPoulpi --exact --silent` із прийнятими угодами. winget сам просить підтвердження адміністратора, коли встановлення загальномашинне. | Панель показує `winget install --id GitPoulpi.GitPoulpi --version <previous>`. |
| Scoop | Випуски GitHub | **Виконати оновлення** виконує `scoop update gitpoulpi` після повного закриття GitPoulpi. | **Повернути** виконує `scoop reset gitpoulpi@<previous>`. |
| Homebrew | Випуски GitHub | **Виконати оновлення** виконує `brew upgrade gitpoulpi` у цьому терміналі. | Панель показує `brew install gitpoulpi@<previous>`. |
| apt | Випуски GitHub | Панель показує `sudo apt update && sudo apt install --only-upgrade gitpoulpi` з **Копіювати команду** і **Відкрити в терміналі**. GitPoulpi ніколи не виконує `sudo` за вас. Без репозиторію apt для GitPoulpi на цьому комп'ютері вона каже натомість завантажити новий `.deb`. | Панель показує `sudo apt install gitpoulpi=<previous>`. |
| Пакунок MSI | Випуски GitHub або джерело вашого адміністратора | Нічого виконувати: встановлення керується вашим адміністратором, чиє повідомлення показує панель. | Не пропонується. |
| AUR | Випуски GitHub | Панель показує `yay -S gitpoulpi-bin` (або `paru`, що знайдеться першим; без помічника - кроки `git clone` і `makepkg -si`). | Не пропонується. |
| cargo | Випуски GitHub | Панель показує `cargo binstall gitpoulpi-cli`, коли встановлено `cargo-binstall`, інакше `cargo install --locked --git https://github.com/Poulpi-Lab/GitPoulpi --tag releases/v<version> gitpoulpi-cli`. | Та сама команда з попереднім тегом. |
| Образ Docker | Випуски GitHub | Нічого виконувати: образ замінюється. Панель показує `docker pull poulpilab/gitpoulpi:<version>` і `:latest`. Див. [Запуск у Docker](docker.md). | Панель показує `docker pull poulpilab/gitpoulpi:<previous>`. |
| Архів випуску в теці, у яку ви не можете писати | Випуски GitHub | Панель каже, що GitPoulpi не може там замінити себе, і вказує на **Завантажити**. | Не пропонується. |
| Збірка для розробки (`cargo build`) | немає | Ніколи не оновлюється. Чип показує версію і більше нічого; панель каже, що запису про встановлення немає. | Не пропонується. |

Рядки «показує» самі нічого не виконують. **Відкрити в терміналі** відкриває ваш термінал із набраною командою, а ви натискаєте Enter.

Випуски завжди надходять із репозиторію проєкту на GitHub, якщо адміністратор не вкаже перевірці інше місце (внутрішню стрічку, дзеркало чи `latest.json`), див. [Корпоративне розповсюдження](enterprise-distribution.md). Нотатки до випуску беруться з випуску або з журналу змін, вбудованого в GitPoulpi, залежно від того, що доступне.

## Сповіщати й авто

`updates.mode` ([Налаштування > Синхронізація](settings.md#синхронізація)):

- **Сповіщати** (типово): раз на день GitPoulpi перевіряє у фоні й показує чип. Нічого не завантажується, доки ви не натиснете кнопку.
- **Авто**: там, де GitPoulpi замінює власні файли (архів випуску, інсталятор Windows), він також завантажує й перевіряє оновлення у фоні, щойно його знаходить. Тоді чип показує **Перезапустіть для оновлення**, а перезапуск ви все одно обираєте самі. Там, де оновлення належить менеджеру пакунків, **Авто** поводиться як **Сповіщати**.
- **Вимкнено**: жодного запиту ніколи не робиться, а чип показує лише версію.

Параметр **Канал оновлень** (`updates.channel`) обирає між **Стабільний** і **Попередній** (також кандидати до випуску). Перевірка, яку ви запускаєте через **Перевірити зараз**, ігнорує обмеження раз на добу. Без мережі або поки репозиторій приватний і токен github.com не збережено, фонова перевірка тихо зазнає невдачі з одним рядком у журналі застосунку.

## Перезапуск і що ви бачите потім

Натискання **Оновити й перезапустити** чи **Виконати оновлення** зберігає ваш сеанс і закриває вікно. Окрема невелика програма, `gitpoulpi-updater`, виконує роботу, тож власні файли GitPoulpi не використовуються, поки їх замінюють, а менеджер пакунків не блокується батьківським процесом, що чекає. Вона спершу зупиняє фонові демони GitPoulpi (інші вікна й сервери MCP вашого користувача також закриваються), виконує оновлення, перевіряє, що новий `gitpoulpi --version` виводить очікувану версію, і знову запускає GitPoulpi: у тому самому терміналі в Linux і macOS, у новому вікні в Windows. Якщо перевірка не проходить, вона повертає старі файли.

Наступний запуск показує один рядок у рядку стану:

- `Оновлено до v1.4.2`
- `Не вдалося оновити: <reason>. Попередня версія лишається встановленою.`
- `Оновлення скасовано: підтвердження адміністратора відхилено. Нічого не змінено.`

Одночасно виконується лише одне оновлення; файл блокування в теці даних GitPoulpi (і ще один у теці встановлення, коли вона доступна для запису) не пускає друге, а блокування старше десяти хвилин ігнорується, тож збійне оновлення ніколи не заблокує GitPoulpi назавжди. CLI і демон не запускаються, поки існує свіже блокування.

## Повернення

Там, де GitPoulpi замінює власні файли, **Повернути** міняє попередні файли назад і перезапускає. Вони лишаються як `<name>.old` ще хвилину після запуску нової версії, потім видаляються, тож повернення призначене для першого запуску після оновлення. Там, де встановлення належить менеджеру пакунків, повернення - це команда з таблиці: панель показує або виконує її. Повернення змінює власні файли GitPoulpi, а не репозиторій, тож не входить до журналу скасувань git.

## Що перевіряється й відхиляється

Перш ніж щось замінити, GitPoulpi завантажує архів, його підпис `.minisig` і `.sha256`. Спершу він перевіряє підпис за ключем випусків проєкту, вбудованим у GitPoulpi, і довірений коментар підпису має називати цей архів і цю версію. Потім перевіряє хеш. Він відхиляє: випуск без `.minisig` (старіший випуск, опублікований до того, як випуски почали підписувати, не можна встановити через програму оновлення, зокрема закріпити його чи повернутися до нього), підпис іншим ключем, підпис для іншого файлу чи іншої версії, випуск без `.sha256`, хеш, що не збігається, архів, ім'я якого не те, що для цієї платформи (`gitpoulpi-<version>-<target>.<zip|tar.gz>`), архів, маркер якого називає іншу версію чи платформу, і посилання для завантаження поза хостами випусків GitHub (кожен перехід за перенаправленням перевіряється) або дзеркалом, яке налаштував адміністратор. Заміна відбувається повністю або зовсім ні: якщо інша програма тримає один із виконуваних файлів, GitPoulpi називає файл, нічого не змінює й лишає завантаження для іншої спроби. У Windows оновлення для всіх користувачів перевіряється повторно підвищеним кроком, який сам завантажує `.minisig` і `.sha256` і знову перевіряє обидва, тож файл, підмінений у теці завантажень користувача між ними, відхиляється. Менеджери пакунків (Chocolatey, winget, Scoop, Homebrew, apt, AUR) перевіряють власні пакунки: GitPoulpi там нічого не завантажує.

## Сповіщення безпеки

Поруч із кожним випуском проєкт публікує `security.json`: список сповіщень безпеки (ідентифікатор, серйозність, зачеплені версії як діапазон на кшталт `>=1.2.0, <1.4.3`, виправлена версія, посилання та підсумок в одне речення). Та сама щоденна перевірка, що шукає нову версію, також отримує його, з того самого місця, що й випуск: зі сторінки випуску репозиторію для GitHub, з теки `latest.json` для дзеркала, з GitHub для публічної стрічки Chocolatey. Сповіщення використовується, лише коли `security.json.minisig` перевіряється за ключем проєкту; непідписаний чи погано підписаний файл ніколи не показується (один рядок у Журналі активності каже, що його проігноровано).

Коли сповіщення називає запущену версію, чип стає червоним і показує **Сповіщення безпеки: ця версія зачеплена**, на кожному встановленні, зокрема й тих, що ними керують менеджери пакунків. Тоді панель оновлення перелічує кожне сповіщення з його серйозністю, підсумком, виправленою версією та посиланням; **Відкрити сповіщення** (`a` або **Оновлення: відкрити сповіщення безпеки** в палітрі) відкриває в браузері посилання найсерйознішого з них. Там, де встановлення належить менеджеру пакунків, панель додає «Оновіть через свій менеджер пакунків.»

З вимкненими перевірками оновлень (`updates.mode = "off"`), з політикою адміністратора, де `check` має значення `none`, і для збірки, зробленої через `cargo build`, нічого не отримується й жодне сповіщення не показується. Власна стрічка NuGet організації не змушує GitPoulpi звертатися до GitHub: її сповіщення надходять лише з дзеркала `download_base` політики.

## Параметри, заблоковані адміністратором

Адміністратор може задати режим оновлення, канал, закріплену версію, де перевіряти і чи може GitPoulpi взагалі оновлювати себе, у загальномашинній політиці. У Налаштуваннях ці рядки показують **Задано вашим адміністратором**, панель показує їхнє повідомлення, а коли самооновлення вимкнено, панель пропонує команди чи примітку замість кнопок, що замінюють файли. Нечитабельні файли політики спрацьовують безпечно: лише сповіщення, без самооновлення. Бік адміністратора описано в розділі [Корпоративне розповсюдження](enterprise-distribution.md#файл-політики-і-реєстр).

## Середовище

`GITPOULPI_UPDATE_API` спрямовує перевірку на інший корінь API (використовується тестами).
