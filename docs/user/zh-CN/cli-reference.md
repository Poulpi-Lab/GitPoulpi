# CLI 参考

不带子命令的 `gitpoulpi` 会打开窗口；带子命令时，它是一个可脚本化的 git 客户端。每条命令都经由与窗口相同的后台守护进程，因此脚本所做的更改会实时显示在已打开的 GitPoulpi 中。代理获得的 MCP 工具正是由这些命令生成的（[MCP 与代理](mcp-and-agents.md)）。`gitpoulpi <command> --help` 列出所有标志。

## 全局标志

| 标志 | 作用 |
|---|---|
| `--json` | 以 JSON 打印结果。错误也是 JSON：stdout 上的 `{"error": "..."}`，退出码为 1。 失败的 git 操作会多出 `"detail": {"operation", "command", "exit_code", "stderr"}`（运行的 git 命令（已隐去机密信息）、它的退出码和 stderr 的末尾部分；对于内置 git 库则是 `"git2": {"class", "code", "message"}`），守护进程能指出名称的失败还会多出 `"context": {"operation", "label", "args", "repo", "frontend", "request", "job"}`（操作、面向用户的名称、隐去机密信息的主要参数、仓库、请求方、请求的 id，对于 fetch 或 push 还有其作业编号）；MCP 工具返回同样的对象。不带 `--json` 时这些行输出到 stderr。 |
| `--repo <path>` | 要操作的仓库（默认：当前目录所在的仓库，与 git 相同）。 |
| `-s, --session <name>` | 要通信的会话（守护进程）。默认：由仓库根目录推导，因此在同一个仓库内打开的所有内容共用一个守护进程，两个仓库则有两个。 |
| `--backend git2\|system` | 本命令所启动的守护进程使用的后端（已在运行的守护进程保持自己的后端）。 |
| `--cwd-file <file>` | 窗口退出时写入活动标签页文件夹的位置（供 `shell-init` 使用）。 |
| `-a, --add [path]`、`--no-raise` | 把文件夹作为新标签页在已运行的 GitPoulpi 中打开，而不是再启动一个；参见[将文件夹添加到已打开的窗口](#将文件夹添加到已打开的窗口)。不接受子命令。 |
| `-l, --lang <lang>` | 仅作用于 `--help` 文本的语言：`en`、`fr`、`es`、`pt-BR`、`pt-PT`、`it`、`de`、`zh-CN`、`ja`、`ko`、`ru`、`uk`、`pl`、`cs`、`nl`、`sv`、`tr`。参见[翻译后的帮助](#翻译后的帮助)。 |

### 将文件夹添加到已打开的窗口

`gitpoulpi --add [path]`（`-a`；`gp -a` 和 `gpa` 命令别名运行的是同一段代码）会把 `path`（默认：当前目录，解析为包含它的仓库）作为新标签页在已运行的 GitPoulpi 中打开，这样你在终端里 `cd` 进入的文件夹就不会再启动第二个窗口。

- *运行中的会话*指其守护进程有响应、且附带了 GitPoulpi 窗口的会话。用户关闭了 **允许 AI 代理控制视图** 的窗口不会对外宣告自己，因此找不到（`gitpoulpi launch` 有同样的限制）。
- 有一个运行中的会话：该会话获得标签页（如果该仓库已经打开，则显示那个标签页），桌面允许时其窗口会移到前台（Windows、WezTerm、Hyprland；`--no-raise` 会跳过这一步），并用一行文字说明由哪个会话接收。
- 有多个：它们会被编号列出，附带标签页数量和仓库名称；输入编号后按 Enter（空行或按 Esc 再按 Enter 会取消，退出码 130）。stdin 没有终端时命令会失败，并提示传入 `--session NAME`。`-s NAME` 会跳过这个提问。
- 没有（或 `-s NAME` 指定的会话没有运行）：GitPoulpi 在此终端中照常启动，打开该文件夹，与 `gp [path]` 完全一样。
- 窗口会立即应用它，视为你自己的选择（没有确认提示条，也没有代理标记），除非你正在那里的表单中输入：此时窗口会在状态栏提示条中提出该标签页，退出码为 3。不在仓库内的文件夹会被拒绝（退出码 1）。

`--json` 输出一个对象：`{"action": "joined", "session", "repo", "already_open", "raised", "outcome": {...}}`（`outcome` 是窗口的应答，与 `ui show` 相同）或 `{"action": "cancelled"}`；错误是 `{"error": "..."}`。退出码：0 标签页已打开，3 已在提示条上提出，1 被拒绝或失败，130 已取消。它没有对应的 MCP 工具：想向用户展示某个仓库的代理应使用 `ui show tab`。

### 翻译后的帮助

`gitpoulpi --help` 是英文的。加上 `-l` 即可用另一种语言阅读说明：`gitpoulpi -l fr --help`、`gitpoulpi -l de commit --help`。只翻译说明文字和章节标题。命令名、标志、值名称和可选值不会改变，因此脚本和代理看到的是同一套接口。帮助语言不会从环境变量中读取：只有在你给出 `-l` 时输出才会改变。MCP 工具的描述始终是英文。

修订版本接受 git 所接受的任何写法（`HEAD~2`、分支、tag、短 sha）。hunk 和行的编号方式与 `gitpoulpi --json diff` 相同。

**查看**

|---|---|
| `status` | staged、unstaged、未跟踪和有冲突的文件。 |
| `log [--graph] [--limit N] [--skip N] [--path P] [--count]` | 历史；`--skip` + `--limit` 用于分页，`--path` 为文件历史。`--count` 只打印 `{"total": N}`，即遍历所得的 commit 数（忽略 `--limit`/`--skip`），也就是 TUI 状态栏斜杠后面的数字（`500 / 2500 commits`）。 |
| `log --format mermaid [--detail structure\|refs\|subjects\|full] [--orientation lr\|tb] [--fence] [--range A..B] [--limit N] [--subject-width N]` | 把 commit 输出为 Mermaid `gitGraph` 脚本，与 Log 的[复制为 Mermaid gitGraph](log-and-history.md#将-commit-复制为-mermaid-gitgraph)弹窗生成的相同。`--range A..B` 即 `git log A..B`（单独的 `A` 表示 `A..HEAD`）；否则取前 `--limit` 个 commit（默认 30）。详细程度、方向和围栏默认取自 `ui.mermaid_*`。带 `--json` 时：`{format, detail, commits, text}`；普通输出就是脚本。 |
| `diff [--staged] [--path P] [--name-only]` | 工作区（或 staged）的 diff，以 hunk 和行表示；`--name-only` 只列出有更改的文件及其状态。 |
| `diff --from <rev> [--to <rev\|worktree>] [--name-only]` | 比较两个修订，或比较一个修订与工作区（`--to` 默认为 `worktree`：已跟踪文件的 staged 和 unstaged 更改）。与 Log 的[比较](log-and-history.md#比较-commit)是同一份列表。 |

[--file F]` | `.mailmap`：为用过多个身份提交的人指定唯一的规范姓名和邮箱。`IDENTITY` 形如 `Name <email>`（或 `<email>`）。`list` 输出 `{identities: [{name, email, as_author, as_committer, mapped_to}], commits, has_mailmap}`：范围（当前分支、`--all-local` 或 `--ref`）内的每个姓名和邮箱，以及它作为作者和作为提交者的 commit 数（按 commit 数从多到少），和 `.mailmap` 已把它映射到的身份（`mapped_to`，没有映射时不出现）；`--mapped` / `--unmapped` 用于筛选。`check` 输出 `{identities: [{identity, shown_as, mapped}]}`：每个身份经过 `.mailmap`（以及 `mailmap.file`）后的显示结果，即 `git check-mailmap` 的回答。`add` 为每个 `--from` 向 `.mailmap` 追加一行（`Canonical Name <canonical@email> Old Name <old@email>`；文件不存在时会创建；已有的行不会重复），并输出 `{mailmap: {added, file}}`。它只编辑文件，不提交任何东西：请自行提交。这是一条可撤销的记录（`undo` 会恢复之前的文件）。`log.use_mailmap` 开启时（默认），`log`、`blame` 和 `file-history` 会立即显示规范身份，已存储的 commit 不变，也无需强制 push。若要重写 commit 本身，请用 `rewrite preview --mailmap`（一条 `mailmap` 规则：作者和提交者变成 `git log --use-mailmap` 所显示的样子；`--who` 选择对象；`--mailmap-file F` 应用另一个文件）。 |
| `reword <commit> -m <msg>` | 为当前分支上的某个 commit 设置新消息；其后代会被重新创建，索引和工作区不受影响。 |
| `amend <commit> [-m MSG \| --summary S \| --description D] [--author-name N] [--author-email E] [--author-date D] [--committer-name N] [--committer-email E] [--committer-date D]` | 修改 commit 属性中的任意一部分（规则和拒绝情形与 `reword` 相同；后代保留各自的作者）。日期格式为 `YYYY-MM-DD HH:MM:SS +HH:MM`、`YYYY-MM-DDTHH:MM:SS+HH:MM` 或原始的 `1700000000 +0100`。未指定的内容保持不变；除非有 `--committer-*` 选项另行指定，提交者是你，时间是现在。输出 `reword` 的结果 `{reworded, previous_head, new_head, replayed}`；一次 `undo` 即可还原。会被拒绝的情形：commit 不在当前分支上、有操作正在进行、消息为空、姓名或邮箱为空（或包含 `<`、`>` 或换行，或邮箱中有空格）、日期无效。 |
| `stash push [--message M] [--ai]`、`stash pop [ID]`、`stash apply [ID]`、`stash drop [ID]`、`stash list` | Stash（`ID` 是 `stash@{n}` 中的 `n`，默认为 0）。 |
| `stash from-commit <rev> [-m M]` | 把某个 commit（已丢失的也行；根 commit 相对于空，merge 相对于它的第一个父 commit）所做的更改保存为列表最上面的一个新 stash。工作区、索引和 HEAD 都不会被触碰。输出 `{stash, commit, from}`；一次 `undo` 会丢弃它，`redo` 会再次存入。 |
| `patch create -o <file> <revs>... \| --range A..B \| --wip [paths]` | 根据 commit、范围或工作区更改写出补丁。 |
| `patch apply <file>` | 把补丁应用到工作区。 |
| `apply-commit <rev>` | 只把某个 commit（已丢失的也行）所做的更改应用到工作区；索引和 HEAD 保持不变。要么全部成功，要么什么都不改：只要有文件无法干净地应用，就不会改动任何内容，命令失败（想保留这些更改请用 `stash from-commit`）。merge commit 会被拒绝。二进制文件和换行符与 commit 中一致。输出 `{files}`；一次 `undo` 会把文件恢复原状。 |
| `undo-forget [--dry-run] [--redo] [--expect ID] [--yes]` | 丢弃被阻塞的最新日志条目（已中断，或仓库已继续前进），使其下面的条目可以被撤销。绝不会触碰仓库。没有 `--yes` 时退出码为 3。 |
| `undo [--dry-run] [--list [--all]] [--expect ID] [--yes]`、`redo [--dry-run] [--expect ID] [--yes]` | 撤回 / 恢复上一次操作。退出码 2 表示被拒绝，3 表示需要 `--yes`。`undo --list` 还会逐个条目说明“仅恢复此项”能带回什么，以及是谁做的（`"source": "gitpoulpi"`；若是 shell 或 AI 代理用纯 git 做出的更改，则为 `"outside"`，由守护进程连同 git 记录的原因和提交者一起记下）。参见[撤销与重做](undo-redo.md)。 |
| `undo-restore <id> [--name N] [--dry-run]`（也可写作 `undo restore <id>`） | “仅恢复此项”：带回更早某个条目移除的内容（已删除的分支或 tag、已丢弃的 stash、已丢弃或已删除的文件、已移除的远程、ignore 行），而不撤销它之后的条目。绝不覆盖：已更改的文件旁会生成 `<name>.restored`；reset、amend 或 rebase 的结果会作为新分支回到旧的顶端。新增一个日志条目，所以 `undo` 可以撤回它。退出码 2 表示被拒绝（名称已被占用、没有可恢复的内容等）。 |
| `reflog [<ref>] [--skip N] [--limit N]` | `HEAD`（默认）或某个分支的 reflog 的一页，最新的在前，附带 git 记录的原因：在 shell 中做的移动也会显示。已删除的分支没有 reflog。 |
| `reflog-restore <ref> <oid> [--mode keep\|soft\|mixed\|hard] [--dry-run]`（也可写作 `reflog restore ...`） | 把分支或 `HEAD` 移到某个 reflog 位置。已检出且有未 commit 更改的分支需要 `--mode`。新增一个日志条目：`undo` 可以撤回。退出码 2 表示被拒绝。 |
| `lost-commits [--skip N] [--limit N] [--no-deep] [--budget-ms MS]` | 没有任何分支、tag、远程或 stash 能到达的 commit（已删除分支的 commit、旧的撤销固定点、游离对象），最新的在前。扫描到达时间预算就会停止，并给出 `partial`。 |

**分支与历史**

| 命令 | 作用 |
|---|---|
| `branch list`、`branch create <name> [at]`、`branch delete <name>`、`branch rename <old> <new>` | 本地分支。 |
| `branch track <remote/branch> [--name N]` | 创建一个跟踪远程分支的本地分支，并检出它。 |
| `branch delete-remote <name> [--remote R]` | 删除远程上的分支，保留本地分支。`undo --yes` 会把它原样 push 回去（[撤销](undo-redo.md#删除远程上的分支或标签)）。 |
| `branch set-upstream <branch> <remote/branch>`、`branch unset-upstream <branch>` | 上游。 |
| `branch upstream list [--branch B]`、`remote-group status [--branch B]` | 一个分支的远程（默认：当前分支）：它的主 upstream、额外的 push 目标和 pull 来源，输出为 `{remotes: {branch, primary, push_to, pull_from, missing}, targets: [{remote, branch, role, pull, tracking, relation, missing}]}`。`relation` 是 `up_to_date`、`{local_ahead: n}`、`{remote_ahead: n}`、`{diverged: {ahead, behind}}`、`absent` 或 `unrelated`，按远程跟踪引用的现状读取（不联网：请先 fetch）。 |
| `branch upstream add <remote>[:<dst>] [--pull] [--branch B]`、`branch upstream remove <remote> [--branch B]` | 添加或移除额外的 push 目标（`<dst>` 是该远程上的分支名，默认同名；`--pull` 同时将其设为 pull 来源）。`remove` 会移除所有指向该远程的目标和来源。它们会输出新的状态。一条可撤销的记录（`undo` 会恢复配置）。退出码 2 表示被拒绝：该远程已是主 upstream、不是目标，或 HEAD 已分离且没有 `--branch`。 |
| `branch upstream pull <remote>[:<dst>] --on\|--off [--branch B]` | 把一个远程开启或关闭为 pull 来源（之后普通的 pull 也会整合它）。输出新的状态。退出码相同。 |
| `branch upstream primary <remote/branch> [--branch B]` | 主 upstream：与 `branch set-upstream` 是同一个请求。 |
| `branch fast-forward <branch> [target]` | 仅当可以快进时才向前移动分支。 |
| `checkout <target> [--autostash]` | 切换分支，或在某个 commit 处分离。 |
| `merge <ref> [--ff \| --no-ff \| --ff-only \| --squash] [--autostash]` | merge 到当前分支。不带标志时由 fast-forward 设置决定（仓库自己的选择，否则 `git.merge_fast_forward`，默认 `never`：即使可以 fast-forward 也生成 merge commit）。`--ff` 可能时 fast-forward（git 的默认行为），`--no-ff` 始终生成 merge commit，`--ff-only` 只做 fast-forward，否则以 *cannot fast-forward* 失败且不改动任何内容；这些标志互斥。JSON 会说明实际发生的情况：`{"FastForwarded": oid}`、`{"Merged": oid}`（一个 merge commit）、`"UpToDate"` 或 `{"Conflicted": [paths]}`。一个 merge commit 或一次 fast-forward 是一条撤销条目。`--squash` 只暂存该分支的更改，不生成 commit（`merge --squash`）；之后需要再 `commit`。不可撤销：没有移动任何 ref。 |
| `rebase [onto] [--autostash]` | Rebase；进行中可使用 `--continue`、`--skip`、`--abort`、`--status`。 |
| `rebase <upstream> --interactive --plan <file\|->` | 根据 JSON 计划（`[{"commit", "action", "message"}]`，动作为 `pick`、`reword`、`squash`、`fixup`、`drop`、`edit`，或它们的单字母形式 `p`、`r`、`s`、`f`、`d`、`e`；不分大小写，和 rebase 待办列表一样）执行非交互式的“交互式”rebase；`--root`、`--onto-commit`、`--autosquash`。请根据 `rebase-plan` 构建计划。 |
| `cherry-pick <commits>...` 或 `cherry-pick --plan <file\|->` | 按顺序应用 commit（计划：`pick` / `drop` 步骤）。 |
| `revert <commit> [-m <parent>]` | 回退一个 commit。merge commit 需要 `--mainline <parent>`（`-m`），即保留的那个父 commit 的编号（从 1 起）：`1` 是创建该 merge 时所在的分支。 |
| `reset <target> --mode soft\|mixed\|hard` | 移动分支。 |
| `tag list [--unpushed]`、`tag create <name> [at] [-m M]`、`tag annotate <name> -m M` | Tag。`tag list` 会输出每个 tag 及其所在位置，信息来自上一次 fetch 或 tag push（从不访问网络）：`local`（本地有）、`remote`（拥有它的远程）、`differs_on`（持有它但指向其他 commit 的远程）以及 `where`：`local`、`remote`（某个远程有它而本仓库没有）、`both` 或 `differs`。 |
| `tag delete <name> [--local \| --remote R \| --both [--remote R]]` | 删除一个 tag：在本地（默认）、只在某个远程上（`git push R --delete`；会影响他人，且无法撤销），或同时在本地和拥有它的远程上。输出带有 `scope`（`local`、`remote`、`both`）；对于某个远程仍有的 tag 只在本地删除的情况，还有 `still_on`（下一次 `fetch` 会把它带回来）。同时删除时先删远程；之后 `undo` 只恢复本地 tag，`tag push` 可以把它放回去。 |
| `tag fetch <name> [--remote R]` | 从某个远程（默认是拥有它的那个）fetch 一个 tag，例如 `where: remote` 的 tag。绝不会覆盖指向其他 commit 的本地 tag。 |
| `tag push [names...] [--remote R]`、`tag delete-remote <name> [--remote R]` | 远程上的 tag（不给名称：push 所有尚无远程拥有的 tag）。在远程上删除 tag 是可以撤销的（`undo --yes`）。 |
| `worktree list`、`worktree add <path> <start> [-b BRANCH]` | 关联的 worktree。 |

|---|---|

**远程**

| 命令 | 作用 |
|---|---|
| `fetch [--remote R \| --all] [--prune] [--prune-tags]` | Fetch 默认远程、某个远程或全部远程。除非 `general.auto_prune` 为 false，否则远程已删除的远程跟踪分支会被清理；`--prune` 会强制清理。每次 fetch 还会刷新每个远程上的 tag 记录（`tag list` 的 `remote`），即使没有 `--prune` 也会清理这份记录。`--prune-tags`（设置：自动清理 tags）还会删除远程已经删除的本地 tag：只涉及曾存在于远程的 tag，绝不会动你没有 push 过的；输出会把它们列为 `pruned_tags`（git 2.41+）。 |
| `pull [--remote R] [--mode merge\|ff-only\|rebase] [--autostash]` | Pull；模式总是明确传给 git。 |
| `push [--remote R] [--branch B] [-u] [--force-with-lease]` | Push。没有单纯的 force：只有 `--force-with-lease`。 |
| `push --all-targets\|--to <remote>[:<dst>]... [--branch B] [--resolve REMOTE=push\|ff\|merge\|rebase\|force\|skip]... [--no-preflight] [--tags] [--yes]` | 把分支 push 到它的主 upstream 和每个额外的 push 目标（`--all-targets`），或恰好 push 到 `--to` 指定的远程（可重复，仅限这一次 push：不更改配置）。它先做计划（会询问各远程，见 `remote-group plan`）。当每个远程都是普通 push、已是最新或是前面某个远程的孪生时就执行；否则回答 `{"needs_resolution": {"plan": ...}}`，退出码 3，不改动任何内容，用 `--resolve` 回答它（远程可写成 `name` 或 `name:branch`；只能选计划为它允许的操作）。`force` 是带显式 lease 的 push，需要 `--yes`，否则回答 `{"needs_confirmation": {...}}`，退出码 3。结果是 `{run_id, branch, mode, status, local_tip, targets: [{remote, branch, action, status, detail, replaced, recovery}], pending, stopped, conflicts, message}`：`replaced` 是被 force push 覆盖的 commit，`recovery` 是把它恢复回来的命令。解决方案要求的 merge 和 rebase 先执行，然后 push 一次一个远程地进行；跨远程没有原子性。退出码 0 表示每个远程都已 push、已是最新或已跳过；4 表示某个远程失败、被拒绝、未知或未尝试，或 merge 或 rebase 因冲突而停止（`stopped`）；2 表示被拒绝（`remote_group_pending`：有已保存的运行在等待，`detached_head`，`checked_out_elsewhere`，`bad_resolve`，`action_not_allowed`）。当 `git.pull_mode` 为 rebase 时，已分叉的远程默认用 rebase 而不是 merge。不带这些标志时 `push` 保持不变。 |
| `pull --all-sources [--branch B] [--mode merge\|ff-only\|rebase] [--resolve REMOTE=ff\|merge\|rebase\|skip]... [--autostash] [--no-preflight]` | Pull 主 upstream 和每个 pull 来源（`branch upstream pull`），每个都按 `--mode` 整合。计划、`--resolve`、结果和退出码都与 `push --all-targets` 相同（需要的不止 fast-forward 或该 mode 自身整合的来源，以及 `--mode ff-only` 下的任何来源，都要 `--resolve`）。本地部分一条撤销记录。 |
| `remote-group plan [--branch B] [--to <remote>[:<dst>]...] [--pull] [--no-preflight]` | 分组 push（或 pull）会逐个远程做什么：`{branch, mode, local, targets: [{remote, branch, role, relation, ahead, behind, suggested, allowed, lease, conflicts, same_url_as, error, ...}]}`。会询问各远程（`ls-remote`，并 fetch 那些尖端未知的远程）；不改动任何内容。 |
| `remote-group continue [--run ID] [--resolve REMOTE=...]... [--yes] [--branch B]`、`remote-group abort [--run ID]`、`remote-group retry [--run ID]` | 此 worktree 已保存的运行（在因冲突而停止、取消或失败之后它会等待）。没有任何东西会自行恢复：merge 或 rebase 完成后，`continue` 会从新的尖端再次 push 到每个远程；当 rebase 让某个远程仍持有旧 commit 时，它会回答 `needs_resolution`（退出码 3），用 `--resolve`（force 时加 `--yes`）回答它。`abort` 会中止运行所启动的 merge 或 rebase 并丢弃它（已完成的 push 保持不变）。`retry` 会运行失败、在 push 途中被取消或从未尝试过的远程。`--run` 是调用方指的那次运行的 id（另一个前端可能已经替换了它）。结果和退出码相同；没有等待的内容或 merge 仍未结束时退出码为 2。 |
| `remote list`、`remote add <name> <url> [--push-url U]`、`remote remove <name>`、`remote rename <old> <new>` | 远程。`remote list` 会把没有对应远程的远程跟踪命名空间标为 `configured: false`；对它执行 `remote remove` 会删除其分支（可撤销）。 |

| `ai prompt --action <a>` | 按层级（`base`、`global`、`workspace`、`repository`、`task`）以及最终的 `system_prompt`，打印某个 AI 操作在此仓库中发送的系统提示。不调用任何模型；AI 关闭时也能用。工作空间是 `GITPOULPI_WORKSPACE` 指定的那个（若它包含该仓库），否则是第一个包含该仓库的。对于 `code_review`，还有一个 `review_context` 条目（不是一层：它在 diff 之前并入请求），说明评审除 diff 外还得到什么，以及实际生效的值。 |
| `ai review-context [--repo PATH \| --project HOST/PROJECT] [--run-in-repo profile\|yes\|no] [--claude-md on\|off] [--agents-md on\|off] [--context-file PATH\|URL] [--no-context-file] [--no-extra-file [on\|off]] [--reset]` | 显示或设置代码评审草稿除 diff 外还会得到什么（`[ai.review]`，见 [AI > 评审上下文](ai.md#评审上下文)）。`--repo` 和 `--project` 都不给时是全局默认值；`--repo`（全局标志）是某个克隆自己的值，`--project github.com/owner/name` 是未克隆仓库的值（`remote-reviews.toml`）。不带设置标志时只显示；带设置标志时保存并输出。JSON：`scope`（`global`、`repository`、`project`）、`target`、`global`、`own`（仅仓库或项目设置过的字段）、`effective`（评审实际得到的）、`changed`。`--reset` 会忘掉仓库或项目自己的值。`--run-in-repo` 不适用于 `--project`。`--no-extra-file`（单独给出或 `on`）让仓库或项目不使用额外文件，不论全局文件是什么；`off` 让它重新沿用全局文件；它需要 `--repo` 或 `--project`，与 `--context-file` 互斥，此时 `own` 会显示 `"no_extra_file": true`。不需要模型；AI 关闭时也能用。 |
| `ai trust <profile> [--accept-origin URL] [--accept-certificate SHA256] [--allow-insecure-http on\|off]` | 把配置文件的 API 密钥绑定到它被存入时的地址（见 [AI > 密钥去向](ai.md#密钥去向)）。不带选项时输出 `{profile, current_origin, trusted}`；`--accept-origin` 在基础 URL 更改之后接受该配置文件当前的基础 URL（拼写与拒绝信息打印的一致），`--accept-certificate` 按 SHA-256 密钥指纹固定自托管服务器的证书，`--allow-insecure-http` 允许不在本机上的纯 `http://` 基础 URL。只有人才会运行它：不是 MCP 工具。AI 关闭时也能使用。 |

另外还有 `commit --ai [--send-all]` 和 `stash push --ai [--send-all]`（`--send-all` 和 `truncated` 与 `ai` 相同；`hosting review suggest` 也接受 `--send-all`）。模型由 `gitpoulpi` 进程调用，因此 API 密钥绝不会传给守护进程或 MCP 客户端。

### 工作空间与搜索

**工作空间**是有名称的仓库分组，可附带默认的提交配置文件。它保存在 `config.toml` 旁的 `workspaces.toml` 中，由所有会话和窗口共用，因此 `workspace` 命令不会启动守护进程（只有 `add` 和 `create --add` 会为每个仓库向守护进程询问其 `origin` URL）。一个仓库可以属于多个工作空间。路径的比较方式与收藏和最近使用列表相同。

| 命令 | 作用 |
|---|---|
| `workspace list`、`workspace show <id>` | `{workspaces: [...]}` / `{workspace}`：`id`（一个 slug，重命名后保持不变）、`name`、`color`、`description`、`profile`、`profile_exists`，以及 `repos: [{path, exists, remote}]`（`remote` 是添加仓库时记录的 `origin` URL，已去除凭据）。 |
| `workspace create <name> [--add PATH]... [--profile ID] [--color C] [--description T]` | 创建工作空间并输出它；两个工作空间不能同名。`--add` 可重复，它不是 `--repo`（后者指定命令在哪个仓库中运行）。 |
| `workspace rename <id> <name>`、`workspace delete <id>` | 重命名会保留 id。删除绝不会动仓库。 |
| `workspace add <id> <path>...`、`workspace remove <id> <path>...` | `add` 会记录每个仓库的根目录和 `origin` URL（不存在或不在仓库内的路径会被拒绝并给出提示，且不保存任何内容：只有之后才消失的仓库会保留在列表中并标为缺失）；`remove` 也接受已从磁盘上消失的仓库的路径。 |
| `workspace set-profile <id> <profile>` / `--none` | 在该工作空间的仓库中提交时所用的 `[[profiles]]` id。不对应任何配置文件的 id 会被保存（`profile_exists: false`），但不会生效。 |
| `workspace set-ai-instructions <id> [--action <a>] [--mode append\|replace] (--text T \| --clear)` | 工作空间的 AI 指令，适用于所有操作或某一个操作（`commit_message`、`code_review` 等）。`append` 把它们追加在全局指令之后，`replace` 则改用它们。它们适用于该工作空间的每个仓库，排在仓库自己的指令之前。`workspace show` 会把它们输出为 `ai_instructions`。 |
| `commit -m M [--workspace ID]` | 当仓库在该工作空间中且配置文件存在时，以该工作空间的配置文件提交；否则用 `general.active_profile`；再否则用仓库自己的身份。不带 `--workspace`（或 `GITPOULPI_WORKSPACE`）时一切照旧：提交绝不会根据成员关系猜测工作空间，因为一个仓库可以属于多个。未知的 id 会报错。 |
| `search <query> [--workspace ID] [--kind K]... [--limit N]` | 对当前仓库（或某个工作空间中所有仓库）的分支（本地和远程）、tag、worktree、stash、commit 消息，以及托管平台缓存中的 pull/merge request 和议题做模糊搜索（`GITPOULPI_WORKSPACE` 可代替该选项）。窗口中的版本见[搜索](search.md)。 |

`search` 的答复是 `{query, workspace, hits, partial, repos}`。每条命中是 `{kind, label, detail, target, score, positions, repo}`：`kind` 为 `branch`、`tag`、`commit`、`stash`、`worktree`、`repo`、`pull_request` 或 `issue`；`positions` 是 `label` 中要高亮的匹配字符；`target` 说明去向（`{type: "ref", name}`，带完整的引用名；`{type: "commit", id}`；`{type: "stash", index, id}`；`{type: "worktree", path}`；`{type: "repo", path}`；`{type: "pull_request", number}`；`{type: "issue", number}`）；各仓库的命中按 `score` 合并，最佳在前。匹配方式与命令面板相同：查询原样匹配，然后是原样出现在任意位置，最后是其字符按顺序出现（更靠前、更短的优先）。只有当 commit 的标题不匹配且查询有三个或更多字符时，才会搜索它的正文。前缀会缩小搜索范围，且不属于文本：`b:` 分支，`t:` tag，`c:` commit，`s:` stash，`w:` worktree，`r:` 仓库（仅限工作空间），`pr:`（或 `mr:`）pull/merge request，`i:` 议题，`#` 是后两者；`--kind`（可重复，名称相同）也能筛选。当某个仓库的 commit 在 [`search.commit_limit`](config-reference.md#search工作空间搜索) 处被截断时，`partial` 为 true；`repos` 说明每个仓库是否被搜索（未搜索时有 `reason`：已从磁盘上消失的路径会被报告，但绝不致命）。一次性命令会先建立每个仓库的索引；同一会话中开着窗口时，守护进程已经预热好了索引。Pull/merge request 和议题读取自每个仓库的托管平台缓存（窗口保存在 `.gitpoulpi/hosting-cache.json` 中的文件），绝不会向平台请求：窗口从未加载过它们的仓库就没有可找的内容，缺失或写了一半的缓存只是没有命中。

| `ui show conflict <path> [--conflict N]` | 在有冲突的文件上打开 merge 编辑器，定位到第 N 个冲突（不会选择或保存任何内容）。 |
| `ui propose reword <rev> -m M`、`ui propose commit-message <summary> [--body B]`、`ui propose branch <name> [--start-point R]`、`ui propose tag <name> [--target R] [-m M]` | 打开一个已预填的对话框供你确认（需要 `[mcp] allow_ui_propose = true`）。 |

| `ui propose split <rev> --plan <file\|->` | 在某个 commit 上打开拆分编辑器，并填入一份计划（即 `split-commit --plan` 的 JSON）供你审阅、修改和应用；在你操作之前不会拆分任何内容。与其他提议的限制相同。 |
| `ui propose resolution <path> (--pick 1=a,2=ba,... [--default a\|b] \| --content-file F)` | 打开已选好解决方案（或整个文件文本）的 merge 编辑器供你审阅；你的“保存并标记为已解决”是唯一的确认。与其他提议的限制相同。 |

退出码：0 表示已应用，3 表示交由用户决定，其他情况为 1。详情以及窗口遵循的规则：[MCP 与代理](mcp-and-agents.md#向用户展示内容)。

## 说明

- **会话。** `gitpoulpi session list` 显示每个会话及其 `live` / `stale`（通过连接其端口来判断）。推导出的名称为 `<folder>-<hash of the path>`。
- **没有交互式提示。** 不会询问任何问题：有风险的操作要么需要一个标志（`--yes`、`--force-with-lease`），要么被拒绝并给出原因。
- **CLI 中没有的功能**：`checkout --file`（恢复单个文件）只在窗口中提供。
