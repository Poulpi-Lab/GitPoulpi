# 评审 pull request 或 merge request

评审一个 pull request（GitHub、Gitea、Forgejo）、merge request（GitLab）或 Gerrit 变更（见 [Gerrit](#gerrit)），
**无需离开仓库所在的窗口**。评审视图显示描述、对话、更改的文件（评论讨论就在对应行下方）和 commit，你也在这里写评审：
评论、批准和请求更改。它需要其中某个平台的配置文件（见[托管平台与议题跟踪器](hosting-integration.md)）
以及已关联到它的仓库；其他提供方不支持评审。平台的限制会得到遵守：GitLab 没有“请求更改”结论，且每条评论只能针对一行。
本页把它们统称为*请求*。

![评审视图的“概览”页：请求的标题栏及其元数据按钮、描述，以及带有一条已提交批准的对话](../images/review-overview.png)

![“文件”页：更改的文件及其已查看复选框、行下方带评论讨论的 diff，以及所示行之外的一个已解决讨论](../images/review-files.png)

## 打开评审

所有入口都通向同一个视图：

- 侧栏的 **PULL REQUESTS** 列表：选中一行按 **Enter**，或右键点击它并选择**评审…**；
- **Radar**：该行的菜单中的**评审…**，或按 `e` 键（会打开仓库并同时打开评审；未克隆仓库的请求会询问是克隆它，还是通过 API 评审，
  见[无需克隆的评审](#无需克隆的评审)）；
- **工作空间搜索**（`Ctrl+Alt+F`）：高亮一个 pull 或 merge request，按 **`Alt+R`**；
- 命令面板：**托管：评审请求…** 会列出可供选择的请求。

该视图铺满窗口、盖在仓库之上（它是仓库标签页的一种模式，不是单独的窗口）。
按 **`Esc`** 或点击右上角的 `✕` 离开。打开时，请求从托管平台读取，其代码在后台用 git 获取；如果耗时超过片刻，会出现一个旋转指示符。

## 标题栏

始终可见：编号和标题、状态（打开、草稿、已合并、已关闭）、分支（`main ← feature/moons`）、作者、检查（`✓ 检查已通过`、
`✗ 检查未通过`、`● 检查运行中`）、能否干净地合并或有冲突、大小，以及写了评论之后出现的 **`3 条待处理评论`**。

四个元数据按钮 - **指派人**、**评审者**、**标签**、**里程碑** - 打开与侧栏相同的选择器（见
[指派人、评审者、标签和里程碑](hosting-integration.md#指派人评审者标签和里程碑)）；平台一接受，标题栏就显示结果。
操作按钮：**检出**（对请求的分支执行通常的检出，同时关闭视图）、**在浏览器中打开**、**刷新**（**`F5`**）和**完成评审**。

## 三个页面

顶部边框中的分段控件用来切换页面：**概览**、**文件**、**Commits**（**`Alt+1`**、**`Alt+2`**、**`Alt+3`**，或点击）。

### 概览

先是描述（基本的 Markdown 会按其含义显示：粗体、斜体、`代码`、链接显示为其文字、项目符号和编号列表、标题、引用和代码块），
然后是对话：不针对代码的评论和已提交的评审，最早的在前，每条带有其结论（`已批准`、`请求更改`、`已评论`、`已驳回`）。
在 GitLab 上，结论就是它的批准。其下是回复框：点击它或按 **`c`** 对对话写评论。**这条评论会立即发布**，回复框里也这么说明。

### 文件

左侧是更改的文件（状态字母、`+新增 -删除`、未解决讨论数 `●n`、你的待处理评论数 `✎n`），右侧是所选文件的 diff。
diff 来自 git：请求的 head 被获取到 `refs/gitpoulpi/pr/<n>`（绝不是分支，也不检出任何内容），并与 merge base 比较，
所以边栏中的行号正是评论所用的行号。

- **文件前的 `[ ]`**：把它标记为*已查看*（点击，或在列表上按 **`v`** / `Space`）。标题会统计数量。
  已查看标记按仓库保存，重启后仍在。
- **讨论**就在其所在行的正下方：第一条评论、回复，以及按钮**回复**和**解决** / **重新打开**。已解决的讨论折叠为一行；
  **`z`**（或在其上按 `Enter`，或点击 `▾`）可折叠和展开任意讨论。
- **已过时的讨论**，以及针对 diff 未显示的行的讨论，会列在 hunk 之后的*所示行之外的评论*下；
  当代码在其下方发生变化时，带有 `已过时` 徽标。
- **`c`** 对光标所在行评论（行首的小 `+` 用鼠标可做同样的事）。**`Shift+Up` / `Shift+Down`**（或在行上拖动）可先选择多行，
  评论会覆盖这个范围。GitLab 每条评论只能针对一行，视图会如此提示，而不是去选择。
- **`r`** 回复光标处的讨论，**`x`** 解决它或重新打开它。两者都会**立即**发送到平台。
- 按键：`Up` / `Down` / `PgUp` / `PgDn` / `Home` / `End` 移动；`Tab`、`Right` 和 `Enter` 从文件列表进入 diff，
  `Left` 和 `Tab` 返回；`]` 和 `[` 跳到下一个和上一个文件。

### diff 的显示选项

**文件**页和 **Commits** 页的 diff 窗格就是 [Diff 视图](staging-and-committing.md)自己的窗格，第一行有同样的栏，
记住的选择也相同（它们是同一项设置：你在这里选的，就是 Diff 视图打开时用的，反过来也一样）：

- **内联 / 分栏**：一列，或前后并排。在分栏中，讨论、待处理评论或建议位于它所属的那一半之下：针对已删除行的评论在左半部分之下，
  针对新增行或未改动行的评论在右半部分之下。在既有删除又有新增的行上按 **`c`** 之前，请先点击你指的那一半；键盘则对新的一侧评论。
- **Hunks**：只显示更改及其上下文，或显示整个文件并在原位标出更改。在整个文件中，位于更改之外的行上的讨论会放在其所在行之下，
  而不是放进*所示行之外的评论*。文件文本在后台读取；在它到达之前，hunk 仍显示在屏幕上，并有一行文字说明（在 Commits 页上，
  一个 commit 最多有 40 个文件以这种方式读取）。
- **WS**：显示或忽略仅空白字符不同的更改。
- **Wrap**：对长行换行。
- **上 / 下箭头**：上一个和下一个 hunk。
- **Map**（**`M`**）：滚动条旁的缩略图，与 Diff 视图共用一项设置。点击或拖动它可滚动。
- **Auto**（**`E`**，或*评审：选择编码…*）：读取文件所用的编码，与 Diff 视图相同：自动检测，或列表中的某个编码，
  为窗格显示的文件选择（在 Commits 页上，是光标所在的文件）。文件的两侧会在后台用该编码重新读取，
  这个选择与 Diff 视图中同一路径共享。无法用该方式读取的文件会在其 diff 上方说明原因。
- **`⋯`**：当窗格太窄放不下所有按钮时，放不下的按钮收在栏末尾的 `⋯` 后面；它的列表会像点击一样运行每一项。它们的按键和面板行照常可用。

滚动条的标尺显示各项所在的位置：更改（仅整个文件，与 Diff 视图相同）、每个讨论、待处理评论和建议各一个圆点 `●`，以及光标。

长行会在窗格边缘被截断（开启 **Wrap** 可看到全部），并可横向滚动：在 diff 上按 **`Right`** 和 **`Left`**（在最左边按 `Left` 会回到文件列表）、
横向滚轮或 `Shift` 加滚轮、底部边框上的滚动条，或*评审：向左 / 向右滚动 diff*。

### 选择文本和行

拖动从哪里开始，决定它选择什么。从**代码中**开始的拖动选择文本，与 Diff 视图相同（双击选择一个词）；
**`Ctrl+C`**（或*评审：复制所选文本或行*）精确复制这些字符，不带行号和标记；没有文本选择时，复制光标所在的行。
从**边栏中**（行号、标记、`+`）开始的拖动选择行，用于像以前一样对它们评论；在边栏中双击仍会对该行开始评论。

Diff 视图的 `n`、`p`、`m`、`w`、`s` 键是评审自己的，所以评审中的开关用大写字母：**`V`** 布局、**`H`** hunk 或整个文件、
**`S`** 空白字符、**`W`** 换行、**`J`** / **`K`** 下一个和上一个 hunk、**`E`** 编码、**`M`** 缩略图。每一项都有面板行
（*评审：切换内联 / 分栏布局*，……）。

### Commits

仅包含请求的 commit（不含其背后的历史），最新的在前，以及所选 commit 的 diff（相对其父 commit 的更改），
它的所有文件依次排列，显示选项相同。

## 写评审

针对代码的评论是**待处理**的：它保存在你的机器上（在仓库的状态文件里，所以重启后仍在），并计入标题栏。
在你完成评审之前不会发送任何内容。待处理评论显示在其所在行之下，带有徽标 `待处理 - 第 12 行` 和两个按钮：**`e`**（编辑）和 **`d`**（删除）。

**完成评审**（**`f`**、按钮或面板）会打开一个小表单：一个摘要（可选）和一个**结论**列表：*评论*、*批准*、*请求更改*。
只列出平台允许的结论：GitLab 没有*请求更改*。**提交评审**（`Ctrl+S`）把摘要、结论和每条待处理评论一次性发送。
**放弃评审…** 在确认之后丢掉待处理评论。

不等评审而立即发送的有：回复、解决和重新打开，以及对对话的评论。评论框会说明它属于哪一种
（*此评论会立即发布*或*此评论会先加入你的待处理评审*）。如果平台拒绝了回复，评论框会带着你写的内容重新打开。

如果在你写下待处理评论之后请求有了新的 commit，视图会警告说它们所在的行可能已经移动
（GitHub 和 GitLab 把评论放在你读到的那个 commit 上；针对较旧 head 的评审会被拒绝）。

## Gerrit

Gerrit 服务器的连接方式与其他平台相同（见[托管平台与议题跟踪器](hosting-integration.md)：服务器 URL、用户名、HTTP 密码），
并在 **PULL REQUESTS** 下关联到一个*项目*。它的变更按 pull request 列出（`#7`，标记 `GR`），并在同一个视图中评审，只是有 Gerrit 带来的差异：

- **补丁集。**一个变更有编号的补丁集（每次上传该 commit 就是一个）。标题栏在顶部边框、页面标签旁有一个 **`补丁集 N`** 组合框
  （**`P`**，或面板行*评审：选择补丁集…*）。它从最新的开始；选择另一个会读取该补丁集的文件和代码，
  写在其他补丁集上的讨论会列为*已过时*。你完成的评审会发送到当前显示的补丁集。
- **与另一个补丁集比较。**它左边还有第二个组合框 **`比较：基础`**（**`D`**，或*评审：比较补丁集…*），列出基础以及比当前显示的补丁集更早的每个补丁集。显示补丁集 3 时选择补丁集 1，文件页就只列出（并只比较）补丁集 3 自补丁集 1 以来改动的内容（用的是服务器自己的差异，所以 rebase 到更新的目标上不会显示成更改）；Commits 页显示的就是这一个差异。两个补丁集会分别被获取到 `refs/gitpoulpi/pr/<n>` 和 `refs/gitpoulpi/pr/<n>-ps<k>`。写在当前显示的补丁集以外的补丁集上的讨论为*已过时*。如果选择阅读的补丁集比正在比较的更早，比较会重置为基础。CLI 对应的是 `review show|fetch --compare-with K`。
- **合入与放弃。**当服务器表明该变更可以合入（所需的投票和检查都已具备）时，标题栏的按钮中会多出一个**合入**按钮；只要你可以放弃该变更，就有**放弃**按钮。两者（按键 **`U`** 和 **`Q`**，面板*评审：合入变更…* / *评审：放弃变更…*）都会先询问，弹窗会说明该操作发生在服务器上，**无法从 GitPoulpi 撤销**（已合入的变更保持已合入；已放弃的变更可以在 Gerrit 网页界面中恢复）。拒绝则不会发送任何内容；成功后视图会重新读取该变更。CLI 对应的是 `gitpoulpi hosting review submit-change <n>` 和 `hosting review abandon <n> [--message M]`。
- **用投票代替结论。****完成评审**会为你可以投票的每个标签显示一个组合框 - `Code-Review`（-2 到 +2）和项目中有的 `Verified` -
  只列出服务器**对此变更和你**允许的值（没有权限的开发者无法选 +2）。它从你当前的投票开始；只发送你改过的投票。
  摘要和待处理评论在同一次调用中发送。你在 Gerrit 网页界面中保存的草稿会随评审一起发布。
- **讨论**就是 Gerrit 的评论链。当其最新评论带有 `unresolved: false` 时，讨论即为已解决；
  **解决**会发布一条回复 `Done` 来做到这一点，**重新打开**则发布回复 `Reopened`。回复和解决会立即发送到服务器，与其他平台相同。
- **推送以供评审。**向 `refs/for/<branch>` 推送时 Gerrit 会创建变更。当 PULL REQUESTS 区域关联到某个 Gerrit 项目时，
  该区域的 **`+`** 按钮和面板行**托管：push 以供评审…**会询问目标分支，并把 `HEAD` 推送到 `refs/for/<branch>`
  （主题可在命令行给出）。这次 push 无法从 GitPoulpi 撤销（请在 Gerrit 中放弃该变更）；消息里会这么说明。
  对应的 CLI 命令是 `gitpoulpi hosting review push`。
- 元数据按钮对 Gerrit 是只读的（会显示评审者），没有*请求更改*结论（-1 或 -2 的投票就是同一回事），检查标记就是 `Verified` 标签。

## ✦ AI 评审草稿

![文件页中两条 ✦ 建议位于各自的行之下，各有接受、编辑和忽略，旁边是一个已有的讨论](../images/review-ai.png)

开启 AI 后（*设置 > AI*，见 [AI 辅助](ai.md)），标题栏有一个 **`✦ 起草评审…`** 按钮（也可按 **`s`**，以及面板行*评审：✦ 起草评审…*）。
它会打开[评审选项](#评审选项)，在其中按 **`Enter`** 才会询问模型。这是唯一会询问模型的操作：打开评审从不会。
模型读取请求的标题和描述、已有的评论（以免重复）和 diff，并给出一份**评审草稿**：要提交的文本、它建议的结论（批准、请求更改或评论）、
一份总体摘要和一组建议的评论。过长的 diff 会为模型截短 - 按文件，也按总量 - 概览会说明有多少个文件被截短或略去。
它工作时，状态栏稍后会显示一个旋转指示符，按 **`Esc`**（或再按同一个按钮）可取消。
[四个层级](ai.md#指令)的*代码评审*指令都会生效，所以团队或工作空间可以说明什么是好的评审。

### 评审选项

`s` 打开 **✦ 评审选项**对话框，其中填入该仓库的默认值（仓库没有设置的项使用全局值）。**`Enter`**（或**运行**按钮）按对话框当前显示的内容开始运行；
`Esc`、**取消**或叉号会关闭它，且不会询问任何东西。

| 控件 | 作用 |
|---|---|
| **在仓库中运行代理** | *按配置设置*（由 AI 配置的工作文件夹决定）、*是*或*否*。对 HTTP 配置（它没有工作文件夹）以及无克隆、通过 API 评审的请求，该项变灰，原因写在其下方。 |
| **CLAUDE.md**、**AGENTS.md** | 将仓库的该文件提供给模型，从请求所针对的分支读取。代理在仓库中运行时会自行读取它们，对话框会这样说明。 |
| **额外文件** | 再多一个文件：仓库中的路径、绝对路径，或指向代码托管平台上某文件的链接。**浏览…**（`Ctrl+B`，或在按钮上按 `Enter`）会打开文件选择器，从仓库根目录（或已填文件的旁边）开始；仓库内的文件写成相对于根目录的路径，仓库外的写成绝对路径。在字段中输入的方式照旧。 |
| **无额外文件** | 本次运行不使用额外文件，即使全局设置或仓库指定了一个；输入文件或用**浏览…**选一个会取消勾选。配合**保存为此仓库的默认值**，它会成为仓库的*无额外文件*开关。此处空字段视为没有，因为对话框从本次运行将继承的值开始。 |
| **保存为此仓库的默认值** | 同时为之后的评审保留这些值：保存在仓库的状态文件中，未克隆的仓库则保存在 `remote-reviews.toml` 中。只保留与全局值不同的值，其余的继续跟随*设置 > AI*。 |

所有控件都可用 `Tab` 到达，`Space` 切换复选框，路径字段是普通的文本字段。同样的四项设置也在*设置 > AI*（*代码评审*）和*仓库专属：AI*中；
见[评审上下文](ai.md#评审上下文)。未能提供给模型的内容（缺失或无法读取的额外文件）以及为符合限制而被截短的文件，都会列在草稿卡片上。

建议**不是评论**。它们显示在两个地方：

- **文件页中它们各自的行之下**，作为标有 `✦` 的幽灵评论，带有严重程度（`提示`、`警告`、`问题`）和三个按钮：**接受**、**编辑**和**忽略**。
  针对 diff 未显示的行的建议会被保留，绝不丢弃：它列在 hunk 之后的 *AI 对整个文件的建议*之下，接受之后会落在文件的第一个更改行上，
  前面带有文字*（关于第 N 行）*。
- **在概览中**，描述之下：摘要，然后是带有同样按钮以及**全部接受** / **全部忽略**的列表。

**接受**（`y`）把建议变成普通的**待处理评论**（你仍可编辑或删除它）；**编辑**（`w`）打开评论框，模型的话在前，接受你留下的内容；
**忽略**（`n`）丢弃它。**全部接受**（`A`）也只是填充待处理列表。在文件页上，这些键作用于光标处的建议，在概览上作用于列表中的第一条。
**使用 AI 摘要**（`i`，或完成评审表单中的按钮）会把模型的摘要放入评审文本；它绝不会自行插入。
**在你提交评审之前，不会向平台发送任何内容。**

概览在建议之上以一张卡片显示草稿：结论标记、评审文本和三个按钮。

- **✦ 使用草稿…**（`u`）把每条未处理的建议都接受为待处理评论，并打开*完成评审*，其中已填好草稿的文本和结论。你仍需自己阅读、修改并提交；
  取消该表单会保留草稿。平台的限制仍然有效：GitLab 没有*请求更改*，表单会这样说明并退回为*评论*；在 Gerrit 上，结论会变成 +1 或 -1 的 Code-Review 投票，
  但仅当服务器允许你投该值时（否则不设置投票，表单会这样说明）。
- **编辑文本…**（`t`）在你使用草稿之前修改其评审文本。
- **丢弃草稿**（`N`）丢弃文本、结论和剩余的建议。

草稿按请求保存，所以关闭再重新打开评审时它仍在。如果自模型写下草稿后请求的 head 已经移动，卡片会显示*自写下此草稿以来，请求已发生变化。*
提交评审会用掉草稿。

## 无需克隆的评审

位于你机器上没有的仓库中的请求也可以评审。在 Radar 中，该行上的**评审**（`e`）会询问怎么做（见 [Radar](radar.md#评审请求)）；
**通过 API 评审**会在主页窗口、盖在 Radar 之上打开同一个视图。本页的一切都一样可用，区别如下：

- 代码（更改的文件、每个文件的 diff、请求的 commit、某个 commit 的 diff、整个文件）从托管平台的 API 读取，所以第一次查看大型请求会稍等片刻；
  托管平台不提供 diff 的文件（二进制或非常大的）会说明这一点，而不是显示 diff。
- 你的待处理评论保存在配置文件夹的 `remote-reviews.toml` 中，按托管平台和项目（`host/project`）归档，而不是保存在仓库自己的状态里。
  关闭再重新打开评审时它们仍在，发送评审会用掉它们。
- 没有编码选择（*没有克隆时不可用*），也没有**检出**（它会提示先克隆仓库）。
- `Esc` 或角落的 `✕` 会离开该视图并把 Radar 还给你。命令面板（`Ctrl+P`）可以像在仓库标签页中那样使用该视图的行。

若想保留克隆，请选择**克隆，然后评审**（或面板的 *Radar：克隆并评审…*）：克隆对话框会在该请求所属的已连接账户上打开，并选中其仓库，克隆完成后，评审会在新仓库的标签页中打开。

## 通过命令行和供代理使用

同样的评审也可通过 `gitpoulpi hosting review show|threads|comment|reply|resolve|submit|fetch|suggest` 使用
（以及由它们生成的 MCP 工具）：见 [CLI 参考](cli-reference.md)。`threads` 还会列出已提交的结论（`reviews`）。
`suggest <n>` 会询问模型（需开启 AI），并以 JSON 输出它的 `verdict`、`body`、摘要和建议而不发布任何内容，
这样脚本或代理就可以挑选要传给 `submit --comment` 的评论。

这一切都不需要克隆：`--project owner/name`（配置了多个集成时加 `--id`）可对当前目录一无所知的项目运行 `show`、`threads`、`comment`、`reply`、
`resolve`、`submit` 和 `suggest`。`hosting review diff <n>` 输出带 hunk 的 diff（`--api` 即使在克隆内也从托管平台读取），
`hosting file <path> --project P [--ref R]` 读取某个修订下的文件，例如项目的 `CLAUDE.md`。两者都读取托管平台的 API：GitHub、GitLab、Gitea、Forgejo 和 Gerrit。
